# 资深前端简历指南

这份指南面向国内中高级技术岗位。目标不是堆砌技术名词，而是让招聘方快速判断：你解决过什么复杂问题、为什么这样决策、结果如何验证，以及能否在新团队复现。

## 先确定投递定位

同一段经历可以支持不同岗位，但每个投递版本只能有一个主定位。

### Senior Frontend

- **核心判断：** 能否独立负责复杂前端系统，从需求澄清、方案设计到上线治理形成闭环。
- **重点证据：** Vue 3 / TypeScript 深度、性能与稳定性、多端一致性、工程化效率、复杂业务抽象。
- **少写：** 只体现排期、汇报和人员协调，缺少亲自解决技术问题的内容。

### Tech Lead

- **核心判断：** 能否在不确定性中做技术取舍，并通过机制放大团队交付能力。
- **重点证据：** 架构演进、跨团队协同、质量门禁、技术债治理、人才培养、业务风险控制。
- **少写：** “带领团队完成项目”这类没有决策、机制和结果的管理口号。

### 全栈偏前

- **核心判断：** 以前端为主责，能否跨越接口、数据和部署边界推进完整交付。
- **重点证据：** 与 Java Spring Boot 或 NestJS 的接口协作、鉴权、异常模型、联调效率、可观测性。
- **少写：** 把会调用接口包装成全栈，或把浅尝辄止的后端技术写成精通。

## 建立一条可证明的叙事链

简历从上到下应回答同一个问题：为什么你适合这个岗位？

1. **一句话定位：** `[年限/阶段] + [主技术方向] + [业务或复杂度] + [目标岗位]`。
2. **核心优势：** 选择 3～5 项与职位描述最相关、能被经历证明的能力。
3. **技术能力：** 按“熟练解决的问题”组织，不按技术词典罗列。
4. **工作经历：** 说明职责边界、关键贡献和团队影响，避免日常任务流水账。
5. **代表项目：** 用背景、难点、决策、行动、结果、复盘还原真实问题解决过程。

示例结构：

> `[X] 年前端经验，长期负责 [业务/系统类型]，擅长以 Vue 3 + TypeScript 推进 [复杂问题]，具备 [架构/多端/团队协作] 经验，目标岗位为 [Senior Frontend / Tech Lead / 全栈偏前]。`

每个占位符都必须替换为真实信息；无法在面试中展开的内容不要写。

## 把“做过”改成“证明过”

高质量要点通常包含以下证据中的 3～5 类。

### 复杂度

说明问题为什么难，而不是只说项目“大”。

- 业务复杂度：角色、流程、状态、权限或合规约束。
- 技术复杂度：多端差异、历史包袱、依赖冲突、性能瓶颈或发布风险。
- 协作复杂度：跨团队、跨语言栈、多供应商或异地协作。

### 结果

优先使用可复核结果：

- 监控平台、构建日志、缺陷系统、工单记录、发布记录；
- 用户调研、业务看板或研发效能平台；
- 明确时间窗内的前后对比。

指标必须写清采集口径。例如：“以 `[监控平台]` 的线上真实用户数据统计，`[时间窗]` 内 P75 LCP 从 `[基线]` 降至 `[结果]`。”没有可靠数据时，写可观察的定性结果，不补造数字。

### 取舍

写明为何选择方案 A，而不是 B：

- 当前约束是什么；
- 比较了哪些方案；
- 接受了什么成本或风险；
- 如何设置回滚、灰度或后续演进路径。

### 团队影响

区分个人完成与组织影响：

- 个人：设计、编码、排障、上线；
- 协作：推动产品、后端、测试达成共识；
- 机制：沉淀规范、脚手架、质量门禁或复盘制度；
- 影响范围：仅写可确认的团队、项目或使用者范围。

### 业务理解

不要停在“按需求开发”。说明技术工作如何影响转化、履约、运营效率、风险或成本，并避免公开客户名称、交易金额等敏感数据。

## 两页简历的内容优先级

中高级岗位优先控制在 2 页；不是越短越好，而是让证据密度足够高。

### 第 1 页

1. 姓名、联系方式、目标岗位与所在城市；
2. 一句话职业定位；
3. 3～5 项核心优势；
4. 与目标岗位最相关的技术能力；
5. 最近一段工作经历及最有说服力的项目。

### 第 2 页

1. 其余相关经历与代表项目；
2. 教育经历；
3. 有明确影响力的开源、分享或认证；
4. 必要的补充说明。

超过 2 页时，优先删除早期重复经历、过时技术、无结果的职责和与职位描述无关的内容。不要缩小字号或压缩行距来塞满页面。

## 常见失真方式

- **空话：** “责任心强”“技术基础扎实”没有证据。
- **职责流水：** “负责页面开发、接口联调、上线维护”无法区分水平。
- **敏感数据：** 客户名、内部系统地址、未公开营收和安全细节不应出现。
- **不可证指标：** “效率提升 80%”若无基线、口径和时间窗，应删除或改成可核验描述。
- **概念冒进：** 参与过微前端项目不等于主导架构，使用 AI 工具不等于建设 AI 工程体系。
- **关键词堆砌：** 技术名词必须能在项目中找到落点，并能回答原理、取舍和故障案例。

## 版本化投递

建立一份事实母版，再按岗位生成投递版本。

建议命名：

```text
姓名-SeniorFrontend-公司简称-YYYYMM.pdf
姓名-TechLead-公司简称-YYYYMM.pdf
姓名-全栈偏前-公司简称-YYYYMM.pdf
```

每个版本只调整排序、措辞和证据重点，不改变事实。保存职位描述、投递日期、简历版本和项目证据来源，便于面试前回看。

## 保持面试口径一致

简历中的每条强结论都应准备以下回答：

- 当时的背景、约束和你的职责边界；
- 备选方案及选择理由；
- 关键行动中哪些由你亲自完成；
- 指标来源、基线、时间窗和干扰因素；
- 失败、遗留问题与后续复盘。

无法一致回答时，降低措辞强度。例如把“主导”改成“参与方案设计并负责 `[范围]`”，比夸大更可靠。

## 发布前自检

- [ ] 主定位唯一，标题和前三项优势与目标岗位一致。
- [ ] 每项优势都能在工作或项目中找到证据。
- [ ] 项目体现复杂度、结果、取舍、团队影响和业务理解。
- [ ] 指标有来源、口径和时间窗，且可在面试中解释。
- [ ] 没有敏感数据、虚构经历或无法证明的技术深度。
- [ ] 控制在 2 页左右，最近且最相关的内容排在前面。
- [ ] 投递版本有记录，简历与面试口径一致。
- [ ] 已使用 [项目经历改写清单](./project-rewrite-checklist) 和 [ATS 检查清单](./ats-checklist) 复核。
