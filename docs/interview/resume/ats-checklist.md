# ATS 简历检查清单

ATS（Applicant Tracking System，招聘管理系统）首先需要正确解析简历，招聘方才有机会阅读内容。通过机器筛选的前提仍是真实匹配，不是重复堆砌关键词。

## 版式与机器可读性

- [ ] 使用单栏，自上而下阅读顺序唯一。
- [ ] 使用常见字体和字号，正文不小于可舒适阅读的尺寸。
- [ ] 姓名、联系方式和正文不放在页眉、页脚、图片或文本框中。
- [ ] 不使用进度条、技能星级、雷达图、图标代替文字。
- [ ] 不依赖表格、分栏、浮动元素或复杂时间轴承载核心信息。
- [ ] 使用真实文本，不把整页简历导出成图片。
- [ ] 装饰符号尽量少，项目符号复制到纯文本后仍能识别。

## 标准标题与顺序

优先使用招聘系统容易识别的标准标题：

1. 职业定位
2. 核心优势
3. 技术能力
4. 工作经历
5. 代表项目
6. 教育经历
7. 开源与技术影响（可选）

检查：

- [ ] 标题没有使用“关于我”“我的旅程”等创意名称替代标准名称。
- [ ] 工作经历按时间倒序，最近且最相关的经历优先。
- [ ] 公司、职位、日期与项目归属关系清楚。
- [ ] 每个项目都能判断角色、时间和关键贡献。

## JD 关键词映射

先从职位描述（Job Description，JD）提取关键词，再映射到真实证据。

- [ ] 标出岗位名称、核心技术、业务场景、职责层级和加分项。
- [ ] 区分“必须”“优先”和泛化描述，不平均分配篇幅。
- [ ] 使用 JD 中通行且准确的术语，例如 `Vue 3`、`TypeScript`、`微前端`。
- [ ] 关键词出现在职业定位、技术能力或相关项目中，而不是集中堆在末尾。
- [ ] 每个关键词都能对应工作或项目证据，并能接受面试追问。
- [ ] 不添加没有实际经验的技术；相近经验应明确写成“协作”“了解”或“可迁移能力”。
- [ ] 同义词可自然并列一次，例如“持续集成与交付（CI/CD）”，不要机械重复。

可使用以下映射草稿，完成后不要放进最终简历：

```text
JD 关键词：[关键词]
重要级别：[必须 / 优先 / 加分]
我的证据：[公司/项目/具体行动]
证据强度：[独立负责 / 共同负责 / 参与 / 了解]
简历位置：[职业定位/优势/技术/经历/项目]
是否保留：[是/否]
```

## 名称、日期与技术术语

- [ ] 姓名、公司、部门、项目和职位名称在全文一致。
- [ ] 简历、招聘平台、作品链接和背调材料中的日期一致。
- [ ] 日期统一使用 `YYYY.MM—YYYY.MM` 或同一种格式。
- [ ] 在职状态统一写“至今”，没有未来日期或经历重叠未解释。
- [ ] 技术名词拼写正确且统一，如 `TypeScript`、`JavaScript`、`Vue 3`、`Ant Design Vue`、`uni-app`、`Spring Boot`、`NestJS`。
- [ ] 不混用不准确缩写，例如把 JavaScript 写成 Java。
- [ ] 版本号只有在体现迁移、兼容或能力差异时才保留。

## 页数与信息密度

- [ ] 中高级岗位优先控制在 2 页左右。
- [ ] 第 1 页包含目标岗位、职业定位、核心优势和最近的关键经历。
- [ ] 每段经历优先保留 3～5 条高价值贡献，不罗列全部任务。
- [ ] 每条要点尽量包含问题、行动与结果，避免连续多条只写“负责”。
- [ ] 删除过时、重复或与 JD 无关的技术和早期细节。
- [ ] 不通过缩小字号、极窄页边距或压缩行距强塞内容。
- [ ] 留白能帮助快速扫描，关键证据不被大段文字淹没。

## 保密、真实性与可验证性

- [ ] 公司、职位、时间、项目和学历均为真实信息。
- [ ] “主导”“负责”“参与”准确反映本人职责边界。
- [ ] 指标有数据源、统计口径、基线和时间窗。
- [ ] 团队结果没有全部归于个人，协作对象与贡献可解释。
- [ ] 删除客户姓名、内部域名、账号、密钥、未公开营收、交易数据和安全架构细节。
- [ ] 身份证号、生日、婚育情况、详细住址、薪资流水等非岗位必填信息不主动写。
- [ ] 公开示例、作品或求职辅导材料已隐藏真实手机和邮箱。
- [ ] 必须表达规模时，使用经允许的区间、比例或脱敏描述。
- [ ] 每项证据已记录数据所有者、可披露级别、脱敏方式和是否仅供本人复盘。
- [ ] 可验证不等于允许披露；未经数据所有者或公司政策允许的内容不进入简历。
- [ ] 没有把学习项目、Demo 或短期试验包装成生产经验。
- [ ] 简历内容与面试、背调和证明材料保持一致。

## 错字、格式与链接

- [ ] 使用拼写检查，并至少人工通读 1 次。
- [ ] 中文标点、数字、空格和项目符号风格统一。
- [ ] 没有残留 `[占位符]`、“示例”、批注或编辑说明。
- [ ] 联系方式完整且属于本人。
- [ ] 链接使用 `https://` 完整地址，能够直接打开。
- [ ] GitHub、Gitee、个人主页和作品链接公开可访问，且没有敏感仓库。
- [ ] 链接文字也能说明目标，纯文本解析后仍可辨认。
- [ ] 文件名包含姓名与目标岗位，不使用“最终版 7”等含糊名称。

## 按岗位生成差异化版本

事实母版保持不变，只调整顺序、篇幅和措辞重点。

### Senior Frontend 版本

- [ ] 标题与职业定位明确为资深前端。
- [ ] Vue 3、TypeScript、性能、稳定性、工程化或多端能力靠前。
- [ ] 项目突出亲自解决复杂问题和端到端交付。
- [ ] 团队影响作为加分项，但没有盖过技术深度。

### Tech Lead 版本

- [ ] 标题与职业定位明确为 Tech Lead，且实际职责能够支撑。
- [ ] 架构取舍、跨团队推动、质量机制和技术债治理靠前。
- [ ] 说明影响范围、本人边界和团队共同成果。
- [ ] 保留足够的亲自设计、编码或排障证据，避免只剩管理口号。

### 全栈偏前版本

- [ ] 标题明确“全栈偏前”或“前端主责”，避免被误判为纯后端岗位。
- [ ] 前端主栈和复杂项目仍占主要篇幅。
- [ ] 与 Java / Spring Boot 后端团队、Node.js / NestJS 后端团队的内容落到接口契约、鉴权、BFF、联调或部署事实。
- [ ] 准确标注独立开发、共同负责或协作范围，不把接触写成精通。

## 文件格式与导出检查

- [ ] 先确认 JD、邮件或招聘平台要求，按要求提交 DOCX 或 PDF，不默认 PDF 更适合 ATS。
- [ ] 同时保留 DOCX 与 PDF 两版，并确保内容和版本号一致。
- [ ] DOCX 使用标准样式和真实文本，不依赖文本框、浮动形状或复杂表格。
- [ ] PDF 不设置密码或复制限制；字体正确嵌入，中文没有方框、乱码或错位。
- [ ] DOCX 与 PDF 均实际检查 A4 页面尺寸、分页和页边距，标题没有单独留在页尾。
- [ ] DOCX 与 PDF 的超链接均可访问，显示文字与实际地址一致。
- [ ] 文件体积适合招聘平台上传，文件名清晰。
- [ ] DOCX 在常用办公软件中打开检查；PDF 在系统预览、浏览器和常用 PDF 阅读器中打开检查。

## 机器解析自测

DOCX 与 PDF 必须分别执行以下 3 项，记录结果后再按平台要求选择提交格式：

1. **实际分页：** 打开文件，以 A4 视图检查是否为目标页数、标题是否悬空、段落是否跨页失控。
2. **纯文本复制 / 提取：** 全选并粘贴到纯文本编辑器；必要时使用对应格式的本地文本提取工具，检查阅读顺序、中文、项目符号和链接。
3. **平台解析：** 分别上传 DOCX 与 PDF 到目标招聘平台的简历解析页面，逐字段核对姓名、联系方式、公司、职位、日期和技术关键词。

没有实际完成分页、复制和招聘平台解析，就只能写“待验证”，不能声称已通过 A4 两页或 ATS 验证。

自测记录：

```text
简历版本：[DOCX 文件名 / PDF 文件名]
目标岗位：[Senior Frontend / Tech Lead / 全栈偏前]
导出日期：[YYYY.MM.DD]
实际 A4 分页：[DOCX 结果 / PDF 结果 / 待验证]
纯文本顺序：[DOCX 结果 / PDF 结果 / 待验证]
姓名与联系方式：[通过 / 待修复]
公司、职位与日期：[通过 / 待修复]
技术关键词：[通过 / 待修复]
链接：[通过 / 待修复]
招聘平台解析：[平台、DOCX 结果、PDF 结果 / 待验证]
修复记录：[问题与处理]
```

## 投递前最后确认

- [ ] 最终提交格式符合当前 JD / 平台要求，不是无差别群发版本。
- [ ] 所有关键词真实、所有数字可解释、所有链接可访问。
- [ ] 机器解析结果正确，招聘方能在 30 秒内找到核心证据。
- [ ] 已保留本次投递版本和 JD，面试前可以恢复同一口径。
