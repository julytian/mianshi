# 架构 / Lead 面试题库

> **怎么用：** 先盖住答案，自己口述 1～2 分钟（决策、取舍、带人、事故），再点开 `参考答案` 对照补洞。追问用来模拟面试官加压；踩坑是实战里最容易翻车的点。中英文术语之间请习惯留空格，口述时也建议如此。

本模块定位是 **前端 Lead / 技术骨干**：少讲「我最懂框架」，多讲**选型怎么拍板、债务怎么还、范围怎么砍、质量怎么卡、人怎么带、跨端资源怎么分**。默认上下文：Vue 3 管理后台 + H5 / uni-app 跨端，可能带一点 Java 联调视野。

纯技术架构原则请转到 [前端架构](/interview/questions/14-frontend-architecture)，具体系统方案请转到 [前端系统设计](/interview/questions/11-frontend-system-design)。本模块保留的技术题，都要回答负责人如何组织决策、争取资源并推动落地。

文中的天数、比例、行数和团队规模均是**示例阈值**，用于展示决策方法；实际应依据团队基线、业务 SLA、风险等级和观察窗口设定。所有「提升、下降、清零」都要说明基线、统计口径、归因与样本量。

口述金句：Lead 不是写得最多的人，是让正确的事以可交付质量发生的人。

### Q1. 做技术选型时，你会用什么框架拍板，而不是「跟风选最火的」？

**考察点：** 选型维度、团队匹配、可回退、决策留痕

::: details 参考答案
选型不是比明星度，是比**问题匹配 + 团队可维护 + 风险可控**。我通常固定几维打分（可口头 / 可一页纸）：

1. **问题匹配**：要解决的是冷启动、包体积、跨端一致性，还是后台 CRUD 效率？工具要对症。
2. **团队能力曲线**：会不会只有我一人会？新人 2 周能不能贡献？文档与社区中文资料是否够。
3. **生态与生命周期**：核心依赖是否活跃、是否有大厂背书或明确 LTS；别选「博客里很炫、半年没 commit」的。
4. **迁移与退出成本**：试点能否局部引入？失败能否回滚到旧方案而不炸主链路。
5. **非功能约束**：合规、包体积、SSR/CSR、小程序审核、内网构建环境。

决策流程：PoC（1～3 天）→ 写清「选 / 不选理由」→ 小流量或子模块试点 → 再推广。口述强调：**我会留下决策记录**，半年后别人问「为什么选 A 不选 B」能答得上，避免口头传说。
:::

**追问：**
1. 业务强烈要求上某新框架，但团队没人熟，你怎么挡或怎么接？
2. Vue 与 React 二选一，除了「我会 Vue」还能讲什么客观维度？
3. 选型 PoC 失败了，你怎么向产品 / 老板交代而不显得甩锅？

**踩坑：** 用个人偏好当选型结论；或一次全量替换核心链路，没有试点与回滚预案。

### Q2. 技术债你怎么识别、分级、排期，避免「永远没空还」？

**考察点：** 债务分类、利息可视化、与业务排期博弈

::: details 参考答案
先统一语言：技术债 = **今天省下的时间，明天以更高成本偿还**。我会按「利息」分级，而不是按「代码丑不丑」：

| 级别 | 典型信号 | 策略 |
| ---- | -------- | ---- |
| P0 利息极高 | 频繁线上故障、阻断发版、安全漏洞 | 立刻插队或跟版本强绑修复 |
| P1 高 | 改一处炸一片、无测试关键路径、重复造轮子拖慢迭代 | 每个迭代固定预算（如 20%） |
| P2 中 | 命名混乱、组件重复、文档缺失 | 顺手还 / 专项周 |
| P3 低 | 风格偏好、过度抽象争论 | 不单独开项目 |

识别来源：事故复盘、CR 反复出现的同类评论、新人上手时长、构建/发布失败率、关键模块变更成本。排期话术对产品：**不讲「重构很重要」，讲「不还会导致 X 功能多估 3 人日 / 每月多一次回滚」**。机制上：看板单独一列「债务」、定义完成标准（有测试、有文档、可观测），避免「重构到一半半成品」。
:::

**追问：**
1. 产品说「下个版本绝对不能动重构」，你怎么谈出最小还债包？
2. 怎么区分「值得还的债」和「过度设计伪装成还债」？
3. 历史遗留巨石文件（2000 行 Vue），你会怎么拆而不停业务？

**踩坑：** 大爆炸式重构、无指标、无里程碑；或把个人洁癖包装成必须还的债，消耗团队信任。

### Q3. 估期总是不准时，你会怎么估？范围必砍时怎么砍得有章法？

**考察点：** 估期方法、缓冲、MVP、砍刀原则

::: details 参考答案
估期不准通常不是「算错算术」，是**范围与风险没拆开**。我的做法：

1. **拆到可验证切片**：按用户故事 / 接口 / 页面状态拆，每片最好 0.5～2 人日；超过 3 人日继续拆。
2. **三点估或风险加码**：乐观 / 最可能 / 悲观；未知接口、第三方、审核、联调单独标风险项，而不是埋进「感觉 5 天」。
3. **缓冲显式化**：缓冲给「联调 + 返工 + 发布」，不假装 100% 利用率。
4. **砍刀原则（有序）**：先砍锦上添花交互与边缘兼容 → 再砍非核心报表 / 运营位 → 保主路径闭环（登录→核心交易/审批→结果可查）。质量活动可以按风险缩减，但要保留**最低安全集**：核心鉴权与数据正确性验证、可回滚产物、主路径烟测和上线观测；删减项要记录风险与补测时间。
5. **书面对齐**：砍掉的进「明确不做」列表，避免口头「回头再加」变范围膨胀。

口述：我交付的是**可验收的主路径**，不是幻想中的完美版。
:::

**追问：**
1. 老板压期砍一半时间，你怎么回应才不像推诿？
2. 后端接口延期，前端估期怎么重谈？
3. 「差不多做完了」和「可上线」之间你用什么定义拉开差距？

**踩坑：** 按理想人日估、不留联调；砍范围时砍测试与灰度，结果准时上线但立刻回滚。

### Q4. 你怎么做 Code Review，才能既挡风险又不变成「风格警察」？

**考察点：** CR 清单优先级、反馈方式、吞吐与质量平衡

::: details 参考答案
CR 目标排序：**正确性与安全 > 可维护性 > 性能直觉 > 风格**。风格尽量交给 ESLint / Prettier / 约定，人工精力留给机器查不出的：

- 权限与数据越权、敏感信息日志、XSS / 危险 HTML；
- 错误处理与空态、并发重复提交、缓存一致性；
- 抽象是否过早 / 重复逻辑该不该抽；
- 可测性与可观测（关键路径有没有日志 / 埋点）。

机制建议：小 PR（最好 <400 行有效 diff）、描述写清「为什么 / 怎么测 / 风险」；Lead 可抽查关键模块与新人 PR。反馈用「建议 + 理由 + 可选方案」，阻塞项（blocker）与可选优化分开，避免一次 CR 提 40 条 nit 打死积极性。

时效：约定 SLA（如 1 个工作日内首轮），阻塞合并的问题必须当天对齐，避免 PR 腐烂。
:::

**追问：**
1. 同事坚持自己的写法，你认为有隐患，僵持怎么收场？
2. 业务很急、来不及细 CR，你最低限度看哪几项？
3. AI 生成的大段 diff，CR 策略和手写代码有何不同？

**踩坑：** 只抠缩进和命名；或「Approve 但不看」当人情，出事时无人负责。

### Q5. 质量门禁你会卡哪些？哪些必须红灯，哪些可以黄灯放行？

**考察点：** CI 门禁分层、例外流程、质量与速度权衡

::: details 参考答案
门禁分层，避免「全红或全绿」极端：

| 层级 | 典型项 | 策略 |
| ---- | ------ | ---- |
| 合并前门禁 | lint、typecheck、单测（关键包）、构建成功 | 默认必须绿 |
| 发布前门禁 | E2E 烟测、包体积预算、关键路径手测清单 | 主版本必须；热修可缩范围但要签字 |
| 运行时门禁 | 错误率 / 白屏监控阈值、核心接口成功率 | 超阈值自动或人工回滚 |

**必须红灯：** 已确认可达且影响生产资产的漏洞、类型/构建失败、核心单测挂、未授权接口暴露。依赖告警是否阻断需结合代码路径可达性、部署暴露面、修复版本与业务 SLA；不可达但高危的项可限时豁免并持续跟踪。
**可黄灯 + 例外：** 某非关键包单测 flaky、文档站点构建失败——走「限期偿还 + 负责人」票据，禁止无限豁免。

口述强调：门禁是**团队契约**，Lead 的职责是守契约并设计合理例外，而不是自己天天特批。
:::

**追问：**
1. 类型检查太严导致改不动遗留代码，你怎么渐进收紧？
2. 谁有权跳过门禁？如何审计？
3. 门禁变慢（CI 20 分钟），你优化优先级怎么排？

**踩坑：** 门禁形同虚设（人人 skip）；或一次加满导致团队绕过 CI 直推生产。

### Q6. 带新人你会怎么设计前 30 天，让他尽快产出又不踩生产？

**考察点：** onboarding、任务梯度、反馈节奏、安全边界

::: details 参考答案
目标分阶段，而不是「自己看文档」：

- **第 1 周**：环境跑通、读架构图与目录约定、跟一次发布/回滚演练；改文档或极小 bug（文案、样式、无风险逻辑）。
- **第 2～3 周**：独立完成带导师 CR 的中等任务（列表页、表单、一个接口联调）；通过风险分级和 CODEOWNERS 明确哪些变更可自主完成、哪些需领域 Owner 评审，而不是按目录机械「请示」。
- **第 4 周**：独立拿一小块功能，端到端负责（需求澄清→实现→自测→发布观察）。

机制：结对时段、CR 必复盘 1～2 条「为什么这样写」、周会只问阻塞不秋后算账。安全边界写清楚：生产凭证、数据库、权限配置、支付/账务相关必须双人。考核看**可合并的产出与学习曲线**，不看加班时长。
:::

**追问：**
1. 新人反复犯同类错，你怎么反馈才有效？
2. 老人不愿带新人，你怎么设计激励或机制？
3. 远程/外包协作时 onboarding 要补什么？

**踩坑：** 第一周就扔核心模块；或过度保护导致三个月仍不能独立发版。

### Q7. 管理后台、H5、小程序多端并行时，人力怎么分配才不崩？

**考察点：** 跨端资源分配、共享层、优先级、单点风险

::: details 参考答案
先分清**共享与差异**：

- 共享：设计 token、请求封装、鉴权模型、业务 API 契约、部分工具库；
- 差异：路由/导航、组件库（Ant Design Vue vs Vant vs uni 组件）、发布审核、性能与包体积约束。

人力模型常见三种：

1. **按端分人**：沟通成本低，但业务逻辑复制、规范漂移——适合端差异极大且人够。
2. **按业务域横切**：一人吃多端同一业务——一致性好，但对个人要求高，需防单点。
3. **平台组 + 业务组**：少数人维护组件/脚手架/CI，业务同学消费——中长期更稳。

分配原则：**先保主营收/主审核路径的那一端**；共享基建投资用「重复三次就抽」规则；排期看板按端可见，避免三端都 80% 完成却没有一端可上线。Lead 要显式管理「唯一懂某端」的单点，强制文档与 backup。
:::

**追问：**
1. 同一需求三端都要，只给你 1.5 人月，怎么谈？
2. uni-app 一套代码多端，和「分仓库分端」如何选？
3. 设计稿只出了 iOS 尺寸，Android / 小程序谁兜底？

**踩坑：** 三端平行 100% 功能对齐，资源被均分导致全部延期；或共享层过度抽象，业务端反而更慢。

### Q8. 线上事故后，一次合格的复盘（postmortem）你怎么主持？

**考察点：** 无指责文化、时间线、根因、动作闭环

::: details 参考答案
复盘目的是**系统变强**，不是找人背锅。我会固定议程：

1. **时间线**：发现→止损→恢复→影响面，用监控/日志说话，不靠回忆吵架。
2. **影响**：用户数、金额、时长、是否合规相关——量化。
3. **根因分层**：直接原因（空指针、错误配置）+ 作用因素（缺门禁、缺告警、变更窗口乱）+ 为何没更早发现。
4. **改进项**：每条有负责人、截止日、验证方式；分「已做止损」与「防再发」。
5. **对外沟通**：对产品/客服的话术与对内技术细节分开。

前端典型事故：错误发布、缓存/CDN 未刷、兼容白屏、权限配置误发、第三方脚本。止损优先级永远高于完美根因分析。
:::

**追问：**
1. 有人明显违规操作，还能「无指责」吗？边界在哪？
2. 复盘结论是「人的疏忽」，你如何改写成可执行的系统改进？
3. 小事故要不要每次正式复盘？如何避免复盘疲劳？

**踩坑：** 复盘变成批斗会；或写一堆「加强责任心」没有可验证动作。

### Q9. 前后端分工边界你怎么划？接口契约冲突时谁说了算？

**考察点：** 职责边界、契约优先、联调协作、升级路径

::: details 参考答案
默认边界：

- **前端**：体验、状态、校验（体验层）、权限展示与路由守卫、性能与兼容、埋点；
- **后端**：权威校验与鉴权、事务与一致性、数据模型、审计、限流与安全；
- **交叉区**：错误码、分页结构、枚举、幂等、文件上传策略——必须**书面契约**（OpenAPI / Apifox），而不是群聊截图。

冲突时原则：**安全与数据正确以后端权威为准；交互效率与字段形状可协商**。例如是否返回多余关联字段、列表是否服务端聚合，用「调用次数 / 复杂度 / 缓存」说话，而不是岗位尊严。前端 Lead 要能读懂接口设计是否坑前端（N+1 调用、分页无 total、时间戳单位混乱），必要时拉架构或 TL 仲裁，并留下 ADR 式简短记录。

有 Java 能力时，口述加一句：简单 CRUD / BFF 可以由前端团队建设，但进入生产前必须明确服务 Owner、容量与安全评审、发布回滚、SLO 和 on-call；账务、授权模型等领域规则仍由后端领域服务负责。
:::

**追问：**
1. 后端让前端「自己拼十个接口」，你何时接受、何时拒绝？
2. 前端做了 BFF，职责膨胀怎么防？
3. 联调环境长期不一致，你怎么推动治理？

**踩坑：** 前端信任后端「不会越权」而只藏按钮；或前端在浏览器里做唯一校验。

### Q10. 要推进组件库 / 设计体系，阻力很大时你怎么落地？

**考察点：** 渐进推广、激励机制、度量、避免空中楼阁

::: details 参考答案
组件库失败常见原因：一步到位、没业务试点、维护无人、和设计不同步。推进策略：

1. **从高频痛点长出来**：Button/Form/Table 封装、请求空态，而不是先写完美主题引擎。
2. **试点业务**：选一个活跃模块迁 3～5 个组件，收集 API 别扭点再固化。
3. **降低接入成本**：文档站点、Changelog、迁移 codemod 或示例仓库；CI 发版自动化。
4. **治理**：breaking change 语义化版本；贡献指南；Lead/指定 owner 值班。
5. **度量**：重复组件数量下降、新页面接入率、缺陷率——用数据说服「继续投」。

与设计协作：token 命名对齐，争议用「可访问性 / 一致性 / 实现成本」三角，而不是谁官大。
:::

**追问：**
1. 业务同学偷偷复制组件改私有份，你怎么治理？
2. 多产品线要不要一个巨型库还是多包？
3. 组件库和业务迭代抢人，预算怎么谈？

**踩坑：** 库很全但没人用；或强制一天迁完导致业务反弹，库被弃用。

### Q11. 和产品经理博弈需求时，你怎么谈才专业、不撕逼？

**考察点：** 共情目标、选项对比、风险可视化、书面结论

::: details 参考答案
立场：产品对**结果负责**，技术对**可行性与质量负责**——目标应对齐「用户价值 / 上线风险 / 成本」。谈法：

1. **复述目标**：先确认要解决的用户问题，避免一上来否决交互细节。
2. **给选项而非只说不**：A 完整版 15 人日；B MVP 6 人日（列清砍掉项）；C 用配置/运营解决 2 人日。
3. **风险显性化**：技术债、审核、性能、安全、依赖第三方——用「概率 × 影响」讲，不恐吓。
4. **决策留给该决策的人**：在选项上让产品/老板选，技术提供约束；结论写进需求或评审纪要。

红线：安全合规、数据正确、不可逆操作无确认——这些不是可砍的「体验优化」。
:::

**追问：**
1. 产品当场拍板「就按完整版，下周上」，你怎么办？
2. 设计稿与技术实现冲突（炫酷动画 vs 低端机），怎么协调？
3. 需求朝令夕改，你如何要求流程而不显得僵化？

**踩坑：** 只会说「做不了」；或全盘答应后用加班硬扛，团队反噬。

### Q12. 招聘前端时，你的「及格线」大概怎么定？（hiring bar 轻量版）

**考察点：** 岗位分层、信号题、避免偏见、试用期验证

::: details 参考答案
按职级定 bar，而不是用同一套八股拷打所有人：

| 层级 | 必须看见的信号 |
| ---- | -------------- |
| 初中级 | 能独立完成页面与联调；基础 JS/Vue 正确；肯查文档；CR 反馈能吸收 |
| 高级 | 能拆复杂需求；性能/工程有实战；能带小范围决策；沟通清楚 |
| Lead 向 | 取舍与事故经验；能谈人与流程；技术深度够但不炫技压场 |

面试设计：1 道贴近业务的编码或讲解 + 1 段项目深挖（STAR + 追问）+ 1 道工程/质量场景。看**证据与推理**，少看「背过多少源码」。AI 辅助编程时代，加一道：如何审查 AI 代码 / 如何拆任务——看责任意识。

录用后：试用期目标写清（能否独立交付范围明确的模块、质量与协作证据、风险沟通和事故演练），不用 PR 数量评价价值；bar 用结果和行为证据验证，不靠感觉。
:::

**追问：**
1. 算法很强但工程一塌糊涂，你招吗？
2. 怎么减少「和我像的人」偏见？
3. 外包转正 / 内推压力下，bar 被挑战时你怎么坚持？

**踩坑：** 用自己十年前的八股当唯一标准；或只聊很爽、不看代码与协作证据。

### Q13. 前端要不要 on-call？若要，你怎么设计值班，避免「前端背所有锅」？

**考察点：** 值班范围、升级路径、疲劳管理、与后端/运维边界

::: details 参考答案
要，但**范围必须清晰**。前端 on-call 典型覆盖：

- 发布后白屏 / 资源 404 / CDN 配置；
- 前端可观测告警（JS error 突增、核心页面 PV 骤降）；
- 配置中心误发、灰度开关；
- 与客户端 WebView / 小程序相关的前端侧问题。

不该默认前端扛：数据库慢查询、网关大面积 5xx、机房网络——应升级后端 / SRE，前端协助提供请求指纹与时间线。

机制：轮值表、升级矩阵（15 分钟未止损找 TL）、值班文档（常见 runbook）、事故后补偿休息、禁止「全年同一人」。工具：Sentry / 自建监控 + 发布版本关联，值班才查得动。

口述：on-call 是**降低 MTTR**，不是荣誉加班。
:::

**追问：**
1. 半夜告警是第三方统计脚本导致的 error 风暴，你怎么处理与事后治理？
2. 只有前端两人，如何排班才不烧人？
3. 小程序审核期间的「值班」和线上 on-call 有何不同？

**踩坑：** 无 runbook 纯靠英雄；或前端值班却没有权限回滚/改 CDN，干瞪眼。

### Q14. 作为 Lead，迭代节奏（Scrum / 看板）你怎么裁剪，避免仪式感空转？

**考察点：** 流程裁剪、WIP、会议ROI、可预测性

::: details 参考答案
流程服务交付，不服务方法论信仰。我会保留高 ROI 仪式、砍掉空转：

- **保留**：清晰的 Sprint / 周期目标、每日短同步（阻塞导向）、评审（给产品看可点产物）、回顾（只改 1～2 个动作）。
- **裁剪**：超长估点会、无准备的「站会轮流报流水账」、形式化故事点通胀。
- **看板纪律**：限制 WIP（在制品），宁可做完再拉，不五件事做到 80%。
- **技术槽位**：每个周期固定比例给债务、工具、文档——写进计划，不是「有空再说」。

和远程/多端团队：异步文档优先，会议带议题与结论区。Lead 自己做示范：会前材料、会后纪要三行。
:::

**追问：**
1. 老板要看故事点燃尽图，但团队厌恶估点，你怎么折中？
2. 紧急插入需求打断 Sprint，规则怎么定？
3. 回顾会总变成吐槽会，你怎么引导到动作？

**踩坑：** 仪式很全但交付不可预测；或完全无流程导致只有 Lead 脑子里有全局。

### Q15. 讲一次你推动的「架构或工程决策」：背景、选项、结果、如果重来？

**考察点：** 决策叙事、证据、复盘诚实度（行为面试）

::: details 参考答案
用 STAR-L 压进 2～3 分钟（示例骨架，面试换成你的真事）：

- **S**：多端三套请求封装，错误码与 token 刷新行为不一致，联调与值班成本高。
- **T**：统一鉴权与错误处理，且不能停业务两周。
- **A**：方案对比（继续复制 / 抽 monorepo shared / 做 BFF）。选「shared SDK + 适配层」：核心 refresh 单测锁住，各端只留平台差异；两周试点后台，再推 H5。
- **R**：重复代码下降、一类线上「串 token」问题消失；代价是首周 CR 变严、有抵触。
- **L**：若重来，更早做迁移手册与兼容层开关，减少业务同学体感摩擦。

口述要点：有选项、有代价、有度量、有反思——比「我推了微前端很成功」更像 Lead。
:::

**追问：**
1. 决策事后证明错了，你怎么讲才加分？
2. 没有「架构师头衔」时，你如何推动跨组决策？
3. 如何避免决策变成「Lead 一言堂」？

**踩坑：** 故事只剩自己正确；或没有数字与后果，听起来像背诵范文。

### Q16. 前端性能与体验优化，你会怎样排优先级并推动落地（Lead 视角）？

**考察点：** 指标、ROI、组织推动、长期机制

::: details 参考答案
Lead 视角不是亲自调每一个 LCP，而是建立**指标 → 预算 → 机制**：

1. **选指标**：视场景定——后台看 TTI / 长列表交互；H5 看 LCP/INP；小程序看启动与 setData。
2. **建预算**：包体积、请求瀑布、主链路接口耗时——超预算 CI 警告或拦截。
3. **排优先级**：用户量 × 慢的程度 × 改动成本；先打「首屏与主转化」。
4. **组织**：性能不是运动式一周，而是 CR 清单一项、版本例行扫描、与需求评审绑定「是否引入重依赖」。
5. **叙事**：对产品讲「转化 / 投诉 / 流失」，对团队讲「可维护的优化，而不是黑客式抠字节」。

有 AI 提速时也一样：AI 可生成懒加载改造，但**指标验收与回归**仍是人的门禁。
:::

**追问：**
1. 产品要加一堆营销脚本导致性能回退，你怎么谈？
2. 优化做了但指标不动，可能卡在哪？
3. 如何防止「性能优化」变成无限打磨？

**踩坑：** 只有个人英雄式优化、无预算无监控；或优化微细节忽略主路径接口。

### Q17. 多仓库 / Monorepo、多环境发布，Lead 要守住哪些「工程底线」？

**考察点：** 仓库策略、环境一致性、发布权责

::: details 参考答案
底线清单（可按团队裁剪）：

1. **环境同源**：dev / test / pre / prod 配置结构一致，差异只在值；禁止「只在生产手改」。
2. **版本可追溯**：构建产物与 git SHA / 版本号绑定；前端 sourcemap 与发布记录可查。
3. **权限最小化**：生产发布权限、CDN、小程序上传密钥——分人分责，审计留痕。
4. **回滚可执行**：按业务 RTO、发布载体（Web/CDN、小程序、App 内嵌页）和数据是否可逆定义恢复方案。纯静态资源可切旧产物；已产生不可逆写入时应前向修复或补偿，不能承诺统一的 5～15 分钟回滚。
5. **依赖与安全**：锁文件、高危依赖扫描、私有源可用性。

Monorepo vs 多仓：协同频繁、共享组件多偏向 monorepo（pnpm workspace 等）；独立生命周期与权限隔离偏多仓。Lead 要选「团队沟通成本最低」的，而不是追时髦。
:::

**追问：**
1. 预发验证通过、生产仍挂，你先查哪几层？
2. 热修是否允许跳过部分流水线？条件是什么？
3. 设计系统在 monorepo 里版本怎么发，避免业务仓永久钉死旧版？

**踩坑：** 生产配置漂移成雪花服务器；或人人能推生产，出事无法追责也无法快速止血。

### D1. 如何为不同级别岗位建立可校准的招聘标准？

**考察点：** 胜任力模型、证据、面试校准、招聘质量

::: details 参考答案
#### 基础结论

Q12 解决单次面试的基础及格线；本题增加「多岗位、多面试官、半年扩招」约束，目标是让不同面试官稳定执行同一标准。招聘标准来自岗位未来 6～12 个月要解决的问题，不是复制现有成员画像。每个级别定义必须项、加分项、不可接受项，并为每项指定可观察证据和评分锚点。

#### 原理深挖

面试信度取决于结构化题目、独立评分和校准，而不是面试官资历。高级岗位要同时验证技术深度、模糊问题拆解、跨团队影响力和事故责任；不能用一道算法题替代全部能力。

#### 工程场景

面试前用同一份题目和样例回答校准「3 分与 4 分」；面试后先独立写证据再讨论。领先信号看候选人体验、流程完成率、面试官评分分歧和反馈证据完整度；试用期目标质量看目标是否与岗位结果对齐、可观察且有合理支持。试用期达标、半年留存和绩效只能作为滞后信号，受团队环境、经理质量和项目分配影响，不能直接归因于招聘标准。还要按群体检查通过率、定级、Offer 和试用期结果的不利影响，在样本足够时调查结构性偏差，而不是追求 Offer 数。

#### 反例 / 踩坑

把「像我、聊得来」当文化匹配；级别先定再拼证据；为了赶人头降低必须项；面试反馈只写「基础不错」；用半年留存或绩效单一滞后指标给面试官排名，却不检查候选人体验和群体不利影响。

#### 资深回答模板

「背景是半年内扩充多个职级；约束是面试官经验不一且不能降 bar；选项是自由面试、统一题库或结构化评分；行动是定义行为锚点、独立评分和双周校准；领先结果看候选人体验、面试官分歧和试用期目标质量，留存与绩效仅作有混杂因素的滞后信号；按群体审查不利影响并反思偏差来源。」
:::

**追问链：**
1. 业务急缺人但候选人只差一项必须能力，怎么办？
2. 如何减少学历、公司背景和相似性偏见？
3. 招错高级工程师后如何复盘招聘系统？

### D2. 如何给表现不达预期的成员反馈并帮助其成长？

**考察点：** 事实反馈、期望对齐、辅导、绩效边界

::: details 参考答案
#### 基础结论

反馈要及时、具体、围绕行为和影响，并给出可观察的下一步标准。先确认是能力、意愿、资源还是目标不清，再选择辅导、调整任务或正式绩效流程。

#### 原理深挖

使用「情境—行为—影响—期待」避免人格判断。成长计划应处在略高于当前能力的挑战区，有导师、反馈频率和截止日期；支持不等于无限延期。

#### 工程场景

成员连续两个迭代交付延期：拿需求拆分、风险上报和返工记录对齐事实；未来 4 周要求任务拆到两天内、风险提前 48 小时上报，每周复盘一次，并提供一次结对拆解。

#### 反例 / 踩坑

季度末才突然给差评；用「不够主动」等不可验证标签；公开批评；只有鼓励没有标准；Lead 代做所有困难部分。

#### 资深回答模板

「背景是成员连续延期；约束是既要保障交付也要公平辅导；选项包括补资源、缩任务、专项培养或绩效流程；行动是对齐事实、根因和四周计划；结果用交付、返工与协作反馈相对基线判断；反思目标或支持是否设置错误。」
:::

**追问链：**
1. 对方不认同反馈怎么办？
2. 高绩效成员协作方式伤害团队，如何处理？
3. 何时判断辅导无效并进入绩效流程？

### D3. 跨团队技术冲突长期僵持时，Lead 如何推动收敛？

**考察点：** 共同目标、决策权、升级机制、关系修复

::: details 参考答案
#### 基础结论

先把立场争论改写为共同目标、约束和可比较选项，再明确谁拥有最终决策权。无法靠数据收敛时，应按约定升级，而不是无限开会。

#### 原理深挖

冲突常混合目标不一致、资源分配和身份威胁。Lead 要分开处理：技术方案用指标和实验，资源由业务负责人取舍，合作关系用一对一沟通修复。

#### 工程场景

前端希望 BFF 聚合，后端拒绝维护：共同量化接口扇出、P95 延迟、故障归属和人力；比较前端聚合、网关编排和专用 BFF，做一周 PoC，由服务 Owner 和产品负责人按 SLA 与成本拍板。

#### 反例 / 踩坑

在大群里证明对方不专业；绕过 Owner 偷偷落地；只说「架构最佳实践」不承担维护成本；结论没有记录。

#### 资深回答模板

「背景是跨团队方案僵持；约束是上线窗口与双方维护能力；选项含前端聚合、网关编排和专用 BFF；行动是量化、PoC、明确 Owner 与决策权；结果比较 SLA、成本和协作等待的基线变化；反思升级是否过早以及接口如何改善。」
:::

**追问链：**
1. 决策者选了你认为风险更高的方案怎么办？
2. 对方团队拒绝提供实验资源怎么办？
3. 如何避免每次争议都升级到上级？

### D4. 没有正式架构权力时，如何推动跨团队架构改造？

**考察点：** 影响力、试点、联盟、采用成本

::: details 参考答案
#### 基础结论

架构推动靠可信证据、低成本试点和共同收益，不靠头衔。先解决一个高频痛点，证明结果，再把经验产品化并建立治理机制。

#### 原理深挖

采用阻力通常来自迁移成本、风险和所有权不清。推动者要同时提供技术方案、迁移路径、支持资源与退出方案，让首批采用者承担的风险最低。

#### 工程场景

统一错误模型先在事故最多的两个应用试点，提供兼容适配器和迁移清单；用定位时长、重复代码和接入工时展示收益，再邀请各团队代表共建 RFC，管理层只负责资源与底线。

#### 反例 / 踩坑

先发规范要求全员执行；只造库不做迁移；拿一次成功宣称适合所有团队；把反对者贴上「不重视技术」标签。

#### 资深回答模板

「背景是跨团队重复故障；约束是无正式授权且不能停业务；选项是只发规范、集中重写或兼容试点；行动是联合首批团队试点并提供迁移支持；结果以接入工时、定位时长和事故率相对基线验收；反思哪些假设不适用于后续团队。」
:::

**追问链：**
1. 试点成功但其他团队仍不采用怎么办？
2. 如何选择第一批盟友？
3. 何时需要管理层强制？

### D5. 重大线上事故中，前端 Lead 如何担任事故指挥官？

**考察点：** 指挥体系、止损、沟通、恢复

::: details 参考答案
#### 基础结论

Q8 讨论恢复后的复盘主持；本题增加「故障仍在扩大、跨团队并发处置」约束。事故指挥官负责建立节奏和决策，不应同时埋头排查。第一目标是控制影响，其次恢复服务，最后才是完整根因。

#### 原理深挖

明确指挥、排障、沟通和记录四个角色；建立单一信息源和固定更新时间。决策基于影响面、可逆性和恢复时间，优先执行已演练的回滚与降级。

#### 工程场景

发布后白屏率突增：5 分钟内冻结发布、确认版本相关性，安排一组回滚、一组查 CDN/配置，客服每 15 分钟收到影响与恢复预期。恢复后继续观察一个告警窗口，再转入复盘。

#### 反例 / 踩坑

所有人挤在一个群里无角色；边排障边互相追责；未经验证连续改配置；恢复后立即散场，没有证据保全和用户补救。

#### 资深回答模板

「背景是发布后白屏持续扩大；约束是信息不全且恢复窗口很短；选项是回滚、降级或前向修复；行动是定级分角色、按 RTO 选择止损并固定通报；结果以影响用户、恢复时间和告警窗口验证；反思指挥、Runbook 与预防门禁。」
:::

**追问链：**
1. 回滚也有风险时如何决策？
2. 多团队都认为不是自己问题怎么办？
3. 事故中高层频繁追问如何处理？

### D6. 如何争取并管理技术债预算？

**考察点：** 债务利息、业务语言、组合管理

::: details 参考答案
#### 基础结论

Q2 解决单项技术债的识别和分级；本题增加「多团队共享预算、业务连续挤压」约束，要求把债务作为投资组合管理。不要争取抽象的「20% 重构时间」，而要展示技术债对交付、事故和人员的利息，并把预算绑定可验收结果。

#### 原理深挖

技术债是投资组合：有些应立即偿还，有些可控制利息，有些应接受直到系统下线。优先级由业务损失、风险暴露、变化频率和偿还成本共同决定。

#### 工程场景

先取最近 8～12 周的变更周期、回滚和 on-call 工时作为基线，区分权限模块、需求变更和外部依赖的归因，再提出两个迭代的兼容层改造。「变更周期下降 30%、同类事故清零」只能作为团队设定目标的示例，验收时需使用相同口径与观察窗口，并报告样本量和非改造因素。

#### 反例 / 踩坑

把所有旧代码都列成债；只讲开发体验不讲业务结果；专项重构没有里程碑；预算被紧急需求挤占却不记录代价。

#### 资深回答模板

「背景是多团队争抢同一预算；约束是本季度不能停业务；选项是不处理、最小止血或分期治理；行动是按归因后的利息排序并绑定里程碑；结果以同窗口基线对比交付与事故指标；反思目标是否受样本和外部变化干扰。」
:::

**追问链：**
1. 业务连续两个季度不给预算怎么办？
2. 如何防止团队夸大技术债？
3. 系统一年后下线，还应还哪些债？

### D7. 如何向业务和管理层沟通三年技术路线？

**考察点：** 战略叙事、不确定性、里程碑、资源

::: details 参考答案
#### 基础结论

路线图表达的是业务能力与风险下降，不是框架版本时间表。远期用方向，近期用承诺，并明确假设、依赖和触发调整的信号。

#### 原理深挖

不确定性随时间增加：未来 1 个季度可承诺交付，半年给主题和指标，一年以上只给战略选项。每项投资要连接增长、效率、可靠性或合规。

#### 工程场景

不说「明年全面微前端」，而说「在当前基线下支持多团队独立发布，并降低跨团队等待」；先完成模块边界与发布度量，只有发布冲突、故障影响面和等待时长持续越过约定阈值后，才决定是否运行时拆分。

#### 反例 / 踩坑

路线图全是技术名词；三年计划写到具体月份；只列建设不列淘汰；没有人力和迁移成本；环境变化后仍按原计划执行。

#### 资深回答模板

「背景是业务增长与历史系统并存；约束是资源和远期信息有限；选项是维持、渐进演进或集中替换；行动是把近期承诺与远期方向分层并设置触发器；结果用交付等待、可靠性和采用成本验证；反思假设变化后如何调整路线。」
:::

**追问链：**
1. 管理层只关心下季度收入怎么办？
2. 路线被临时项目打断如何调整？
3. 如何公开说明原路线判断错了？

### D8. 团队快速扩张时，如何重构组织边界？

**考察点：** 团队拓扑、认知负载、所有权、协作接口

::: details 参考答案
#### 基础结论

团队扩张先明确业务边界和 Owner，再增加流程与平台能力。目标是降低认知负载和跨团队等待，不是给每个新小组复制一套管理层级。

#### 原理深挖

人数增加会放大沟通路径和认知负载。团队应围绕可独立交付的业务域组织，平台团队提供自助能力而非接单；用服务目录、Owner、SLA 和团队交互模式替代临时拉群。

#### 工程场景

团队从 8 人扩到 25 人：比较按职能、按业务域和平台 + 业务域三种方案，按三个业务域设 Owner，以接口契约协作；平台组以自助接入率和业务等待时长验收，不按工单数量考核。

#### 反例 / 踩坑

先按前端、后端、测试职能切出交接流水线；Owner 名义明确但无决策权；平台组成为集中接单组；扩张效果没有基线。

#### 资深回答模板

「背景是团队半年从 8 人扩到 25 人；约束是业务不能停且领域知识集中；选项是职能制、业务域或平台 + 业务域；行动是渐进调整 Owner 和接口；结果对比跨团队等待、交付周期与认知负载基线；反思边界是否过细并预留缩编方案。」
:::

**追问链：**
1. 平台团队与业务团队如何划责任？
2. Owner 有责任却没有资源怎么办？
3. 团队缩编时哪些边界需要合并？

### D9. 重大技术决策证明错误后，如何止损和退出？

**考察点：** 决策回滚、沉没成本、迁移支持、信任

::: details 参考答案
#### 基础结论

把「判断错误」与「执行失职」分开。用预设成功指标和停止线判断继续、缩小或退出；承认新证据，优先控制新增暴露，再为已有消费者提供可执行迁移。

#### 原理深挖

可逆决策应快速试验，不可逆决策要分阶段下注。退出不是简单回滚代码：需考虑发布载体、数据兼容、消费者数量、合同与 RTO；数据不可逆时采用前向修复或补偿。

#### 工程场景

统一状态平台试点后接入耗时翻倍、故障定位变慢：冻结新接入，比较修复、保留最小协议和完全退出三项；保留兼容层，列出消费者与迁移 Owner，分批迁回并公开基于证据的复盘。

#### 反例 / 踩坑

为维护威信继续追加投入；只发弃用通知不给迁移资源；把试点团队当责任人；忽略已写入数据和长尾客户端；没有验证退出后的新风险。

#### 资深回答模板

「背景是试点指标持续劣化；约束是已有多个消费者与不可逆数据；选项是修复、缩小或退出；行动是冻结暴露、按 RTO 和数据可逆性迁移；结果看迁移完成率、故障与交付基线；反思决策前缺失的证据和下次停止线。」
:::

**追问链：**
1. 回滚会损害负责人威信吗？
2. 多个团队不愿迁移时如何处理？
3. 退出期间出现新故障由谁负责？
