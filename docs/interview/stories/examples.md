> **怎么用：** 以下三条是**可替换占位**样板——结构与答法可直接练，投递前把「〔〕」里的公司 / 业务 / 数字换成简历真实内容。模板说明见 [故事模板](/interview/stories/template)。

**替换规则：**

1. 保留技术决策与排查路径，改业务名词即可。
2. 数字用你能量化的量级（约、下降一半、从 x 天到 y 天），勿编造精确假指标。
3. 每条至少练熟 **2 分钟版**；30 秒背熟；5 分钟按提纲不背稿。

## 示例 A：Ant Design Vue 管理后台

**故事标题：** 〔ToB 运营中台〕复杂表格与权限体系落地  
**适用岗位：** A 资深前端（主） / B Lead（可加带人视角）  
**技术栈关键词：** Vue3、TypeScript、Ant Design Vue、Pinia、动态路由、RBAC  
**关联题库：** [Ant Design Vue](/interview/questions/04-admin-antdv) · [工程化](/interview/questions/03-engineering) · [Vue3](/interview/questions/02-vue3)

### STAR-L 骨架（填写参考）

| 段 | 内容要点 |
| -- | -------- |
| S | 〔SaaS / 内部运营〕后台，多角色、大表格、存量 jQuery / Vue2 混用；业务要 6 周内切到 Vue3 + Ant Design Vue |
| T | 我负责前端架构：权限与动态路由、通用 ProTable 封装、关键业务页迁移；验收=权限不漏、列表可交互、核心链路可上线 |
| A | 统一权限码；`componentMap` 动态路由；表格列配置 + 请求层取消与缓存；抽离 3～5 个业务组件进内部库 |
| R | 核心模块按期上线；列表交互从「卡顿投诉」降到可接受；新页面接入表格成本从「抄旧页」变成「配列」 |
| L | 权限前后端同码；表格先解决请求与渲染边界，再谈虚拟滚动；封装以「配置驱动」而不是「再造 AntDV」 |

### 30 秒版

> 我在〔运营中台〕负责 Vue3 + Ant Design Vue 的前端架构。当时最大约束是多角色权限不能漏、列表字段多还要可配。我主导做了权限码 + 动态路由，以及一套列配置驱动的 ProTable。核心模块按时上线，新列表页接入成本明显下降。

### 2 分钟版

> 项目是〔ToB 运营后台〕，角色多、菜单深，列表动辄几十列，还夹着导出和批量操作。我负责权限体系、动态路由和表格基建，成功标准是「直链进不了无权限页、按钮和接口同一套码、列表不靠复制粘贴堆页面」。
>
> 行动上分三块：第一，RBAC 落到菜单 / 路由 / 按钮三级，前端只做展示控制，强制校验对齐后端；第二，后端下发菜单，前端用组件名映射 `import`，避免动态字符串拼路径；第三，表格统一封装查询、分页、列设置和请求取消，业务页只配 columns 和 API。取舍上我没一上来上虚拟滚动，先把重复请求和整表重渲染砍掉，真有万行再对齐后端导出或虚拟列表。
>
> 结果是核心链路按期上线，列表相关投诉明显减少，后续业务页大多在表格封装上扩展。学习点是：权限同码、表格先治「请求与渲染」，封装别和 Ant Design Vue 抢职责。

### 5 分钟版（提纲口述）

1. **S+T（45s）：** 业务形态、角色复杂度、迁移工期、你的边界 vs 后端权限服务。  
2. **A1 选型（60s）：** 为何 Ant Design Vue；权限前端展示 vs 后端强制；动态路由 `componentMap` vs 全量静态路由。  
3. **A2 表格（75s）：** 列配置、远程排序筛选、请求竞态、`a-table` 性能手段；何时虚拟列表 / 何时导出。  
4. **A3 坑（45s）：** 例如刷新丢动态路由、超管 `*`、按钮藏了接口没拦——怎么发现、怎么修。  
5. **R+L（60s）：** 上线与复用结果；沉淀「权限码表 / 表格接入文档」；若重来会更早做 E2E 冒烟权限用例。

### 预埋追问与参考答法（≥3）

**追问 1：动态路由刷新后 404，你怎么处理？**

参考答法：登录后把菜单转成路由并 `addRoute`，同时在路由守卫里保证「已登录但路由未注入」时先注入再 `next`。刷新会丢内存路由，所以要在应用启动或守卫里根据 token 重拉菜单并重新注册；404 页与「无权限 403」分开，避免无权限被误当成找不到页。静态基础路由（登录、404）始终存在，业务路由全部动态加。

**追问 2：表格很卡，你怎么定位是渲染还是请求？**

参考答法：先看 Network：是否重复打列表、是否一次拉全量、是否瀑布请求。再看性能面板：是不是整表因父级状态变化重渲染、列里有没有重型自定义 render、有没有在 `dataSource` 上做深拷贝。我的顺序一般是：合并请求与取消过期请求 → 稳定 `rowKey` 与列定义 → 分页与字段裁剪 → 最后才考虑虚拟列表。前端优化同时会推动后端支持字段筛选和下发必要列。

**追问 3：按钮权限藏了，用户还能调接口怎么办？**

参考答法：前端隐藏只是体验，不是安全边界。正确做法是前后端同一权限码：网关或 Controller 校验；前端用指令 / 组件根据码表控制显隐。若只藏按钮，属于缺陷。联调时我会用无权限账号抓包验证 403，并把这类用例写进冒烟清单。超管也不该在前端写死「全放行」，应由后端下发全部码或明确的 `*` 策略并文档化。

**追问 4（加分）：组件沉淀和「为封装而封装」怎么划界？**

参考答法：出现 3 次以上相同模式（查询区 + 表格 + 分页 + 导出）再抽；封装暴露 columns、API、钩子，不把业务文案写死进组件。若业务差异大于 30%，宁可页面内组合 Ant Design Vue 原语，也不要搞八个 Boolean 开关的超级表格。

## 示例 B：uni-app / 小程序跨端

**故事标题：** 〔C 端营销 / 会员〕uni-app 多端统一与包体积治理  
**适用岗位：** A 资深前端（主） / 外包交付向也可讲节奏  
**技术栈关键词：** uni-app、微信小程序、H5、条件编译、分包、登录态  
**关联题库：** [uni-app / 小程序](/interview/questions/06-uniapp-miniprogram) · [Vant H5](/interview/questions/05-h5-vant) · [工程化](/interview/questions/03-engineering)

### STAR-L 骨架（填写参考）

| 段 | 内容要点 |
| -- | -------- |
| S | 同一套业务要出微信小程序 + H5（〔可选 App〕）；设计稿按小程序来，H5 有浏览器差异；要赶大促节点 |
| T | 我负责跨端架构与主流程：登录、分包、公共组件、发布流水线；验收=三端主路径可用、主包体积可控 |
| A | 条件编译隔离 API；登录态与静默登录策略；主包只留 tab 与首屏；CI 区分端构建与体验版上传 |
| R | 大促前主路径稳定；主包从超限边缘压回限额内；H5 / 小程序缺陷能按端分流排查 |
| L | 「能共用 UI，慎共用能力」；体积治理是持续过程；登录态要画时序图 |

### 30 秒版

> 我在〔会员小程序〕用 uni-app 同时交付微信小程序和 H5。难点是登录态、端差异和主包体积。我做了条件编译分层、分包裁剪和分端发布流水线，大促前主路径稳定，主包压回限额以内。

### 2 分钟版

> 业务要求一份代码覆盖小程序和 H5，工期绑大促。我负责跨端基建和登录、下单主链路。成功标准很硬：主包不超限、两端都能完成授权登录和下单、出问题能分清是哪一端。
>
> 行动上：第一，UI 尽量复用，支付、文件、定位等能力用条件编译和适配层，禁止页面里散落 `wx.`；第二，登录画清「未登录浏览 / 静默 / 强制授权」时序，token 刷新与 401 重试只放在请求层；第三，主包只留 tabBar 和首屏，活动页与个人中心下级进分包，图片走 CDN，无用页面从 pages 剔除。取舍上没有强行一套 UI 框架打天下，H5 个别页用更合适的移动组件，但业务模型保持一致。
>
> 结果是节点前上线，体积从「上传报警」回到安全区，后续活动页大多在分包迭代。学习点是跨端先隔离能力差异，再谈复用率数字。

### 5 分钟版（提纲口述）

1. **S+T：** 多端范围、大促时间盒、你与原生 / 后端的边界。  
2. **A1 架构：** uni-app 目录、条件编译、适配层；什么坚决不共用。  
3. **A2 登录与存储：** code 换会话、cookie vs storage、H5 与小程序差异、安全注意点。  
4. **A3 体积与发布：** 分包策略、依赖分析、体验版 / 正式版、H5 部署。  
5. **坑：** 例如 iOS 时间格式、键盘顶起、分包异步组件、权限声明遗漏。  
6. **R+L：** 指标与复盘；「端差异清单」沉淀。

### 预埋追问与参考答法（≥3）

**追问 1：主包又超了，你的排查顺序？**

参考答法：先看微信开发者工具的代码依赖分析，找出被主包引用的大图、公共 js、误放在主包的业务页。然后检查是否有「分包页面被主包 import」导致依赖上浮。再砍静态资源、延迟非首屏组件、确认 tabBar 页面最小集。治本是约定：新页面默认进分包，进主包要说明理由。CI 里可以对主包大小做阈值，超了阻断。

**追问 2：小程序和 H5 登录怎么统一心智？**

参考答法：对业务层只暴露 `ensureLogin()` / `getSession()`，内部按端走不同授权。小程序用 code 换会话；H5 可能是 OAuth 或短信。token 存在各自可靠存储，请求拦截器统一带鉴权头，401 时清会话并引导登录，避免各页面自己 `reLaunch`。不要在页面里直接调 `uni.login` 散落多处，否则一端改策略另一端漏改。

**追问 3：条件编译把代码写乱了怎么办？**

参考答法：页面模板少写 `#ifdef`，差异下沉到 `api/`、`platform/` 适配模块；页面只调统一接口。若某端差异超过页面 30%，可以接受独立页面文件，比满屏条件编译更可读。Code Review 重点看「有没有在业务组件里直接写端 API」。

**追问 4（加分）：如何保证发版不踩错端？**

参考答法：流水线按 `mp-weixin` / `h5` 分 job；环境变量与请求 baseURL 绑定；小程序上传体验版与 H5 预发分开验收清单。版本号与 git tag 对齐，出问题能回答「当前线上是哪次构建」。

## 示例 C：AI + Java Spring Boot + Vue 全栈快速交付

**故事标题：** 〔内部工具 / 试点业务〕AI 辅助 Spring Boot + Vue 两周闭环  
**适用岗位：** C 全栈偏前（主） / A 资深（差异化） / 创业 AI 面主线  
**技术栈关键词：** Vue3、Spring Boot、MyBatis-Plus、MySQL、AI vibe coding、接口契约  
**关联题库：** [Java 全栈偏前](/interview/questions/07-java-fullstack) · [AI / vibe coding](/interview/questions/09-ai-vibe-coding) · [前端系统设计](/interview/questions/11-frontend-system-design)

> **叙事边界（务必遵守）：** 主身份是前端；Java 用来证明「能闭环、能联调、能控质量」，不碰 JVM 调优 / 分布式事务论文题。详见 [总览 · Java 叙事边界](/interview/00-overview)。

### STAR-L 骨架（填写参考）

| 段 | 内容要点 |
| -- | -------- |
| S | 〔内部审批 / 运营小工具〕要快；后端人手不足；栈允许 Spring Boot 单体 + Vue3 管理端 |
| T | 我以前端为主独立扛简单后端：表设计、CRUD、鉴权对接、管理页；验收=可演示闭环 + 基本校验与审计 |
| A | 先定接口契约与表结构；AI 生成样板代码后人工审查；统一异常与校验；前端联调与权限；上线检查清单 |
| R | 〔约 1～2 周〕交付可演示版本；返工集中在业务规则而非「跑不起来」；后续可交给后端增强 |
| L | AI 加速样板，人负责边界与正确性；契约先行；简单后端也要有校验、日志、权限意识 |

### 30 秒版

> 在〔内部工具〕项目里，后端资源紧，我用 Vue3 做管理端，并用 AI 辅助搭 Spring Boot + MyBatis-Plus 的简单接口，两周左右跑通闭环。重点不是生成代码快，而是契约、校验和审查——AI 写样板，我把关边界和联调质量。

### 2 分钟版

> 场景是〔某内部流程工具〕，要快速验证，后端排期排不上完整班底。我的任务是前端页面 + 足够用的 Spring Boot API，做成可演示、可给少数人用的版本。
>
> 做法是契约先行：先定资源、字段、错误码和权限，再让 AI 按模板生成 Controller / Service / Mapper 和 Vue 列表表单页。我审查的重点是：校验是否在服务端、有没有越权查询、分页与删除是否安全、异常是否统一、密钥与配置有没有进仓库。前端按契约 mock 并行，联调时用真实鉴权走一遍增删改查和失败路径。取舍上坚持单体 CRUD，不上微服务，Redis 只在真有会话或热点需要时加。
>
> 结果是按节点演示通过，后续若业务做大可以交给专职后端演进。学习点是：vibe coding 的产能来自「模板 + 审查清单」，不是放任自动生成。

### 5 分钟版（提纲口述）

1. **S+T：** 为什么全栈偏前合理；成功标准与不做清单（微服务、复杂工作流引擎等）。  
2. **A1 契约与模型：** 表字段、DTO、幂等与删除策略；和前端表单怎么对齐。  
3. **A2 AI 工作流：** 提示词怎么写、生成粒度、审查清单（安全 / 校验 / N+1 / 事务边界）。  
4. **A3 联调与质量：** 统一响应体、错误码、日志、基础权限；前端怎么验 401/403/校验失败。  
5. **R+L：** 交付结果；哪些交给 AI、哪些必须人手；若重来会先写 OpenAPI / 契约测试。

### 预埋追问与参考答法（≥3）

**追问 1：AI 生成的代码你怎么审查？怕不怕线上炸？**

参考答法：按清单审，不按「能不能跑」审。清单至少包括：入参校验、权限与数据范围、SQL 注入与模糊查询、删除/更新条件是否带主键与租户、异常是否泄露内部信息、配置与密钥、无用接口是否暴露。先本地跑通主路径和失败路径，再小范围灰度。AI 加速的是样板，责任仍在提交者——这一点我会主动说清楚。

**追问 2：为什么是 Spring Boot 而不是 Node 做后端？**

参考答法：团队或公司存量是 Java、招聘与运维更熟 Java，长期交接成本更低；我本人用 AI 补齐 Spring Boot CRUD 效率足够。Node 我更多用在工程脚本或简单 BFF。选型看协作与交接，不是个人偏好炫技。若面试官栈是 Node，我会说明「原理上都是 API + DB，我可以适应，但近期实战闭环在 Spring Boot」。

**追问 3：前后端错误码和校验怎么对齐？**

参考答法：后端 Bean Validation + 统一异常处理，返回稳定结构（code / message / data）；业务错误与系统错误分开。前端表单先做体验校验，提交后以后端为准展示字段错误。联调时故意传缺字段、越权 id，确认不会「前端拦了后端没拦」。文档里写清常见 code，避免每个页面 if-else 魔数。

**追问 4（加分）：Lead 问你——这种交付怎么保证可维护？**

参考答法：目录与分层固定、README 写清启动与环境变量、关键业务规则留注释或短文档、避免在 AI 生成代码上叠更多生成而不重构。约定「超过简单 CRUD 就拉专职后端」，前端 Lead 守的是边界，不是把团队带进不可维护的天才代码。
