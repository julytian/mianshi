# 数据库与 Prisma 面试题库

> **怎么用：** 普通题先按「概念 → 机制 → 工程边界」口述 1～2 分钟；深层题按「结论 → 原理 → 方案 → 反例 → 验证」展开。重点不是背 SQL，而是把查询正确性、性能、事务、安全和发布风险讲清楚。

> **岗位定位：** 面向 10 年资深前端偏全栈岗位。本模块负责 MySQL 原理、SQL 性能与 Prisma 数据访问实践；NestJS 请求链见 [NestJS 题库](/interview/questions/13-nestjs)。数据库负责约束、并发控制和持久化，Prisma 提供类型化数据访问与迁移工具，应用层负责用例编排、授权、幂等和错误契约，三者不能互相冒充。

> **版本边界：** MySQL 以 InnoDB 和 MySQL 8.0 常见能力为主要语境；CTE、窗口函数、`EXPLAIN ANALYZE`、锁行为及执行计划字段应以实际数据库版本、隔离级别和配置验证。Prisma 的生成器、驱动适配器、关系加载策略、事务选项及 Preview 能力随版本演进，回答只依赖稳定概念；具体 API 以项目锁定版本的官方文档、类型声明和测试为准。

## 一、关系模型、SQL 与索引

### Q1. MySQL 常用数据类型如何选择，金额、时间和 JSON 分别有什么边界？

**考察点：** 类型语义、精度、时区、可查询性、存储边界

::: details 参考答案

类型选择先看业务语义、取值范围、比较规则和查询模式，再看空间。整数按上限选择并明确有无符号；字符串区分定长与变长，长度、字符集和排序规则会影响索引大小及比较结果。布尔值在 MySQL 中通常落为数值语义，应用层仍应保持明确类型。

金额优先用最小货币单位的整数，或精度固定的 `DECIMAL(p, s)`；不能用 `FLOAT` / `DOUBLE` 承担需要精确相等的财务计算。时间要先定义语义：跨时区事件通常存 UTC 时间点并在展示层转换；纯日期、营业日或用户设定的本地时刻不应强行当 UTC 瞬间。`TIMESTAMP` 与 `DATETIME` 的范围、时区转换行为不同，必须结合版本和连接时区测试。

`JSON` 适合结构有弹性、主要整体读写或少量路径查询的附属属性，不适合逃避建模。高频筛选、排序、关联和强约束字段应提升为普通列；需要索引 JSON 路径时，使用数据库版本支持的生成列或函数索引并用执行计划验证。Prisma 字段类型只负责映射，不能替代数据库精度、默认值和约束设计。

:::

**追问：** 订单金额应该存「分的整数」还是 `DECIMAL`？

::: details 追问参考答案

两者都可，取决于币种和计算规则。单一币种且最小单位固定时，用整数便于精确比较和跨语言传输；存在多币种、小数位不同或税率分摊时，`DECIMAL` 更贴近领域表达。无论哪种，都要同时保存币种、舍入规则并禁止 JavaScript `Number` 直接做最终财务计算；Prisma 返回类型的实际表示也要按锁定版本确认。

:::

### Q2. 主键、唯一键、外键和业务唯一性应该怎样分工？

**考察点：** 实体身份、约束、幂等、参照完整性

::: details 参考答案

主键标识一行，要求稳定、非空且尽量不承载会变化的业务含义。自增整数写入紧凑、聚簇索引局部性好，但跨系统生成和暴露规律需要评估；UUID 等分布式 ID 便于跨节点生成，但格式、顺序性和索引尺寸会影响存储与写放大，不能只比较「是否唯一」。

唯一键表达数据库可强制执行的业务不变量，例如「同一租户下邮箱唯一」应是 `(tenant_id, normalized_email)`，而不是只给 `email` 加唯一。应用层先查再插不能防并发，最终仍需唯一约束兜底，并把冲突映射成幂等成功或明确业务错误。

外键维护参照完整性，适合边界清晰、同库事务内的核心关系；级联更新删除必须谨慎，避免大范围隐式写入。高吞吐、分片、跨库或遗留系统可能不建物理外键，但这不是「不需要完整性」，而是把校验、清理和审计责任移到应用与运维流程。Prisma Relation 描述对象关系；是否生成或依赖数据库外键，取决于 relation mode、数据库能力和项目配置，不能把 Schema 中有 Relation 等同于数据库一定存在外键。

:::

**追问：** 软删除后怎样允许原值重新注册，又保持「有效记录唯一」？

::: details 追问参考答案

MySQL 没有通用的 partial unique index，可增加生成列：`active_unique_key = CASE WHEN deleted_at IS NULL THEN normalized_email ELSE NULL END`，再创建唯一索引 `(tenant_id, active_unique_key)`。MySQL 唯一索引允许多行含 `NULL`，因此多轮删除留下的历史记录可共存；同租户两条有效记录使用相同规范化值时则会冲突。

`normalized_email` 的大小写、空白和 Unicode 规范化规则必须固定：可由应用写入独立列，或使用目标 MySQL 版本允许的确定性生成表达式，并明确索引列的 collation。应用预查只改善提示，并发兜底仍是数据库唯一约束；恢复旧记录时若已有新有效记录，应拒绝或先完成显式合并。若历史还要区分每轮注册身份，应保留独立主键、删除时间和审计事件，不能用邮箱唯一键代表历史实体身份。

:::

### Q3. `INNER JOIN`、`LEFT JOIN` 等 JOIN 如何选择，为什么结果集会膨胀？

**考察点：** 连接语义、基数、重复行、聚合正确性

::: details 参考答案

`INNER JOIN` 只保留两侧匹配行；`LEFT JOIN` 保留左表全部行，右侧不匹配列为 `NULL`；`RIGHT JOIN` 可改写为交换表顺序的 `LEFT JOIN`；`CROSS JOIN` 产生笛卡尔组合。选择依据是业务是否要保留未匹配主体，而不是哪种看起来更快。

结果集膨胀来自关系基数。一个订单关联 3 个商品和 2 张标签，若同时展开两个一对多关系，可能得到 6 行，不是 5 行。此时对订单金额直接 `SUM` 会重复累计，分页和 `COUNT(*)` 也会失真。应先分别聚合、使用 `EXISTS` 做存在性判断、拆分查询，或明确按主实体 `COUNT(DISTINCT id)`，但 `DISTINCT` 不是掩盖错误建模的万能补丁。

过滤条件位置也会改变语义：对 `LEFT JOIN` 右表字段的条件放在 `WHERE`，常把未匹配行过滤掉，效果接近内连接；放在 `ON` 才是限制匹配行。Prisma `include` 表达关系加载，不代表数据库一定执行单条 JOIN；实际查询形态由版本、连接器和加载策略决定，应看查询日志和执行计划。

:::

**追问：** 列表查询需要订单和商品数量，怎样避免 JOIN 膨胀？

::: details 追问参考答案

优先把商品按 `order_id` 聚合后再与订单连接，或使用相关聚合、预计算统计列，避免先展开明细再分页。列表分页必须以订单作为主集合稳定排序，先确定订单 ID，再获取聚合结果。若用 Prisma，可选择 `_count`、分两次批量查询后按 ID 合并，或在参数化原生 SQL 中完成；最终以 SQL 日志和数据规模验证，而不是假设 ORM 自动优化。

:::

### Q4. 子查询、CTE 和窗口函数分别适合什么场景？

**考察点：** SQL 表达、可读性、执行计划、分析计算

::: details 参考答案

子查询适合存在性判断、标量计算和先筛后关联，例如 `EXISTS` 常比连接后去重更准确地表达「是否存在」。相关子查询会引用外层行，优化器可能改写，也可能按大量外层行反复工作，必须看计划而不是按语法判断快慢。

CTE 用名字拆解复杂查询、复用中间逻辑或表达递归层级。MySQL 8.0 支持 CTE，但是否物化、合并及由此产生的性能影响与版本和查询形态有关；CTE 首先是可读性和边界工具，不保证比子查询快。递归 CTE 要限制深度并防环。

窗口函数在不折叠明细行的前提下计算排名、累计值、分组前后值，例如 `ROW_NUMBER()` 取每组最新记录。它与 `GROUP BY` 的关键差异是保留行粒度。窗口排序可能产生临时表或排序成本，需控制分区和数据量。Prisma Client 对复杂分析 SQL 的抽象有限时，可以使用 View、专门读模型或参数化原生 SQL，但权限、字段白名单和结果类型校验仍由应用负责。

:::

**追问：** 「每个用户最近一笔订单」为什么常用窗口函数？

::: details 追问参考答案

可按 `user_id` 分区，以 `created_at DESC, id DESC` 排序生成 `ROW_NUMBER()`，再取序号 1，能明确处理时间相同的稳定决胜规则。仅 `GROUP BY user_id` 配 `MAX(created_at)` 拿不到同一行的其他字段，回连时还可能命中多行。MySQL 8.0 之前需用反连接、相关子查询或聚合回连，并同样处理并列值。

:::

### Q5. B+ Tree 索引为什么适合范围查询？

**考察点：** 页结构、树高、局部性、范围扫描

::: details 参考答案

InnoDB 常规索引使用 B+ Tree。内部节点保存导航键和子页指针，叶子节点保存记录或主键值；高扇出使大量记录也能维持较低树高。查到范围起点后，叶子页按键序组织并可顺序扫描后续页，所以 `BETWEEN`、前缀范围和排序读取具有良好局部性。

聚簇主键索引的叶子包含整行；二级索引叶子通常包含索引列和主键，命中后若还需其他列，要按主键回到聚簇索引。索引并非免费：每个二级索引增加写入维护、页分裂、缓存占用和统计信息成本；低选择性条件也不一定值得走索引。

B+ Tree 不天然适合所有查询。普通索引无法高效支持任意包含匹配、复杂 JSON 路径或空间相似度；`LIKE '%word%'` 通常不能利用普通前缀索引定位。应根据访问模式选择全文、空间索引、搜索系统或专用结构，并以真实计划验证。

:::

**追问：** 为什么随机主键可能比单调主键带来更多写入成本？

::: details 追问参考答案

聚簇索引按主键组织。单调键多数写入落在右侧热点页，局部性较好；完全随机且较宽的键会把插入分散到更多页，增加缓存压力、页分裂和所有二级索引携带的主键尺寸。但单调键也可能形成并发热点并暴露业务量。选择应结合生成方式、写并发、分片需求和基准测试，不能把 UUID 一概判为错误。

:::

### Q6. 联合索引与最左匹配怎样理解？

**考察点：** 索引键顺序、等值与范围、排序复用

::: details 参考答案

联合索引 `(tenant_id, status, created_at)` 按完整键的字典序排列，因此可高效定位 `tenant_id`，也可继续利用 `status` 和 `created_at`。如果跳过首列只查 `status`，通常不能直接利用该索引的有序前缀完成精准定位；优化器的跳跃扫描等能力属于版本和成本敏感优化，不能当通用保证。

列顺序不应机械遵循「选择性最高放最前」。要从真实查询模式出发：多租户系统通常先放租户隔离列；等值条件一般放在需要范围扫描或排序的列前；`ORDER BY` 是否可复用索引，还受过滤、方向和后续列约束影响。一个范围条件之后的列往往难再用于缩小扫描区间，但仍可能参与索引下推或覆盖。

设计时列出高频查询的过滤、排序、返回列和基数，再用少量复合索引覆盖主路径。不要为每种条件排列创建索引，写成本和空间会失控。Prisma 的 `@@index` 只是声明索引，最终 DDL、前缀长度、排序方向和数据库支持应检查 migration SQL。

:::

**追问：** 查询 `WHERE tenant_id=? AND created_at>? ORDER BY created_at`，索引中要不要放 `status`？

::: details 追问参考答案

若查询不限制 `status`，把它夹在 `tenant_id` 与 `created_at` 之间会破坏目标排序范围的连续性，通常不适合这条路径。若主查询总是 `status = ?`，则 `(tenant_id, status, created_at)` 更合理。不要凭字段重要性决定；应按具体谓词组合拆分主路径，比较候选索引的扫描行数、排序和写入成本。

:::

### Q7. 覆盖索引、回表和索引下推分别是什么？

**考察点：** 二级索引读取、I/O、ICP 边界

::: details 参考答案

覆盖索引是查询所需的过滤、排序和返回列都能从某个索引取得，无需再访问聚簇记录。它描述查询与索引的关系，不是一种独立索引类型。回表指通过二级索引找到主键后，再访问聚簇索引取其余列；大量离散回表会增加随机访问。

索引条件下推（ICP）让存储引擎在扫描索引时就评估可由索引列判断的部分条件，减少返回给 Server 层并回表的记录。它不等于把任意 `WHERE` 都变成索引定位，也不保证消除回表。是否出现可看 `EXPLAIN Extra`，但仍要结合实际扫描和耗时。

为了覆盖而把大量宽列塞进索引会放大写入、缓存和页数量。列表页应先减少 `SELECT *`，只覆盖高频小字段；大文本、JSON 和低频展示字段留给详情查询。Prisma 用 `select` 收窄返回字段有助于减少传输和对象构造，但数据库是否覆盖仍取决于物理索引和生成 SQL。

:::

**追问：** `select` 少几个字段就一定能走覆盖索引吗？

::: details 追问参考答案

不一定。只有过滤、排序、连接和返回所需的全部列都在同一索引中，才可能覆盖；事务可见性检查和执行器行为也应以计划为准。Prisma `select` 只是让生成 SQL 少取列，不会自动创建索引。应抓取实际 SQL，用 `EXPLAIN` / `EXPLAIN ANALYZE` 查看所选索引和真实工作量，再判断是否值得调整索引。

:::

### Q8. 看 `EXPLAIN` 时如何理解访问类型、`key`、`rows` 和 `Extra`？

**考察点：** 执行计划阅读、估算、排序与临时表

::: details 参考答案

先看访问路径，再看估算工作量。`type` 从常见的 `const`、`eq_ref`、`ref`、`range` 到 `index`、`ALL`，大体反映定位方式，但不能脱离返回行数下结论；小表全扫可能完全合理。`possible_keys` 是候选，`key` 是最终选择，`key_len` 可辅助判断联合索引实际使用到哪些部分。

`rows` 是基于统计信息的估算扫描行数，不是实际值；还要结合过滤比例和连接顺序理解总成本。`Extra` 中 `Using index` 常表示覆盖读取，`Using index condition` 表示索引条件下推，`Using temporary`、`Using filesort` 提示额外临时结构或排序，但名字不等同于一定落磁盘，也不应见到就判故障。

计划只是诊断入口。要核对 SQL 参数分布、统计信息、表规模、返回行数和慢日志；支持时用 `EXPLAIN ANALYZE` 对比估算与实际。它会真正执行查询，写操作或高成本查询必须在安全环境评估，不能直接在生产随意运行。

:::

**追问：** `key` 命中了索引，为什么查询仍可能很慢？

::: details 追问参考答案

命中索引只说明选择了该访问路径，不说明扫描少。低选择性条件可能扫描大量索引项并大量回表；排序、临时表、宽行传输、锁等待和客户端消费也可能占主要时间。应继续看估算与实际行数、循环次数、回表量、排序和等待事件，并用完整请求 trace 区分数据库执行慢还是连接池排队、网络及应用处理慢。

:::

### Q9. 深分页、游标分页和稳定排序如何选择？

**考察点：** Offset 成本、Keyset Pagination、一致性

::: details 参考答案

`LIMIT offset, size` 简单且支持跳页，但数据库通常仍需定位、扫描并丢弃前 `offset` 行；排序和回表越重，深页成本越高。它适合数据量可控、后台需要页码跳转且深页不常访问的场景。

游标分页也叫 Keyset Pagination，用上一页最后一行的排序键继续查询，例如按 `(created_at DESC, id DESC)` 排序后，下一页条件使用对应的字典序边界。它能让扫描从索引位置继续，适合无限滚动、大表和导出。排序键必须唯一且稳定，单用可能重复的时间会漏行或重行。

并发写入下，任何分页都要定义一致性：实时列表允许新数据插入时，可接受相邻页轻微变化；审计导出则应固定截止水位、版本或快照。游标应编码必要排序键并校验租户、筛选条件和方向，不能让客户端提供任意 SQL 字段。Prisma `cursor` / `skip` / `take` 的具体组合和生成 SQL需按锁定版本验证。

:::

**追问：** 产品坚持显示总页数，又要求大表翻到最后一页，怎么办？

::: details 追问参考答案

先拆需求：总数可异步、缓存或给近似值，浏览用游标分页；「最后一页」若是找最旧数据，可反转排序从另一端读取，而不是深 Offset。若业务确需精确页码和任意跳转，可维护搜索索引、分段锚点或专用读模型。应向产品说明实时精确总数、任意跳页与低延迟的成本三角，并用真实数据验证方案。

:::

## 二、事务、并发与连接

### Q10. ACID 分别是什么，应用事务边界怎样划？

**考察点：** 原子性、一致性、隔离性、持久性、用例边界

::: details 参考答案

原子性表示事务内操作整体提交或回滚；一致性表示约束和业务不变量在事务前后成立，它不是数据库自动理解全部业务；隔离性描述并发事务互相可见的程度；持久性表示提交后的结果在承诺的故障模型下可恢复，具体强度受日志刷盘、复制和配置影响。

事务边界通常与一个数据库内的业务用例一致，例如创建订单与订单明细应同事务提交。边界过小会暴露中间状态，过大会延长锁持有、占用连接并增加冲突。网络调用、发消息和文件上传不应无控制地放在数据库事务中等待；跨系统一致性通常通过 Outbox、幂等消费者、状态机和补偿实现。

Prisma 的 `$transaction` 提供批量或交互式事务抽象，但底层隔离、锁、超时和连接仍由数据库与连接器决定。应用必须处理唯一冲突、死锁、超时和「客户端超时但数据库结果未知」等结果，而不是看到 Promise reject 就认定一定未提交。

:::

**追问：** 事务提交后再发 MQ，进程在两步之间崩溃怎么办？

::: details 追问参考答案

用 Outbox 模式把业务变更和待发布事件写入同一数据库事务，再由独立发布器可靠投递并标记状态；消费者按事件 ID 幂等。这样把「数据库提交成功但消息丢失」转成可重试的本地记录。若基础设施支持事务消息也要理解其故障语义。前端只展示可恢复状态，不应通过重复点击模拟补偿。

:::

### Q11. 隔离级别与脏读、不可重复读、幻读是什么关系？

**考察点：** 并发现象、SQL 标准、InnoDB 实现差异

::: details 参考答案

脏读是读到其他事务尚未提交的数据；不可重复读是同一事务两次读取同一行得到不同已提交版本；幻读通常指按同一谓词再次查询，出现或消失了满足条件的行。SQL 标准用这些现象描述隔离级别，但数据库实现还可能防止更多或不同异常，不能只背一张表。

`READ COMMITTED` 通常每个语句建立新的一致性视图，减少长快照影响，但同一事务两次快照读可能不同。InnoDB 常见默认是 `REPEATABLE READ`，一致性读在事务内通常复用快照；当前读和写操作仍读取并锁定较新版本，并可能使用间隙锁防止范围内插入。`SERIALIZABLE` 隔离更强，但并发和等待成本更高。

选择隔离级别要从不变量出发。账户、库存、排班等不能只靠「读起来一样」保证正确，还需条件更新、唯一约束或显式锁。实际默认级别可能被云数据库、驱动或会话配置修改，必须查询运行时设置并做并发测试。

:::

**追问：** 可重复读是否意味着事务中的所有查询永远看到同一份数据？

::: details 追问参考答案

不是。InnoDB 的普通一致性读通常复用快照，但锁定读如 `SELECT ... FOR UPDATE`、更新和删除属于当前读，会基于较新可见版本并加锁；事务自身写入也对自己可见。DDL、自动提交和不同数据库实现还有额外边界。因此排查时要区分快照读与当前读，并确认事务何时真正开始、连接是否被复用及隔离级别。

:::

### Q12. MVCC、快照读和当前读如何协作？

**考察点：** 版本链、Read View、Undo、可见性

::: details 参考答案

MVCC 让读取者通过行版本和可见性规则读取合适版本，从而减少普通读写互相阻塞。InnoDB 记录事务相关的隐藏信息，旧版本通过 Undo 链恢复；一致性视图根据活跃事务等信息判断哪个版本可见。具体内部字段和清理机制会随实现演进，面试重点应放在可见性与成本，而不是死背源码名。

普通 `SELECT` 多为快照读，读取符合 Read View 的版本且通常不加行锁。`SELECT ... FOR UPDATE` / `FOR SHARE`、`UPDATE`、`DELETE` 属于当前读，需要读取可操作的新版本并加相应锁。MVCC 不代表没有锁，也不能避免写写冲突。

长事务会长期保留旧版本清理需求，增加 Undo 压力并让观测与故障恢复变复杂。应用应缩短事务、避免在事务中等待用户或外部 API，监控长事务与历史版本积压。Prisma 事务只是执行入口，无法屏蔽这些数据库成本。

:::

**追问：** 为什么一个长时间不提交的只读事务也可能有危害？

::: details 追问参考答案

若它持有较老的一致性视图，数据库可能需要保留仍对该事务可见的旧版本，延迟清理并增加存储与扫描压力；它也长期占用连接。危害大小取决于隔离级别、查询和数据库实现。治理上设置事务与语句超时、避免交互式等待、监控最老事务和 Undo 历史，而不是只关注是否执行了写操作。

:::

### Q13. 行锁、间隙锁、死锁和锁等待怎样区分？

**考察点：** 锁范围、索引、并发故障、重试

::: details 参考答案

行锁是口语化称呼，InnoDB 实际通常锁索引记录；条件没有合适索引时，扫描和锁定范围可能远超预期。间隙锁锁住索引记录之间的范围，Next-Key Lock 组合记录与间隙，用于特定隔离级别下的范围并发控制。唯一索引等值命中、隔离级别和查询形态会影响锁范围，应通过版本对应文档和实验确认。

锁等待是事务等待另一个事务释放所需锁，可能最终成功或超时。死锁是形成等待环，数据库检测后选择一个事务回滚，让其他事务继续。死锁不是简单把超时调大能解决；应缩短事务、统一访问顺序、增加正确索引并减少一次锁定的行数。

应用要分类处理：死锁和部分瞬态冲突可在整个事务边界外做有限、带退避的重试；业务冲突应返回明确结果；未知提交结果先按幂等键查询。日志需关联 SQL、事务、锁等待与请求 TraceId，不能只打印 ORM 异常文案。

:::

**追问：** 为什么缺少索引会放大更新语句的锁影响？

::: details 追问参考答案

数据库必须扫描更多索引记录才能判断哪些行满足更新条件，扫描过程中可能锁定更多记录或范围，增加等待和死锁概率；最终只更新少量行也不代表锁足够小。应为定位条件建立合适索引，限制批次并查看锁监控与执行计划。索引会增加写成本，所以要针对真实更新路径设计，而不是给所有字段都加索引。

:::

### Q14. 连接池、超时和连接泄漏应怎样治理？

**考察点：** 有界资源、排队、超时分层、生命周期

::: details 参考答案

数据库连接昂贵且数据库可承载并发有限，连接池用于复用并限制并发，不是越大越快。池大小应结合数据库总连接预算、应用实例数、查询耗时和目标吞吐计算；所有实例池上限之和还要给管理、迁移和故障恢复留余量。

超时要分层：获取连接超时限制池排队，连接超时限制建连，语句或事务超时限制数据库工作，请求 Deadline 限制用户等待。只在 HTTP 层超时而不取消数据库工作，会造成客户端已失败、后台仍占连接。驱动是否支持取消、取消后的连接状态及 Prisma 暴露能力需按版本验证。

连接泄漏常见于手工获取后异常路径未释放、流式结果未消费、事务悬挂或热重载重复创建 Client。应使用框架托管生命周期和 `finally`，单进程复用 Prisma Client，记录池等待、使用中连接、查询耗时与超时。Prisma 的具体池参数受连接器、驱动适配器及部署方式影响，不能套用单一参数名。

:::

**追问：** 请求超时后，数据库查询会自动停止吗？

::: details 追问参考答案

不一定。HTTP Promise 被拒绝或调用方放弃响应，只说明上层不再等待；底层查询可能继续执行并占用连接。要确认驱动和 Prisma 版本是否支持传播取消，数据库是否配置语句超时，以及事务取消后连接能否安全复用。对写操作还要处理结果未知：用幂等键和状态查询确认，不能盲目重发。

:::

## 三、Prisma 数据访问与迁移

### Q15. Prisma Schema、Model、Relation 和 Client 分别是什么？

**考察点：** ORM 抽象、数据库映射、类型生成、边界

::: details 参考答案

Prisma Schema 是声明数据源、Client 生成配置和数据模型的配置文件。Model 描述应用可操作的实体字段，并通过 `@map` / `@@map` 等映射现有数据库命名；字段属性可声明 ID、唯一性、默认值和索引。最终是否形成数据库约束，要看迁移 SQL、relation mode 和数据库支持。

Relation 由关系字段和底层标量外键字段共同表达一对一、一对多或多对多。关系字段主要存在于 Prisma 数据模型和 Client API 中，不等于数据库里多了一列。必选/可选关系、级联动作和组合唯一约束要与真实业务生命周期一致。

Prisma Client 根据 Schema 生成类型化查询 API，减少字符串字段和手写映射错误，但它不是领域模型、授权层或数据库优化器。应用服务仍负责租户与权限条件、用例事务和错误映射；数据库仍负责真实约束、执行计划和锁。生成器名称、输出路径和初始化方式是版本敏感配置，应以锁定版本官方文档为准。

:::

**追问：** Prisma Schema 写了 `@unique`，是否就能认为生产库已有唯一约束？

::: details 追问参考答案

不能。Schema 只是期望模型；必须确认对应 migration 已生成、评审并通过 `migrate deploy` 应用到目标环境，或在 introspection 场景确认它来自真实数据库。漂移、失败迁移和人工改库都可能让两者不一致。生产验收应检查迁移历史与数据库 DDL，并保留应用对唯一冲突的正确映射。

:::

### Q16. Prisma 的 `select`、`include`、分页和关系查询怎样使用？

**考察点：** 字段投影、关系加载、分页、N+1

::: details 参考答案

`select` 明确返回字段，减少敏感字段泄露、网络传输和对象构造；`include` 加载关系。两者应围绕 API 输出模型设计，不能把完整数据库对象直接返回给前端。嵌套关系也要继续收窄字段和数量，避免一个详情接口无界展开整张关系图。

页码分页常用 `skip` / `take`，实现简单但深页仍受 Offset 成本影响；游标分页用稳定唯一排序键和 `cursor` 等能力，具体是否需要跳过游标行及反向读取语义按锁定版本测试。无论哪种，排序都应带唯一决胜列，筛选和租户条件必须固定进入查询。

关系查询要警惕 N+1。循环中逐条查询关系会产生大量往返；可用嵌套读取、批量 `findMany` + `in` 后按键组装、`_count` 或专用 SQL。Prisma 在不同版本和数据库上的关系加载实现可能是多查询、批处理或数据库 JOIN，不能仅凭 `include` 猜测；用查询日志和 Trace 统计实际 SQL 数量与总耗时。

:::

**追问：** 为什么 `include` 不是解决 N+1 的绝对答案？

::: details 追问参考答案

它能表达一次 API 调用所需关系，但底层可能生成 JOIN 或若干批量查询，具体取决于连接器、版本和关系加载策略；深层嵌套与无界集合仍可能造成结果膨胀、内存和传输压力。应先限制字段与每层基数，再查看实际 SQL 数、扫描行和响应体；复杂读场景可拆成批量查询或专用读模型。

:::

### Q17. Prisma Migration、Seed 和生产部署应怎样分工？

**考察点：** 迁移工作流、环境边界、可重复初始化

::: details 参考答案

开发环境使用迁移开发命令根据 Schema 生成并应用 migration，允许开发者检查 SQL、修正数据迁移步骤并重建本地库；生产使用 `migrate deploy` 应用已提交的待执行迁移，不在生产根据 Schema 临时生成。命令细节和配置位置随 Prisma 版本变化，应以项目锁定版本为准。

迁移文件是可审查的发布资产。加索引、改非空、改类型和删列可能锁表或失败，必须结合表规模、数据库在线 DDL 能力和回滚方案评审。Schema 更新、生成 Client、应用部署与数据库迁移要安排兼容顺序，不能把「CI 命令成功」等同于零停机。

Seed 用于可重复写入基础字典、测试账号或开发样例，不负责生产大规模历史数据修复。它应幂等、可区分环境，禁止写死真实密钥和个人数据。生产数据回填用可观测、可暂停、分批和可重入的独立任务，并与结构迁移分离。

:::

**追问：** 为什么生产环境不应直接运行开发迁移命令？

::: details 追问参考答案

开发迁移流程面向迭代，会比较 Schema 与开发库、生成迁移并可能要求重置处理漂移；这些交互和破坏性选项不适合作为生产发布策略。生产只应执行已评审、版本化的 migration，使用最小权限发布身份，并在执行前检查备份、锁影响和兼容顺序。具体命令行为仍以锁定 Prisma 版本文档为准。

:::

## 四、深层场景题

### D1. 如何从查询模式设计联合索引，而不是从字段列表猜索引？

**考察点：** 工作负载、列顺序、覆盖、写成本、验证闭环

::: details 参考答案

#### 基础结论

索引服务于具体查询模式。先收集高频且高成本 SQL 的过滤、连接、排序、分组、返回列与参数分布，再设计能减少扫描和排序的最小索引集合。

#### 原理深挖

联合索引按键的字典序组织。通常把稳定等值前缀放前面，再安排范围或排序列；租户列常是隔离前缀，但不能机械套用「选择性最高优先」。要同时考虑覆盖收益、主键宽度、统计信息和一个索引能否支持多个主路径。范围后的列可能无法继续缩小定位区间，但仍可能参与过滤或覆盖。

#### 工程场景

订单后台主查询是 `tenant_id + status + created_at` 倒序分页，候选索引可为 `(tenant_id, status, created_at, id)`；若另一条主路径不带 `status`，需要单独评估 `(tenant_id, created_at, id)`，不能指望前一个索引同样高效。对候选方案记录执行计划、实际扫描行、排序、延迟分布和写入成本。

#### 反例 / 踩坑

给每个筛选字段各建单列索引；只按选择性排序列；为覆盖把大文本塞进索引；看到 `Using filesort` 就盲目加索引；忽略租户条件导致跨租户扫描甚至授权漏洞。

#### 资深回答模板

「我先按真实 SQL 聚类，明确等值、范围、排序和返回列；再基于 B+ Tree 顺序提出少量候选索引，用 `EXPLAIN ANALYZE` 与生产参数分布验证扫描和排序，同时评估写放大。最后通过慢查询和未使用索引持续复审，而不是一次性建完。」

:::

**追问链：**
1. 等值列一定要按选择性从高到低排列吗？
2. 一个查询有两个范围条件，联合索引怎样取舍？
3. 如何判断两个相似联合索引能否合并？

::: details 追问参考答案

**1. 等值列一定要按选择性从高到低排列吗？**

不一定。同一查询中多个等值列都被完整约束时，它们的前后顺序未必像单列直觉那样决定扫描量；还要看其他查询能否使用前缀、租户隔离、排序与统计信息。应以工作负载复用价值和实际计划决定。把高选择性当启发式可以，但不能替代候选索引对比。

**2. 一个查询有两个范围条件，联合索引怎样取舍？**

B+ Tree 通常只能把一个连续范围高效用于定位，另一个多作为残余过滤。应优先选择能显著缩小扫描、支持排序或更稳定的范围列；也可先按一个条件取候选 ID，再过滤另一个，或为不同主路径建不同索引。最终用参数分布测试，避免只拿一组样例得结论。

**3. 如何判断两个相似联合索引能否合并？**

比较它们的左前缀、排序方向、覆盖列和服务的查询集合。若宽索引能稳定支持短索引的主要查询，且额外宽度和写成本可接受，才考虑删除短索引；不能仅因列集合相似就合并。上线前在影子或测试环境验证计划，生产采用可回退方式观察慢查询和写入负担。

:::

### D2. 如何使用 `EXPLAIN ANALYZE` 定位慢查询？

**考察点：** 估算与实际、执行树、生产安全、端到端诊断

::: details 参考答案

#### 基础结论

先从慢日志或 Trace 获取真实 SQL、绑定参数和等待阶段，再用普通 `EXPLAIN` 做无执行预检；确认安全后，在隔离环境或受控生产只读场景使用 `EXPLAIN ANALYZE` 比较每个算子的估算行数、实际行数、循环次数和时间。

#### 原理深挖

优化器根据统计信息估算基数并选择连接顺序与访问路径。估算严重偏差可能来自数据倾斜、相关列、过期统计或表达式；实际成本还会被回表、排序、临时结果、缓存冷热和锁等待影响。`EXPLAIN ANALYZE` 会执行查询，因此结果包含运行时证据，但一次运行不是长期分位表现。

#### 工程场景

先确认慢在池排队、锁等待还是 SQL 执行。对 SQL 比较「估算 10 行、实际大量行」的节点，检查谓词与统计；查看嵌套循环是否被放大、是否深 Offset、是否无界排序。调整索引或 SQL 后，用相同参数族和冷热缓存分别验证，并监控发布后的扫描行、P95/P99 与数据库负载。

#### 反例 / 踩坑

直接对未知写语句或超大查询在生产执行分析；只看总耗时不看循环；用单个幸运参数验证参数敏感查询；把 ORM 调用名当 SQL；忽略网络传输、连接池排队和锁等待。

#### 资深回答模板

「我先用 Trace 分段，确认数据库执行才是瓶颈；再取真实 SQL 与参数，普通计划预检后受控执行 `EXPLAIN ANALYZE`，寻找估算偏差和被循环放大的节点。修复后用参数分布、冷热缓存和线上分位验证，并保留回退。」

:::

**追问链：**
1. `EXPLAIN ANALYZE` 显示执行很快，但接口仍慢，下一步查什么？
2. 估算行数与实际行数相差很大，如何处理？
3. 为什么不能只用一组参数验证执行计划？

::: details 追问参考答案

**1. `EXPLAIN ANALYZE` 显示执行很快，但接口仍慢，下一步查什么？**

回到端到端 Trace，检查连接池等待、事务锁等待、网络往返、返回体大小、Prisma 对象构造、序列化和下游调用。分析执行可能命中热缓存，也可能没有复现并发等待。应关联同一请求的池指标、数据库会话与应用耗时，不能因单次 SQL 快就把问题归给 Node.js。

**2. 估算行数与实际行数相差很大，如何处理？**

先更新并核对统计信息，再检查数据倾斜、组合列相关性、隐式类型转换和表达式是否让统计失真。可改写谓词、增加更匹配的索引或使用数据库版本支持的统计能力。任何调整都要对多组真实参数复测；强制 Hint 只作为有退出条件的最后手段，避免锁死未来优化器选择。

**3. 为什么不能只用一组参数验证执行计划？**

同一 SQL 的租户、状态和时间范围可能有完全不同的基数，一组参数可能命中小租户或热数据，掩盖长尾。应按参数分布选典型、热点和极端样本，观察是否出现计划或延迟分化。若数据库存在计划缓存或参数敏感行为，还需结合实际版本验证缓存策略。

:::

### D3. 高并发库存扣减如何设计，悲观锁和乐观策略怎样选择？

**考察点：** 原子条件更新、锁策略、幂等、热点治理

::: details 参考答案

#### 基础结论

库存不超卖的核心是让「校验剩余量并扣减」成为数据库可原子判断的写入，并用受影响行数确认结果；不是先查库存再在应用内减。是否加显式悲观锁取决于后续业务是否必须基于锁住的状态完成多步操作。

#### 原理深挖

单 SKU 可使用 `UPDATE inventory SET available = available - ? WHERE sku_id = ? AND available >= ?`，数据库在写入时串行化冲突，受影响 0 行表示不足。版本号 CAS 是另一种乐观方案，冲突后需有限重试。`SELECT ... FOR UPDATE` 能锁住目标记录后执行复杂校验，但会延长持锁时间；多 SKU 必须统一锁顺序以降低死锁。

#### 工程场景

请求携带业务幂等键，订单和库存流水在同库时可放一个短事务；跨服务时使用预占、确认、释放状态机，配合 Outbox 和幂等消费者。热点秒杀还需入口限流、队列削峰或分段库存，但最终数据库约束与对账仍是底线。Prisma 可发条件更新或事务，但不能替代库存不变量设计。

#### 反例 / 踩坑

先 `findUnique` 再 `update`；在前端禁用按钮就认为防重；冲突无限重试形成风暴；事务中调用支付；多 SKU 按请求顺序加锁；缓存扣减成功却没有数据库对账和补偿。

#### 资深回答模板

「我先定义不变量：可售库存不能为负，同一幂等键只生效一次。单行优先条件更新并检查受影响行；复杂多行流程用短事务和固定锁顺序。跨服务改成可恢复状态机，重试有界，最后用库存流水与订单对账。」

:::

**追问链：**
1. 条件更新和版本号 CAS 有什么差异？
2. 一次订单扣多个 SKU，怎样降低死锁？
3. 数据库扣减成功但应用响应超时，客户端应怎么做？

::: details 追问参考答案

**1. 条件更新和版本号 CAS 有什么差异？**

条件更新直接把业务不变量写进 `WHERE`，适合「库存足够就扣减」这类单一原子规则；版本号 CAS 适合更新依赖读出状态的复杂计算，但冲突后要重新读取并重算。两者都应检查受影响行数。CAS 并非无锁，数据库写入仍会加锁，只是应用用版本检测冲突。

**2. 一次订单扣多个 SKU，怎样降低死锁？**

先对 SKU ID 去重并按稳定顺序排序，所有事务按同一顺序更新或锁定；确保定位索引准确、事务短且不含外部调用。仍要捕获死锁并在整个事务外有限重试，因为固定顺序只能降低而非消灭所有死锁。大批量订单可拆批，但要重新定义原子性和补偿。

**3. 数据库扣减成功但应用响应超时，客户端应怎么做？**

结果属于未知而不是失败。客户端使用原幂等键查询订单或扣减状态，服务端重复请求应返回同一业务结果，不能再次扣库存。应用日志要记录幂等键、事务结果和 TraceId；若状态暂不可见，返回处理中并异步核对，而不是让前端随机更换键重试。

:::

### D4. 如何复现、诊断死锁，并设计正确的重试边界？

**考察点：** 等待环、锁顺序、证据、事务级重试

::: details 参考答案

#### 基础结论

死锁需要至少两个事务形成等待环。用两条独立连接、明确事务和相反访问顺序可最小复现；诊断依赖数据库死锁记录、事务 SQL 与锁对象，不能只看应用报错字符串。

#### 原理深挖

InnoDB 检测等待图中的环并选择牺牲者回滚。锁对象通常是索引记录或间隙，因此 SQL 看似更新不同行，也可能因扫描范围、二级索引和访问顺序冲突。重试必须重新执行完整事务，因为被回滚事务中的所有写入都已撤销，不能只重放最后一条 SQL。

#### 工程场景

在测试库建立两条连接：事务 A 先改资源 1 再改 2，事务 B 先改 2 再改 1，并用同步点稳定复现。生产关联死锁日志中的 SQL、索引与请求 Trace，检查缺索引和顺序不一致。修复后做并发测试；应用仅对确认可重试的数据库冲突做少量指数退避和抖动。

#### 反例 / 踩坑

把所有锁等待都叫死锁；仅提高锁等待超时；在事务函数内部从失败语句继续；无幂等副作用却自动重试；日志不记录参数和事务关联；用生产真实数据随意复现。

#### 资深回答模板

「我先用两连接和相反锁顺序做最小复现，再从死锁报告定位等待环、索引和 SQL。根治优先统一顺序、补索引、缩短事务；重试放在完整事务外，有次数、退避和幂等边界，并监控重试后成功率。」

:::

**追问链：**
1. 死锁与锁等待超时如何区分？
2. 为什么只重试失败的最后一条 SQL 是错误的？
3. 事务里已经调用外部接口，还能自动重试吗？

::: details 追问参考答案

**1. 死锁与锁等待超时如何区分？**

死锁是等待图形成环，数据库通常主动选择一个事务回滚；锁等待超时是等待超过配置阈值，不要求存在环。两者错误码、诊断证据和根因不同。应用可把它们都列为潜在瞬态错误，但是否重试要看事务幂等性、剩余 Deadline 和数据库状态，不能统一无限重试。

**2. 为什么只重试失败的最后一条 SQL 是错误的？**

死锁牺牲者的整个事务通常已回滚，前面成功执行的语句不再生效；仅重试最后一步会产生缺失状态或违反不变量。正确做法是让事务函数无外部不可重放副作用，从入口重新读取并执行全部数据库步骤。重试前还要清理失败事务上下文并获取可用连接。

**3. 事务里已经调用外部接口，还能自动重试吗？**

不能默认重试，因为外部调用可能已成功，重放会重复扣款或发货。应把外部调用移出数据库事务，使用 Outbox、任务状态机和幂等键衔接；若历史代码无法立即改造，至少查询外部结果并按其幂等协议恢复。数据库重试器不应隐藏跨系统副作用。

:::

### D5. 大表分页和数据导出怎样兼顾性能、一致性与可恢复性？

**考察点：** Keyset、快照水位、流式批处理、后台任务

::: details 参考答案

#### 基础结论

在线浏览优先稳定排序的游标分页；大规模导出应是后台任务，按索引键分批读取并流式写入对象存储，不让一个 HTTP 请求持有长事务、连接和内存。

#### 原理深挖

深 Offset 需要扫描并丢弃大量行。Keyset 用 `(sort_key, id)` 的字典序边界继续扫描，成本更稳定。导出还要定义一致性：可固定 `id <= high_watermark` 或业务截止时间，避免过程中新增数据漂移；若要求事务级快照，要评估长快照对 Undo 和连接的压力。

#### 工程场景

创建导出任务时固化租户、授权后的筛选条件、排序、字段集和截止水位。Worker 每批参数化查询，写临时文件或分片对象，保存游标与进度，失败可从检查点恢复；完成后生成短期签名下载地址。数据权限在服务端每批强制应用，敏感字段按策略脱敏并记录审计。

#### 反例 / 踩坑

前端传 `pageSize=999999`；使用 `SELECT *` 一次加载内存；以可重复时间单列做游标；导出过程中复用用户随后变化的权限却无规则；用一个数小时事务追求快照；下载地址永久公开。

#### 资深回答模板

「浏览用唯一稳定排序的 Keyset；导出转后台任务，固化授权条件和截止水位，按索引批读、流式写、游标检查点恢复。根据业务选择水位一致性或短快照，并用行数、校验和、审计日志验证完整性。」

:::

**追问链：**
1. 导出过程中有新增和更新，如何定义数据一致性？
2. 游标列的值会被修改，怎么办？
3. 导出任务重试如何避免文件重复或数据重复？

::: details 追问参考答案

**1. 导出过程中有新增和更新，如何定义数据一致性？**

先让业务选择语义：按创建水位排除新记录但允许读取更新后的值，还是要求某一时刻的完整快照。前者可固化最大 ID 或截止时间，成本较低；后者可能需要数据库快照、历史表或 CDC 读模型，不能用长事务草率实现。导出元数据应记录口径和水位，便于解释结果。

**2. 游标列的值会被修改，怎么办？**

不要用可变业务字段单独做游标。可选择不可变且唯一的主键分批，同时把展示排序放到后处理；或建立导出任务快照表，固化本次 ID 集合。若必须按可变时间排序，更新可能造成漏读或重复，需要去重清单与最终校验，不能只靠 `(updated_at, id)` 假设不变。

**3. 导出任务重试如何避免文件重复或数据重复？**

把任务、分片和游标持久化，每个分片使用确定性编号与临时对象键；写完校验后原子标记完成，重试覆盖未完成分片而非盲目追加。最终合并只引用已完成分片，并核对行数或业务校验和。任务创建也用幂等键，避免用户重复点击生成多份相同重任务。

:::

### D6. 如何治理 Prisma N+1 和关系加载问题？

**考察点：** 查询观测、批量加载、结果膨胀、读模型

::: details 参考答案

#### 基础结论

先通过查询日志和 Trace 证明 N+1：一次请求对同类关系执行随父记录数增长的重复 SQL。治理目标是有界查询次数和数据量，不是强行把所有读取合成一条 JOIN。

#### 原理深挖

N+1 的成本包含连接池排队、网络往返、重复解析和数据库执行。JOIN 可减少往返，却可能因多个一对多关系产生笛卡尔膨胀；多条批量查询通常以父 ID 集合取子项，再在应用按键组装。Prisma 的关系加载、批处理和 `relationLoadStrategy` 等行为具有版本与数据库边界，Preview 或默认策略不能当稳定契约。

#### 工程场景

为列表设置请求级 SQL 数量与返回行观测。先用 `select` 限字段、`take` 限嵌套集合；对计数用 `_count`；对关系用 `include` 后检查实际 SQL，或显式 `findMany({ where: { parentId: { in: ids }}})` 批量加载。复杂报表建立专用读模型或参数化 SQL，并做授权和结果校验。

#### 反例 / 踩坑

在 `map` 中逐条 `findMany`；看到多个 SQL 就认定 N+1；为追求单 SQL 同时 JOIN 多个无界集合；依赖未锁定版本的隐式批处理；只统计 SQL 条数不看扫描行与响应体。

#### 资深回答模板

「我先用 Trace 看 SQL 数是否随父项线性增长，再按关系基数选择嵌套加载、批量 `IN`、计数或读模型。验收同时看查询数、扫描行、结果体和池等待；Prisma 策略按锁定版本实测，不靠名字推断。」

:::

**追问链：**
1. 一次请求执行 3 条 SQL 是否一定比 1 条差？
2. 批量 `IN` 的 ID 很多时如何处理？
3. GraphQL 场景怎样避免 Resolver 触发 N+1？

::: details 追问参考答案

**1. 一次请求执行 3 条 SQL 是否一定比 1 条差？**

不一定。三条按实体批量查询可能避免大 JOIN 的行乘法，数据量和内存更小；一条 SQL 也可能扫描、排序并返回巨量重复数据。应比较总往返、扫描行、返回字节、数据库 CPU、池占用和端到端延迟。目标是稳定有界，而不是把 SQL 条数降到 1。

**2. 批量 `IN` 的 ID 很多时如何处理？**

先限制父集合分页，避免无界 ID。确有大量 ID 时分批查询、使用临时表或数据库支持的集合输入方式，并检查参数数量、SQL 长度和计划；不同数据库连接器边界不同。分批后按键合并且保持结果顺序，授权条件必须在每一批重复施加，不能只信父查询已过滤。

**3. GraphQL 场景怎样避免 Resolver 触发 N+1？**

使用请求级 DataLoader 按实体和租户维度收集键、去重并批量查询，再按输入顺序返回。缓存仅限请求生命周期，键必须包含会影响授权和结果的上下文，避免跨用户串数据。也可按 selection set 设计专用查询，但不要把任意前端字段直接转换为无界深层 `include`。

:::

### D7. Prisma 批量事务、交互式事务与外部调用边界如何划分？

**考察点：** `$transaction`、依赖写入、事务时长、未知结果

::: details 参考答案

#### 基础结论

互不依赖、已能构造完整参数的多条 Prisma 操作可用批量事务；后一步依赖前一步查询结果或需要条件分支时，使用交互式事务。两者都应短小、只包含数据库工作，外部 HTTP、MQ 和用户等待移出事务。

#### 原理深挖

事务占用底层连接并持有锁或快照。交互式回调中的每次 `await` 都可能延长事务，JavaScript 逻辑和外部网络越多，冲突与池耗尽越严重。批量 API 仍不自动解决业务不变量；并发正确性依赖条件写、唯一约束和隔离级别。事务选项及隔离能力按 Prisma 版本和连接器确认。

#### 工程场景

创建主记录与已知明细可用嵌套写或批量事务；需要读状态、判断转换并写流水可用交互式事务，但在回调内只做必要查询和写入。提交后通过 Outbox 发布事件。对死锁等瞬态错误在事务外有限重试，对超时导致的未知结果按业务幂等键查询。

#### 反例 / 踩坑

在事务回调里调用支付接口；用 `Promise.all` 误以为能让同一事务连接真正并行；把大批循环逐条写入；捕获错误后仍从已失败事务继续；把 Prisma Promise 成功等同于跨服务业务全部完成。

#### 资深回答模板

「能预先构造且无依赖的操作用批量事务；需要读后决策才用交互式事务。回调内只保留短数据库步骤，正确性由约束与条件写保证，跨系统通过 Outbox 和幂等状态机衔接；失败按可重试、业务冲突和未知结果分类。」

:::

**追问链：**
1. 交互式事务里能否使用 `Promise.all` 提高并发？
2. 事务超时后是否可以直接告诉用户「操作失败」？
3. 大批量写入应该怎样避免长事务？

::: details 追问参考答案

**1. 交互式事务里能否使用 `Promise.all` 提高并发？**

不要假设能。一个事务通常绑定一个数据库连接，而单连接上的语句通常串行执行；`Promise.all` 只会并发调度 JavaScript Promise，还可能让错误和顺序更难理解。若操作彼此独立且允许不同事务，可在事务外受控并发；若必须原子提交，应按明确顺序执行并缩短语句。

**2. 事务超时后是否可以直接告诉用户「操作失败」？**

不能一概而论。客户端或应用超时可能发生在数据库已提交但响应丢失之后，结果是未知。服务端应通过幂等键、唯一业务号和状态查询确认；用户界面可显示「处理中，请稍后查询」，而不是诱导重复提交。只有确认事务已回滚，才能明确返回未生效。

**3. 大批量写入应该怎样避免长事务？**

按业务可接受的原子边界分批，使用 `createMany` 等批量能力或数据库装载工具，限制每批行数与耗时，并保存检查点。批次必须可重入，用唯一键或任务明细防重复；若全量必须原子，则要重新评估离线窗口、临时表切换或数据库专用方案，而不是在在线请求里硬撑。

:::

### D8. Prisma 迁移如何采用 expand-and-contract 实现兼容发布？

**考察点：** 零停机迁移、双版本兼容、回填、回滚

::: details 参考答案

#### 基础结论

先扩展兼容结构，再发布能同时处理新旧结构的应用，完成可恢复回填与校验，切换读写后观察，最后收缩旧结构。数据库迁移和应用发布不是一个瞬时动作，而是多版本共存协议。

#### 原理深挖

直接改名、改非空或删列会让旧应用立即失效。Expand 阶段新增可空列、表或索引，不破坏旧代码；迁移期通过应用双写、数据库能力或数据同步保持一致；Contract 只有在所有实例、任务和回滚窗口都不再依赖旧结构后执行。双写本身会引入部分失败，必须定义权威源和修复机制。

#### 工程场景

字段改名时先新增新列，发布应用写新旧两列并优先读新、缺失回退旧；后台分批回填，比较计数与校验和；再切为只读新列并观察，最后另一个发布删除旧列。Prisma migration SQL 要人工评审，大表索引按 MySQL 版本的在线 DDL 能力安排，并限制迁移账号权限。

#### 反例 / 踩坑

一个 migration 同时改名并删除旧列；结构变更与全量回填塞进单事务；发布失败只会回滚应用，却没考虑数据库向前兼容；长期双写无 Owner；使用 `db push` 代替生产迁移历史。

#### 资深回答模板

「我把破坏性变更拆成 expand、migrate、switch、contract。每一步都兼容前后两个应用版本，有回填检查点、数据校验和退出条件；数据库优先向前修复，旧列只在回滚窗口关闭后删除。」

:::

**追问链：**
1. 双写一边成功一边失败怎么办？
2. 大表新增索引如何控制发布风险？
3. 已应用的生产 migration 写错了，能直接修改文件吗？

::: details 追问参考答案

**1. 双写一边成功一边失败怎么办？**

同库且能同事务时把两列写入放在同一事务；跨表或跨系统无法原子时，明确一个权威源，记录待修复事件并异步对账。读取阶段按权威顺序回退，监控新旧值不一致。双写只是迁移手段，必须有结束日期，否则永久增加故障模式和维护成本。

**2. 大表新增索引如何控制发布风险？**

先评估表规模、写流量、磁盘空间和目标 MySQL 版本支持的在线 DDL 算法及锁级别，在影子或副本演练时长。生产选择低峰、设置锁等待边界并监控复制延迟与负载；必要时使用组织批准的在线变更工具。Prisma 生成 SQL 可手工调整，但需保留可审查迁移记录。

**3. 已应用的生产 migration 写错了，能直接修改文件吗？**

不应直接改历史文件，因为其他环境已记录其校验与执行状态，修改会制造不可追踪漂移。通常新增一个向前修复 migration，并根据 Prisma 锁定版本的官方修复流程处理失败或已标记状态。若涉及数据损坏，先停止扩散、备份证据并执行专门恢复方案。

:::

### D9. 如何诊断连接池耗尽，Serverless 与 PgBouncer / 数据库代理有什么边界？

**考察点：** 连接预算、排队、部署拓扑、会话语义

::: details 参考答案

#### 基础结论

池耗尽表现为获取连接排队或超时，不等同于数据库 CPU 高。先计算「实例数 × 每实例池上限」与数据库连接预算，再区分慢查询、长事务、泄漏、流量突发和扩容风暴。

#### 原理深挖

连接池把并发转换成有界排队；池太小会排队，太大会把压力直接推给数据库并增加上下文切换。Serverless 实例弹性和并发启动会形成连接风暴，单实例复用 Client 仍无法控制全局实例数。外部代理复用后端连接，但事务池模式会削弱会话级状态、临时表、预处理语句等假设。

#### 工程场景

关联池等待、活跃连接、事务时长、SQL 延迟和数据库会话。Serverless 使用平台推荐的数据库代理或 Prisma 对应连接方案，限制函数并发并设置连接预算。使用 PgBouncer 时确认模式、连接字符串参数、预处理语句兼容和迁移是否走独立直连；具体要求随 Prisma、驱动和 PgBouncer 版本变化，必须按官方矩阵测试。

#### 反例 / 踩坑

超时就把池翻倍；每次请求创建 Prisma Client；只看数据库 `max_connections`；事务中等待外部 API；代理上线后仍依赖会话变量；迁移和在线请求争用同一小池；忽略热重载重复实例。

#### 资深回答模板

「我先做全局连接预算，并用 Trace 判断时间花在池等待还是 SQL。根因按慢查询、长事务、泄漏和扩容风暴分类；Serverless 用代理和并发上限控制总连接。代理模式的会话语义与 Prisma 兼容性按锁定版本实测，迁移保留独立通道。」

:::

**追问链：**
1. 数据库 CPU 很低，为什么仍会连接池超时？
2. Serverless 中复用全局 Prisma Client 是否就解决了连接问题？
3. 事务池模式的数据库代理为什么会影响会话语义？

::: details 追问参考答案

**1. 数据库 CPU 很低，为什么仍会连接池超时？**

连接可能被锁等待、长事务、网络阻塞或空闲但未归还的代码占住，这些不一定消耗高 CPU；池上限也可能远小于数据库能力。应看获取连接等待、使用中连接、事务年龄、锁等待和每条查询阶段。只扩池会暂时隐藏泄漏，还可能在流量恢复时压垮数据库。

**2. Serverless 中复用全局 Prisma Client 是否就解决了连接问题？**

它只能避免同一热实例内重复创建 Client，不能限制平台同时启动多少实例；每个实例仍可能建立自己的池。还需控制函数并发、设置合理池大小、使用兼容代理并给数据库保留总连接预算。冷启动、冻结恢复和平台生命周期也要通过实际部署指标验证。

**3. 事务池模式的数据库代理为什么会影响会话语义？**

事务结束后，下一次操作可能被分配到不同后端连接，因此会话变量、临时表、会话锁和某些预处理语句状态不能跨事务可靠保留。应用应避免依赖连接身份，把必要状态显式放进事务或查询。Prisma 与代理的具体预处理语句处理方式随版本变化，需按官方配置测试。

:::

### D10. 多租户系统如何安全使用 Prisma 与原生 SQL，防止 SQL 注入和越权？

**考察点：** 租户隔离、授权权威、参数化、动态标识符、安全审计

::: details 参考答案

#### 基础结论

租户隔离必须由服务端从可信身份上下文确定，并在每次数据访问中强制加入；客户端传来的 `tenantId` 只能作为待校验输入。原生 SQL 所有数据值必须参数化，查询能力还要经过资源级授权，防注入不等于防越权。

#### 原理深挖

参数化查询把 SQL 结构与数据值分离，可防止值逃逸为语法；表名、列名、排序方向等标识符通常不能用值参数绑定，必须由代码白名单映射，禁止字符串拼接用户输入。共享表模式需组合唯一键与索引都带租户维度；独立 Schema / 数据库隔离更强，但迁移、连接和运维成本更高。

#### 工程场景

认证层解析主体与租户成员关系，应用服务做资源动作授权，Repository 接口要求显式 `tenantId` 并构造 `where: { tenantId, ... }`。可用 Prisma Client Extension 等方式减少漏加条件，但扩展 API 和能力随版本变化，且不能替代代码审查、数据库权限与集成测试。原生 SQL 使用安全参数 API，动态排序映射固定枚举，查询账号遵循最小权限并记录审计。

#### 反例 / 踩坑

相信前端隐藏租户选择器；只在列表加租户条件、详情按全局 ID 查询；用 `$queryRawUnsafe` 拼字符串；参数化了值却允许用户传任意列名；管理员接口复用普通查询时无显式授权；把软删除过滤当安全隔离。

#### 资深回答模板

「租户来自可信身份上下文，授权在应用层按主体、租户、资源和动作判断，所有 Repository 查询显式携带租户条件。原生 SQL 的值全部参数化，动态标识符只走白名单；数据库账号最小权限，组合约束含租户维度，并用跨租户负向测试和审计日志验证。」

:::

**追问链：**
1. 参数化查询是否能处理动态排序字段？
2. Prisma Client Extension 自动加 `tenantId` 后，还需要应用层授权吗？
3. 如何测试不会出现跨租户数据泄露？

::: details 追问参考答案

**1. 参数化查询是否能处理动态排序字段？**

通常不能把列名或 `ASC` / `DESC` 当普通值参数绑定。应把 API 的排序枚举映射到代码中固定的 SQL 片段，例如只允许 `createdAt` 和 `amount`，方向只允许两种常量；筛选值仍使用参数。绝不能把用户输入直接插入模板字符串，即使做了简单转义也不足以证明安全。

**2. Prisma Client Extension 自动加 `tenantId` 后，还需要应用层授权吗？**

需要。自动过滤只能降低漏写条件的概率，无法判断用户是否有权执行退款、导出或访问某个资源，也可能被原生 SQL、未覆盖操作和错误上下文绕过。应用层仍做资源动作授权，Repository 明确租户参数，数据库账号最小权限；扩展作为防御纵深，并按锁定 Prisma 版本测试覆盖面。

**3. 如何测试不会出现跨租户数据泄露？**

建立至少两个租户的同形数据，用租户 A 身份对列表、详情、更新、删除、关系嵌套、导出和原生 SQL 做负向集成测试，特别测试猜测租户 B 的全局 ID。再做属性或契约测试确保所有查询入口携带租户上下文，审计日志记录拒绝决策。仅测试 UI 看不到按钮不构成安全证据。

:::
