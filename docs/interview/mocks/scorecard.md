# 模拟面试评分表

> **怎么用：** 每场模拟结束后立刻打分（搭档评或自评）。只打整数 1～5；先看「描述」再给分，避免全场打 4。配合 [模拟脚本](/interview/mocks/scripts) 使用；弱项回到对应 [题库](/interview/questions/02-vue3) 或 [故事模板](/interview/stories/template) 加练。

**建议：** 九维组成完整评分框架。单场至少覆盖 7 维，并且必须覆盖目标岗位核心维；每个已考察维度都要写一句可复核证据。未考察项不填默认分，也不能与九维全覆盖场直接比较。

## 统一 1～5 分锚点

| 分数 | 通用锚点 |
| ---- | -------- |
| 1 | 无法回答，或答案明显错误、危险、与事实冲突 |
| 2 | 能说术语或表面流程，但缺少机制、证据、边界或失败路径 |
| 3 | 达到岗位基本要求；答案完整，有一个可验证项目证据，常规追问可接住 |
| 4 | 能解释机制与取舍，覆盖边界和异常，并用数据、实验或复盘验证 |
| 5 | 在 4 分基础上形成可迁移方法论，能处理复杂追问、指导他人并主动说明未知 |

各维下方的描述用于解释该维在 1～5 分时分别应看到什么；如与通用锚点冲突，取较低分。

## 总分计算与岗位权重

### 基础总分与百分制

- **九维全覆盖时：** 基础总分为九维直接相加，范围为 9～45 分；百分制为 `基础总分 ÷ 45 × 100`。
- **未覆盖九维时：** 不计算或展示「/45」基础总分，只报告覆盖率、未考察项和归一化百分制。
- **可比性：** 不同覆盖组合的归一化分只能说明各自已考察范围内的表现；报告必须附覆盖率与未考察项，不可直接与九维全覆盖场或其他覆盖组合比较。

### 岗位加权分

设已考察维度集合为 `E`，每维得分为 `sᵢ`，岗位权重为 `wᵢ`：

**归一化百分制 = `Σ(sᵢ × wᵢ) ÷ Σ(5 × wᵢ) × 100`，其中 `i ∈ E`。**

九维全覆盖时，分母权重之和为 100%，该公式等价于完整岗位加权百分制。未考察维度从分子、分母同时剔除，不补默认分。

| 岗位 | 技术深度 | 表达结构 | 决策取舍 | AI 协作 | 前后端闭环 | 约束识别 | 原理深度 | 故障治理 | 演进能力 | 合计 |
| ---- | -------- | -------- | -------- | ------- | ---------- | -------- | -------- | -------- | -------- | ---- |
| Senior Frontend | 20% | 15% | 10% | 5% | 10% | 10% | 15% | 10% | 5% | 100% |
| Tech Lead | 10% | 10% | 15% | 5% | 5% | 15% | 10% | 15% | 15% | 100% |
| 全栈偏前 | 15% | 10% | 10% | 10% | 20% | 10% | 10% | 10% | 5% | 100% |

岗位核心维如下，单场不得遗漏：

- **Senior Frontend：** 技术深度（最高权重），并至少覆盖原理深度。
- **Tech Lead：** 决策取舍、架构约束识别、故障治理、演进能力（四项并列最高权重）。
- **全栈偏前：** 前后端闭环（最高权重），并至少覆盖技术深度。

原则上尽量覆盖九维；时长有限时至少覆盖 7 维、全部岗位核心维和四个新增架构维度。

### 重叠维度如何区分

| 容易重叠的维度 | 区分规则 |
| -------------- | -------- |
| 技术深度 vs 原理深度 | 技术深度看主栈整体实践的广度、边界与验证；原理深度只看能否解释关键机制、因果链和失效条件 |
| 决策取舍 vs 架构约束识别 | 约束识别评「输入是否找全并排序」；决策取舍评「拿到输入后如何比较方案并承担代价」 |
| 技术深度 vs 故障治理 | 技术深度评正常机制和工程实现；故障治理评异常状态下的发现、止损、恢复与防复发 |
| 决策取舍 vs 演进能力 | 决策取舍评当下选择；演进能力评跨阶段触发器、迁移路径、兼容期和退出方案 |
| 前后端闭环 vs 故障治理 | 前后端闭环评契约、职责和交付链路；故障治理评跨边界故障的定位、恢复与复盘 |

同一回答可以被多个维度引用，但每维必须记录不同的观察事实。例如「缓存故障」中，机制解释计入原理深度，降级与恢复计入故障治理，是否采用缓存及其代价计入决策取舍。

### 红线

红线独立于九维总分。命中任一项时，本场结论为「不通过 / 待核验」，不得被基础总分或岗位加权分掩盖：

- **诚信红线：** 编造项目、指标、职责或生产经验；无法区分「主导、参与、了解」。
- **安全红线：** 泄露密钥或个人数据、信任前端鉴权、绕过权限校验，或让未经审查的 AI 代码直接上线。
- **可验证性红线：** 核心项目结论没有代码、指标、日志、评审记录或可复述过程中的任何一种证据，且追问后仍无法核验。
- **故障责任红线：** 面对高风险变更或线上故障，没有止损、回滚、降级和升级通知意识。
- **基础能力红线：** 任一已考察维度为 1 分，或目标岗位任一核心维 / 任一并列最高权重维度 ≤2 分；Tech Lead 的决策取舍、架构约束识别、故障治理、演进能力任一项 ≤2 即命中。

## 维度一：技术深度

考察：原理与实践是否匹配年限；能否下沉到机制、边界与排查，而不是只报库名。

| 分 | 描述 |
| -- | ---- |
| 1 | 只会名词堆叠；追问一层即卡壳；对所用框架关键机制说不清 |
| 2 | 能讲常用 API 与表面流程；说不清为什么；排查停留在「重启 / 再试试」 |
| 3 | 主栈（如 Vue3 / 工程化 / 中后台）能讲清常见原理与项目证据；次要领域点到为止 |
| 4 | 能对比方案、指出边界与坑；结合项目讲清性能 / 权限 / 构建等至少一块深水区 |
| 5 | 深度与广度平衡；追问仍稳定；能教级讲解且主动标明「我没做过的部分」 |

**观察信号：**

- 正向：主动画时序 / 分层、提到取舍代价、能量化或描述验证方式  
- 负向：全程「我们用了 XX」、回避具体模块归属、原理背诵与项目脱节

---

## 维度二：表达结构

考察：是否结论先行、时长可控、STAR-L 完整；被打断后能否收回主线。

| 分 | 描述 |
| -- | ---- |
| 1 | 无结构，从细节或公司历史扯起；超时严重；听者抓不住结论 |
| 2 | 有片段结构但不稳定；常缺结果或任务边界；「我们」远多于「我」 |
| 3 | 自我介绍与项目能按背景→行动→结果讲述；偶有跑题但可拉回 |
| 4 | 明显结论先行；30s / 2min 档切换自如；追问回答短而完整 |
| 5 | 全程可当范文；主动控时、预埋钩子、复述面试官问题后再答 |

**观察信号：**

- 正向：先答一句结论再展开；用「三点」组织；主动说「我停在这里看你想听哪块」  
- 负向：重复同一句、术语瀑布、答非所问

---

## 维度三：决策取舍

考察：是否呈现方案对比、约束意识、否决理由与演进条件（Lead 面核心）。

| 分 | 描述 |
| -- | ---- |
| 1 | 只有唯一做法，说不清为什么；或一切「听领导的」无自己判断 |
| 2 | 能说出选了什么，但对比弱；不考虑代价、风险或回滚 |
| 3 | 至少给出 2 选 1 的理由，能联系工期 / 复杂度 / 团队能力 |
| 4 | 清晰对比维度（成本、风险、可维护、交接）；承认当时信息差；有兜底 |
| 5 | 决策像方法论：目标→约束→选项→标准→复盘；能指导他人做同类判断 |

**观察信号：**

- 正向：「没选 B 是因为…」「若指标到 X 会升级方案」  
- 负向：事后诸葛式完美叙事、从不承认坑、一切都是最优解

---

## 维度四：AI 协作成熟度

考察：是否把 AI 当产能工具且有质量边界；而非「会用 ChatGPT」或「完全不用装清高」。

| 分 | 描述 |
| -- | ---- |
| 1 | 否认任何 AI 使用却答不出传统路径；或声称全自动生成从不审查 |
| 2 | 只会「用 AI 查报错 / 写片段」；无流程、无审查清单、无责任意识 |
| 3 | 能说明典型使用场景（样板、单测草稿、重构建议）并提到人工把关 |
| 4 | 有可复述的工作流：契约 / 提示粒度 / 审查清单 / 测试；清楚不信任点（安全、权限、复杂业务） |
| 5 | 能定团队级规范（何时用、何时禁、CR 看什么）；把 AI 纳入质量门禁叙事 |

**观察信号：**

- 正向：主动讲「AI 写了什么、我改了什么」；提到越权与校验  
- 负向：神秘化提示词、或道德审判式「我们不用 AI」却无替代产能说明  

**场次说明：** 业务型中小厂若未涉及 AI，本维可标「未考察」，并从归一化公式的分子、分母同时剔除；创业 AI / 相关深挖场必评。

---

## 维度五：前后端闭环

考察：接口契约、联调排障、错误处理、简单后端或协作深度；符合「全栈偏前」边界。

| 分 | 描述 |
| -- | ---- |
| 1 | 只认前端页面；接口问题一律「后端的锅」；说不清自己如何联调 |
| 2 | 会调接口、贴字段；不懂错误码 / 鉴权 / 环境；Java 或后端叙事空洞 |
| 3 | 能讲清契约、联调步骤、常见 401/403/校验失败处理；知道前后端责任分界 |
| 4 | 能独立扛或讲清简单 Spring Boot CRUD 闭环；统一响应、校验、权限有实践细节 |
| 5 | 闭环质量意识强（可观测、可回滚、可交接）；在边界内深度足够，且不越界吹微服务 |

**观察信号：**

- 正向：主动提契约先行、失败路径、小范围验证  
- 负向：大谈分布式事务 / JVM 却答不清一个列表接口的分页与权限  

**叙事对齐：** 评分时对照 [总览 · Java 叙事边界](/interview/00-overview)——越界吹深度反而扣「决策取舍 / 表达」可信度。

## 维度六：架构约束识别

考察：设计前能否主动发现、验证并排序业务、规模、团队、合规、存量系统与成本约束。

| 分 | 描述 |
| -- | ---- |
| 1 | 不问背景直接选框架；忽略明确的安全、合规或成本限制 |
| 2 | 会问用户量和工期，但问题零散；无法区分硬约束、假设与偏好 |
| 3 | 能覆盖业务目标、规模、团队、存量与时间，并指出最关键的 1～2 项约束 |
| 4 | 能量化质量目标、验证假设、识别约束冲突，并按业务风险排序 |
| 5 | 能建立约束清单与复审机制；信息不足时会设计低成本实验并说明决策置信度 |

---

## 维度七：原理深度

考察：能否解释关键机制、因果链、边界和失效条件，而不是停留在框架 API 或类比。

| 分 | 描述 |
| -- | ---- |
| 1 | 关键机制明显错误；把框架名、配置项当作原理 |
| 2 | 能复述表面流程，但无法解释调用顺序、依赖关系或为什么会失效 |
| 3 | 能画出核心链路，解释主要机制与常见边界，并与一个项目现象对应 |
| 4 | 能从机制推导性能、隔离、一致性或安全后果，并用实验、源码或日志验证 |
| 5 | 能跨框架比较机制与失效模型；面对变体仍可从第一原则推导并清楚标明未知 |

---

## 维度八：故障治理

考察：是否覆盖故障发现、止损、定位、恢复、复盘、防复发与责任协作的完整闭环。

| 分 | 描述 |
| -- | ---- |
| 1 | 无监控与止损意识；高风险操作没有回滚；倾向甩锅 |
| 2 | 只会查日志或重启；没有故障分级、降级、通知和复盘 |
| 3 | 能讲清一次故障的发现、定位、修复与复盘，具备基本监控和回滚方案 |
| 4 | 能设计指标、告警、开关、隔离、降级、演练与责任分工，并量化恢复目标 |
| 5 | 能从多次故障提炼治理机制，持续降低故障半径与恢复时间，并推动跨团队执行 |

---

## 维度九：演进能力

考察：能否为架构设定演进触发器、迁移步骤、兼容策略、退出路径和阶段性验证。

| 分 | 描述 |
| -- | ---- |
| 1 | 把当前方案当作永久终局；没有升级、迁移或退出意识 |
| 2 | 只说「以后再重构」；没有触发条件、步骤、成本与兼容安排 |
| 3 | 能给出下一阶段触发条件和基本迁移顺序，知道需要灰度与回退 |
| 4 | 能设计可度量触发器、双轨兼容、数据 / 契约迁移、阶段验收与退出方案 |
| 5 | 能把技术、组织和成本演进联动管理；根据证据调整路线，并避免一次性大爆炸迁移 |

## 总分解读（参考）

| 基础总分 | 基础均分 | 解读 | 行动 |
| ---------- | ---------- | ---- | ---- |
| 9～22 | <2.5 | 未达可投递口述水位 | 专攻 ≤2 的维度，并先处理所有红线 |
| 23～31 | 2.5～3.4 | 及格线附近 | 每场只改 Top 3；补可验证项目证据 |
| 32～38 | 3.5～4.2 | 稳健可面试 | 按目标岗位最高权重维度再打一场 |
| 39～45 | ≥4.3 | 优秀 | 换脚本加压，防止对单一题型过拟合 |

本表仅适用于九维全覆盖场；31 分的基础均分为 3.44，归入「及格线附近」。岗位判断优先看归一化百分制，但只有在未命中红线时才允许使用「稳健」或「优秀」结论。
