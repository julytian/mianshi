### Q1. `unknown` 和 `any` 怎么选？

**考察点：** 类型安全边界、收窄习惯、与第三方脏数据对接

::: details 参考答案
`any` 是「放弃检查」：传进去、传出来都畅通，编译器闭嘴，责任全在你。`unknown` 是「我知道这是未知」：你可以接住任意值，但**用之前必须收窄**（`typeof` / 类型守卫 / 断言在边界上一次做完）。

实战习惯：外部输入（API、`JSON.parse`、`localStorage`、SDK 回调）先标 `unknown`，在边界模块收窄成业务类型，再往内层传。内层业务代码尽量不见 `any`。库类型烂到没法修时，用局部 `any` + 注释「为何逃逸」比全局 `any` 干净。

面试别说「永远不用 `any`」——那不诚实。要说「逃逸点可控、尽量窄、别传染」。
:::

**追问链：**
1. `unknown` 赋给别的类型时，为什么比 `any` 更安全？
2. 和 `Record<string, unknown>`、`object` 相比，你怎么接「任意 JSON 对象」？
3. 项目里已经满屏 `any`，你怎么做渐进治理而不拖垮排期？

::: details 追问参考答案

**1. `unknown` 赋给别的类型时，为什么比 `any` 更安全？**

`unknown` 更安全，因为除 `unknown` 和 `any` 外，不能在未收窄时直接赋给具体类型。它迫使调用方先证明数据形状：类型守卫或 Schema 校验能做运行时验证，类型断言不验证任何值，只适合已有外部保证的边界；`any` 则跳过读、写和调用检查。工程上应在 I/O 边界完成校验与收窄，再向内部暴露稳定业务类型。

**2. 和 `Record<string, unknown>`、`object` 相比，你怎么接「任意 JSON 对象」？**

接收任意 JSON 时应先用 `unknown`，校验顶层确为非空、非数组对象后再收窄为 `Record<string, unknown>`。`object` 只排除原始值，不能安全地按字符串键读取；`Record` 又不能表达数组、字符串等完整 JSON 值。若接口真接受任意 JSON，最好定义递归 `JsonValue`，并在边界做运行时校验。

**3. 项目里已经满屏 `any`，你怎么做渐进治理而不拖垮排期？**

渐进治理应按风险和传播性推进，而不是一次性清零。先开启统计与 lint 告警，阻止新增裸 `any`；再从 API、存储、消息等外部边界改成 `unknown` 加校验，随后治理高频公共函数和事故模块。对暂时无法修复的点保留局部逃逸、注明原因和负责人，以错误率和 `any` 数量趋势验收。

:::

**踩坑：** `as unknown as T` 双断言等于手动 `any`，只适合「我比编译器更懂」的极少数边界；滥用等于自我安慰。

### Q2. 泛型约束（`extends`）解决什么问题？口述一个真实场景

**考察点：** 泛型约束、keyof、默认类型参数

::: details 参考答案
无约束的 `T` 几乎什么都能进，你在函数里就不敢碰字段。`T extends { id: string }` 是在说：「我只关心有 `id` 的东西，其余字段保留推断」。

常见场景：表格 `getRowKey<T extends { id: string | number }>`、深取字段 `getProp<T, K extends keyof T>(obj: T, key: K): T[K]`、请求封装 `request<T = unknown>(...)`。约束写「最少需要的形状」，别写成整个业务 Entity——否则复用立刻死。

默认类型参数（`T = void`）适合「多数调用方不关心返回值」的 API；约束和默认一起用时，先想清楚「推断失败时掉到哪」。
:::

**追问链：**
1. `K extends keyof T` 和 `K extends string` 差在哪？
2. 约束过宽 / 过窄分别会带来什么代码味道？
3. 条件类型 `T extends U ? X : Y` 和约束有什么分工？

::: details 追问参考答案

**1. `K extends keyof T` 和 `K extends string` 差在哪？**

`K extends keyof T` 把键限制为 `T` 实际拥有的键，并允许返回值写成 `T[K]`；`K extends string` 只保证它是字符串，无法证明能索引 `T`。还要注意 `keyof T` 可能包含 `number` 或 `symbol`，若底层 API 只接受字符串，应使用 `Extract<keyof T, string>`，不要用断言掩盖键域差异。

**2. 约束过宽 / 过窄分别会带来什么代码味道？**

约束过宽会让实现内部频繁断言、可选链或运行时猜测，说明泛型没提供足够能力保证；约束过窄则要求调用方拼出无关字段、复制完整实体或到处转换，说明 API 把实现细节泄漏给了用户。工程上只约束算法真正读取或调用的最小形状，并用正反类型用例验证可用范围。

**3. 条件类型 `T extends U ? X : Y` 和约束有什么分工？**

约束负责限制「什么类型可以传入」，条件类型负责根据已传入类型计算「得到什么类型」。例如 `<T extends object>` 拒绝原始值，而 `T extends readonly unknown[] ? ... : ...` 为不同结构选择结果。不要把条件类型当运行时分支；涉及联合时裸类型参数会分布，若要整体判断需用元组包裹。

:::

### Q3. 常用 Utility Types 你会主动用哪些？哪些在项目里反而添乱？

**考察点：** `Partial` / `Required` / `Pick` / `Omit` / `Record` / `ReturnType` / `Parameters`

::: details 参考答案
高频有用：`Pick`/`Omit` 做表单编辑 DTO 与列表 VO 的差集；`Partial` 做 PATCH；`Record<Union, V>` 做穷尽映射；`ReturnType`/`Parameters` 从已有函数抽类型，避免双份维护。

添乱的：层层 `Partial<Omit<Pick<...>>>` 让人读不懂「到底必填什么」；用 `Partial` 掩盖本该明确的创建 vs Update 模型；`Exclude`/`Extract` 嵌套过深变成「类型体操表演」。

原则：Utility 是手术刀，不是乐高。超过两层嵌套，宁可写一个命名清晰的 `type UserUpdate = { ... }`。
:::

**踩坑：** `Partial` 后所有字段可选，和「字段存在但值可为 null」不是一回事——后端常混用，前端要对齐语义。

### Q4. 闭包与作用域：你会怎么讲「闭包有啥用、有啥坑」？

**考察点：** 词法作用域、自由变量、内存与过期状态

::: details 参考答案
闭包就是函数带着定义时的词法环境跑。用途：工厂函数私有状态、事件处理器记住配置、hooks/composables 里的「实例级」变量、柯里化配置。

坑不在「闭包本身」，而在**抓住了过期的值**：循环里 `var` + 异步；React/Vue 里闭包捕获了旧 props/state；定时器没清导致组件卸了还改状态；长生命周期闭包（全局 EventBus、module 单例）挂着大对象导致泄漏。

口述结构：先说用途 → 再说「抓住引用还是值」→ 再举一个过期闭包事故。
:::

**追问链：**
1. `let` 在 `for` 循环里为什么能「修好」经典闭包题？
2. 模块顶层变量算不算闭包？和函数闭包有何异同？
3. 如何排查「闭包泄漏」而不是凭感觉怪闭包？

::: details 追问参考答案

**1. `let` 在 `for` 循环里为什么能「修好」经典闭包题？**

`let` 能修好经典问题，因为 `for` 的词法声明会为每次迭代创建新的绑定，回调各自闭包引用不同的迭代环境；`var` 只有函数级同一绑定，异步回调执行时通常都看到循环结束值。这是 ECMAScript 的词法环境语义，不是简单的「复制值」规则；若闭包捕获对象，仍共享对象引用。

**2. 模块顶层变量算不算闭包？和函数闭包有何异同？**

模块顶层变量本身不叫闭包，但模块内导出的函数若引用它，就形成对模块词法环境的闭包。它与普通函数闭包都按词法作用域解析自由变量；区别在于模块环境通常随模块实例长期存活、默认严格模式，并通过 ESM live binding 共享绑定。因而模块单例状态更容易跨 SPA 路由、组件生命周期或测试用例残留。

**3. 如何排查「闭包泄漏」而不是凭感觉怪闭包？**

排查应证明对象已过业务生命周期却仍被强引用。稳定重复进入和退出页面，对比 Heap Snapshot 的对象数量、retained size 与 retaining path，定位是监听器、定时器、缓存还是回调环境持有。闭包只是引用路径的一环；修复应找到 owner，建立注册与注销、创建与销毁的对称关系，再做多轮回归。

:::

### Q5. 事件循环：宏任务、微任务，画一条时间线说明 `Promise` / `queueMicrotask` / `setTimeout`

**考察点：** 浏览器事件循环、微任务队列排空、渲染时机直觉

::: details 参考答案
一次大致模型（浏览器）：执行同步 JS → 清空微任务队列（`Promise.then`、`queueMicrotask`、`MutationObserver`）→ 可能渲染 → 取一个宏任务（`setTimeout`、I/O、UI 事件等）→ 再清微任务……

经典口述：

```js
console.log('a')
setTimeout(() => console.log('b'), 0)
Promise.resolve().then(() => console.log('c'))
console.log('d')
// a d c b
```

`async/await` 在 `await` 之后的代码本质是微任务续体。别背「所有 Promise 都比 setTimeout 早」的绝对口号——嵌套、`await` 拆分、以及 Node 与浏览器细节会变；面试给「同步 → 微任务清空 → 宏任务」就够用，再补一句「别用定时器做精确时序」。

本题只保留执行顺序判断；渲染机会、微任务饥饿、Long Tasks 与切片诊断见 D2。
:::

**追问链：**
1. 微任务里再塞微任务会怎样？会不会饿死渲染？
2. `requestAnimationFrame` 相对微任务大概在哪一档？
3. Vue 的 `nextTick` 和微任务的关系你怎么理解？

::: details 追问参考答案

**1. 微任务里再塞微任务会怎样？会不会饿死渲染？**

微任务检查点通常会持续执行到队列清空，因此微任务中递归追加微任务可以长期占住主线程，让渲染和后续任务得不到机会。Promise Job 属于 ECMAScript 抽象，何时做检查点和渲染由 HTML 事件循环定义。工程上大计算要通过任务切片或 Worker 真正让出线程，不能只改成连续 `await`。

**2. `requestAnimationFrame` 相对微任务大概在哪一档？**

`requestAnimationFrame` 回调属于浏览器更新渲染步骤中的动画回调，通常在当前任务结束并完成微任务检查点后、绘制前运行。它不是宏任务队列中的普通任务，也不保证每轮事件循环或固定 16.7 ms 执行；后台页和高刷新率设备都会不同。回调内仍须控制计算量，否则会直接挤占当帧预算。

**3. Vue 的 `nextTick` 和微任务的关系你怎么理解？**

`nextTick` 的语义是等待 Vue 当前一轮异步 DOM 更新队列完成，不应被理解为通用的「等浏览器绘制」。Vue 通常借助已解析 Promise 安排调度，因此回调多在微任务阶段执行，但这是框架调度实现，不是浏览器渲染保证。需要读取更新后的 DOM 可用它；需要确认视觉帧则再结合 `requestAnimationFrame`。

:::

**踩坑：** 在微任务里疯狂 `await` 链式干活，主线程长时间不交给浏览器，页面会「卡住」——看着像性能问题，其实是调度问题。

### Q6. `this` 绑定规则：你会怎么一口气压住追问？

**考察点：** 默认 / 隐式 / 显式 / `new` / 箭头函数、严格模式

::: details 参考答案
优先级口头版：`new` > `bind/call/apply` 显式 > 对象调用隐式 > 独立调用（严格模式 `undefined`，非严格指向全局）。箭头函数**没有自己的 this**，继承外层词法 this——所以适合回调，不适合需要动态 this 的方法（除非你故意）。

类字段箭头、Vue Options API 的 methods（别用箭头）、React class 里 bind——都是同一套规则的不同皮肤。面试官扔一段「解构出方法再调用」——隐式绑定丢失，this 飘走。
:::

**追问链：**
1. `obj.fn()` 和 `const f = obj.fn; f()` 差在哪？
2. `bind` 多次，以哪次为准？
3. 为什么说「箭头函数不能当构造函数」？

::: details 追问参考答案

**1. `obj.fn()` 和 `const f = obj.fn; f()` 差在哪？**

差别在调用表达式是否保留基值：`obj.fn()` 以 `obj` 作为隐式 `this`，赋值给 `f` 后再独立调用则丢失该引用关系，严格模式下 `this` 为 `undefined`。函数对象没有永久记住来源对象。工程上可在调用处保留接收者、显式 `bind`，或把不依赖动态 `this` 的回调写成箭头函数。

**2. `bind` 多次，以哪次为准？**

对已绑定函数再次 `bind` 不能替换第一次绑定的 `this`，最早绑定的接收者生效；后续 `bind` 仍可继续预置参数。若用 `new` 调用绑定函数，构造调用的实例会覆盖绑定的 `this`，但预置参数仍参与调用。多层绑定可读性和调试性很差，工程上应在边界只绑定一次并保留原函数引用。

**3. 为什么说「箭头函数不能当构造函数」？**

箭头函数没有 `[[Construct]]` 内部方法，也没有自己的 `prototype`、`this`、`arguments` 或 `new.target`，所以用 `new` 调用会抛出 `TypeError`。它的 `this` 来自定义位置的词法环境，无法执行构造函数需要的实例绑定流程。需要可构造 API 应使用 `class` 或普通函数，不要依赖语法变形绕过。

:::

### Q7. 深拷贝的边界在哪？什么时候不该自己写？

**考察点：** 引用类型、循环引用、特殊对象、结构化克隆

::: details 参考答案
「深拷贝」不是一个函数，是一组产品决策：要不要拷函数、Symbol、原型、Date、Map/Set、DOM、File、循环引用？

`JSON.parse(JSON.stringify(x))`：丢函数/`undefined`/Symbol，Date 变字符串，撑不住循环引用——只适合「纯 JSON 数据快照」。手写递归要处理循环（`WeakMap` 记忆）、容器类型、以及「拷到哪一层算深」。

现代优先：`structuredClone`（见 Q21）。业务上更多时候要的是**不可变更新局部字段**（immer / 展开运算符），不是整树深拷贝。整树拷贝贵，还容易拷漏响应式代理。
:::

**追问链：**
1. Vue 里对 `reactive` 对象深拷贝要注意什么？
2. 为什么「深拷贝解决了所有引用共享问题」是错的？

::: details 追问参考答案

**1. Vue 里对 `reactive` 对象深拷贝要注意什么？**

对象图中只要存在可达的 Vue 响应式 Proxy，`structuredClone` 就会抛出 `DataCloneError`。`toRaw` 只解除当前 Proxy，不会递归清除嵌套代理；克隆前必须确认整个对象图都可结构化克隆，或显式转换成纯数据 DTO。克隆结果也不是响应式的，若业务确实需要再重新 `reactive`；通常局部不可变更新比整树复制更合适。

**2. 为什么「深拷贝解决了所有引用共享问题」是错的？**

深拷贝只在某个时点切断被算法覆盖的对象引用，不能解决外部资源、函数闭包、DOM、类实例语义或后续重新共享的问题。它还可能丢原型、访问器和不可枚举属性，并制造高峰内存。工程上应先定义所有权和可变边界：共享只读数据、局部复制写入，比无差别复制整棵对象图更可控。

:::

**踩坑：** 把 Proxy / 组件实例 / 路由对象塞进深拷贝，轻则报错，重则静默丢行为。

### Q8. 防抖和节流：场景怎么拆？实现上你会盯哪些细节？

**考察点：** debounce / throttle、leading/trailing、取消与卸载

::: details 参考答案
防抖：动作停了再触发——搜索联想、窗口 resize 后重算布局、表单自动保存。节流：固定频率最多一次——滚动埋点、拖拽跟手、按钮防连点（有时用节流或锁）。

实现细节比「setTimeout 模板」更重要：`leading`/`trailing` 要不要首尾都触发；`this`/`arguments` 透传；返回 Promise 时后到的调用如何取消前一次；组件卸载 `cancel`；和 `AbortController` 组合取消进行中的请求。

口述别只背定义，给一对业务例子 +「卸载必 cancel」。
:::

**追问链：**
1. 搜索框防抖 300ms，用户选中联想项时还要不要立刻请求？
2. 节流期间最后一次触发丢失，怎么补 trailing？
3. 和「请求序号 / 忽略过期响应」怎么配合？

::: details 追问参考答案

**1. 搜索框防抖 300ms，用户选中联想项时还要不要立刻请求？**

选中联想项通常应取消待执行的防抖并立即提交，因为用户已表达明确意图，继续等待 300 ms 只会增加延迟。若选项已包含完整业务数据，可直接使用而非重复请求；若仍需详情，则立即请求并锁定选中值。工程上要区分输入预览与确认动作，并取消旧请求，避免迟到响应覆盖已选结果。

**2. 节流期间最后一次触发丢失，怎么补 trailing？**

要补 trailing，就在节流窗口内保存最后一次调用的参数、`this` 和时间，在剩余窗口结束时执行一次；新的调用只更新快照而不重复建多个定时器。还要定义 leading 与 trailing 同时开启时单次调用是否执行一次，并提供 `cancel`/`flush`。执行后清空参数引用，避免长生命周期节流器持有大对象。

**3. 和「请求序号 / 忽略过期响应」怎么配合？**

防抖和节流控制发起频率，请求序号只保证最新请求可以提交状态，不保证请求完成或状态提交的先后顺序。每次发请求递增序号，响应仅在序号仍为最新时更新；同时用 `AbortController` 尽量取消旧请求以节省资源。即使底层不支持取消，序号门禁仍防止旧结果覆盖新结果，但错误和 loading 也必须按序号隔离。

:::

### Q9. Promise 并发控制：如何限制最多 N 个同时进行？

**考察点：** 并发池、队列、失败策略、与 `Promise.all` 区别

::: details 参考答案
`Promise.all` 是「全开火」；并发池是「工人数固定，做完一个再取下一个」。实现直觉：维护执行中计数 + 等待队列；或用 async 池循环 `await Promise.race(executing)`。

业务点：失败是 fail-fast 还是收集错误继续？要不要重试？结果顺序要不要与输入对齐（占位数组按 index 回填）？取消（`AbortSignal`）怎么传到每个任务？

管理后台批量导出、图片压缩上传、对后端打一批详情接口——都是经典场景。N 的取值看后端限流和浏览器连接数，不是越大越快。
:::

**追问链：**
1. `allSettled` 和并发池怎么组合？
2. 如何保证输出顺序与任务数组一致？
3. 中途用户离开页面，池子怎么停？

::: details 追问参考答案

**1. `allSettled` 和并发池怎么组合？**

并发池负责限制同时运行数量，`allSettled` 语义负责为每个输入保留成功或失败结果；不能先对全部任务调用并启动 Promise，再用 `allSettled`，那会绕过限流。正确做法是工人从队列取任务，在任务内部捕获并写入 `{ status, value/reason }`，最后等待工人结束，并单独判断是否出现系统性批量失败。

**2. 如何保证输出顺序与任务数组一致？**

按输入顺序预分配结果数组，并在取任务时携带原始索引，完成后写回 `results[index]`，即可让执行顺序与输出顺序解耦。不要靠 `push`，它只反映完成先后。若任务可取消或失败，也应为该索引写入明确状态，避免数组空洞；超大任务集还要考虑流式消费，别为排序承诺长期保留全部结果。

**3. 中途用户离开页面，池子怎么停？**

页面离开时应由页面 owner 触发共享 `AbortController`，池子停止领取新任务，并把 signal 传给正在执行的 fetch、解析或 Worker 协议。已运行且不支持协作取消的 Promise 无法强杀，只能等待结算并禁止回写页面。最后在 `finally` 清理监听器和队列引用，明确取消结果而不是混成普通失败。

:::

**踩坑：** 在池子外又包一层无限制的 `map(async ...)`，等于没限流。

### Q10. `async/await` 错误处理，你在项目里的惯例是什么？

**考察点：** try/catch 粒度、错误上抛、边界消化、浮游 Promise

::: details 参考答案
分层：底层库/请求封装把「可预期业务错误」收成统一类型（code/message），不可预期的保留 cause；页面/用例边界 `try/catch` 做 UX（toast）；中间层该抛就抛，别到处吞。

`async` 函数返回的是 Promise——别忘了调用方 `await` 或 `.catch()`，否则变成 unhandled rejection。并行用 `Promise.all` 时一个失败整组挂，看要不要 `allSettled`。在循环里 `await` 是串行，故意并发要用 `map` + 限制。

空 `catch (e) {}` 是事故温床；至少打日志或上报，并决定是否 rethrow。

本题只回答错误处理惯例；Promise 链式传播差异、可观测分层和取消语义见 D3。
:::

**追问链：**
1. 什么时候该在拦截器吞错，什么时候必须抛到页面？
2. `for await` 和普通 `for` + `await` 的适用场景？
3. 如何统一处理「取消」与「真正失败」？

::: details 追问参考答案

**1. 什么时候该在拦截器吞错，什么时候必须抛到页面？**

拦截器只有在错误已被完整恢复并能返回符合契约的替代结果时才可消化，例如命中明确的离线缓存；统一鉴权跳转后也应返回可识别的终止结果。页面需要决定重试、降级或业务提示的错误必须继续抛出。拦截器不应 toast 后返回 `undefined`，否则原始故障会变成更难定位的空值错误。

**2. `for await` 和普通 `for` + `await` 的适用场景？**

`for await...of` 主要消费异步可迭代对象，如流式分页、ReadableStream 适配器或持续消息；它也能消费同步 iterable，但会增加 Promise 解包语义。普通 `for` 加 `await` 适合已有数组且明确要求串行依赖的任务。若元素彼此独立并需要并发，应使用有上限的并发池，而不是换一种循环语法。

**3. 如何统一处理「取消」与「真正失败」？**

应把取消建模为可识别的独立原因，并在边界统一归一化，而不是仅靠错误消息字符串判断。传递 `AbortSignal`，结合 `signal.reason` 区分用户取消、路由离开和超时；网络、业务与程序错误保留 `cause` 和上下文。UI 通常不对用户主动取消报错，但监控仍可计数；未知错误必须继续上报或抛出。

:::

### Q11. ESM 和 CJS 互操作，你会怎么讲给同事听？

**考察点：** 模块系统、默认导出互操作、双包陷阱

::: details 参考答案
CJS：`require`/`module.exports`，运行时加载，同步为主。ESM：`import`/`export`，静态可分析，浏览器原生友好，利于 tree-shaking。

坑在互操作：`import x from 'cjs-pkg'` 到底拿到 `module.exports` 还是 `.default`，取决于打包器与 `esModuleInterop`；Node 的 `"type": "module"`、双包（CJS+ESM 两份入口）容易「instanceof 失效」或加载到两份拷贝。

前端 Vite/现代工具链默认 ESM 心智；写库时注意 `exports` 字段条件导出。面试讲清楚「静态结构 vs 运行时导出」比背语法有用。

本题只做 ESM/CJS 基础区分；ESM live binding、循环求值与 TDZ 诊断见 D6。
:::

**踩坑：** 同一依赖被打进两份（CJS/ESM 各一），Vue 插件或 context 对不上号——很像「玄学 bug」。

### Q12. Tree-shaking 的直觉：什么能摇掉，什么摇不掉？

**考察点：** 副作用、命名导出、barrel file、CSS/JSON

::: details 参考答案
摇树依赖：ESM 静态结构 + 打包器判定无副作用。命名导出、纯函数模块友好；`import *`、动态 `import()` 路径不确定、有顶层副作用（改全局、polyfill、CSS 副作用导入）会保守保留。

`export * from './x'` 的大 barrel 经常让分析变钝，开发爽、体积疼。副作用标注（`sideEffects` in package.json）是库作者的责任；业务侧少写「为了方便全部 re-export」。

直觉口令：能静态看到「没用到的绑定」且模块无副作用 → 可摇；靠运行时才能知道用啥 → 难摇。

本题只保留 tree-shaking 基础判断；与 ESM 循环依赖、副作用证明和构建保留链的组合诊断见 D6。
:::

**追问链：**
1. 为什么 lodash 全量 `import _` 和 `lodash-es` 按函数导入差很多？
2. CSS Modules / 全局 CSS 跟 tree-shaking 是什么关系？

::: details 追问参考答案

**1. 为什么 lodash 全量 `import _` 和 `lodash-es` 按函数导入差很多？**

差异主要来自模块格式和导入粒度：传统 lodash 的 CJS 聚合入口在部分工具链中难以静态证明哪些属性未用，`lodash-es` 提供 ESM 命名导出，更利于 tree-shaking。具体体积仍取决于打包器、插件和版本；直接按路径导入单函数也可缩小范围。应以产物分析验证，不能把默认导入语法本身当唯一原因。

**2. CSS Modules / 全局 CSS 跟 tree-shaking 是什么关系？**

CSS 导入通常被视为有副作用，因为即使 JS 绑定未使用，加载样式也可能改变页面。CSS Modules 能让类名引用更局部，某些构建链可进一步清理未用规则，但这不等于 ESM tree-shaking 自动删除 CSS。全局 CSS、重置样式和组件注册样式更需保留；库的 `sideEffects` 必须准确标注 CSS 路径，避免被误删。

:::

### Q13. Vue 里 props / emits 的 TypeScript 写法，你推荐哪套？

**考察点：** `defineProps`/`defineEmits` 泛型、运行时声明与纯类型声明、校验边界

::: details 参考答案
`<script setup lang="ts">` 下优先类型声明：

```ts
const props = defineProps<{ modelValue: string; size?: 'sm' | 'md' }>()
const emit = defineEmits<{ 'update:modelValue': [value: string]; change: [id: number] }>()
```

需要运行时校验/默认值时用对象写法或 `withDefaults`。别把复杂业务类型塞进 props 还不拆——子组件会变成上帝。emits 类型写清 payload，避免 `emit('xxx', any)`。

和外部类型同步：props 用业务 `type`，不要在组件里复制粘贴一份接口字段。
:::

**追问链：**
1. 类型-only props 和运行时 props 同时存在时要注意什么？
2. `v-model` 多参在类型上怎么建模？

::: details 追问参考答案

**1. 类型-only props 和运行时 props 同时存在时要注意什么？**

同一次 `defineProps` 调用不能同时传类型参数和运行时对象声明，应选择一种来源。类型声明可由编译器生成部分运行时 props 信息，但复杂导入类型和校验规则不等价于完整运行时验证；默认值用响应式解构能力或 `withDefaults`。外部数据仍需运行时校验，不能因 TypeScript 类型存在就假设浏览器输入可靠。

**2. `v-model` 多参在类型上怎么建模？**

多个 `v-model` 应把每个参数建模为独立 prop 与对应的 `update:参数名` 事件，例如 `title` 配 `update:title`，并为各事件载荷声明准确类型。Vue 新版本也可用多个 `defineModel` 表达同一契约。修饰符需单独声明和处理；不要用一个宽泛对象事件包住所有模型，否则父组件失去逐项推断与更新边界。

:::

**踩坑：** 解构 `props` 会丢失响应性（要用 `toRefs`/`storeToRefs` 那套心智）；类型对了运行时仍可能传入多余字段——TS 不挡运行时。

### Q14. 前后端类型怎么同步？你见过哪些靠谱与不靠谱方案？

**考察点：** OpenAPI/Swagger、代码生成、契约测试、漂移治理

::: details 参考答案
靠谱方向：以 OpenAPI（或等价 IDL）为契约，前端用 openapi-typescript / 自研生成 `types` + 轻量 client；CI 校验契约变更；后端改字段先改契约。

不靠谱：口口相传；前端手写「猜的」interface；把后端 Java DTO 源码当唯一真相却无生成流水线；生成一次再手改生成物。

折中：核心实体生成，边缘页面手写；或 Zod/io-ts 在边界校验，类型从 schema 推断——运行时兜底比「纯 TS 信仰」更抗炸。
:::

**追问链：**
1. 后端字段突然变可选，前端生成类型更新了但页面没改，怎么防？
2. 枚举/字典类数据跟类型同步怎么做？

::: details 追问参考答案

**1. 后端字段突然变可选，前端生成类型更新了但页面没改，怎么防？**

要靠契约变更门禁和运行时测试双重防护。CI 先生成类型并禁止脏差异，再对 OpenAPI 做 breaking-change 检查；关键页面开启严格空值检查，并用契约样本或端到端测试覆盖字段缺失场景。类型更新只会暴露直接使用点，若代码已滥用断言或可选链仍可能静默失败，因此边界 Schema 和可观测降级同样必要。

**2. 枚举/字典类数据跟类型同步怎么做？**

稳定、参与分支穷尽的枚举应进入契约并生成字符串联合或常量映射；展示名、排序等高频变化字典则由服务端下发并缓存，不要每次发版固化。前端对未知值保留兜底分支和监控，以支持服务端先发布新值。禁止同时手写 TS 枚举和接口字典，否则很快出现值、文案与权限语义漂移。

:::

**踩坑：** 生成类型是 `string`，业务当联合类型用——类型绿了，运行时脏数据照样穿模。

### Q15. 可选链 `?.` 的坑有哪些？

**考察点：** 短路语义、与赋值/调用组合、掩盖空值根因

::: details 参考答案
`a?.b.c` 在 `a` 空时短路；但 `a?.b.c` 若 `a` 有而 `b` 空，访问 `.c` 仍炸——位置要对。`obj?.()` 是「对象为空则不调用」；和 `obj?.method?.()` 不同。

最大产品坑：满屏 `?.` 把「本不该为空」的数据问题吞成 `undefined`，页面空白却不报错，排障更难。该在边界断言/校验的，别在深渲染链上一路可选下去。

和 `??` 组合常见：`a?.b ?? default`——先弄清「没有」和「有但为 null」的语义。
:::

**踩坑：** `left?.[index] = value` 这类可选链赋值限制；以及把 `?.` 当「防御性编程勋章」滥用。

### Q16. 空值合并 `??` 和 `||` 差在哪？什么时候会踩？

**考察点：** nullish coalescing、假值陷阱

::: details 参考答案
`||` 把 `0`、`''`、`false`、`NaN` 都当「没有」；`??` 只把 `null`/`undefined` 当没有。表单里数量 `0`、开关 `false`、允许空字符串，几乎必须用 `??` 或显式判断。

`??=` 适合惰性默认赋值。注意和可选链：`a ?? b ?? c` 可读性尚可，再长就提取变量。和默认参数 `fn(x = 1)`：默认参数不吃 `null`（`fn(null)` 不会回落到 1），`??` 可以补这层。
:::

**追问链：**
1. 后端用 `0` 表示「不限」、用 `null` 表示「未设置」，前端默认值怎么写才不容易错？
2. `??` 和 `?.` 优先级相关括号你怎么记？

::: details 追问参考答案

**1. 后端用 `0` 表示「不限」、用 `null` 表示「未设置」，前端默认值怎么写才不容易错？**

必须保留 `0` 的业务含义，只对 `null` 或 `undefined` 回落，例如 `const limit = value ?? defaultLimit`，不能用 `value || defaultLimit`。更稳妥的是在 API 边界把原始值转换为判别联合，如 `{ kind: 'unlimited' }`、`{ kind: 'unset' }`、`{ kind: 'limited', value }`，避免数字魔法值渗透到页面计算。

**2. `??` 和 `?.` 优先级相关括号你怎么记？**

不要靠背完整优先级表，按语义分组：先用 `?.` 安全取得值，再用 `??` 提供空值默认，例如 `(user?.quota) ?? fallback`。可选链通常先结合，但与 `||`、`&&` 混用时语法要求显式括号，且长表达式极易误读。工程规范可要求跨两类逻辑运算符就加括号或提取中间变量。

:::

### Q17. `Map` / `Set` 相对普通对象 / 数组，什么时候更合适？

**考察点：** 键类型、插入顺序、去重、频繁增删查

::: details 参考答案
`Set`：去重、成员存在性（`has` O(1) 均摊），别再用 `array.includes` 扫超级大列表做热点路径。`Map`：键可以是对象引用；频繁增删；需要保证插入顺序迭代；避免 `Object` 把数字键转字符串、或和原型链搅在一起。

对象字面量仍适合「固定形状的记录」、JSON 序列化友好结构。需要 `JSON.stringify` 时 Map/Set 要自己转换。

选型口令：结构化字段用 object；集合语义与任意键用 Map/Set。
:::

### Q18. `WeakMap` / `WeakSet` 适合解决哪类问题？

**考察点：** 弱引用、元数据挂载、防泄漏

::: details 参考答案
键必须是对象，且不阻止 GC。典型：给 DOM 节点或第三方实例挂私有元数据，而不想用可枚举字段污染；库在外部对象上存「已处理标记」；实现深拷贝时的循环引用表（遍历期间）。

不能迭代、不能取 size——这是特性不是缺陷：你不该依赖「弱集合里现在有谁」。需要枚举用 `Map`。

和 Vue 响应式：框架内部大量用弱连接思路管理依赖；业务里少直接碰，但面试能讲清「为何不阻 GC」就加分。
:::

**踩坑：** 把原始类型当 WeakMap 键——直接不行；用完仍被别处强引用，弱也救不了泄漏。

### Q20. `Proxy` 对比 `Object.defineProperty`，为什么 Vue3 换了？

**考察点：** 拦截能力、数组/新增属性、性能与兼容性叙事

::: details 参考答案
`defineProperty` 要在初始化时递归劫持已有属性；新增属性、删除、数组索引/长度等不完整或很别扭（Vue2 的 `$set` 历史包袱）。`Proxy` 代理整个对象，`get/set/has/deleteProperty` 等陷阱更齐全，懒代理也更自然。

代价：环境要支持 Proxy（现代浏览器没问题）；代理身份与原对象不同（`===`、部分库检测）；也不是免费午餐，仍需合理设计依赖收集。

口述抓「能力完整性 + 开发体验」，别只背「Proxy 更快」——快不快看场景。
:::

**追问链：**
1. 为什么对数组用 Proxy 仍可能有性能问题？
2. `Reflect` 在陷阱里扮演什么角色？

::: details 追问参考答案

**1. 为什么对数组用 Proxy 仍可能有性能问题？**

Proxy 能完整拦截数组操作，但不会让操作免费。大量索引读取、写入、迭代及 `length` 变化都会进入陷阱，并可能触发依赖收集和批量更新；稀疏化、频繁变形还会影响引擎对数组元素的优化。性能结论取决于框架和引擎实现，工程上应减少深层代理范围、批量提交，并用真实 trace 验证热点。

**2. `Reflect` 在陷阱里扮演什么角色？**

`Reflect` 提供与内部对象操作更接近的默认转发接口，使 Proxy 陷阱能保留接收者、访问器 `this` 和布尔返回语义，例如 `Reflect.get(target, key, receiver)`。它不是 Proxy 的强制搭档，也不会自动避免递归；若对代理本身再次 Reflect 操作仍可能重入。陷阱还必须遵守不可配置属性等语言不变量。

:::

### Q21. `structuredClone` 能做什么、不能做什么？

**考察点：** 结构化克隆算法、与 JSON 拷贝对比

::: details 参考答案
`structuredClone` 能处理更多内建类型（Date、Map、Set、ArrayBuffer、循环引用等），比 JSON 往返靠谱，是浏览器/平台提供的深克隆。

不能：函数、DOM 节点、部分浏览器对象、带方法的 class 实例（通常丢原型方法，只留数据）。传 `transfer` 可转移可转移对象所有权。

在 Worker 消息、跨上下文时同一套算法也在起作用。业务里：纯数据树优先它；要保留原型行为就别指望克隆。

**踩坑：** 克隆 Vue Proxy 可能丢响应式或抛错——先 `toRaw` 再决定是否该克隆。

### Q22. `AbortController` 怎么用在实战请求里？

**考察点：** 取消、竞态、与防抖/路由切换结合

::: details 参考答案
创建 `AbortController`，把 `signal` 传给 `fetch`/axios；需要取消时 `abort()`。路由切换、搜索防抖新请求发出前、组件卸载——取消上一次，避免「慢请求回写新页面」。

和错误处理：abort 通常表现为特定错误（`AbortError`），UI 层别当失败 toast。多个请求可共享一个 signal，或分层（页面级 + 请求级）。

这是并发与正确性工具，不是性能银弹；但能显著减少竞态 bug。
:::

**追问链：**
1. axios 取消和 fetch 的 AbortSignal 现在怎么对齐？
2. 如何区分用户取消与超时取消？

::: details 追问参考答案

**1. axios 取消和 fetch 的 AbortSignal 现在怎么对齐？**

现代 axios 与 fetch 都可接收标准 `AbortSignal`，新代码应在调用层统一接受 `signal` 并向下透传；axios 旧 `CancelToken` 已是遗留方案，不宜继续扩散。两者抛出的取消错误形态并不完全相同，应在请求适配层归一化为领域取消结果，同时保留原始 `cause`。取消只是协作通知，不保证服务端副作用回滚。

**2. 如何区分用户取消与超时取消？**

应给不同取消源明确 reason，并在组合信号前保留来源，例如用户按钮、路由离开和超时分别使用独立 controller；支持时可用 `AbortSignal.timeout()` 与 `AbortSignal.any()`。捕获后优先读取 `signal.reason` 或平台错误类型，再归一化。UI 可静默处理用户取消、提示超时重试，但监控需分别统计。

:::

### Q24. 可辨识联合（Discriminated Unions）怎么设计才好用？

**考察点：** 字面量 tag、穷尽检查、`never`

::: details 参考答案
用一个字面量字段（`type: 'success' | 'error'`）做 tag，各分支携带不同载荷。`switch (res.type)` 里每条分支类型自动收窄；`default` 里把值赋给 `never` 做穷尽检查，新增分支编译期炸——这是联合类型的工程价值。

比一堆可选字段（`data?`/`error?` 同时存在）清晰得多。API 结果、UI 状态机、弹窗互斥内容都很合适。
:::

**追问链：**
1. tag 用 `type` 还是 `kind`？和后端枚举不对齐怎么办？
2. 如何避免「假联合」（各分支字段大量重叠可选）？

::: details 追问参考答案

**1. tag 用 `type` 还是 `kind`？和后端枚举不对齐怎么办？**

`type` 或 `kind` 都可以，关键是判别字段由所有分支共享、保持稳定，且每个分支使用互斥的字面量值，团队统一命名即可。若后端枚举命名或粒度不适合 UI，应在 API 适配层做穷尽映射，保留未知值兜底并上报，而不是把传输模型直接扩散到组件。这样后端变更只影响边界，内部状态机仍保持清晰。

**2. 如何避免「假联合」（各分支字段大量重叠可选）？**

避免假联合的核心是让每个分支只携带该状态合法的数据，把共享且必需的字段提到交叉类型中，而不是把所有字段都写成可选。为 tag 使用字面量，并在 `switch` 中做 `never` 穷尽检查。若状态可正交组合，应拆成多个状态维度；强塞进一个巨大联合会导致分支爆炸和断言回潮。

:::

### Q25. `satisfies` 运算符解决什么痛？和注解类型有何不同？

**考察点：** TS `satisfies`、推断保留、校验形状

::: details 参考答案
`const cfg = { ... } satisfies Config`：检查值符合 `Config`，但**变量推断仍保留字面量细节**（例如键的字面量联合、具体字符串字面量），不会被拓宽成 `string`。

对比 `: Config` 注解——通过检查，但推断常被拓宽，后续 `cfg.mode` 可能丢掉自动补全的字面量信息。适合路由表、主题 token、权限码表「既要符合接口，又要保留精确键」。

老项目无 `satisfies` 时，可用 `as const` + 满足函数校验曲线救国。
:::

**踩坑：** 以为 `satisfies` 会「变成」注解类型去传给只接受宽类型的 API——它主要影响检查与推断，不是运行时转换。

### Q26. 模块扩充（Module Augmentation）轻量场景怎么讲？

**考察点：** `declare module`、扩展第三方类型、全局接口合并

::: details 参考答案
第三方库类型缺字段、或你给 `vue`/`express`/`axios` 挂自定义属性时，用 `declare module 'xxx' { interface ... }` 做合并，而不是改 `node_modules`。

原则：扩充放在独立 `shim.d.ts` / `types/*.d.ts`，范围尽量小；能 wrapper 出自己的类型就别改全局。接口合并是开放的，类型别名不行——这点常考。

### Q27. 数组 vs 对象：热点路径上性能与 API 怎么选？

**考察点：** 局部性、查找复杂度、引擎优化直觉、可读性优先

::: details 参考答案
数组：有序序列、栈队列、密集索引；引擎对 packed array 很友好。按 id 高频查找，先建成 `Map`/`Record<id, Item>`，别在渲染热路径 `find` 扫几千条。对象/Map：字典语义；注意属性添加形态变化导致隐藏类/退化（不必背细节，知道「形状稳定更友好」）。

前端多数瓶颈在 DOM、网络、不合理渲染，不在 `[]` vs `{}`。先量再优化；但「列表 + 字典双视角」是正规军做法（列表保序，Map 保查）。
:::

**追问链：**
1. 为什么说稀疏数组性能差？
2. 大列表更新时，不可变「拷贝全数组」的成本如何缓解？

::: details 追问参考答案

**1. 为什么说稀疏数组性能差？**

稀疏数组可能使引擎从紧凑元素存储退化为更通用的表示，索引访问、迭代和内存局部性都可能变差；具体表示和阈值属于 V8 等引擎实现，不是 ECMAScript 性能保证。语义上数组空洞与值为 `undefined` 也不同，部分迭代方法会跳过空洞。需要稀疏键空间时通常应选 `Map` 或对象。

**2. 大列表更新时，不可变「拷贝全数组」的成本如何缓解？**

先避免高频小更新每次复制整表：按批次合并变更、按页或分块保存，并将实体字典与有序 ID 列表拆开，只替换受影响分片。持久化数据结构或 Immer 可改善开发体验，但仍有代理和分配成本。若数据达到十万级，还应下推服务端、虚拟化展示并控制历史快照，不能只优化一次拷贝。

:::

### Q28. 你怎么向面试官证明「你会用 TypeScript」而不是「只会写类型注解」？

**考察点：** 综合表达、边界收窄、与运行时分工、和团队规范

::: details 参考答案
TS 的价值在边界：外部数据 `unknown` + 校验；内部用联合与穷尽检查表达非法状态不可达；用泛型减少重复又不过度体操；与 Vue/接口生成结合形成闭环。

**追问链：**
1. 什么时候你会选择少写类型、多写测试？

::: details 追问参考答案

**1. 什么时候你会选择少写类型、多写测试？**

当风险来自运行时行为而非静态形状时，应减少复杂类型并增加测试，例如时序、网络重试、权限、序列化、第三方脏数据和跨浏览器差异。类型仍用于稳定接口和非法状态约束，但不能证明副作用顺序或真实输入。判断标准是缺陷能否由编译器可靠发现；不能的就用单测、契约测试或端到端测试覆盖。

**2. 如何 review 别人「过度类型体操」的 PR？**

先要求说明它消除了哪类真实错误，再检查调用端提示、错误可读性、`tsc`/IDE 性能和团队可维护性。让作者提供正反类型测试，并比较命名接口、少量重载或运行时 Schema 的更简单方案。若工具类型递归过深、依赖双断言或只有作者能解释，应降级实现；Review 针对成本收益，不针对炫技动机。

### D2. 浏览器 Event Loop、渲染机会与长任务如何串起来分析卡顿？

### D3. Promise 与 `async/await` 的错误传播怎样设计成可观察、可取消的链路？

::: details 参考答案
#### 基础结论

#### 反例 / 踩坑
空 `catch`、在拦截器统一 toast 后返回 `undefined`、`void doAsync()` 却不接 `.catch`，都会制造静默失败或二次类型错误。全局 `unhandledrejection` 只能兜底上报，不能替代局部恢复。

### D4. 条件类型、分布式条件类型与 `infer` 如何正确组合？

::: details 参考答案
#### 基础结论
承接 Q2/Q3 的泛型约束与 Utility Types：条件类型 `T extends U ? X : Y` 用可赋值关系选择分支。D4 只扩展分布规则、`infer` 模式匹配和复杂度边界。

#### 原理深挖
`type Element<T> = T extends readonly (infer U)[] ? U : T` 是结构模式匹配。分布式条件可实现联合过滤，但 `never` 在分布中会被消去。对重载函数做 `infer` 通常从最后一个签名推断，并不会执行真正的重载解析。

#### 工程场景
适合从既有契约提取 Promise 结果、事件载荷、函数参数或过滤联合。公共库应给复杂类型配类型测试与命名中间类型；业务代码若只服务一个 DTO，显式接口往往更可维护。

#### 反例 / 踩坑

#### 资深回答模板
「我先判断是否需要按联合成员映射，再决定裸 `T` 还是 `[T]`。`infer` 用于提取既有结构，不用来炫技；复杂工具类型必须有类型测试、错误提示和复杂度预算。」

2. 如何实现不分布的 `IsUnion` 或数组包装？
3. `never`、`any`、`unknown` 进入条件类型分别有哪些直觉差异？

### D5. TypeScript 中协变、逆变和不变如何影响 API 设计？类型体操边界在哪？

::: details 参考答案
#### 基础结论
承接 Q2/Q28 的泛型 API 与 TS 工程边界：类型论上，纯生产者通常协变、纯消费者通常逆变、同时读写常要求不变；但 TypeScript 的实际可赋值行为不等于完全安全模型。D5 只扩展方差与兼容性例外。

#### 原理深挖
最小对照：

```ts
interface Animal { name: string }
interface Dog extends Animal { bark(): void }

type FunctionProperty<T> = { consume: (value: T) => void }
type Method<T> = { consume(value: T): void }

declare let animalFn: FunctionProperty<Animal>
declare let dogFn: FunctionProperty<Dog>
dogFn = animalFn // 安全：能处理 Animal，自然能处理 Dog
// animalFn = dogFn // strictFunctionTypes 下报错

declare let animalMethod: Method<Animal>
declare let dogMethod: Method<Dog>
animalMethod = dogMethod // 方法参数保留双变兼容；可赋值不代表类型论安全

declare const dogs: ReadonlyArray<Dog>
const animals: ReadonlyArray<Animal> = dogs // 只读观察可协变

const writableDogs: Dog[] = []
const writableAnimals: Animal[] = writableDogs // TS 允许，但 mutable Array 并非严格不变
writableAnimals.push({ name: 'cat' }) // 破坏 writableDogs 的元素假设
```

官方提供 `in`/`out` 方差标注，但强调它们极少需要，不能强行改变结构比较，只应与真实结构一致。

#### 工程场景
事件总线、回调注册、只读容器和状态写入器最能暴露方差问题。设计 API 时分离 `ReadonlyState<T>` 与 `Dispatch<TAction>`，比把可读写大对象到处传更安全；用 `tsd`、`expectTypeOf` 等验证正反例。

#### 反例 / 踩坑
把「TS 允许赋值」说成「类型论证明安全」会误导；方法双变和可写数组协变都可能留下运行时洞。为消除报错直接双断言同样会掩盖风险。复杂递归映射若让 IDE 卡顿或错误不可读，就已越过收益边界。

#### 资深回答模板
「我先讲类型论方向，再明确 TS 的兼容性例外：函数属性受 `strictFunctionTypes` 约束，方法/构造仍双变，可写数组也非严格不变。API 用只读与写入接口拆边界；类型复杂度损害工具链时退回命名接口和运行时校验。」

#### 追问链
1. 函数属性和方法语法为什么得到不同检查结果？
2. `ReadonlyArray<Dog>` 为何比 `Dog[]` 的协变更安全？
3. 你如何量化类型体操对 `tsc` 与编辑器的成本？
:::

### D6. ESM live binding、循环依赖与 tree-shaking 失效如何一起排查？

::: details 参考答案
#### 基础结论
承接 Q11 的 ESM/CJS 区分和 Q12 的 tree-shaking 直觉：ESM import 指向导出绑定的实时只读视图，而非导入时复制值。D6 只扩展循环图求值、TDZ、保留链诊断与副作用证明。

#### 原理深挖
静态 import/export 让工具建立模块图并做 tree-shaking，但 live binding 不等于「任意循环都安全」。顶层副作用、动态不可分析路径、CJS 边界、保守的 `sideEffects` 标注与大范围聚合导出，都会迫使打包器保留代码。

#### 工程场景
用构建分析图确认保留链；将共享常量或协议类型下沉到无副作用模块；用依赖反转或显式初始化消除业务循环。库作者准确声明 `sideEffects`，并用消费方构建测试验证 CSS、polyfill 没被误摇掉。

#### 反例 / 踩坑
把 `"sideEffects": false` 当瘦身开关，可能删除必须执行的样式或注册代码；把循环依赖仅靠调整 import 顺序压住，升级打包器后可能再次暴露。

#### 资深回答模板
「我把问题拆成链接、求值和打包保留三层：live binding 保证看到最新绑定，不保证初始化顺序；tree-shaking 依赖静态图和副作用证明。先画模块环，再拆无副作用契约层并验证产物。」

1. 默认导出表达式与导出命名绑定的 live 语义有何区别？
2. `import()` 能否自动解决循环依赖？
3. 如何证明某段代码因副作用而未被摇掉？

### D7. 前端内存泄漏如何系统定位？WeakRef 与 FinalizationRegistry 的边界是什么？

::: details 参考答案
#### 基础结论
承接 Q4 的闭包生命周期与 Q18 的弱集合：泄漏是对象已无业务用途却仍被强引用。D7 只扩展堆快照诊断、持有链和 WeakRef/FinalizationRegistry 的非确定性边界。

#### 原理深挖
GC 从根集合追踪强引用；Heap Snapshot 的 retained size 与 retaining path 比单看对象数量更有价值。弱引用目标可在任意未来时刻消失，规范刻意不给确定回收时序，终结回调也不可作为释放关键资源的唯一机制。

#### 工程场景
稳定复现「进入—操作—退出」多轮，强制 GC 仅作实验辅助，对比快照和 Allocation Timeline，沿支配树查持有链。修复时建立申请/释放对称关系，并加入路由切换或组件卸载回归。

#### 反例 / 踩坑
把缓存值改成 `WeakRef` 会造成随机 miss，且缓存键本身若仍强引用也无济于事；看到内存未立即下降就断言泄漏，也可能只是 GC 尚未运行或引擎保留堆容量。

#### 资深回答模板
「我先证明对象跨业务生命周期仍可达，再沿 retaining path 找强引用 owner。弱引用只用于可丢失的辅助缓存或元数据，不负责资源关闭；WebSocket、Observer 等必须显式清理。」

3. FinalizationRegistry 为什么不适合统计准确在线实例数？

### D8. Web Worker 何时值得引入？数据传输、取消和容错怎么设计？

#### 基础结论

#### 原理深挖

### D9. 浏览器处理十万到百万级数据时，如何避免内存、主线程和渲染一起爆？

::: details 参考答案
#### 基础结论

#### 反例 / 踩坑

「我先画数据生命周期并给每段设预算：能下推服务端就下推，客户端流式/分块，计算移出主线程，展示只渲染窗口。验收看峰值内存、长任务、交互延迟和结果正确性。」

### D10. JavaScript 如何落地结构化并发与分层取消？

::: details 参考答案
#### 基础结论
承接 Q9 的并发池和 Q22 的 AbortController：JavaScript 目前没有统一内建的结构化并发作用域。D10 只扩展任务 owner、分层取消、结算与资源退出纪律。

#### 原理深挖
取消是协作式协议：`abort()` 只广播 signal，不会强行停止任意 Promise 或 CPU 循环。`AbortSignal.any()` 可合并多个取消源，`AbortSignal.timeout()` 可表达超时，但使用前要核对目标运行时并准备兼容方案。聚合失败策略要明确 fail-fast、收集全部还是部分成功。

#### 工程场景
页面或一次用例创建根 signal，派生给 fetch、并发池、Worker 协议和重试器；新搜索取消旧搜索；作用域退出在 `finally` 清理监听并等待子任务结算。错误模型区分超时、用户取消、父级取消与真实失败。

#### 反例 / 踩坑
只在 UI 上忽略过期响应并未停止网络和计算；创建 controller 却没把 signal 传到底层等于没有取消；重试器若复用已 aborted 的 signal，会立刻连续失败。

#### 资深回答模板
「我让每个并发任务都有 owner 和退出条件。父作用域持有 signal，子任务必须接受并传播；退出先发取消，再等待结算，最后清理。无法协作取消的库要包装隔离，不能假装 Promise 可被强杀。」

#### 追问链
1. 如何组合路由离开、用户点击取消和请求超时？
2. CPU 循环怎样响应 AbortSignal？
3. `Promise.race` 做超时为什么可能留下后台任务？
:::
