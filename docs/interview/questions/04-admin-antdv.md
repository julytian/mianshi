# Ant Design Vue 中后台题库

> **怎么用：** 先盖住答案，自己口述 1～2 分钟（权限边界、表格封装、线上事故），再点开 `参考答案` 对照补洞。追问用来模拟面试官加压；踩坑是实战里最容易翻车的点。中英文术语之间请习惯留空格，口述时也建议如此。

本模块偏「十年经验口述」：少背 Ant Design Vue 组件 API，多讲**权限怎么不漏、表格怎么不卡、表单怎么可配置还敢改**。

### Q1. 中后台权限模型你会怎么设计？RBAC 讲到哪一层够用？

**考察点：** RBAC / ABAC、角色与资源、前端展示权 vs 后端强制权

::: details 参考答案
先想：前端权限只是「别让用户点到不该点的」；真正拦枪的是后端。口述必须把这两层拆开。

常见落地是 **RBAC**：用户 → 角色 → 权限码（菜单 / 路由 / 按钮 / API）。角色解决「一批人长得像」；权限码才是真正判断单元。菜单权限决定「能不能看见入口」；路由权限决定「直链能不能进」；按钮权限决定「页内能不能操作」——三者码表最好同源，别各写一套字符串。

什么时候升级到 ABAC / 数据权限？同一角色但「只能看本部门订单」「只能改自己创建的草稿」——这是资源属性 + 主体属性，前端最多做字段脱敏与筛选默认值，**过滤条件必须以后端为准**。

十年经验说法：权限模型先简单（角色 + 权限码），复杂规则沉到后端策略引擎；前端维护一份「码 → 是否可见」的计算函数，全站复用，禁止页面里散落 `if (role === 'admin')`。
:::

**追问链：**
1. 超管「全部权限」你是前端写死还是后端下发 `*`？各有什么风险？
2. 权限码用字符串还是分层编码（如 `order:list:export`）？怎么做兼容演进？
3. 多租户 SaaS 下，角色是租户内还是平台级？前端路由表怎么切？

::: details 追问参考答案

**1. 超管「全部权限」你是前端写死还是后端下发 `*`？各有什么风险？**

我会让服务端在租户与会话范围内判定超管，前端只消费明确的能力结果；即使下发 `*`，也只用于菜单和按钮展示，不能替代 API 授权。前端写死超管角色会造成角色改名、租户切换和权限回收后继续放行；裸 `*` 又容易被错误扩散到平台级资源。服务端仍须逐请求校验主体、租户、动作和资源，并记录命中超级权限的审计事件。

**2. 权限码用字符串还是分层编码（如 `order:list:export`）？怎么做兼容演进？**

权限码本质上仍是稳定字符串，分层命名用于检索和治理，不应在前端靠切分字符串推导隐含权限。我会建立权限注册表，记录负责人、资源、动作、版本和废弃状态；重命名时服务端在过渡期同时下发新旧码，前端只通过统一 `hasPermission` 读取。上线顺序是先兼容消费者，再迁移角色绑定，最后监控旧码归零后删除，避免一次发布把入口全部隐藏。

**3. 多租户 SaaS 下，角色是租户内还是平台级？前端路由表怎么切？**

业务角色默认属于租户，平台运营角色进入独立命名空间，二者不能用同一个 `admin` 模糊表达。切租户时先使权限、字典、查询和 `keep-alive` 缓存按租户键失效，再拉取新租户能力并重建动态路由；切换完成前阻断业务请求。路由只是展示投影，服务端仍从可信会话解析租户并校验资源归属，不能接受前端传来的 tenantId 作为授权依据。

:::

**踩坑：** 只藏按钮不拦路由——用户改 URL 仍进页；或只拦路由不藏按钮——体验差且接口仍可能被直接调。前后端必须同一套码。

### Q2. 动态路由你怎么从「后端菜单」落到 Vue Router？

**考察点：** 菜单树 → 路由表、组件映射、404 / 403、刷新后还原

::: details 参考答案
流程口述：登录后拉菜单 / 权限 → 前端把后端节点映射成 `RouteRecordRaw` → `router.addRoute` → 再放行导航。关键不是 API 形状，而是**组件怎么安全解析**。

常见两种：
1. **后端只给 path + 组件名字符串**，前端维护 `componentMap`（`OrderList: () => import('...')`）——安全，可审查；
2. **后端给相对路径**，前端 `import.meta.glob` 扫 views 再匹配——灵活，但要防路径穿越与漏扫。

刷新页面：权限与动态路由在内存，必须在 `beforeEach` 里做「未加载则先拉权限再 addRoute，然后 `next({ ...to, replace: true })`」——这是高频坑。404 要最后挂；无权限走 403 页而不是空白。

布局路由（`Layout` + `children`）通常前端固定外壳，业务页动态挂 children。口述强调：**动态的是业务树，不是整棵路由哲学重写**。
:::

**追问链：**
1. `addRoute` 后为什么有时第一次导航还是 404？
2. 微前端或多 layout（侧栏 / 顶栏 / 空白页）时，动态路由挂在哪一层？
3. 路由 `meta` 里你会放哪些字段？哪些绝不能信前端伪造？

::: details 追问参考答案

**1. `addRoute` 后为什么有时第一次导航还是 404？**

常见原因是当前导航开始匹配时动态路由尚未注册，或兜底 404 的匹配优先级、父路由名称和重定向配置不正确。守卫中应先完成权限初始化与 `addRoute`，再以 `replace: true` 重新发起同一目标导航，而不是让原导航继续；同时用一次性初始化状态防止死循环。排查时打印注册前后的 `router.getRoutes()`、目标 `matched` 和守卫时序，避免靠延时器碰运气。

**2. 微前端或多 layout（侧栏 / 顶栏 / 空白页）时，动态路由挂在哪一层？**

我会先固定 Layout 与微前端容器等壳路由，再让后端菜单节点声明受限的 `layoutKey` 或应用标识，由前端白名单映射到对应父路由名。普通业务页挂在选定 Layout 的 children，微应用只挂到它的容器入口，空白页进入独立父级，不能让后端直接提供任意组件路径。这样导航、面包屑和卸载边界稳定，也便于按父路由整体撤销某租户或应用的动态路由。

**3. 路由 `meta` 里你会放哪些字段？哪些绝不能信前端伪造？**

`meta` 可承载标题、图标、布局、缓存策略、面包屑、菜单高亮和展示所需权限码，这些都属于客户端体验配置。租户范围、数据权限、资源归属、审批资格和 API 授权结果绝不能由 `meta` 决定，因为用户可修改运行时状态或直接绕过页面请求接口。前端守卫只做导航体验控制，服务端对每次敏感操作重新校验，并把拒绝原因映射为 401、403 或约定业务错误。

:::

**踩坑：** 组件 map 用了同步 `import`，首屏把所有后台页打进主包——动态路由≠懒加载，要确认是 `() => import()`。

### Q3. 你会怎么封装一个「类 ProTable」的列表页？边界画在哪里？

**考察点：** 查询区 + 表格 + 分页约定、插槽扩展、反模式

::: details 参考答案
目标：把「搜、表、页、刷新、列设置」收敛成约定，让业务页只声明**列、请求、操作**。

我习惯的契约：
- `api`：`(params) => Promise<{ list, total }>`，统一分页字段转换（`current/pageSize` ↔ 后端）；
- `columns`：列定义 + 可选 `valueType`（金额、字典、日期）；
- `search`：字段 schema 或从 columns 推导；
- 插槽：`toolbar`、`bodyCell`、行操作；
- 命令式：`reload()`、`getSelected()`、重置查询。

封装原则：**约定优于配置地狱**。能覆盖 80% CRUD 列表即可；超复杂筛选、行内编辑、树表、可编辑单元格别硬塞进 ProTable——拆专用页或提供「无头模式」只包请求与分页。

口述金句：ProTable 是**减少样板**，不是第二个低代码平台。团队要有「什么时候不准用封装」的清单。
:::

**追问链：**
1. 查询参数与 URL query 同步吗？刷新还原筛选你怎么做？
2. 多 Tab 列表共用一个封装时，缓存与请求竞态怎么处理？
3. 列设置（显隐 / 排序）持久化到 localStorage 还是用户配置中心？

::: details 追问参考答案

**1. 查询参数与 URL query 同步吗？刷新还原筛选你怎么做？**

可分享、可回退的筛选条件应同步 URL，临时输入、敏感字段和大对象不放进去。我会用一份规范化 Query Model，通过纯函数解析和序列化数组、日期、空值与默认值；页面初始化先校验 URL 再填表和请求，提交筛选时重置页码并通常使用 `router.replace`。无效参数回退默认值并上报，浏览器前进后退也走同一水合流程，避免表单、路由和表格互相 watch。

**2. 多 Tab 列表共用一个封装时，缓存与请求竞态怎么处理？**

缓存键至少包含租户、用户、路由实例和规范化查询，不以组件名或当前 URL 粗粒度复用。每个 Tab 保存独立查询、分页、滚动和选择状态；请求使用 `AbortController` 或递增序号，只允许当前 Tab 的最新响应落库和关闭 loading。切 Tab 不一定取消可复用请求，但响应必须写入对应键；关闭 Tab、切租户和退出登录时精确清理，避免数据串页或串租户。

**3. 列设置（显隐 / 排序）持久化到 localStorage 还是用户配置中心？**

只要求本机记忆且不敏感时可用 localStorage，但键要包含用户、租户、页面和列协议版本；跨设备、受管岗位或需要管理员下发默认值时应使用用户配置中心。我会保存列 key、显隐、顺序和宽度，不保存渲染函数，并在加载时与当前列白名单合并。新增列采用产品默认值，删除列自动丢弃；远端写入带版本或更新时间，解决多端覆盖冲突。

:::

**踩坑：** 封装里偷偷改响应结构或吞错——业务页调试时「接口明明有数据表格空」，查半天真凶是适配层。

### Q4. 大数据量表格卡顿，你会按什么顺序排查和优化？

**考察点：** 渲染成本、分页 vs 虚拟滚动、列过多、单元格重渲染

::: details 参考答案
先归因再动手：是**行数**、**列数 / 复杂单元格**、还是**频繁整表重渲染**？

顺序：
1. **业务层**：默认分页，禁止一次拉 1 万行「图省事」；导出走异步任务；
2. **渲染层**：单元格别塞重型组件；字典用纯文本 / 轻量 tag；避免每行 `deep watch`；
3. **表格层**：固定列、横向滚动时注意合成层；必要时虚拟滚动（见 Q11）；
4. **数据层**：行 key 稳定；更新用局部 patch，别每次 `dataSource = res.list` 换全新深对象树还附带巨型 computed。

口述要有数字感：200 行 × 30 列 × 每格一个组件 ≈ 6000 个 VNode，比「AntDV 慢」更接近真相。十年经验：先砍复杂度，再谈虚拟列表。
:::

**追问链：**
1. 为什么「只是加了个自定义 filterDropdown」整表就抖？
2. `rowSelection` 跨页勾选状态你怎么存？
3. 服务端排序 / 筛选与前端排序如何分工？

::: details 追问参考答案

**1. 为什么「只是加了个自定义 filterDropdown」整表就抖？**

通常不是下拉本身，而是它让 columns、插槽闭包或筛选状态在每次输入时整体重建，Table 因此重新计算列并渲染大量单元格；下拉内重型组件、同步测量和深层响应式对象会进一步放大抖动。我会用 Vue Performance 与组件更新高亮确认触发源，稳定列定义和 `rowKey`，把草稿筛选与已提交查询分开，并让弹层只更新自身。若服务端筛选，则确认后再刷新数据，不在每个按键上重建整表。

**2. `rowSelection` 跨页勾选状态你怎么存？**

选择状态必须由业务主键受控保存，不能依赖当前页行对象、数组下标或 DOM。普通跨页选择维护 `selectedRowKeys` 集合，并按权限变化清理失效项；「全选全部结果」不能存十万条 ID，应表达为查询快照加排除集合。提交时把选择模式、查询版本和排除项交给服务端再次鉴权，页面明确显示范围；筛选条件改变时要求用户确认清空，或创建新的选择快照。

**3. 服务端排序 / 筛选与前端排序如何分工？**

只要数据经过分页，排序和筛选就应由服务端对完整结果集执行，否则前端只能处理当前页，却容易给用户造成全量已排序的错觉。前端负责受控保存 sorter、filters 与分页，将列 key 映射到服务端允许字段，并展示加载和空态；本地排序仅用于已明确全量加载的小字典或临时视图。服务端要白名单校验字段、保证稳定次序，并用唯一键补齐同值排序，避免翻页重复或漏行。

:::

**踩坑：** 用 `v-if` 控制整表销毁重建代替刷新——数据一多必闪白；优先改 `dataSource` 或 `key` 策略要克制。

### Q5. Schema 表单（配置化表单）你怎么落地？和「手写 a-form」怎么选？

**考察点：** JSON Schema / 自研 schema、校验、联动、可维护性

::: details 参考答案
Schema 表单适合：**字段多、常改、多端/多租户差异大**的中后台录入。手写 Form 适合：**强交互、复杂步进、高度定制布局**。

落地要点：
- 字段描述：`name`、`label`、`component`、`props`、`rules`、`visible`/`disabled` 表达式；
- 联动：依赖字段变化时重算可见性与选项（要防循环依赖）；
- 校验：复用 async-validator / Zod 一类，前后端规则尽量同源文档；
- 布局：栅格、分组、分步——schema 表达布局别无限嵌套。

风险：配置膨胀后「没人敢改」；调试比 Vue 模板难。治理手段：schema 分模块、可视化搭建与代码导出二选一要克制、复杂字段允许 `slot` / 自定义组件逃逸。

口述结构：先讲选型边界，再讲联动与校验，最后讲**逃生舱**——这才像带过项目的人。
:::

**追问链：**
1. 表达式用字符串 `eval` 还是 JS Function？安全与 DX 怎么权衡？
2. 后端下发表单 schema 时，如何防恶意 component 名？
3. 和低代码平台的边界你怎么画？

::: details 追问参考答案

**1. 表达式用字符串 `eval` 还是 JS Function？安全与 DX 怎么权衡？**

后端下发内容不执行 `eval`，也不把任意 `Function` 当配置；两者都扩大注入面，难以静态分析、审计和灰度回滚。我会采用受限 DSL，或只允许引用前端注册表中的具名谓词，输入限制为表单值和只读上下文，输出限制为 visible、disabled 等声明结果。动态规则映射到响应式 rules，异步校验加序号或取消，避免旧结果覆盖；复杂规则回到可测试代码。

**2. 后端下发表单 schema 时，如何防恶意 component 名？**

Ant Design Vue Form 只提供 model、rules、FormItem 与校验能力，并不原生解释业务 schema，因此渲染器必须自行设防。component 名只能查前端白名单注册表，props、事件、插槽和远程选项协议也分别校验，未知项拒绝渲染并告警；不能把字符串当模块路径动态导入。Schema 还要携带版本，服务端最终重复做字段、权限和业务校验，前端白名单不是安全终点。

**3. 和低代码平台的边界你怎么画？**

Schema Form 只解决受控字段、布局、联动、校验和提交转换，目标是减少同类录入页样板；一旦需要流程编排、页面搭建、数据源治理、权限模型、发布版本和可视化调试，就已进入低代码平台范畴。我会设复杂度门槛：少量特殊字段走 slot 或业务组件，跨页面状态机回代码实现。是否升级平台要看复用率、交付角色和治理投入，不能让一份 JSON 悄悄承担平台职责。

:::

**踩坑：** 把业务规则全写进 schema 字符串，Code Review 形同虚设——规则一复杂就该回到代码。

### Q6. 上传 / 下载在中后台你会怎么设计？大文件和权限怎么讲？

**考察点：** 直传 / 中转、进度与断点、下载鉴权、导出任务化

::: details 参考答案
上传分场景：
- **小文件走业务网关**：简单，便于鉴权与病毒扫描；
- **大文件 / 私有云**：前端直传 OSS（STS 临时凭证）+ 回调业务登记——省带宽、可断点；
- 组件层：`a-upload` 控 `beforeUpload`、文件类型 / 大小、自定义请求、失败重试；别默认把整文件转 base64 塞进 JSON。

下载：
- 有权限的文件用**带鉴权的下载接口**或短时签名 URL，禁止长期公开链；
- Excel / 报表导出：同步下载只适合小结果；超时与大结果必须**异步任务 + 通知 / 轮询**。

口述强调：上传成功只代表对象存储有了，**业务状态要以服务端登记为准**；下载失败要区分网络、权限、文件过期。
:::

**追问链：**
1. 图片要压缩再传，你放前端还是网关？
2. `Content-Disposition` 中文文件名乱码你怎么处理？
3. 同一表单多文件与表单字段提交的事务一致性怎么讲？

::: details 追问参考答案

**1. 图片要压缩再传，你放前端还是网关？**

前端压缩适合预览图、弱网和降低上传带宽，但结果不可作为唯一可信版本：浏览器编码能力、EXIF 方向、色彩空间和内存上限差异明显。原图有留档、取证或二次裁剪价值时应直传私有存储，再由服务端异步生成规格图；网关不适合承担长耗时图像计算，可交给媒体服务。前端只做可取消的体验优化，并把原始尺寸、压缩策略和失败回退展示清楚。

**2. `Content-Disposition` 中文文件名乱码你怎么处理？**

服务端应同时提供 ASCII 兼容的 `filename` 和按 RFC 5987 编码的 `filename*=UTF-8''...`，并正确暴露响应头；前端 blob 下载时优先解析 `filename*`，解码后清理路径分隔符、控制字符和超长名称。不能直接信任响应头拼成本地文件名，也不要手写一次 `encodeURI` 就认为兼容完成。需在 Chrome、Edge 与实际网关链路验证代理改写。

**3. 同一表单多文件与表单字段提交的事务一致性怎么讲？**

浏览器上传和数据库事务无法做真正原子提交，我会采用暂存加确认协议：文件先以临时对象上传并返回 fileId，业务提交只携带这些 ID；服务端在一个事务内校验归属、状态和权限，写业务记录并把文件标记为已绑定。提交失败可重试，未绑定临时文件由定时任务回收。多次提交使用幂等键，删除和替换也走服务端状态机，不能让前端自行声明上传成功即业务成功。

:::

**踩坑：** 用 `window.open(url)` 下带 token 的文件——token 进 Referrer / 历史；应 blob 下载或短时签名。

### Q7. 按钮级权限你怎么做才不又臭又长？

**考察点：** 指令 / 组件 / 函数式鉴权、与后端码对齐、无权限时隐藏 vs 禁用

::: details 参考答案
三层工具都要，按场景用：
1. **函数** `hasPermission('order:export')`——逻辑分支、组合条件；
2. **组件** `<Auth code="...">`——包一截 DOM；
3. **指令** `v-auth`——简单显隐，注意指令对组件根节点、异步更新的坑。

产品策略：无权限**隐藏**（减少噪音）还是**禁用 + Tooltip 说明**（让人知道有功能但无权限）——需和产品统一，别一页一种。

实现上权限码来自登录态 / 权限接口，放 Pinia；路由 `meta.permission` 与按钮码同一套。禁止硬编码角色名。

十年经验：按钮权限的维护成本在「码表治理」，不在指令写法——码要可检索、可废弃、有负责人。
:::

**追问链：**
1. 一个按钮依赖「权限码 + 行状态」双重条件，封装放哪？
2. 指令删除 DOM 与 `v-if` 哪个更稳？SSR / 测试呢？
3. 权限变更后如何热更新，要不要强制重新登录？

::: details 追问参考答案

**1. 一个按钮依赖「权限码 + 行状态」双重条件，封装放哪？**

权限能力由统一鉴权函数提供，行状态能否操作则由领域策略函数判断，页面只组合两者并生成可执行、禁用及原因三态。不要把订单状态机塞进通用 `v-auth`，也不要让组件库认识业务枚举；可在业务模块提供 `getOrderActions(row, abilities)`，同时供操作列、批量工具栏和测试复用。服务端仍须按最新资源状态和权限重新校验，前端判断只负责一致体验与提前解释。

**2. 指令删除 DOM 与 `v-if` 哪个更稳？SSR / 测试呢？**

能在模板表达时优先 `v-if` 或 Auth 组件，因为渲染条件显式、SSR 水合可预测，也容易在组件测试中断言。删除 DOM 的指令属于挂载后的命令式修改，对组件多根节点、权限异步变化、服务端渲染和事件清理更脆弱，适合约束明确的简单元素。无论采用哪种方式，都应让首屏权限状态确定，避免先渲染后移除造成闪现；敏感操作最终仍由服务端授权。

**3. 权限变更后如何热更新，要不要强制重新登录？**

普通权限热更新：版本/事件拉权，重建菜单/路由/按钮并关闭失权页；服务端始终最终鉴权。主体变化、refresh 撤销/过期、会话安全策略变化、降权不收敛则强制重登。页内 single-flight，跨标签 Web Locks 互斥；BroadcastChannel 只通知结果。无 Web Locks 靠服务端 rotation 原子、幂等/宽限，`invalid_grant` 后单次重登。仅重放确认未执行请求，写操作带幂等键。

:::

**踩坑：** `v-auth` 只 `display:none`——元素还在，爬虫或误点仍可能触发；应移除或真正禁用事件。

### Q8. 菜单、多页签与 `keep-alive` 你怎么一起设计？

**考察点：** 缓存 key、页签关闭、onActivated、内存泄漏

::: details 参考答案
中后台常见「侧栏菜单 + 多页签 + 页面缓存」。模型：
- 路由 `name` 必须稳定且唯一，`keep-alive` 的 `include` 跟页签打开集合走；
- 打开页签 = 加入缓存名单；关闭页签 = 从 include 剔除并删组件实例；
- 同路由不同参数（两个订单详情）要决定：共用一个缓存还是 `key` 到 params——多数详情**不缓存**或按 id 限长 LRU。

生命周期：首次 `onMounted`，回页签 `onActivated`——拉数放哪要约定清楚，避免双请求。离开时重置临时 UI 状态（弹窗、抽屉）防「幽灵弹层」。

口述强调：**缓存是产品体验，不是默认全开**。列表可缓存；巨型报表、带 WebSocket 的页谨慎。
:::

**追问链：**
1. 关闭「其他 / 全部」页签时，如何批量清缓存？
2. `keep-alive` 与动态路由 name 不一致导致缓存失效，你怎么查？
3. 缓存页里定时器 / 事件监听漏清，你会在哪一层兜底？

::: details 追问参考答案

**1. 关闭「其他 / 全部」页签时，如何批量清缓存？**

页签仓库应同时维护可见页签和 `keep-alive` include，不让页面自己零散管理。批量关闭时先计算保留集合，再一次性更新 include；需要确保实例释放时，可先移出缓存并等待一个渲染周期，再删除页签状态、查询快照和滚动位置。固定首页、正在提交或有脏表单的页签要按策略保留或逐个确认。清理依据稳定 route name 与实例 key，不能遍历 DOM 猜测哪些页面仍存活。

**2. `keep-alive` 与动态路由 name 不一致导致缓存失效，你怎么查？**

先确认 Vue 缓存匹配的是组件名及 include 规则，团队是否错误地把 route name 当成组件名使用；再检查动态组件是否有稳定 name、同一路由是否因 key 变化反复创建。排查时记录 `to.name`、组件 name、VNode key、include 集合和生命周期时序。解决方案是建立明确映射并做唯一性校验，不靠路径截取生成名字；动态路由注册时即可在开发环境报错。

**3. 缓存页里定时器 / 事件监听漏清，你会在哪一层兜底？**

页面资源应封装为可暂停的 composable：`onActivated` 恢复，`onDeactivated` 暂停定时器与订阅，`onUnmounted` 最终销毁。全局层维护订阅注册表，在关闭页签、退出登录和切租户时按 scope 释放，并用计数告警发现重复监听。不能只依赖 `beforeUnmount`，因为进入 keep-alive 后组件并未卸载；WebSocket 等共享连接还要做引用计数，避免误关其他页面使用的资源。

:::

**踩坑：** 用路径当 keep-alive key，query 一变整页重建；或 include 写了组件名但路由 name 不同——缓存静默失效。

### Q9. 主题与布局（暗色、紧凑、多布局）你会怎么做才可维护？

**考察点：** CSS-in-JS、Design Token、ConfigProvider、布局切换

::: details 参考答案
Ant Design Vue 4 移除 Less 主题链路，采用 **CSS-in-JS + Design Token** 支持动态主题，通过 `ConfigProvider` 的 `theme` 配置 Token 与算法（默认 / 暗色 / 紧凑），业务少写死十六进制。业务可以在 Token 之上维护 `--app-*` CSS 自定义属性，服务图表、地图或自研组件，但它们是业务语义变量，**不是 Ant Design Vue 4 的主题机制**，需要显式从 Token 映射和同步。

布局：侧栏、顶栏、混合、内容全屏——用 layout 组件 + 路由 `meta.layout` 切换，别复制四套壳。宽度折叠、固定 Header、内容区滚动容器要统一，否则表格 sticky、弹层定位会到处打架。

持久化：用户主题偏好进 localStorage 或用户配置接口；**首屏要防闪**（先读偏好再绘，或内联脚本设 `data-theme`）。

口述别停在「能切暗色」：要讲**token 单一真相**和**业务自定义样式的逃生方式**（少 `!important` 盖组件）。
:::

**追问链：**
1. 图表、地图第三方画布如何跟暗色主题同步？
2. 多品牌白标如何在构建期 / 运行期切换 token？
3. 紧凑模式下表格行高与可点击热区怎么平衡无障碍？

::: details 追问参考答案

**1. 图表、地图第三方画布如何跟暗色主题同步？**

Ant Design Vue 4 的主题由 ConfigProvider、Design Token 与 CSS-in-JS 驱动，Canvas 图表不会自动继承 CSS。我会在受 ConfigProvider 包裹的组件内读取当前 Token，映射为业务语义色，再显式调用图表或地图实例的主题更新接口；切换时节流重绘并保持数据、缩放和选中状态。颜色还要验证对比度和色盲可辨识性，不能只把背景改黑；导出图片应固定记录所用主题版本。

**2. 多品牌白标如何在构建期 / 运行期切换 token？**

少量完全隔离的品牌可在构建期注入品牌配置，获得更小资产和更严格隔离；同一部署承载多租户时，用 ConfigProvider 的响应式 theme 配置切换 Token，并把 logo、图表色和业务 CSS 变量归入同一版本化品牌包。缓存键必须包含品牌或租户，服务端返回配置前先校验域名归属。首屏在挂载前读取已确认品牌并注入基础背景，避免闪成默认主题；失败时回退安全默认品牌。

**3. 紧凑模式下表格行高与可点击热区怎么平衡无障碍？**

紧凑是提高信息密度，不等于无限压缩交互目标。我会分别定义视觉行高与真实点击区域：文字可紧凑，但复选框、图标按钮和行操作保留足够热区、可见焦点和键盘顺序。触控设备或低精度指针应降低信息密度并增大点击热区，但不能仅靠 `pointer` 媒体查询牺牲桌面可用性；混合输入设备和环境识别可能失真，仍要按实际设备、任务和用户密度设置验证。

:::

**踩坑：** 全局覆写 `.ant-btn` 颜色「调品牌色」，升级 AntDV 后全站回归——应走 token / 少层包装组件。

### Q10. 字典 / 枚举如何与后端同步，避免前后端各写一套？

**考察点：** 字典服务、缓存、本地兜底、类型生成

::: details 参考答案
原则：**枚举语义以后端 / 数据字典为准**，前端不做第二真相。

常见架构：
1. 启动或首次使用时拉字典（按 type 分批）；
2. Pinia / 内存缓存 + 版本号 / ETag；变更低频可长缓存，变更频繁按 type 失效；
3. 表格 / 表单通过 `valueType: 'dict'` 或组件 `DictSelect` 消费；
4. 编译期：若后端 OpenAPI / 枚举稳定，可 codegen TS 联合类型——运行时仍以后端值为准做校验。

展示层：`code → label`，未知码显示原文 + 打点，别静默成空白。前后端口径冲突时，联调以接口文档与字典服务为准，前端写死常量只做「网络失败兜底」且要可观测。
:::

**追问链：**
1. 字典项上百万怎么办？还拉全量吗？
2. 多语言下 label 放前端 i18n 还是字典服务？
3. 后端改了枚举含义但码不变，前端如何发现？

::: details 追问参考答案

**1. 字典项上百万怎么办？还拉全量吗？**

百万级内容已不是适合全量缓存的普通字典，应改成服务端搜索或分页实体选择器。前端按租户、字典类型、查询词和游标缓存有限结果，输入防抖、请求可取消，并为已选 ID 提供批量回显接口；不能为了显示 label 拉整库。服务端负责权限过滤、稳定排序和索引，热点项可单独预取。导出与提交只传稳定 code/ID，由服务端按同一数据版本解释，避免客户端缓存旧语义。

**2. 多语言下 label 放前端 i18n 还是字典服务？**

固定、随版本发布的界面枚举可用前端 i18n，运营可配置、租户自定义或频繁变化的 label 应由字典服务按 locale 返回。无论哪种方式，code 都保持稳定，缓存键必须包含租户、语言和字典版本；语言切换后精确失效 label，不能复用上一语言结果。若服务端缺翻译，可按约定回退默认语言并标记缺失，监控补齐率；不要把中文 label 当业务判断条件。

**3. 后端改了枚举含义但码不变，前端如何发现？**

复用旧码却改变业务语义属于破坏性变更，正确做法是新增码或提升字典协议版本并提供迁移期。前端通过 ETag、版本号和契约测试发现变化，未知或版本不匹配时保留原码、告警并阻断高风险提交；普通展示可使用可接受的新鲜旧缓存。发布流水线还应比对字典快照，要求负责人确认删除、重命名和状态迁移，不能依赖短 TTL 希望用户自己刷新后“自然正确”。

:::

**踩坑：** 前端本地写死一份 statusMap，后端加新状态，线上出现「空白标签 / 筛选不到」——还查不出错。

### Q11. 标准 `a-table` 的纵向滚动与真正虚拟化有什么区别？

**考察点：** `scroll.y`、滚动容器、虚拟列表定义、选型边界

::: details 参考答案
标准 `a-table` 的 `scroll.y` 只是给表体设置纵向滚动区域和固定表头，数据行仍会进入 DOM，**不等于虚拟化**。面试先把这个定义讲准：真正虚拟列表只渲染视口附近行，才会显著减少节点数量。

基础选型只回答三件事：
1. 后端分页能满足业务时，优先分页；
2. 连续浏览大数据确有价值时，再评估官方文档链接到的 Surely Table、第三方网格或自研虚拟 body；
3. 固定列、展开行、合并单元格、编辑态和动态行高都必须实测，不能因配置了 `scroll.y` 就宣称已优化。

Q11 只负责辨清概念和单点选型；窗口状态、无障碍与故障降级留给 D3。
:::

**追问链：**
1. 如何用 DOM 数量证明 `scroll.y` 没有虚拟化？
2. Surely Table、第三方网格和自研 body 分别适合什么边界？
3. 为什么列很多时只做行虚拟仍可能卡？

::: details 追问参考答案

**1. 如何用 DOM 数量证明 `scroll.y` 没有虚拟化？**

准备稳定的千行数据，只开启 `scroll.y`，在开发者工具统计表体行节点并滚动到首尾；若 DOM 行数仍接近数据量，只是容器出现滚动条，就不是虚拟化。再用 Performance 记录渲染、样式计算和内存，与只渲染几十行窗口的方案对照。截至当前 Ant Design Vue 4.x，标准 Table 没有 React Ant Design 的 `virtual` 属性，不能把 React 文档 API 套到 Vue 版本。

**2. Surely Table、第三方网格和自研 body 分别适合什么边界？**

Surely Table 适合希望保持 Ant 风格且需要成熟虚拟表格能力的项目，但应逐版本核对授权、固定列、展开、编辑与包体；第三方网格适合分组、透视、聚合等重数据工作台，代价是视觉体系、学习成本和迁移风险。自研 body 只适合列型和交互受控的场景，因为列宽同步、固定列、展开行、动态测量、键盘和升级兼容都要自行负责。选型前应以真实页面建立兼容矩阵和降级方案。

**3. 为什么列很多时只做行虚拟仍可能卡？**

行虚拟只减少纵向节点，视口内仍可能同时渲染几十行乘上上百列；固定列还会增加层叠与同步成本，单元格里的 Tooltip、编辑器、图表和深层响应式计算也不会自动消失。应先裁剪默认列、按场景分组展示，稳定 columns 与渲染函数，并评估列虚拟或专用网格。验收要分别观察脚本、布局、绘制和内存，不能只看到 DOM 行数下降就宣布问题解决。

:::

**踩坑：** 把 `:scroll="{ y: 600 }"` 当成虚拟滚动，数据量上来后仍渲染全部行；或换了虚拟方案却每行塞编辑器和图表，DOM 少了但计算仍然爆炸。

### Q12. 弹窗 Modal 和抽屉 Drawer，中后台 UX 你怎么选？

**考察点：** 信息架构、任务时长、多层叠、表单场景

::: details 参考答案
直觉模型：
- **Modal**：短任务、强聚焦、要明确确认（删除确认、小表单、关键警告）。模态打断主流程，适合「做完再回去」；
- **Drawer**：中长表单、详情对照列表、需要同时瞥见背后上下文。从侧面推入，空间更大，适合「边看列表边改」。

细则：
- 表单字段多、有分步 → Drawer 或独立页，别塞巨大 Modal；
- 危险操作 → 小 Modal 确认，文案讲清不可逆后果；
- 避免 Modal 套 Modal、Drawer 套 Modal 叠罗汉——改为步进或独立路由页；
- 关闭拦截：脏数据要确认；Esc / 遮罩点击是否可关要按表单危险级别定。

十年经验：组件选择是信息架构问题，不是「哪个好看」。面试讲清**任务时长 × 是否需要对照上下文**两个轴就够打动人。
:::

**追问链：**
1. 详情既要分享 URL 又要抽屉体验，怎么做？
2. 移动端宽度下 Drawer/Modal 策略如何降级？
3. 全局唯一弹层管理（防多个业务同时弹）你怎么做？

::: details 追问参考答案

**1. 详情既要分享 URL 又要抽屉体验，怎么做？**

把抽屉视为路由驱动的详情：子路由或 query 只保存不含 PII、凭证的非秘密 opaque ID，直接访问仍能加载，关闭时返回列表。opaque 不等于保密，URL 会进入浏览器历史、服务器日志和 Referrer；站点应配置严格的 `Referrer-Policy`，服务端每次按主体、租户和资源重新鉴权。若没有列表背景，则降级为独立详情页，避免分享链接打开空壳抽屉。

**2. 移动端宽度下 Drawer/Modal 策略如何降级？**

小屏下长表单优先变为全屏 Drawer 或独立路由页，短确认仍可用尺寸受控的 Modal；不能简单把桌面宽度按比例缩小。需要重排字段、让底部操作避开安全区、保证软键盘出现后焦点和按钮可见，并支持返回键与关闭前脏数据确认。断点只是起点，还要按内容长度、输入方式和任务时长决策；真实移动设备上验证滚动锁、焦点归还和读屏顺序。

**3. 全局唯一弹层管理（防多个业务同时弹）你怎么做？**

我会用弹层协调器按 key 和优先级排队：同 key 去重，危险确认不被普通提示覆盖，路由切换统一取消；业务只提交请求，不操纵其他模块。Ant Design Vue 4 的静态 Modal、message 不继承 ConfigProvider 上下文；应用级用 `<a-app>` 后代的 `App.useApp()`，局部用 `Modal.useModal()`、`message.useMessage()` 并渲染 holder，再把实例交给协调器。

:::

**踩坑：** 列表页每个操作都开全屏 Modal 重型表单——用户失去列表上下文，保存后还要重新找行。

### Q13. 中后台「操作列 / 批量操作」权限与交互怎么设计才稳？

**考察点：** 行操作收敛、批量权限、二次确认、失败部分成功

::: details 参考答案
行操作超过三个就收进「更多」；危险操作（删除、作废、打款）视觉降权并二次确认。批量操作：工具栏按钮受权限码控制，且**以勾选行的实际可操作集合为准**——部分行不满足状态时，要么禁用并提示原因，要么允许提交由后端过滤并返回部分成功报告。

前端要处理：
- 跨页勾选的数据范围提示（当前页 / 全部结果）；
- 批量请求的并发限制与进度；
- 部分失败时的明细展示与可重试。

口述强调：批量是后端事务与幂等问题，前端负责**预期管理**，别假装 100% 成功。
:::

**追问链：**
1. 「跨页全选 10 万条」产品坚持要，你怎么技术谈判？
2. 操作列根据行状态动态变化，和按钮权限指令如何组合？
3. 审计日志要记「谁点的」，前端埋点还是纯后端？

::: details 追问参考答案

**1. 「跨页全选 10 万条」产品坚持要，你怎么技术谈判？**

查询条件加排除集合并不能冻结十万条范围。我会先预览，由服务端在同一授权与数据版本下生成不可变 selection token，内部指向固定 ID 集合或可重复读取的数据版本；异步任务按 token 分批执行并记录幂等键。若执行前数据版本变化或 token 过期，必须重新预览影响数量并由用户确认，不能把新数据悄悄纳入。再配合限流、取消和部分失败报告，谈判依据是误操作半径与可审计性。

**2. 操作列根据行状态动态变化，和按钮权限指令如何组合？**

先由业务策略根据行状态计算允许动作及禁用原因，再与统一权限能力求交集，最后由操作列渲染器决定展示、禁用或收进“更多”。权限指令只处理单个动作的能力，不承担状态机，以免同一规则在列表、详情和批量入口表现不同。动作定义应包含 code、label、danger 和 handler，便于复用与测试；点击后服务端仍按最新状态和权限校验，遇到并发变化时返回可解释冲突。

**3. 审计日志要记「谁点的」，前端埋点还是纯后端？**

可信审计必须由服务端根据认证会话记录主体、租户、动作、资源、结果、时间和 traceId，不能信任前端上传的 userId，也不能把“点击”当作“操作成功”。前端埋点仍有价值，可记录入口曝光、确认与取消等体验行为，并携带相关 traceId 便于串联，但它属于行为分析。敏感前后值要脱敏或摘要化，审计存储设置防篡改、保留期限和访问权限，查询链路与业务库适当隔离。

:::

**踩坑：** 前端过滤完可操作行再调接口，后端没校验——篡改请求即可越权批量。

### Q14. 表格列的「自定义渲染 / 插槽」泛滥了，你怎么治理？

**考察点：** 列工厂、价值类型、性能与一致性

::: details 参考答案
症状：每个页面复制 `bodyCell` 大段 switch，字典、金额、时间、用户卡片各写一套，样式还不一致。

治理：
1. **valueType 映射**：`money`、`date`、`dict`、`user`、`status` 走统一渲染器；
2. **列工厂函数**：`col.dict('status', STATUS)`、`col.money('amount')`；
3. 真正特殊的业务列才允许页面级 slot，并限制复杂度；
4. 文档化「推荐渲染器清单」，Code Review 盯重复 UI。

性能上：渲染器保持纯函数 / 轻量组件；禁止在 render 里 new 大对象或现场请求。一致性比「这页特别好看」更重要——中后台是效率工具。
:::

**追问链：**
1. 渲染器要不要自动加 Tooltip 处理超长文本？
2. 空值显示 `—` 还是空白，如何全局统一？
3. 列渲染与导出 Excel 的字段格式如何复用？

::: details 追问参考答案

**1. 渲染器要不要自动加 Tooltip 处理超长文本？**

不应给每个单元格无条件挂 Tooltip，也不要为静态截断文本批量添加 `tabindex`，否则会制造大量 Tab 停靠点和读屏噪音。仅当承载元素本就可操作或可聚焦时，Tooltip 才同时支持 hover、focus 触发，并通过可访问描述关联完整说明；敏感内容仍需脱敏。普通静态长文本应提供行内展开或详情入口，让键盘与触控用户都能主动读取完整内容。

**2. 空值显示 `—` 还是空白，如何全局统一？**

展示态建议统一用 `—` 表示无值，避免用户把空白误认为渲染失败；但表单输入、可复制数据和机器导出不能直接复用该占位符。应由基础展示组件或 valueType 渲染器区分 `null/undefined`、空字符串、数值 0 和布尔 false，并允许少数业务语义覆盖。规范写进组件文档与视觉回归测试，页面不得用 `value || '—'`，否则合法的 0 和 false 会被错误替换。

**3. 列渲染与导出 Excel 的字段格式如何复用？**

复用的是领域格式规则，不是 Vue VNode 或 DOM 文本。我会为每个字段定义纯函数 formatter，输入原始值、记录、locale 和字典版本，分别由表格渲染器与服务端导出适配器消费同一协议；百万行导出仍由服务端完成，不能遍历当前页 DOM。金额保留原始数值与单位，日期明确时区，字典记录版本。若前后端无法共享代码，就用契约样例测试保证同一输入输出一致。

:::

**踩坑：** 在自定义渲染里直接调接口补全字段——表格一翻页请求风暴，应在数据层 join 好。

### D2. 复杂表格如何统一查询、URL、分页与请求竞态？

#### 原理深挖

### D4. 中后台权限如何形成前后端授权、数据范围与审计闭环？

::: details 参考答案
#### 基础结论
Q1/Q7/Q13 已回答 RBAC、按钮显隐和批量操作体验；D4 专注攻击与故障链路：服务端资源授权、凭证续期、跨租户隔离和可信审计。前端按钮仍然不是授权边界。

#### 原理深挖
权限判定至少包含主体、动作、资源、租户和上下文。RBAC 负责稳定角色集合，部门、归属人、订单状态等动态条件可由 ABAC 或策略层处理。前端拿到的是可展示能力或策略摘要，不能自行拼接 `departmentId` 就声称完成数据授权，更不能相信客户端上传的操作者身份。

#### 工程场景
权限码建立注册表与负责人，菜单、路由、按钮和 API 文档引用同一资源动作命名。HTTP 401 只表示请求缺少服务器可接受的认证凭证，或凭证不可接受；是否属于可续期过期必须结合 `WWW-Authenticate`、业务错误码或约定字段判断，不能见 401 就刷新。确认可续期时做 single-flight，等待请求最多重放一次；重放仍为 401 或刷新失败就清理登录态并退出。403 表示身份已被接受但无权执行。高风险操作使用幂等键、服务端审计事件和 traceId。

#### 反例 / 踩坑
只隐藏按钮、只校验路由、把 `role=admin` 写在前端、让前端传 `userId` 作为审计主体，都会留下越权或审计伪造空间。批量接口若只由前端过滤可操作行，篡改请求仍能越权。

#### 资深回答模板
「60–90 秒主回答：Q1/Q7 解决展示，安全边界仍在服务端按动作、资源、租户和数据范围授权。401 只说明凭证缺失或不可接受，先按业务码识别可续期过期，再 single-flight 刷新且最多重放一次；仍 401 就退出，403 直接按无权处理。关键操作由服务端记录可信主体、结果与 traceId。」

#### 追问链
1. 权限刚被回收但客户端仍有缓存，窗口期如何控制？
2. 多租户切换时，路由缓存和列表缓存如何防串租户？
3. 审计日志如何兼顾不可抵赖、脱敏与查询性能？
:::

### D5. 字典缓存如何做到高命中、可失效且不把旧语义带到线上？

::: details 参考答案
#### 基础结论
Q10 已回答字典来源、基础缓存和未知码展示；D5 专注多租户、多语言、大字典与服务故障下的一致性、失效和可观测性。

#### 原理深挖
低频字典适合 stale-while-revalidate：先展示新鲜度可接受的缓存，再条件请求校验 ETag 或版本。并发首次读取做 single-flight，避免几十个组件同时请求。服务端复用编码但修改含义属于破坏性变更，应通过新码或版本迁移，而不是期待 TTL 自动解决。

#### 工程场景
实现 `useDictionary(type)` 时返回 `status/data/error/refresh`，内存缓存为一级，持久化仅存必要字典。登录、切租户、切语言时按命名空间失效；未知码显示原码或「未知（code）」并上报。大字典改为远程搜索，不拉全量；导出任务由服务端按同一版本翻译。

#### 反例 / 踩坑

### D6. 百万行导入导出如何设计成可恢复、可审计的任务系统？

::: details 参考答案
#### 基础结论
Q6 已回答小文件上传、对象存储直传和同步/异步导出边界；D6 只处理百万行规模下的任务状态、部分成功、幂等恢复、数据快照和审计交付。

#### 原理深挖
导入链路是上传原文件 → 服务端扫描与解析 → 分批校验 → 幂等写入 → 生成错误报告；导出链路是冻结查询快照 → 后台生成 → 私有存储 → 短期授权下载。任务状态应单调演进并包含版本，重试需要幂等键；「取消」通常只能停止后续批次，不能假装回滚已提交事务。

#### 工程场景
前端先校验扩展名、大小和模板版本，但服务端重复校验 MIME、病毒、字段与权限。任务中心支持轮询、SSE 或通知恢复，刷新页面后仍可按 taskId 查询。导出记录查询条件、字段范围、数据版本和申请人；下载使用一次性或短时签名 URL，并限制敏感字段。

#### 反例 / 踩坑
前端用 `FileReader` 一次读入巨型文件会冻结页面或崩内存；同步接口等待报表生成容易超时。用公开永久 URL 交付含个人信息的文件，会绕过权限回收与审计。

#### 资深回答模板
「60–90 秒主回答：超过 Q6 的同步边界后，我把导入导出做成可恢复任务。原文件私有直传，服务端扫描、分批校验和幂等写入，前端只跟踪 taskId；导出冻结查询快照并短时授权下载。部分成功给错误报告，取消只停止后续批次，任务、申请人和下载全过程可审计。」

#### 追问链

2. 导出期间源数据变化，如何解释结果一致性？

### D7. Ant Design Vue 主题 Token 与二次封装如何避免双重 API 和升级锁死？

::: details 参考答案
#### 基础结论
Q9 已回答 Token、暗色与布局的基础方案，Q14 已回答列渲染器治理；D7 专注主题上下文丢失、命令式 API、包装组件透传和跨版本升级边界。

#### 原理深挖
全局 Token 解决品牌色、圆角、字号等基础语义，组件级 Token 处理局部差异，业务层再定义 `--app-color-risk` 等领域语义。包装组件若重新命名每个属性，会形成第二套 API；多根节点还可能导致 `$attrs`、`aria-*` 和事件没有落到真实交互元素。

#### 工程场景
我会分三层：直接使用 AntDV；薄封装如 `AppButton` 只加入权限、埋点或业务默认值；复合组件拥有独立领域契约。Ant Design Vue 4.x 有两条官方上下文路径：
1. **局部 hooks**：分别调用 `message.useMessage()`、`Modal.useModal()`、`notification.useNotification()`，取得 API 与 `contextHolder`，并把 holder 渲染在需要继承的上下文内；适合局部作用域；
2. **应用级 App**：在应用上层渲染 `<a-app>`，其后代组件内调用 `App.useApp()` 取得 `message`、`modal`、`notification`，减少手工 holder；应用级场景优先此方案。`App.useApp()` 必须在 `<a-app>` 后代调用。若还要消费主题 Token，应让 `<a-config-provider>` 包住并与 `<a-app>` 配对；`ConfigProvider` 负责 Token 等配置，不替代 `<a-app>` 的上下文实例。

#### 反例 / 踩坑
全局覆盖 `.ant-*` 内部类、堆 `!important` 或复制全部组件 props，会在升级时集中爆炸。直接调用导入的全局 `message`、`Modal`、`notification` 静态方法，其动态创建的 Vue 实例不在当前上下文中，可能拿不到主题、locale、Pinia 等配置。使用 hooks 却忘记渲染 `contextHolder`，或在 `<a-app>` 外调用 `App.useApp()`，同样无法得到预期上下文。

#### 资深回答模板
「60–90 秒主回答：AntDV 4 的主题机制是 CSS-in-JS、Design Token 和 ConfigProvider，`--app-*` 只是业务变量。命令式反馈有两路：局部用三个 `use*` hooks 并渲染 holder；应用级优先 `<a-app>`，后代再用 `App.useApp()`。ConfigProvider 负责 Token，App 负责上下文化实例；封装仍按薄约定与领域组件分层。」

#### 追问链
1. `Modal`、Message 等命令式能力如何接入主题上下文？
2. 白标租户需要运行时换品牌时，缓存和首屏如何处理？
3. 哪些变更应升级组件库，哪些适合业务 Token 覆盖？
:::

### D8. 中后台如何把无障碍、审计与稳定性做成可验收的工程指标？

::: details 参考答案
#### 基础结论
Q12/Q13 已回答弹层选型和批量操作交互；D8 专注把无障碍、可信审计和稳定性从页面建议提升为可量化门禁、运行指标与故障降级。

#### 原理深挖
语义化控件提供浏览器默认键盘与可访问性树；自造 `div` 按钮需要补角色、Tab 顺序和键盘行为。Modal/Drawer 应管理初始焦点、焦点陷阱和关闭后焦点归还。审计事件记录服务端认证主体、动作、资源、前后状态摘要和结果；稳定性则用错误率、关键操作成功率、延迟和前端版本关联。

#### 工程场景
组件库层检查 label、可见焦点、状态不只靠颜色、表格表头和弹层焦点；页面层做键盘冒烟与读屏抽检。危险操作提供明确确认、幂等键和失败恢复。发布采用灰度与功能开关，前端错误带 release、route、traceId，告警围绕用户动作失败而不是日志数量。

#### 反例 / 踩坑
把 `aria-label` 当万能补丁、紧凑模式把点击区压得过小、弹层关闭后焦点丢到 body，都会让键盘用户受阻。仅前端埋「点击成功」不能证明服务端操作成功，也不能作为可信审计。

#### 资深回答模板
「60–90 秒主回答：我把无障碍写入基础组件契约，把审计放在服务端可信链路，把稳定性落到关键动作 SLI。上线前检查语义、焦点、键盘和失败恢复，关键操作具备幂等与审计；上线后按 release、route、trace 观测成功率和延迟，超过停止线就暂停灰度或用开关降级。」

#### 追问链
1. 虚拟表格、拖拽排序和自定义下拉如何支持键盘？
2. 前端异常与后端审计事件如何通过 traceId 串联？
3. 哪些指标适合作为后台系统的发布停止线？
:::
