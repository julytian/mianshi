# 微前端面试题库

> **怎么用：** 先盖住答案，按 **适用边界 → 运行机制 → 工程治理 → 故障降级** 口述 2～3 分钟，再展开答案补洞。本篇聚焦 qiankun、Garfish、Module Federation、Wujie 的机制与运行时治理；组织与交付的一般性决策请结合 [工程化](/interview/questions/03-engineering) 复习。

> **版本基线：** 本文按 qiankun 2.x、Garfish 1.x、Wujie 1.x 与 Module Federation 2.0 官方文档核查，核查日期截至 2026-08。框架默认值和实验能力可能随小版本变化，面试回答与生产配置均应以项目锁定版本的官方文档、类型声明和实测结果为准。

## 一、基础与边界

### Q1. 微前端解决的核心问题是什么？它与组件库、Monorepo 有什么区别？

**考察点：** 问题定义、运行时边界、替代方案

::: details 参考答案

微前端首先解决的是**多个业务域或团队在同一产品壳内独立演进、独立交付**的问题，不是新的组件化语法。它把页面级业务能力做成可独立开发、构建、部署和运行的应用，再由主应用完成导航、装配和公共治理。

- 组件库共享的是源码或构建产物，发布后仍由消费方一起构建、一起上线。
- Monorepo 统一代码管理和工具链，但不天然带来独立部署；一个仓库也可以产出多个微应用。
- 微前端关注运行时装配与故障边界，代价是额外的加载链路、隔离、通信、版本和可观测性治理。

所以我不会把「项目很大」直接等同于「要上微前端」，先看是否存在真实的独立交付和渐进替换诉求。

**追问链：**
1. 多仓库是否等于微前端？
2. 后端微服务和微前端能否一一对应？
3. 只有一个团队时有哪些更低成本的替代方案？

::: details 追问参考答案

**1. 多仓库是否等于微前端？**

不等于。多仓库只描述源码和权限的管理边界，多个仓库仍可能由同一流水线合并构建、整站发布；微前端强调页面级应用可独立构建、部署、装载和回滚，并具备稳定运行时契约。判断时应检查入口是否独立、发布是否互不阻塞、故障能否隔离，而不是统计 Git 仓库数量。

**2. 后端微服务和微前端能否一一对应？**

通常不应机械对应。后端按数据一致性、领域模型和伸缩边界拆分，前端按用户任务、页面连贯性和团队交付边界拆分；一个微应用可编排多个服务，一个服务也可供多个应用使用。若照服务数量切页面，会增加跳转和通信。应以领域契约或 BFF 屏蔽后端拓扑变化。

**3. 只有一个团队时有哪些更低成本的替代方案？**

优先选择模块化单体、路由懒加载、按功能拆包、Monorepo 包边界和组件库；构建慢可用增量构建与缓存，发布冲突可用特性开关和分支治理。只有遗留系统必须渐进替换或确有独立发布需求时再引入运行时装配，并先用一个低耦合页面验证其架构税是否值得。

:::

### D1. 哪些场景适合微前端，哪些场景坚决不适合？

::: details 参考答案

#### 基础结论

适合信号是：多个稳定团队、业务域边界清晰、需要独立发布，或遗留系统必须渐进替换。不适合信号是：单团队小系统、模块高度耦合、发布节奏一致、基础设施无人维护。微前端解决组织扩展问题，同时会引入架构税。

#### 原理深挖

收益来自把「编译时耦合」或「整站发布耦合」后移到运行时契约；成本也因此转移到入口加载、版本兼容、路由、样式、权限和故障恢复。若跨应用调用比应用内部调用还频繁，说明边界切错了，运行时解耦只是在掩盖领域耦合。

#### 工程场景

我会先记录 4～8 周数据：团队数量、发布冲突、回滚粒度、跨域需求、构建耗时和故障归属。若旧 Vue 2 财务域与新 Vue 3 运营域可独立验收，且双方发布互不等待，微前端有价值；若只是首页包大，路由懒加载和拆包通常更直接。

#### 反例 / 踩坑

为了技术栈自由而拆分，最后每个子应用各带一套 Vue、组件库和埋点，首屏更慢、体验不一致；又没有平台团队负责契约和故障，组织问题会被放大。

#### 资深回答模板

「判断：先确认是否有独立交付或渐进迁移的刚需。证据：用发布冲突、边界耦合和平台能力数据验证。兜底：若只是体积或代码组织问题，退回模块化、路由懒加载或 Monorepo。」

:::

**追问链：** 独立部署的证据是什么？→ 架构税如何量化？→ 试点失败如何退回单体？

::: details 追问参考答案

**1. 独立部署的证据是什么？**

证据不是仓库或流水线数量，而是某应用能独立完成构建、验收、灰度和回滚，其他应用无需重发且契约仍兼容。可从连续发布记录抽样：版本号、制品、清单指针和故障域是否独立，团队是否无需协调窗口。若每次上线仍要整站联测或同步发版，就没有实现独立部署。

**2. 架构税如何量化？**

同时记录收益和新增成本：发布等待与回滚时长是否下降；首屏请求、LCP、重复依赖、内存是否上升；接入改造、契约测试、平台值班和跨应用故障工时是多少。用试点前后 4～8 周同口径数据比较，并设性能和运维预算；只统计团队满意度或 Demo 速度无法支持决策。

**3. 试点失败如何退回单体？**

试点开始就保留旧路由和独立运行入口，以版本化接口而非共享 Store 连接主壳；流量清单可把用户稳定切回旧页面，数据库和 API 在观察窗口保持双向兼容。失败时先停灰、切回上一稳定入口，再移除装载层。若已把领域拆散且无旧产物，所谓回退通常只是再次重写。

:::

### D2. 如何划分微应用边界，避免拆成「分布式巨石」？

::: details 参考答案

#### 基础结论

按稳定业务域和团队责任边界拆，通常以页面簇为最小粒度，不按按钮、弹窗或技术层拆。边界质量可用「独立验收、独立发布、低频通信、故障可隔离」验证。

#### 原理深挖

运行时装配无法消除业务一致性。订单列表与订单详情若共享大量临时状态、事务和路由上下文，拆开会把函数调用变成事件协议。好的边界内部高内聚，跨边界只交换稳定的身份、命令和结果，不共享可变对象。

#### 工程场景

管理后台可按会员、商品、订单、财务拆。主应用只掌握导航、身份、租户、特性开关和错误兜底；领域应用拥有自己的页面、接口适配和领域状态。公共搜索框若只是 UI 用组件库，若包含完整业务流程才考虑独立应用。

#### 反例 / 踩坑

按菜单项机械拆分会产生几十个微应用；按 Vue/React 技术栈拆会让同一业务跨应用往返；把全局 Store 暴露给所有应用则重新形成共享数据库。

#### 资深回答模板

「判断：按业务能力而不是目录切边界。证据：边界必须能独立验收、回滚，且跨应用通信低频。兜底：若一个流程需要连续同步多个应用，就合并边界或上收编排。」

:::

**追问链：** 页面级和组件级如何选？→ 公共能力归谁？→ 如何用数据发现边界错误？

::: details 追问参考答案

**1. 页面级和组件级如何选？**

默认以可独立验收的页面簇为微应用；组件级只有在能力具备独立团队、发布节奏和稳定输入输出时才成立。普通按钮、弹窗应走组件库或包依赖，避免为一次渲染引入远程网络和生命周期。用用户任务是否完整、通信频率、故障降级方式判断，跨边界共享框架对象说明粒度过细。

**2. 公共能力归谁？**

身份、租户、导航、主题、埋点和装载故障由平台 Owner 管理，并以最小、版本化、可观测契约提供；领域规则、页面状态和 API 适配归业务 Owner。通用 UI 放设计系统，但不把业务流程伪装成公共组件。每项能力必须写明数据权威源、兼容窗口、SLO 和故障时的降级责任。

**3. 如何用数据发现边界错误？**

观察跨应用同步调用、事件数量与变更频率、联动发布比例、跨团队需求等待、失败关联和用户跨应用往返。若一个流程频繁传递大对象、必须同版本上线，或故障总是同时发生，边界可能切错。结合 trace 和发布记录复盘，优先合并高耦合边界，而不是继续增加总线协议。

:::

### Q2. 微前端平台需要建立哪些最小治理规则？

**考察点：** 契约治理、平台边界、质量门禁

::: details 参考答案

最小规则不是统一所有技术栈，而是统一运行契约：

1. 应用清单：应用 ID、负责人、入口、路由前缀、版本、健康状态和回滚版本。
2. 生命周期：挂载、卸载、超时、重试和幂等约定。
3. 公共契约：身份、租户、权限、主题、语言、埋点与事件 Schema。
4. 性能预算：入口大小、并发请求、缓存策略、预加载上限和浏览器基线。
5. 安全基线：入口域名白名单、CSP/CORS、通信来源校验和最小凭证暴露。
6. 观测归属：日志必须带 host、app、release、traceId，告警能路由到责任团队。
7. 发布门禁：契约测试、独立运行测试、主应用集成冒烟和一键回滚。

平台只治理公共面，不侵入领域实现，否则会把独立团队重新锁死。

**追问链：**
1. 应用清单由配置中心还是代码仓库维护？
2. 契约如何兼容新旧两版？
3. 平台团队和业务团队如何划分故障责任？

::: details 追问参考答案

**1. 应用清单由配置中心还是代码仓库维护？**

源定义适合进代码仓库审查，环境入口、灰度桶和紧急回退指针适合由受控配置服务发布；二者通过流水线生成签名、不可变版本清单，不能让浏览器直接消费任意后台录入 URL。配置服务需审计、权限、缓存和上一稳定版本，仓库则保留评审与可重建证据。

**2. 契约如何兼容新旧两版？**

契约使用显式版本和能力协商，新增字段保持可选，消费者忽略未知字段，破坏变更并行提供 v1/v2。CI 用当前与历史主壳、子应用做契约测试，清单声明兼容范围；灰度期间监控协议错误，确认旧消费者退出后再删除 v1。不要用共享 TypeScript 类型替代运行时校验。

**3. 平台团队和业务团队如何划分故障责任？**

按失败阶段和控制权划分：清单、装载器、公共契约及壳降级归平台，应用渲染、领域接口和资源预算归业务；CDN、身份等共享依赖设联合 Runbook。日志必须带 host、app、release、stage、traceId，告警直达首责 Owner；争议先止损，事后按证据调整 SLO 和边界。

## 二、qiankun

### Q3. qiankun 如何注册、激活和执行子应用生命周期？

**考察点：** `registerMicroApps`、路由激活、生命周期

::: details 参考答案

主应用通过 `registerMicroApps` 声明唯一 `name`、`entry`、`container`、`activeRule` 和可选 `props`，调用 `start` 后监听 URL。路由命中 `activeRule` 时加载 HTML Entry，依次执行子应用导出的 `bootstrap`、`mount`；离开时执行 `unmount`。`bootstrap` 通常只执行一次，`mount` / `unmount` 会随进入和离开重复执行。

`loadMicroApp` 适合非路由驱动或嵌入式场景，返回实例供主应用手动 `mount`、`unmount`、`update`。生命周期要幂等，挂载节点必须从 `props.container` 内查询，不能抢主应用的全局 `#app`。

**追问链：**
1. `activeRule` 前缀冲突怎么处理？
2. `bootstrap` 中适合放什么，不能放什么？
3. 手动加载为何默认更容易出现多实例问题？

::: details 追问参考答案

**1. `activeRule` 前缀冲突怎么处理？**

路由前缀必须唯一且按路径段匹配，不能用会让 `/app` 同时命中 `/application` 的朴素 `startsWith`。主壳集中维护路由注册表，CI 检测交集、保留字和优先级；复杂规则用函数同时校验 pathname、租户等条件。命中冲突应拒绝发布或只激活明确的单一应用。

**2. `bootstrap` 中适合放什么，不能放什么？**

`bootstrap` 只执行一次，适合初始化应用级、跨多次挂载复用且可长期存活的轻量元数据；依赖容器的渲染、路由监听、定时器和用户会话订阅应放 `mount`，并在 `unmount` 对称清理。把租户或 Token 缓存在 `bootstrap` 会造成切换后陈旧，也不能假设它在每次进入时重跑。

**3. 手动加载为何默认更容易出现多实例问题？**

`loadMicroApp` 不受统一 `activeRule` 排他控制，调用方若重复点击、并发请求或路由回放，可能为同一 `name` 和容器创建多个实例。应以业务实例键做注册表与并发去重，等待前一状态稳定后再 mount/unmount，并为容器所有权设断言。手动模式的销毁、超时和错误恢复也须由调用方负责。

:::

**踩坑：** 卸载时只卸 Vue 实例，不清理定时器、订阅和动态 DOM，页面看似消失但副作用仍在。

:::

### D3. qiankun 的 JS 沙箱能隔离什么，为什么仍会逃逸？

::: details 参考答案

#### 基础结论

qiankun 默认使用基于 `Proxy` 的沙箱隔离子应用对全局 `window` 的读写，并在切换时恢复副作用；它不是浏览器安全边界，不能替代 iframe、CSP 或权限控制。

#### 原理深挖

子应用代码被放到代理上下文执行，写入落在代理对象，读取可回退到真实 `window`。沙箱还能收集部分全局事件、定时器和样式副作用。但原生对象引用、未被劫持的 DOM 路径、第三方脚本、`window.top`、Cookie、网络请求与持久化存储并不会天然形成强隔离。

#### 工程场景

接入前扫描 `window.xxx`、原型修改、全局事件和动态脚本；运行时为每个应用建立资源账本。卸载后检查事件监听数、定时器、DOM、网络轮询和堆快照。高风险不可信应用放到独立域 iframe，而不是依赖 Proxy。

#### 反例 / 踩坑

认为开启 `sandbox: true` 就安全，引入会修改 `HTMLElement.prototype` 的旧插件；或缓存真实 `window` 引用后继续写全局，都会绕过预期隔离。

#### 资深回答模板

「判断：Proxy 沙箱只解决可信应用间的冲突，不是安全容器。证据：用资源账本和卸载测试验证隔离范围。兜底：不可信代码使用独立域 iframe，并配合 CSP 和消息白名单。」

:::

**追问链：** Proxy 与快照沙箱差异？→ `document` 如何造成逃逸？→ 如何证明卸载干净？

::: details 追问参考答案

**1. Proxy 与快照沙箱差异？**

Proxy 沙箱让写入落到代理 window，可为多实例维持各自状态并在激活时管理副作用；快照沙箱在切换前后比较真实全局并恢复差异，兼容无 Proxy 环境，但对并行实例和不可枚举、原型级修改更弱。两者都是冲突隔离，不拦 Cookie、网络或真实 DOM，不能当安全边界。

**2. `document` 如何造成逃逸？**

`document` 指向共享主文档，子应用可通过 `body`、全局选择器、Portal 或缓存的原生节点越过容器，修改主壳 DOM、样式和事件；第三方 SDK 还可能持有未代理引用。应从 `props.container` 查询，限制挂载目标并盘点动态节点。真正不可信代码需独立域 iframe，而非继续补 Proxy 劫持。

**3. 如何证明卸载干净？**

建立资源账本并自动重复 mount/unmount 至少 20 次，比较事件监听、定时器、Observer、WebSocket、轮询、动态节点、对象 URL 和 Detached DOM 数量；再用堆快照查看实例保留路径。指标应回到稳定基线且应用不再发请求或响应事件。单次页面消失、GC 后内存下降都不足以证明无泄漏。

:::

### Q4. qiankun 的样式隔离有哪些模式，如何选择？

**考察点：** 默认隔离、Shadow DOM、运行时 scoped CSS

::: details 参考答案

默认沙箱能处理单实例子应用切换时的样式副作用，但不能保证主应用与子应用、或多实例之间绝对隔离。`strictStyleIsolation` 会用 Shadow DOM 包裹容器，隔离最强，但弹窗 Portal、主题变量、字体、事件委托和部分组件库需要适配。`experimentalStyleIsolation` 会为选择器增加作用域前缀，但官方明确标为实验能力，且 `@keyframes`、`@font-face`、`@import`、`@page` 等不会被改写。

生产上我优先使用 CSS Namespace、设计令牌和 lint 约束；冲突风险高且能承担适配成本时才用 Shadow DOM。

**追问链：**
1. 弹窗挂到 `body` 为什么会失去作用域？
2. CSS 变量能否穿透 Shadow DOM？
3. 如何治理组件库多版本样式？

::: details 追问参考答案

**1. 弹窗挂到 `body` 为什么会失去作用域？**

运行时 scoped CSS 通常把选择器限定在子应用容器属性下，弹窗 Portal 若直接插入主文档 `body`，就不再是该容器后代，选择器无法命中；Shadow DOM 内样式也不会自动作用于外部节点。应配置组件库的弹层容器到应用根节点，并处理定位和层级；确需挂 body 时使用受控全局样式。

**2. CSS 变量能否穿透 Shadow DOM？**

继承型自定义属性可从宿主元素传入 Shadow Tree，所以适合下发主题 Token；但 Shadow 内定义的变量默认不会反向影响外部，且具体属性仍受继承关系和 fallback 影响。应在 host 元素声明版本化语义变量，不依赖内部选择器；同时验证弹层、暗色模式和动态切换，避免把穿透误解为所有 CSS 都共享。

**3. 如何治理组件库多版本样式？**

先按主版本划兼容组，统一设计 Token、CSS 前缀和弹层容器；能共享且运行时身份确有要求时才复用依赖，异构版本各自打包并计入体积预算。对全局 Reset、字体和动画名做 lint 与快照测试，冲突高的应用用 Shadow DOM。升级通过灰度和视觉回归，不强迫所有团队同步切版。

### D4. qiankun 的路由和预加载如何设计，才能不拖慢首屏？

::: details 参考答案

#### 基础结论

主应用只分配一级路由前缀，子应用自治内部路由；预加载按用户下一跳概率和网络条件分级，不能把 `prefetch: 'all'` 当默认性能优化。

#### 原理深挖

`activeRule` 决定应用激活，子应用必须配置正确的 base。qiankun 官方 API 中，`prefetch: true` 会在首个微应用挂载后预取其他应用，`'all'` 会在 `start` 后预取全部，也可传应用名数组或函数。预取只减少后续网络等待，不减少下载量和解析缓存压力。

#### 工程场景

首屏应用不参与竞争；登录后根据权限、菜单曝光和历史转移概率预取 1～2 个高概率应用。弱网、低端设备、流量模式关闭预取；静态资源使用内容哈希和长缓存，HTML Entry 短缓存。

#### 反例 / 踩坑

所有子应用同时预加载，占满连接和主线程，首屏 LCP 反而恶化；主子应用同时控制同一段 history，出现重复导航和返回栈错乱。

#### 资深回答模板

「判断：主应用管应用级前缀，子应用管域内路径，预取不得竞争首屏。证据：用命中率、额外流量和 LCP 对照实验验证。兜底：弱网或低命中场景关闭预取。」

:::

**追问链：** hash 与 history 如何同步？→ 预加载命中率怎么统计？→ 权限菜单变化后如何撤销无效预取？

::: details 追问参考答案

**1. hash 与 history 如何同步？**

先规定单一 URL 真源：主壳只管理应用级前缀，子应用管理前缀内路径，并通过 base 映射刷新和回退。hash 子应用可把内部片段编码进主路由参数，history 子应用则使用独占路径段；同步时标记来源避免循环 push。必须测试深链、刷新、前进后退、重定向和独立运行。

**2. 预加载命中率怎么统计？**

以“预取完成后在有效窗口内实际装载且复用该资源”为命中，记录 app、release、触发策略、字节数、网络类型、完成与消费时间；同时统计浪费流量、内存、主线程解析和对 LCP/INP 的影响。按权限与下一跳分组做对照实验。高命中但拖慢首屏仍是失败策略。

**3. 权限菜单变化后如何撤销无效预取？**

qiankun 预取一旦已发出，公开配置没有通用的底层请求取消承诺；权限变化后应停止调度尚未开始的任务、用代次丢弃过期结果，并避免挂载已失权应用。已进入 HTTP 或内存缓存的资源按预算自然淘汰，不能宣称撤回网络。敏感性必须由服务端授权保证，预取内容本身不得携带用户秘密。

:::

### Q5. qiankun 如何通信？如何排查卸载后的内存泄漏？

**考察点：** `props`、`initGlobalState`、资源清理

::: details 参考答案

一次性能力和上下文通过 `props` 注入；少量公共状态可由主应用 `initGlobalState`，通过 `onGlobalStateChange`、`setGlobalState`、`offGlobalStateChange` 管理。复杂业务不要塞进全局状态，应使用版本化事件或后端事实源。

泄漏排查按资源账本做：Vue `app.unmount()`、路由监听、Store 订阅、EventBus、`window/document` 事件、定时器、Observer、WebSocket、AbortController、动态 DOM 和对象 URL。连续挂载/卸载 20 次，对比监听器、网络、Detached DOM 和 Heap Snapshot 的保留路径。

**追问链：**
1. 为什么不直接共享 Pinia 实例？
2. `offGlobalStateChange` 应在何时调用？
3. 保活与真正卸载的验收标准有什么不同？

::: details 追问参考答案

**1. 为什么不直接共享 Pinia 实例？**

共享可变 Pinia 会把应用绑定到同一 Vue/Pinia 运行时、Store 结构和升级节奏，任何一方都可改状态，难以追踪所有权、版本与回放顺序；独立运行也会失去依赖。只共享身份等只读快照或版本化命令/事件，领域状态归自己的应用。确需共享时封装窄 API，不暴露 Store 本体。

**2. `offGlobalStateChange` 应在何时调用？**

qiankun 会在微应用 `unmount` 时默认调用 `offGlobalStateChange`，常规场景可依赖自动清理；需要提前停止监听时也可显式调用，但该 API 不接收 callback，而是幂等移除当前应用的全局状态监听，不能按函数逐个解绑。匿名函数引用导致无法解绑只适用于普通 EventBus 等按 callback 注销的接口。重复进入后仍应验证监听数不增长。

**3. 保活与真正卸载的验收标准有什么不同？**

保活允许 DOM、状态和部分资源继续存在，验收重点是隐藏后不抢焦点、不渲染、不发无意义轮询，后台 CPU、内存和订阅受预算控制，恢复状态正确。真正卸载则要求实例、监听、定时器、网络和动态 DOM 回到基线。两者需在清单标明语义，不能拿“切走后仍占内存”直接判定保活泄漏。

:::

**踩坑：** 每次 `mount` 都注册匿名回调，`unmount` 时因拿不到同一函数引用而无法解绑。

:::

## 三、Garfish

### Q6. Garfish 的加载与子应用管理模型是什么？

**考察点：** 路由驱动、`loadApp`、应用实例

::: details 参考答案

Garfish 可通过 `run` 注册应用并由 Router Plugin 根据 `activeWhen` 自动加载，也可用 `loadApp` 手动创建应用实例。实例提供 `mount`、`show`、`unmount`、`hide` 等能力，并通过 `activeApps` 管理活动应用。

官方生命周期可概括为加载、渲染、销毁。开启缓存后，路由再次命中通常通过 `show` 恢复；`show` 会再次调用 provider 的 `render`，但不会创建新的执行上下文，因此业务仍要控制重复副作用。离开时，`hide` 会执行 `provider.destroy`、移除渲染容器并将应用从活动列表移除，但保留执行上下文，后续可用 `show` 恢复；`unmount` 在执行 `provider.destroy` 和移除容器之外，还会销毁执行上下文、清理沙箱收集的运行时副作用，并把 `mounted`、`display` 置为 `false`。手动模式不受 `activeWhen` 控制，销毁责任完全落在调用方。

**追问链：**
1. `hide` 与 `unmount` 如何在恢复速度和资源回收之间取舍？
2. `mount` 与 `show` 的语义差异是什么？
3. provider 缺失时在哪个阶段失败？

::: details 追问参考答案

**1. `hide` 与 `unmount` 如何在恢复速度和资源回收之间取舍？**

`hide` 会调用 provider 的 `destroy`、移除容器并隐藏实例，但保留执行上下文，适合高频返回且上下文重建昂贵的页面；`unmount` 还销毁执行上下文并清理沙箱收集的副作用，适合低频或高内存应用。用二次恢复耗时、后台 CPU、堆大小和泄漏回归定预算，不能仅凭接口名推断已完全回收。

**2. `mount` 与 `show` 的语义差异是什么？**

`mount` 面向已加载但尚未挂载的应用，建立执行与渲染流程；`show` 面向曾隐藏且保留执行上下文的实例，重新提供容器并再次调用 provider 的 `render`。因此 `show` 不是简单改 CSS，也可能重复注册业务副作用。render/destroy 必须幂等，并按实例状态机拒绝并发或非法调用。

**3. provider 缺失时在哪个阶段失败？**

入口资源可能已加载和执行，但 Garfish 在渲染阶段需要取得 provider 及其 render/destroy 契约；未正确导出时通常无法完成 mount，而不是把它归为纯网络失败。监控应区分 load、provider 获取、render 与 destroy，并保留原始异常。CI 同时做独立运行和主壳挂载冒烟，提前发现 UMD/导出配置错误。

:::

### D5. Garfish 沙箱的机制、能力与边界是什么？

::: details 参考答案

#### 基础结论

Garfish 以 VM 沙箱为主要能力，借助 `new Function`、`with` 和 `Proxy` 构造执行上下文，并收集 DOM、样式、事件和定时器等副作用；不支持 Proxy 时可降级到快照沙箱。它仍是兼容性隔离，不是安全隔离。

#### 原理深挖

代理 `window` 把变量写入局部容器；代理 `document` 及 DOM 创建/插入路径，为节点标记来源并在销毁时回收。动态脚本需要被拦截后拉取并放回沙箱执行，因此会遇到原生 `<script>` 没有、而 `fetch/XHR` 存在的 CORS 约束。快照沙箱通过激活前后比较真实全局，难以支持可靠多实例。

#### 工程场景

接入旧应用时先盘点动态 import、JSONP、原型修改、DOM 向上查找和 Storage。多实例下配合 CSS Namespace 或 Shadow DOM；对计时器、事件、节点数量做卸载回归。

#### 反例 / 踩坑

把 `localStorage` 视为天然隔离，或让第三方 SDK 持有原始 `document`；动态脚本因跨域被拦截后又直接关闭沙箱，最终把兼容问题变成全局污染。

#### 资深回答模板

「判断：Garfish 沙箱提高兼容性，但仍有动态脚本、原生对象和存储逃逸。证据：用接入扫描与重复卸载测试确认副作用。兜底：不兼容资源走白名单或独立 iframe，不全局关闭沙箱。」

:::

**追问链：** VM 与快照沙箱如何降级？→ 动态 import 为什么需要 CORS？→ 多实例 DOM 如何归属？

::: details 追问参考答案

**1. VM 与快照沙箱如何降级？**

默认优先用 Proxy 支撑的 VM 执行上下文；目标浏览器不支持 Proxy 时可评估快照沙箱，但它通过真实全局前后差异恢复，难以可靠支持并行多实例，也覆盖不了原型和外部引用。降级前应按浏览器矩阵实测，不兼容则限制为单实例或独立 iframe，不能悄悄关闭沙箱后继续承诺隔离。

**2. 动态 import 为什么需要 CORS？**

沙箱为了让动态资源继续在受控上下文执行，往往需要用 fetch/XHR 获取脚本文本再编译，而这些请求受 CORS；传统 `<script src>` 能跨域加载，并不代表 fetch 同一地址也获许可。CDN 应返回明确 `Access-Control-Allow-Origin`，资源 URL 使用绝对路径。不要以关闭沙箱绕过 CORS，否则副作用会逃逸。

**3. 多实例 DOM 如何归属？**

每个实例必须有唯一容器和实例 ID，代理 document 创建/插入节点时记录来源，查询默认限制在该容器，卸载按资源账本回收。Portal、全局弹层和第三方 SDK 需显式指定实例容器或登记例外；相同应用的两个实例不得共享固定 `#app`。自动化测试应并行操作两实例并验证事件、样式和销毁互不影响。

:::

### Q7. Garfish 如何预加载，为什么预加载不一定越多越好？

**考察点：** `preloadApp`、智能预加载、资源竞争

::: details 参考答案

`Garfish.preloadApp(appName)` 会预取已注册应用的入口及 HTML 中的 script、link 子资源，并放入独立内存缓存，真正加载时复用。`run` 默认具备应用预加载能力，可通过 `disablePreloadApp` 关闭；官方文档说明会参考应用打开次数计算权重，并在弱网和移动端不启用。

工程上仍要给预加载设预算：首屏关键请求完成后再启动，按权限和下一跳概率选择，限制并发与内存，并记录命中率。若入口使用短缓存，预加载到挂载间还要防版本漂移。

**追问链：**
1. 内存缓存与 HTTP 缓存有什么区别？
2. 如何避免预加载旧版本、挂载新版本？
3. 怎样判断智能预加载策略真的有效？

::: details 追问参考答案

**1. 内存缓存与 HTTP 缓存有什么区别？**

Garfish 预加载说明中的独立内存缓存由当前页面运行时持有，命中时直接复用已取资源，刷新、进程回收或缓存淘汰后消失；HTTP 缓存由浏览器按响应头管理，可跨导航复用并可能发起协商请求。两层的键、容量和失效语义不同，观测要区分内存命中、磁盘命中与网络 304。

**2. 如何避免预加载旧版本、挂载新版本？**

`preloadApp(appName)` 的公开返回类型是 `void`，没有通用的取消或清空预加载内存缓存 API。应先把会话固定到不可变 release，让预加载与挂载使用版本化入口及应用 key；切版时还要处理 `loadApp` 的实例缓存，避免旧上下文复用新配置。无法证明缓存一致时整页刷新，不能宣称已撤回在途请求或清掉旧资源。

**3. 怎样判断智能预加载策略真的有效？**

按策略组记录预载触发、完成、实际消费、节省等待、额外字节、内存和主线程耗时，并与未预载对照组比较下一页可交互时间及首屏 LCP/INP。还应按弱网、移动端、权限和应用分层。打开次数权重只是启发式；若命中低、流量高或首屏退化，就降低并发、延后触发或关闭。

### D6. Garfish 与 qiankun 应如何做技术选型，而不是罗列功能？

::: details 参考答案

#### 基础结论

两者都提供 HTML Entry、路由装配、沙箱和生命周期。选型应以现有生态、旧应用兼容性、多实例需求、运维经验和 PoC 数据为准，不能仅凭「谁功能更多」。

#### 原理深挖

qiankun 基于 single-spa 的应用生命周期，社区认知和接入案例广；Garfish 把 loader、VM 沙箱、Router、缓存和应用实例管理组合得更完整，手动实例控制更显式。机制不同会影响动态脚本、DOM 副作用、缓存恢复和调试路径。

#### 工程场景

选 2 个真实应用做同样 PoC：一个 Vue 3 新应用，一个带 JSONP、全局插件和弹窗的旧应用。比较接入改动、首次/二次加载、卸载残留、多实例、异常定位、社区风险和维护人力，再做决策记录。

#### 反例 / 踩坑

只跑官方 Demo 就宣布选型；或因为团队熟悉 qiankun 就忽略多实例硬需求。框架切换也有迁移成本，不应把可通过规范解决的问题都归因于框架。

#### 资深回答模板

「判断：先按多实例、旧应用兼容和运维能力列硬约束。证据：用真实旧应用对照 PoC，比较接入、隔离、性能和可运维性。兜底：保留框架替换与独立运行路径。」

:::

**追问链：** PoC 必测哪 5 项？→ 多实例为何改变选择？→ 框架停止维护如何退出？

::: details 追问参考答案

**1. PoC 必测哪 5 项？**

至少测五类：真实旧应用接入改动；首次与二次加载瀑布；样式、全局变量和动态脚本隔离；并行多实例及重复卸载残留；入口故障、灰度回滚和定位链路。用同一 Vue 2 旧应用、Vue 3 新应用与地图/弹窗等压力样例，固定设备和网络采集数据，不能只比较官方 Demo。

**2. 多实例为何改变选择？**

多实例要求同时存在独立 window 状态、DOM 容器、路由、样式和资源账本；快照式全局恢复或固定容器 ID 很难提供这种并行语义。选型要验证同一应用双开、不同应用并行、Portal、事件和销毁，而非只看文档写“支持”。若业务无多实例需求，不必为该能力承担额外兼容成本。

**3. 框架停止维护如何退出？**

保持子应用独立运行、标准 mount/unmount 契约和框架适配层，不让领域代码直接依赖全局实例；入口清单、通信 Schema 与监控字段采用自有协议。定期演练单应用切独立站或替换装载器，并保留旧版本资产。停止维护时先冻结升级、评估安全风险，再逐应用迁移，避免一次性重写。

:::

## 四、Module Federation

### Q8. 解释 host、remote、`exposes`、`remotes` 和 `shared`。

**考察点：** 联邦角色、构建配置、运行时关系

::: details 参考答案

host 是消费远程模块的一方，remote 是提供模块的一方；同一个应用可以同时扮演两种角色。remote 用 `exposes` 把内部模块映射为稳定公开键，host 用 `remotes` 为生产者入口配置消费侧别名，再通过 `<remoteAlias>/<exposeKey>` 消费。`remoteAlias` 是 host 本地引用名，可以与生产者配置的 `name` 不同；入口字符串内部仍可包含生产者 `name`。`shared` 把依赖注册到 Share Scope，由运行时决定复用哪个提供者，减少重复包或满足单例要求。

这是一种**模块级运行时组合**，本身不提供完整的路由、CSS/JS 沙箱和安全隔离。公开模块应有小而稳定的契约，不能把 remote 的内部目录结构当 API。

**追问链：**
1. 应用为何能同时是 host 和 remote？
2. `exposes` 粒度过细有什么问题？
3. Module Federation 能否替代微前端框架？

::: details 追问参考答案

**1. 应用为何能同时是 host 和 remote？**

host/remote 是一次依赖关系中的角色，不是应用固定类型：同一构建可消费别人的公开模块，同时把自己的模块通过 `exposes` 提供给其他消费者。应避免形成隐式循环依赖，并为每条边记录版本、Owner 和故障降级。拓扑复杂时用 Manifest/Snapshot 和依赖图审计，而不是假定所有 remote 都是叶子。

**2. `exposes` 粒度过细有什么问题？**

每个内部组件都暴露会扩大公共 API，消费者绑定目录、样式和框架细节，remote 重构变成跨团队破坏变更；还可能产生大量远程 chunk 请求和多阶段失败。应围绕稳定业务能力暴露少量入口，内部组件继续由本应用组合。CI 检查公开键、类型和语义版本，并为删除提供兼容窗口。

**3. Module Federation 能否替代微前端框架？**

不能一概替代。MF 解决模块容器、运行时加载和 shared 协商，不自带应用级路由激活、DOM/CSS/JS 隔离、完整 mount/unmount 或保活治理。若团队只需模块共享，它可单独使用；完整页面装配则需自建壳契约或与微前端框架组合，并处理生命周期、错误边界与安全。

:::

### D7. MF 2.0 与 Webpack 5 内置 Module Federation 有什么区别？

::: details 参考答案

#### 基础结论

Webpack 5 内置版本提供模块导出、远程加载和依赖共享等核心能力。官方 MF 2.0 在此基础上增加动态类型提示、Manifest、独立 Federation Runtime、Runtime Plugin System 和配套调试能力，更适合大规模运行时治理。不能把 MF 2.0 的能力倒推为所有 Webpack 5 项目都自带。

#### 原理深挖

内置插件主要在构建产物和容器协议层工作；MF 2.0 把加载、注册 remote、预加载、错误恢复和钩子开放为运行时能力，并用 `mf-manifest.json` 提供入口、资产、shared 和类型元数据。它也扩展到 Rspack、Vite 等集成，但具体支持以对应集成文档为准。

#### 工程场景

若只是固定 remote 的少量模块共享，Webpack 5 内置能力可能足够；若要动态注册、类型分发、Manifest 驱动预取、统一重试和观测，我会评估 `@module-federation/enhanced` 体系，并锁定版本做兼容测试。

#### 反例 / 踩坑

配置了 Webpack `ModuleFederationPlugin`，却按 MF 2.0 文档期待自动下载 `@mf-types` 或使用 Runtime Plugin；又或者升级增强版不做产物协议和 shared 回归。

#### 资深回答模板

「判断：先区分核心联邦协议与 MF 2.0 增强层。证据：根据 Manifest、运行时插件和动态类型等真实需求选择。兜底：锁定版本做 PoC，不混用两套文档和能力假设。」

:::

**追问链：** 哪些需求必须增强运行时？→ 混合新旧 remote 是否可行？→ 升级如何验证协议兼容？

::: details 追问参考答案

**1. 哪些需求必须增强运行时？**

需要运行时动态 `registerRemotes`、独立实例、Runtime Plugin 钩子、Manifest/Snapshot 驱动预加载、远程类型提示或统一加载观测时，才有采用 `@module-federation/enhanced` 体系的明确理由。固定少量 remote、只做模块导入与 shared 的项目，Webpack 5 内置能力可能足够。具体 API 仍以锁定集成版本为准。

**2. 混合新旧 remote 是否可行？**

可能可行，但不能默认兼容。增强运行时可消费符合容器协议的 remoteEntry，Manifest 能力、类型、插件钩子和预加载元数据则不是旧 remote 自动具备。应建立新 host×旧 remote、旧 host×新 remote 的版本矩阵，逐项测容器初始化、expose、shared 和 chunk。失败时保留旧入口而非现场改协议。

**3. 升级如何验证协议兼容？**

锁定 host、remote、bundler 和 runtime 版本，在 CI 保存一组历史制品，双向测试 remoteEntry/Manifest 解析、容器 `init/get`、公开键、shared 选择、动态类型和缓存旧 chunk。灰度记录运行时版本与 Snapshot，注入 404、超时和 shared 冲突。只有矩阵通过并可切回旧清单，才扩大升级范围。

:::

### D8. `shared`、`singleton` 和版本协商如何工作？Vue 为什么要谨慎共享？

::: details 参考答案

#### 基础结论

`shared` 不是简单的 external。各参与方把依赖及版本注册到同一 Share Scope，运行时按策略和版本约束复用。`singleton: true` 要求作用域内只使用一个版本。只有在跨边界共享 Vue 组件、响应式对象、插件或依赖注入上下文，确实要求运行时身份一致时，Vue 的单例约束才是关键；若应用只通过 DOM、序列化数据或挂载协议交互，各自携带 Vue 也可以是合理隔离。

#### 原理深挖

`requiredVersion` 表达可接受范围；非 singleton 且版本不兼容时，各方可加载自己的版本。singleton 下官方增强版文档说明会选择一个版本并对不匹配方告警。`shareKey` 必须一致才能协商，子路径导入也要被正确拦截。`eager: true` 会把 shared 打进入口，可能显著增大入口。

#### 工程场景

跨边界共享 Vue 对象或组件时，Vue 与相关插件统一主版本、锁定兼容范围并做集成测试；页面级独立应用则先判断是否真的需要共享。UI 库是否共享取决于体积、样式和升级耦合。上线后从运行时快照和产物分析确认是否真的复用，而不是只看配置。

#### 反例 / 踩坑

host 与 remote 的 `shareKey` 不同导致静默双份；只共享 `vue` 根路径却遗漏子路径；把所有依赖都 singleton，任何团队升级都必须全局协同；同时配置 shared 和 externals 导致运行时缺包。

#### 资深回答模板

「判断：只共享重复成本高或确有单例语义的依赖。证据：跨边界共享 Vue 对象、组件或插件时，再用版本矩阵和运行时快照验证身份一致。兜底：不兼容升级使用独立 Share Scope、各自打包或分阶段发布。」

:::

**追问链：** `requiredVersion` 不满足会怎样？→ 双份 Vue 有哪些症状？→ 多 Share Scope 何时有价值？

::: details 追问参考答案

**1. `requiredVersion` 不满足会怎样？**

结果取决于 shared 策略，不能概括成统一报错：非 singleton 场景可各自加载兼容或自己的版本；增强版 singleton 会在作用域内选择一个版本，并对不满足约束的一方告警，实际行为还受提供版本与加载顺序影响。应以锁定版本实测运行时快照，不把警告忽略成“肯定安全”。

**2. 双份 Vue 有哪些症状？**

两个 Vue 本身不必然出错，页面级应用各自渲染反而可形成隔离；问题出现在跨边界传组件、VNode、响应式对象、插件或注入上下文时，可能出现 `inject` 丢失、响应不更新、实例判断失败和 Devtools 分裂。先确认是否真的跨边界共享身份，再决定 singleton，而不是看到双包就强制统一。

**3. 多 Share Scope 何时有价值？**

当两组应用必须并存但依赖主版本不兼容，或要隔离稳定域与实验域时，可用不同 Share Scope 防止错误协商；remote 的 `shareScope` 和各方注册键必须一致。代价是重复下载、内存和配置复杂度，且跨 scope 对象不能假定同一身份。它是迁移手段，不应替代长期版本治理。

:::

### Q9. 如何在运行时动态加载和切换 remote？

**考察点：** Federation Runtime、动态注册、版本选择

::: details 参考答案

MF 2.0 可通过默认或手动创建的 Federation 实例，在运行时注册 remote，再用 `loadRemote` 加载公开模块；构建插件通常会自动创建默认实例。动态入口应来自受控应用清单，而不是拼接任意 URL。

切换版本时要保证 `name`、入口、公开键和 shared 契约一致，并处理并发去重、超时、缓存和旧模块已执行后的状态。官方 `loadRemote` 签名返回 Promise，并未提供原生取消参数：业务超时后应标记请求代次并丢弃过期结果，不能假设底层网络和脚本执行已经停止。若确需真正取消，必须下沉到自定义 `fetch` / 资源加载层，并先确认对应扩展点是否透传和支持 `AbortSignal`。灰度不能只替换 URL，还要记录 release 并保持会话版本固定。

**追问链：**
1. 动态注册与构建时 `remotes` 各适合什么场景？
2. 已执行的 remote 能否靠改 URL 热切换？
3. 如何防止入口地址被篡改？

::: details 追问参考答案

**1. 动态注册与构建时 `remotes` 各适合什么场景？**

构建时 `remotes` 适合拓扑稳定、需要静态导入体验和简单配置的依赖；运行时 `registerRemotes` 适合租户插件、灰度版本或配置中心下发。增强运行时注册项可含 `name`、`alias`、`entry`、`shareScope` 等，alias 是消费侧引用名。动态能力必须配白名单、版本固定、并发去重和审计。

**2. 已执行的 remote 能否靠改 URL 热切换？**

不能安全地假定可以。remote 容器、模块 Promise、已求值模块和 shared 往往已被当前实例缓存，改注册 URL 不会撤销旧代码的副作用或替换现有引用。官方形式是 `registerRemotes(remotes, { force: true })`：第一参为 remote 配置数组，`force` 位于第二参 options；即使强制重注册也不等于业务状态热迁移。稳妥做法是会话固定 release，切换后刷新或创建隔离实例，并提供旧版回滚。

**3. 如何防止入口地址被篡改？**

浏览器只接受受信发布服务生成的 HTTPS 白名单清单，清单含 app、release、入口、摘要、过期时间并由可信密钥签名；主壳内置或安全轮换信任根，拒绝任意查询参数拼 URL。配合 CSP `script-src`、最小权限和发布审计。动态 chunk 的完整性需按实际加载链设计，不能只给入口加 SRI 就宣称全链可信。

### D9. `mf-manifest.json`、类型提示和 remoteEntry 各自解决什么问题？

::: details 参考答案

#### 基础结论

`remoteEntry.js` 是可执行容器入口；`mf-manifest.json` 是运行时说明文件，包含入口、exposes 资产、shared 和类型地址等元数据；动态类型在开发/构建阶段提升消费契约，不提供运行时兼容保证。

#### 原理深挖

host 指向 Manifest 时，运行时先请求 Manifest，生成或获取 Snapshot，再解析最终 remoteEntry、预加载资产和 shared。启用 `dts` 后，生产者默认可生成 `@mf-types.zip`，消费者拉取并解压到类型目录。类型产物与 JS 必须同版本发布，否则「编译通过、运行失败」。

#### 工程场景

发布流水线把 JS、Manifest 和类型视为一个不可分割版本，先上传内容哈希资产，再原子更新版本清单。CI 校验公开类型、expose 键和 breaking change；生产观测分别标记 Manifest、remoteEntry、chunk、expose 四个失败阶段。

#### 反例 / 踩坑

Manifest 长缓存指向已删除的 chunk；类型文件来自最新环境而运行时入口被灰度到旧版；把 `mf-stats.json` 当消费入口。官方定位中 stats 更适合分析和工具，Manifest 才是稳定紧凑的运行时产物。

#### 资深回答模板

「判断：remoteEntry 负责执行，Manifest 负责描述，类型负责开发期契约。证据：三者绑定同一 release，并分阶段监控加载链。兜底：用原子发布和契约测试阻止类型与运行时代码漂移。」

:::

**追问链：** Manifest 多一次请求怎么优化？→ Snapshot 是什么？→ 类型服务不可用是否应阻断生产构建？

::: details 追问参考答案

**1. Manifest 多一次请求怎么优化？**

先确认它是否在关键路径：可让边缘或服务端把首屏 remote 的解析结果随应用清单返回，预连接资源域，或利用 Manifest 生成的 Snapshot/预加载提示并行发现资产。`stale-if-error` 是 HTTP `Cache-Control` 扩展，仅在浏览器、代理、CDN 支持且缓存策略命中时生效，不是 Manifest 自带能力；客户端 LKG / 版本回退还须显式校验签名、撤销状态和最大陈旧上限。

**2. Snapshot 是什么？**

Snapshot 是增强运行时基于 Manifest 和 remote 信息生成或获取的标准化运行时描述，用于解析 remoteEntry、exposes 资产、shared 以及预加载关系；它不是业务状态快照，也不是所有 Webpack 5 remote 都自动产出的文件。观测需记录 Snapshot 对应 release，缓存键要随版本变化，避免把旧描述配上新资产。

**3. 类型服务不可用是否应阻断生产构建？**

生产者发布时应要求 JS、Manifest 与类型包同 release 生成并通过契约校验；消费者临时拉不到远程类型时，是否阻断取决于是否已有锁定缓存。生产部署不能临时退到“最新类型”，可使用经校验的上一份类型继续构建并告警。类型只保证开发期检查，运行时仍需兼容清单与降级。

:::

### D10. Module Federation 加载失败如何分类并建立应用级故障边界？

::: details 参考答案

#### 基础结论

先按 Manifest、remoteEntry、远程 chunk、容器初始化、expose、shared、模块执行分层定位，再决定重试、隔离或熔断。网络错误可有限重试，脚本执行和版本不兼容不能靠重试解决；版本发布与全局回滚策略放到 Q16 回答。

#### 原理深挖

入口 404/CORS/超时属于网络层；请求成功但容器未注册或抛异常属于执行层；容器存在但公开键缺失属于契约层；shared 初始化失败属于版本/作用域层。旧缓存引用被清理资产是最常见的发布型故障之一。

#### 工程场景

加载器设置超时、一次带抖动重试和按应用熔断；失败后渲染内置降级组件或跳转独立站。错误 UI 保留主导航，并上报 app、release、URL、阶段和原始异常，避免一个 remote 拖垮 host。

#### 反例 / 踩坑

无限重试执行错误形成请求风暴；catch 后返回空对象导致静默白屏；全局错误边界把一个 remote 的异常升级为整页崩溃；把 shared 冲突误判成 CDN 抖动。

#### 资深回答模板

「判断：把联邦加载当作分阶段状态机，先分类再处置。证据：网络错误有限重试，执行或契约错误立即熔断并上报原始异常。兜底：用应用级错误边界和内置降级组件保住 host。」

:::

**追问链：** 为什么重试修不好执行错误？→ 回退如何保证资产完整？→ remote 故障如何不拖垮 host？

::: details 追问参考答案

**1. 为什么重试修不好执行错误？**

语法错误、容器未注册、expose 缺失或 shared 不兼容是确定性的制品/契约问题，同一 release 再下载通常仍会失败，还可能重复执行部分全局副作用。只有超时、连接中断或可确认的 5xx 才做有限抖动重试。执行错误应立即熔断该 app、保留原异常并切降级或上一稳定版本。

**2. 回退如何保证资产完整？**

每个 release 的 Manifest、remoteEntry、chunk、CSS 和类型包必须以内容哈希不可变发布，清单记录摘要，旧版本在回滚窗口内不得删除。回退只原子切清单指针，并用合成探测验证所有引用可达、Content-Type 和 CORS 正确。LKG（上一已知稳定版）必须经过真实健康门禁，不能只是“上一个版本号”。

**3. remote 故障如何不拖垮 host？**

每个 remote 有独立超时、并发上限、熔断器和 UI 错误边界，失败时保留主导航并展示内置占位、只读缓存或独立站链接；不要让共享启动 Promise 阻塞整个壳。上报 app、release、stage 和 traceId，按应用 SLO 告警。关键 host 能力不得反向依赖非关键 remote 才可启动。

:::

### Q10. Module Federation 中 Vue 应用和跨框架模块如何划边界？

**考察点：** Vue Bridge、组件边界、框架耦合

::: details 参考答案

同为 Vue 3 且版本受控，并且确实要跨边界共享组件、插件或响应式上下文时，可公开无全局副作用的组件、Composable 或领域 SDK；若只交换序列化数据，则无需为了「身份一致」强行共享 Vue。页面级应用要显式提供 `render/destroy`、路由 base 和容器边界。MF 2.0 官方提供 `@module-federation/bridge-vue3`，可用 `createBridgeComponent` 暴露应用级模块、用 `createRemoteAppComponent` 消费，但是否采用仍需按项目版本验证。

跨框架时优先用 Web Components、DOM 挂载协议或纯 JS 契约，不跨边界传框架实例、VNode、响应式对象或 Store。样式隔离和生命周期仍需自行治理，Module Federation 不会自动提供。

**追问链：**
1. 为什么不公开整个 Pinia Store？
2. 远程 Vue 组件如何继承主题和国际化？
3. 跨框架组件的事件与属性如何版本化？

::: details 追问参考答案

**1. 为什么不公开整个 Pinia Store？**

公开 Store 会泄露可变状态、action 和 Vue/Pinia 运行时身份，消费者依赖内部字段后，生产者无法独立升级或独立运行；shared 协商失败还会出现双运行时问题。应公开纯函数 SDK、只读快照或窄命令接口，领域写操作由拥有者处理。若确需共享组件上下文，明确兼容版本并做身份测试。

**2. 远程 Vue 组件如何继承主题和国际化？**

host 通过版本化 props、provide 适配器或 CSS 自定义属性传入语义 Token、locale 和消息读取接口；只有 host/remote 共用兼容 Vue 身份时，直接 inject 才可靠。远程组件应有默认主题与缺少翻译的 fallback，不读取 host 私有 Store。视觉回归覆盖动态切换、弹层容器和 RTL，避免全局样式暗耦合。

**3. 跨框架组件的事件与属性如何版本化？**

把 Web Component 或 DOM 挂载协议当独立公共 API：属性只传可序列化值，事件名含领域和版本，事件 payload 有 Schema、可选字段与关联 ID；破坏变更并行发布新标签或 v2 事件。运行时校验来源和载荷，未知字段可忽略。不要传 VNode、框架实例或可变引用，以免双方升级锁死。

## 五、Wujie

### Q11. Wujie 为什么同时使用 Web Components 和 iframe？

**考察点：** DOM 与 JS 分离、隔离模型

::: details 参考答案

Wujie 把子应用 JS 放在同域 iframe 的独立 `window` 中执行，获得浏览器原生的全局环境隔离；把子应用 DOM 渲染到主页面的 Web Component 容器，便于布局、样式承载和应用切换。它不是把整个页面塞进一个普通可见 iframe。

这种模型减少 Proxy 沙箱兼容工作，但仍需处理 iframe 与主文档 DOM 的映射、路由同步、资源跨域和第三方库对 `window/document` 身份的假设。官方快速上手明确要求子应用资源和接口满足相应 CORS 条件。

**追问链：**
1. JS 在 iframe、DOM 在主文档会产生哪些兼容问题？
2. 同域 iframe 与跨域 iframe 的安全边界有何不同？
3. Web Component 是否等于 Shadow DOM？

::: details 追问参考答案

**1. JS 在 iframe、DOM 在主文档会产生哪些兼容问题？**

代码中的 `window` 属于 iframe，而代理后的 `document`/DOM 呈现在主页面，第三方库若比较 `ownerDocument.defaultView`、依赖全局构造器身份、Portal、焦点、Selection、打印或坐标系，可能行为异常。地图、编辑器、文件下载和窗口 SDK 必须做真实 PoC。问题不能用“iframe 原生隔离”一概掩盖。

**2. 同域 iframe 与跨域 iframe 的安全边界有何不同？**

Wujie 标准模式把通过远程 `url` / `fetch` 取得的代码注入主应用同源的运行 iframe，代码来源使用独立资源域并不会把执行环境变成跨域安全边界，主子窗口仍可同源互访。低信任应用应改用真正将 `src` 导航到独立 origin 的普通 iframe，并配置最小 `sandbox`、严格 CSP，以及对 `postMessage` 的 origin、source 和 Schema 校验。

**3. Web Component 是否等于 Shadow DOM？**

概念上不等于，但 Wujie 标准路径的 `wujie-app` 实际会调用 `attachShadow({ mode: 'open' })`，因此默认渲染容器具有可访问的 open Shadow Root，不能只按一般 Custom Element 下结论。降级 iframe 路径、CSS 继承属性、主题变量、Portal 或挂到外部的节点仍要分别验证，不能据此宣称所有样式路径都已隔离。

:::

:::

### D11. Wujie 的保活、单例、重建模式如何选？路由如何处理？

::: details 参考答案

#### 基础结论

`alive: true` 是保活模式：应用只渲染一次，Web Component 离开时保存在内存；`alive: false` 且实现 `__WUJIE_MOUNT/UNMOUNT` 是单例模式；未保活也未改生命周期则是重建模式。按状态保留价值、内存预算和路由语义选择。

#### 原理深挖

保活时 DOM、状态和 iframe 实例持续存在，切换快，但官方说明仅改变传入 URL 不会驱动内部路由，需要通过通信触发。单例模式切走会卸载业务实例但可复用同名 Wujie 实例；重建模式连 iframe 和实例一起销毁，隔离最彻底、重开成本最高。

#### 工程场景

高频工作台可保活，但限制最多保活数并支持主动销毁；低频报表用单例；不易改造且偶尔访问的旧系统用重建。路由同步定义单一真源，处理刷新、前进后退、深链和权限重定向。

#### 反例 / 踩坑

所有应用都保活导致内存和后台轮询持续增长；认为更新 `url` 就能让保活应用跳转；多个菜单复用同名实例却没有处理路由和状态复位。

#### 资深回答模板

「判断：三种模式是速度、状态和回收的取舍。证据：按访问频率、重建成本和内存上限选择并验证路由。兜底：设置保活上限和主动销毁，低频应用退回单例或重建。」

:::

**追问链：** 保活应用如何强制刷新？→ 同名实例如何共享？→ 如何制定 LRU 回收策略？

::: details 追问参考答案

**1. 保活应用如何强制刷新？**

保活模式只改传入 URL 不会自动驱动内部路由。普通刷新应通过 EventBus/props 调用子应用暴露的版本化 reset 或导航命令；需要彻底刷新时先确认脏数据，再主动销毁对应 Wujie 实例并以固定 release 重建。命令带关联 ID 和完成回执，避免主壳误把消息发出当作页面已刷新。

**2. 同名实例如何共享？**

同一 `name` 只能用于同一个子应用的不同页面 URL，以复用其 Wujie 实例和运行 iframe；相关调用中的 `url` / `fetch` / `alive` / `degrade` 等关键配置必须保持同一应用语义和预加载—启动一致性。不同应用、不同入口或不兼容配置必须使用不同 name，不能为省 iframe 强行复用；切页仍要串行卸载、同步路由并重新挂载。

**3. 如何制定 LRU 回收策略？**

以实例为单位记录最近激活、内存估算、后台 CPU、重建耗时和脏状态；超过最大实例数或内存水位时，优先销毁最久未用且无未保存数据的应用，而非仅隐藏 Web Component。高重建成本可加权保留。回收前调用业务确认/持久化钩子，回收后清理总线订阅，并观测命中率和恢复失败。

:::

### Q12. Wujie 有哪些通信方式，如何避免 EventBus 失控？

**考察点：** `props`、window、EventBus、契约

::: details 参考答案

官方提供三类方式：主应用通过 `props` 注入数据和方法；同域 iframe 可通过父子 `window` 直接访问；主子或子子应用可通过 EventBus 通信。

工程上优先级是：初始化上下文用 props，跨应用通知用带命名空间和版本的事件，持久业务状态回到后端或主应用状态服务。直接访问 `window.parent` 耦合最强，只用于受控基础能力。EventBus 要有事件目录、Schema、所有者、幂等语义和 `$off`；保活应用切走后仍可能响应事件，必须判断激活状态。

**追问链：**
1. 保活应用为什么更容易收到「幽灵事件」？
2. request/response 模式如何加超时和关联 ID？
3. 何时应禁止子应用之间直接通信？

::: details 追问参考答案

**1. 保活应用为什么更容易收到「幽灵事件」？**

保活时 iframe、业务状态和 EventBus 订阅可能仍在内存，页面虽不可见却未真正销毁；若每次激活又重复 `$on`，同一事件还会被消费多次。订阅要用稳定函数并在模式要求时 `$off`，回调检查实例激活代次；后台应用只处理明确允许的系统事件，业务事件默认暂停。

**2. request/response 模式如何加超时和关联 ID？**

请求生成唯一 correlationId，并在事件名或 payload 中携带 source、target、version、deadline；响应回传同一 ID。调用方维护 pending Map，超时后删除并忽略迟到响应，必要时发送业务取消命令，但不能假设超时会停止对方副作用。接收方用幂等键去重，双方记录耗时、结果和 traceId。

**3. 何时应禁止子应用之间直接通信？**

涉及身份、权限、跨域写操作、多个消费者编排或需要审计补偿时，应经主壳能力层或后端事实源，避免子应用形成不可见网状依赖。只有同一领域内、低风险且契约稳定的通知可直接通信，也须登记 Schema、Owner 和版本。若删除任一应用会让另一应用无法启动，通常应重新划边界。

### Q13. Wujie 的性能优势和局限分别是什么？

**考察点：** 原生隔离、预加载、内存、兼容性

::: details 参考答案

优势来自 iframe 原生 JS 上下文隔离、预执行/预加载和 Web Component 保活，二次切换可很快；局限是首次仍要下载、解析和执行资源，iframe 与 DOM 映射有兼容成本，保活会用内存换速度，资源和接口还受 CORS 约束。

性能评估要分首次可交互、二次激活、内存峰值、后台 CPU、预加载流量和低端机表现。不能只用「秒开」Demo 代替真实应用测试。涉及编辑器、地图、Portal、打印、文件下载和依赖窗口身份的 SDK，要专门做 PoC。

**追问链：**
1. 预执行与保活分别优化哪一段时间？
2. iframe 数量多会带来什么成本？
3. 如何设计低端设备降级策略？

::: details 追问参考答案

**1. 预执行与保活分别优化哪一段时间？**

预执行把资源下载、解析和部分初始化提前到用户进入前，主要缩短首次激活等待，但会提前消耗网络与主线程；保活保存已运行的 iframe、DOM 和状态，主要缩短再次切换。二者都不是免费“秒开”：应分别统计首开、二开、额外流量、后台 CPU 和内存，并避免与首屏关键资源竞争。

**2. iframe 数量多会带来什么成本？**

每个 iframe 有独立 window、全局对象、事件环境和框架实例，叠加后会增加堆内存、GC 压力、后台定时器、网络连接和 Devtools/故障定位复杂度；保活 Web Component 还保存 DOM。设置同时保活数和内存水位，切后台暂停轮询，按 LRU 主动销毁。只看可见 DOM 数无法衡量成本。

**3. 如何设计低端设备降级策略？**

依据 deviceMemory、硬件并发、网络和实测分层，但不把单一 UA 当结论。低端/弱网关闭非首屏预执行，限制并发和保活数量，低频应用改为单例或重建，提供静态骨架和独立站降级。通过远程开关灰度，监控 LCP、INP、崩溃和内存水位；设备 API 缺失时采用保守默认。

## 六、隔离、通信与治理

### Q14. CSS 与 JS 隔离有哪些通用层级？

**考察点：** 隔离强度、兼容性、安全边界

::: details 参考答案

CSS 从弱到强可分为命名约定/CSS Modules、运行时 scoped、Shadow DOM、完整 iframe；JS 可分为共享 `window` + 自律、Proxy/快照/VM 沙箱、同域 iframe、跨域 iframe。隔离越强，主题透传、弹窗、路由、调试和通信适配成本通常越高。

可信内部应用主要防冲突，可选 Namespace + Proxy/VM；多版本组件库可评估 Shadow DOM；不可信或强安全要求必须用独立域跨域 iframe，并限制 `sandbox` 权限、CSP 和 `postMessage` 来源。任何 JS 兼容沙箱都不能自动成为安全沙箱。

**追问链：**
1. Shadow DOM 能否隔离 JS？
2. 同域 iframe 能否阻止子应用读主应用数据？
3. 为什么 CSS Reset 特别危险？

::: details 追问参考答案

**1. Shadow DOM 能否隔离 JS？**

不能。Shadow DOM 主要封装 DOM 树和样式选择器，运行脚本仍在同一个 JavaScript realm，可访问 window、网络、Storage，并可通过宿主元素和公开引用影响外部。它适合降低样式冲突，不是恶意代码沙箱。JS 安全边界应使用独立域 iframe、最小 `sandbox` 权限、CSP 和受控消息。

**2. 同域 iframe 能否阻止子应用读主应用数据？**

不能依赖它阻止。同源策略允许同域父子窗口互访，子应用通常可读 `window.parent`、DOM、Cookie 和同源 Storage；即使框架提供代理，也不是浏览器级安全保证。敏感或第三方应用应放独立 origin，Cookie 设置合理 Domain/SameSite/HttpOnly，并只通过校验 origin、source 和 Schema 的消息授权能力。

**3. 为什么 CSS Reset 特别危险？**

Reset 常用 `*`、元素名和 `html/body` 等低特异性但覆盖面极广的全局规则，会改变主壳及其他应用的盒模型、字体、边距和表单样式，且加载顺序变化即可产生回归。应限制在应用根节点、用 CSS Layers/Namespace 管理优先级，并做视觉回归；跨 Shadow 边界时仍需处理宿主与继承变量。

### D12. 跨应用状态和通信如何设计，才能避免「全局 Store 地狱」？

::: details 参考答案

#### 基础结论

共享身份与环境，不共享领域内部状态；传值、事件和命令都要有所有者、Schema、版本和生命周期。后端事实以服务端为准，前端只缓存可重建视图状态。

#### 原理深挖

共享可变 Store 会形成时序耦合：任一应用可修改，消费者不知道来源、版本和回放顺序。事件能降低空间耦合，却增加时间和可观测性问题。因此需要区分初始化上下文、领域事件、查询和命令，并为 request/response 加关联 ID、超时、取消与幂等键。

#### 工程场景

主应用提供只读 `AuthContext`、租户和主题；订单应用发布 `order.created.v2`，消费者只依赖 Schema；跨页强一致结果通过 API 查询。契约仓库生成 TypeScript 类型，CI 做兼容检查，监控记录发布方、订阅方和耗时。

#### 反例 / 踩坑

暴露主应用 Pinia，让子应用直接改菜单和 Token；EventBus 使用 `update` 这类无命名空间事件；切换应用后监听未解绑，同一消息消费多次。

#### 资深回答模板

「判断：按数据所有权设计通信，不共享领域可变 Store。证据：公共上下文只读、事件版本化、订阅绑定生命周期。兜底：关键命令增加超时、幂等和链路日志，最终事实回查后端。」

:::

**追问链：** 事件 Schema 如何演进？→ 丢事件怎么补偿？→ 哪些数据允许主应用缓存？

::: details 追问参考答案

**1. 事件 Schema 如何演进？**

事件名包含领域和主版本，如 `order.created.v2`；同版本只新增可选字段，消费者忽略未知字段，破坏变更并行发布 v1/v2。Schema 仓库生成类型并做生产者—消费者兼容测试，但接收端仍运行时校验。记录 Owner、保留期和弃用指标，确认旧消费者归零后再删除旧版。

**2. 丢事件怎么补偿？**

前端 EventBus 不应承载必须可靠送达的业务事实。关键结果由后端持久化，消费者用关联 ID/幂等键查询或重放；页面切回时按游标拉取缺口，超时显示状态待确认，而不是盲目重复写。纯 UI 通知可容忍丢失。若必须跨页可靠，应采用服务端 Outbox/消息机制并监控积压。

**3. 哪些数据允许主应用缓存？**

可缓存身份显示信息、租户、能力快照、主题、语言和应用清单等公共、可版本化且可重新获取的数据；缓存键必须包含主体、租户、版本与环境，并有过期和失效机制。领域草稿、交易状态和长期 Token 不应成为全局缓存。权限缓存只能改善体验，服务端仍逐请求权威授权。

:::

### Q15. 微前端中的登录、权限和 Token 应如何治理？

**考察点：** 认证中心、前端权限边界、最小暴露

::: details 参考答案

认证由统一身份层负责，主应用提供当前用户、租户和能力集合，子应用做展示级路由与按钮控制；真正授权必须由后端执行，前端隐藏按钮不是安全措施。Token 尽量由同域 BFF 配合 HttpOnly Cookie 管理，避免把长期凭证通过 props、EventBus 或日志扩散。

主应用只下发应用需要的最小权限，权限变化要可刷新并使旧请求失效。独立域应用通过标准登录协议或受控消息交换短期凭证，不共享任意 Cookie。

**追问链：**
1. 子应用独立运行时如何获得身份？
2. 多租户切换如何防止旧缓存串租户？
3. 权限服务不可用时默认放行还是拒绝？

::: details 追问参考答案

**1. 子应用独立运行时如何获得身份？**

子应用通过同一 OIDC/OAuth 登录流程或同域 BFF 会话取得身份，不依赖主壳私有 Store；嵌入时主壳只传最小、短期上下文，子应用仍从受信身份端校验和刷新。开发环境可用明确标记的 mock。独立与嵌入模式共享 Auth Adapter，避免两套权限语义，长期 Token 不经 props/EventBus 扩散。

**2. 多租户切换如何防止旧缓存串租户？**

租户切换先提升会话代次并取消或忽略旧请求结果，再清空以主体+租户为键的内存、持久化缓存、Store、预取和保活实例；重新获取能力与应用清单后才开放导航。服务端校验租户归属，不能信任前端参数。日志记录 tenantId 和 generation，用并发慢请求测试旧数据不会回写。

**3. 权限服务不可用时默认放行还是拒绝？**

高风险写操作和敏感数据默认拒绝；只读低风险页面可使用未过期、签名且绑定主体/租户的上一能力快照，明确显示降级状态。绝不能因前端权限接口超时就全量放行，后端授权仍是最终门禁。Runbook 规定快照 TTL、允许能力范围、告警和恢复后强制刷新。

### Q16. 微应用如何做灰度和回滚？

**考察点：** 版本清单、会话固定、资产保留

::: details 参考答案

主应用不要硬编码「latest」入口，而由应用清单按用户、租户或灰度桶返回不可变 release。一次会话固定版本，日志带 release；先灰度 remote，再扩大比例。回滚是把清单指针切回上一完整版本，不是覆盖同名文件。

旧 HTML/Manifest、remoteEntry、chunk、CSS 和类型产物要成套保留；新旧版本的公共契约需在过渡窗口双向兼容。主应用自身与子应用联动发布时要定义先后顺序和兼容矩阵。

**追问链：**
1. 为什么覆盖 `remoteEntry.js` 仍可能无法回滚？
2. 灰度用户刷新后如何保持同一版本？
3. 数据库变更如何支持前端回滚？

::: details 追问参考答案

**1. 为什么覆盖 `remoteEntry.js` 仍可能无法回滚？**

浏览器、CDN 或 Service Worker 可能缓存旧入口，而入口引用的新哈希 chunk 已被删除；反向覆盖后又可能让已缓存入口与另一批 chunk 混配。remote 已执行的模块和 shared 也不会自动撤销。正确做法是每个 release 全套不可变发布，保留旧资产，只原子切换短缓存清单指针并验证引用完整。

**2. 灰度用户刷新后如何保持同一版本？**

首次分桶由服务端或受信配置层按稳定用户/租户键计算，并把 release 写入短期、签名会话绑定；刷新继续返回同一不可变版本，直到实验结束或明确迁移。匿名用户可用稳定 cookie，但要处理清理和隐私。日志带 bucket、release 和决策版本，避免浏览器每次随机导致状态跨版本。

**3. 数据库变更如何支持前端回滚？**

采用 expand/contract：先新增可空字段、兼容 API 和双读/双写，再发布新前端；确认旧前端退出后才收缩旧列与语义。回滚窗口内后端同时接受新旧请求，数据迁移可重放且有校验。若数据库已执行不可逆删除，单纯切旧前端无法恢复，因此破坏性迁移必须晚于观察窗口。

:::

:::

### D13. 微前端的安全风险模型应该包含什么？

::: details 参考答案

#### 基础结论

把每个远程入口视为可执行供应链依赖。核心风险包括入口劫持、XSS 横向扩散、过度权限、消息伪造、依赖投毒、数据泄露和不可信应用逃逸。可信内部应用与第三方应用必须采用不同隔离等级。

#### 原理深挖

HTML Entry 和 remoteEntry 都能在用户上下文执行代码；Proxy 沙箱隔离变量但不阻止网络和 DOM 读取，同域 iframe 也可互访。qiankun、Garfish 等方案的部分沙箱/加载链依赖 `eval`、`new Function` 或等价的字符串执行机制，会与禁止 `'unsafe-eval'` 的严格 CSP 冲突。真正的信任边界需要独立域、iframe sandbox、严格 CSP、`postMessage` 的 origin/source/Schema 校验，以及最小能力令牌。

#### 工程场景

应用清单只允许 HTTPS 白名单域名并签名/审核；CSP 使用 nonce/hash，资源发布有制品签名和 SBOM；通信层拒绝未知事件与超大载荷。不能为了兼容字符串执行而无条件放宽 `'unsafe-eval'`：高安全域优先使用独立域 iframe，或选择不依赖字符串执行且能满足 CSP 的装配方案。

#### 反例 / 踩坑

动态拼接 remote URL；`postMessage('*')` 且不校验来源；把主应用 API Client 和完整 Token 注入所有子应用；为接入微前端在整站永久开启 `'unsafe-eval'`；把沙箱开启当作安全评审已完成。

#### 资深回答模板

「判断：先区分可信内部应用与第三方代码的信任边界。证据：核对字符串执行、CSP、入口供应链、消息来源和凭证暴露。兜底：不放宽高安全域的 `'unsafe-eval'`，低信任应用放入独立域 iframe。」

:::

**追问链：** SRI 对动态入口有什么限制？→ CSP 如何兼容动态 chunk？→ 子应用被攻破时如何缩小爆炸半径？

::: details 追问参考答案

**1. SRI 对动态入口有什么限制？**

SRI 要求加载标签预先知道固定摘要，并通常需正确 CORS；入口 URL 由运行时变化、HTML Entry 内再发现资源或 remoteEntry 动态注入 chunk 时，单个入口摘要覆盖不了后续资产。可在签名 Manifest 中绑定 release 与各资源哈希，并由受控加载器校验，但须按框架扩展点实测，不能宣称自动保护整条链。

**2. CSP 如何兼容动态 chunk？**

为可信 CDN 配置最小 `script-src`，优先使用 nonce/hash 与 `'strict-dynamic'` 的受控引导链，并确保运行时创建脚本能携带所需 nonce；具体浏览器和 bundler 需实测。qiankun/Garfish 某些执行链依赖 `eval`/`new Function`，会与禁用 `'unsafe-eval'` 冲突，不能为兼容无条件放宽高安全域。

**3. 子应用被攻破时如何缩小爆炸半径？**

低信任应用使用独立 origin iframe，最小化 `sandbox`、Permissions Policy、Cookie 和网络权限；主壳只暴露能力令牌而非完整 API Client/Token，消息严格校验 origin、source、Schema 与大小。入口清单可熔断单 app，后端按应用和用户授权限流。独立日志、密钥与数据域可减少横向扩散。

:::

### Q17. 微前端可观测性最少要采集哪些数据？

**考察点：** 分阶段指标、版本归因、用户体验

::: details 参考答案

至少采集：

- 装载阶段：入口解析、DNS/TLS、Manifest/HTML、remoteEntry、chunk、执行、mount、首个业务渲染。
- 结果：成功、超时、重试、降级、卸载耗时和泄漏指标。
- 上下文：host、app、release、route、灰度桶、网络、设备、traceId。
- 体验：子应用可交互时间、LCP/INP/CLS、切换白屏和资源体积。

错误边界既要上报原始异常，也要标注失败阶段和责任应用。Dashboard 按 release 对比基线，告警能直接关联入口 URL、发布记录和负责人。

**追问链：**
1. 如何定义「子应用可用」而不只是 `mount` 成功？
2. Source Map 如何按子应用版本匹配？
3. 如何监控卸载泄漏？

::: details 追问参考答案

**1. 如何定义「子应用可用」而不只是 `mount` 成功？**

可用应以用户关键任务为准：入口与资源加载成功、首个业务视图渲染、必要数据返回、关键控件可交互且无白屏；`mount` resolve 只表示生命周期完成。为每个 app 定义 ready 信号和合成事务，统计成功率与 P95/P99 时间。降级页算“壳存活”但不算该业务任务成功。

**2. Source Map 如何按子应用版本匹配？**

构建时将 app、release、chunk hash 写入文件名和上报事件，Source Map 与制品同批上传到受控符号服务，生产 CDN 不必公开 `.map`。解析端按三元组精确查找，不能用最新 map 猜测旧堆栈。旧 release 的 map 保留至少覆盖错误留存期，并校验 sourceRoot 和上传完整性。

**3. 如何监控卸载泄漏？**

在开发/巡检环境自动循环进入退出，采集每个 app 的监听器、定时器、Observer、WebSocket、DOM 节点、Detached DOM、堆大小和后台请求；以多轮趋势而非单点内存判定。生产侧可采样卸载后 CPU、请求和实例计数，超预算关联 release 告警，再用 Heap Snapshot 保留路径定位。

## 七、性能、故障与演进

### D14. 微前端首屏瀑布、预加载与缓存如何优化？

::: details 参考答案

#### 基础结论

先画真实瀑布：主壳 → 应用清单 → HTML/Manifest → remoteEntry → shared/chunk → 数据 → 渲染。优化目标是减少串行关键路径，不是盲目预加载全部；入口应急处置放到 Q18，发布回滚放到 Q16。

#### 原理深挖

Manifest 带来元数据和预加载能力，也可能多一次请求；可由服务端清单预解析、边缘合并或 Snapshot 降低串行。内容哈希资产长缓存，入口/清单短缓存；`stale-if-error` 只能由确认支持的 HTTP / CDN `Cache-Control` 策略提供，并非 Manifest 能力。MF 客户端的 LKG / 版本回退需显式实现签名校验、撤销检查和最大陈旧上限。预加载只对高概率下一跳生效，shared 过度集中可能阻塞所有 remote。

#### 工程场景

主壳内联最小骨架；建立 preconnect，让首屏 remote 提前发现，并让数据请求与代码并行。按权限和下一跳概率预取，限制并发、流量和主线程解析成本，用命中率与 LCP 共同验收。

#### 反例 / 踩坑

主应用启动后串行请求权限、菜单、清单、入口、数据；所有应用 `prefetch all` 抢占带宽；remoteEntry 短缓存但 chunk 被过早清理；Service Worker 永久缓存旧入口。

#### 资深回答模板

「判断：先找瀑布中最长的串行关键链。证据：用 LCP、预取命中率、额外流量和主线程耗时验证并行与缓存效果。兜底：低命中或弱网关闭预取，入口和哈希资产采用不同缓存策略。」

:::

**追问链：** Manifest 请求怎么消除？→ stale-if-error 适合缓存什么？→ shared 是优化还是单点瓶颈？

::: details 追问参考答案

**1. Manifest 请求怎么消除？**

不一定要彻底消除，应先减少关键路径串行：服务端/边缘解析首屏 Manifest，把固定 release 的 Snapshot 或资产提示随应用清单返回，让代码、数据和连接预热并行；也可短缓存 Manifest。内联结果必须带版本和完整性信息，发布后能原子失效。若因此失去动态治理与回滚元数据，省一次请求得不偿失。

**2. stale-if-error 适合缓存什么？**

`stale-if-error` 是 HTTP 缓存扩展，不是 Module Federation Manifest 或运行时自带能力；只有确认浏览器、代理和 CDN 链路支持并按预期执行时，才为可公开、可版本化的清单或 Manifest 配置。客户端 LKG 必须显式实现，并校验签名、撤销状态、release 与最大陈旧上限；权限数据和已撤销版本不得因源站失败继续复用。

**3. shared 是优化还是单点瓶颈？**

两者都可能。共享大依赖可减少重复下载并保证必要的运行时身份；但 eager 或集中提供会放大首屏入口，提供者故障、版本冲突或初始化阻塞可影响多个 remote。只共享高重复成本或确有 singleton 语义的包，按 Share Scope 隔离升级，并用产物分析、运行时 Snapshot 和故障注入验证。

:::

### Q18. `remoteEntry` 或 Manifest 线上突然失败，你如何在 15 分钟内处置？

**考察点：** 应急响应、证据分类、止损

::: details 参考答案

先止损再根因分析：

1. 从告警确认影响 app、release、地区和失败阶段，禁止继续放量。
2. 直接检查入口状态码、Content-Type、CORS、响应内容和引用 chunk；区分网络失败与脚本执行失败。
3. 将应用清单切回上一完整 release，确认旧资产仍可访问；必要时启用内置降级页或独立站。
4. 对比发布记录、CDN 回源、缓存键和 shared 版本，不做无上限重试。
5. 恢复后保留证据，补充制品完整性、资产保留和合成巡检。

**追问链：**
1. 请求 200 为什么仍可能加载失败？
2. CDN 回滚后浏览器缓存如何处理？
3. 如何建立入口的主动拨测？

::: details 追问参考答案

**1. 请求 200 为什么仍可能加载失败？**

响应可能是 CDN/WAF 返回的 HTML 错误页、错误 Content-Type、被代理截断的脚本、过期 Manifest，或入口引用的 chunk 404；脚本下载成功后还可能语法异常、容器未注册、expose/shared 初始化失败。处置时同时检查响应体、头、最终 URL、引用资产和控制台原始异常，不能只看状态码。

**2. CDN 回滚后浏览器缓存如何处理？**

不要覆盖同 URL 期待所有缓存立即一致。入口/清单使用短 TTL、版本化缓存键和受控 stale 窗口，哈希 chunk 永久不可变；回滚切回旧 release 清单后，旧资产可直接命中。必要时只精准 purge 入口，不清空全部哈希缓存。Service Worker 也必须按 release 原子更新并有撤销策略。

**3. 如何建立入口的主动拨测？**

从多个地区和网络周期性获取清单/入口，校验 DNS/TLS、状态码、Content-Type、CORS、摘要和所有引用 chunk，再在真实浏览器完成容器初始化、加载一个 expose 或 mount 冒烟。探测固定生产灰度与 LKG 两条路径，结果带 app/release/stage 告警到 Owner，避免只测首页 HTTP 200。

### Q19. 如何把一个巨石 Vue 管理后台渐进迁移为微前端？

**考察点：** 绞杀者模式、迁移顺序、可回退

::: details 参考答案

我会采用绞杀者模式，不先重写主壳：

1. 建基线：路由、全局变量、权限、组件库、性能和发布依赖。
2. 抽出最小平台契约：身份、租户、导航、主题、埋点和错误边界。
3. 选择低耦合、可独立验收的只读域试点，保留旧路由开关。
4. 让旧应用先作为一个子应用运行，再逐域替换，避免同时拆边界和升级所有技术栈。
5. 每迁一域都验证独立运行、深链、刷新、权限、卸载、灰度和回滚。
6. 用流量和功能覆盖率决定删除旧代码，最后才收缩旧壳。

若只有模块共享需求，可先用 Monorepo 或 Module Federation；需要完整应用生命周期和隔离时再引入 qiankun、Garfish 或 Wujie。

**追问链：**
1. 第一个试点为什么不选核心交易域？
2. Vue 2 与 Vue 3 如何共存？
3. 迁移完成度用什么指标衡量？

::: details 追问参考答案

**1. 第一个试点为什么不选核心交易域？**

首个试点同时验证边界、装载器、权限、发布和观测，未知风险最高；核心交易域对一致性、可用性和回滚要求高，失败成本会掩盖技术学习。应选低耦合、只读、访问适中且有真实复杂度的页面，保留旧路由开关。平台能力稳定并经过故障演练后，再按业务价值迁移核心域。

**2. Vue 2 与 Vue 3 如何共存？**

以页面级应用各自打包 Vue，分别挂载到独立容器，通过序列化 props/事件和后端 API 交互，不跨边界传 VNode、响应式对象或 Pinia。样式用 Namespace/Shadow DOM，路由前缀独占。若用 MF shared，不要强行把两代 Vue 放同一 singleton；按 scope 隔离并计入重复体积。

**3. 迁移完成度用什么指标衡量？**

同时看业务覆盖和退出能力：已迁路由/流量、旧代码与旧接口删除比例、独立发布率、联动发布、回滚耗时、装载成功率、LCP/INP、故障和运维工时。每个域只有通过独立运行、深链、权限、卸载与回滚验收才算完成。代码搬到新仓库但仍依赖旧壳，不算完成迁移。

:::

**踩坑：** 一边迁微前端、一边重写权限、组件库和后端接口，变量过多导致无法判断故障来源。

### D15. 请完成 qiankun、Garfish、Module Federation、Wujie 的四方案选型答辩。

::: details 参考答案

#### 基础结论

没有通用最优解：完整应用装配和成熟接入可评估 qiankun；需要 Garfish 的 loader、实例管理与沙箱特性时做真实 PoC；模块级动态共享和强类型治理选 Module Federation；需要更强 JS 环境隔离、低侵入旧应用和保活时可评估 Wujie。Wujie 使用的同域 iframe 不是安全边界，安全不可信场景仍优先独立域 iframe。

#### 原理深挖

- qiankun：HTML Entry + single-spa 生命周期 + Proxy 沙箱，路由应用模型清晰。
- Garfish：HTML Entry + loader + VM/快照沙箱 + Router/应用实例体系。
- Module Federation：构建与运行时模块容器、Share Scope；不自带完整 CSS/JS 沙箱。
- Wujie：同域 iframe JS 上下文 + Web Component DOM 承载，提供更强的 JS 环境隔离和保活，但同域下主子窗口可互访，不构成安全边界。

#### 工程场景

我用加权矩阵评估：应用/模块粒度、旧系统侵入、多实例、隔离强度、首屏、保活、类型契约、动态发布、故障回退、生态、团队经验和退出成本。拿真实 Vue 2 旧应用、Vue 3 新应用、弹窗/地图/编辑器跑 PoC，并进行弱网、重复卸载和故障注入。

#### 反例 / 踩坑

把四者放在同一维度比 API 数量；把 Module Federation 当安全沙箱；因 Wujie 使用 iframe 就误判为跨域安全隔离；用 qiankun/Garfish Demo 成功代替旧应用兼容验证。

#### 资深回答模板

「判断：先定模块或应用粒度，再按隔离、侵入和保活等硬约束筛选。证据：用真实应用对兼容、性能、故障和运维做 PoC。兜底：方案必须保留独立运行、回滚、安全边界和框架退出路径。」

:::

**追问链：** 同一平台能否混用两种方案？→ 哪些指标是一票否决？→ 选型一年后如何复盘和替换？

::: details 追问参考答案

**1. 同一平台能否混用两种方案？**

可以，但必须由统一壳契约收敛路由、身份、主题、观测、错误边界和发布清单。例如页面用 qiankun/Wujie，稳定组件用 MF；不要让同一边界被两套生命周期重复管理。混用会增加调试、缓存和安全模型，应记录采用理由、Owner 与退出路径，并通过一个适配层隐藏框架细节。

**2. 哪些指标是一票否决？**

无法满足目标浏览器/CSP、安全信任边界、核心第三方 SDK、深链刷新或可回滚发布，是硬性否决；重复卸载持续泄漏、低端机超内存预算、首屏 P75 明显越线且无可行优化也应否决。团队陌生度只是成本，不应替代技术证据。阈值在 PoC 前写入 ADR，避免结果出来后移动标准。

**3. 选型一年后如何复盘和替换？**

按最初 ADR 对比发布等待、接入成本、装载成功率、LCP/INP、内存、事故、平台工时和生态维护状态，并访谈业务 Owner；区分框架缺陷与边界/治理问题。替换时保持独立运行和标准生命周期，先由适配层双跑一个低风险应用，按清单灰度迁移，保留 LKG 与逐应用回退，不做整平台重写。
