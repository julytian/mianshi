# uni-app / 小程序题库

> **怎么用：** 先盖住答案，自己口述 1～2 分钟（条件编译、分包、登录、审核），再点开 `参考答案` 对照补洞。追问用来模拟面试官加压；踩坑是实战里最容易翻车的点。中英文术语之间请习惯留空格，口述时也建议如此。

本模块偏「十年经验口述」：少背 uni API 清单，多讲**多端差异、包体积、登录态、审核合规与真机坑**。

### Q1. 条件编译你怎么用才不把项目写成「井号地狱」？

**考察点：** `#ifdef`、多端差异收敛、目录级拆分

::: details 参考答案
条件编译是 uni-app 的手术刀：`#ifdef MP-WEIXIN` / `H5` / `APP-PLUS` 等。适合**真正平台差异**（支付 SDK、登录、文件系统、原生能力），不适合把业务 if-else 全塞进一个文件。

治理：
1. 差异沉到 `platform` 适配层（如 `pay.weixin.ts` / `pay.h5.ts`），页面只调统一接口；
2. 文件级：`*.mp.vue` / 目录拆分，比满屏 ifdef 可读；
3. 约定「业务代码零 ifdef」的 Code Review 规则，超限就抽适配器；
4. 样式差异用 scss 条件编译或 class 前缀，别复制整页。

口述金句：条件编译是能力边界，不是复制粘贴许可证。
:::

**追问：**
1. 同一套 UI 在小程序和 H5 差很多，你拆项目还是继续 uni？
2. `ifdef` 导致 tree-shaking / 类型检查失效，怎么补？
3. 新同学最容易滥用条件编译的三种场景是什么？

**踩坑：** 在模板、脚本、样式各写一套互相矛盾的 ifdef，一端改了另一端忘了——用适配层单测或端到端清单兜住。

### Q2. uni-app 生命周期和小程序 / Vue 生命周期差异，你会怎么讲？

**考察点：** `onLaunch` / `onShow` / `onLoad`、页面 vs 组件、Vue3

::: details 参考答案
分层：
- **应用级**：`onLaunch`（冷启动一次）、`onShow` / `onHide`（前后台）；
- **页面级**：`onLoad`（拿 query，只一次）、`onShow`（每次可见）、`onReady`、`onUnload`；
- **Vue**：`mounted` 等——与小程序页面生命周期**不要混为一谈**。

实战约定：
- 路由参数用 `onLoad`；
- 每次回页刷新用 `onShow`（但要防「太勤」——配合时间戳或脏标记）；
- 和 Vue3 `setup` 组合时，用 `@dcloudio/uni-app` 的生命周期钩子，注意调用时机与组件实例。

口述强调：小程序页面不是浏览器路由组件那么简单，**有被回收、被切后台、被分享落地**的状态机。
:::

**追问：**
1. `onShow` 里拉数导致闪烁，你怎么做「仅必要时刷新」？
2. 分包预下载与页面 `onLoad` 时序问题怎么排查？
3. keep-alive 在 H5 端有、在小程序端无，同一套代码如何兼容？

**踩坑：** 只在 `mounted` 取 `options` 参数——部分端或场景拿不到，应用 `onLoad`。

### Q3. 小程序主包体积超了，你怎么做分包与瘦身？

**考察点：** 主包 2M / 总包限制、分包、独立分包、分包预下载

::: details 参考答案
先量：分析构建报告，看主包里谁最大（静态图、公共 JS、UI 组件、稀有页面误放主包）。

手段：
1. **分包**：非首开链路页面进 subPackages；首页与登录进主包；
2. **独立分包**：活动页等可独立打开，减少依赖主包；
3. **图片**：上 CDN，别打进包；图标用字体 / 精简 SVG；
4. **代码**：按页引入、减少巨型 util 被主包引用；警惕「公共模块被主包依赖 → 整棵树进主包」；
5. **插件 / npm**：选体积，必要时自建瘦封装。

预下载：配置关键分包在空闲时拉，平衡「首开」与「二跳等待」。口述要带数字：从超限到剩多少余量。
:::

**追问：**
1. 为什么「页面放进分包了」主包还是没变小？
2. 分包异步化组件解决什么问题？
3. 总包上限和「用户下载体验」你怎么跟产品讲？

**踩坑：** 主包 `import` 了分包页面或仅分包用的大组件——依赖反穿，分包策略失效。

### Q4. 小程序登录与 session，你会怎么设计整条链路？

**考察点：** `wx.login`、code 换 session、token 续期、静默登录

::: details 参考答案
典型链路：
1. 前端 `uni.login` / `wx.login` 拿 `code`；
2. 后端用 code 换 openid/session，签发**自家 token**（或自定义登录态）；
3. 前端存 storage，请求头带上；
4. 过期：静默再 login + 换票，失败再引导用户交互登录。

注意：
- `code` 只能用一次且短时有效，别当长期身份；
- 手机号 / 用户信息是**另套授权**，与登录态分开讲；
- 多端：App / H5 走另一套 OAuth，后端统一成同一用户模型。

安全：token 刷新要防并发刷爆；敏感操作二次校验。口述画时序图比背 API 强。
:::

**追问：**
1. 多个子包同时 401，如何做单飞刷新？
2. openid 与业务 userId 映射变更（合并账号）前端怎么适应？
3. H5 端没有 `wx.login`，同一套 store 怎么抽象？

**踩坑：** 把 `code` 当 session 存本地反复用——必失败；或每次 `onShow` 都 login，触发频率限制。

### Q5. 授权与 scope（位置、相册、用户信息）你怎么讲清「能做与不能做」？

**考察点：** 授权时效、引导设置页、隐私合规 API

::: details 参考答案
小程序授权是**能力级**的：定位、相册、摄像头、通讯录等。用户拒绝后不能死循环弹窗，应引导「去设置页打开」。

历史坑：`getUserInfo` 弹窗已废弃路径，现多用头像昵称填写能力 / 手机号按钮等新合规组件。位置：`authSetting` 查询 → 申请 → 失败降级（不强制定位也能浏览）。

产品话术与技术一致：先讲清用途再申请；能延迟授权就延迟（用到再要）。与《用户隐私保护指引》声明的能力必须一致，否则审核挂。
:::

**追问：**
1. 拒绝授权后的降级体验你怎么设计？
2. 企业微信 / 其他小程序宿主的授权差异怎么处理？
3. 为什么「一进首页就弹一堆授权」会被拒审或留存差？

**踩坑：** 还在用已废弃用户信息接口「偷偷拿头像」——审核与真机行为都不稳，应跟现行文档。

### Q6. `rpx` 你怎么理解？和 H5 的 rem/vw 混用时要注意什么？

**考察点：** rpx 规则、双端样式、固定尺寸

::: details 参考答案
`rpx`：规定屏幕宽 750rpx，随屏宽缩放——小程序设计稿友好。注意：
- 1px 细线、字体下限有时仍要用 `px`；
- 不同端编译后表现接近但不完全同一套 CSS 引擎；
- H5 端 uni 会转译，但与纯 Vant H5 项目的 rem 方案混在同一设计体系时要对齐基准。

原则：布局与间距用 rpx；需要「物理恒定」的（如发丝线、部分图标）用 px；大屏是否限制最大宽度看产品。别在计算里用 JS 拿系统信息手写一套第二缩放，除非做图表 canvas。
:::

**追问：**
1. 横屏下 rpx 行为是否符合预期？你怎么处理？
2. `rpx` 与 `vh` 混用做全屏页有什么坑？
3. 设计给的是 375 稿，团队如何统一换算？

**踩坑：** 在内联 style 里用了 `rpx` 字符串，部分端或旧基础库支持不一致——关键样式优先 class。

### Q7. 小程序原生组件限制（input、video、map、canvas）对你业务的影响？

**考察点：** 原生组件层级、`cover-view`、同层渲染

::: details 参考答案
小程序部分组件是原生实现，默认层级高于 WebView 渲染的普通组件，于是出现：弹层被 video/map 挡住、`fixed` 遮不住原生组件等。

应对：
1. 用 `cover-view` / `cover-image` 盖在原生组件上（能力有限，样式受限）；
2. 能同层渲染的组件走同层模式（视基础库）；
3. 交互上：弹层出现时销毁或隐藏原生组件；
4. 架构上：减少「复杂 H5 思维」硬套——原生组件区交互单独设计。

口述要举例：直播间、门店地图选点、扫码页——你怎么避免被层级坑延期。
:::

**追问：**
1. `v-if` 销毁 video 与 `hidden` 哪个更适合弹层场景？
2. canvas 旧版与新版 2d 差异，对图表库选型的影响？
3. 自定义 tabBar 与原生组件冲突怎么处理？

**踩坑：** 用普通 `view` 做自定义相机遮罩——真机直接被原生层穿透，开发者工具却正常。

### Q8. 小程序发布链路（开发 / 体验 / 审核 / 灰度）你怎么控质量？

**考察点：** 版本、CI 上传、审核素材、回滚

::: details 参考答案
链路：本地 / CI 构建 → 上传代码（`miniprogram-ci` 或工具）→ 体验版验证 → 提交审核 → 通过后发布 → 可灰度。

质量闸：
1. 构建产物体积检查、eslint、关键页面冒烟；
2. 体验版用真实接口环境或稳定 mock，别「开发者工具能过」；
3. 审核：准备类目、隐私协议、测试账号、不涉及未声明能力；
4. 发布：高峰慎发；准备回滚到上一版本；服务端兼容旧前端。

十年经验：小程序发版**不可像 H5 那样随时刷 CDN**，前端要更依赖服务端开关与配置下发做紧急止血。
:::

**追问：**
1. 审核被拒常见原因你怎么预审？
2. 多环境（dev/stage/prod）appid 与接口域名如何管理？
3. 热修复没有时，如何用配置中心关功能？

**踩坑：** 体验版连着开发者机器代理，一提审就挂——提审包必须指向可公网访问的合法域名。

### Q9. uni-app / 小程序性能优化，你会抓哪些优先级最高的点？

**考察点：** setData、列表、渲染层、启动

::: details 参考答案
优先级：
1. **启动**：主包体积、首屏请求并行、减少同步存储读写、分包；
2. **setData / 更新**：少传大数据、路径更新、合并更新；Vue/uni 层避免无意义整树刷新；
3. **列表**：分页、回收、图片懒加载、长列表优化方案；
4. **渲染**：减少复杂 CSS、大图、WXML 过深；
5. **逻辑**：避免在 `onPageScroll` 高频 setData；防抖；

工具：性能面板、真机 Trace、体验评分。口述别背清单，讲你做过的一次「从 60 分到 90 分」归因。
:::

**追问：**
1. 为什么开发者工具流畅、真机卡？
2. 一次性 `setData` 全量列表 1000 条会怎样？
3. 骨架屏对「感知性能」与真实 TTI 分别是什么？

**踩坑：** `onPageScroll` 里做复杂计算 + 改一堆响应式数据——滚动掉帧，用户以为机型问题。

### Q10. uni-app 里用 npm 包与小程序插件，你怎么选型与排坑？

**考察点：** 构建转译、包体积、插件权限、兼容

::: details 参考答案
npm：优先选有小程序 / uni 适配说明的库；注意：
- 依赖 Node/DOM/BOM 的包不能直接用；
- 体积进主包风险——按需、替换轻量实现；
- 部分库要放在 `uni_modules` 或按官方方式构建。

小程序插件：适合地图、客服、登录等官方 / 第三方能力，但有**权限、跳转、版本、审核**约束；插件是黑盒，调试难，要评估退出成本。

原则：能 API 搞定别引插件；能小模块别引全家桶；锁定版本并在发版清单里回归。
:::

**追问：**
1. 遇到只支持微信、不支持其他小程序端的 npm，多端怎么办？
2. `uni_modules` 与自建适配层如何分工？
3. 插件突然升级导致线上异常，你怎么防御？

**踩坑：** 为了一个 `dayjs` 插件链引入巨型 i18n 语言包进主包——体积问题常来自「顺手安装」。

### Q11. Vue3 组合式 API 在 uni-app 里有哪些特有坑？

**考察点：** 生命周期写法、响应式、跨端 DOM、Pinia

::: details 参考答案
常见坑：
1. **生命周期**：要用 uni 提供的 `onLoad`/`onShow` 等，在 `setup` 中同步注册，不能异步延后注册；
2. **取组件实例 / 节点**：小程序侧是 `selectComponent` / `createSelectorQuery` 思路，不是随便 `document`；
3. **响应式大对象**：往页面堆巨大 reactive 再整页下发，性能差——列表数据要克制；
4. **跨端 API**：`window`/`localStorage` 在 MP 不存在，要用 `uni.*`，封装时类型与运行时双保险；
5. **Pinia**：可用，但持久化插件要选支持小程序 storage 的；注意启动时恢复时序与登录态；
6. **条件编译 + script setup**：可读性差，更要拆文件。

口述：Vue3 语法糖香，但不等于浏览器 Vue；**端能力边界仍在**。
:::

**追问：**
1. `ref` 在模板里用，和小程序编译到 WXML 的限制有何关系？
2. 组合式复用 composable 里直接调 `uni.request`，测试如何做？
3. Vue2 Options 老项目迁 Vue3 uni，你优先迁什么？

**踩坑：** 在 `setup` 的 `setTimeout` 里再注册 `onShow`——注册无效，回调永远不跑。

### Q12. 微信小程序与 H5 在同一 uni 项目里，关键差异你怎么对面试官讲？

**考察点：** 路由、存储、BOM、登录、样式、跳转

::: details 参考答案
差异清单（口述挑重点）：
1. **运行时**：小程序双线程 + 原生组件；H5 是浏览器 DOM；
2. **路由**：`pages.json` 栈式导航 vs H5 history/hash；返回、传参、拦截不同；
3. **登录**：小程序 code；H5 OAuth / 账号密码 / 短信；
4. **能力**：支付、分享、扫码、订阅消息——端能力矩阵不同，要适配层；
5. **样式**：rpx vs 浏览器 CSS；部分选择器 / 定位差异；
6. **SEO / 链接**：H5 可分享 URL；小程序靠小程序码 / 路径 + query；
7. **发版**：H5 即时；小程序审核。

架构结论：业务领域模型共享，**端适配与页面壳**分流；强差异页面允许 fork，别为了「一套代码」牺牲两端体验。
:::

**追问：**
1. 什么指标下你会建议拆成「小程序仓库 + H5 仓库」？
2. 分享到微信好友的落地页如何同时服务小程序与 H5？
3. Cookie 会话在 H5 有、小程序无，鉴权统一成什么？

**踩坑：** 在所谓「通用页面」里直接用 `window.location`——小程序端运行时报错或构建告警被忽略。

### Q13. 隐私协议与《用户隐私保护指引》在工程上怎么落地？

**考察点：** 隐私弹窗、`wx.requirePrivacyAuthorize`、声明与代码一致

::: details 参考答案
合规是发版门槛：
1. 后台配置隐私指引，声明实际用到的能力（定位、相册等）；
2. 前端在收集前展示协议，未同意不调对应 API；
3. 使用官方隐私授权能力（如需）与按钮组件；
4. 日志 / 埋点避免未同意前上传敏感字段；
5. 第三方 SDK 同步合规，不能「自己弹了协议但 SDK 先采」。

工程化：把「隐私同意状态」放全局，能力调用统一经网关函数检查。审核同学最爱抓「声明与调用不一致」。
:::

**追问：**
1. 用户撤回同意后，本地缓存与个性化推荐怎么清？
2. 隐私弹窗与登录弹窗的产品顺序如何定？
3. App 端与小程序端隐私法规差异，uni 层如何抽象？

**踩坑：** 为了过审做「假弹窗」，真机仍直接调定位——审核加强或用户投诉后翻车。

### Q14. 分享与 `open-type`（share、getPhoneNumber 等）你怎么用得稳？

**考察点：** `onShareAppMessage`、按钮 open-type、手机号、卡片参数

::: details 参考答案
分享：
- 页面配置 / `onShareAppMessage`（与时间线分享等）返回 title、path、imageUrl；
- path 要带齐还原上下文的 query（商品 id、邀请人）；注意长度与编码；
- 分享图：尺寸与CDN，别太大；可域需配置。

`open-type`：
- `getPhoneNumber`：需用户点击按钮触发，拿 encryptedData / code 走服务端解密（跟现行文档）；
- `share`：引导分享按钮；
- 其他能力同理——**必须用户手势**，不能静默。

安全：手机号、分享裂变奖励以后端校验防刷；前端只负责触发与展示。
:::

**追问：**
1. 分享到朋友圈与分享给好友的能力与限制差异？
2. 被分享人打开后「未登录」如何接登录再回跳原 path？
3. `open-type` 失败或用户取消，UI 如何反馈？

**踩坑：** 分享 path 写成开发版页面路径或漏了 query——好友打开落首页，转化归零还不好查。

### Q15. 小程序本地存储限制与缓存策略，你会怎么设计？

**考察点：** storage 上限、异步 API、清理策略、与内存

::: details 参考答案
`uni.setStorage` 有大小限制（数量与单 key / 总容量，以现行文档为准，量级通常有限）。策略：
1. **只存必要**：token、用户偏好、少量草稿；大方图、长列表别塞 storage；
2. **异步优先**：避免同步 API 卡线程；
3. **版本化 key** + 过期时间；升级时迁移 / 清理；
4. **超限处理**：捕获失败、LRU 淘汰、降级仅内存；
5. **敏感数据**：加密或少存，退出登录清理。

与接口缓存：用内存 + 时效；冷启动再水合。口述强调 storage 不是 Mini IndexedDB。
:::

**追问：**
1. 存储满了导致登录态写失败，用户会看到什么？你如何兜底？
2. 多账号切换如何隔离 storage？
3. 和大文件缓存（用户目录）如何分工？

**踩坑：** 把整个 Vuex/Pinia 快照 JSON 塞进 storage——易超限，且恢复时造成启动巨卡。

### D1. 微信小程序逻辑层与渲染层通信为什么会成为性能瓶颈？

::: details 参考答案
#### 基础结论
微信小程序通常由逻辑层和渲染层协作，数据更新会经过组件框架与线程通信；因此更新频率、数据量和组件 Shadow 树规模都会影响性能。该结论针对微信小程序运行机制，不能直接泛化到所有 uni-app 目标平台。

#### 原理深挖
`setData` 或编译后的等价更新会触发数据序列化、传输、diff 与渲染。官方当前建议只传界面需要且真正变化的数据，合并连续更新，避免在滚动回调中高频调用；性能审计中的频率与体积阈值是检查口径，不是达到阈值就必然流畅。Skyline、glass-easel 等新引擎的路径又与传统 WebView/exparser 不完全相同。

#### 工程场景
先用微信开发者工具性能面板、真机 Trace 和更新性能监听定位热组件。列表按页与可视区域裁剪，非渲染数据留在普通变量或领域层；高频进度按帧或时间预算合并，路径更新只发送变化字段。uni-app 层还要观察响应式对象被编译后实际产生的更新，而非只看源码写没写 `setData`。

#### 反例 / 踩坑
把完整接口响应、日志对象和 1000 行列表都挂进页面响应式状态，会放大通信与 diff。机械把 20 次小更新合成一次超大更新，也可能造成单次长卡顿；开发者工具流畅不能替代低端真机证据。

#### 资深回答模板
「我把小程序更新看成逻辑层到渲染层的数据管道，优化目标是少更新、少传、缩小组件树。先用真机工具看实际更新，再做字段级合并和列表裁剪；同时说明这是微信端机制，多端结果必须分别验证。」

#### 追问链
1. uni-app 响应式赋值如何映射为微信端更新，如何观察产物？
2. 进度条每 10 ms 更新一次时，如何保证视觉流畅又不淹没通信？
3. Skyline 下哪些旧经验仍成立，哪些必须重新测量？
:::

### D2. 分包、预下载与主包治理如何以首开和二跳指标共同决策？

::: details 参考答案
#### 基础结论
分包不是只为过体积门槛，而是控制首开关键路径。微信分包预下载通过配置触发，当前官方文档说明可按页面、网络和包名配置，并有预下载额度；实际限制与基础库支持应在发版时再次核对。

#### 原理深挖
页面移入分包不代表依赖自动离开主包：主包入口、公共组件或全局初始化一旦引用，依赖仍可能回流。普通分包依赖主包运行环境，独立分包则有更强隔离；uni-app Vue 3 独立分包还存在全局插件、store、i18n、App 样式和 root 外依赖不能直接复用等限制。

#### 工程场景
先画冷启动依赖图，首页、登录和最小公共运行时留主包，低频页面与专属资源放业务分包。用构建产物分析比较主包、各分包和重复依赖；只对高概率二跳预下载，并按 Wi-Fi/全网络策略衡量流量。CI 设体积预算和余量告警，体验版真机测冷启动与首次进入分包。

#### 反例 / 踩坑
为了去重把所有依赖提到主包，会让首开变慢；把每个页面拆一个分包则增加管理与加载开销。预下载全部分包会抢首页网络和用户流量，独立分包却继续依赖主包全局注册，会直接缺能力。

#### 资深回答模板
「我用首开、二跳概率和依赖图决定分包，不只看能否构建通过。主包保持最小闭包，预下载只覆盖高概率路径；独立分包按独立运行环境设计，CI 看体积预算，体验版看真机时延和流量。」

#### 追问链
1. 公共依赖在多个分包重复与提升主包之间如何权衡？
2. 预下载未发生时，如何从日志与基础库版本定位？
3. 首页改版后，如何防止主包预算持续回涨？
:::

### D3. uni-app 多端条件编译、生命周期与能力适配如何避免语义泄漏？

::: details 参考答案
#### 基础结论
多端共享应停在领域模型和稳定业务流程，平台能力通过适配器暴露。条件编译只选择实现，不应让页面到处感知平台；Vue 生命周期、uni-app 页面生命周期和各宿主原生生命周期必须分层说明。

#### 原理深挖
`onLoad`、`onShow` 是页面语义，`onMounted` 是 Vue 组件语义，触发顺序和可用上下文不能凭浏览器经验推断。组合式 API 的页面钩子需在 `setup` 或 `<script setup>` 中同步注册，并从 `@dcloudio/uni-app` 使用；不同平台支持矩阵与最低版本会变化，`MP` 也不等于每个小程序宿主行为一致。

#### 工程场景
定义 `PlatformPort`：登录、支付、分享、存储、文件和路由各有能力检测、标准错误与降级。平台实现文件内部使用条件编译，页面只调用接口。测试分三层：领域层单测、适配器契约测试、微信/H5/App 关键路径真机清单；生命周期副作用有幂等、脏标记和清理。

#### 反例 / 踩坑
在 composable 顶层直接读 `window`、把 `onShow` 延后注册，都会让部分端失效。用一个 `#ifdef MP` 分支假设微信、支付宝、抖音小程序 API 与审核规则相同，是典型错误泛化。

#### 资深回答模板
「我共享业务语义，不假设平台机制相同。页面钩子、Vue 钩子和宿主能力分层，条件编译收敛在适配器；每个能力有检测和降级，并按目标端做契约与真机验证。」

#### 追问链
1. `onShow` 高频刷新如何用脏标记避免重复请求？
2. 强差异页面何时应该 fork，而不是继续抽象？
3. 新增支付宝小程序端时，如何快速发现微信语义泄漏？
:::

### D4. 小程序登录、Session 续期与隐私授权如何组成不越权的状态机？

::: details 参考答案
#### 基础结论
`wx.login` 的 code 是短时一次性交换凭据，不是 Session；后端换取平台身份后签发业务登录态。隐私同意、手机号等能力授权与登录认证是不同状态，不能因用户登录就默认获得隐私授权。

#### 原理深挖
并发 401 应由 single-flight 刷新：首个请求换票，其他等待同一 Promise，失败后统一退出并防无限重放。隐私侧按现行微信文档查询是否需要授权、在调用相关接口前完成同意流程；官方弹窗、`onNeedPrivacyAuthorization` 和项目自定义流程要按当前基础库与后台配置核对，不能沿用旧版 `getUserInfo` 经验。

#### 工程场景
状态机区分 anonymous、authenticating、authenticated、refreshing、expired，以及 privacy unknown/required/agreed/denied。请求队列只重放可安全重放的操作；Token、缓存和草稿按业务 userId 隔离，切账号清理。隐私网关在定位、相册、SDK 初始化前检查声明与同意，并记录版本。

#### 反例 / 踩坑
每次 `onShow` 都调用 login 会浪费配额并制造竞态；把 code 存 storage 重复使用必然失败。SDK 在隐私同意前先采设备信息，即使页面后来弹协议，也不构成合规。

#### 资深回答模板
「我把平台换票、业务 Session、能力授权和隐私同意拆成四层状态。401 单飞续期且只重放安全请求；隐私能力统一走网关，在现行微信规则下先声明和同意再调用，切账号彻底隔离缓存。」

#### 追问链
1. 刷新 Token 期间用户主动退出，等待中的请求如何终止？
2. 用户撤回隐私同意后，已缓存数据与 SDK 如何处理？
3. 小程序、H5 和 App 登录如何映射到统一账号体系？
:::

### D5. rpx、原生组件与长列表优化为什么必须以微信真机渲染为准？

#### 反例 / 踩坑

#### 资深回答模板
「我把 rpx 当设计尺寸映射，不当跨端一致性保证。原生组件按当前基础库和渲染引擎做能力矩阵，长列表同时控制数据、节点和图片；所有层级与性能结论以目标端低端真机为准。」

### D6. npm、插件与小程序发布如何建立可回滚的供应链？

::: details 参考答案
#### 基础结论
npm 包解决代码复用，小程序插件提供宿主能力，两者的运行边界、审核和升级风险不同。选型要检查 DOM/Node 依赖、目标端兼容、包体积、维护状态、权限与退出成本；发布必须锁版本并保留服务端兼容和功能开关。

#### 原理深挖
能在 Vite/H5 构建的包不代表能在小程序 JS 环境运行；动态代码、BOM、原生二进制和条件 exports 都可能出问题。插件由独立主体和版本交付，storage 等能力可能隔离，升级还可能影响审核。小程序客户端存在版本滞留，服务端不能只兼容最新审核版。

#### 工程场景
引入前做许可证、漏洞、体积和多端冒烟；锁文件入库，构建产物生成依赖清单。体验版验证真实域名、支付、隐私和插件能力；灰度阶段按客户端版本观测错误率。紧急情况通过服务端兼容、配置开关关闭入口，并准备回退上一线上版本。

#### 反例 / 踩坑
为一个工具函数引入依赖树，可能把语言包或 polyfill 带进主包。使用 `latest` 插件版本、只在开发者工具测试、后端上线后立即删除旧字段，都会让已发布旧客户端无法恢复。

#### 资深回答模板
「我把 npm 和插件都纳入供应链：先查运行时与目标端，再看体积、安全和退出成本。版本固定、体验版真机验收、服务端向后兼容；上线靠灰度和开关止血，不能假设小程序像 H5 一样即时覆盖。」

#### 追问链
1. 插件主体故障或下架时，业务如何降级？

### D7. 支付、分享与 `open-type` 如何确保用户手势、结果确认和防刷闭环？

#### 原理深挖

#### 工程场景
支付状态机包含 created、paying、unknown、paid、closed；前端请求带业务幂等键，取消与网络异常都进入可查单状态。分享 path 使用白名单参数与服务端短码，落地后校验邀请关系。能力调用前做基础库检测，失败按用户取消、版本不支持、配置错误和系统错误分类反馈。

#### 反例 / 踩坑
支付 success 立刻发货、fail 立刻关单，都会在异步通知或网络抖动下出错。用普通按钮模拟手机号授权、静默触发 `open-type`、依据前端分享回调发奖励，都不可靠且可能违规。

#### 资深回答模板
「我把平台回调当交互结果，不当业务最终真相。支付由服务端下单、通知和查单闭环；手机号凭据服务端核验；分享奖励按服务端事件防刷。前端只在用户手势内调用，并按能力与错误类型降级。」

### D8. Storage、WebView 与主包之间的数据边界如何治理？

::: details 参考答案
#### 基础结论
微信小程序当前官方文档说明：同一微信用户、同一小程序的 Storage 上限为 10 MB，并按用户与小程序隔离；它适合少量状态，不是数据库。`web-view` 内网页有独立浏览器存储与安全边界，不能假设能直接共享小程序 Storage 或登录态。

#### 原理深挖
同步 Storage 会占用逻辑线程，冷启动集中读取会拉长启动；大对象序列化也会增加内存峰值。WebView 页面运行在网页上下文，通信与可调用能力受平台组件、业务域名和基础库限制；从 H5 跳转、传 Token 或回传消息都必须按当前微信文档核对，不能沿用 App WebView 的任意 Bridge 设计。

#### 工程场景
缓存 key 包含 userId、schemaVersion 和 expiresAt，建立容量预算与 LRU 清理；Token、偏好、草稿分命名空间，退出登录只清对应用户。启动只水合关键小对象，其余按需异步读取。小程序给 H5 使用一次性授权码换取 Web Session，URL 不放长期 Token；WebView 页面进入、退出和消息都做来源、参数与 trace 记录。

#### 反例 / 踩坑
持久化整个 Pinia 树会拖慢启动并快速占满容量；`clearStorage` 可能误删其他业务缓存。把业务 Token 拼进 WebView URL 会进入日志、历史或 Referrer；把 H5 静态资源塞进主包也不会让 WebView 自动离线可用。

#### 资深回答模板
「我给 Storage 做用户、版本、时效和容量治理，只在启动读取关键数据。WebView 是独立网页安全域，用一次性码换 Session，不传长期 URL Token；通信和能力按微信现行文档实现，并与主包体积、离线策略分开设计。」
