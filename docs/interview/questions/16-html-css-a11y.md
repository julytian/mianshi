# HTML、CSS 与可访问性面试题库

> **怎么用：** 普通题按「平台语义 → CSS / 无障碍机制 → 工程边界 → 验证」口述 1～2 分钟；深层题按「结论 → 原理 → 方案 → 失败模式 → 验证」展开。优先使用浏览器原生 HTML、CSS 和交互语义，ARIA 只补充语义，不负责焦点、键盘、状态或行为。

> **标准边界：** 可访问性以 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 与 [WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/) 当前官方口径为基线。WCAG 是可测试的成功准则，APG 是实现复合组件的设计模式，不应把示例代码当唯一实现。HTML / CSS 新能力先查 Baseline、MDN 和目标浏览器矩阵，再用特性查询、回退样式与真机验证做渐进增强。

> **模块边界：** 本模块讨论 HTML 语义、CSS 布局与可访问交互；资源加载性能的系统治理见性能模块，组件框架封装与前端架构见 [前端架构题库](/interview/questions/14-frontend-architecture)。设计稿不是规范，视觉一致也不代表语义、键盘和辅助技术体验一致。

## 一、HTML 语义与内容

### Q1. 语义化 HTML 和文档结构应该怎样设计？

**考察点：** 原生语义、Landmark、标题层级、内容模型、验证方法

::: details 参考答案

语义化的目标是让浏览器、搜索引擎和辅助技术理解内容关系，而不是把标签名当 CSS 钩子。页面骨架优先使用 `header`、`nav`、`main`、`aside`、`footer` 等 landmark；操作用 `button`，导航用 `a`，列表和表格只用于相应数据关系。原生元素自带角色、状态、键盘行为和表单能力，通常比 `div` 加 ARIA 更稳。

标题要表达内容层级并保持顺序可理解，不能只按字号选择 `h1`～`h6`。页面有一个清晰主标题通常是良好实践，但「只能有一个 `h1`」不是 WCAG 的硬性成功准则；真正要验证的是标题是否准确描述内容、层级是否帮助导航，以及页面是否有可识别的主区域和名称。多个同类 landmark 还应通过可访问名称区分。

组件化不能切断文档语义。卡片组件不能擅自固定标题级别，虚拟列表不能丢掉集合关系，SSR 与客户端渲染后的 DOM 也应一致。验证时先关闭 CSS 阅读 DOM 顺序，再看浏览器 Accessibility Tree，用仅键盘和至少一种屏幕阅读器检查 landmark、标题列表与控件名称；HTML 校验器和 lint 只能发现一部分结构错误。

:::

**追问：** 设计系统中的 Card 标题应该固定为 `h3` 吗？

::: details 追问参考答案

不应固定。Card 不知道自己被放在页面哪一层，固定 `h3` 可能跳级或破坏宿主文档大纲。可让调用方传入标题元素或 heading level，并限制合法范围；若标题只是视觉标签而非章节标题，就用普通文本。测试应在实际组合页面检查标题导航，而不是只做组件快照。若 API 允许任意标签，还要避免调用方把交互元素或不合法嵌套传进去。

:::

### Q2. 可访问表单怎样处理 label、错误提示和自动填充？

**考察点：** 表单名称、错误关联、状态通知、autocomplete、原生校验边界

::: details 参考答案

每个输入控件都要有稳定、可感知的标签。首选 `<label for>` 与控件 `id` 显式关联，或在简单结构中用 `label` 包裹；`placeholder` 会消失、对比度常较低，不能代替标签。分组选择使用 `fieldset` / `legend`，必填、格式和单位要在用户输入前可获得。可访问名称回答「这是什么控件」，补充说明和错误属于可访问描述，不能把整段帮助文本都塞进名称造成冗长重复。

提交失败后既要有页面级错误摘要，也要在字段旁给出具体、可修复的信息，并通过 `aria-describedby` 关联；字段状态可用 `aria-invalid="true"`。动态错误可用克制的 live region 通知，但不能每次按键都打断。焦点通常移到错误摘要或第一个错误字段，并保留用户已输入内容。颜色、图标不能是唯一错误信号。

自动填充依赖正确的 `name`、`type` 与 `autocomplete` token，例如 `email`、`current-password`、`new-password`，不要通过随机字段名或禁用粘贴阻碍密码管理器。原生约束验证可作为基础能力，但文案、时机和跨浏览器表现有限；业务规则仍需服务端验证。用真实浏览器自动填充、键盘、缩放和屏幕阅读器验证，自动化只检查关联是否存在，不能证明提示是否好懂。

:::

**追问：** `aria-label`、`aria-labelledby` 和 `aria-describedby` 应怎样区分？

::: details 追问参考答案

`aria-label` 直接提供名称，适合没有可见文本的少数控件；`aria-labelledby` 引用页面上已有文本作为名称，通常能保持视觉与朗读一致；`aria-describedby` 提供名称之外的帮助、格式或错误描述。名称来源存在优先级，随意叠加可能覆盖原生 `label` 或产生重复朗读。应在 Accessibility Tree 核对最终 computed name 与 description，而不是看到属性存在就算通过。

:::

### Q3. 响应式图片、`srcset`、`sizes` 和媒体内容怎样设计？

**考察点：** 图片候选、艺术指导、替代文本、媒体字幕、失败回退

::: details 参考答案

内容图片用 `img`，装饰图片使用空 `alt=""` 并避免产生多余可访问名称。`alt` 描述图片在当前语境中的作用，不是文件名或机械复述附近文字；功能图片的替代文本应表达操作结果。复杂图表需要邻近摘要和可访问的数据表或详情，不能指望一个超长 `alt` 承载全部信息。CSS 背景图适合纯装饰，不应承载唯一内容。

`srcset` 的宽度描述符配合 `sizes` 告诉浏览器图片在不同条件下的预期槽位宽度，由浏览器结合 DPR、网络与缓存选候选；`sizes` 写错会下载过大或模糊资源。需要裁切构图变化时，用 `picture` / `source` 做艺术指导；只换格式时要保留可靠回退。图片应给出 `width` / `height` 或 `aspect-ratio` 预留空间，懒加载首屏资源要谨慎，资源失败还要保留替代文本和可理解布局。

视频要按内容提供字幕、文字稿，必要时提供音频描述；音频不能自动播放并困住用户。原生 `video` / `audio` 控件是起点，但要在目标平台检查键盘、字幕选择和触摸命中区。验证包括 Network 中实际候选、不同 DPR / viewport、禁图与加载失败、屏幕阅读器朗读，以及字幕准确度人工抽查。

:::

**追问：** `sizes="100vw"` 为什么经常导致列表图片浪费流量？

::: details 追问参考答案

它告诉浏览器图片槽位约等于整个视口宽度；如果图片实际只占两列网格的一半或受最大宽度约束，浏览器会选取过大的候选。应按真实布局写媒体条件与槽位，例如窄屏接近 `100vw`、宽屏接近容器的一部分，并考虑间距。用响应式模式不足以证明正确，还要清缓存观察请求资源的固有宽度和传输量；容器查询控制布局时，`sizes` 的表达能力与资源选择时机也要单独评估。

:::

## 二、CSS 机制与布局

### Q4. CSS 层叠、优先级、继承和 cascade layers 如何共同决定最终样式？

**考察点：** Cascade Origin、层叠层、Specificity、作用域治理、兼容回退

::: details 参考答案

最终值不是只比较选择器优先级。应先理解来源与重要性、层叠上下文中的 layer 顺序、选择器 specificity、作用域接近度和源码顺序，再经过继承与初始值形成计算值。`!important` 会改变同一来源中的优先级，并且层叠层对普通声明和 important 声明的排序方向不同，所以不能用「多写一个类」解释所有覆盖问题。

`@layer reset, base, components, utilities, overrides;` 可以提前声明稳定顺序，让低 specificity 的工具类按架构意图覆盖组件，而不靠 ID、深层嵌套或不断追加 `!important`。第三方 CSS 可放入较低优先级层；`:where()` 把自身 specificity 置零，适合可覆盖的基础规则，`:is()` / `:not()` 则会采用参数中最高 specificity。自定义属性通常继承，但其 token 流在使用点解析，回退值也只有在变量无效或缺失时生效。

工程上用 layer 管大边界，用类或属性管组件状态，用 CSS Modules、scoped CSS 或命名约定管作用域。兼容旧浏览器时，不能把关键样式只放进不被识别的 `@layer` 块后假设会降级；应依据支持矩阵决定是否经构建工具降级，或先提供无层基础样式再增强。通过 DevTools 的 Computed / Cascade 面板、目标浏览器截图和最小复现定位覆盖来源。

:::

**追问：** 为什么把第三方样式放进低优先级 layer，常比增加选择器权重更可维护？

::: details 追问参考答案

layer 在架构层明确「谁可覆盖谁」，不需要知道第三方选择器有几层，也不会把权重竞赛传给后续维护者。项目规则可以保持单类选择器，主题和局部修正仍有稳定出口。但迁移时必须一次性梳理未分层规则，因为未分层的普通 author 样式通常高于已分层普通样式；还要测试第三方 `!important` 和运行时注入顺序，不能只改一条声明后宣布治理完成。

:::

### Q5. BFC、包含块和格式化上下文分别解决什么问题？

**考察点：** BFC、Containing Block、Margin Collapsing、定位参照、诊断

::: details 参考答案

块级格式化上下文（BFC）是一套块布局环境：内部浮动参与其高度计算，外部浮动不会侵入其内部，且它会影响块级盒子的排列与 margin 折叠。常见创建方式包括 `display: flow-root`、非 `visible` / `clip` 的 overflow、浮动、绝对定位、inline-block，以及部分 flex / grid 项。为了清除浮动，`flow-root` 比借用 `overflow: hidden` 更能表达意图，也不会意外裁剪阴影或内容。

包含块决定百分比尺寸和定位偏移的参照。普通流、绝对定位、固定定位的包含块规则不同；`transform`、`filter`、`perspective`、某些 `contain` 等属性还可能为绝对或固定定位后代建立新的包含块，使原本相对 viewport 的浮层变成相对局部祖先。格式化上下文则不止 BFC，还包括 inline、flex、grid 等，各自决定子项参与布局的算法。

失败模式通常来自把三个概念混为一谈：用 `overflow` 修 margin 却裁掉弹层，用 `position: relative` 误以为创建 BFC，或父级 transform 导致 `position: fixed` 不再贴视口。验证时在 DevTools 查看盒模型、布局与 containing block，高亮滚动容器；用去掉可疑属性的最小复现确定是谁改变了格式化或定位参照。

:::

**追问：** `overflow: hidden` 与 `display: flow-root` 创建 BFC 时有什么工程差异？

::: details 追问参考答案

两者都可能形成 BFC，但语义和副作用不同。`flow-root` 明确表示建立独立块格式化上下文，通常不会裁剪溢出；`overflow: hidden` 同时改变溢出处理，可能裁剪阴影、焦点环、粘性定位或下拉内容。若需求只是包含浮动、隔离外部浮动，优先 `flow-root`；若确实要裁剪，还要检查焦点可见性与弹层 portal。旧环境不支持时可把 overflow 方案放在 `@supports` 外作为受控回退。

:::

### Q6. Flexbox 适合什么布局，常见边界和失败模式是什么？

**考察点：** 一维布局、Flex Sizing、最小尺寸、换行、可访问顺序

::: details 参考答案

Flexbox 面向一维主轴布局，适合工具栏、导航、卡片内部对齐和未知尺寸项的空间分配。布局过程会结合 `flex-basis`、grow、shrink、可用空间以及项的最小最大尺寸；`flex: 1` 不是简单的「各占一半」，其 basis 与内容最小尺寸会影响结果。文本项常因默认 `min-width: auto` 不肯收缩，需要在明确允许截断或换行时设置 `min-inline-size: 0`。

多行 `flex-wrap` 的每一行独立分配空间，不擅长跨行严格对齐，二维卡片矩阵通常 Grid 更合适。自动 margin 可吸收主轴剩余空间；`gap` 比对子项写 margin 更少受首尾和书写方向影响。不能用 `order` 或 `row-reverse` 只改变视觉顺序却保留不合理 DOM、Tab 和朗读顺序；视觉与操作顺序不一致会造成认知和键盘问题。

工程边界包括长文本、本地化、200% 文本放大、320 CSS px 窄视口、嵌套滚动和浏览器旧版本。测试不要只用短英文假数据，应放入长单词、中文、RTL、缺失图标和动态按钮，并在 DevTools Flex overlay 中检查尺寸约束。若依赖较新的 gap 或逻辑属性，要按支持矩阵提供 margin 或物理属性回退，但避免两套规则同时生效。

:::

**追问：** Flex 子项设置了 `overflow: hidden` 后截断正常，为什么仍可能不是好修复？

::: details 追问参考答案

它会让子项可收缩，但也把「尺寸约束」和「裁剪策略」绑在一起，可能裁掉焦点环、浮层、徽标或用户放大后的内容。若目标只是允许文本区域缩小，应优先在相应 flex item 上设置 `min-inline-size: 0`，再由具体文本节点决定换行、`text-overflow` 或展开机制。截断的信息还必须有可访问的获取方式，`title` 不是稳定的键盘和触摸方案。

:::

### Q7. Grid 适合什么布局，如何处理隐式轨道、溢出和降级？

**考察点：** 二维布局、Track Sizing、显式与隐式网格、Subgrid、渐进增强

::: details 参考答案

Grid 面向二维轨道，适合页面区域、表单对齐、卡片矩阵和需要跨行列约束的布局。`fr` 分配的是扣除固定尺寸和 gap 后的剩余空间，但轨道默认最小值受内容影响；`1fr` 可能被长内容撑开，常用 `minmax(0, 1fr)` 明确允许收缩。`repeat(auto-fit, minmax(...))` 可形成自适应列，但最小值要能容纳放大文本，不能只按设计稿卡片宽度拍脑袋。

显式网格由模板定义，超出放置范围的项会进入隐式轨道，其尺寸由 `grid-auto-*` 决定。自动放置和 `dense` 能填洞，但可能让视觉顺序偏离 DOM 顺序；交互内容不应为视觉紧凑牺牲朗读与键盘顺序。`subgrid` 适合让嵌套卡片继承父轨道对齐，但支持边界和组件耦合要评估。

渐进增强可先提供单列普通流或 Flex 回退，再在 `@supports (display: grid)` 中升级；现代目标矩阵普遍支持 Grid 时，不必维护复杂等价旧布局。验证要覆盖真实内容上限、动态增删、RTL、缩放和窄视口，并检查是否出现非必要二维滚动。数据表等本质需要二维浏览的内容可有例外，但要提供表头关联和可操作的滚动区域。

:::

**追问：** `auto-fill` 和 `auto-fit` 的区别如何口述？

::: details 追问参考答案

两者都会按容器能容纳的数量重复轨道。`auto-fill` 会保留当前可容纳但没有内容占据的空轨道；`auto-fit` 会把空轨道折叠，已有轨道可扩展填满空间。项目中不要靠背定义选择，应放入 1 个、临界数量和超量卡片观察布局，再结合固定卡宽还是填满容器的产品意图决定。旧浏览器回退到单列或固定列即可，不必模拟每个细节。

:::

### Q8. 定位、`z-index` 和 stacking context 应怎样分析？

**考察点：** 定位方案、层叠上下文、Top Layer、浮层治理、诊断方法

::: details 参考答案

优先让普通流、Flex 和 Grid 完成结构布局；相对定位适合建立局部定位参照或轻微偏移，绝对定位适合不占流的局部装饰和锚定元素，固定定位面向视口级 UI，sticky 则受最近滚动容器和 inset 约束。用绝对定位拼主布局会在文本放大、本地化和内容变化时迅速失效。

`z-index` 只在层叠规则允许的范围内比较。根元素、定位元素配非 auto `z-index`、`opacity < 1`、`transform`、`filter`、`isolation: isolate`、部分 `contain` 等都会创建 stacking context；子元素的巨大 `z-index` 也不能逃出父上下文与外部兄弟竞争。原生 `dialog.showModal()`、Popover 等可进入 top layer，通常比全局堆叠数字更可靠，但语义、焦点与兼容回退仍需分别实现。

工程上建立少量语义层级 Token，例如 base、sticky、overlay、toast，而不是不断加到 999999；组件内部可用 `isolation` 限定竞争。弹层要同时考虑 portal 宿主、滚动锁定、包含块、裁剪祖先和 top layer。排障时用 DevTools Layers / stacking context 信息，从目标元素逐级检查是谁创建上下文或裁剪，不能只反复提高 `z-index`。

:::

**追问：** 为什么 `position: fixed` 的浮层可能跟着局部容器滚动或被裁剪？

::: details 追问参考答案

某些祖先的 `transform`、`filter`、`perspective` 或 `contain` 会为 fixed 后代建立新的包含块，使它不再以初始包含块为参照；祖先的 overflow 还可能裁剪。修复方向是移除无意的上下文、把浮层 portal 到合适根节点，或使用 top layer 的原生能力。迁移到 portal 后要重新验证样式继承、主题变量、事件边界、焦点恢复和 SSR 挂载，不能把定位问题换成可访问性问题。

:::

### Q9. 响应式设计、容器查询和逻辑属性如何配合？

**考察点：** 内容驱动断点、Container Query、Logical Properties、Reflow、降级

::: details 参考答案

媒体查询描述 viewport 或用户环境，容器查询让组件依据其容器可用尺寸或样式状态调整，更适合同一组件同时出现在主栏、侧栏和弹窗。先用普通流、`min()` / `max()` / `clamp()`、Flex / Grid 做内在响应，再在内容真正失效的点加断点，不要照设备型号维护一串像素值。

尺寸容器查询需要祖先建立合适的 `container-type`，这会带来 containment 行为，不能随手加在任意节点。为组件命名容器可避免嵌套时命中错误祖先。逻辑属性如 `margin-inline`、`padding-block`、`inset-inline-start` 能随书写模式和方向映射，减少 RTL 覆盖；但图标方向、数字、代码与混合双向文本仍需按语义处理，不能只翻转整个页面。

可访问响应式还要满足文本通过 200% 浏览器缩放或等效方式放大时不丢内容或功能，并在水平书写内容约 320 CSS px 宽时实现回流，除非属于确需二维布局的例外；200% 缩放与 320 CSS px 回流是不同检查，不能混成一个断点。渐进增强时先提供可用的 viewport / 单列布局，再用 `@supports (container-type: inline-size)` 启用容器查询。验证真实嵌套宽度、400% 页面缩放对应的窄视口、RTL 与长文本。

:::

**追问：** 容器查询能否完全替代媒体查询？

::: details 追问参考答案

不能。组件内部布局更适合容器查询；全局导航模式、viewport 高度、输入方式、`prefers-reduced-motion`、`prefers-color-scheme` 等环境条件仍属于媒体查询。两者可分层：页面壳根据视口安排区域，组件根据容器自适应。还要保留无容器查询时可操作的基础布局，并检查 container 建立的 size containment 是否改变固有尺寸、sticky 或百分比计算。

:::

### Q10. CSS 自定义属性如何支撑主题和暗色模式？

**考察点：** Custom Properties、语义 Token、颜色方案、用户偏好、回退

::: details 参考答案

CSS 自定义属性适合在运行时继承和覆盖，设计系统应先定义语义 Token，如 `--color-text-primary`、`--surface-raised`，再映射到基础色板，而不是让业务到处引用 `--blue-500`。主题切换可在根节点或局部容器覆盖语义值；组件消费语义 Token，并为必要属性提供安全回退。自定义属性值不是静态类型，拼写错误、循环引用或在使用点无效会使声明失效，需要 lint 和视觉测试。

暗色模式可用 `prefers-color-scheme` 作为初始偏好，允许用户显式选择亮色、暗色或跟随系统，并持久化选择；用户选择应高于系统变化。设置 `color-scheme` 能让表单控件、滚动条等 UA UI 适配，但不能替代自己的颜色定义。主题不是把背景变黑，还要检查文本、边框、图标、焦点、禁用态和图表的对比与非颜色提示。

首屏要避免主题闪烁，可在渲染前注入很小的同步主题决策，SSR 环境则注意服务端不知道客户端偏好带来的水合差异。旧浏览器不支持自定义属性时，关键声明先放静态值，再放 `var()` 增强，或由构建产物提供固定主题。用系统模式、强制颜色、提高对比度、200% 缩放和不同显示器验证；对比度工具是门槛，不替代人工辨识。

:::

**追问：** 为什么不建议组件直接使用基础色板 Token？

::: details 追问参考答案

基础色板只表达色值，不表达用途。组件直接使用 `--gray-700` 后，暗色、高对比主题或品牌换肤时无法知道它是正文、边框还是禁用态，只能全局碰运气替换。语义 Token 把设计意图稳定下来，并可按主题映射到不同基础色。边界是 Token 层级不能无限膨胀：应记录所有者、弃用策略与视觉回归，找不到复用语义时才增加组件级 Token。

:::

## 三、键盘与 ARIA

### Q11. 键盘操作、焦点管理和可访问名称有哪些核心规则？

**考察点：** Tab 顺序、组合控件、焦点可见性、Accessible Name、测试

::: details 参考答案

所有功能必须可由键盘完成。普通页面中 Tab / Shift+Tab 在可聚焦元素之间移动，DOM 顺序应与视觉和任务顺序一致；不要用正 `tabindex` 人工维护顺序。原生 button 用 Enter 和 Space 激活，链接用 Enter。组合控件遵循 APG 模式：通常只有一个 Tab 停靠点，进入后用方向键在内部选项移动，Escape 关闭或撤销；不能让 Tab 穿过菜单、Tablist 或 listbox 的每个内部项。

焦点必须始终可见且不被 sticky 区域遮挡。使用 `:focus-visible` 提供清晰指示，不要无替代地 `outline: none`。DOM 删除、路由切换、弹窗关闭或异步刷新后要把焦点放到逻辑位置，避免落到 `body`。焦点样式还要在暗色、强制颜色和高缩放下检查。

可访问名称是辅助技术识别控件的主标签，来源可以是原生文本、`label`、`alt`、`aria-labelledby` 或 `aria-label`；可访问描述提供补充帮助和错误。名称应简短、稳定并与可见标签一致，尤其要让可见文本包含在名称中。验证时仅键盘走完整任务，用 Accessibility Tree 检查 computed name / description，并选择至少一种桌面和一种移动辅助技术做关键流程抽测。

:::

**追问：** Roving `tabindex` 与 `aria-activedescendant` 怎样选择？

::: details 追问参考答案

Roving `tabindex` 会把 DOM 焦点移动到当前项，适合 Toolbar、Tabs 等每项本身可聚焦的组件，浏览器会自然滚动焦点项；`aria-activedescendant` 保持 DOM 焦点在容器或输入框，通过 ID 指向活动项，适合 Combobox 等必须保留文本光标的场景。后者需要自己同步视觉状态、活动 ID 和滚动可见性。选择后应严格实现对应 APG 键盘模式，并用屏幕阅读器验证朗读，而不是同时混用两套焦点。

:::

### Q12. ARIA 的使用原则和常见误用是什么？

**考察点：** No ARIA Better、角色状态、原生优先、隐藏语义、行为实现

::: details 参考答案

第一原则是原生元素优先。能用 `button`、`input`、`select`、`details`、`dialog` 等满足需求时，不要先造 `div role`。ARIA 只改变 Accessibility Tree 中暴露的角色、名称、状态和关系，不会自动增加键盘事件、焦点管理、表单提交、约束校验或视觉样式；给 `div` 写 `role="button"` 后，开发者仍要承担 Enter / Space、禁用态和焦点的全部行为。

角色要与交互模型一致，状态必须随真实 UI 同步，例如 `aria-expanded`、`aria-selected`、`aria-checked` 不能只写初始值。不要在原生语义上添加冲突角色，不要引用不存在的 ID，不要把可聚焦内容放在 `aria-hidden="true"` 子树中。`aria-live` 要控制粒度与频率，状态更新优先考虑原生控件和现有文本关系，避免重复播报。

复杂组件应先查 APG Pattern，理解其键盘契约，再根据产品需求实现并测试；APG 示例本身也明确要求在具体浏览器与辅助技术组合中验证。静态 lint、axe 等能发现非法属性、缺名称和部分关系错误，却不能证明名称准确、状态同步、焦点顺序或任务可完成。工程门禁应把组件单测、浏览器键盘测试和人工辅助技术测试组合起来。

:::

**追问：** `aria-disabled="true"` 与原生 `disabled` 有什么差异？

::: details 追问参考答案

原生 `disabled` 会阻止控件交互，并通常移出 Tab 顺序和表单提交；`aria-disabled` 只向辅助技术声明不可用，不阻止点击、键盘或提交，也不自动改变样式。需要不可操作时优先原生 `disabled`。若产品要求不可用项仍可聚焦以解释原因，可使用 `aria-disabled`，但必须在所有事件入口拦截行为、提供说明并验证状态；链接没有通用原生 disabled，常应移除 `href` 或调整信息架构。

:::

## 四、深层场景题

### D1. 如何设计复杂后台的布局与自适应策略？

::: details 参考答案

#### 基础结论

先按信息优先级和任务流建立可读 DOM，再用 Grid 负责页面二维区域、Flex 负责区域内部排列，组件用容器查询做局部适应。基础版本必须在单列普通流中可读可操作，宽屏密度和拖拽分栏属于增强。

#### 原理深挖

后台常同时有侧栏、工具栏、筛选、表格和详情。固定像素会被本地化、200% 文本放大和 320 CSS px 窄视口击穿；过多嵌套滚动又会让 sticky、键盘与触摸失控。应使用 `minmax(0, 1fr)`、逻辑属性、内容驱动断点和明确的滚动所有者。数据表天然二维，可保留局部横向滚动，但表外页面仍应回流。

#### 工程场景

页面壳以 Grid 划分导航与主区；主区最小尺寸允许收缩。筛选在容器不足时折叠为有名称的 Disclosure，操作区保留主操作并把次要项收入 Menu。表格保持语义表格、表头关联和键盘可达，窄屏可选择局部滚动、字段优先级或独立详情，而不是用 CSS 把每一行伪装成不可理解的卡片。断点由内容溢出测试确定。

#### 反例 / 踩坑

用 `order` 把视觉主内容提前却不改 DOM，会让键盘顺序跳跃；全页 `overflow: hidden` 会破坏滚动和缩放；把所有区域都做独立滚动会产生焦点不可见。只在 1440 px 中文短数据上验收，也会漏掉长英文、RTL、浏览器缩放和软键盘问题。

#### 资深回答模板

我先确认主任务、信息优先级和必须保持二维的区域，再定义基础单列 DOM。页面用 Grid，局部用 Flex，组件按容器增强；明确唯一主滚动容器和表格例外。最后用 200% 文本、约 320 CSS px 宽、键盘、RTL、真实长数据和目标浏览器验证，不以设计稿像素对齐作为唯一验收。

:::

**追问链：**
1. 大表格在 320 CSS px 宽时一定要完全取消横向滚动吗？
2. 侧栏收起后焦点应该怎样处理？
3. 如何避免容器查询和媒体查询互相打架？

::: details 追问参考答案

**1. 大表格在 320 CSS px 宽时一定要完全取消横向滚动吗？**

不一定。WCAG Reflow 对需要二维布局才能表达或使用的内容有例外，数据表属于可能的例子，但不能把整个页面都变成二维滚动。应把横向滚动限制在有名称、可聚焦且有明确边界的表格区域，保持表头关联与关键列可辨识；还可提供列选择、摘要或详情视图。用键盘、触摸、缩放和屏幕阅读器验证滚动区是否可发现、焦点是否被遮挡。

**2. 侧栏收起后焦点应该怎样处理？**

若用户通过侧栏内按钮关闭，而该按钮随侧栏消失，焦点应移到仍存在的展开按钮或与下一步最相关的主内容标题；若外部按钮切换侧栏，焦点通常可留在该按钮。被隐藏区域不能继续保留可聚焦后代，可用原生隐藏机制或 `inert` 配合视觉状态。必须测试 CSS 动画中间态和 DOM 卸载，避免焦点短暂落到 `body`。

**3. 如何避免容器查询和媒体查询互相打架？**

先划分职责：媒体查询只控制页面级区域和用户偏好，容器查询只控制组件内部排布；规则使用同一组语义断点 Token 或注释记录触发原因，但不强求数值相同。控制层叠层与源码顺序，避免两处同时修改同一属性。建立组件在多种宿主宽度下的视觉测试，并用 DevTools 检查实际命中的容器和规则。

:::

### D2. 如何实现 Modal、Menu 和 Combobox 的可访问性？

::: details 参考答案

#### 基础结论

三者不能共用一个「弹层组件加几个 ARIA」的交互模型。Modal 管焦点闭环与背景 inert；Menu 是命令集合，Tab 进入一次后主要用方向键；Combobox 是输入或选择模式，通常保持输入框 DOM 焦点并管理活动选项。优先采用原生 `dialog`、`button`、`input`，复杂模式严格参考 APG。

#### 原理深挖

Modal 打开时焦点进入内部合适位置，Tab / Shift+Tab 不离开，背景对所有用户不可交互，关闭后通常恢复到触发者。`aria-modal="true"` 是语义声明，不会自动让背景 inert。MenuButton 用按钮暴露展开状态，Menu 内部使用方向键、Home / End、Escape；普通网站导航通常不是 ARIA Menu。Combobox 要同步 expanded、controls、value / selected 状态和活动项，`aria-activedescendant` 方案还要手动滚动活动项可见。

#### 工程场景

建立独立状态机与组件契约：记录 opener，打开后在渲染完成时设置初始焦点；原生 `inert` 或可靠 polyfill 禁用背景；关闭路径统一执行清理和焦点恢复。Menu 采用 roving tabindex 或活动后代之一。Combobox 处理输入法组合、异步结果过期、空结果、Escape、Enter 选择和触摸点击。Portal 只解决裁剪与层叠，不替代这些行为。

#### 反例 / 踩坑

只写 `role="dialog"` 而不移焦点，屏幕阅读器仍可能停在背景；用 `aria-hidden` 隐藏包含 dialog 的祖先会把弹窗一并隐藏。让 Tab 遍历 Menu 每一项违反组合控件惯例。Combobox 每次请求返回都重置活动项，会造成竞态和错误朗读。页面导航硬套 `role="menu"` 会引入用户不期待的桌面菜单键盘模型。

#### 资深回答模板

我先按用户任务判断它到底是对话框、命令菜单还是输入建议，不按视觉浮层归类。能用原生元素就用原生；随后逐项实现 APG 的焦点、键盘、状态与名称契约。测试覆盖打开、取消、提交、异步更新、触发者删除、嵌套浮层、缩放，并用真实浏览器和屏幕阅读器验证。

:::

**追问链：**
1. Modal 初始焦点是否总是第一个可聚焦元素？
2. `aria-modal="true"` 是否等于已经实现背景 inert？
3. Combobox 中 Tab 和方向键分别负责什么？

::: details 追问参考答案

**1. Modal 初始焦点是否总是第一个可聚焦元素？**

不是。简单确认框可聚焦最合适的安全操作；长内容或结构复杂时，可给开头静态标题加 `tabindex="-1"` 并聚焦，避免内容顶部滚出视口；不可逆操作还应考虑把焦点放在风险较低的按钮。选择依据是用户先需要理解什么和下一步是什么。必须保证焦点确实在 dialog 内，且初始位置在高缩放下可见。

**2. `aria-modal="true"` 是否等于已经实现背景 inert？**

不等于。它向辅助技术声明模态语义，不会阻止背景鼠标、触摸、键盘或脚本交互。实现仍需让背景真正 inert、限制 Tab、管理滚动，并保证 dialog 不位于被隐藏的祖先中。原生 `showModal()` 能提供 top layer 和部分模态行为，但焦点初始策略、恢复、业务关闭路径与跨浏览器测试仍由应用负责。

**3. Combobox 中 Tab 和方向键分别负责什么？**

Tab 通常把焦点移入或移出整个 Combobox，不用于逐个浏览弹出的 option；上、下方向键在建议项中移动活动选项，Enter 接受，Escape 关闭或清除临时选择。可编辑 Combobox 通常保持 DOM 焦点在输入框，以 `aria-activedescendant` 暴露活动项，同时保留原生文本编辑按键。具体 Home / End、自动选择与环绕行为要按采用的 APG 变体实现并测试。

:::

### D3. 大型项目如何治理 CSS 架构、作用域和重复样式？

::: details 参考答案

#### 基础结论

CSS 治理要同时解决层叠顺序、作用域、复用边界和删除能力。推荐用 cascade layers 管全局优先级，用 CSS Modules / scoped CSS 或稳定命名管局部作用域，用语义 Token 管值，用组件 API 管变体；不要把 CSS-in-JS、BEM 或原子类当成单一答案。

#### 原理深挖

CSS 的全局性来自层叠、继承和选择器匹配。构建时哈希只能减少名称冲突，不能自动解决 Token 漂移、运行时 portal、全局 reset 或 specificity。原子类减少声明重复但可能把状态组合暴露到模板；组件样式封装更强但易复制相同值。真正的边界应由依赖方向决定：基础 Token 不依赖业务，组件不覆盖页面，业务通过公开 variant 和 slot 定制。

#### 工程场景

预声明 `reset, base, components, utilities, overrides`，规定未分层样式准入；基础选择器使用低 specificity，状态使用 `data-*` 或语义类。建立样式入口、Token 包和弃用清单，统计未使用规则、重复声明与产物体积。微前端还要明确 reset、字体、portal 宿主和 Token 版本契约，必要时用 Shadow DOM 隔离，但同时评估主题透传与可访问关系。

#### 反例 / 踩坑

深层后代选择器绑定 DOM，重构即失效；`!important` 白名单外扩散会破坏主题与用户样式；全局 `.disabled`、`.active` 容易误伤。运行时按组件注入样式可能造成顺序不确定和 SSR 闪烁。Shadow DOM 也不是免费沙箱，弹层、表单、焦点和辅助技术组合仍需验证。

#### 资深回答模板

我会先画样式依赖图，再确定 layer 顺序、局部作用域和 Token 所有权。覆盖必须通过公开变体或指定 overrides 层，禁止依赖 DOM 深度。CI 检查无界 `!important`、选择器复杂度、重复 Token 和 CSS 体积；迁移按页面灰度，用视觉回归与 computed style 采样证明没有顺序漂移。

:::

**追问链：**
1. CSS Modules 是否已经彻底解决样式隔离？
2. 如何迁移历史 `!important` 而不引发大面积回归？
3. 如何判断一段样式应成为 Utility 还是组件 Variant？

::: details 追问参考答案

**1. CSS Modules 是否已经彻底解决样式隔离？**

没有。它主要哈希本地类名，仍可能受全局 reset、元素选择器、继承、自定义属性、portal 内容和第三方样式影响；`:global` 还会重新打开全局边界。它也不解决重复值和层叠顺序。应结合 layer、Token 和组件契约，并测试弹层挂载到根节点后的主题、字体与状态样式。

**2. 如何迁移历史 `!important` 而不引发大面积回归？**

先用静态扫描和 DevTools 采样列出来源、用途与覆盖对象，区分第三方、工具类和临时修复。预声明 layers，把旧规则放在受控层，再逐组件降低 specificity 与删除 important；不要一次全局替换。每批迁移跑关键页面视觉回归、主题和交互状态测试，并对仍保留的 important 建白名单、负责人和删除期限。

**3. 如何判断一段样式应成为 Utility 还是组件 Variant？**

若规则表达单一、跨组件稳定的布局或视觉原语，且组合不会破坏组件语义，可做 Utility；若它代表组件业务状态、需要多个属性协同或有可访问行为约束，应做 Variant。比如通用 `display: grid` 可是工具，危险按钮的颜色、焦点和禁用态应是组件变体。评审还要看调用频率、主题映射和未来删除成本。

:::

### D4. 如何使用 `contain`、`content-visibility` 优化渲染，又不破坏页面？

::: details 参考答案

#### 基础结论

先用 Performance 工具证明样式、布局或绘制是瓶颈，再选择最小 containment。`contain` 是隔离布局、绘制、尺寸或样式影响的正确性承诺；`content-visibility: auto` 可跳过视口外子树的渲染工作。它们不是通用加速开关，错误承诺会改变尺寸、定位、裁剪、sticky 和可访问体验。

#### 原理深挖

Layout containment 限制内部布局对外部的影响，paint containment 会裁剪绘制并形成相关上下文，size containment 让元素尺寸不依赖内容。`content-visibility: auto` 允许浏览器跳过离屏内容的样式布局绘制，但元素仍可能参与可访问性与查找语义；跳过渲染和从 DOM / Accessibility Tree 删除不是一回事。`contain-intrinsic-size` 可提供占位估算，减少滚动条和布局跳动。

#### 工程场景

长信息流或折叠区域可逐块启用 `content-visibility: auto`，根据真实高度分布设 intrinsic size。独立图表、卡片或第三方小部件可评估 layout / paint containment；先在单个边界实验，再扩大。监控渲染耗时、CLS、滚动响应与内存，保留不支持浏览器的普通渲染作为正确回退。

#### 反例 / 踩坑

给高度依赖内容的容器加 size containment 会塌陷；paint containment 会裁掉阴影、焦点环和浮层；新的 containing block / stacking context 会改变 fixed 或 z-index。占位尺寸偏差过大导致滚动跳变，浏览器内查找、锚点跳转和焦点进入离屏区域也可能暴露实现缺陷。

#### 资深回答模板

我先用 trace 定位 Layout / Paint 热点，并确认节点数和更新频率。然后只对具备独立边界的区域声明最小 contain，长列表再试 content-visibility 与真实占位尺寸。验收同时看耗时、CLS、滚动、锚点、查找、键盘焦点、屏幕阅读器和不支持环境；若正确性依赖属性生效，就不是渐进增强。

:::

**追问链：**
1. `content-visibility: auto` 能替代虚拟列表吗？
2. `contain: strict` 为什么风险较高？
3. 如何验证优化不是把成本推迟到用户滚动时？

::: details 追问参考答案

**1. `content-visibility: auto` 能替代虚拟列表吗？**

不能一概替代。它让浏览器跳过部分离屏渲染，但节点和应用状态仍存在，超大列表的 DOM 数量、内存和框架更新成本可能仍高；虚拟列表会控制挂载窗口，但要承担高度估算、焦点、查找和辅助技术语义。中等长度静态内容可先尝试原生能力，超大高频更新列表再基于测量选择虚拟化或分页。

**2. `contain: strict` 为什么风险较高？**

它组合了较强的 size、layout、paint 等隔离，要求容器尺寸不依赖内容，并可能裁剪绘制、创建新的布局与层叠边界。多数业务卡片并不满足这些承诺，直接使用容易塌陷、截断焦点环或改变浮层定位。应从具体瓶颈选择 `contain: layout`、`paint` 等最小集合，并为尺寸明确的组件提供约束与回归测试。

**3. 如何验证优化不是把成本推迟到用户滚动时？**

在同一设备与数据上记录初始加载和连续滚动 trace，比较总 scripting、style、layout、paint、长帧和 INP，而不只看首屏。以真实滚动速度触发离屏内容，观察是否出现集中布局、图片解码和 CLS；同时做 CPU 降速与低端真机测试。若首屏更快但滚动掉帧，应调整块大小、预渲染距离或选择虚拟化。

:::

### D5. RTL、国际化与逻辑属性应该怎样系统落地？

::: details 参考答案

#### 基础结论

国际化不是把容器设为 `direction: rtl` 后镜像全部 UI。结构尺寸优先用逻辑属性，文本方向由语言与内容决定，方向性图标按语义选择是否翻转，混合双向文本用 HTML 的 `dir`、`bdi` 等原生机制隔离。

#### 原理深挖

`inline` / `block` 轴由 writing mode 决定，`start` / `end` 随方向映射，因此 `margin-inline-start`、`border-start-start-radius` 比 `margin-left` 更适合可国际化组件。Unicode 双向算法会根据字符推断方向，但用户名、订单号等未知方向片段嵌入句子时可能重排标点，`bdi` 或 `dir="auto"` 能隔离。方向与语言不同，`lang` 影响发音、断词和字体，不能省略。

#### 工程场景

在根节点设置准确 `lang` 和 `dir`，组件不重复硬编码方向。Token 采用 start / end 命名，布局用逻辑属性；返回、前进、进度等有方向语义的图标按语言翻转，播放、暂停、品牌和数字一般不翻。日期、货币、复数与排序使用 `Intl`，用户生成内容用 `bdi` 包裹。旧浏览器若仍在支持矩阵，先提供物理属性，再用逻辑属性覆盖。

#### 反例 / 踩坑

对整个页面 `transform: scaleX(-1)` 会翻转文字和输入；用构建脚本机械把 left 换成 right 会误改地图、坐标和方向无关图标。只截图阿拉伯语首页会漏掉弹层 portal、图表轴、混合邮箱和键盘顺序。把 CSS 视觉顺序反转也不会自动修正 DOM 与焦点顺序。

#### 资深回答模板

我把方向能力拆为文档元数据、逻辑布局、双向文本、图标语义和本地化格式五层。默认使用逻辑属性，未知方向内容用 bdi 隔离，只翻转具有导航方向的图形。验证覆盖 RTL 长文案、数字和拉丁字符混排、表单光标、弹层、键盘顺序与屏幕阅读器发音。

:::

**追问链：**
1. `dir="rtl"` 与 CSS `direction: rtl` 有何边界？
2. 哪些图标不应该在 RTL 中镜像？
3. 旧浏览器的逻辑属性回退怎样写才安全？

::: details 追问参考答案

**1. `dir="rtl"` 与 CSS `direction: rtl` 有何边界？**

HTML `dir` 是内容方向语义，会被继承并参与双向文本处理，用户代理与辅助技术都能理解；CSS `direction` 主要是呈现属性，不适合作为文档语义的唯一来源。页面和内容片段应优先用 `dir`，样式通过 `[dir="rtl"]` 或逻辑属性响应。动态切换时同步 DOM 属性，并测试输入框光标、选择和 portal 内容。

**2. 哪些图标不应该在 RTL 中镜像？**

没有方向含义的图标通常不镜像，例如播放 / 暂停、相机、搜索、下载、品牌标识、时钟，以及代表真实物体固定方向或数字顺序的图形。返回 / 前进、撤销 / 重做、步骤流向等通常需要按产品语义评估。不要按 SVG 是否有箭头机械判断，应由图标组件公开 `directional` 元数据并做 RTL 视觉回归。

**3. 旧浏览器的逻辑属性回退怎样写才安全？**

先写物理属性作为基础，再在其后写对应逻辑属性，让支持环境覆盖；RTL 旧环境可能还需在明确作用域内写物理反向规则。用 `@supports (margin-inline-start: 1px)` 可隔离增强，避免同时累计 margin。回退范围应基于真实浏览器矩阵和使用数据，若旧环境已退出支持，就删除双轨规则减少长期冲突。

:::

### D6. 如何设计 Design Token 与 CSS 变量的工程体系？

::: details 参考答案

#### 基础结论

Design Token 是跨设计与代码的命名契约，CSS 变量只是 Web 运行时载体。体系应分基础值、语义 Token、组件 Token，业务优先消费语义或公开组件 Token；同时定义类型、主题映射、版本、弃用和质量门禁。

#### 原理深挖

基础 Token 表示原始色板、间距和字号，语义 Token 表达 text、surface、border、focus、danger 等用途，组件 Token 只承载组件确有差异的决策。过早让业务使用基础值会锁死主题，组件 Token 过多又会复制设计决策。CSS 自定义属性可继承、局部覆盖和运行时切换，但不能天然提供类型、引用环检测和跨平台单位转换，需要构建层补足。

#### 工程场景

用单一结构化源生成 CSS、TypeScript 和设计工具产物，CI 校验命名、引用环、缺失主题与颜色对比。CSS 输出在低优先级 tokens layer，根主题映射语义值，组件仅暴露少数可定制变量。版本升级发布迁移表和弃用期，视觉回归覆盖亮暗、高对比与品牌主题；运行时遥测可统计旧 Token 的代码引用。

#### 反例 / 踩坑

把每个设计稿值都变成 Token 会形成无语义字典；直接覆盖组件内部变量等于依赖私有 API。只同步颜色不处理焦点、图表与状态会让暗色主题不可用。将数值 Token 无条件跨 Web、iOS、Android 复用，也会忽略单位、字体栅格和平台控件差异。

#### 资深回答模板

我先定义跨平台稳定语义，再决定各平台输出，不把 CSS 变量反向当领域模型。业务只依赖语义和公开组件 Token，基础值由主题映射。每次变更做类型、引用、对比度和视觉回归校验，并通过弃用周期演进；紧急覆盖也要有 owner 和回收日期。

:::

**追问链：**
1. Token 命名应该按颜色值还是按用途？
2. CSS 变量运行时覆盖如何避免成为新的全局污染？
3. 如何安全删除一个 Token？

::: details 追问参考答案

**1. Token 命名应该按颜色值还是按用途？**

基础层可按色阶命名，但业务接口应按用途，如 `color.text.muted`、`color.border.focus`，这样主题可改变具体值而不改消费者。名称要避免绑定某个亮暗结果，例如 `white` 不等于所有主题的 surface。一个语义 Token 若承担多个无关用途，应拆分；反之不要为每个页面复制同义 Token。

**2. CSS 变量运行时覆盖如何避免成为新的全局污染？**

限制覆盖根：全局主题只在明确的主题属性下定义，组件定制只在组件根和公开变量上进行；私有变量采用命名空间并不写入 `:root`。用 layer 管默认值与覆盖顺序，文档记录继承范围。Portal 内容需要显式携带主题上下文。CI 可扫描未登记的全局变量和业务对私有变量的引用。

**3. 如何安全删除一个 Token？**

先在生成清单中标记 deprecated，提供替代项和语义差异；扫描仓库、运行时主题与下游包引用，发布至少一个兼容周期。迁移后让旧 Token 暂时代理到新值并发出构建告警，再在 major 或约定窗口删除。最后跑所有主题视觉回归和对比度检查，避免静态搜索漏掉动态拼接或外部消费者。

:::

### D7. 移动端安全区、软键盘和视口应该怎样处理？

::: details 参考答案

#### 基础结论

移动端布局应使用正确 viewport 元数据、动态视口单位和 `env(safe-area-inset-*)`，但安全区只处理被系统遮挡的边缘，不是统一内边距。软键盘属于可视视口变化和输入流程问题，优先让浏览器滚动聚焦控件可见，确需精细控制时再渐进增强使用 Visual Viewport API。

#### 原理深挖

移动浏览器存在 layout viewport、visual viewport 和随浏览器 UI 变化的动态高度。传统 `100vh` 可能对应大视口，导致地址栏或键盘遮挡；`svh`、`lvh`、`dvh` 分别表达不同视口语义。安全区变量需配合 `viewport-fit=cover` 才有预期效果。虚拟键盘行为还受浏览器、WebView、滚动容器和输入类型影响，不能由一套高度公式完全统一。

#### 工程场景

页面基础使用 `min-block-size: 100%` 和普通流，沉浸式底栏用 `padding-block-end: max(基础间距, env(safe-area-inset-bottom))`。全屏场景再使用 `100dvh`，并给不支持环境保留 `100vh` / 百分比回退。表单减少固定底部遮挡，焦点后用 `scrollIntoView` 也要等待布局稳定且尊重用户滚动。Visual Viewport 监听需节流并正确清理。

#### 反例 / 踩坑

所有容器都加 safe-area 会产生双倍间距；监听 window resize 后强制改高度会造成抖动。禁止页面缩放来「解决」键盘布局违反可访问性目标。输入聚焦时把整个页面 fixed 锁住，可能丢失滚动位置和焦点可见性。仅在桌面模拟器改尺寸无法覆盖 iOS Safari、Android Chrome 和内嵌 WebView 差异。

#### 资深回答模板

我先让普通流在无 API 时可用，再对沉浸区域加安全区，对全屏壳使用动态视口单位。软键盘优先依赖原生聚焦滚动，Visual Viewport 只增强确有遮挡的组件。验收覆盖横竖屏、刘海设备、浏览器栏展开收起、不同键盘、200% 缩放和真机 WebView。

:::

**追问链：**
1. `100vh`、`100svh` 和 `100dvh` 如何选择？
2. 安全区内边距为什么常用 `max()`？
3. 软键盘弹起后是否应该固定把按钮顶到键盘上方？

::: details 追问参考答案

**1. `100vh`、`100svh` 和 `100dvh` 如何选择？**

`svh` 取小视口，适合希望浏览器 UI 展开时也不被遮挡的稳定首屏；`dvh` 随动态视口变化，适合全屏面板跟随地址栏收起展开，但可能触发布局变化；传统 `vh` 的移动端映射历史上不一致，适合作为回退而非精确键盘方案。应按内容是否允许高度变化选择，并在真机滚动与旋转时观察。

**2. 安全区内边距为什么常用 `max()`？**

设备没有安全区时 `env()` 往往为 0，直接使用会丢掉设计要求的基础间距；`max(1rem, env(safe-area-inset-bottom))` 能取两者较大值，既保持常规留白又避开系统区域。若目标是基础间距加安全区，应使用 `calc()`，两种语义不能混淆。还要避免父子重复消费同一 inset。

**3. 软键盘弹起后是否应该固定把按钮顶到键盘上方？**

不一定。固定按钮会压缩内容、遮挡错误提示，并在不同键盘高度下抖动。优先让表单和提交按钮处于自然文档流，浏览器滚动当前输入可见；只有聊天发送、短表单等明确任务才考虑贴键盘增强。实现时观察 visual viewport、保留安全区，并测试键盘切换、横屏、放大和外接键盘。

:::

### D8. 如何建立符合 WCAG 2.2 的审计、自动化与人工测试流程？

::: details 参考答案

#### 基础结论

可访问性验收应以目标 WCAG 2.2 等级和用户关键任务为范围，把静态规则、组件测试、浏览器自动化、人工键盘、缩放与辅助技术测试组合起来。自动化能快速发现一部分确定性问题，但无法判断文案意义、焦点逻辑、朗读质量和任务是否真正完成。

#### 原理深挖

成功准则要转成可复现检查。例如 2.5.8 Target Size (Minimum) 的 AA 要求是指针目标至少可容纳 24 × 24 CSS px，或满足 spacing、inline、user agent control、essential 等例外；不是把所有控件一律写成 24 px。1.4.4 检查文本通过 200% 浏览器缩放或等效方式放大后是否丢失内容或功能；1.4.10 对水平书写内容检查约 320 CSS px 宽时有无非必要二维滚动，两者不能混为同一个响应式断点。结构上检查标题层级是否有意义，但不把单个 `h1` 当硬性 WCAG 条款。

#### 工程场景

需求阶段标注键盘、名称、状态和错误契约；组件层用 Testing Library 类查询和 axe 检查角色、名称及合法关系；E2E 走 Tab、方向键、Escape、焦点恢复与错误流程。发布前分别检查 200% 浏览器缩放和 400% 页面缩放所形成的约 320 CSS px 窄视口，再检查对比度、强制颜色与减少动画，并在关键流程用 NVDA / JAWS + Chrome / Firefox、VoiceOver + Safari 等目标组合抽测。缺陷按阻断任务和影响范围分级。

#### 反例 / 踩坑

把 Lighthouse 100 分当合规证明会漏掉大量语义和交互错误；只测 Tab 会漏掉组合控件方向键。看到目标小于 24 px 就报错而不核对 spacing / inline 等例外，会产生错误结论；反过来滥用 essential 例外也不可接受。用 ARIA 修复 axe 告警却不实现功能，会让树看似正确、操作仍失败。

#### 资深回答模板

我先声明标准版本、等级、页面样本和关键任务，再把成功准则映射为自动与人工证据。自动化负责回归确定性规则，人工负责键盘模型、名称语义、缩放回流、认知理解和辅助技术。每个例外记录依据、范围和负责人；修复优先改原生结构和组件源头，最后用原问题路径复测并保留证据。

::: details 追问参考答案

**1. WCAG 2.2 AA 的 24 CSS px 目标尺寸有哪些重要例外？**

2.5.8 允许尺寸不足但周围 spacing 满足规定、目标位于行内文本、尺寸由 user agent 决定且作者未修改，或特定呈现属于 essential 等例外；等价目标也可能满足条件。检查时以实际可点击区域和 CSS px 为准，不能把视觉图标尺寸等同于 target，也不能靠用户缩放补足。即使满足例外，重要高频控件仍应尽量提供更大命中区。

**2. 200% zoom 与 320 CSS px reflow 应怎样分别验证？**

1.4.4 关注文本在不依赖辅助技术时放大到 200% 后，内容与功能是否保留；桌面浏览器的 200% 页面缩放是常用验证方式，但不能用断点抵消实际文字放大。1.4.10 关注水平书写内容在等效 320 CSS px 宽时是否无需同时横纵滚动，常可用 1280 CSS px 初始 viewport 下 400% 页面缩放验证。两项都要检查弹层、sticky、表单错误和控件，数据表等例外区域要单独记录依据。

**3. 自动化扫描通过后，人工测试至少还要覆盖什么？**

至少完成全流程键盘操作，确认 Tab 顺序、组合控件方向键、焦点可见与恢复；核对可访问名称和描述是否准确而非仅存在；检查 200% 文本、320 CSS px 回流、目标尺寸、对比和非颜色提示；用目标屏幕阅读器完成登录、表单错误、弹窗与动态更新等关键任务。还要验证高对比 / 强制颜色、减少动画和触摸场景中的实际可用性。
