# 架构与系统设计速记

> **真源：** [14 前端架构](/interview/questions/14-frontend-architecture)、[11 前端系统设计](/interview/questions/11-frontend-system-design)、[12 微前端](/interview/questions/12-microfrontend) 为唯一真源；冲突时以题库为准。
>
> **用法：** 面试前遮住口述稿先自讲，再对结论卡与追问速答。证据坑位请填入你自己的项目指标，勿背他人数字。

## 一句话定位

本域讲清「质量属性驱动的前端架构 + 可答辩的系统设计题 + 微前端选型与隔离税」。资深面试要的是**边界、依赖方向与故障隔离**，不是框架名词。你应能在五分钟内把分层、状态、权限、可观测与「何时不上微前端」讲成一条决策故事。

## 核心结论卡

1. **结论：** 架构从质量属性反推：性能、可用性、安全、可修改性写成「刺激—响应—指标」，再选结构。  
   **边界：** 先选最火框架再补故事，是反模式。  
   **证据坑位：** 〔填〕一次选型 ADR：上下文、选项、取舍、后果。

2. **结论：** 分层要有依赖方向：UI → 应用服务 → 领域 / API 适配；禁止页面与 Store 被基础设施反向引用。  
   **边界：** 目录同名≠分层成立；跨层走接口或用例，不走捷径。  
   **证据坑位：** 〔填〕包依赖矩阵或 lint 规则截图。

3. **结论：** 模块按业务域拆，不按页面机械切；共享模块要有 Owner、语义稳定，否则宁可复制。  
   **边界：** 「两处用到就抽」是泥球温床。  
   **证据坑位：** 〔填〕共享包清单与 Owner 表。

4. **结论：** 状态分组件、应用、服务端、URL 四类；单向数据流管写入可追踪，不要求一切进巨型 Store。  
   **边界：** 服务端状态有缓存与失效；URL 状态要可分享可刷新。  
   **证据坑位：** 〔填〕关键页状态归属图。

5. **结论：** API 适配层负责 DTO 映射、错误归一、鉴权头，不塞业务规则与 UI 文案。  
   **边界：** 错误分业务拒绝、鉴权、瞬态、限流、缺陷，并定义重试与提示。  
   **证据坑位：** 〔填〕统一错误码表与一次错误恢复用例。

6. **结论：** 前端权限是体验与入口控制；权威授权在服务端资源实例。多应用统一词汇与审计，不必统一每个 UI。  
   **边界：** 能力快照可缓存，变更要可失效。  
   **证据坑位：** 〔填〕资源—动作词汇表与跨应用复用方式。

7. **结论：** 应用壳只拥有会话、导航、布局、主题、监控与全局降级；业务经注册表接入。  
   **边界：** 业务依赖壳内部 Store 会锁死演进。  
   **证据坑位：** 〔填〕壳扩展点列表与一次插件化接入。

8. **结论：** 性能预算与稳定性 SLO 进入架构治理；SLI 看用户可感知结果，不只看 JS Error 数。  
   **边界：** 降级预置、可观测、可回滚，并演练。  
   **证据坑位：** 〔填〕核心任务可用率 / 白屏率与错误预算。

9. **结论：** 可观测最小闭环：日志、指标、trace；`sessionId` / `actionId` / `traceId` / `spanId` 职责不同，不可互替。  
   **边界：** 传播用 W3C Trace Context；前端日志不落秘密。  
   **证据坑位：** 〔填〕一次端到端故障定位的四类 ID 关联记录。

10. **结论：** 微前端解决组织与独立发布问题，同时引入架构税；单团队小系统通常不应上。  
    **边界：** 按稳定业务域与团队责任拆，不按按钮拆。  
    **证据坑位：** 〔填〕上 / 不上微前端的决策表与试点验收。

11. **结论：** qiankun / Garfish 沙箱是兼容性隔离，不是浏览器安全边界；不可信内容要更高隔离。  
    **边界：** 样式隔离模式有取舍；预加载不能默认 `all`。  
    **证据坑位：** 〔填〕子应用卸载后泄漏排查与隔离模式说明。

12. **结论：** Module Federation 的 `shared` / `singleton` 是运行时协商；Vue 共享要谨慎，只有跨边界共享实例身份时才强求单例。  
    **边界：** Webpack 5 内置 MF ≠ 官方 MF 2.0 全能力；失败要分层熔断，不是盲目重试。  
    **证据坑位：** 〔填〕shared 版本矩阵与一次 remote 失败降级。

13. **结论：** Wujie 结合 Web Components 与同域 iframe 降侵入、可保活；同域 iframe 仍非安全边界。  
    **边界：** 保活 / 单例 / 重建按内存与状态价值选。  
    **证据坑位：** 〔填〕保活内存预算与路由同步方案。

14. **结论：** 跨应用通信共享身份与环境，不共享领域内部状态；消息要 Schema、版本、Owner。  
    **边界：** 全局 EventBus 无生命周期会变泄漏源。  
    **证据坑位：** 〔填〕跨应用事件目录与一次总线事故。

15. **结论：** 系统设计题要讲清约束、流量、一致性、失败与演进；中后台框架、监控、权限、低代码都按此骨架答。  
    **边界：** 只画组件树不算系统设计。  
    **证据坑位：** 〔填〕一道系统设计题的 10 分钟提纲自测记录。

16. **结论：** 发布是前端、API、配置、缓存协同契约；默认后端先兼容旧客户端，再发前端，最后清理旧协议。  
    **边界：** 无兼容窗口的双向 breaking 会放大故障面。  
    **证据坑位：** 〔填〕一次 expand-and-contract 发布顺序。

17. **结论：** 平台化要有足够消费者与明确维护责任；先用两三个真实业务验证再抽平台。  
    **边界：** 过早抽象的成本常高于复制。  
    **证据坑位：** 〔填〕平台能力的消费者数与维护 Owner。

18. **结论：** ADR 记录高成本难回退决策的上下文与后果，不是百科；团队变大再渐进拆分，先模块化单体。  
    **边界：** 无压力信号时拆分是自嗨。  
    **证据坑位：** 〔填〕现有 ADR 索引与一条可回读的决策。

## 高频追问速答

1. **为什么说「先选框架」是反模式？**  
   框架是实现手段，架构要先回答质量属性与约束：独立发布吗、团队边界在哪、性能与安全预算是什么、失败如何降级。把这些写成可测场景后，再比较 SPA、SSR、微前端或 BFF。否则容易为简历选型，上线后才发现组织与运维税付不起。合格回答应能指出被放弃选项及其原因，而不是只赞美最终选择。

2. **共享包什么时候不该抽？**  
   当两处代码只是暂时相似、变化节奏不同、没有明确 Owner 时，抽取会制造协调成本与隐性耦合。优先复制小而不稳定的片段，待语义稳定、消费者足够、测试与版本策略清晰后再抽象。共享模块泥球的典型信号是「谁都敢改、谁都不敢发」。治理靠依赖矩阵、Owner 与删除能力，而不是再加一层 utils。

3. **微前端什么时候坚决不上？**  
   单团队、小系统、模块高度耦合、发布节奏本就一致、又没有人维护基座时，微前端只增加调试与隔离税。适合信号是多稳定团队、清晰域边界、必须独立发布或渐进替换遗留。决策要用独立验收、独立发布、低频通信、故障可隔离来验证边界，而不是先挑 qiankun 再找理由。

4. **qiankun 沙箱能防 XSS 吗？**  
   不能把它当成安全沙箱。它主要隔离对全局对象的读写并尽量恢复副作用，方便多应用共存； XSS、权限与不可信脚本仍要靠 CSP、鉴权、来源隔离甚至独立域 iframe。子应用仍可能通过 DOM、网络与主应用暴露的 API 互相影响。面试应明确「兼容性隔离」与「安全隔离」两层词，避免过度承诺。

5. **Vue 为什么要谨慎 `shared` 单例？**  
   当跨应用传递组件实例、响应式对象或依赖注入上下文时，多份 Vue 会导致身份不一致与难以解释的缺陷，这时 singleton 协商才关键。若应用只通过 DOM 挂载或序列化数据交互，各自携带 Vue 反而是合理隔离。`shared` 是版本协商，不是简单 external；协商失败要有构建期检查与运行时降级，不能假设永远合得上。

6. **系统设计题你的口述骨架？**  
   先澄清用户、规模、一致性与非功能约束，再画端到端：客户端、BFF / API、数据、配置与发布。接着讲关键用例时序、权限、缓存、失败与降级，最后给演进与观测。中后台就落到权限、路由、表格框架与扩展点；监控题落到 SLI、采样、告警与隐私。避免一上来罗列技术栈，也避免只画页面线框。

7. **壳和业务如何避免锁死？**  
   壳只暴露稳定能力：会话、导航、布局、主题、监控、降级开关；业务通过声明式注册接入，不依赖壳私有 Store 与内部组件。版本化契约，破坏性变更走兼容窗口。业务域数据留在业务包，壳不变成第二个「上帝模块」。这样换壳或抽微应用时，才有可迁移边界。

8. **四类 ID 怎么分工？**  
   `sessionId` 串一次访问会话，`actionId` 串一次用户意图，`traceId` 串分布式调用，`spanId` 标单次操作。定位故障时常要四者联查：用户点了什么、前端版本、后端哪一段慢或错。只用 JS Error 时间戳很难归因。传播遵循 Trace Context，业务属性单独携带，且日志绝不写 Token 与隐私字段。

## 反例 / 红线

- 无质量属性与 ADR 的「为微前端而微前端」。
- 把 qiankun / 同域 iframe 说成安全沙箱。
- 全局共享 Store / EventBus 无 Owner、无版本、无卸载。
- 目录分层但依赖反向；共享 utils 无删除策略。
- 系统设计只报技术栈，不谈失败与演进。
- 前后端同时 breaking 且无兼容窗口。

## 5 分钟口述稿

「架构我从质量属性讲起：要什么指标，再选分层与边界。依赖单向，状态分类，适配层归一错误，权限词汇统一但授权在服务端。壳只做稳定能力，业务注册接入。可观测用 session、action、trace 联查，稳定性看用户可感知 SLI。

微前端先问组织与发布是否真需要；沙箱是兼容不是安全。MF 的 shared 要谨慎，尤其 Vue 实例身份；通信有 Schema 与 Owner。系统设计题按约束、链路、失败、演进答。发布遵循兼容窗口。收口用一份 ADR、一次故障定位和一次『决定不上微前端』的理由。」
