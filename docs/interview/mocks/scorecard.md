# 模拟面试评分表

> **怎么用：** 每场模拟结束后立刻打分（搭档评或自评）。只打整数 1～5；先看「描述」再给分，避免全场打 4。配合 [模拟脚本](/interview/mocks/scripts) 使用；弱项回到对应 [题库](/interview/questions/02-vue3) 或 [故事模板](/interview/stories/template) 加练。

**建议：** 九维组成完整评分框架。单场尽量覆盖九维；综合终场至少覆盖 7 维，并且必须覆盖目标岗位核心维。每个已考察维度都要写一句可复核证据，不能只凭印象。未考察项不填默认分，也不能与九维全覆盖场直接比较。

## 统一 1～5 分锚点

| 分数 | 通用锚点 |
| ---- | -------- |
| 1 | 无法回答，或答案明显错误、危险、与事实冲突 |
| 2 | 能说术语或表面流程，但缺少机制、证据、边界或失败路径 |
| 3 | 达到岗位基本要求；答案完整，有一个可验证项目证据，常规追问可接住 |
| 4 | 能解释机制与取舍，覆盖边界和异常，并用数据、实验或复盘验证 |
| 5 | 在 4 分基础上形成可迁移方法论，能处理复杂追问、指导他人并主动说明未知 |

各维下方的描述用于解释该维在 1～5 分时分别应看到什么；如与通用锚点冲突，取较低分。**没有写下证据的维度视为未考察，不得打 3 分凑数。**

## 总分计算与岗位权重

### 基础总分与百分制

- **九维全覆盖时：** 基础总分为九维直接相加，范围为 9～45 分；百分制为 `基础总分 ÷ 45 × 100`。
- **未覆盖九维时：** 不计算或展示「/45」基础总分，只报告覆盖率、未考察项和归一化百分制。
- **可比性：** 不同覆盖组合的归一化分只能说明各自已考察范围内的表现；报告必须附覆盖率与未考察项，不可直接与九维全覆盖场或其他覆盖组合比较。

### 岗位加权分

设已考察维度集合为 `E`，每维得分为 `sᵢ`，岗位权重为 `wᵢ`：

**归一化百分制 = `Σ(sᵢ × wᵢ) ÷ Σ(5 × wᵢ) × 100`，其中 `i ∈ E`。**

九维全覆盖时，分母权重之和为 100%，该公式等价于完整岗位加权百分制。未考察维度从分子、分母同时剔除，不补默认分。

| 岗位 | 正确性 | 原理深度 | 工程落地 | 架构约束 | 故障治理 | 演进能力 | 业务价值 | 领导力 | 表达与证据 | 合计 |
| ---- | ------ | -------- | -------- | -------- | -------- | -------- | -------- | ------ | ---------- | ---- |
| Senior Frontend | 20% | 15% | 15% | 10% | 10% | 5% | 10% | 5% | 10% | 100% |
| Staff / 架构 | 10% | 15% | 10% | 20% | 15% | 15% | 5% | 5% | 5% | 100% |
| Tech Lead | 10% | 10% | 10% | 15% | 15% | 10% | 5% | 15% | 10% | 100% |
| 前端偏全栈 | 15% | 10% | 25% | 10% | 10% | 5% | 10% | 5% | 10% | 100% |

岗位核心维如下，单场不得遗漏；综合终场额外要求至少 7 维：

- **Senior Frontend：** 正确性（最高权重），并至少覆盖原理深度。
- **Staff / 架构：** 架构约束、原理深度、故障治理、演进能力。
- **Tech Lead：** 领导力、架构约束、故障治理、演进能力。
- **前端偏全栈：** 工程落地（最高权重），并至少覆盖正确性。

原则上尽量覆盖九维；专项场时长有限时，未考到的维从分母移除。架构类脚本应让架构约束、原理深度、故障治理、演进能力都有可记分问题。

### 百分制 60、75、85 分怎么读

归一化百分制对应已考察维的加权均分：`百分制 ÷ 20 = 加权均分`（因为满分是 5 分 × 20 = 100）。

| 归一化分 | 加权均分 | 九维全覆盖约等于 | 含义 | 行动 |
| -------- | -------- | ---------------- | ---- | ---- |
| **60** | 3.0 | 27 / 45 | 达到岗位基本要求，弱项仍明显 | 可以投递，但先补 ≤2 的维和所有红线 |
| **75** | 3.75 | 约 34 / 45 | 稳健可面试，核心维多为 4 | 按目标岗位最高权重维再打一场 |
| **85** | 4.25 | 38～39 / 45 | 优秀，有可迁移方法论 | 换脚本加压，防止对单一题型过拟合 |

中间分数按线性理解：70 分约均分 3.5，80 分约均分 4.0。75 分按百分制公式精确对应均分 3.75；九维全覆盖时 34 / 45 的基础均分是 3.78（百分制约 76），因此「约 34 / 45 ≈ 75 档」是四舍五入后的约数，两表小数不必对齐。只有未命中红线时，才允许把 75 / 85 写成「稳健」或「优秀」。触红线时只写「不通过 / 待核验」，即使百分制高于 85。

### 重叠维度如何区分

| 容易重叠的维度 | 区分规则 |
| -------------- | -------- |
| 正确性 vs 原理深度 | 正确性看结论对不对、方案危不危险；原理深度看能否解释机制、因果链和失效条件 |
| 工程落地 vs 故障治理 | 工程落地评正常交付、契约、门禁和 AI 审查；故障治理评异常状态下的发现、止损、恢复与防复发 |
| 架构约束 vs 领导力 | 约束评「输入是否找全并排序」；领导力评「拿到输入后如何拍板、推动人和组织」 |
| 业务价值 vs 工程落地 | 业务价值评为何值得做、对谁有用；工程落地评如何做成、如何验证 |
| 表达与证据 vs 正确性 | 表达与证据评结构、控时和可核验材料；正确性评事实本身是否成立 |
| 演进能力 vs 领导力 | 演进能力评跨阶段触发器、迁移和退出；领导力评当下对人与优先级的影响 |

同一回答可以被多个维度引用，但每维必须记录**不同的观察事实**。例如「缓存故障」中，机制对错计入正确性，机制解释计入原理深度，降级与恢复计入故障治理，是否采用缓存及其业务代价计入业务价值。

### 红线

红线独立于九维总分。命中任一项时，本场结论为「不通过 / 待核验」，**正确性或诚信红线不得被基础总分或岗位加权分抵消**：

- **正确性红线：** 关键机制明显错误；信任前端鉴权、泄露密钥或个人数据、绕过权限校验，或让未经审查的 AI 代码直接上线。
- **诚信红线：** 编造项目、指标、职责或生产经验；无法区分「主导、参与、了解」。
- **可验证性红线：** 核心项目结论没有代码、指标、日志、评审记录或可复述过程中的任何一种证据，且追问后仍无法核验。
- **故障责任红线：** 面对高风险变更或线上故障，没有止损、回滚、降级和升级通知意识。
- **基础能力红线：** 任一已考察维度为 1 分，或目标岗位任一核心维 / 任一并列最高权重维度 ≤2 分；Staff / 架构的架构约束、原理深度、故障治理、演进能力任一项 ≤2 即命中；Tech Lead 的领导力、架构约束、故障治理、演进能力任一项 ≤2 即命中。

## 维度一：正确性

考察：结论、机制和方案是否成立；有没有给出危险或事实错误的做法。

| 分 | 描述 |
| -- | ---- |
| 1 | 关键机制明显错误，或给出危险方案（前端鉴权、明文密钥、跳过校验） |
| 2 | 大方向勉强对，但把配置项、库名或口诀当成事实，追问即露出错误 |
| 3 | 主结论正确，常见边界说得清；次要细节可有小缺口但不致误导 |
| 4 | 结论正确且能指出反例；主动纠正自己刚才不精确的表述 |
| 5 | 面对变体仍保持正确，并标明「我没验证过的部分」，不靠猜测硬答 |

**观察信号：**

- 正向：先给可检验的结论，再补条件；主动说「这个说法只在 XX 浏览器成立」
- 负向：把 Vue 调度讲成浏览器 Event Loop；把 Token 当 CSRF 的完整解

**证据示例：** 「画出宏任务 / 微任务顺序且与题目代码一致」；「否定前端鉴权并给出服务端校验点」。

## 维度二：原理深度

考察：能否解释关键机制、因果链、边界和失效条件，而不是停留在框架 API 或类比。

| 分 | 描述 |
| -- | ---- |
| 1 | 关键机制明显错误；把框架名、配置项当作原理 |
| 2 | 能复述表面流程，但无法解释调用顺序、依赖关系或为什么会失效 |
| 3 | 能画出核心链路，解释主要机制与常见边界，并与一个项目现象对应 |
| 4 | 能从机制推导性能、隔离、一致性或安全后果，并用实验、源码或日志验证 |
| 5 | 能跨框架比较机制与失效模型；面对变体仍可从第一原则推导并清楚标明未知 |

**证据示例：** 「用一次列表错位说明 key 复用」；「用 PerformanceObserver 条目解释 INP 归因」。

---

## 维度三：工程落地

考察：正常路径上能否把方案做成可发布、可联调、可审查的交付；含契约、流水线、测试门禁和 AI 协作质量。

| 分 | 描述 |
| -- | ---- |
| 1 | 只会报技术名词；说不清自己如何联调、发布或审查 |
| 2 | 会走表面流程（调接口、提 MR），但没有门禁、失败路径或责任边界 |
| 3 | 能讲清一条真实流水线或契约，并提到人工把关 |
| 4 | 有可复述的工作流：契约 / 测试 / 审查清单 / 回滚；清楚不信任点（安全、权限、AI 生成代码） |
| 5 | 能定团队级规范并把 AI、测试、发布纳入同一套质量门禁 |

**观察信号：**

- 正向：主动提契约先行、CI 红线、AI 必审项
- 负向：大谈分布式却答不清一个列表接口的分页与权限；对照 [Java 叙事边界](/interview/00-overview#java-叙事边界)

**场次说明：** 业务型中小厂若完全未涉及 AI 或后端，不把「没提到 AI」扣分；该部分并入本维已考察证据即可。创业 AI / 全栈偏前场必须看到审查与闭环。

**证据示例：** 「描述 MR → 预发 → 灰度的卡点」；「说明 AI 生成 CRUD 后必审鉴权与校验」。

## 维度四：架构约束

考察：设计前能否主动发现、验证并排序业务、规模、团队、合规、存量系统与成本约束。

| 分 | 描述 |
| -- | ---- |
| 1 | 不问背景直接选框架；忽略明确的安全、合规或成本限制 |
| 2 | 会问用户量和工期，但问题零散；无法区分硬约束、假设与偏好 |
| 3 | 能覆盖业务目标、规模、团队、存量与时间，并指出最关键的 1～2 项约束 |
| 4 | 能量化质量目标、验证假设、识别约束冲突，并按业务风险排序 |
| 5 | 能建立约束清单与复审机制；信息不足时会设计低成本实验并说明决策置信度 |

**证据示例：** 「先问发布频率和团队边界再谈微前端」；「列出合规导致不能热更新的条件」。

## 维度五：故障治理

考察：是否覆盖故障发现、止损、定位、恢复、复盘、防复发与责任协作的完整闭环。

| 分 | 描述 |
| -- | ---- |
| 1 | 无监控与止损意识；高风险操作没有回滚；倾向甩锅 |
| 2 | 只会查日志或重启；没有故障分级、降级、通知和复盘 |
| 3 | 能讲清一次故障的发现、定位、修复与复盘，具备基本监控和回滚方案 |
| 4 | 能设计指标、告警、开关、隔离、降级、演练与责任分工，并量化恢复目标 |
| 5 | 能从多次故障提炼治理机制，持续降低故障半径与恢复时间，并推动跨团队执行 |

**证据示例：** 「给出停止线与回滚动作」；「复盘后加了告警和开关，而不是只修代码」。

---

## 维度六：演进能力

考察：能否为架构设定演进触发器、迁移步骤、兼容策略、退出路径和阶段性验证。

| 分 | 描述 |
| -- | ---- |
| 1 | 把当前方案当作永久终局；没有升级、迁移或退出意识 |
| 2 | 只说「以后再重构」；没有触发条件、步骤、成本与兼容安排 |
| 3 | 能给出下一阶段触发条件和基本迁移顺序，知道需要灰度与回退 |
| 4 | 能设计可度量触发器、双轨兼容、数据 / 契约迁移、阶段验收与退出方案 |
| 5 | 能把技术、组织和成本演进联动管理；根据证据调整路线，并避免一次性大爆炸迁移 |

**证据示例：** 「写明 QPS 或团队人数到阈值才拆 BFF」；「试点失败如何退回单体」。

## 维度七：业务价值

考察：技术工作是否连到用户结果、收入、风险、效率或合规，而不是只证明「做得很酷」。

| 分 | 描述 |
| -- | ---- |
| 1 | 完全讲技术实现；问「谁受益」答不上，或用假指标充数 |
| 2 | 会说「提升体验 / 提高效率」，但没有口径、对象或对照 |
| 3 | 能指出服务对象和一项可观察结果（转化、工时、故障、审核通过率） |
| 4 | 能把方案对比接到业务约束，并说明不做的代价 |
| 5 | 能主动放弃技术优越但业务不值的方案，并解释如何复盘价值是否兑现 |

**证据示例：** 「首屏从 4.2 s 到 2.1 s，活动页转化按同一窗口统计」；「否决微前端是因为发布冲突并不存在」。

---

## 维度八：领导力

考察：如何做取舍、推动人与组织、处理冲突和承担责任（含无正式职权时的影响）。

| 分 | 描述 |
| -- | ---- |
| 1 | 只有唯一做法，或一切「听领导的」无自己判断；冲突只会升级甩锅 |
| 2 | 能说出选了什么，但对比弱；对人的影响停留在「我跟他们说了」 |
| 3 | 至少给出 2 选 1 的理由，能联系工期 / 团队能力，并说明自己的动作 |
| 4 | 清晰对比维度，承认信息差，有兜底；能描述拆任务、CR 或冲突收口 |
| 5 | 决策像方法论：目标→约束→选项→标准→复盘；能指导他人做同类判断 |

**观察信号：**

- 正向：「没选 B 是因为…」「若指标到 X 会升级方案」
- 负向：事后诸葛式完美叙事、从不承认坑、把管人经历说成自己没有的职级

**证据示例：** 「列出两个方案的代价并说明谁签字」；「无职权时用试点数据推动契约」。

## 维度九：表达与证据

考察：是否结论先行、时长可控、STAR-L 完整；被打断后能否收回主线；关键结论是否有可核验证据。

| 分 | 描述 |
| -- | ---- |
| 1 | 无结构，从细节或公司历史扯起；超时严重；或关键数字经不起「怎么算的」 |
| 2 | 有片段结构但不稳定；常缺结果或任务边界；「我们」远多于「我」 |
| 3 | 自我介绍与项目能按背景→行动→结果讲述；偶有跑题但可拉回；至少一项证据可复核 |
| 4 | 明显结论先行；30 s / 2 min 档切换自如；追问回答短而完整，口径清楚 |
| 5 | 全程可当范文；主动控时、预埋钩子、复述面试官问题后再答，并主动标明证据缺口 |

**观察信号：**

- 正向：先答一句结论再展开；用「三点」组织；主动说「我停在这里看你想听哪块」
- 负向：重复同一句、术语瀑布、答非所问、用无法核验的百分比收尾

**证据示例：** 「2 分钟内讲完权限模型并指出自己改的路由表」；「指标注明来源为 RUM 周报」。
