# 前端架构面试题库

> **怎么用：** 先按 **约束识别 → 质量属性 → 边界与依赖 → 风险与演进** 口述 2～3 分钟，再展开参考答案。普通题检查知识面；深层题检查能否把原则落到指标、故障与组织治理。

本模块面向 **5 年+ 前端、前端架构师与技术负责人**，重点回答「系统为什么这样分、依赖为什么这样流、如何持续治理」。[工程化](/interview/questions/03-engineering) 讲工具链与流水线实操；[微前端](/interview/questions/12-microfrontend) 讲运行时原理；[前端系统设计](/interview/questions/11-frontend-system-design) 讲具体系统案例。本模块只讨论这些能力如何纳入整体架构。

## 一、质量属性与架构边界

### Q1. 前端架构设计开始前，必须澄清哪些约束？

**考察点：** 业务目标、规模、团队、合规、存量系统

::: details 参考答案
先确认「为什么改」，再讨论框架。至少澄清：核心用户与主路径、端与地区、峰值流量及数据量、可用性与性能目标、交付期限、团队技能与人数、合规边界、存量依赖和退出成本。

输出不应是一张技术清单，而应是一页约束表。例如：主路径月活 300 万、LCP P75 ≤ 2.5 s、发布失败按载体满足既定 RTO、6 人团队半年内不能停业务迁移。决策时把**风险暴露**（概率、影响、持续时间）与**治理成本**（建设、迁移、认知和运维）分开估算，再比较净收益；约束冲突时按业务损失排序。
:::

**追问：** 需求方只说「做成业内领先」，你如何把它转成可验证目标？

::: details 追问参考答案

先拒绝把「领先」直接当验收条件，按目标用户与关键旅程拆成性能、可用性、交付效率等质量属性，并用现状基线、竞品证据和业务损失确定目标区间及观察窗口。产品 Owner 决定业务优先级，架构 Owner 记录取舍，数据 Owner 校验口径；先小流量试验，复盘收益与副作用，证据不足时不承诺伪精确数字。

:::

### D1. 如何从质量属性反推架构，而不是先选框架？

**考察点：** 质量属性场景、优先级、可测量决策

::: details 参考答案
#### 基础结论

架构是质量属性的取舍结果。先把性能、可用性、安全、可修改性、可测试性等写成「刺激—环境—响应—指标」场景，再选择能控制主要风险的结构。

#### 原理深挖

质量属性会互相牵制：运行时隔离提高故障边界，却增加加载和治理成本；强一致状态减少歧义，却可能放大耦合。应以架构效用树排序：先计算风险暴露（影响 × 概率），再把建设、迁移、认知与运维等治理成本单列，并标注证据充分度与信心区间；比较候选方案的预期净收益，而不是把不同量纲乘成一个分数。

#### 工程场景

多团队后台最痛的是发布互相阻塞，优先优化可修改性与部署独立性；大促 H5 最痛的是首屏和容灾，则优先性能预算、静态兜底与开关。两者不应复制同一套架构。

#### 反例 / 踩坑

先决定上微前端、SSR 或 Monorepo，再倒推理由；只写「高性能、高可用」，没有分位值、观察窗口和故障恢复目标。

#### 资深回答模板

「我先列出前三项质量属性及阈值，分开风险暴露与治理成本，再说明冲突。反例是先选框架；证据来自基线、实验与故障演练；最后反思未满足的属性和复审触发器。」
:::

**追问链：**
1. 业务要首屏更快又要更多个性化，如何取舍？
2. 指标暂时拿不到基线时如何决策？
3. 哪些决策应延迟到信息更充分时？

::: details 追问参考答案

**1. 业务要首屏更快又要更多个性化，如何取舍？**

先约束个性化不能阻塞核心内容：首屏输出稳定骨架与通用数据，个性化按价值分级并延后加载，必要时以缓存或边缘计算换取时延，但接受短暂非个性化。产品 Owner 确认哪些差异影响转化，架构 Owner 管依赖预算；用分桶实验同时验证用户性能分位、转化和布局稳定性，再决定扩大范围。

**2. 指标暂时拿不到基线时如何决策？**

基线缺失时只做可逆、低成本决策，不用行业均值冒充自身事实。先通过日志、RUM 或抽样测试建立最小观测，风险较高的方案用 PoC 比较区间和失败模式。架构 Owner 标注假设、证据等级和复审日期，数据 Owner 校验采样偏差；以试点结果和事故演练验证，达到信息门槛后再锁定长期结构。

**3. 哪些决策应延迟到信息更充分时？**

可逆且当前不影响关键质量属性的选择应延迟，例如状态库、拆仓粒度或通用抽象；涉及数据不可逆写入、安全边界和公开契约的决策不能拖延。提案 Owner 记录延迟成本、最后决策时点与触发条件，相关领域 Owner 审核边界；通过需求变化频率、替换实验和风险清单验证，避免延迟变成无人负责。

:::

### Q2. 分层架构怎样避免只剩目录分组？

**考察点：** 职责、契约、依赖方向、可替换性

::: details 参考答案
有效分层必须同时具备职责边界、稳定契约和依赖规则。常见方向是 `页面/交互 → 应用用例 → 领域规则 → 基础设施端口实现`，领域层不直接依赖路由、组件库和 HTTP 客户端。

用静态依赖检查、包导出白名单和架构测试约束跨层引用。衡量标准不是目录整齐，而是更换请求库、路由或 UI 框架时，核心业务规则无需跟着重写。
:::

**追问：** 一个简单 CRUD 项目是否也需要四层？

::: details 追问参考答案

不需要机械套四层，约束是业务规则简单、生命周期短且团队很小；可先保留页面、用例与 API 适配的最小边界，让依赖仍朝业务语义流动。取舍是少一些隔离，换更低认知成本。模块 Owner 负责观察变化，当测试困难、规则复用或替换成本上升时再拆层；以依赖图、变更影响和替换请求库的测试验证结构是否足够。

:::

### D2. 如何设计依赖方向并处理跨层调用？

**考察点：** 依赖倒置、端口适配器、循环依赖

::: details 参考答案
#### 基础结论

依赖应指向更稳定、更接近业务规则的一侧；跨层能力通过接口、事件或应用服务进入，禁止为省一步而反向引用页面和 Store。

#### 原理深挖

稳定依赖原则关注变化频率，不等同于「底层永远稳定」。领域定义 `OrderRepository` 端口，基础设施实现 HTTP 适配器；组合根负责注入。这样业务规则可脱离浏览器和后端联调测试。

#### 工程场景

支付结果页需要查询、埋点和导航：应用用例返回领域结果，页面决定导航，埋点适配器观察用例事件。领域代码不调用 Router，也不拼上报字段。

#### 反例 / 踩坑

所有模块互相从 `index.ts` 导入形成环；把依赖注入理解为给每个函数传十几个对象；用全局事件总线隐藏真实依赖。

#### 资深回答模板

「我先按变化原因分层，再画允许的依赖箭头。反例是全局事件总线隐藏依赖；证据用依赖图、架构测试和替换实验；最后反思抽象是否增加了认知成本。」
:::

**追问链：**
1. 类型定义应该放调用方还是提供方？
2. 为消除循环依赖而抽 `common` 包有什么风险？
3. 何时允许临时越层，如何偿还？

::: details 追问参考答案

**1. 类型定义应该放调用方还是提供方？**

类型随契约所有权放置：提供方拥有稳定公开响应与命令契约，调用方拥有仅服务自身的视图模型；端口由需要它的一侧定义，避免基础设施反向控制领域。取舍是少量映射成本换解耦。契约 Owner 管版本，消费方 Owner 管适配；用编译契约测试、运行时高风险边界校验和替换实现实验验证依赖方向。

**2. 为消除循环依赖而抽 `common` 包有什么风险？**

把环两端代码搬进 `common` 往往只是隐藏共同变化原因，容易形成高扇入、无 Owner 的大泥球，扩大故障与发布影响面。约束是只有语义稳定且消费者一致的契约才能共享。原领域 Owner 共同负责拆边，架构 Owner 审批例外；用依赖图、变更牵连范围和独立测试验证，若仍需互知内部状态，应重划边界而非继续上提。

**3. 何时允许临时越层，如何偿还？**

仅在事故止损、硬期限且正规接口来不及建立时允许临时越层，且不得绕过服务端授权或数据一致性边界。取舍是短期交付换未来利息。变更 Owner 必须登记非法依赖、影响、隔离措施、到期日和替代方案，领域 Owner 验收拆除；架构测试对该边做定向豁免并禁止新增消费者，到期由 CI 与债务看板复核。

:::

### Q3. 如何按领域拆前端模块，而不是按页面机械拆分？

**考察点：** 业务能力、聚合变化、公开契约

::: details 参考答案
模块边界应围绕稳定业务能力和共同变化原因，例如订单、履约、结算，而不是首页、列表页、详情页。模块内部可包含页面、用例、状态和 API 适配器，对外只暴露用例、路由入口和稳定类型。

判断边界可看：需求是否总一起变、数据是否有明确所有者、是否能独立测试和发布。跨域查询通过组合层或专门读模型完成，避免直接读另一个域的内部 Store。
:::

**追问：** 搜索页同时展示商品、订单和客户，应该归哪个域？

::: details 追问参考答案

搜索页属于组合层或独立查询体验，不应硬塞进任一领域；商品、订单、客户仍各自拥有数据和公开查询契约，页面只编排读模型与导航。取舍是增加一层聚合，换取领域自治。搜索体验 Owner 负责排序与降级，各领域 Owner 负责字段语义；用契约测试、跨域变更影响和单域故障时的部分可用性验证边界。

:::

### D3. 如何识别并治理「共享模块」大泥球？

**考察点：** 内聚、复用成本、所有权、演进

::: details 参考答案
#### 基础结论

共享不是「两处用到就抽」，而是语义一致、变化节奏一致且有明确 Owner。优先复制小而不稳定的代码，晚于事实建立抽象。

#### 原理深挖

共享包增加消费者数量，也增加变更协调成本。评估时分别记录风险暴露（故障影响面、供应链与兼容风险）和治理成本（评审、发布、迁移与支持），不能混成一个「风险分」。应区分稳定内核（金额、资源—动作词汇）、平台能力（监控 SDK）和业务复用（组织选择器）；三者版本与兼容策略不同。

#### 工程场景

统计共享包的入边数量、破坏性发布次数和变更牵连项目数。把 `shared` 按能力拆包，限制深层导入，废弃 API 提供迁移窗口和使用方清单。

#### 反例 / 踩坑

把所有 DTO、常量、Hook 都扔进 `common`；共享包没有负责人；一次修改要求十个应用同日升级。

#### 资深回答模板

「我用语义一致性和共同变化判断是否共享，分别估算风险暴露与治理成本。反例是万能 common 包；证据看扇入、牵连发布和迁移工时；最后反思复制是否反而更便宜。」
:::

**追问链：**
1. 重复三次就抽象是否总成立？
2. 共享类型与共享运行时代码要不要同包？
3. 如何安全拆解已有大包？

::: details 追问参考答案

**1. 重复三次就抽象是否总成立？**

不成立，次数只是发现信号；只有语义、变化原因和生命周期一致才值得抽象，否则复制能保留自治。约束是先评估消费者数量、稳定度与迁移成本，取舍复用收益和协调成本。候选能力 Owner 负责收集真实用例，消费方参与评审；通过后续变更是否同步、试点接入成本和撤回难度验证，未稳定前允许受控重复。

**2. 共享类型与共享运行时代码要不要同包？**

通常分包：纯契约类型可低成本被多端消费，运行时代码带平台、依赖和安全风险，耦合升级节奏；但同一能力且版本必须原子演进时可同包。契约 Owner 与实现 Owner 分别负责兼容策略，发布 Owner 管依赖范围；用产物检查、消费者矩阵和独立升级测试验证，避免类型导入意外携带运行时代码。

**3. 如何安全拆解已有大包？**

先用依赖图与变更历史识别稳定内核和业务簇，冻结新增深层导入，再建立版本化公开入口与兼容适配层，按消费者逐批迁移。取舍是短期双轨成本换可回滚性。大包 Owner 维护使用方清单，各领域 Owner 承担迁移；用契约测试、构建影响、故障率和旧入口调用量验证，归零后再删除，不能一次性搬家。

:::

## 二、状态、数据流与接口边界

### Q4. 如何划分组件状态、应用状态、服务端状态和 URL 状态？

**考察点：** 状态所有权、生命周期、可分享性

::: details 参考答案
状态按所有权和生命周期放置：临时交互留在组件；跨页面会话与工作流放应用 Store；服务端数据交给查询缓存管理；筛选、分页和可分享视图进入 URL。派生值尽量计算，不做双份存储。

每类状态明确单一写入口、失效规则和恢复策略。刷新页面后必须恢复的状态不能只藏在组件内；权限与价格等权威数据不能只相信本地缓存。
:::

**追问：** 多步骤表单草稿应该放哪里？

::: details 追问参考答案

按恢复范围决定：仅当前步骤的临时输入留组件，跨页流程放应用状态；要求刷新、跨设备或长期恢复时持久化到服务端草稿，URL 只保存可公开定位信息。取舍是恢复能力与隐私、同步复杂度。流程 Owner 定义状态机，数据 Owner 定保留策略；用刷新、断网、并发编辑和退出清理场景验证，敏感字段不得无期限落本地。

:::

### D4. 复杂前端如何保持单向数据流又不过度集中？

**考察点：** 命令查询分离、事件、事务边界

::: details 参考答案
#### 基础结论

单向数据流的目标是让写入可追踪，不是把所有数据塞进一个 Store。读取可组合，写入应经过明确用例或命令入口。

#### 原理深挖

前端应用层只编排用户流程、展示进度、触发查询失效和提供可恢复 UI；跨服务事务、一致性、幂等记录与补偿由后端领域服务或工作流负责。前端不能以本地 Store、事件顺序或重试模拟跨服务强一致。

#### 工程场景

「审批通过」先防重复提交，调用权威 API，成功后更新详情并失效列表，再异步上报。失败保留用户输入并映射可恢复错误；不会让三个组件各自改同一份状态。

#### 反例 / 踩坑

把 Store 当数据库；监听器互相触发形成隐式链；乐观更新失败后没有回滚快照；缓存键没有实体和租户维度。

#### 资深回答模板

「我先定义状态所有者和写入口，再区分命令与查询。前端传递幂等键并呈现可恢复状态，服务端保障跨服务一致性；反例是前端双写两个服务。证据看重复写、未知结果恢复率与任务完成率，并反思职责是否越界。」
:::

**追问链：**
1. 什么时候适合乐观更新？
2. 多标签页同时编辑如何处理？
3. 事件顺序错乱时怎样恢复？

::: details 追问参考答案

**1. 什么时候适合乐观更新？**

适合成功率高、可逆、冲突可检测且失败代价低的操作，如收藏或排序；支付、权限和不可逆写入不应只靠乐观结果。取舍是即时反馈换回滚复杂度。用例 Owner 定义幂等键、快照和冲突提示，服务端 Owner 提供权威版本；用失败注入、重复提交和乱序响应测试回滚及最终状态。

**2. 多标签页同时编辑如何处理？**

先明确并发语义，不能让最后写入无提示覆盖。低风险草稿可用版本号加冲突提示，高风险实体由服务端条件写入、租约或合并策略裁决；BroadcastChannel 仅改善本机体验，不是权威锁。领域 Owner 定冲突规则，前端 Owner 管提示与恢复；用双标签、跨设备和断网重连验证无静默丢失。

**3. 事件顺序错乱时怎样恢复？**

前端按实体版本、序列号或服务端时间线拒绝陈旧事件，发现缺口后重新拉取权威快照，而不是猜测重排跨服务事件。取舍是额外查询换状态可信。后端事件 Owner 保证版本与幂等语义，前端状态 Owner 实现去重和重同步；通过重复、延迟、丢失事件注入验证最终收敛，并记录恢复失败。

:::

### Q5. API 适配层应该负责什么，不应该负责什么？

**考察点：** DTO 转换、契约、领域隔离

::: details 参考答案
API 适配层负责传输协议、鉴权头、超时取消、DTO 到领域模型转换、错误归一化和 TraceId 透传；不负责页面提示、路由跳转和复杂业务决策。

以 OpenAPI 或等价契约生成基础类型；运行时校验集中在不可信输入、高风险写入响应、配置和外部第三方边界，普通内部只读响应不必无差别重复校验。后端字段改名时，优先让变化收敛在适配器，而不是传播到全部组件。
:::

**追问：** 后端返回成功但字段缺失，前端应怎样处理？

::: details 追问参考答案

把它视为契约违约而非正常空值：适配层在高风险响应边界校验，能安全降级则保留旧数据或展示局部错误，不能构造业务默认值掩盖问题。取舍是运行时校验成本与错误扩散风险。API 契约 Owner 修复源头，页面 Owner 定降级体验；用契约测试、畸形响应注入和 TraceId 关联验证告警、隔离与恢复。

:::

### D5. 如何设计统一错误模型和恢复策略？

**考察点：** 错误分类、用户体验、重试、观测

::: details 参考答案
#### 基础结论

错误至少区分业务拒绝、认证授权、网络瞬态、限流、服务故障、客户端缺陷。每类定义用户提示、是否重试、是否上报、是否降级和责任归属。

#### 原理深挖

HTTP 状态、业务码和用户文案是不同维度。统一错误对象可含 `kind/code/retryable/traceId/cause`。重试只用于幂等且瞬态的操作，采用退避和抖动，并受总时限控制。

#### 工程场景

列表超时保留旧数据并提供重试；提交订单未知结果先按幂等键查询状态，不能直接再次创建；401 只允许一个刷新 Token 请求，其余请求排队或失败。

#### 反例 / 踩坑

拦截器遇错一律弹 Toast；所有 401 都跳登录造成并发风暴；静默吞错；前端生成的错误码与后端无法关联。

#### 资深回答模板

「我先按可恢复性分类错误，再定义体验与技术动作。反例是一律 Toast 或重试；证据看恢复率、重复写和 Trace 关联率；最后反思分类是否遗漏未知结果。」
:::

**追问链：**
1. 全局错误边界和局部错误态如何分工？
2. 离线恢复后请求队列如何处理？
3. 第三方 SDK 报错如何隔离？

::: details 追问参考答案

**1. 全局错误边界和局部错误态如何分工？**

局部边界处理可预期、可恢复的模块失败并保留其他功能；全局边界只兜住未分类异常，提供重载、回退与诊断入口，不能替代业务错误态。取舍是边界越细恢复越好但维护更重。页面 Owner 定局部策略，壳 Owner 管全局兜底；用组件抛错、异步拒绝和路由切换故障注入验证隔离范围。

**2. 离线恢复后请求队列如何处理？**

仅排队可幂等、可过期且用户明确预期的命令，记录幂等键、依赖顺序、主体与租户；恢复后先重新鉴权和校验前置版本，冲突或过期交给用户确认。取舍是可用性换陈旧写入风险。用例 Owner 定重放规则，服务端 Owner 保证幂等；用跨账号、乱序、部分成功和重复恢复测试验证。

**3. 第三方 SDK 报错如何隔离？**

第三方能力经内部适配器、超时和熔断接入，非关键 SDK 延迟初始化并允许禁用；运行在主线程的脚本无法完全隔离时，应限制权限和采集字段。平台 Owner 负责版本、开关与退出方案，业务 Owner 定降级体验；通过脚本加载失败、长任务和异常风暴演练验证核心路径不受阻且告警可归因。

:::

### Q6. 前端权限架构的边界是什么？

**考察点：** 鉴权权威、体验控制、策略一致性

::: details 参考答案
后端是授权权威，前端负责入口隐藏、路由拦截、字段展示和操作前提示，不能把「看不见按钮」当安全。组织层统一「资源类型—动作」词汇，并分别映射前端能力项与服务端策略；UI 标识和 API 策略不能共用一个码冒充同一授权判断。

前端消费带主体、租户、策略版本和有效期的能力快照。服务端按主体、资源实例、租户、动作、上下文和策略版本权威授权，并记录允许/拒绝、命中策略和 TraceId 的决策日志。敏感数据应由服务端裁剪或脱敏，不能先全量下发再由前端隐藏。
:::

**追问：** 离线应用如何做权限判断？

::: details 追问参考答案

离线时只能使用服务端签发、带主体、租户、策略版本和短有效期的能力快照改善体验，不能获得新的高风险权限；过期或无法证明资源实例授权时默认拒绝写操作。取舍是离线可用性与越权风险。权限服务 Owner 定签名和失效语义，客户端 Owner 管缓存清理；用过期、撤权、切租户和篡改快照测试验证。

:::

### D6. 多应用如何统一权限模型又保持自治？

**考察点：** 策略分发、缓存、兼容、故障模式

::: details 参考答案
#### 基础结论

统一的是资源—动作词汇、映射规则、主体上下文和审计协议，不一定统一每个应用的 UI 实现。应用消费版本化能力快照，服务端仍逐请求对资源实例执行权威授权。

#### 原理深挖

集中策略中心降低口径漂移，却形成关键依赖。应提供短期缓存、签名版本、灰度发布和旧策略回退；高风险写操作在策略中心不可用时默认拒绝。

#### 工程场景

壳应用下发用户上下文，各业务模块用统一 SDK 判断展示；API 网关或服务执行权威策略。策略变更带版本号，监控拒绝率突增，并支持按租户回滚。

#### 反例 / 踩坑

子应用各写一套角色字符串；权限快照永久放在 localStorage；策略中心故障时全部默认放行；只测正向用例。

#### 资深回答模板

「我统一资源—动作词汇及映射，前端快照只改善体验，服务端按资源实例授权。反例是 UI/API 同码；证据看越权用例、租户隔离和决策日志；最后反思集中服务故障策略。」
:::

**追问链：**
1. 权限变更如何在长会话中生效？
2. 多租户切换如何避免串权？
3. 策略升级如何做兼容测试？

::: details 追问参考答案

**1. 权限变更如何在长会话中生效？**

能力快照必须有短有效期和策略版本，可通过推送提示失效，但每次敏感请求仍由服务端按当前策略授权。取舍是刷新频率与一致性、负载之间平衡。权限服务 Owner 定撤权传播目标，应用 Owner 在版本变化时清缓存并更新 UI；用会话中撤权、推送丢失和策略服务故障演练验证最终不越权。

**2. 多租户切换如何避免串权？**

租户是鉴权与缓存的一级边界：切换时获取新租户上下文，取消旧请求，清理 Store、查询缓存和离线队列，所有缓存键与观测字段都带租户维度。身份平台 Owner 管令牌或上下文，应用 Owner 管状态重建；用快速切换、旧响应晚到和多标签页测试验证旧租户数据不能回填。

**3. 策略升级如何做兼容测试？**

策略与能力快照都版本化，先建立旧客户端—新策略、新客户端—旧策略矩阵，新增动作默认不让旧端误解，破坏性语义走扩展—迁移—收缩。权限平台 Owner 维护契约样例，领域 Owner 提供允许与拒绝用例；影子评估对比决策差异，按租户灰度并监控拒绝率后再推广。

:::

## 三、路由、组件与平台化

### Q7. 路由与布局架构如何支持多端和多业务？

**考察点：** 路由契约、布局组合、端差异

::: details 参考答案
路由描述业务导航语义，布局提供壳能力。将路由元信息做成类型化契约，包含权限、标题、缓存、埋点和布局槽位；端差异由路由适配器映射到 Web、WebView 或小程序导航。

布局用组合而不是业务页面直接改壳。深链、返回栈、登录恢复和 404/403 是必须验证的故障路径；不能只测菜单点击。
:::

**追问：** 动态路由应由后端下发到什么粒度？

::: details 追问参考答案

后端应下发稳定的导航意图、资源标识、参数和能力要求，不下发任意组件路径、脚本或前端实现细节；客户端用版本化注册表映射到本地路由。取舍是配置灵活性与供应链、兼容风险。导航契约 Owner 管 Schema，业务 Owner 注册实现；用未知路由、旧客户端、越权菜单和签名配置测试验证拒绝与降级。

:::

### D7. 如何设计可演进的应用壳与扩展点？

**考察点：** 插件契约、生命周期、兼容性

::: details 参考答案
#### 基础结论

壳只拥有跨业务稳定能力：会话、导航、布局、主题、监控和全局降级。业务通过声明式注册表接入，禁止依赖壳内部组件和 Store。

#### 原理深挖

扩展点本质是版本化协议，应定义输入、生命周期、失败隔离、超时和能力探测。壳与业务之间使用最小上下文，避免暴露可随意修改的全局对象。

#### 工程场景

业务注册路由、菜单和顶部动作；壳在激活时注入用户与观测接口。某插件初始化超时则跳过并展示局部故障，不阻断整个工作台。

#### 反例 / 踩坑

业务通过相对路径导入壳源码；扩展点无限增加且无 Owner；壳升级要求所有业务同日发版；插件异常拖垮启动。

#### 资深回答模板

「我把壳限制为稳定公共能力并版本化接入点。反例是业务深层导入壳源码；证据看兼容测试、启动故障隔离和升级等待；最后反思某能力是否应留在业务。」
:::

**追问链：**
1. 壳与业务谁拥有面包屑？
2. 如何处理旧插件不认识的新能力？
3. 什么时候应拆成独立应用？

::: details 追问参考答案

**1. 壳与业务谁拥有面包屑？**

壳拥有渲染、无障碍和导航一致性，业务拥有领域层级、标题及参数语义，通过声明式路由契约提供条目；不允许业务直接修改壳 Store。壳 Owner 维护协议，领域 Owner 保证语义正确；用深链、动态参数、返回栈和无权限节点测试验证，协议不能表达时先扩展契约而非越层。

**2. 如何处理旧插件不认识的新能力？**

扩展协议采用能力探测与可选字段，壳只在插件声明支持后启用新能力；关键不兼容变更保留旧协议适配窗口，不能要求同步升级。取舍是兼容层成本换独立发布。壳 Owner 定版本与弃用期，插件 Owner 负责升级；用版本矩阵、未知字段和初始化失败测试验证旧插件可继续运行或明确降级。

**3. 什么时候应拆成独立应用？**

当领域所有权、发布节奏、故障边界或合规权限长期独立，且协调成本已高于运行时与治理成本时再拆；页面数量不是依据。提案 Owner 需给出现状证据和退出方案，平台 Owner 评估壳接入成本；先做边界清晰模块试点，用发布等待、故障隔离、性能与认知负载验证，收益不足则停止拆分。

:::

### Q8. 组件、业务组件与设计系统如何分层？

**考察点：** Token、模式、领域语义、所有权

::: details 参考答案
设计系统包含原则、Token、基础组件、交互模式与治理，不等于组件仓库。基础组件保持无业务语义；模式组件沉淀表单、反馈等组合；业务组件带领域假设，应放在对应领域包。

每层有兼容策略和 Owner，以接入率、重复实现、缺陷率和升级耗时衡量价值。跨端统一 Token 与交互语义，不强求 DOM 和组件代码完全复用。
:::

**追问：** 基于第三方组件库时还需要自己的设计系统吗？

::: details 追问参考答案

需要，但不必重写基础组件。第三方库解决实现，自有设计系统负责品牌 Token、交互模式、无障碍、业务约束和升级治理；通过薄封装或主题扩展控制差异，避免全量二次封装。设计系统 Owner 管规范与版本，组件 Owner 管适配；以一致性审查、可访问性测试、升级工时和业务采用率验证价值。

:::

### D8. 平台化能力何时值得建设，何时是过度抽象？

**考察点：** 投资回报、产品化、采用率

::: details 参考答案
#### 基础结论

平台化适合重复需求稳定、消费者足够多、维护责任明确的场景。先用两三个真实业务验证，再抽成自助能力。

#### 原理深挖

平台收益是节省的重复成本和风险下降，成本包括建设、迁移、支持与机会成本。可用「消费者数 × 单次节省 − 年度维护成本」粗算，并设置停止投资条件。

#### 工程场景

统一请求 SDK 已在 5 个应用重复，事故口径不一，可先抽最小内核和适配层；接入时长、错误率和版本覆盖率进入平台 SLO。

#### 反例 / 踩坑

没有用户就先做万能低代码；平台团队只发版本不负责接入体验；强制迁移却没有兼容层；功能按最大客户不断膨胀。

#### 资深回答模板

「我先证明重复成本与共同需求，再用试点验证最小平台。反例是无用户先建万能平台；证据看接入时间、采用率和故障下降；最后反思维护成本与停止投资条件。」
:::

**追问链：**
1. 业务拒绝接入时先查什么？
2. 平台是否应该强制统一？
3. 如何避免平台团队成为交付瓶颈？

::: details 追问参考答案

**1. 业务拒绝接入时先查什么？**

先查真实接入成本、能力缺口、迁移风险和平台 SLO，而不是归因为不配合；若业务语义不同，强制统一会制造适配债。平台产品 Owner 访谈消费者，业务 Owner 提供替代方案成本；用一条真实链路试点，对比接入时长、故障与维护负担，证据显示净收益后再推广。

**2. 平台是否应该强制统一？**

只强制安全、合规、观测协议和跨应用公共契约等底线；实现方式与业务差异保留自治，并提供有期限、可审计的例外。取舍是规模一致性与局部效率。治理 Owner 定强制级别和申诉流程，领域 Owner 对例外风险负责；用合规检查、采用率和例外复审验证，规则阻碍交付时调整而非绕过。

**3. 如何避免平台团队成为交付瓶颈？**

平台应提供稳定自助接口、模板、文档和兼容策略，让业务可独立接入；定制需求按通用价值进入路线，紧急情况允许受控扩展点。平台 Owner 对接入 SLO 与支持容量负责，业务 Owner 对集成负责；以等待时间、首次成功率、支持工单和版本覆盖验证，持续高等待则拆分职责或收窄平台范围。

:::

## 四、性能、稳定性、安全与降级

### Q9. 性能预算应如何进入架构治理？

**考察点：** 指标、预算分配、回归

::: details 参考答案
先按用户和页面类型选指标：内容首屏关注 LCP，交互密集页关注 INP；后台重点看路由可用率、INP、长任务占比和关键任务完成时长，不把「大表格」本身当指标。预算分到壳、业务包、第三方脚本和接口链路，并以真实用户 P75/P95 复核。

架构层关注加载边界、缓存策略、渲染模式和第三方治理；具体打包插件属于工程化模块。超预算需有例外负责人、影响说明和偿还日期。
:::

**追问：** 实验室指标变好，真实用户指标变差，如何排查？

::: details 追问参考答案

先核对实验室与 RUM 的用户、设备、网络、路由、缓存和版本分桶是否同口径，再按地域、机型、灰度组和第三方脚本切片，排查长任务、接口尾延迟与采样偏差。性能 Owner 负责预算与归因，业务 Owner 评估体验影响；用同版本可重复测试、真实会话路径和关闭变量的对照实验验证，不能只优化单一实验室分数。

:::

### D9. 如何设计前端稳定性目标和故障预算？

**考察点：** SLI/SLO、错误预算、业务影响

::: details 参考答案
#### 基础结论

以用户可感知结果定义 SLI，例如核心页面可用率、关键操作成功率和白屏率，而不是只看 JS Error 数量。SLO 应有观察窗口和排除规则。

#### 原理深挖

错误预算把可靠性与交付速度连接起来：预算充足可加速实验，消耗过快则冻结高风险发布并优先修复。不同链路按业务价值设不同目标。

#### 工程场景

结算提交成功率按 28 天滚动窗口设 99.95%，并拆分前端、API、第三方支付影响。发布后 30 分钟燃烧率突增时自动停止灰度并回滚。

#### 反例 / 踩坑

承诺 100% 可用；把用户取消算故障；指标无法从监控计算；错误预算只用于处罚团队。

#### 资深回答模板

「我用用户结果定义含分母、窗口和排除项的 SLI。反例是只数 JS Error；证据看燃烧率、任务成功和事故影响；最后反思 SLO 是否过松、过严或被错误归因。」
:::

**追问链：**
1. 新系统无历史数据如何定 SLO？
2. 第三方故障是否应排除？
3. 低流量链路如何避免百分比失真？

::: details 追问参考答案

**1. 新系统无历史数据如何定 SLO？**

先依据业务损失和最低用户承诺设临时目标，不从成熟系统复制小数点；上线前用容量测试、依赖 SLO 与演练估算区间，上线后积累完整窗口再校准。服务 Owner 对目标和误差预算负责，产品 Owner 确认关键旅程；通过告警可计算性、故障注入和首个观察周期验证，目标过松或不可达都要复审。

**2. 第三方故障是否应排除？**

对外用户 SLI 通常不排除，因为用户仍然失败；内部归因可单列第三方贡献，并为合同、降级和架构决策建立辅助指标。取舍是责任分析不能稀释用户承诺。服务 Owner 拥有端到端结果，供应商 Owner 推动依赖治理；用故障演练验证降级，复盘时同时看总失败与依赖分解，排除项须预先书面定义。

**3. 低流量链路如何避免百分比失真？**

低流量场景同时报告成功数、失败数和观察时长，采用更长窗口、合并有相同语义的样本，并以连续失败、绝对故障数或合成探测补充百分比；不能用少量成功宣称高可用。指标 Owner 定分母与告警规则，业务 Owner 确认链路价值；用历史回放和故障注入检验告警灵敏度与误报。

:::

### Q10. 前端可观测性最小闭环包含什么？

**考察点：** 版本、上下文、关联、告警

::: details 参考答案
最小闭环是发现、定位、止损、复盘：错误和性能事件携带版本、环境、匿名用户、路由、设备、灰度组与 TraceId；SourceMap 受控解析；告警关联发布并指向 Runbook 和 Owner。

采样、脱敏、去重和限流必须前置。大盘不等于闭环，应追踪 MTTD、MTTR、告警有效率与重复事故率。
:::

**追问：** 如何检测「接口都成功但页面不可用」？

::: details 追问参考答案

增加用户结果型 SLI：路由完成、关键元素可交互、核心动作闭环、白屏与长任务，而非只看 HTTP 状态；关键页面可布置受控合成探测，并用 actionId 关联前端 Span 与请求。可观测平台 Owner 管采集可靠性，页面 Owner 定成功语义；通过返回空数据、渲染异常和主线程阻塞注入验证能告警且定位到版本。

:::

### D10. 如何设计端到端故障定位链路？

**考察点：** TraceId、会话、版本归因、隐私

::: details 参考答案
#### 基础结论

区分四类标识：`sessionId` 关联一次访问会话，`actionId` 关联一次用户意图，`traceId` 关联一条分布式调用链，`spanId` 标识链路中的单次操作。它们不可互相替代；通过 W3C Trace Context 的 `traceparent`/`tracestate` 传播 Trace 与 Span，并把 session/action 作为受控业务属性关联版本和配置快照。

#### 原理深挖

Trace 与 Span 在请求边界按 W3C 规范传播，异步任务通过新 Span、Span Link 或受控业务关联保留因果关系；不能自行拼接 TraceId。观测数据遵循数据最小化：字段白名单、HMAC 轮换标识、留存期限和访问审计。

#### 工程场景

用户点击提交生成 actionId；SDK 创建客户端 Span 并携带 `traceparent`，后端继续该 Trace 并返回可查询关联。事故面板用 session/action 串用户过程，用 trace/span 定位依赖耗时，再按版本和租户聚合归因。

#### 反例 / 踩坑

全量录屏和采集输入框；每个 SDK 自定义用户 ID；日志只有错误字符串；SourceMap 公开部署。

#### 资深回答模板

「我区分 session、action、trace、span，并按 W3C 传播调用上下文。反例是把四种 ID 混用；证据看跨端关联率和定位时长；最后反思采样、隐私和断链位置。」
:::

**追问链：**
1. TraceId 缺失时如何降级关联？
2. 会话回放何时不应使用？
3. 监控 SDK 自身故障如何防扩散？

::: details 追问参考答案

**1. TraceId 缺失时如何降级关联？**

不能由前端伪造同一条跨服务 Trace。缺失时保留时间窗口、版本、路由、actionId 和匿名 sessionId 等受控属性做概率关联，并明确置信度；新请求可正常创建新 Trace，断点处单独告警。观测平台 Owner 修传播链路，服务 Owner 补边界；用断头注入与日志抽样验证关联召回及误配风险。

**2. 会话回放何时不应使用？**

涉及密码、支付、医疗、未成年人、内部敏感后台或无法可靠遮蔽输入时不应录制；高风险页面优先结构化事件和合成探测。取舍是定位细节与隐私合规。隐私 Owner 审批采集范围，页面 Owner 维护遮蔽清单；上线前做字段审计、抽样人工检查和删除演练，无法证明最小化就关闭回放。

**3. 监控 SDK 自身故障如何防扩散？**

SDK 必须异步、限流、采样、批量且失败静默降级，设 CPU、内存、网络预算和熔断开关；不得阻塞渲染或递归上报自身错误。平台 Owner 负责版本与远程禁用，应用 Owner 控制接入边界；用上报端超时、异常风暴、存储满和弱网测试验证核心操作不受影响，并以独立健康指标观测 SDK。

:::

### Q11. 前端安全架构应建立哪些边界？

**考察点：** 威胁模型、输入输出、供应链、密钥

::: details 参考答案
从资产、信任边界和攻击面做威胁建模：优先使用 `Secure`、`HttpOnly`、合适 `SameSite` 的 Cookie 管理 Web 会话，并用 CSRF Token / Origin 校验防跨站请求；公开客户端登录采用 OIDC Authorization Code + PKCE，不在浏览器保存客户端秘密。

输出侧用框架默认转义、富文本白名单净化和 Trusted Types 控制危险 DOM Sink；CSP 使用逐响应 nonce 或稳定资源 hash，结合 `frame-ancestors` / `X-Frame-Options` 防点击劫持。第三方脚本优先固定精确版本并自托管；无法自托管时，经代理做内容与域名审查，放入受限 iframe、Worker 或独立页面隔离能力和故障。SRI 只适合 URL 与内容固定、跨域 CORS 配置可控的静态资源，不适合内容频繁变化的地址。

供应链需锁文件、来源与完整性校验、依赖审计、构建权限隔离和制品签名/溯源。浏览器环境变量不是秘密；高风险动作仍由服务端授权、防重放并审计。
:::

**追问：** 使用 HttpOnly Cookie 后还需要防 XSS 吗？

::: details 追问参考答案

需要。HttpOnly 只阻止脚本直接读取 Cookie，XSS 仍可借用户会话发请求、读取页面敏感数据或篡改交易；还需框架转义、富文本净化、CSP/Trusted Types 和危险 Sink 治理，服务端继续授权与防重放。安全 Owner 定基线，业务 Owner 修输入输出边界；用覆盖存储型、反射型和 DOM 型路径的测试验证，而非只扫一个登录页。

:::

### D11. 如何为前端设计分级降级与灾备？

**考察点：** 关键路径、功能开关、静态兜底、演练

::: details 参考答案
#### 基础结论

先按业务价值把功能分为必须、可降级、可关闭。降级动作需预置、可观测、可回滚，并在真实环境定期演练。

#### 原理深挖

故障可能来自 API、CDN、配置、第三方和客户端版本。降级应减少依赖和状态复杂度，而不是换一条同样脆弱的链路；开关控制面与数据面要隔离。

#### 工程场景

推荐服务不可用时隐藏模块并保留搜索；配置中心故障使用签名的最后已知好版本；CDN 故障切备用域名；关键静态页可由边缘缓存兜底。

#### 反例 / 踩坑

事故时临时写降级代码；所有开关依赖同一个故障服务；关闭功能后仍发请求；兜底数据过期且没有明显标识。

#### 资深回答模板

「我先画关键路径依赖图，再定义依赖失败时的用户结果。反例是事故时临时写降级；证据来自演练、RTO 和降级成功率；最后反思控制面是否存在共同故障。」
:::

**追问链：**
1. 降级开关误开如何防止？
2. 缓存兜底的数据一致性如何说明？
3. 灾备切换后如何安全恢复？

::: details 追问参考答案

**1. 降级开关误开如何防止？**

高影响开关采用最小权限、双人审批、作用域与有效期限制，默认只影响稳定分桶；配置需 Schema 校验、签名、审计和一键回退，控制面故障不应改变已知好状态。平台 Owner 管机制，业务 Owner 对开关语义负责；用误配置、过期和控制面不可用演练验证爆炸半径与恢复。

**2. 缓存兜底的数据一致性如何说明？**

兜底应明确是最后已知好版本还是可接受的陈旧读，展示数据时间和功能限制；价格、权限等高风险数据过期时拒绝写入或重新向权威服务确认，前端不能宣称跨服务一致。数据 Owner 定最大陈旧边界，页面 Owner 定提示；用过期、回源失败和版本冲突测试验证不产生误导性提交。

**3. 灾备切换后如何安全恢复？**

先确认主链路健康与数据追平，再按只读、低风险写入、全量能力分阶段回切，避免两侧同时接受无协调写入；缓存和配置按版本失效。灾备 Owner 负责切换状态机，领域服务 Owner 负责一致性校验，前端 Owner 管功能开关；通过对账、幂等重放和小流量观察验证后扩大。

:::

## 五、Monorepo、依赖与发布治理

### Q12. 何时选择 Monorepo，何时保持多仓？

**考察点：** 协作拓扑、发布自治、权限隔离

::: details 参考答案
共享代码多、原子变更频繁、团队治理统一时，Monorepo 可降低跨仓协调成本；生命周期、权限、合规和技术栈差异大时，多仓更自然。仓库形态不能替代模块边界。

决策要量化跨仓联动次数、CI 时长、代码所有权和发布耦合。无论哪种形态，都要有清晰 Owner、公开 API、版本契约和依赖图。
:::

**追问：** Monorepo 是否意味着所有包一起发布？

::: details 追问参考答案

不意味着。仓库统一只提供原子变更和治理视图，各包仍可按独立版本、固定版本组或应用制品发布；选择取决于契约耦合和消费者升级能力。取舍是发布自治与版本矩阵复杂度。发布平台 Owner 管变更集和依赖图，包 Owner 定兼容策略；用受影响项目测试、独立回滚和消费者矩阵验证没有隐式同步发布要求。

:::

---

### D12. 如何治理 Monorepo 中的依赖方向与所有权？

**考察点：** 依赖图、分区、CODEOWNERS、例外

::: details 参考答案
#### 基础结论

按业务域与层次划分包标签，定义允许的依赖矩阵；Owner 对公共契约和升级负责，工具只负责执行规则。

#### 原理深挖

依赖图以无环且指向稳定能力为目标。应用可依赖领域与平台包，领域包不能依赖具体应用；跨域只能通过公开入口。遗留迁移可存在受控临时环，但必须记录边、影响、Owner、隔离措施、拆除里程碑和到期日，且禁止新增消费者。

#### 工程场景

为包标注 `scope` 与 `type`，架构测试拦截非法边；变更公共包时计算受影响项目并选择性验证。高扇入包要求双人评审和兼容测试。

#### 反例 / 踩坑

全仓都能从源码深层导入；根目录出现万能 `utils`；CODEOWNERS 覆盖过宽导致一人审批所有变更；为了消环把代码移进更大的 common 包。

#### 资深回答模板

「我把依赖规则写成可执行矩阵，以无环为目标并允许受控迁移例外。反例是为消环制造大 common；证据看非法边、扇入和牵连构建；最后反思规则是否阻碍合理演进。」
:::

**追问链：**
1. 如何处理类型包形成的循环？
2. 选择性测试会不会漏风险？
3. Owner 离职时如何交接？

::: details 追问参考答案

**1. 如何处理类型包形成的循环？**

先区分仅 TypeScript 类型边与真实语义互赖；类型循环也常说明契约所有权不清，应把端口移到需要它的一侧，或拆出由明确领域拥有的稳定协议包，不能统一塞进 `types`。相关领域 Owner 重画依赖，架构 Owner 审核；用编译依赖图、产物检查和独立版本测试验证无运行时环及隐式耦合。

**2. 选择性测试会不会漏风险？**

会，因此选择依据必须来自完整依赖图并保留保守兜底：动态加载、配置引用、生成代码和高扇入包变更应扩大到全量或契约测试。CI Owner 维护图准确性，包 Owner 标注非静态依赖；通过定期全量构建对比、故意改动样例和漏测复盘验证召回率，图不可信时宁可多测不能假装精确。

**3. Owner 离职时如何交接？**

所有权不能只存在于人名。高风险包至少有团队级 Owner、备份评审者、公开契约、运行手册和消费者清单；离职前转移权限并完成演练。平台主管负责所有权目录，接任团队对 SLO 和路线负责；用 CODEOWNERS 无人项扫描、发布与事故演练验证，找不到接任者时冻结高风险变更并收缩能力。

:::

### Q13. 第三方依赖应如何分级治理？

**考察点：** 供应链、替换成本、升级策略

::: details 参考答案
按运行权限、业务关键度、维护活跃度和替换成本分级。核心依赖要有许可证与漏洞审查、版本锁定、升级窗口、变更日志和退出方案；边缘依赖避免进入公共层。

关注依赖总拥有成本，而非包体积一个指标。关键能力可通过内部适配器隔离，紧急漏洞时能替换或禁用，并记录影响范围。
:::

**追问：** 一个依赖长期不更新但运行稳定，是否必须替换？

::: details 追问参考答案

不必仅因更新时间替换，应评估已知漏洞、维护响应、平台兼容、许可证、权限和退出成本；稳定且攻击面小可隔离并继续使用，高权限核心依赖无人维护则风险更高。依赖 Owner 记录接受风险和复审触发器，安全 Owner 核验暴露面；用漏洞扫描、升级演练、替代 PoC 和禁用测试验证，不用下载量或更新时间单项决策。

:::

### D13. 如何设计前端发布契约和兼容策略？

**考察点：** 向前向后兼容、灰度、回滚

::: details 参考答案
#### 基础结论

发布不是上传静态文件，而是前端、API、配置、缓存和数据库版本的协同契约。默认要求后端先兼容旧客户端，再发布前端，最后清理旧协议。

#### 原理深挖

浏览器缓存和长会话使多个前端版本并存不可避免。协议应支持扩展字段、能力探测和弃用窗口；破坏性变更采用 expand-and-contract，而不是同一时刻切换。

#### 工程场景

新字段先由后端可选返回，前端按能力启用；灰度按用户稳定分桶；静态资源文件名不可变缓存，HTML 短缓存；回滚前验证旧前端仍能调用新后端。

#### 反例 / 踩坑

只保留最新资源导致旧 HTML 404；前后端约定「晚上同时发」；配置结构无版本；回滚只回前端却未考虑已写入的新数据。

#### 资深回答模板

「我按多版本并存设计契约，采用先扩展、再迁移、后收缩。反例是前后端同步切换；证据看兼容测试、灰度指标与 RTO；最后反思不可逆数据如何前向修复。」
:::

**追问链：**
1. 不可逆数据写入如何回滚？
2. Service Worker 缓存旧壳如何处理？
3. 移动 WebView 长期不升级怎么办？

::: details 追问参考答案

**1. 不可逆数据写入如何回滚？**

不可逆写入通常不能靠前端版本回滚，应提前采用扩展—迁移—收缩、幂等命令和前向修复；写入新格式前确认旧客户端仍可读取或被能力门禁阻止。数据 Owner 负责迁移与补偿，发布 Owner 决定停止灰度；用新旧版本矩阵、影子写入对账和恢复演练验证，失败时优先停止新增写入。

**2. Service Worker 缓存旧壳如何处理？**

静态资源使用内容哈希并长期保留，壳 HTML 与清单短缓存、版本化；新 Service Worker 先安装验证资源，再提示或在安全时激活，不能强制接管正在提交的会话。Web 平台 Owner 管更新协议，应用 Owner 定刷新体验；用离线、跨版本标签页、资源回收和安装失败测试验证可继续启动及回退。

**3. 移动 WebView 长期不升级怎么办？**

把 WebView 视为长生命周期客户端，维护最低能力基线、协议版本和服务端兼容窗口；新能力通过探测启用，超期版本进入只读、提示升级或安全拒绝，而非无限兼容。客户端 Owner 管容器升级，API Owner 管弃用；用真实旧内核版本矩阵、灰度遥测和强制失效演练验证。

:::

## 六、技术债、ADR 与组织演进

### Q14. 技术债如何进入架构治理，而不是变成代码洁癖？

**考察点：** 利息、风险、预算、停止条件

::: details 参考答案
技术债必须关联可观察利息：事故、交付周期、变更失败率、性能退化或安全暴露。按影响与紧迫性分级，为高利息债设置迭代预算和验收指标。

还债可采用童子军规则、专项治理或业务需求搭车。每项明确「不处理的后果、最小偿还范围、完成定义和何时停止」，避免无限重构。
:::

**追问：** 如何向业务证明 20% 技术债预算值得？

::: details 追问参考答案

不能先把 20% 当永恒定额，应把债务关联事故损失、交付等待、变更失败和安全暴露，比较最小偿还成本与不处理的风险区间，再按阶段批准预算。技术债 Owner 提供基线和停止条件，产品 Owner 排业务机会成本；通过试点前后趋势、对照需求和复发情况验证，收益不足就收缩或停止投入。

:::

### D14. ADR 应记录什么，如何避免形式主义？

**考察点：** 决策上下文、替代方案、复审

::: details 参考答案
#### 基础结论

架构决策记录（ADR）记录高成本、跨边界、难回退的决策；重点是当时的上下文、约束、选项、取舍与后果，不是写技术百科。

#### 原理深挖

决策正确性依赖上下文，ADR 让后来者区分「当时合理」与「今天仍适用」。状态应包含提议、接受、废弃、取代，并链接指标和后续决策。

#### 工程场景

选择状态方案时记录团队规模、离线要求、候选方案和反对意见；约定当跨应用同步故障率、变更等待或认知成本持续越过有基线的阈值时复审，而不是用「应用数超过 5」等机械数量替代证据。

#### 反例 / 踩坑

每次改命名都写 ADR；只记录最终结论；会后补写成对胜者有利的历史；文档无人能发现。

#### 资深回答模板

「我只记录高影响决策及复审触发器。反例是只写胜出方案；证据链接基线、PoC、反对意见和后果指标；最后反思当时未知信息，并用 supersede 保留历史。」
:::

**追问链：**
1. 团队意见不一致如何写入 ADR？
2. 紧急事故中的决策何时补录？
3. 哪类决策不值得写 ADR？

::: details 追问参考答案

**1. 团队意见不一致如何写入 ADR？**

如实记录各选项、反对理由、证据缺口和最终决策权，不把少数意见改写成共识；同时写明接受的风险与触发复审的信号。提案 Owner 对结论负责，异议方确认观点未被歪曲；用评审记录、PoC 结果和后续指标验证，出现异议预测的风险时按约定复审而非追责。

**2. 紧急事故中的决策何时补录？**

事故中先止损，只记录时间线、决策人、假设和回退点；服务稳定后在复盘前补成 ADR，并标为临时或已接受，避免事后合理化。事故指挥 Owner 提供原始记录，受影响领域 Owner 评估长期后果；通过时间线与变更记录交叉验证，并给临时决策设置到期日和复审。

**3. 哪类决策不值得写 ADR？**

可轻易回退、局部实现且不改变公开契约、依赖方向或质量属性的决定不值得单独写 ADR，例如普通命名和局部重构；可留在代码评审。领域 Owner 依据门槛判断，架构 Owner 维护轻量清单；定期抽样检查遗漏与文档噪声，若后续跨边界或回退成本升高再补录。

:::

### Q15. 架构评审应该评什么，谁来负责？

**考察点：** 风险前置、轻量门禁、责任

::: details 参考答案
评审聚焦不可逆风险、边界变化、质量属性和演进成本，不逐行审实现。提案人负责证据与结果，领域 Owner、运维安全和消费者代表按影响参与，架构师不替团队背全部责任。

小改走清单，大改做 RFC 和 PoC；结论包含接受的风险、观测指标、回滚方案与复审时间。评审 SLA 也要受控，避免架构委员会成为排期瓶颈。
:::

**追问：** 如何判断某个改动必须进入架构评审？

::: details 追问参考答案

满足任一高影响信号就进入：改变领域边界或依赖方向、引入高权限依赖、修改公开契约、造成不可逆数据、显著扩大故障半径，或触碰既定质量预算；局部可逆改动走清单。提案 Owner 负责申报，领域与安全 Owner 按影响参与；通过门禁命中率、漏审事故和评审等待时间复核阈值，防止委员会化。

:::

### D15. 团队规模和复杂度变化时，架构如何渐进演进？

**考察点：** 认知负载、团队拓扑、绞杀者模式

::: details 参考答案
#### 基础结论

架构应匹配当前团队的认知负载和协作边界。先用模块化单体保持简单，在发布节奏、故障边界或所有权出现真实压力时再拆分。

#### 原理深挖

系统边界会映射沟通结构。团队从 5 人扩到 30 人时，关键不是多建几层，而是明确领域 Owner、平台服务边界和交互模式，减少同步协调。

#### 工程场景

先建立模块公开 API 和依赖测试，再选变化频繁且边界清晰的模块试点独立部署。通过适配层双写或旁路读逐步迁移，以错误率、交付周期和跨团队阻塞衡量是否继续。

#### 反例 / 踩坑

预测三年后的组织一次拆完；只拆仓库不拆数据与责任；迁移没有停止条件；新旧系统长期双轨却无人维护。

#### 资深回答模板

「我先用指标证明现有边界成为瓶颈，再做可回退的最小切片。反例是预测未来一次拆完；证据看交付等待、故障边界和迁移成本；最后反思组织变化后是否应合并。」
:::

**追问链：**
1. 哪些信号说明模块化单体已不够？
2. 微前端如何纳入而不成为默认答案？
3. 组织再次收缩时是否应合并架构？

::: details 追问参考答案

**1. 哪些信号说明模块化单体已不够？**

持续出现发布互相阻塞、单模块故障拖垮整体、权限或技术栈边界无法隔离，且模块已有稳定契约和独立 Owner，才说明需要更强隔离；代码量大不是充分条件。领域 Owner 提供基线，架构 Owner 评估拆分成本；先试点一条边界，用交付等待、故障影响和运行成本验证是否继续。

**2. 微前端如何纳入而不成为默认答案？**

把微前端视为部署与运行时隔离手段，只在团队自治、独立发布或故障隔离收益有证据时采用；先建立模块 API、壳契约和观测，再选择最小试点。平台 Owner 管运行时与兼容，业务 Owner 管生命周期；用首屏成本、卸载泄漏、独立回滚和协作等待验证，收益不足保留模块化单体。

**3. 组织再次收缩时是否应合并架构？**

应重新评估，不必维护超出团队认知与 on-call 能力的边界；若独立部署、协议和平台成本已超过隔离收益，可先合并仓库或发布流程，再逐步收敛运行时。架构 Owner 提案，领域 Owner 共同接管责任；用事故响应、交付周期、平台成本和可回退迁移验证，数据与安全边界仍须保留。

:::
