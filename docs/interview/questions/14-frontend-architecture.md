# 前端架构面试题库

> **怎么用：** 先按 **约束识别 → 质量属性 → 边界与依赖 → 风险与演进** 口述 2～3 分钟，再展开参考答案。普通题检查知识面；深层题检查能否把原则落到指标、故障与组织治理。

本模块面向 **5 年+ 前端、前端架构师与技术负责人**，重点回答「系统为什么这样分、依赖为什么这样流、如何持续治理」。[工程化](/interview/questions/03-engineering) 讲工具链与流水线实操；[微前端](/interview/questions/12-microfrontend) 讲运行时原理；[前端系统设计](/interview/questions/11-frontend-system-design) 讲具体系统案例。本模块只讨论这些能力如何纳入整体架构。

## 一、质量属性与架构边界

### Q1. 前端架构设计开始前，必须澄清哪些约束？

**考察点：** 业务目标、规模、团队、合规、存量系统

::: details 参考答案
先确认「为什么改」，再讨论框架。至少澄清：核心用户与主路径、端与地区、峰值流量及数据量、可用性与性能目标、交付期限、团队技能与人数、合规边界、存量依赖和退出成本。

输出不应是一张技术清单，而应是一页约束表。例如：主路径月活 300 万、LCP P75 ≤ 2.5 s、发布失败 15 分钟内回滚、6 人团队半年内不能停业务迁移。约束冲突时按业务损失排序，并记录暂不解决的风险。
:::

**追问：** 需求方只说「做成业内领先」，你如何把它转成可验证目标？

---

### D1. 如何从质量属性反推架构，而不是先选框架？

**考察点：** 质量属性场景、优先级、可测量决策

::: details 参考答案
#### 基础结论

架构是质量属性的取舍结果。先把性能、可用性、安全、可修改性、可测试性等写成「刺激—环境—响应—指标」场景，再选择能控制主要风险的结构。

#### 原理深挖

质量属性会互相牵制：运行时隔离提高故障边界，却增加加载和治理成本；强一致状态减少歧义，却可能放大耦合。应以架构效用树排序：业务影响 × 发生概率 × 改造成本，而不是所有指标都追求极致。

#### 工程场景

多团队后台最痛的是发布互相阻塞，优先优化可修改性与部署独立性；大促 H5 最痛的是首屏和容灾，则优先性能预算、静态兜底与开关。两者不应复制同一套架构。

#### 反例 / 踩坑

先决定上微前端、SSR 或 Monorepo，再倒推理由；只写「高性能、高可用」，没有分位值、观察窗口和故障恢复目标。

#### 资深回答模板

「我先列出前三项质量属性及阈值，再说明它们的冲突。针对最大风险选择结构，并给出验证实验、降级路径与复审日期。」
:::

**追问链：**
1. 业务要首屏更快又要更多个性化，如何取舍？
2. 指标暂时拿不到基线时如何决策？
3. 哪些决策应延迟到信息更充分时？

### Q2. 分层架构怎样避免只剩目录分组？

**考察点：** 职责、契约、依赖方向、可替换性

::: details 参考答案
有效分层必须同时具备职责边界、稳定契约和依赖规则。常见方向是 `页面/交互 → 应用用例 → 领域规则 → 基础设施端口实现`，领域层不直接依赖路由、组件库和 HTTP 客户端。

用静态依赖检查、包导出白名单和架构测试约束跨层引用。衡量标准不是目录整齐，而是更换请求库、路由或 UI 框架时，核心业务规则无需跟着重写。
:::

**追问：** 一个简单 CRUD 项目是否也需要四层？

### D2. 如何设计依赖方向并处理跨层调用？

**考察点：** 依赖倒置、端口适配器、循环依赖

::: details 参考答案
#### 基础结论

依赖应指向更稳定、更接近业务规则的一侧；跨层能力通过接口、事件或应用服务进入，禁止为省一步而反向引用页面和 Store。

#### 原理深挖

稳定依赖原则关注变化频率，不等同于「底层永远稳定」。领域定义 `OrderRepository` 端口，基础设施实现 HTTP 适配器；组合根负责注入。这样业务规则可脱离浏览器和后端联调测试。

#### 工程场景

支付结果页需要查询、埋点和导航：应用用例返回领域结果，页面决定导航，埋点适配器观察用例事件。领域代码不调用 Router，也不拼上报字段。

#### 反例 / 踩坑

所有模块互相从 `index.ts` 导入形成环；把依赖注入理解为给每个函数传十几个对象；用全局事件总线隐藏真实依赖。

#### 资深回答模板

「我先按变化原因分层，再画允许的依赖箭头。跨边界用最小端口，组合根集中装配，并用静态规则和契约测试防止方向回退。」
:::

**追问链：**
1. 类型定义应该放调用方还是提供方？
2. 为消除循环依赖而抽 `common` 包有什么风险？
3. 何时允许临时越层，如何偿还？

### Q3. 如何按领域拆前端模块，而不是按页面机械拆分？

**考察点：** 业务能力、聚合变化、公开契约

::: details 参考答案
模块边界应围绕稳定业务能力和共同变化原因，例如订单、履约、结算，而不是首页、列表页、详情页。模块内部可包含页面、用例、状态和 API 适配器，对外只暴露用例、路由入口和稳定类型。

判断边界可看：需求是否总一起变、数据是否有明确所有者、是否能独立测试和发布。跨域查询通过组合层或专门读模型完成，避免直接读另一个域的内部 Store。
:::

**追问：** 搜索页同时展示商品、订单和客户，应该归哪个域？

### D3. 如何识别并治理「共享模块」大泥球？

**考察点：** 内聚、复用成本、所有权、演进

::: details 参考答案
#### 基础结论

共享不是「两处用到就抽」，而是语义一致、变化节奏一致且有明确 Owner。优先复制小而不稳定的代码，晚于事实建立抽象。

#### 原理深挖

共享包增加消费者数量，也增加变更协调成本。应区分稳定内核（金额、权限码模型）、平台能力（监控 SDK）和业务复用（组织选择器）；三者版本与兼容策略不同。

#### 工程场景

统计共享包的入边数量、破坏性发布次数和变更牵连项目数。把 `shared` 按能力拆包，限制深层导入，废弃 API 提供迁移窗口和使用方清单。

#### 反例 / 踩坑

把所有 DTO、常量、Hook 都扔进 `common`；共享包没有负责人；一次修改要求十个应用同日升级。

#### 资深回答模板

「我用语义一致性和共同变化判断是否共享，再明确 Owner、消费者契约、版本策略与退出机制。共享收益小于协调成本时宁可局部重复。」
:::

**追问链：**
1. 重复三次就抽象是否总成立？
2. 共享类型与共享运行时代码要不要同包？
3. 如何安全拆解已有大包？

## 二、状态、数据流与接口边界

### Q4. 如何划分组件状态、应用状态、服务端状态和 URL 状态？

**考察点：** 状态所有权、生命周期、可分享性

::: details 参考答案
状态按所有权和生命周期放置：临时交互留在组件；跨页面会话与工作流放应用 Store；服务端数据交给查询缓存管理；筛选、分页和可分享视图进入 URL。派生值尽量计算，不做双份存储。

每类状态明确单一写入口、失效规则和恢复策略。刷新页面后必须恢复的状态不能只藏在组件内；权限与价格等权威数据不能只相信本地缓存。
:::

**追问：** 多步骤表单草稿应该放哪里？

---

### D4. 复杂前端如何保持单向数据流又不过度集中？

**考察点：** 命令查询分离、事件、事务边界

::: details 参考答案
#### 基础结论

单向数据流的目标是让写入可追踪，不是把所有数据塞进一个 Store。读取可组合，写入应经过明确用例或命令入口。

#### 原理深挖

跨域流程可用应用层编排：命令触发领域变更，结果产生事件，查询缓存按键失效。局部强一致操作在一个用例内完成；非关键副作用异步处理并允许补偿。

#### 工程场景

「审批通过」先防重复提交，调用权威 API，成功后更新详情并失效列表，再异步上报。失败保留用户输入并映射可恢复错误；不会让三个组件各自改同一份状态。

#### 反例 / 踩坑

把 Store 当数据库；监听器互相触发形成隐式链；乐观更新失败后没有回滚快照；缓存键没有实体和租户维度。

#### 资深回答模板

「我先定义状态所有者和写入口，再区分命令与查询。关键写入有幂等、回滚和观测，跨域副作用通过显式编排或事件完成。」
:::

**追问链：**
1. 什么时候适合乐观更新？
2. 多标签页同时编辑如何处理？
3. 事件顺序错乱时怎样恢复？

### Q5. API 适配层应该负责什么，不应该负责什么？

**考察点：** DTO 转换、契约、领域隔离

::: details 参考答案
API 适配层负责传输协议、鉴权头、超时取消、DTO 到领域模型转换、错误归一化和 TraceId 透传；不负责页面提示、路由跳转和复杂业务决策。

以 OpenAPI 或等价契约生成基础类型，但在边界做运行时校验和兼容映射。后端字段改名时，优先让变化收敛在适配器，而不是传播到全部组件。
:::

**追问：** 后端返回成功但字段缺失，前端应怎样处理？

### D5. 如何设计统一错误模型和恢复策略？

**考察点：** 错误分类、用户体验、重试、观测

::: details 参考答案
#### 基础结论

错误至少区分业务拒绝、认证授权、网络瞬态、限流、服务故障、客户端缺陷。每类定义用户提示、是否重试、是否上报、是否降级和责任归属。

#### 原理深挖

HTTP 状态、业务码和用户文案是不同维度。统一错误对象可含 `kind/code/retryable/traceId/cause`。重试只用于幂等且瞬态的操作，采用退避和抖动，并受总时限控制。

#### 工程场景

列表超时保留旧数据并提供重试；提交订单未知结果先按幂等键查询状态，不能直接再次创建；401 只允许一个刷新 Token 请求，其余请求排队或失败。

#### 反例 / 踩坑

拦截器遇错一律弹 Toast；所有 401 都跳登录造成并发风暴；静默吞错；前端生成的错误码与后端无法关联。

#### 资深回答模板

「我先按可恢复性分类错误，再为每类定义体验与技术动作。涉及写操作时优先保证幂等和结果可查询，所有故障都携带版本与 TraceId。」
:::

**追问链：**
1. 全局错误边界和局部错误态如何分工？
2. 离线恢复后请求队列如何处理？
3. 第三方 SDK 报错如何隔离？

### Q6. 前端权限架构的边界是什么？

**考察点：** 鉴权权威、体验控制、策略一致性

::: details 参考答案
后端是授权权威，前端负责入口隐藏、路由拦截、字段展示和操作前提示，不能把「看不见按钮」当安全。权限码应按资源与动作命名，并与菜单、API 和审计关联。

权限上下文包含租户、角色、数据范围和版本；变更后要有失效策略。敏感数据应由服务端裁剪或脱敏，不能先全量下发再由前端隐藏。
:::

**追问：** 离线应用如何做权限判断？

### D6. 多应用如何统一权限模型又保持自治？

**考察点：** 策略分发、缓存、兼容、故障模式

::: details 参考答案
#### 基础结论

统一的是权限语义、主体上下文和审计协议，不一定统一每个应用的 UI 实现。应用消费版本化策略或权限快照，服务端仍逐请求鉴权。

#### 原理深挖

集中策略中心降低口径漂移，却形成关键依赖。应提供短期缓存、签名版本、灰度发布和旧策略回退；高风险写操作在策略中心不可用时默认拒绝。

#### 工程场景

壳应用下发用户上下文，各业务模块用统一 SDK 判断展示；API 网关或服务执行权威策略。策略变更带版本号，监控拒绝率突增，并支持按租户回滚。

#### 反例 / 踩坑

子应用各写一套角色字符串；权限快照永久放在 localStorage；策略中心故障时全部默认放行；只测正向用例。

#### 资深回答模板

「我统一权限词汇、上下文和审计，前端判断只改善体验。集中服务必须有缓存与回滚，但高风险操作始终由服务端拒绝越权。」
:::

**追问链：**
1. 权限变更如何在长会话中生效？
2. 多租户切换如何避免串权？
3. 策略升级如何做兼容测试？

## 三、路由、组件与平台化

### Q7. 路由与布局架构如何支持多端和多业务？

**考察点：** 路由契约、布局组合、端差异

::: details 参考答案
路由描述业务导航语义，布局提供壳能力。将路由元信息做成类型化契约，包含权限、标题、缓存、埋点和布局槽位；端差异由路由适配器映射到 Web、WebView 或小程序导航。

布局用组合而不是业务页面直接改壳。深链、返回栈、登录恢复和 404/403 是必须验证的故障路径；不能只测菜单点击。
:::

**追问：** 动态路由应由后端下发到什么粒度？

---

### D7. 如何设计可演进的应用壳与扩展点？

**考察点：** 插件契约、生命周期、兼容性

::: details 参考答案
#### 基础结论

壳只拥有跨业务稳定能力：会话、导航、布局、主题、监控和全局降级。业务通过声明式注册表接入，禁止依赖壳内部组件和 Store。

#### 原理深挖

扩展点本质是版本化协议，应定义输入、生命周期、失败隔离、超时和能力探测。壳与业务之间使用最小上下文，避免暴露可随意修改的全局对象。

#### 工程场景

业务注册路由、菜单和顶部动作；壳在激活时注入用户与观测接口。某插件初始化超时则跳过并展示局部故障，不阻断整个工作台。

#### 反例 / 踩坑

业务通过相对路径导入壳源码；扩展点无限增加且无 Owner；壳升级要求所有业务同日发版；插件异常拖垮启动。

#### 资深回答模板

「我把壳限制为稳定公共能力，接入点协议化并版本化。每个扩展点都有生命周期、失败边界、兼容矩阵和废弃窗口。」
:::

**追问链：**
1. 壳与业务谁拥有面包屑？
2. 如何处理旧插件不认识的新能力？
3. 什么时候应拆成独立应用？

### Q8. 组件、业务组件与设计系统如何分层？

**考察点：** Token、模式、领域语义、所有权

::: details 参考答案
设计系统包含原则、Token、基础组件、交互模式与治理，不等于组件仓库。基础组件保持无业务语义；模式组件沉淀表单、反馈等组合；业务组件带领域假设，应放在对应领域包。

每层有兼容策略和 Owner，以接入率、重复实现、缺陷率和升级耗时衡量价值。跨端统一 Token 与交互语义，不强求 DOM 和组件代码完全复用。
:::

**追问：** 基于第三方组件库时还需要自己的设计系统吗？

---

### D8. 平台化能力何时值得建设，何时是过度抽象？

**考察点：** 投资回报、产品化、采用率

::: details 参考答案
#### 基础结论

平台化适合重复需求稳定、消费者足够多、维护责任明确的场景。先用两三个真实业务验证，再抽成自助能力。

#### 原理深挖

平台收益是节省的重复成本和风险下降，成本包括建设、迁移、支持与机会成本。可用「消费者数 × 单次节省 − 年度维护成本」粗算，并设置停止投资条件。

#### 工程场景

统一请求 SDK 已在 5 个应用重复，事故口径不一，可先抽最小内核和适配层；接入时长、错误率和版本覆盖率进入平台 SLO。

#### 反例 / 踩坑

没有用户就先做万能低代码；平台团队只发版本不负责接入体验；强制迁移却没有兼容层；功能按最大客户不断膨胀。

#### 资深回答模板

「我先证明重复成本与共同需求，再用试点验证最小平台。平台有产品 Owner、采用指标、支持 SLA 和退出条件。」
:::

**追问链：**
1. 业务拒绝接入时先查什么？
2. 平台是否应该强制统一？
3. 如何避免平台团队成为交付瓶颈？

## 四、性能、稳定性、安全与降级

### Q9. 性能预算应如何进入架构治理？

**考察点：** 指标、预算分配、回归

::: details 参考答案
先按用户和页面类型选指标：内容首屏关注 LCP，交互密集页关注 INP，后台还要看路由切换、长任务与大表格。预算分到壳、业务包、第三方脚本和接口链路，并以真实用户 P75/P95 复核。

架构层关注加载边界、缓存策略、渲染模式和第三方治理；具体打包插件属于工程化模块。超预算需有例外负责人、影响说明和偿还日期。
:::

**追问：** 实验室指标变好，真实用户指标变差，如何排查？

---

### D9. 如何设计前端稳定性目标和故障预算？

**考察点：** SLI/SLO、错误预算、业务影响

::: details 参考答案
#### 基础结论

以用户可感知结果定义 SLI，例如核心页面可用率、关键操作成功率和白屏率，而不是只看 JS Error 数量。SLO 应有观察窗口和排除规则。

#### 原理深挖

错误预算把可靠性与交付速度连接起来：预算充足可加速实验，消耗过快则冻结高风险发布并优先修复。不同链路按业务价值设不同目标。

#### 工程场景

结算提交成功率按 28 天滚动窗口设 99.95%，并拆分前端、API、第三方支付影响。发布后 30 分钟燃烧率突增时自动停止灰度并回滚。

#### 反例 / 踩坑

承诺 100% 可用；把用户取消算故障；指标无法从监控计算；错误预算只用于处罚团队。

#### 资深回答模板

「我用用户结果定义 SLI，设定窗口和目标，再用多窗口燃烧率驱动发布决策。预算是风险管理工具，不是绩效排名。」
:::

**追问链：**
1. 新系统无历史数据如何定 SLO？
2. 第三方故障是否应排除？
3. 低流量链路如何避免百分比失真？

---

### Q10. 前端可观测性最小闭环包含什么？

**考察点：** 版本、上下文、关联、告警

::: details 参考答案
最小闭环是发现、定位、止损、复盘：错误和性能事件携带版本、环境、匿名用户、路由、设备、灰度组与 TraceId；SourceMap 受控解析；告警关联发布并指向 Runbook 和 Owner。

采样、脱敏、去重和限流必须前置。大盘不等于闭环，应追踪 MTTD、MTTR、告警有效率与重复事故率。
:::

**追问：** 如何检测「接口都成功但页面不可用」？

---

### D10. 如何设计端到端故障定位链路？

**考察点：** TraceId、会话、版本归因、隐私

::: details 参考答案
#### 基础结论

统一一次用户操作的 `sessionId/actionId/traceId`，贯通前端事件、网关与后端日志，并保留版本和配置快照，才能回答「谁在何版本做什么时失败」。

#### 原理深挖

关联标识必须在请求边界传播，异步任务需要父子关系。观测数据遵循数据最小化：字段白名单、敏感值哈希、留存期限和访问审计。

#### 工程场景

用户点击提交生成 actionId，请求携带 traceparent；前端记录状态转换，后端返回 TraceId。事故面板按版本和租户聚合，可快速判断是发布、配置还是后端依赖。

#### 反例 / 踩坑

全量录屏和采集输入框；每个 SDK 自定义用户 ID；日志只有错误字符串；SourceMap 公开部署。

#### 资深回答模板

「我以用户操作为关联单位，打通端到端标识与发布上下文，同时用白名单和留存策略控制隐私。告警必须能落到版本、Owner 和处置动作。」
:::

**追问链：**
1. TraceId 缺失时如何降级关联？
2. 会话回放何时不应使用？
3. 监控 SDK 自身故障如何防扩散？

### Q11. 前端安全架构应建立哪些边界？

**考察点：** 威胁模型、输入输出、供应链、密钥

::: details 参考答案
从资产、信任边界和攻击面做威胁建模：所有外部输入不可信；富文本按白名单净化；Token 使用与场景匹配的存储和过期策略；CSP、SRI、依赖审计与第三方脚本隔离形成纵深防御。

浏览器不能保存真正秘密，环境变量也不是密钥保险箱。高风险动作需要服务端鉴权、CSRF 防护、重放保护与审计，前端只提供防误触体验。
:::

**追问：** 使用 HttpOnly Cookie 后还需要防 XSS 吗？

### D11. 如何为前端设计分级降级与灾备？

**考察点：** 关键路径、功能开关、静态兜底、演练

::: details 参考答案
#### 基础结论

先按业务价值把功能分为必须、可降级、可关闭。降级动作需预置、可观测、可回滚，并在真实环境定期演练。

#### 原理深挖

故障可能来自 API、CDN、配置、第三方和客户端版本。降级应减少依赖和状态复杂度，而不是换一条同样脆弱的链路；开关控制面与数据面要隔离。

#### 工程场景

推荐服务不可用时隐藏模块并保留搜索；配置中心故障使用签名的最后已知好版本；CDN 故障切备用域名；关键静态页可由边缘缓存兜底。

#### 反例 / 踩坑

事故时临时写降级代码；所有开关依赖同一个故障服务；关闭功能后仍发请求；兜底数据过期且没有明显标识。

#### 资深回答模板

「我先画关键路径依赖图，再定义每个依赖失败时的用户结果。降级预案包含开关、缓存、观测、恢复条件和演练记录。」
:::

**追问链：**
1. 降级开关误开如何防止？
2. 缓存兜底的数据一致性如何说明？
3. 灾备切换后如何安全恢复？

## 五、Monorepo、依赖与发布治理

### Q12. 何时选择 Monorepo，何时保持多仓？

**考察点：** 协作拓扑、发布自治、权限隔离

::: details 参考答案
共享代码多、原子变更频繁、团队治理统一时，Monorepo 可降低跨仓协调成本；生命周期、权限、合规和技术栈差异大时，多仓更自然。仓库形态不能替代模块边界。

决策要量化跨仓联动次数、CI 时长、代码所有权和发布耦合。无论哪种形态，都要有清晰 Owner、公开 API、版本契约和依赖图。
:::

**追问：** Monorepo 是否意味着所有包一起发布？

---

### D12. 如何治理 Monorepo 中的依赖方向与所有权？

**考察点：** 依赖图、分区、CODEOWNERS、例外

::: details 参考答案
#### 基础结论

按业务域与层次划分包标签，定义允许的依赖矩阵；Owner 对公共契约和升级负责，工具只负责执行规则。

#### 原理深挖

依赖图需要无环且指向稳定能力。应用可依赖领域与平台包，领域包不能依赖具体应用；跨域只能通过公开入口。例外必须有原因、负责人和到期日。

#### 工程场景

为包标注 `scope` 与 `type`，架构测试拦截非法边；变更公共包时计算受影响项目并选择性验证。高扇入包要求双人评审和兼容测试。

#### 反例 / 踩坑

全仓都能从源码深层导入；根目录出现万能 `utils`；CODEOWNERS 覆盖过宽导致一人审批所有变更；为了消环把代码移进更大的 common 包。

#### 资深回答模板

「我把依赖规则写成可执行矩阵，并结合图指标找高风险节点。公共能力有 Owner、公开入口、兼容策略和限时例外。」
:::

**追问链：**
1. 如何处理类型包形成的循环？
2. 选择性测试会不会漏风险？
3. Owner 离职时如何交接？

### Q13. 第三方依赖应如何分级治理？

**考察点：** 供应链、替换成本、升级策略

::: details 参考答案
按运行权限、业务关键度、维护活跃度和替换成本分级。核心依赖要有许可证与漏洞审查、版本锁定、升级窗口、变更日志和退出方案；边缘依赖避免进入公共层。

关注依赖总拥有成本，而非包体积一个指标。关键能力可通过内部适配器隔离，紧急漏洞时能替换或禁用，并记录影响范围。
:::

**追问：** 一个依赖长期不更新但运行稳定，是否必须替换？

### D13. 如何设计前端发布契约和兼容策略？

**考察点：** 向前向后兼容、灰度、回滚

::: details 参考答案
#### 基础结论

发布不是上传静态文件，而是前端、API、配置、缓存和数据库版本的协同契约。默认要求后端先兼容旧客户端，再发布前端，最后清理旧协议。

#### 原理深挖

浏览器缓存和长会话使多个前端版本并存不可避免。协议应支持扩展字段、能力探测和弃用窗口；破坏性变更采用 expand-and-contract，而不是同一时刻切换。

#### 工程场景

新字段先由后端可选返回，前端按能力启用；灰度按用户稳定分桶；静态资源文件名不可变缓存，HTML 短缓存；回滚前验证旧前端仍能调用新后端。

#### 反例 / 踩坑

只保留最新资源导致旧 HTML 404；前后端约定「晚上同时发」；配置结构无版本；回滚只回前端却未考虑已写入的新数据。

#### 资深回答模板

「我按多版本并存设计契约，采用先扩展、再迁移、后收缩。灰度指标和回滚兼容在发布前验证，不把同步上线当方案。」
:::

**追问链：**
1. 不可逆数据写入如何回滚？
2. Service Worker 缓存旧壳如何处理？
3. 移动 WebView 长期不升级怎么办？

## 六、技术债、ADR 与组织演进

### Q14. 技术债如何进入架构治理，而不是变成代码洁癖？

**考察点：** 利息、风险、预算、停止条件

::: details 参考答案
技术债必须关联可观察利息：事故、交付周期、变更失败率、性能退化或安全暴露。按影响与紧迫性分级，为高利息债设置迭代预算和验收指标。

还债可采用童子军规则、专项治理或业务需求搭车。每项明确「不处理的后果、最小偿还范围、完成定义和何时停止」，避免无限重构。
:::

**追问：** 如何向业务证明 20% 技术债预算值得？

### D14. ADR 应记录什么，如何避免形式主义？

**考察点：** 决策上下文、替代方案、复审

::: details 参考答案
#### 基础结论

架构决策记录（ADR）记录高成本、跨边界、难回退的决策；重点是当时的上下文、约束、选项、取舍与后果，不是写技术百科。

#### 原理深挖

决策正确性依赖上下文，ADR 让后来者区分「当时合理」与「今天仍适用」。状态应包含提议、接受、废弃、取代，并链接指标和后续决策。

#### 工程场景

选择状态方案时记录团队规模、离线要求、候选方案和反对意见；约定当应用数超过 5 或同步故障率超过阈值时复审，而不是永久有效。

#### 反例 / 踩坑

每次改命名都写 ADR；只记录最终结论；会后补写成对胜者有利的历史；文档无人能发现。

#### 资深回答模板

「我只记录高影响决策，用一页说明上下文、选项、取舍、后果和触发复审的指标。新决策通过 supersede 保留历史。」
:::

**追问链：**
1. 团队意见不一致如何写入 ADR？
2. 紧急事故中的决策何时补录？
3. 哪类决策不值得写 ADR？

### Q15. 架构评审应该评什么，谁来负责？

**考察点：** 风险前置、轻量门禁、责任

::: details 参考答案
评审聚焦不可逆风险、边界变化、质量属性和演进成本，不逐行审实现。提案人负责证据与结果，领域 Owner、运维安全和消费者代表按影响参与，架构师不替团队背全部责任。

小改走清单，大改做 RFC 和 PoC；结论包含接受的风险、观测指标、回滚方案与复审时间。评审 SLA 也要受控，避免架构委员会成为排期瓶颈。
:::

**追问：** 如何判断某个改动必须进入架构评审？

### D15. 团队规模和复杂度变化时，架构如何渐进演进？

**考察点：** 认知负载、团队拓扑、绞杀者模式

::: details 参考答案
#### 基础结论

架构应匹配当前团队的认知负载和协作边界。先用模块化单体保持简单，在发布节奏、故障边界或所有权出现真实压力时再拆分。

#### 原理深挖

系统边界会映射沟通结构。团队从 5 人扩到 30 人时，关键不是多建几层，而是明确领域 Owner、平台服务边界和交互模式，减少同步协调。

#### 工程场景

先建立模块公开 API 和依赖测试，再选变化频繁且边界清晰的模块试点独立部署。通过适配层双写或旁路读逐步迁移，以错误率、交付周期和跨团队阻塞衡量是否继续。

#### 反例 / 踩坑

预测三年后的组织一次拆完；只拆仓库不拆数据与责任；迁移没有停止条件；新旧系统长期双轨却无人维护。

#### 资深回答模板

「我先用指标证明现有边界成为瓶颈，再选择可回退的最小切片演进。每一步都明确 Owner、兼容层、迁移指标和停止条件。」
:::

**追问链：**
1. 哪些信号说明模块化单体已不够？
2. 微前端如何纳入而不成为默认答案？
3. 组织再次收缩时是否应合并架构？
