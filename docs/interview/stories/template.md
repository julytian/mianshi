# 故事模板（STAR-L）

> **怎么用：** 每条项目经历先填完整 STAR-L，再压成 30 秒 / 2 分钟 / 5 分钟三档；最后用「预埋追问表」把面试官最爱追的点写死参考答法。示例见 [故事示例](/interview/stories/examples)。

---

## 为什么是 STAR-L

经典 STAR 只讲「做了什么、结果如何」。十年经验还缺一层：**你从这件事学到什么、下次怎么做得更好**——这就是 **L（Learning）**。它把「苦劳」升级成「可迁移的决策力」，Lead 面尤其吃香。

| 字母 | 英文 | 口述重点 | 时长占比（参考） |
| ---- | ---- | -------- | ---------------- |
| S | Situation | 背景：业务、团队、约束、为什么难 | 15% |
| T | Task | 你的职责与成功标准（不是团队目标糊在一起） | 10% |
| A | Action | **主体**：你做了什么、怎么取舍、踩了什么坑 | 50% |
| R | Result | 可量化或可验证的结果（数据 / 上线 / 事故下降） | 15% |
| L | Learning | 沉淀、复盘、可复用原则 | 10% |

**口诀：** 背景短、任务清、行动深、结果硬、学习亮。

## 空白模板（复制填写）

把方括号内容换成你的真实经历；数字可以是区间或量级，别编精确到离谱的假数据。

```markdown
### 故事标题：（一句话项目名 + 你的角色）

**适用岗位：** A 资深前端 / B Lead / C 全栈偏前（可多选，标主线）
**技术栈关键词：** （如 Vue3、TS、Ant Design Vue、Pinia…）
**可替换占位：** 公司名 / 业务名 / 具体指标 → 投递前按简历改一版

#### S — Situation
- 业务背景：
- 团队规模与分工：
- 约束（工期 / 性能 / 合规 / 多端 / 存量代码）：
- 为什么这件事值得讲：

#### T — Task
- 我负责的边界：
- 成功标准（可验收）：
- 不在我范围内、但需要协作的部分：

#### A — Action（按时间或按决策写，至少 3 个关键动作）
1. …
2. …
3. …
- 关键取舍（选了 A 没选 B，因为…）：
- 坑与排查路径：

#### R — Result
- 量化：（耗时、体积、首屏、事故率、人日、复用次数…）
- 质性：（上线稳定性、协作方式变化、可维护性…）
- 证据来源：（监控 / 工单 / CR 记录 / 用户反馈）——心里有数即可，不必出示

#### L — Learning
- 可复用原则（1～2 条）：
- 若重来会改什么：
```

## 三档时长结构

同一故事只改「密度」，不改事实。面试官说「简单介绍一下」用 30 秒；「展开讲讲」用 2 分钟；「深入聊聊」或 Lead 深挖用 5 分钟。

### 30 秒版（电梯稿）

**目标：** 30～45 秒内让对方记住「你是谁 + 干成了什么」。

| 句序 | 内容 | 参考秒数 |
| ---- | ---- | -------- |
| 1 | 项目一句话 + 你的角色 | 8s |
| 2 | 最硬的约束或难点 | 8s |
| 3 | 你做的核心动作（1 个就够） | 10s |
| 4 | 结果数字或上线结论 | 8s |

**禁忌：** 堆技术名词、讲团队分工八卦、从公司历史讲起。

**句式模板：**

> 我在〔项目〕里负责〔角色〕。当时最大约束是〔约束〕。我主导做了〔动作〕，最终〔结果〕。

---

### 2 分钟版（标准项目介绍）

**目标：** 把 STAR 讲完整，L 可压缩成一句；给面试官抛 1～2 个「想追问」的钩子。

建议时间盒：

| 段落 | 秒数 | 内容 |
| ---- | ---- | ---- |
| S | 20s | 业务 + 约束 |
| T | 15s | 你的职责与验收标准 |
| A | 60s | 2～3 个关键动作 + 1 个取舍 |
| R | 20s | 结果 |
| L / 钩子 | 5～10s | 「后来我们沉淀成…」或停在可追问点 |

**结构口诀：** 背景 → 我要搞定什么 → 我怎么干（取舍）→ 结果 → 收束。

**自检：** 去掉公司名后，听起来仍像**你的贡献**，而不是「我们组很忙」。

---

### 5 分钟版（深挖 / Lead）

**目标：** 展现决策深度、协作与风险控制；准备被打断。

建议时间盒：

| 段落 | 秒数 | 内容 |
| ---- | ---- | ---- |
| S+T | 45s | 背景、干系人、成功标准 |
| A1 | 60s | 方案对比与选型 |
| A2 | 75s | 落地细节（架构 / 性能 / 权限 / 联调） |
| A3 | 45s | 事故或坑 + 排查 |
| R | 30s | 结果与复盘指标 |
| L | 30s | 原则沉淀 + 若重来 |
| 缓冲 | 15s | 等追问 |

**讲法技巧：**

1. **先结论后展开**：每个 Action 先说决策，再补细节。
2. **主动暴露边界**：「后端强校验我只对齐接口契约」——显得诚实，也好接 Java / 协作题。
3. **预埋钩子**：故意点到「动态路由」「包体积」「AI 生成代码审查」等，方便对方追问你已准备的答案。

## 预埋追问表

写故事时同步填表。面试官追问往往落在这几类；每条故事至少准备 **3** 个已演练答法（示例见 [故事示例](/interview/stories/examples)）。

| 类型 | 面试官常问 | 你要准备的证据 |
| ---- | ---------- | -------------- |
| 深度 | 为什么这样设计？还有别的方案吗？ | 方案对比表、否决理由 |
| 责任 | 这段是你写的还是别人的？ | 你的边界、PR / 模块归属 |
| 量化 | 提升了多少？怎么测的？ | 指标口径、前后对比 |
| 故障 | 出过线上问题吗？怎么查的？ | 排查路径、止损、复盘 |
| 协作 | 和后端 / 产品怎么扯皮的？ | 接口契约、优先级取舍 |
| AI | 哪些用 AI？你怎么保证质量？ | 提示词边界、审查清单、不信任点 |
| Lead | 怎么带人 / 守门禁 / 排期？ | 分工、Code Review、质量闸 |

### 通用追问速查（可套到任意故事）

| 追问 | 答法骨架 |
| ---- | -------- |
| 如果重来一次你会怎么做？ | 承认当时信息差 → 给出 1～2 个更优决策 → 说明代价 |
| 最大的技术风险是什么？ | 风险点 → 你怎么降险 → 兜底方案 |
| 你和平庸实现的差别在哪？ | 可观测 / 可回滚 / 可复用 / 边界清晰，选 1～2 点展开 |
| 有没有做一半推倒的？ | 真实小翻车 → 信号是什么 → 止损动作 → Learning |

## 打磨检查清单

写完或口述录音后过一遍：

- [ ] S 里没有超过 2 句的公司历史
- [ ] T 里能听清「成功标准」
- [ ] A 里「我」的动作占比 > 「我们」
- [ ] R 至少有 1 个数字或可验证事实
- [ ] L 不是空话「沟通很重要」，而是可执行原则
- [ ] 三档时长事实一致，只是详略不同
- [ ] ≥3 个预埋追问已口头说过一遍
- [ ] 敏感信息（客户名、未公开指标）已脱敏或改成量级
