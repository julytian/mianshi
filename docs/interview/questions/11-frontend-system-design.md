# 前端系统设计

> **怎么用：** 先盖住答案，按 **目标 → 约束 → 方案权衡 → 演进** 自己画一页纸口述 8～12 分钟，再对照参考答案补洞。本模块面向 Lead / 中大厂：要的是取舍与演进，不是组件 API 清单。中英文术语之间请习惯留空格。

口述开场固定三问：**用户是谁、规模多大、哪些绝对不能崩**。没澄清就开画架构，是减分项。

### Q1. 设计一个中后台「管理后台框架」（Vue 3 + 组件库）

**考察点：** 布局与路由壳、权限接入点、模块边界、可替换基建

::: details 参考答案
#### 目标

为多业务线提供统一的**壳应用**：登录会话、布局（侧栏/顶栏）、动态路由与菜单、权限指令、请求层、错误页、主题与水印；业务以「页面模块」插入，而不是复制整仓脚手架。

#### 约束

- 团队以 Vue 3 + Ant Design Vue（或同类）为主；TS 强制。
- 首屏可接受「壳 + 首个业务页」合计可控（内网后台可略宽，但别无脑全量同步路由）。
- 多仓库或 monorepo 都可能；权限以后端为准。
- 要能灰度、要能按业务分包懒加载。

#### 方案权衡

| 方案 | 优点 | 代价 |
| ---- | ---- | ---- |
| A. 单一巨石后台 | 联调简单、权限一套 | 构建慢、发布耦合、权限误伤面大 |
| B. 壳 + 业务子应用（微前端） | 独立发布、技术栈可异构 | 路由/样式/公共依赖治理成本高 |
| C. Monorepo 多 package + 统一壳 | 类型与组件复用好、发布仍可拆 | 工程门槛、CI 复杂度上升 |

推荐默认路径：**先 C 的轻量版**（`app-admin` 壳 + `features/*` 业务包 + 共享 `shared`），真有独立发布与多团队强隔离再上 B。

关键设计点：

1. **路由**：布局路由固定；业务路由由权限接口下发后 `addRoute`；组件用白名单 `import.meta.glob` / `componentMap`。
2. **请求层**：统一 `baseURL`、Token、错误码、幂等与取消；禁止页面直接 `axios.create`。
3. **扩展点**：菜单图标映射、页面 keep-alive 白名单、全局水印、字典缓存——做成注册表，而不是改壳源码。
4. **质量门禁**：ESLint + 路由 meta 类型 + 权限码静态扫描（可选）。

#### 演进

1. **MVP**：登录 + 布局 + 静态菜单 + 2 个业务页 + 统一请求。
2. **V1**：动态路由 / 按钮权限、字典与用户偏好、错误监控接入。
3. **V2**：按业务分包、可插拔布局、设计令牌主题；若团队 ≥3 独立发布节奏，评估微前端。
4. **长期**：模块联邦或包级版本策略；壳升级与业务升级解耦（peerDeps + 兼容矩阵）。
:::

**追问：**
1. 多 tab 页签（keep-alive + 缓存淘汰）你放在壳还是业务？
2. 微前端的样式隔离与公共 AntDV 多实例怎么处理？
3. 壳发版如何保证旧业务页不炸？

**踩坑：** 业务直接改壳的 layout；或权限只藏菜单不拦路由；一上来全量微前端。

### Q2. 设计前端监控体系（稳定性 + 体验）

**考察点：** 采集分层、采样、隐私、报警闭环、和性能指标挂钩

::: details 参考答案
#### 目标

让线上问题**可发现、可定位、可归因**：JS 错误、资源失败、接口异常、白屏、核心性能（LCP/INP/CLS 或内网自定义）、关键业务漏斗（登录成功率、下单成功率）。

#### 约束

- 包体积与主线程开销有预算；不能拖垮弱网 H5。
- 合规：脱敏、禁止扫本地存储明文、用户标识可哈希。
- 多端：Web 管理端、H5、可能还有小程序（小程序另有平台数据，需对齐字段）。
- 已有或可自建上报网关；报警要对人负责（on-call），不是只堆大盘。

#### 方案权衡

| 层次 | 采什么 | 注意 |
| ---- | ------ | ---- |
| 错误 | `window.onerror` / `unhandledrejection`、框架 errorHandler、资源 `error` | SourceMap 私有化；去重与聚合 |
| 性能 | PerformanceObserver、长任务、路由切换耗时 | 采样率；SPA 软导航要自己打点 |
| 行为 / 业务 | 关键按钮、接口 code、自定义 `metric` | 和产品漏斗对齐命名 |
| 会话 | sessionId、版本号、环境、用户角色（非敏感） | 便于「仅某版本」过滤 |

自建 vs 商业 SaaS：团队小、合规严 → 可自建采集 + 现有日志平台；要快速有洞察 → SaaS + 敏感字段网关剥离。

SDK 形态：薄封装 `report(event, payload)` + 插件（error/perf/api）；默认**采样**（错误可 100%，性能 / 行为按环境）。接口监控优先在请求层统一拦截，比页面手埋稳。

#### 演进

1. **MVP**：错误 + 版本号 + 用户匿名 id；钉钉/飞书报警（阈值阈值）。
2. **V1**：API 失败率大盘、白屏检测（根节点空 + 骨架超时）、SourceMap 解码流水线。
3. **V2**：性能预算门禁（CI）、发布对照（跨版本对比）、会话回放（慎用，隐私评审）。
4. **长期**：SLO（如「管理端可交互错误率 < x%」）驱动排期；和后端 TraceId 打通。
:::

**追问：**
1. 如何区分「脚本错误」和「业务可预期失败」？
2. 小程序监控和 H5 字段怎么统一？
3. 报警风暴你怎么降噪？

**踩坑：** 只接 SDK 不看大盘；上报 PII；在 render 里同步疯狂 `report`。

### Q3. 设计一套前端组件库（面向中后台 + 少量 H5）

**考察点：** 原子/业务分层、Token、文档与发布、破坏性变更

::: details 参考答案
#### 目标

沉淀**可复用、可主题化、可版本化**的 UI 能力：基础组件（Button/Modal）少造轮子，重点做**业务组件**（ProTable、SchemaForm、OrgPicker）与设计令牌，让多项目观感与交互一致。

#### 约束

- 主力 Vue 3；不轻易同时维护 React 版，除非有强需求。
- 基于 Ant Design Vue / Vant 做**增强与约束**，而不是从零画按钮。
- 发布要 semver；文档站点与 Playground 必须有，否则没人用。
- 包体积：业务项目按需引入；避免强绑全量图标库。

#### 方案权衡

| 层级 | 职责 | 是否自研 |
| ---- | ---- | -------- |
| 设计 Token | 色板、间距、圆角、字体 | 要，CSS 变量 |
| 基础组件 | 直接用 AntDV/Vant | 原则上不封装「换皮」 |
| 模式组件 | Table+查询、Form 布局 | 薄封装，暴露 slot |
| 业务组件 | 组织树、审批流水线 | 自研，带领域假设 |

仓库策略：`ui`（通用）与 `biz-ui`（绑定领域）拆开，避免通用库被业务字段污染。技术：Vite library mode + TS 声明；Monorepo 下用 workspace 协议本地联调。

API 设计原则：**props 语义稳定、slot 扩展、事件命名一致**；复杂逻辑用 composable 导出，而不是只能通过组件黑盒用。

#### 演进

1. **MVP**：Token + 3～5 个最高频业务组件 + 文档站 + changelog。
2. **V1**：主题切换、暗色（若需要）、单元测试 / 视觉回归抽样、peerDeps 对齐 Vue/AntDV 大版本。
3. **V2**：RFC 流程做破坏性变更；codemod 辅助升级；按需自动引入优化。
4. **长期**：度量「接入率 / 重复组件数下降」；淘汰长期 0 引用组件。
:::

**追问：**
1. 「再包一层 a-button」什么时候合理？
2. 多项目不同 AntDV 大版本怎么共存？
3. 组件库和脚手架谁先谁后？

**踩坑：** 一上来造完整 Atomic Design；业务字段写进通用 Button；无文档靠口口相传。

### Q4. 设计低代码 / 配置化表单方案

**考察点：** Schema 驱动、扩展点、复杂联动、与手写 Form 分界

::: details 参考答案
#### 目标

让运营 / 后端配置或前端用 JSON Schema 快速生成中后台表单：校验、布局、联动、异步选项，覆盖 80% CRUD 录入；剩余 20% 复杂交互可**逃生舱**手写。

#### 约束

- 字段类型有限且可扩展（input/select/date/upload/自定义）。
- 要对接后端校验规则或至少同源（避免前后规则漂移）。
- 性能：百级字段要能分组 / 懒渲染，不能一次挂载 200 个重组件。
- 权限：字段级可见 / 可编；值不能只靠前端藏。

#### 方案权衡

| 方案 | 适用 | 风险 |
| ---- | ---- | ---- |
| 纯 JSON Schema + 渲染器 | 配置平台、多租户差异大 | 联动 DSL 容易变成新语言 |
| 代码 Schema（TS 对象） | 前端主导、要类型提示 | 「低代码」纯度下降，但可维护 |
| 拖拽搭建器 | 非研发配页面 | 工程与权限、版本治理重 |

推荐：**TS/JSON Schema 渲染器 + 自定义组件注册表**；拖拽搭建另立项目，不要和渲染器绑死。

核心模型：

```ts
type Field = {
  name: string
  label: string
  type: string
  props?: Record<string, unknown>
  rules?: unknown[]
  visibleOn?: string // 或函数注册名
  effect?: { watch: string[]; run: string }
}
```

联动用「声明式 visible/disabled + 少量注册函数」，禁止在 Schema 里塞任意 JS 字符串 eval。上传、富文本等重字段异步加载组件定义。

#### 演进

1. **MVP**：布局 + 基础类型 + 校验 + 回填/提交适配器。
2. **V1**：联动、异步 options、字段权限、分组/步骤条。
3. **V2**：与流程引擎/审批单结合；Schema 版本化与迁移脚本。
4. **长期**：可视化编辑器；监控「渲染器兜底率」（多少页被迫手写）反哺组件扩展。
:::

**追问：**
1. 循环依赖联动（A 变 B、B 变 A）怎么防？
2. 后端下发 Schema 被篡改的风险？
3. 和 Ant Design Vue Form 的 `name path` 怎么对齐？

**踩坑：** Schema 里 `eval`；无逃生舱导致极端页硬拧配置；校验只做前端。

### Q5. 设计中后台权限体系（前端视角的端到端）

**考察点：** RBAC、菜单/路由/按钮/数据权、前后端分工、多租户

::: details 参考答案
#### 目标

保证**越权不可达**：无权限用户看不见入口、进不了路由、打不出成功写操作；审计可追踪。前端是体验与防御纵深，**权威在后端**。

#### 约束

- 模型以 RBAC 为主，必要时加数据范围（部门/本人/全部）。
- 权限码全站唯一，菜单 / 路由 / 按钮 / API 同源。
- 超管、多角色并集、权限变更后要能生效（重新拉码或短 TTL）。
- 多租户时角色空间隔离。

#### 方案权衡

| 控制面 | 前端做什么 | 后端做什么 |
| ------ | ---------- | ---------- |
| 菜单 | 按码过滤树 | 下发用户可访问菜单 |
| 路由 | `addRoute` + 守卫 403 | 直接刷 URL 也不能返回数据 |
| 按钮 | `v-permission` / 函数 | 接口鉴权同码 |
| 数据 | 默认筛选项、字段脱敏展示 | where 条件与字段裁剪 |

实现要点：登录后拉 `codes[]` + 菜单树 → 生成路由 → 存 store；`v-permission` 只做 `codes.includes`；禁止 `if (role === 'admin')` 散落。超管用后端 `*` 或全量码，前端不写死上帝分支（除开发本地 mock）。

数据权限：列表请求不带「我要看全公司」的前端开关作权威；最多提供 UI，以服务端为准。

#### 演进

1. **MVP**：角色 + 菜单 + 路由守卫 + 按钮码。
2. **V1**：数据范围、字段级、权限变更强制重登或热更新码表。
3. **V2**：权限码治理平台（申请/审批/过期）；自动化测试「越权用例」。
4. **长期**：ABAC / 策略引擎对接；与审计日志、脱敏规范一体。
:::

**追问：**
1. 权限码命名规范怎么定才利于演进？
2. 微前端下子应用权限如何下发？
3. 前端路由懒加载组件被打包进 chunk，算不算泄露？

**踩坑：** 只藏按钮；权限存在 localStorage 可篡改就信；刷新丢动态路由。

### Q6. 跨端项目治理（H5 / uni-app / 小程序 / 管理端）

**考察点：** 代码复用边界、发版矩阵、设计一致性、质量门禁

::: details 参考答案
#### 目标

在多端并存时，让团队有**清晰的复用与差异规则**：业务节奏可预期，不因一端需求拖死另一端；共享逻辑可测，UI 差异可解释。

#### 约束

- 端：Vue 3 管理端、Vant H5、uni-app 小程序可能同时在。
- 人力有限，不能每端一支完整团队。
- 小程序有包体积与审核；H5 有弱网与 WebView 差异。
- 设计资源未必每端一稿，需要 Token 级对齐而不是像素级抄。

#### 方案权衡

| 复用层 | 放什么 | 不放什么 |
| ------ | ------ | -------- |
| `shared-utils` / 领域 model | 校验、金额、日期、API DTO 类型 | 带 DOM 假设的工具 |
| `shared-api` | 请求封装差异用 adapter | 写死平台 URL 拼接脏逻辑 |
| UI | 各端组件库 | 强行一套组件打全端 |
| 页面 | 极少「一字不改」 | 复杂交互页 |

策略：

1. **合约优先**：同一业务后端 API 尽量统一；端上差异用 BFF 或 adapter。
2. **条件编译谨慎**：uni-app `#ifdef` 控制在基础设施，业务满屏 ifdef 宣布失败。
3. **发版矩阵**：表格列出端 × 版本 × 强制更新策略；阻断问题按端热修。
4. **质量**：公共包单测；端上 E2E 只覆盖主路径；包体积预算进 CI。

组织上：指定「平台 Owner」审共享包变更；业务需求先标影响端，再估期。

#### 演进

1. **MVP**：抽 `shared` 包 + 文档「何时能复用」；统一错误码与登录态刷新策略。
2. **V1**：设计 Token 多端映射；API adapter 标准化；发版检查清单。
3. **V2**：跨端埋点字段字典；组件级复用度量；废弃一套老 H5。
4. **长期**：评估是否收敛端数量（能 H5 就不硬上小程序等）。
:::

**追问：**
1. 管理端和 C 端 H5 的设计系统要不要强行统一？
2. 小程序独立分包和 uni 主包怎么划？
3. 共享包 breaking change 怎么通知各端？

**踩坑：** 盲目 all-in 跨端框架；共享包变成大泥球；一端紧急需求直接改 shared 破坏另一端。

### Q7. 设计「配置化列表页」框架（查询 + 表格 + 操作）

**考察点：** Schema 列表、列定义、请求协议、扩展槽、性能

::: details 参考答案
#### 目标

用一份配置生成中后台标准列表：**查询区 + 工具栏 + 表格 + 分页 + 行操作 + 导出**，让新 CRUD 列表以小时计而非天计；复杂列表可局部定制而不 fork 整页。

#### 约束

- 协议对齐后端：分页 `{ list, total }`、排序字段白名单、查询参数命名一致。
- 列要支持：格式化、枚举字典、权限控制、固定列、溢出省略。
- 大数据：虚拟滚动或「只做服务端分页」，别假装一次拉 10 万行。
- 可测试：请求函数可注入，不写死在组件内部。

#### 方案权衡

| 方案 | 优点 | 代价 |
| ---- | ---- | ---- |
| 配置 JSON + 通用 ProTable | 快 | 复杂单元格表达力差 |
| 配置 + slot 具名逃生 | 平衡 | 要规范 slot 命名 |
| 纯手写 Table | 最灵活 | 重复劳动、风格漂移 |

推荐 **ProTable：columns + searchFields + actions + request`**，单元格用 `customRender` / slot；禁止在配置里塞 React/Vue 组件的字符串名以外的任意代码。

关键设计：

1. **request(params)** 统一把查询表单、分页、排序编成 API 参数；返回标准结构。
2. **columns** 声明 `dataIndex/title/valueType/permission`；`valueType` 映射到金额、日期、字典。
3. **actions**：工具栏与行操作带 `permission` 与 `confirm`。
4. **状态**：URL query 同步（可分享筛选）；重置与默认值清晰。
5. **性能**：列过多时按需展示列设置；远程字典缓存。

#### 演进

1. **MVP**：查询 + 表格 + 分页 + 行操作权限。
2. **V1**：导出、批量选择、列设置持久化、URL 同步。
3. **V2**：可编辑单元格、主子表、与配置化表单详情联动。
4. **长期**：列表 Schema 可由低代码平台生成；监控「自定义 slot 占比」防止框架空心化。
:::

**追问：**
1. 筛选条件与 URL 同步时，类型与数组字段怎么序列化？
2. 后端字段变更如何减少前端列配置灾难？
3. 虚拟列表和合并单元格冲突怎么办？

**踩坑：** 配置吞掉所有定制导致业务 copy 一份 ProTable 魔改；请求层把分页参数写死三种风格。

## 口述检查清单

每题收尾自问四句：

1. **目标**一句话是否可验收？
2. **约束**是否提了规模 / 合规 / 团队？
3. **权衡**是否至少对比了两条路？
4. **演进**是否有 MVP → 可运营的台阶，而不是一步到位？
