# 性能与用户体验面试题库

> **怎么用：** 普通题按「指标定义 → 测量条件 → 优化手段 → 验证边界」口述 1～2 分钟；深层题按「基线 → 预算 → 分层诊断 → 灰度 → 回滚」展开。任何性能结论都要记录页面、设备、网络、浏览器、版本和样本量，不能把相关性直接解释为因果，也不承诺所有业务获得统一幅度的提升。

> **当前口径：** Core Web Vitals 为 LCP、INP、CLS；“良好”阈值分别是 LCP ≤ 2.5 s、INP ≤ 200 ms、CLS ≤ 0.1。页面或站点应在移动端、桌面端分别聚合，以第 75 百分位判断三项是否都达标。字段能力、浏览器实现和实验性 API 会变化，上线前应核对目标版本的 web.dev、W3C 草案与兼容性数据。

---

## 一、指标、测量与预算

### Q1. Core Web Vitals 如何定义和判定？

**考察点：** LCP、INP、CLS、阈值、p75、设备分层和指标边界

::: details 参考答案

Core Web Vitals 当前包括 LCP、INP 和 CLS。LCP 衡量主要内容的加载体验，良好为不超过 2.5 s；INP 以一次页面访问中的合格 click、tap 和 keyboard 交互延迟评估整体响应性，良好为不超过 200 ms；CLS 衡量意外布局偏移，良好为不超过 0.1。介于良好与差之间是“需改进”，差的边界分别为 LCP 大于 4 s、INP 大于 500 ms、CLS 大于 0.25。

CLS 先排除 `hadRecentInput=true` 的 `layout-shift` 条目，也就是发生在合格离散输入后 500 ms 内、被标记为与近期输入相关的偏移；hover、scroll 等不一定触发这个排除。再把其余条目组成 session window：相邻 shift 间隔小于 1 s，且窗口从首个 shift 起最长 5 s，最终取各窗口累计值的最大值。判定不是看平均值或一次 Lighthouse 跑分，而是按页面或站点的真实访问样本聚合，移动端和桌面端分别计算第 75 百分位；三项都在良好阈值内才算通过。没有合格交互的访问没有 INP 样本，不能填 0 参与聚合；还应单报 eligible 状态、采集 coverage 与缺失原因。CWV 之外，错误率、业务可用时间、动画流畅度和任务完成率仍需独立 SLI。

:::

**追问：** 为什么不能把移动端和桌面端样本混在一起算一个 p75？

::: details 追问参考答案

两类设备的 CPU、内存、输入方式、网络和页面布局通常不同，混合分布会让高占比人群掩盖另一端的退化，也无法对应 web.dev 的分端判定口径。应分别设基线、预算和 owner；总体看板可以展示加权结果，但不能替代移动端、桌面端各自的 p75 与样本量。

:::

### Q2. RUM、Lab 与 PerformanceObserver 应如何配合？

**考察点：** 现场数据、实验室数据、采样、`buffered`、`entryTypes` 和支持边界

::: details 参考答案

Lab 在可控设备与网络下复现路径，适合发布前诊断、对比和定位瀑布图；RUM 来自真实用户，覆盖设备、网络、缓存、交互和长会话差异，适合判断 SLO 与线上回归。两者不能互相替代：普通页面加载模式的 Lighthouse 没有 click、tap 或 keyboard 交互，因此不产生 INP；Lab 要用 timespan / user flow 或自动化脚本执行真实、可重复的交互。Lab 变快不保证用户 p75 变快，RUM 退化也需要可复现样本和 trace 才能定位。

`PerformanceObserver.supportedEntryTypes` 可做运行时能力探测。`observe({ type, buffered: true })` 可接收该类型缓冲区中较早的条目，适合延迟加载采集器；`entryTypes` 用于同时订阅多个类型，但不能和 `type`、`buffered` 混用，且不支持的类型可能被忽略。缓冲并非无限历史，条目字段、阈值与实现也有兼容差异。工程上优先使用维护中的 `web-vitals` 库计算 CWV，自定义 Observer 用于归因，并记录库、浏览器和指标版本。RUM 事件只使用白名单路由模板；资源和 LoAF 脚本 URL 删除 query、fragment，函数名、元素 selector 映射为低基数语义标签，设置采样率、字段基数上限并禁止 Token、用户输入和个人信息。

:::

**追问：** 使用 `buffered: true` 是否就能保证拿到页面生命周期内的全部条目？

::: details 追问参考答案

不能。缓冲区有容量和类型限制，部分 API 不支持 `buffered`，跨 frame、后台页面、BFCache、预渲染与进程终止也有额外边界。应先检查 `supportedEntryTypes`，尽早建立关键观察器，按 `visibilitychange` 到 hidden 阶段发送当前值，并允许缺失字段。INP 还必须区分“浏览器或采集不支持”与“本次访问无合格交互”；后者保持无样本而不是补 0，分别上报 eligible、coverage 和缺失原因。

:::

### Q3. 如何制定可执行的性能预算？

**考察点：** 用户体验预算、资源预算、基线、分层、owner 和例外机制

::: details 参考答案

预算先从用户任务和 SLO 反推，而不是复制行业数字。体验预算可包含移动端与桌面端各自的 LCP、INP、CLS、业务首屏、错误率；资源预算可包含关键路径 JS、CSS、字体、图片字节，主线程执行时间、长任务数和第三方占比。每项明确统计窗口、p75 / p95、设备与网络层、冷暖缓存、版本和最小样本量。

预算要进入 PR 与发布门禁：Lab 用固定基线阻止明显膨胀，RUM 在灰度阶段检查真实回归。每项有 owner、到期时间和回滚动作；例外必须写明业务收益、增量成本、替代方案和偿还日期。预算是风险控制线，不是为了追求单次满分，也不能据此承诺固定转化提升。

:::

**追问：** 为什么只给 Bundle 大小设预算还不够？

::: details 追问参考答案

相同压缩体积可能有完全不同的解析、编译、执行和内存成本，加载时机及缓存命中也会改变体验。还要约束关键路径执行时间、长任务、请求优先级、图片解码和第三方 CPU，并在代表性低端设备与网络下测量；否则体积过线不一定慢，体积未超也可能阻塞交互。

:::

## 二、加载链路与资源治理

### Q4. Resource Hints、`preload` 与 `fetchpriority` 应怎样使用？

**考察点：** `dns-prefetch`、`preconnect`、`preload`、优先级提示和资源竞争

::: details 参考答案

`dns-prefetch` 只提前解析域名，`preconnect` 还提前建立连接，适合极少数确定会访问的关键跨源；过多连接会浪费 socket、CPU 和电量。`preload` 是对当前导航必需资源的强提示，必须给出正确的 `as`、类型和跨源属性，否则可能重复下载或抢占更关键资源。响应式图片 preload 还要让 `imagesrcset`、`imagesizes` 与目标 `<img>` 的 `srcset`、`sizes` 匹配，使浏览器采用同一候选选择逻辑；不能用指向某个固定候选的 `href` 误预载，再由 `<img>` 下载另一个候选。后续页面可能使用的资源更适合谨慎 `prefetch`，但浏览器可基于条件忽略提示。

`fetchpriority="high|low"` 表达相对优先级，常用于提高已在 HTML 中发现的 LCP 图片优先级，或降低非关键图片；它不替代正确的 DOM 发现顺序、`preload`、懒加载策略，也不保证浏览器采用。先用网络瀑布确认发现时间和实际优先级，再逐项实验，避免把所有资源标成 high 导致关键资源互相争抢。

:::

**追问：** LCP 图片已经写了 `fetchpriority="high"`，为什么仍可能很晚？

::: details 追问参考答案

图片可能由客户端 JS 很晚插入、被 CSS 背景间接发现、等待 HTML 或 CSS、经过重定向，或与更早的高优先级资源竞争。`fetchpriority` 只影响相对调度，不会让浏览器提前发现 URL。应先让图片进入初始 HTML；确需 preload 响应式图片时同步 `imagesrcset` / `imagesizes` 与 `<img>`，再用网络瀑布确认只请求最终候选，没有固定 `href` 引起的重复下载。

:::

### Q5. 如何治理 Bundle 与 Chunk？

**考察点：** Tree Shaking、代码分割、缓存、重复依赖和请求瀑布

::: details 参考答案

先用构建分析器和覆盖率找出入口中未使用、重复和高执行成本模块，再按路由、低频能力或重组件做动态导入。公共 Chunk 要基于真实复用与更新频率设计：过大使每个路由都支付成本，过碎则增加请求、调度、模块初始化和瀑布。稳定依赖与高频业务代码适当分离，可提高长期缓存命中，但不能只按包名机械拆分。

优化同时看 gzip / Brotli 传输量、解析编译执行、缓存命中和交互时序。删除无用 polyfill、改用可 Tree Shake 的入口、按 locale 加载数据，并防止 barrel file 意外拉入整库。每次构建记录 Chunk 名、内容哈希和依赖图，在 PR 比较增量，在真实路由和目标设备验证。

:::

**追问：** Chunk 越小是否越有利于性能？

::: details 追问参考答案

不是。细粒度分割能减少初始字节，却可能增加请求调度、压缩损失、模块包装、执行碎片和串行动态导入；频繁变更的小 Chunk 还可能降低缓存收益。应围绕用户路径和并行加载边界设计，用关键路由的总字节、请求链深度、主线程时间和 RUM 验证，而不是追求统一大小。

:::

### Q6. 响应式图片如何兼顾质量和性能？

**考察点：** `srcset`、`sizes`、现代格式、尺寸预留、懒加载和 LCP

::: details 参考答案

为图片提供与展示槽位匹配的 `srcset` 和准确 `sizes`，让浏览器按视口与 DPR 选择候选；在质量可接受且目标浏览器支持时使用 AVIF / WebP，并保留合适回退。服务端或构建流程生成受控尺寸，避免下载远大于 CSS 显示尺寸的原图。`width`、`height` 或 `aspect-ratio` 预留空间以降低 CLS。

首屏 LCP 图片通常不应 `loading="lazy"`，应让它尽早在 HTML 中可发现，并根据瀑布考虑 `fetchpriority="high"`；只有图片发现确实过晚等场景才考虑 preload，且响应式图片使用与 `<img>` 匹配的 `imagesrcset`、`imagesizes`，验证只下载选中的一个候选。视口外图片再懒加载和限制并发。优化不仅看文件大小，还要看解码时间、内存、裁剪语义和失败回退，并在不同 DPR、网络及内容样本上验证。

:::

**追问：** `sizes="100vw"` 为什么可能造成浪费？

::: details 追问参考答案

如果图片实际只占容器一半，浏览器会按整个视口估算槽位，可能选择宽度更大的候选，尤其在高 DPR 设备上浪费流量和解码内存。`sizes` 应描述加载时的真实布局规则，例如不同断点下的列宽；修改布局后也要同步更新，并通过网络面板检查最终候选。

:::

### Q7. Web 字体应如何优化而不牺牲可读性？

**考察点：** WOFF2、子集化、预加载、`font-display`、Fallback 和布局偏移

::: details 参考答案

优先使用 WOFF2，按实际字符集、字重和样式子集化，删除未使用字体；可变字体是否更省需以真实轴和字形比较。只 preload 首屏确定需要且能被当前 CSS 匹配的字体，并正确设置 `type` 与 `crossorigin`，否则会重复请求或抢占 LCP。长期缓存字体文件，CSS 与文件使用内容版本。

`font-display` 根据品牌与可读性选择 swap、optional 等策略；Fallback 字体用相近 metrics，必要时通过 `size-adjust`、`ascent-override` 等减小替换偏移。监控字体加载失败、FCP、LCP 和 CLS，避免为了字体“无闪动”长期隐藏文字。中文字体体积尤其大，系统字体、按需子集或产品视觉取舍应共同评估。

:::

**追问：** 为什么 preload 所有字重通常会更慢？

::: details 追问参考答案

preload 会把资源提前放入竞争队列，未在首屏使用的字重会占带宽、连接和缓存，可能延迟 CSS、LCP 图片及真正需要的字体。应从首屏文本和 CSS 匹配确认必要集合，只预载少量关键字体；其余按正常发现顺序加载，并用瀑布验证是否命中和复用。

:::

### Q8. 第三方脚本的主要性能风险和治理手段是什么？

**考察点：** 主线程竞争、网络链路、权限、隔离、延迟加载和供应商管理

::: details 参考答案

第三方脚本会增加 DNS / TLS、传输、解析执行、长任务、DOM 变更和内存，还可能注入更多级联请求；供应商更新不受当前仓库发布控制。先建立清单，记录业务目的、owner、加载页面、权限、字节、CPU、错误和到期复审。没有明确收益或 owner 的脚本应移除。

技术上使用 `async` / `defer`、用户同意或空闲后加载、服务端代理必要数据、iframe / Worker 等隔离，并限制超时、网络目标和 DOM 能力；隔离方案仍有通信和功能边界。灰度比较有无脚本的性能和业务指标，配置 kill switch 与降级。相关性变化不能直接证明脚本导致业务变化，需要对照实验和风险审查。

:::

**追问：** `async` 是否意味着第三方脚本不会阻塞用户交互？

::: details 追问参考答案

不是。`async` 主要避免下载阶段阻塞 HTML 解析，但脚本下载完成后仍会在主线程执行，可能产生长任务、同步布局、网络级联和事件处理延迟。应测量脚本执行与 Long Animation Frame 归因，延后非关键初始化，限制功能和超时，并保留关闭开关。

:::

## 三、运行时与可观测性

### Q9. Long Task 与 Long Animation Frame 各能说明什么？

**考察点：** 50 ms 阈值、主线程阻塞、LoAF、脚本归因和帧边界

::: details 参考答案

Long Tasks API 报告主线程持续超过 50 ms 的任务，可发现大段 JavaScript 或浏览器工作，但归因粒度有限，也不能直接等同一次慢交互。Long Animation Frames API 报告 duration 超过 50 ms 的长动画帧，能把脚本、样式、布局和呈现前工作放进帧上下文，并提供更有用的脚本归因；条目不保证真的执行了渲染阶段，没有渲染阶段时 `renderStart` 可能为 0，不能据此计算渲染耗时。其浏览器支持和字段仍需运行时检测。

INP 的一次交互延迟可拆成输入延迟、事件处理时长和呈现延迟。长任务或 LoAF 是诊断证据，不是 INP 本身：慢交互可能跨多个任务，任务也可能发生在没有交互时。应把 interaction id、低基数语义目标、LoAF、任务、组件和版本关联；LoAF 脚本 URL 删除 query / fragment，函数名降维并限制基数，在 DevTools 复现后拆分工作、让出主线程或移至 Worker。

:::

**追问：** 把一个 100 ms 任务拆成两个 50 ms 任务就一定能改善 INP 吗？

::: details 追问参考答案

不一定。如果两个任务连续排队、没有给输入和渲染机会，用户仍要等待；拆分还可能增加调度开销。应在非关键阶段使用调度 API 或分片，让浏览器获得实际的输入与绘制机会，并减少总工作量。最终以交互的输入、处理、呈现三段及 RUM 分位数验证。

:::

### Q10. 前端内存问题如何识别和定位？

**考察点：** 泄漏、堆快照、Allocation、Detached DOM、监听器和长期会话

::: details 参考答案

内存上涨不等于泄漏：缓存、懒初始化和 GC 时机都会形成锯齿。先定义可重复场景，如路由进出 20 次或大表格持续操作，固定版本、数据和设备，观察 GC 后保留堆、DOM 节点、监听器、定时器和进程内存是否持续增长。再用 Heap Snapshot 的 dominator / retaining path、Allocation instrumentation 和 Detached DOM 定位所有者。

常见原因包括未清理事件与 Observer、闭包保留大对象、全局 Map / Store 无上限、组件卸载后异步回调、第三方实例和对象 URL 未释放。修复要明确生命周期 owner，统一 dispose，缓存设容量与淘汰，并验证重复场景回落。浏览器内存 API 的支持、精度和权限有限，线上只做分层趋势与异常采样，不能承诺精确等同操作系统占用。

:::

**追问：** 为什么只比较两次堆快照的总大小容易误判？

::: details 追问参考答案

两次快照可能处于不同 GC、缓存预热和用户状态，总量差异不能说明对象不可回收。应执行相同操作周期并主动触发可用的测试 GC，比较对象数量、保留大小和 retaining path，确认 owner 已结束但对象仍被引用；再用修复前后多轮趋势验证。

:::

### Q11. Vue 大列表应如何优化？

**考察点：** 虚拟列表、响应式成本、稳定 Key、调度、可访问性和降级

::: details 参考答案

先确认瓶颈是数据请求、响应式依赖、VNode 创建、DOM 数量、布局还是单元格计算。大量行优先分页或虚拟化，只渲染可视窗口与 overscan；稳定唯一 `key`，避免索引 key 引发错误复用。大而近似只读的数据可用 `shallowRef` / `markRaw` 控制深层代理成本，昂贵派生结果做有边界缓存，更新批处理并避免每格创建重复 watcher。

虚拟化会影响动态行高、滚动定位、键盘焦点、屏幕阅读器、复制和打印，应提供语义、焦点保持和非虚拟降级。筛选排序可在数据量和设备达到阈值后移到 Worker，但要计算序列化成本。以目标低端设备测首屏、滚动帧、INP 和内存，不能仅用桌面开发机 FPS 下结论。

:::

**追问：** 为什么虚拟列表可能让无障碍体验变差？

::: details 追问参考答案

未渲染行不在可访问性树中，DOM 回收还可能让键盘焦点丢失，读屏用户无法感知总数、当前位置或连续浏览。需要使用正确表格 / 列表语义，暴露行列计数与位置，稳定焦点和选中状态，并为打印、复制或辅助技术提供分页等降级；最后必须人工键盘和读屏验证。

:::

### Q12. 性能告警如何减少误报并支持行动？

**考察点：** SLI、统计窗口、样本量、分层、版本、告警路由和回滚

::: details 参考答案

告警基于明确 SLO 和错误预算，而不是单个样本。对 LCP、INP、CLS、业务首屏、错误率等分别定义移动 / 桌面、白名单路由模板、设备和网络层，使用滚动窗口、p75 / p95、最小样本量及绝对值加相对基线条件。INP 看板只对有合格交互的访问聚合，不用 0 填补；同时告警 eligible 访问数、支持浏览器中的采集 coverage 和无交互 / 不支持 / 上报失败等缺失原因。低流量页面可延长窗口或聚合相似路由，不能用不稳定分位数频繁叫醒 owner。

事件必须携带生效版本、发布时间、实验桶、地区、样本量和数据新鲜度，路由到明确 owner，并附代表样本与回滚手册。事件维度使用路由模板和低基数标签，设置采样率与基数上限，禁止敏感自由字段。发布告警可采用快慢双窗口，避免瞬时噪声又能捕捉持续回归。自动回滚只针对证据充分且回滚安全的变化；业务活动、流量结构和监控版本变化应作为候选解释，而不是预设根因。

:::

**追问：** 为什么全站一个 LCP 告警阈值通常不可操作？

::: details 追问参考答案

不同路由的内容、流量、设备和 owner 不同，全站聚合可能让高流量快页面掩盖核心慢页面，或因流量结构变化产生假回归。应先按移动 / 桌面和页面类型设 SLO，再按版本、网络与设备切片；全站指标用于趋势总览，告警应能直接定位责任域和回滚对象。

:::

## 四、深层工程场景

### D1. 如何建立体验 SLI / SLO？

::: details 参考答案

#### 基础结论

从关键用户任务定义少量可计算的体验 SLI，再以真实用户分层基线制定 SLO、预算和错误预算。每项必须有口径版本、owner、告警、例外和回滚机制。

#### 原理深挖

CWV 覆盖加载、响应与稳定性，但不等于业务可用。一个 SLI 要说明起止点、成功条件、统计单位、分位数、样本资格和缺失处理。例如“商品详情移动端 LCP p75”与“从点击提交到可确认结果 p95”不能混成一个数。CLS 采用排除 `hadRecentInput=true` 条目后的最大 session window；INP 只来自有合格 click、tap 或 keyboard 交互的访问，无交互时保持无样本。移动 / 桌面、设备、网络与关键路由的分布不同，聚合会产生辛普森悖论。SLO 应根据用户容忍度、当前基线和改造能力制定，不把行业阈值机械变成所有业务唯一目标。

#### 工程场景

先盘点登录、搜索、详情、提交等旅程，建立 RUM 基线；CWV 按移动 / 桌面分别看 p75，关键任务补充成功率、可用时间和 p95。定义月度 SLO 与发布期性能预算，事件使用白名单路由模板，并带设备、网络、浏览器、版本和实验桶。INP 看板同时展示 eligible 访问、采集 coverage 与分原因缺失率，不把无交互访问补成 0。所有事件设置采样和基数上限，禁止敏感字段。超预算由页面 owner 处理，平台团队维护采集质量，发布负责人决定灰度或回滚。

#### 反例 / 踩坑

只看平均加载时间、把所有页面混合、把 INP 缺失填 0、在样本很少时计算 p75、采集版本变化却不标记、没有 owner 的红色看板，都会让 SLO 不可执行。将性能与转化同步上涨直接写成因果，也会误导投资判断。

#### 资深回答模板

我先从关键任务定义“用户何时感到可用和响应”，再把 CWV、业务首屏、成功率拆成可计算 SLI。以移动 / 桌面、设备和网络分层基线定 p75 / p95 SLO，绑定版本、样本量、owner、预算与回滚；业务影响通过实验验证，不从相关曲线直接推导。

:::

**追问链：**
1. SLO 应该直接照抄 CWV 良好阈值吗？
2. 低流量页面怎样设分位数告警？
3. 指标口径升级时如何保持可比性？

::: details 追问参考答案

**1. SLO 应该直接照抄 CWV 良好阈值吗？**

不应机械照抄。LCP、INP、CLS 的良好阈值是重要外部基线，仍要结合页面任务、当前分布和业务风险补充更严格或不同的内部 SLO。比如交易提交需要端到端成功时间，不能由 INP 替代；口径、分层和错误预算必须明确。

**2. 低流量页面怎样设分位数告警？**

设置最小样本量并延长统计窗口，或按相同模板与 owner 聚合路由，同时保留单页诊断。还可结合 Lab 门禁和错误率等更稳定信号。样本不足时展示“不确定”而不是强行判定通过或失败，避免少量极端值触发噪声。

**3. 指标口径升级时如何保持可比性？**

事件记录采集 SDK、算法和 schema 版本，新旧口径并行一段时间，比较覆盖率与分布差异；看板按版本切分并标注断点。确认迁移后再重设基线和阈值，保留历史定义，不能把算法变化伪装成产品性能改善。

:::

### D2. 如何做首屏性能端到端治理？

::: details 参考答案

#### 基础结论

把首屏拆成服务端、网络、资源发现、下载、主线程、渲染和业务数据阶段，以用户可见内容为终点。先从 RUM 长尾定位，再用代表性 Lab 复现，按预算灰度并保留回滚。

#### 原理深挖

LCP 从导航开始计时，候选会随更大内容出现而更新；浏览器通常在首次用户输入后停止报告新的 LCP 候选。原生 API 与 CWV 计算仍有 iframe、后台、预渲染等差异。传统 LCP API 以硬导航为中心，SPA soft navigation 的标准识别和指标重置仍有实现限制，不能简单把路由切换后的最后一个候选当新页面 LCP。首屏还可能被 TTFB、渲染阻塞 CSS、LCP 资源发现延迟、JS 水合或业务接口共同限制。

#### 工程场景

RUM 记录 TTFB、FCP、LCP 候选的低基数元素标签、资源发现和请求时刻、关键 Chunk 及页面版本；资源 URL 删除 query、fragment，并映射到允许的资源或路由模板，禁止业务数据和敏感字段。按移动 / 桌面、低端设备、4G / 慢网、冷暖缓存分层，设置采样率和维度基数上限。服务端优化缓存和流式输出；HTML 提前暴露 LCP 图片；校准 preload 与 `fetchpriority`。响应式图片确需 preload 时匹配 `imagesrcset` / `imagesizes` 与 `<img>`，用瀑布确认没有固定 `href` 误预载产生的重复请求。每项设置字节和阶段预算，灰度观察 p75 / p95、错误与业务任务，超阈值回滚。

#### 反例 / 踩坑

只压缩图片而忽略 TTFB、把骨架屏当业务首屏、对所有图片 preload、用固定 `href` 预载响应式图片的错误候选、首屏 LCP 图片懒加载、仅跑高配桌面 Lighthouse，或在 SPA 中自行重置时间却宣称等同标准 CWV，都会产生错误结论。

#### 资深回答模板

我先定义“首个非占位关键内容可见”，把 LCP 链路拆为 TTFB、发现、下载、渲染和业务数据。RUM 找到设备与网络长尾，Lab 复现具体资源链，再按阶段预算优化；硬导航和 soft navigation 分开标注口径，版本灰度验证并设置 owner 与回滚阈值。

:::

**追问链：**
1. LCP 观察何时停止，有什么采集风险？
2. SPA 路由切换能否直接沿用硬导航 LCP？
3. 首屏优化怎样避免资源优先级反转？

::: details 追问参考答案

**1. LCP 观察何时停止，有什么采集风险？**

浏览器在用户首次输入后通常不再报告新的 LCP 候选；页面隐藏、后台启动、iframe 和预渲染也影响有效值。延迟采集应使用支持时的 `buffered` 并处理 visibility，但不能假设拿到所有历史。生产优先用 `web-vitals` 库，并记录缺失率和浏览器版本。

**2. SPA 路由切换能否直接沿用硬导航 LCP？**

不能直接等同。传统 LCP 从文档导航开始，soft navigation 的识别、时间原点和重置仍受实验性 API、浏览器与库版本限制。内部可定义“路由内容可见”指标，但要另命名并记录口径；采用 soft-navigation 实验能力时先检测支持，不能冒充跨浏览器标准 CWV。

**3. 首屏优化怎样避免资源优先级反转？**

先画关键资源图，确保 HTML 尽早发现 CSS、字体和 LCP 图片；只 preload 确定必需资源，匹配 `as`、类型与跨源属性。响应式图片同步 link 的 `imagesrcset` / `imagesizes` 与 `<img>` 的 `srcset` / `sizes`，不要用固定候选 `href` 代替选择逻辑；用瀑布确认只有最终候选请求。限制 high 数量，并在弱网验证非关键资源没有挤占 LCP。

:::

### D3. 如何诊断和优化 INP 与长任务？

::: details 参考答案

#### 基础结论

把慢交互拆成输入延迟、处理时长和呈现延迟，再关联交互目标、Long Task、Long Animation Frame、组件和版本。先减少总工作量，再分片、调度或移出主线程。

#### 原理深挖

一次交互可包含多个事件，INP 从页面访问中的合格 click、tap 和 keyboard 交互延迟选取代表值，并对交互很多的页面做离群处理，而不是简单平均。没有合格交互就没有 INP 样本，不能填 0。输入延迟来自前序主线程工作；处理时长来自事件回调；呈现延迟可能来自后续任务、样式、布局与绘制。Long Task 以超过 50 ms 的任务为线索，LoAF 是 duration 超过 50 ms 的长动画帧；LoAF 可能没有渲染阶段，此时 `renderStart=0`，不能把 0 当真实渲染起点。两者都不等于 INP。

#### 工程场景

RUM 对 eligible 访问采集 INP、interaction type、三段耗时、LoAF 归因、路由模板和版本，并单报支持范围、coverage 与无交互 / 不支持 / 上报失败的缺失原因。元素 selector、函数名映射为白名单低基数语义标签；资源和 LoAF 脚本 URL 删除 query、fragment，设置采样率和基数上限，禁止输入值等敏感字段。Lab 使用 timespan / user flow 或自动化脚本执行真实交互，普通加载 Lighthouse 不会产生 INP。DevTools 在相同数据和低端设备复现后，再按三段优化并灰度看移动 / 桌面 p75 与错误率。

#### 反例 / 踩坑

只给 handler 加 debounce、把同步任务包进 Promise、把 100 ms 连续切成两个无渲染机会的任务、盲目迁移 Worker 却传输巨大对象、把无交互访问记作 INP=0，或用普通加载 Lighthouse 声称测得 INP，都可能得出错误结论。

#### 资深回答模板

我先分别报告 INP eligible、coverage 和缺失原因，只在有合格交互的访问中计算分位数。RUM 使用路由模板和低基数标签定位页面、目标、设备与版本，Lab 脚本化真实交互，再按输入、处理、呈现三段结合 LoAF 归因；以分层 p75 灰度验证，异常关闭变更。

:::

**追问链：**
1. 输入延迟高但事件处理很短说明什么？
2. Worker 为什么不一定改善 INP？
3. 如何避免 INP 采集泄露用户数据？

::: details 追问参考答案

**1. 输入延迟高但事件处理很短说明什么？**

用户输入到达时主线程可能正执行前一个长任务，例如水合、JSON 处理或第三方脚本，事件只能排队。应查看交互前的任务与 LoAF，而不是只优化当前 handler；延后初始化、分片或减少第三方工作后，再验证输入延迟是否下降。

**2. Worker 为什么不一定改善 INP？**

数据结构化克隆、序列化、消息排队和主线程应用结果都有成本，DOM 与许多框架状态也不能直接在 Worker 操作。只有可独立的重计算且传输成本可控时收益明显；应做代表数据 benchmark，提供主线程降级，并观察总延迟和内存。

**3. 如何避免 INP 采集泄露用户数据？**

不要上报文本、输入值、完整 DOM、原始函数名或含账号的选择器。为交互点设置稳定的语义 id 白名单，路由改为模板；资源与 LoAF 脚本 URL 删除 query、fragment，只记录低基数组件、事件类型、耗时、版本和粗粒度设备信息。限制采样率、字段基数、访问权限与保留期，对敏感自由字段直接禁止而非仅掩码。

:::

### D4. 如何治理 Vue 大表格并设计响应式降级？

::: details 参考答案

#### 基础结论

按数据量、交互和设备能力建立分级方案：服务端分页是上限保护，虚拟化控制 DOM，浅响应式与批量更新控制计算；同时保留键盘、读屏、复制和打印能力。

#### 原理深挖

大表格成本来自数据传输、深层 Proxy、派生计算、VNode / DOM、布局、粘性列和高频更新。虚拟化减少 DOM，却引入动态行高、滚动锚点、焦点和可访问性问题。服务端分页减少客户端总量，但增加网络和选择状态复杂度。优化应以用户任务和数据规模选择组合，不能把一个方案用于所有设备。

#### 工程场景

先用 1 千、1 万、10 万行基准拆分请求、转换、响应式、渲染和滚动成本。默认服务端游标分页；中等规模启用行虚拟化与 overscan，列很多时评估列虚拟化。稳定 row key，`shallowRef` 保存批次数据，编辑行局部响应，排序筛选达到阈值后放服务端或 Worker。按内存、帧时长和 INP 自动降低实时刷新频率或关闭装饰列，用户可见提示。为表格语义、焦点、选中、复制和打印提供专门路径。

#### 反例 / 踩坑

一次加载所有数据、每格创建 watcher、用数组索引作 key、滚动时同步测量所有行、低端机仍开启实时高亮，或虚拟化后宣称“DOM 少所以无障碍自然没问题”，都是常见风险。

#### 资深回答模板

我先用真实数据和低端设备建立基线，按请求、Proxy、VNode、布局和滚动分段。服务端分页保护上限，虚拟化控制窗口，编辑状态局部化；预算超限时分级降低刷新和装饰。性能、键盘、读屏、复制与打印一起验收，并绑定组件 owner 与回滚开关。

:::

**追问链：**
1. 大表格何时应优先服务端分页而不是虚拟化？
2. 动态行高如何影响虚拟列表？
3. 响应式降级的触发条件如何设计？

::: details 追问参考答案

**1. 大表格何时应优先服务端分页而不是虚拟化？**

总数据很大、查询频繁变化、客户端内存有限或权限不允许下载全量时，服务端分页优先。虚拟化只减少 DOM，不减少传输和数据驻留；可在每页内部继续虚拟化，但要维护稳定游标、排序、筛选和跨页选择语义。

**2. 动态行高如何影响虚拟列表？**

未测量高度会让总高度和滚动偏移估算不准，内容展开后可能跳动。可使用合理估值、ResizeObserver 增量校正与滚动锚定，并限制极端内容；校正不能在每帧同步测量全部行，还要测试快速滚动、焦点定位和 CLS。

**3. 响应式降级的触发条件如何设计？**

优先用可观测负载而不是粗暴 UA：数据量、近期帧时长、内存压力代理信号、网络和用户设置共同判断。阈值来自分层基线，降级应稳定、防抖且可解释，例如降低刷新频率；记录生效版本和原因，并允许远程调整与回滚。

:::

### D5. 如何诊断内存泄漏和长期会话退化？

::: details 参考答案

#### 基础结论

将长期会话视为独立可靠性场景：用可重复操作周期观察 GC 后保留对象和进程趋势，以 retaining path 找 owner，修复后做耐久回归和线上分层告警。

#### 原理深挖

JS 堆只是浏览器内存的一部分，DOM、图片、Canvas、GPU、Worker 和第三方原生分配未必完整反映在普通堆快照中。缓存预热会增长后稳定，真正泄漏则在 owner 生命周期结束后仍被引用。SPA 路由、事件总线、Observer、定时器、异步闭包和无限 Store 常使页面长期驻留。跨浏览器内存测量 API 支持和精度有限，不能把单个值当绝对真相。

#### 工程场景

为客服台等长会话建立 2 小时脚本，循环开关路由、表格、弹窗与上传。记录版本、设备、JS heap、DOM、Worker、任务和崩溃；在实验室用快照、allocation timeline 和 retaining path 定位。组件维护 disposal 清单，AbortController 取消请求，停止 watcher / Observer / timer，撤销对象 URL，缓存设 LRU 上限。发布前耐久测试，灰度观察内存趋势、页面失效和任务耗时，异常回滚。

#### 反例 / 踩坑

看到内存上涨就每分钟强制刷新、只在组件 `beforeUnmount` 清 DOM、不取消全局监听、用 WeakMap 代替所有缓存却不检查 value 引用，或拿一次快照总量宣称修复，都会掩盖根因。

#### 资深回答模板

我先定义长期会话的操作周期和内存预算，区分预热平台期与 GC 后持续增长。快照沿 retaining path 找到生命周期 owner，统一 dispose 和缓存上限；再跑相同耐久脚本及线上版本灰度，观察内存、崩溃和 INP，超过阈值关闭特性或回滚。

:::

**追问链：**
1. 如何区分缓存增长与泄漏？
2. Vue 组件卸载后仍被保留的常见原因是什么？
3. 线上内存告警为什么要谨慎？

::: details 追问参考答案

**1. 如何区分缓存增长与泄漏？**

缓存应有明确 owner、容量、淘汰策略和可解释命中收益，预热后趋于平台；泄漏通常随相同操作周期持续增长，owner 消失后对象仍有 retaining path。清空或达到容量后做对照，并比较 GC 后多轮趋势，而不是只看瞬时峰值。

**2. Vue 组件卸载后仍被保留的常见原因是什么？**

全局事件总线、未停止的 `watch` / effect scope、Observer、定时器、第三方实例、Store 中保存组件对象，以及异步回调闭包都可能保留实例。应在 composable 中让创建与 dispose 对称，异步任务可取消，并通过快照确认保留链真正断开。

**3. 线上内存告警为什么要谨慎？**

浏览器暴露能力不一致，采样值受 GC、标签页、图片和设备总内存影响，隐私限制也降低精度。应按浏览器、设备和版本看趋势，结合崩溃、页面丢弃、长任务等信号，并设最小样本量；告警用于定位候选版本，不直接判定根因。

:::

### D6. 如何隔离和治理第三方资源？

::: details 参考答案

#### 基础结论

第三方默认不进入关键路径。以资产清单、业务价值、最小权限、加载预算、运行隔离、可观测和 kill switch 管理其完整生命周期。

#### 原理深挖

第三方资源既竞争网络和主线程，也拥有读取 DOM、Cookie 或发送请求的潜在权限，供应商可独立更新。`async` 不消除执行阻塞，CSP / SRI 能降低部分风险但不解决 CPU，iframe 隔离 DOM 仍会占资源，Worker 可隔离主线程但不适合依赖 DOM 的 SDK。治理是性能、安全、隐私和业务共同决策。

#### 工程场景

建立域名、脚本、owner、目的、数据权限、SLA、到期日清单；CI 记录字节和已知资源，RUM 记录资源时序、LoAF、错误和业务触发。资源与 LoAF 脚本 URL 去除 query、fragment，路由使用模板，函数名映射为允许的低基数标签；设置采样率、基数上限，并禁止 Token、用户输入和个人信息。营销脚本在同意与关键内容后加载，聊天等按用户操作加载；能服务端采集的能力不下发完整 SDK。用 iframe / Worker 做适配隔离，设置超时和网络白名单。按稳定实验桶灰度，异常远程关闭并退化为基础流程。

#### 反例 / 踩坑

Tag Manager 可任意加脚本、所有页面加载全部 SDK、供应商异常时无限重试、只比较脚本字节不看 CPU、关闭第三方后业务埋点也完全丢失，都会使故障不可控。

#### 资深回答模板

我把每个第三方当外部依赖：先证明业务必要性，再分配网络、CPU 和权限预算，尽量在同意或用户触发后加载。用隔离适配层、版本记录与 RUM 归因观测，稳定灰度对比性能和业务；超阈值 kill switch 关闭，并保留最小自有事件链。

:::

**追问链：**
1. SRI 能否解决第三方脚本的全部风险？
2. 如何判断第三方脚本值得保留？
3. 第三方故障时怎样保证回滚？

::: details 追问参考答案

**1. SRI 能否解决第三方脚本的全部风险？**

不能。SRI 校验指定文件内容完整性，但无法降低已批准代码的 CPU、网络、隐私权限和业务逻辑风险，动态子资源也需另行治理。频繁变更脚本还要维护 hash。仍需 CSP、权限最小化、隔离、预算、监控和关闭开关。

**2. 如何判断第三方脚本值得保留？**

用稳定对照实验比较启用与关闭组的任务完成、收入或运营收益，同时看 LCP、INP、错误、隐私和运维成本。实验需控制版本与流量分层；观察到相关变化不自动等于因果，统计显著也要评估效应量和长期副作用。

**3. 第三方故障时怎样保证回滚？**

通过自有适配层和远程配置控制加载，设置失败超时、熔断和基础降级，不让页面等待供应商。配置版本化、可审计，并预演关闭后的登录、支付和埋点路径；紧急回滚指向已验证配置，而不是临时修改线上脚本。

:::

### D7. 如何建立性能回归门禁与灰度体系？

::: details 参考答案

#### 基础结论

采用“PR Lab 预算 + 版本灰度 RUM SLO + 自动或人工回滚”三层门禁。所有比较绑定基线、环境、版本、样本量、owner 和例外期限。

#### 原理深挖

Lab 可重复但不能代表真实分布，RUM 真实但有延迟、噪声和流量结构变化。绝对阈值防止长期劣化，相对基线捕捉本次回归；两者结合并设置容差。统计比较必须分移动 / 桌面、设备和网络，保持实验桶稳定，避免把流量变化当版本影响。性能改善也不能掩盖错误率和业务功能退化。

#### 工程场景

PR 对关键路由运行固定设备网络的多次测试，检查关键 JS / CSS / 图片预算、LCP、阻塞时间和可访问流程；INP 场景必须用 timespan / user flow 或自动化脚本执行真实 click、tap、keyboard 交互，普通加载 Lighthouse 只作为加载诊断。合并后先内部与 1% 灰度，再分阶段扩大；RUM 按版本和稳定桶比较 p75 / p95、CWV、错误与任务成功率，INP 另看 eligible、coverage 和缺失原因，不补 0。设置快慢窗口、最小样本和数据延迟保护。每项门禁有 owner；超阈值可停止扩量、关闭 feature flag 或回滚制品。

#### 反例 / 踩坑

只跑一次普通加载 Lighthouse 并声称覆盖 INP、不同机器互比、把 INP 缺失填 0、用平均值、灰度桶漂移、未记录实际生效版本、指标一红就自动回滚不可逆迁移，或为了过门禁删除监控样本，都会让体系失真。

#### 资深回答模板

我在 PR 用固定基线和资源预算阻断明显回归，在灰度用按版本、设备、网络分层的 RUM 验证真实 p75。门禁同时看性能、错误和业务任务，满足样本量才决策；每个阈值有 owner、例外期限、feature flag 与已演练回滚路径。

:::

**追问链：**
1. Lab 指标波动如何设置门禁？
2. RUM 回归怎样排除流量结构变化？
3. 哪些情况下不应自动回滚？

::: details 追问参考答案

**1. Lab 指标波动如何设置门禁？**

固定硬件或受控 runner、浏览器版本、网络和页面数据，多次运行取中位或稳定分位，并维护主分支同时段基线。门禁使用绝对预算加超过噪声带的相对变化；临界结果重跑并保存 trace，不能以一次最好成绩通过。

**2. RUM 回归怎样排除流量结构变化？**

按版本和稳定实验桶比较同一时间窗，再对移动 / 桌面、设备、网络、地区、路由和缓存状态分层，检查样本量与权重。必要时做标准化或持有对照组；这些方法降低混杂，但因果结论仍应依赖受控发布或实验设计。

**3. 哪些情况下不应自动回滚？**

数据库迁移不可逆、回滚版本存在更严重安全问题、样本不足、采集口径刚变化或回滚会造成协议不兼容时，不应机械执行。应停止扩量、关闭可逆功能、人工确认依赖和数据兼容，再按预案选择前滚或回滚。

:::

### D8. 如何分析性能指标与业务结果的关联？

::: details 参考答案

#### 基础结论

先用分层观察发现假设，再用随机实验或可信准实验估计某个具体性能干预对业务结果的总效应。A/B 随机化的是干预方案，不会自动证明业务变化由 LCP、INP 等性能指标中介；报告要区分总效应与速度本身的因果效应，不承诺统一提升。

#### 原理深挖

快页面用户可能本就拥有更好设备、网络、地区或更高购买意愿，业务活动也会同时改变流量与页面内容，因此“LCP 更快的用户转化更高”只是相关性。按会话事后分组还可能引入幸存者偏差。把图片、SSR 或缓存方案随机化，只能识别该方案包含功能、视觉、成本等全部路径的总效应；即使方案同时改善 LCP 与转化，也不能自动断言 LCP 是中介。要估计速度本身的效应，需要干预只通过速度起作用的排除限制，或预先设计并满足相应假设的因果中介、工具变量等识别方案，而不是事后按 LCP 分组。

#### 工程场景

观察阶段按设备、网络、地区、新老用户和路由模板查看 LCP / INP 与任务完成率，只形成“某项性能干预可能改善加购”的假设。实验阶段灰度一个具体图片或 SSR 方案，记录实际版本与曝光，预先定义主要指标、CWV、错误率和实验周期。先分析 ITT 总效应与必要的分层效应；只有研究问题确实要求速度中介效应，才在实验前声明识别假设并设计中介分析或有效工具变量。报告绝对变化、区间和适用人群；实验异常可回滚。

#### 反例 / 踩坑

把快慢用户直接对比当因果、把干预总效应解释成 LCP 中介效应、事后把分桶当工具变量、只挑显著切片、同时改性能和推荐算法、忽略错误率、按结果提前结束实验，或把一个页面的结论承诺给所有业务，都会夸大收益。

#### 资深回答模板

我先把 RUM 与业务事件按同一页面版本和会话做低基数、脱敏关联，用设备、网络等分层提出假设。随后随机化一个具体干预，预注册性能、业务与护栏指标，报告该干预的 ITT 总效应；不把它自动解释为速度中介。若要估计速度本身，则另行声明排除限制或中介 / 工具变量识别假设，结论限定人群和版本。

:::

**追问链：**
1. 为什么“快用户转化高”不能证明提速会提高转化？
2. 性能实验应设置哪些护栏指标？
3. 性能改善但业务指标不显著时怎么办？

::: details 追问参考答案

**1. 为什么“快用户转化高”不能证明提速会提高转化？**

快用户可能同时拥有高端设备、稳定网络、不同地区和更强购买意愿，这些混杂因素既影响性能也影响转化；未完成加载的用户还可能不进入分析样本。随机分配具体优化能估计该干预的总效应，但若干预还改变视觉或功能，就不能把总效应称为“速度本身”的增量效果；后者需要额外识别设计。

**2. 性能实验应设置哪些护栏指标？**

至少包含错误率、崩溃或白屏、任务成功率、服务端成本、流量、CLS / INP 等未直接优化的体验指标，以及数据采集覆盖率。按移动 / 桌面和关键设备网络分层，防止总体收益掩盖弱势用户退化；达到安全阈值应停止扩量。

**3. 性能改善但业务指标不显著时怎么办？**

先检查实验功效、曝光、优化幅度、周期和指标链路，再报告置信区间而不是宣称“无影响”。体验 SLO、可访问性和基础质量本身仍有价值，但需与投入比较；可保留低成本改进、缩小场景或回滚复杂方案，不能虚构统一业务收益。

:::
