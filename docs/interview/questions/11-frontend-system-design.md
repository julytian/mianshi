> **怎么用：** 先盖住答案，按 **目标 → 约束 → 方案权衡 → 演进** 自己画一页纸口述 8～12 分钟，再对照参考答案补洞。本模块面向 Lead / 中大厂：要的是取舍与演进，不是组件 API 清单。中英文术语之间请习惯留空格。

### Q1. 设计一个中后台「管理后台框架」（Vue 3 + 组件库）

**考察点：** 布局与路由壳、权限接入点、模块边界、可替换基建

::: details 参考答案
#### 目标

为多业务线提供统一的**壳应用**：登录会话、布局（侧栏/顶栏）、动态路由与菜单、权限指令、请求层、错误页、主题与水印；业务以「页面模块」插入，而不是复制整仓脚手架。

#### 约束

- 团队以 Vue 3 + Ant Design Vue（或同类）为主；TS 强制。
- 首屏可接受「壳 + 首个业务页」合计可控（内网后台可略宽，但别无脑全量同步路由）。
- 多仓库或 monorepo 都可能；权限以后端为准。
- 要能灰度、要能按业务分包懒加载。

#### 方案权衡

| 方案 | 优点 | 代价 |
| ---- | ---- | ---- |
| A. 单一巨石后台 | 联调简单、权限一套 | 构建慢、发布耦合、权限误伤面大 |
| B. 壳 + 业务子应用（微前端） | 独立发布、技术栈可异构 | 路由/样式/公共依赖治理成本高 |
| C. Monorepo 多 package + 统一壳 | 类型与组件复用好、发布仍可拆 | 工程门槛、CI 复杂度上升 |

推荐默认路径：**先 C 的轻量版**（`app-admin` 壳 + `features/*` 业务包 + 共享 `shared`），真有独立发布与多团队强隔离再上 B。

关键设计点：

1. **路由**：布局路由固定；业务路由由权限接口下发后 `addRoute`；组件用白名单 `import.meta.glob` / `componentMap`。
2. **请求层**：统一 `baseURL`、Token、错误码、取消与幂等键协议；服务端负责幂等记录、冲突判定与结果复用，前端不能单独保证写操作幂等。
3. **扩展点**：菜单图标映射、页面 keep-alive 白名单、全局水印、字典缓存——做成注册表，而不是改壳源码。
4. **质量门禁**：ESLint + 路由 meta 类型 + 资源—动作能力映射静态检查（可选）。

#### 启动、装载与运行闭环

- 登录建立会话后拉能力快照、菜单和字典，再生成路由；页面经统一请求层访问领域 API。按路由数、并发会话、首屏请求和业务包体积做预算，菜单与字典按租户和版本缓存。
- 动态组件清单由受信发布服务签发，壳通过信任根校验入口、版本和资源摘要；密钥按 `keyId` 轮换。验签或摘要失败即拒绝装载并展示降级页，服务端仍逐资源实例授权。
- 权限接口失败时关闭高风险入口，字典失败显示原值，业务包失败由壳隔离。壳、业务包和后端契约维护兼容矩阵，分别灰度并保留上一稳定产物。
- 平台 Owner 负责壳与接入协议，业务 Owner 负责页面与领域 API；路由可用率、登录恢复、装载失败、版本和 TraceId 进入共同 Runbook。

#### 演进

1. **MVP**：登录 + 布局 + 静态菜单 + 2 个业务页 + 统一请求。
2. **V1**：动态路由 / 按钮权限、字典与用户偏好、错误监控接入。
3. **V2**：按业务分包、可插拔布局、设计令牌主题；只有独立发布冲突、故障隔离和自治收益经数据证实后，才评估微前端，不以团队数量设机械阈值。
4. **长期**：模块联邦或包级版本策略；壳升级与业务升级解耦（peerDeps + 兼容矩阵）。
:::

**追问链：**
1. 多 tab 页签（keep-alive + 缓存淘汰）你放在壳还是业务？
2. 微前端的样式隔离与公共 AntDV 多实例怎么处理？
3. 壳发版如何保证旧业务页不炸？

::: details 追问参考答案

**1. 多 tab 页签（keep-alive + 缓存淘汰）你放在壳还是业务？**

页签导航、租户切换清空、总缓存预算和 LRU 淘汰放壳，业务只通过版本化协议声明稳定页 ID、是否可缓存、脏数据确认与恢复钩子；缓存键含租户、主体、路由参数和业务版本，禁止跨权限快照复用。超预算先淘汰后台页，保存失败则提示而非静默丢状态。壳 Owner 观测命中率、内存和恢复失败，灰度协议并保留关闭页签模式的回滚开关。

**2. 微前端的样式隔离与公共 AntDV 多实例怎么处理？**

先用 Token 命名空间、CSS Modules 和约定挂载根隔离，强冲突应用再用 Shadow DOM；AntDV 按 Vue 大版本与主题协议划兼容组共享，不能强制全局单例，异构组各自加载并计入容量预算。壳向子应用下发版本化 Token，不共享可变 Store；样式或依赖加载失败只降级该应用。平台 Owner 观测重复体积、冲突率，兼容组灰度，异常时回退独立依赖。

**3. 壳发版如何保证旧业务页不炸？**

壳只暴露带版本的路由、会话、主题和通信协议，CI 用历史子应用做契约与回放测试，动态清单声明兼容范围、入口摘要和 `keyId`，壳验签后才装载。发布按租户稳定分桶，监控装载成功率、白屏和协议错误；超阈值自动停灰并切上一壳产物。接口新增保持向后兼容，破坏变更走双版本窗口；平台 Owner 管壳回滚，业务 Owner 管页面降级。

:::

**踩坑：** 业务直接改壳的 layout；或权限只藏菜单不拦路由；一上来全量微前端。

### Q2. 设计前端监控体系（稳定性 + 体验）

**考察点：** 采集分层、采样、隐私、报警闭环、和性能指标挂钩

::: details 参考答案
#### 目标

让线上问题**可发现、可定位、可归因**：JS 错误、资源失败、接口异常、白屏、核心性能（LCP/INP/CLS 或内网自定义）、关键业务漏斗（登录成功率、下单成功率）。

#### 约束

- 包体积与主线程开销有预算；不能拖垮弱网 H5。
- 合规：脱敏、禁止扫本地存储明文、用户标识可哈希。
- 多端：Web 管理端、H5、可能还有小程序（小程序另有平台数据，需对齐字段）。
- 已有或可自建上报网关；报警要对人负责（on-call），不是只堆大盘。

#### 方案权衡

| 层次 | 采什么 | 注意 |
| ---- | ------ | ---- |
| 错误 | `window.onerror` / `unhandledrejection`、框架 errorHandler、资源 `error` | SourceMap 私有化；去重与聚合 |
| 性能 | PerformanceObserver、长任务、路由切换耗时 | 采样率；SPA 软导航要自己打点 |
| 行为 / 业务 | 关键按钮、接口 code、自定义 `metric` | 和产品漏斗对齐命名 |
| 会话 | sessionId、版本号、环境、用户角色（非敏感） | 便于「仅某版本」过滤 |

自建 vs 商业 SaaS：团队小、合规严 → 可自建采集 + 现有日志平台；要快速有洞察 → SaaS + 敏感字段网关剥离。

SDK 形态：薄封装 `report(event, payload)` + 插件（error/perf/api）；错误也受应用级与租户级配额、指纹聚合、入口限流和动态采样控制，高价值新错误优先保留。接口监控优先在请求层统一拦截，比页面手埋稳。

#### 采集管道与运营闭环

- SDK 批量上报，经网关配额和脱敏、队列、指纹聚合后进入指标与事件存储。按峰值事件/s、高基数字段和留存估算成本，用分级采样与租户配额控制噪声。
- 网关从已认证会话派生主体，用服务端轮换密钥生成 HMAC 后立即丢弃原始 ID；浏览器不持密钥。SourceMap 私有访问，字段和留存最小化，会话回放单独评审。
- 网关过载丢低优先级事件，队列积压延迟告警，存储降级保聚合指标；SDK 熔断且可远程停插件，Schema 向后兼容并支持版本回滚。
- SDK、管道和告警各有 Owner；平台接收 SLI 明确分母、窗口和维护排除，业务团队拥有告警规则与 on-call，平台团队不替业务判断影响。

#### 演进

1. **MVP**：错误 + 版本号 + 网关生成的轮换 HMAC 用户标识；网关基于已认证主体和服务端密钥计算后立即丢弃原始 ID，浏览器不持密钥；标识最小留存且访问有审计，钉钉/飞书按阈值报警。
2. **V1**：API 失败率大盘、白屏检测（根节点空 + 骨架超时）、SourceMap 解码流水线。
3. **V2**：性能预算门禁（CI）、发布对照（跨版本对比）、会话回放（慎用，隐私评审）。
4. **长期**：用正式 SLI/SLO 驱动排期。例如：28 天滚动窗口内，核心路由导航请求中，在目标时限内达到可用态且期间未出现白屏的请求数 / 全部有效核心路由导航请求数 ≥ 99.9%。目标时限应按该产品、设备和网络分层的真实基线校准；「3 秒」只能作为某产品的示例目标，不是普适常数。分母包含导航后立即退出或中途退出的用户请求，未达可用态即计失败，避免过滤退出用户造成幸存者偏差；仅排除机器人、内部压测和已公告维护窗口，并设置最小样本量。再与后端 TraceId 打通。
:::

**追问链：**
1. 如何区分「脚本错误」和「业务可预期失败」？
2. 小程序监控和 H5 字段怎么统一？
3. 报警风暴你怎么降噪？

::: details 追问参考答案

**1. 如何区分「脚本错误」和「业务可预期失败」？**

建立版本化事件 Schema：未捕获异常、资源失败归稳定性错误；库存不足、无权限等由业务显式上报结果码，不能用异常栈冒充故障。请求层关联 route、release、tenant 和 TraceId，服务端结果仍是事实源；采集载荷最小化并在网关脱敏。未知码单独观测，Schema 解析失败降级为低优先事件；监控 Owner 与业务 Owner 分别维护分类和结果 SLI。

**2. 小程序监控和 H5 字段怎么统一？**

统一事件名、时间、应用、版本、路由、租户、会话、结果和 TraceId 的核心 Schema，各端适配器补容器、基础库、网络等维度。网关校验版本、限流并最小化字段；由认证会话在服务端生成 HMAC 假名化关联标识，它不是匿名化或加密，仍按个人数据治理。密钥按租户、应用和用途分域并轮换，端上不持密钥。端 Owner 维护映射、访问审计与兼容测试。

**3. 报警风暴你怎么降噪？**

入口按租户和应用配额、指纹聚合与动态采样，告警按影响用户数、错误率和多窗口 SLI 触发，并用 release、route、依赖故障合并事件；相同根因只开一个事故。队列积压时丢低价值性能事件，保核心失败计数，SDK 熔断不阻塞业务。告警规则版本化并可回滚，平台 Owner 看有效率与漏报，业务 on-call 负责影响判断和关闭复盘。

:::

**踩坑：** 只接 SDK 不看大盘；上报 PII；在 render 里同步疯狂 `report`。

### Q3. 设计一套前端组件库（面向中后台 + 少量 H5）

**考察点：** 原子/业务分层、Token、文档与发布、破坏性变更

::: details 参考答案
#### 目标

沉淀**可复用、可主题化、可版本化**的 UI 能力：基础组件（Button/Modal）少造轮子，重点做**业务组件**（ProTable、SchemaForm、OrgPicker）与设计令牌，让多项目观感与交互一致。

#### 约束

- 主力 Vue 3；不轻易同时维护 React 版，除非有强需求。
- 基于 Ant Design Vue / Vant 做**增强与约束**，而不是从零画按钮。
- 发布采用 semver；至少提供可发现的使用说明和可验证示例。消费者与交互复杂度上升后再建设文档站或 Playground，不把具体载体当硬性前提。
- 包体积：业务项目按需引入；避免强绑全量图标库。

#### 方案权衡

| 层级 | 职责 | 是否自研 |
| ---- | ---- | -------- |
| 设计 Token | 色板、间距、圆角、字体 | 要，CSS 变量 |
| 基础组件 | 直接用 AntDV/Vant | 原则上不封装「换皮」 |
| 模式组件 | Table+查询、Form 布局 | 薄封装，暴露 slot |
| 业务组件 | 组织树、审批流水线 | 自研，带领域假设 |

仓库策略：`ui`（通用）与 `biz-ui`（绑定领域）拆开，避免通用库被业务字段污染。技术：Vite library mode + TS 声明；Monorepo 下用 workspace 协议本地联调。

API 设计原则：**props 语义稳定、slot 扩展、事件命名一致**；复杂逻辑可用 composable 导出。跨层状态允许受控的 `provide/inject` 或 composable，但要类型化、只读优先、明确 Provider 与生命周期；核心业务状态禁止依赖隐式全局可变单例。

#### 组件供应链与故障边界

- Token 从设计源生成，组件经文档、视觉基线和按影响范围选择的测试后发布。业务数据优先用 props/事件；跨层场景可用类型化、只读优先且生命周期明确的 `provide/inject` 或 composable。
- 富文本、URL 和透传属性按威胁面限制，Playground 与生产凭证隔离；预算关注 JS/CSS 体积、渲染开销、视觉回归量和多版本维护成本。
- 字体和图标失败使用文本/系统字体兜底，基础库可钉旧版。`errorCaptured` 只捕获上报，显式 ErrorBoundary 组件负责错误态和降级 UI。
- semver、兼容矩阵和弃用窗口支持 canary 与撤回；设计和前端共管规范，组件 Owner 负责 SLA。版本覆盖、升级耗时、错误和可访问性缺陷均与接入前基线比较。

#### 演进

1. **MVP**：Token + 3～5 个最高频业务组件 + 文档站 + changelog。
2. **V1**：主题切换、暗色（若需要）、单元测试 / 视觉回归抽样、peerDeps 对齐 Vue/AntDV 大版本。
3. **V2**：RFC 流程做破坏性变更；codemod 辅助升级；按需自动引入优化。
4. **长期**：度量「接入率 / 重复组件数下降」；淘汰长期 0 引用组件。
:::

**追问链：**
1. 「再包一层 a-button」什么时候合理？
2. 多项目不同 AntDV 大版本怎么共存？
3. 组件库和脚手架谁先谁后？

::: details 追问参考答案

**1. 「再包一层 a-button」什么时候合理？**

只有要固化安全或业务语义时才包，例如高风险动作统一权限资源—动作检查、二次确认、幂等键和审计 TraceId；纯改颜色应走 Token。包装层保持 props/事件透传和 semver，服务端仍最终授权与幂等，前端失败可退回原按钮但关闭高风险动作。组件 Owner 观测接入率、错误和体积，先灰度少量页面，破坏变更保留旧版与迁移期。

**2. 多项目不同 AntDV 大版本怎么共存？**

按 Vue/AntDV 主版本建立兼容组，组件库将框架设为 peerDependencies，应用锁定经验证组合；同页微前端无法共享时各自加载并用样式命名空间隔离，容量预算接受重复体积，不能冒险强制单例。公共 DTO 和 Token 协议独立版本化，运行异常隔离到子应用。平台 Owner 维护兼容矩阵、重复字节和回归指标，逐租户灰度升级，可回滚到旧组。

**3. 组件库和脚手架谁先谁后？**

先从真实项目提炼最小 Token、请求和三五个高频组件，再让薄脚手架固定 lint、构建、权限接入和发布门禁；两者都不是一次性大平台。模板只钉兼容范围，不复制业务状态，初始化数据流仍经受信 API。组件或脚手架发布失败可锁旧版继续交付。平台 Owner 看生成项目升级率、包体与缺陷，版本化发布并提供 codemod 和回滚说明。

:::

**踩坑：** 一上来造完整 Atomic Design；业务字段写进通用 Button；无文档靠口口相传。

### Q4. 设计低代码 / 配置化表单方案

**考察点：** Schema 驱动、扩展点、复杂联动、与手写 Form 分界

::: details 参考答案
#### 目标

让运营 / 后端配置或前端用自定义 Schema（可映射 JSON Schema）快速生成中后台表单：校验、布局、联动、异步选项。若目标业务经样本统计约 80% 为标准 CRUD，可将其作为阶段覆盖假设；复杂交互保留**逃生舱**手写，不能把 80/20 当通用定律。

#### 约束

- 字段类型有限且可扩展（input/select/date/upload/自定义）。
- 要对接后端校验规则或至少同源（避免前后规则漂移）。
- 性能：百级字段要能分组 / 懒渲染，不能一次挂载 200 个重组件。
- 权限：字段级可见 / 可编；值不能只靠前端藏。

#### 方案权衡

| 方案 | 适用 | 风险 |
| ---- | ---- | ---- |
| 纯 JSON Schema + 渲染器 | 配置平台、多租户差异大 | 联动 DSL 容易变成新语言 |
| 代码 Schema（TS 对象） | 前端主导、要类型提示 | 「低代码」纯度下降，但可维护 |
| 拖拽搭建器 | 非研发配页面 | 工程与权限、版本治理重 |

推荐：**TS/JSON Schema 渲染器 + 自定义组件注册表**；拖拽搭建另立项目，不要和渲染器绑死。

核心模型：

```ts
type Field = {
  name: string
  label: string
  type: string // 自定义字段类型，可通过适配器映射 JSON Schema
  props?: Record<string, unknown>
  rules?: unknown[]
  visibleOn?: string // 或函数注册名
  effect?: { watch: string[]; run: string }
}
```

联动用「声明式 visible/disabled + 少量注册函数」，禁止在 Schema 里塞任意 JS 字符串 eval。上传、富文本等重字段异步加载组件定义。

#### 配置生命周期与数据安全

- 草稿经 Schema 校验、审批后生成不可变版本；渲染器拉取配置，前端做体验校验，服务端做权威校验并持久化。字段、联动、版本和峰值提交量决定分步加载与归档策略。
- 组件注册白名单、受限表达式、上传鉴权和富文本净化形成信任边界；字段可见不代表可写。选项接口失败可重试/只读，未知类型拒绝发布，渲染异常回退上一稳定配置。
- 配置灰度、版本和审计支持回滚，但回滚前检查已提交数据兼容性，必要时迁移。监控渲染失败、提交成功、字段耗时和逃生率。
- 平台 Owner 负责 Schema/渲染器，业务 Owner 负责规则、数据合规与审批；安全 Owner 只介入高风险组件，不机械参与全部配置。

#### 演进

1. **MVP**：布局 + 基础类型 + 校验 + 回填/提交适配器。
2. **V1**：联动、异步 options、字段权限、分组/步骤条。
3. **V2**：与流程引擎/审批单结合；Schema 版本化与迁移脚本。
4. **长期**：可视化编辑器；监控「渲染器兜底率」（多少页被迫手写）反哺组件扩展。
:::

**追问链：**
1. 循环依赖联动（A 变 B、B 变 A）怎么防？
2. 后端下发 Schema 被篡改的风险？
3. 和 Ant Design Vue Form 的 `name path` 怎么对齐？

::: details 追问参考答案

**1. 循环依赖联动（A 变 B、B 变 A）怎么防？**

发布前把字段联动编译为有向图并拒绝无明确收敛规则的环；运行时按事务批次计算拓扑增量，携带 revision 和来源字段，同一 revision 不重复触发，异步结果只接收最新版本。达到步数上限立即停止联动并保留可编辑原值，不能提交半计算状态。平台 Owner 观测环检测、超限和耗时，规则版本灰度，异常配置回退上一稳定版。

**2. 后端下发 Schema 被篡改的风险？**

Schema 由发布端私钥做非对称签名，前端内置或安全更新公钥信任根，按 `keyId` 轮换；签名覆盖规范化 Schema、租户、版本和内容摘要，必须在解析前验签，不能与共享密钥 HMAC 混用。验签、摘要或租户不匹配即拒绝渲染并回退安全版本；服务端仍做权威校验。安全 Owner 管密钥、拒绝率与轮换演练。

**3. 和 Ant Design Vue Form 的 `name path` 怎么对齐？**

定义唯一规范路径为字符串段与数字段数组，Schema、初值、错误和提交适配器都使用它；禁止点号字符串承载可含点的业务键。渲染层把路径直接传给 Form.Item，提交时按版本化映射生成 DTO，服务端再做权威校验。数组增删使用稳定业务 ID，索引只表达位置；映射失败保留草稿并阻止提交。表单 Owner 观测校验错位，迁移双读后回滚。

:::

**踩坑：** Schema 里 `eval`；无逃生舱导致极端页硬拧配置；校验只做前端。

### Q5. 设计中后台权限体系（前端视角的端到端）

**考察点：** RBAC、菜单/路由/按钮/数据权、前后端分工、多租户

::: details 参考答案
#### 目标

保证**越权不可达**：无权限用户看不见入口、进不了路由、打不出成功写操作；审计可追踪。前端是体验与防御纵深，**权威在后端**。

#### 约束

- 模型以 RBAC 为主，必要时加基于资源实例和上下文的策略。
- 统一「资源类型—动作」词汇，并分别映射为前端能力项与服务端策略；UI 能力标识和 API 授权策略不能共用一个码冒充同一判断。
- 超管、多角色并集、权限变更后要能生效（重新拉码或短 TTL）。
- 多租户时角色空间隔离。

#### 方案权衡

| 控制面 | 前端做什么 | 后端做什么 |
| ------ | ---------- | ---------- |
| 菜单 | 消费能力快照过滤树 | 下发主体在当前租户下的导航能力 |
| 路由 | `addRoute` + 守卫 403 | 直接刷 URL 仍执行权威授权 |
| 按钮 | 按资源—动作映射判断能力 | 按主体、资源实例、租户、动作与上下文执行策略 |
| 数据 | 默认筛选项、字段脱敏展示 | 数据范围判定、字段裁剪并记录决策日志 |

实现要点：登录后拉带 `tenantId/subjectId/policyVersion/expiresAt` 的**能力快照**和菜单树，生成路由并存 Store；组件按统一资源—动作词汇映射能力，禁止散落 `if (role === 'admin')`。服务端对每次敏感请求基于主体、资源实例、租户、动作、上下文和策略版本权威授权，记录允许/拒绝、命中策略与 TraceId 的决策日志。

数据权限：列表请求不带「我要看全公司」的前端开关作权威；最多提供 UI，以服务端为准。

#### 身份到授权决策链

- IdP 签发令牌/断言，应用验证后建立会话；服务端从已验证凭证派生主体并校验租户成员关系，绝不信任客户端自报主体、租户或角色，再生成能力快照和执行资源实例策略。
- 判定容量由主体、资源实例、策略和 QPS 决定；短 TTL 快照与服务端缓存键都包含主体、租户、资源、动作和策略版本。策略不可用时，高风险动作 fail-close。
- 身份故障可按风险延续已建立的短会话但禁止新登录；策略版本化、双人审批、租户灰度和上一版本回滚，词汇映射先保持双版本兼容。
- 身份、策略和业务资源各有 Owner；判定延迟、拒绝率、缓存命中和决策日志关联策略发布，业务服务 Owner 对最终授权与审计负责。

#### 演进

1. **MVP**：统一资源—动作词汇、角色映射、能力快照、菜单与路由守卫、服务端决策日志。
2. **V1**：数据范围、字段级、权限变更强制重登或热更新码表。
3. **V2**：资源—动作词汇与策略治理平台（申请/审批/过期）；自动化测试「越权用例」。
4. **长期**：ABAC / 策略引擎对接；与审计日志、脱敏规范一体。
:::

**追问链：**
1. 资源—动作词汇和各端能力映射怎么定才利于演进？
2. 微前端下子应用权限如何下发？
3. 前端路由懒加载组件被打包进 chunk，算不算泄露？

::: details 追问参考答案

**1. 资源—动作词汇和各端能力映射怎么定才利于演进？**

权限中心登记稳定的资源类型、层级与动作语义，各端能力码和服务端策略分别映射，禁止一个 UI 码冒充 API 授权。词汇只新增或弃用，语义变化发新版本；请求携带受信主体与租户，服务端按资源实例最终判定并记录 TraceId。发布走审批、租户灰度和双版本兼容，失败回退上一策略。权限 Owner 观测判定延迟、拒绝异常和映射覆盖。

**2. 微前端下子应用权限如何下发？**

壳从认证会话拉取含 tenantId、subjectId、policyVersion 和过期时间的能力快照，经版本化只读上下文传给验签通过的子应用；子应用不得读取壳 Store，也不能切租户沿用旧快照。快照失效或通信失败时关闭高风险入口，页面请求仍由服务端按资源实例最终授权。权限 Owner 管快照 SLI，平台 Owner 管协议，策略按租户灰度并可撤回。

**3. 前端路由懒加载组件被打包进 chunk，算不算泄露？**

算代码与静态文案可被下载分析，不能算数据权限突破；敏感密钥、个人数据和仅授权可见的数据都不得打进 chunk。可按高敏业务拆独立入口并由 CDN 做会话门禁，但服务端仍对每次请求按租户、资源和动作最终授权。资源拒绝或加载失败展示 403/降级页。安全 Owner 扫描产物与 SourceMap，发布按版本灰度，泄露时撤回产物并轮换凭据。

:::

**踩坑：** 只藏按钮；权限存在 localStorage 可篡改就信；刷新丢动态路由。

### Q6. 跨端项目治理（H5 / uni-app / 小程序 / 管理端）

**考察点：** 代码复用边界、发版矩阵、设计一致性、质量门禁

::: details 参考答案
#### 目标

在多端并存时，让团队有**清晰的复用与差异规则**：业务节奏可预期，不因一端需求拖死另一端；共享逻辑可测，UI 差异可解释。

#### 约束

- 端：Vue 3 管理端、Vant H5、uni-app 小程序可能同时在。
- 人力有限，不能每端一支完整团队。
- 小程序有包体积与审核；H5 有弱网与 WebView 差异。
- 设计资源未必每端一稿，需要 Token 级对齐而不是像素级抄。

#### 方案权衡

| 复用层 | 放什么 | 不放什么 |
| ------ | ------ | -------- |
| `shared-utils` / 领域 model | 校验、金额、日期、API DTO 类型 | 带 DOM 假设的工具 |
| `shared-api` | 请求封装差异用 adapter | 写死平台 URL 拼接脏逻辑 |
| UI | 各端组件库 | 强行一套组件打全端 |
| 页面 | 极少「一字不改」 | 复杂交互页 |

策略：

1. **合约优先**：同一业务后端 API 尽量统一；端上差异用 BFF 或 adapter。
2. **条件编译谨慎**：uni-app `#ifdef` 控制在基础设施，业务满屏 ifdef 宣布失败。
3. **发版矩阵**：表格列出端 × 版本 × 强制更新策略；阻断问题按端热修。
4. **质量**：公共包单测；端上 E2E 只覆盖主路径；包体积预算进 CI。

组织上：指定「平台 Owner」审共享包变更；业务需求先标影响端，再估期。

#### 多端能力与发布矩阵

- 共享领域请求经端适配器进入 API，响应映射统一模型；导航、存储和 UI 生命周期按端实现。维护端 × 容器版本 × API 能力矩阵，核算审核、设备覆盖和长尾支持成本。
- 凭证存储、Bridge 白名单、深链和小程序域名按端建模，服务端仍权威授权。Bridge 缺失回退 Web 能力，其他能力用 feature detection。
- H5 可切旧资源，小程序预置配置降级，App 长尾依赖服务端兼容；共享 API 按主路径分级降级，不可逆数据用补偿而非假回滚。
- 平台 Owner 负责共享协议，各端 Owner 负责发布、兼容和 on-call，业务 Owner 负责结果一致性；统一事件词汇并保留端、容器、版本与设备维度。

#### 演进

1. **MVP**：抽 `shared` 包 + 文档「何时能复用」；统一错误码与登录态刷新策略。
2. **V1**：设计 Token 多端映射；API adapter 标准化；发版检查清单。
3. **V2**：跨端埋点字段字典；组件级复用度量；废弃一套老 H5。
4. **长期**：评估是否收敛端数量（能 H5 就不硬上小程序等）。
:::

**追问链：**
1. 管理端和 C 端 H5 的设计系统要不要强行统一？
2. 小程序独立分包和 uni 主包怎么划？
3. 共享包 breaking change 怎么通知各端？

::: details 追问参考答案

**1. 管理端和 C 端 H5 的设计系统要不要强行统一？**

统一品牌语义 Token、无障碍底线和状态词汇，不统一组件尺寸与交互密度；管理端偏信息效率，H5 按触控、弱网和安全区实现各自组件。Token 从版本化设计源编译，各端映射并做视觉契约，租户品牌缓存键隔离。映射失败回退安全默认主题。设计系统 Owner 看一致性缺陷、包体和任务成功率，分端灰度，异常只回滚对应端版本。

**2. 小程序独立分包和 uni 主包怎么划？**

主包只放启动、登录、首页骨架和高频共享基础设施，普通分包按业务路径与访问概率拆；独立分包仅用于确需脱离主包运行、依赖可自足的低耦合场景，避免复制身份逻辑。CI 统计主包、分包及重复依赖，路由数据携带版本和租户上下文，服务端仍最终授权。加载失败回退轻量页；端 Owner 观测首开、二跳和失败率，分阶段发布并可撤回入口。

**3. 共享包 breaking change 怎么通知各端？**

共享包用 semver、变更清单和端 × 容器 × API 兼容矩阵，破坏变更先 RFC，再提供适配层、codemod 和双版本窗口；CI 对各端跑契约测试，未声明兼容不得发布。共享数据模型新增字段向后兼容，写操作保幂等协议。某端升级失败可继续钉旧版，服务端兼容长尾。平台 Owner 跟踪版本覆盖、升级失败和截止时间，各端 Owner 签收并负责回滚。

:::

**踩坑：** 盲目 all-in 跨端框架；共享包变成大泥球；一端紧急需求直接改 shared 破坏另一端。

### Q7. 设计「配置化列表页」框架（查询 + 表格 + 操作）

**考察点：** Schema 列表、列定义、请求协议、扩展槽、性能

::: details 参考答案
#### 目标

用一份配置生成中后台标准列表：**查询区 + 工具栏 + 表格 + 分页 + 行操作 + 导出**，让新 CRUD 列表以小时计而非天计；复杂列表可局部定制而不 fork 整页。

#### 约束

- 协议对齐后端：分页 `{ list, total }`、排序字段白名单、查询参数命名一致。
- 列要支持：格式化、枚举字典、权限控制、固定列、溢出省略。
- 大数据：虚拟滚动或「只做服务端分页」，别假装一次拉 10 万行。
- 可测试：请求函数可注入，不写死在组件内部。

#### 方案权衡

| 方案 | 优点 | 代价 |
| ---- | ---- | ---- |
| 配置 JSON + 通用 ProTable | 快 | 复杂单元格表达力差 |
| 配置 + slot 具名逃生 | 平衡 | 要规范 slot 命名 |
| 纯手写 Table | 最灵活 | 重复劳动、风格漂移 |

推荐 **ProTable：`columns + searchFields + actions + request`**，单元格用 `customRender` / slot；禁止在配置里塞 React/Vue 组件的字符串名以外的任意代码。

关键设计：

1. **request(params)** 统一把查询表单、分页、排序编成 API 参数；返回标准结构。
2. **columns** 声明 `dataIndex/title/valueType/permission`；`valueType` 映射到金额、日期、字典。
3. **actions**：工具栏与行操作带 `permission` 与 `confirm`。
4. **状态**：URL query 同步（可分享筛选）；重置与默认值清晰。
5. **性能**：列过多时按需展示列设置；远程字典缓存。

#### 查询、批量操作与导出闭环

- URL/查询表单经白名单和类型转换后进入服务端分页、筛选和排序；批量操作传资源 ID 与幂等键。按行列规模、并发查询和字典基数估算，大导出改异步任务与短期下载链接。
- 服务端限制筛选/排序字段并逐资源授权，导出防公式注入且审计；前端隐藏列不是脱敏。列表失败保留筛选和旧数据，字典失败显示原值，导出任务状态可查询且服务端保障幂等。
- Schema/DTO 保持版本兼容，列配置灰度；回滚前确认用户设置能被旧版读取或安全丢弃。查询 P95、超时、导出排队和操作成功率关联租户、版本与 TraceId。
- 平台 Owner 负责 ProTable 与协议，业务 Owner 负责字段、授权和导出合规，后端 Owner 负责容量、异步任务与幂等。

#### 演进

1. **MVP**：查询 + 表格 + 分页 + 行操作权限。
2. **V1**：导出、批量选择、列设置持久化、URL 同步；批量导出与行操作由服务端逐资源授权，写操作使用幂等键并记录操作者、条件、结果和 TraceId 审计。
3. **V2**：可编辑单元格、主子表、与配置化表单详情联动。
4. **长期**：列表 Schema 可由低代码平台生成；监控「自定义 slot 占比」防止框架空心化。
:::

**追问链：**
1. 筛选条件与 URL 同步时，类型与数组字段怎么序列化？
2. 后端字段变更如何减少前端列配置灾难？
3. 虚拟列表和合并单元格冲突怎么办？

::: details 追问参考答案

**1. 筛选条件与 URL 同步时，类型与数组字段怎么序列化？**

定义版本化 Query Schema：日期转 ISO，布尔和数字显式解析，数组用重复键并保持排序，空数组与未传分开；解析、序列化必须可逆且限制字段与长度。URL 水合生成规范查询快照，只接收最新请求结果，服务端仍校验租户、字段和权限。非法值丢弃后用 `replaceState` 写回规范且脱敏的 URL，诊断只留错误类型与字段名，绝不保留原敏感值；列表 Owner 监控失败率。

**2. 后端字段变更如何减少前端列配置灾难？**

以版本化 DTO/OpenAPI 为契约，字段新增保持可选，重命名先双写双读并给弃用期；列 Schema 引用稳定字段 ID，而非展示名，CI 做生成类型、契约和历史配置回放。服务端按资源与租户裁剪字段，前端不能靠隐藏列授权。未知字段降级为不展示并告警，旧配置继续可读。前后端 Owner 共管变更窗口，观测解析错误后灰度、停止或回滚。

**3. 虚拟列表和合并单元格冲突怎么办？**

虚拟化依赖可预测行高，跨窗口合并会破坏偏移计算；先确认规模与交互，常见做法是服务端分页加普通表格，或把合并语义改为分组标题，不能同时承诺任意合并和高性能虚拟滚动。数据按稳定 ID 外置，窗口卸载不丢选择状态。测量失败回退分页视图并保持可访问性。组件 Owner 观测帧率、内存和错位，按功能开关灰度回滚。

:::

**踩坑：** 配置吞掉所有定制导致业务 copy 一份 ProTable 魔改；请求层把分页参数写死三种风格。

### D1. 设计一个面向多团队的微前端平台

**考察点：** 独立交付、接入协议、运行时治理、故障隔离

::: details 参考答案
#### 基础结论

Q1 设计单一中后台壳与模块边界；本题新增「多技术栈、多团队独立发布、跨应用故障隔离」约束。目标不是「把页面切碎」，而是让 5～10 个业务团队在统一体验下独立开发、灰度、发布和回滚；若自治收益未被证实，仍优先模块化单体。

#### 原理深挖

平台分控制面与运行面：控制面管理应用注册、版本、权限、灰度和兼容矩阵；运行面负责路由匹配、资源加载、生命周期、上下文注入与隔离。壳只提供版本化协议，不暴露内部 Store。

#### 工程场景

- **约束：** Vue/React 并存，主导航一致，壳首屏 P75 ≤ 2.5 s，单个子应用故障不能白屏全站。
- **方案：** 受信发布服务为子应用清单签名，清单包含入口、版本、资源摘要和 `keyId`；壳以内置/安全更新的信任根验签。签发密钥轮换时保留短期双验窗口，验签或摘要失败即拒绝加载、展示降级 UI 并告警；通过后再稳定分桶灰度，公共依赖按兼容组共享。
- **指标：** 接入时长、独立发布率、壳启动开销、跨应用事故数和回滚 MTTR。
- **演进：** 先接入两个发布冲突最严重的业务，验证协议后再平台化；运行时沙箱等原理细节参见 [微前端](/interview/questions/12-microfrontend)。

#### 反例 / 踩坑

按菜单数量拆应用；让子应用自行签名而没有受信签发方；清单不含资源摘要或密钥轮换策略；验签失败仍继续加载；强制所有依赖单例；跨应用直接读全局变量；壳升级要求全部子应用同步发布。

#### 资深回答模板

「规模是 8 个团队、日活 50 万；数据流从控制面清单到壳加载和子应用 API；对比模块化单体、构建时集成和运行时微前端；故障验证清单服务、资源加载和子应用异常；证据看发布等待、壳开销、隔离率和 MTTR；反思拆分是否匹配真实组织边界。」
:::

**追问链：**
1. 子应用间通信和跳转如何设计？
2. 公共组件库多版本怎样处理？
3. 控制面故障时已上线应用能否继续运行？

::: details 追问参考答案

**1. 子应用间通信和跳转如何设计？**

跨应用用能力通道或专属 `MessagePort` 交换版本化命令，建连绑定应用身份、主体与租户并限制命令白名单；但白名单不代替授权，每个特权命令都按当前主体、租户、资源和策略版本重新判定。能力短期过期，主体、租户或授权 epoch 变化立即撤销；命令带 correlationId 与幂等键。平台 Owner 观测越权、撤销延迟和重放，失败时关闭特权通道。

**2. 公共组件库多版本怎样处理？**

控制面按 Vue、组件库主版本和 Token 协议声明兼容组，同组可共享满足 semver 范围的实例，不同组隔离加载；不能为省体积强制单例。清单含依赖版本和资源摘要，壳验签后装载。只有可捕获的加载、生命周期和渲染错误能降级对应子应用；死循环、内存挤占及全局副作用在同线程无法隔离，强边界需跨源 iframe 或独立进程。平台 Owner 观测资源预算并灰度回滚。

**3. 控制面故障时已上线应用能否继续运行？**

可以短时使用签名的最后已知好清单，但 LKG 无法自行得知故障后发生的紧急撤销。撤销必须走独立 HA 通道签名分发，壳按环境、租户、版本和 `keyId` 验证，并给清单与撤销状态设置最大陈旧时间；控制面故障时禁止新灰度，超过新鲜度上限就关闭高风险入口。平台 Owner 观测撤销传播 P99、陈旧度与命中率，恢复后对账并演练 fail-close。

:::

### D2. 设计一个统一权限中心，服务多个前端应用

**考察点：** RBAC/ABAC、策略分发、审计、多租户

::: details 参考答案
#### 基础结论

Q5 设计单个中后台的权限接入；本题新增「20 个应用、多租户、集中策略发布」约束。权限中心统一资源—动作词汇及其映射、主体上下文、策略版本与审计；前端只消费能力快照改善体验，服务端按资源实例执行权威授权。

#### 原理深挖

核心模型包含用户/服务主体、租户、角色、资源层级、动作和条件。管理面负责申请、审批、发布、回滚；数据面提供低延迟判定与版本化快照。简单场景以 RBAC 为主，数据范围和上下文条件再引入 ABAC。

#### 工程场景

- **约束：** 20 个应用、1000 个权限点，多租户隔离，策略变更 5 分钟内生效，高风险写操作不可默认放行。
- **方案：** 资源—动作词汇注册表防语义漂移，并分别映射前端能力与服务端策略；策略发布带版本和审计；前端 SDK 读取短 TTL 能力快照；网关/服务端基于主体、资源实例、租户、动作、上下文和策略版本判定。
- **故障：** 中心不可用时读取最后已知好版本，低风险只读可短时延续，高风险写入默认拒绝。
- **演进：** 先统一权限词汇和审计，再迁移菜单、按钮与 API；最后补权限申请和自动越权测试。

#### 反例 / 踩坑

应用各自硬编码角色；UI 标识与 API 策略共用一个码；权限全量永久缓存；跨租户切换复用旧快照；服务端不记录允许/拒绝、命中策略与 TraceId；策略发布无灰度和回滚。

#### 资深回答模板

「规模是 20 个应用、1000 个资源—动作项；数据流从身份到能力快照、服务端决策和日志；对比分散 RBAC、集中 RBAC 与条件策略；故障验证租户串权、策略超时和旧版本；证据看判定 P95、拒绝异常率、策略生效与审计完整率；反思集中化边界。」
:::

**追问链：**
1. 资源数量达到百万级如何建模？
2. 权限中心如何避免成为所有发布的瓶颈？
3. 临时权限和到期回收如何设计？

::: details 追问参考答案

**1. 资源数量达到百万级如何建模？**

不为每个实例预生成权限点；词汇层登记资源类型—动作，角色授予范围规则，服务端结合主体、租户、资源实例与单调授权 epoch 判定。缓存键含租户、主体或权限组、资源、动作与 epoch，并使用短 TTL；变更通过可靠、可重放事件传播，消费者持久化 offset，周期全量对账修复遗漏，不承诺绝对精确失效。新鲜度超 SLO 时高风险 fail-close，权限 Owner 监控传播 P99 与落后量。

**2. 权限中心如何避免成为所有发布的瓶颈？**

把稳定词汇注册与应用发布解耦：已登记资源—动作可由团队自助引用，新增语义才走评审；前端能力映射和服务端策略分别版本化，CI 做静态与越权契约测试。数据面多区部署并缓存最后好策略，发布面故障不阻断已上线流量。策略按租户灰度、可撤回。权限平台 Owner 管词汇和 SLO，业务服务 Owner 对最终授权、审计及发布负责。

**3. 临时权限和到期回收如何设计？**

临时授权包含租户、主体、资源范围、动作、起止时间与审批证据，服务端按可信时钟和单调递增授权 epoch 最终判定。能力快照使用短 TTL；撤销经可靠、有序且可重放的事件流传播，消费者持久化 offset，并由周期全量对账修复漏事件。超过新鲜度 SLO 时高风险动作 fail-close。权限 Owner 监控撤销传播 P99、epoch 落后量与对账差异，支持紧急吊销。

:::

### D3. 设计一个可运营的前端监控平台

**考察点：** 数据管道、聚合、告警、成本与隐私

::: details 参考答案
#### 基础结论

Q2 解决应用侧采集、指标和告警的基础闭环；本题新增「日活 500 万、峰值事件流、平台多租户运营」约束，重点是数据管道、成本与平台 SLO。验收指标包括 MTTD、MTTR、告警有效率、SourceMap 解析率和单事件成本。

#### 原理深挖

系统由采集 SDK、上报网关、消息队列、清洗聚合、事件存储、符号化服务、查询告警和发布中心组成。原始事件高基数且昂贵，应在入口做限流、采样、脱敏和指纹聚合。

#### 工程场景

- **规模：** 日活 500 万，峰值 5 万事件/s，错误保留 30 天，聚合指标保留 1 年。
- **方案：** 错误高采样、性能分层采样；`app/version/route/fingerprint` 聚合；SourceMap 私有上传并按版本匹配；告警使用多窗口阈值关联发布。
- **故障：** 上报端过载时服务端丢弃低优先级性能事件，SDK 有熔断，绝不阻塞主线程和业务请求。
- **演进：** 从错误与版本归因开始，再建设性能、Trace 关联和会话回放；回放需单独隐私评审。

#### 反例 / 踩坑

所有事件全量永久保存；日志中包含 Token 和输入内容；报警按单条错误触发；监控网关故障反向拖垮页面；接入后无人值班。

#### 资深回答模板

「规模是日活 500 万、峰值 5 万事件/s；数据流经 SDK、网关、队列、聚合和告警；对比 SaaS、自建与混合方案；故障验证配额耗尽、队列积压和存储降级；证据看有明确分母与窗口的接收 SLI、告警有效率、MTTR 和单事件成本；反思采样偏差与隐私边界。」
:::

**追问链：**
1. 错误指纹如何避免聚合过度？
2. SourceMap 泄露风险如何控制？
3. 如何证明监控平台的投入产出？

::: details 追问参考答案

**1. 错误指纹如何避免聚合过度？**

指纹由规范化异常类型、顶层业务栈、资源版本和路由模板组成，去掉输入与随机 ID。影响人数使用服务端生成的 HMAC 假名标识；它是假名化而非匿名化，密钥按租户、应用和用途分域，带 `keyId`、TTL 与访问审计。HLL 只能合并同一兼容密钥窗口，跨不兼容轮换须分段展示或明确估算误差。监控 Owner 观测簇纯度、基数与轮换偏差。

**2. SourceMap 泄露风险如何控制？**

SourceMap 由 CI 按 release 私有上传到符号化服务，不随静态资源公开部署；访问走最小权限、短时凭证和审计，上传前扫描源码、Token 与环境配置。事件只传栈、release 和摘要，服务端匹配版本并输出脱敏结果。映射缺失降级展示原栈，不影响业务。安全 Owner 管保留与访问，平台 Owner 看解析率；泄露时撤销访问、删除产物并轮换真实凭据。

**3. 如何证明监控平台的投入产出？**

先记录接入前 MTTD、MTTR、线上失败用户数、发布回滚耗时和人工排障工时，再按应用与租户比较接入后的同口径趋势；体验 SLI 必须有分母、窗口、有效导航定义和维护排除，不能拿事件量当价值。成本计 SDK 开销、事件存储与 on-call。平台过载先保核心 SLI。平台 Owner 每季复盘告警有效率、避免损失和单事件成本，低价值采集下线。

:::

### D4. 设计一个配置化运营活动平台

**考察点：** Schema、发布链路、预览、风控与回滚

::: details 参考答案
#### 基础结论

目标是让运营在 30 分钟内搭建并安全发布常见活动页，同时保留复杂活动的代码扩展能力。平台必须把「搭建」与「安全发布」同等对待。

#### 原理深挖

配置模型包含页面树、组件 Schema、数据源、规则、实验和版本。编辑器、渲染器与发布服务通过版本化协议解耦；组件不是任意代码，而是经过审核的注册表能力。

#### 工程场景

- **约束：** 峰值百万 PV，移动端弱网，运营可预览和定时发布，涉及优惠券与用户分群。
- **方案：** 草稿/审核/发布状态机；预览使用隔离环境和测试身份；配置经双人审批、版本审计和租户灰度后生成不可变版本并推 CDN；动态数据经受控 API 代理；按人群稳定分桶。
- **故障：** 配置解析失败回退上一版本；数据源超时隐藏局部组件；优惠发放仍由服务端校验幂等和资格。
- **演进：** 先覆盖 Banner、列表和表单等高频模块，再加入实验、素材治理和模板市场。

#### 反例 / 踩坑

Schema 中允许 `eval`；运营可直发生产；预览与生产数据源不同；组件升级破坏历史页面；追求 100% 配置化导致 DSL 失控。

#### 资深回答模板

「规模是百万 PV、数百活动版本；数据流从草稿审批到 CDN 配置、动态 API 和提交；对比代码活动页、Schema 渲染和拖拽平台；故障验证坏配置、数据源超时和优惠重复发放；证据看搭建时长、回滚 RTO、任务成功率与违规发布数；反思配置化边界。」
:::

**追问链：**
1. 历史页面如何兼容组件升级？
2. 多人同时编辑怎样处理冲突？
3. 活动被恶意配置成钓鱼页如何防止？

::: details 追问参考答案

**1. 历史页面如何兼容组件升级？**

发布版本冻结页面 Schema 与组件兼容范围，渲染器按清单解析到已验签的组件版本；组件只做向后兼容新增，破坏变更发布新主版本和迁移器，先对历史快照回放。旧运行包按容量与风险保留期限，缺失时回退静态安全页，不能用最新组件强渲染。平台 Owner 观测历史渲染成功率与版本占用，租户灰度迁移，失败回滚页面和组件清单。

**2. 多人同时编辑怎样处理冲突？**

先用草稿 revision 做乐观并发控制：读取返回版本，保存携带 baseRevision 和幂等键；服务端原子比较，冲突返回字段级差异，由用户合并后生成新 revision，不能后写覆盖。需要实时协作再引入 OT/CRDT，不为低并发过度设计。断网保留按用户、租户隔离的本地草稿，恢复先对账。编辑器 Owner 观测冲突和恢复率，协议版本化并可关闭协作模式。

**3. 活动被恶意配置成钓鱼页如何防止？**

配置只允许审核组件、受限文案和白名单数据源，禁止任意 HTML、脚本、外链表单与仿登录组件；发布服务校验租户、域名、品牌和资源摘要，高风险活动双人审批并留审计。凭证与支付动作只能走受信服务端授权，组件不接触 Token。命中规则即拒绝发布，线上可总开关下架并回退安全页。安全 Owner 管规则，业务 Owner 对内容负责，观测投诉和拦截率。

:::

### D5. 设计一套跨端工程体系

**考察点：** 共享边界、适配层、版本矩阵、端侧质量

::: details 参考答案
#### 基础结论

Q6 讨论有限人力下的跨端复用判断和发版治理；本题新增「统一工程控制面、长尾版本与端能力矩阵」约束。体系服务 Web、H5、小程序和混合 App 的一致交付，但只复用领域模型、协议、Token 和无平台假设的逻辑；UI 与生命周期按端实现。

#### 原理深挖

公共内核通过端口访问存储、网络、导航和设备能力，各端提供适配器。发布控制面维护端 × 应用版本 × API 能力矩阵，解决小程序审核和 App WebView 长尾版本问题。

#### 工程场景

- **约束：** 3 个端、2 个业务团队，小程序主包受限，App 容器半年才强更。
- **方案：** Monorepo 放共享领域包和契约测试；端能力用 feature detection；设计 Token 编译为各端变量；API 使用能力协商而非 User-Agent 猜测。
- **指标：** 跨端需求交付周期、共享包变更失败率、各端崩溃/白屏率和版本覆盖。
- **演进：** 先统一登录、错误码和埋点协议，再抽稳定领域逻辑；不以共享代码比例作为成功指标。

#### 反例 / 踩坑

为了复用把所有页面写满条件编译；共享包依赖 DOM；一端热修直接破坏公共契约；假设所有客户端都已升级；设计要求像素级完全一致。

#### 资深回答模板

「规模是 3 个端、多个容器版本；数据流从共享领域模型经端适配器到 API；对比各端独立、共享内核和全量跨端框架；故障验证 Bridge 缺失、审核延迟和长尾兼容；证据看交付周期、端侧任务成功率、版本覆盖和共享变更失败率；反思复用边界。」
:::

**追问链：**
1. 何时应该为某一端分叉实现？
2. 公共包破坏性升级如何发布？
3. App 容器能力缺失时 H5 如何降级？

::: details 追问参考答案

**1. 何时应该为某一端分叉实现？**

当平台生命周期、性能预算、审核规则或交互任务长期不同，适配层出现大量条件分支且端侧故障互相阻塞时分叉；决策依据是交付周期、缺陷和包体数据，不看共享率。领域 DTO、幂等协议、权限与埋点词汇继续共享，UI 独立。缺能力时只降级该端。架构 Owner 记录 ADR 和版本边界，各端 Owner 管发布与 on-call，先灰度一条路径，收益不成立可合回。

**2. 公共包破坏性升级如何发布？**

发布新主版本并保留旧主线，先提供迁移器和端 × 容器兼容矩阵；消费者通过契约测试声明支持范围，Monorepo 也不能原子升级掩盖 App 长尾。共享数据新增向后兼容，写请求沿用幂等键与版本协商。失败端继续锁旧版，服务端维持双协议窗口。平台 Owner 观测覆盖率、失败和截止日，各端 Owner 分批灰度，异常回滚锁文件与产物。

**3. App 容器能力缺失时 H5 如何降级？**

Bridge 握手时由 Native 校验顶层 origin 与页面身份，用 nonce 绑定本次页面会话，再签发短期 capability；每次调用校验会话、方法和参数白名单，携带 requestId、超时且至多结算一次。分享等能力缺失可回退 Web，高风险支付、身份和设备能力还需服务端最终授权与用户确认，失败即关闭。端 Owner 审计拒绝、重放和超时，按容器版本灰度并可撤回 capability。

:::

### D6. 设计一个 BFF / API 聚合层

**考察点：** 聚合边界、缓存、鉴权、可用性

::: details 参考答案
#### 基础结论

BFF 为特定体验聚合和裁剪后端能力，减少前端扇出与协议耦合；它不拥有核心业务规则和权威数据。只有当多个客户端需求明显不同或页面调用链成为瓶颈时才引入。

#### 原理深挖

BFF 负责并行编排、字段整形、协议适配、轻量缓存和客户端友好错误；领域事务、库存判断与权限权威仍在服务端领域服务。身份上下文必须以受信令牌或网关签名传播，BFF 不接受客户端自报的主体与租户；调用下游时保留主体、租户、资源、动作、策略版本和 Trace 上下文。GraphQL、REST 聚合和网关编排要按团队能力与查询复杂度选择。

#### 工程场景

- **约束：** 首页依赖 8 个服务，移动弱网，目标首屏接口 P95 ≤ 800 ms，任一推荐服务故障不能阻断交易入口。
- **方案：** 聚合接口并行调用，设置分依赖超时与总预算；按租户、主体/客户端和路由限流；用隔离舱或独立连接池限制慢下游并发，核心数据失败返回错误，推荐失败返回空模块。
- **授权与缓存：** BFF 先验证身份和租户成员关系，再由下游对资源实例权威授权；缓存键至少包含租户、权限/策略版本、查询条件和数据版本，用户相关结果还要包含主体或可证明等价的权限分组，禁止跨租户命中。
- **高可用：** 多可用区无状态部署，配置与缓存降级不影响核心透传；定义如「5 分钟窗口内合法核心请求成功数 / 合法核心请求总数」的 SLI、目标 SLO、排除项和错误预算。
- **观测与运维：** 传播 W3C Trace Context，记录每个下游耗时、限流、隔离、缓存和降级率；BFF 有生产 Owner、容量评审、发布回滚、Runbook 与 on-call。
- **演进：** 先为一个高价值页面建立薄 BFF，避免变成新的业务单体；重复编排再下沉共享服务。

#### 反例 / 踩坑

把所有接口都代理一遍；信任客户端传来的租户；缓存键缺少租户或策略版本；在 BFF 复制授权与领域规则；串行调用下游；无限并发拖垮连接池；单可用区且没有 SLO/on-call。

#### 资深回答模板

「规模是百万请求/日、首页扇出 8 个服务；数据流携带受信主体、租户和 W3C Trace 上下文；对比客户端聚合、网关编排与 BFF；故障验证慢下游、跨租户缓存、限流和可用区失效；证据看有分母窗口的可用性 SLI、P95、降级率与成本；反思 BFF 是否吸收了领域职责。」
:::

**追问链：**
1. BFF 与 API Gateway 的边界是什么？
2. 聚合返回部分成功时协议如何设计？
3. GraphQL 是否天然优于 REST BFF？

::: details 追问参考答案

**1. BFF 与 API Gateway 的边界是什么？**

Gateway 负责通用入口能力：验证受信身份、路由、TLS、租户/客户端限流和基础观测；BFF 按特定端编排、裁剪与降级，不拥有领域事实。身份、租户和 W3C Trace Context 从网关签名传播，下游按资源实例最终授权。Gateway 故障影响全站需多区 HA，BFF 故障只降级对应体验。两者 Owner 分离，观测 P95、限流和降级率，独立灰度回滚。

**2. 聚合返回部分成功时协议如何设计？**

响应返回版本化 envelope：整体 requestId、数据分区，以及每个模块的 `status/code/data/retryable`；核心交易依赖失败则整体失败，推荐等非核心依赖超时可为空并标 degraded，不能用 HTTP 200 隐藏核心错误。BFF 给下游设置总预算、隔离舱和幂等键，重试只用于安全操作。前端局部渲染并可重试。BFF Owner 观测模块成功率、降级率和 Trace，契约灰度可回滚。

**3. GraphQL 是否天然优于 REST BFF？**

不天然优越。字段组合多变且团队能治理 Schema、复杂度和 N+1 时选 GraphQL；固定聚合则 REST 更简单。两者缓存键都要含租户、主体或可证明的权限等价组、资源范围、授权版本与查询；无法证明结果与用户无关时禁止共享，命中缓存也必须执行当前授权。写操作仍保障幂等。GraphQL 限深度与成本，异常可切持久化查询或 REST；BFF Owner 观测串权与命中率。

:::
