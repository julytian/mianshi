# 前端系统设计

> **怎么用：** 先盖住答案，按 **目标 → 约束 → 方案权衡 → 演进** 自己画一页纸口述 8～12 分钟，再对照参考答案补洞。本模块面向 Lead / 中大厂：要的是取舍与演进，不是组件 API 清单。中英文术语之间请习惯留空格。

口述开场固定三问：**用户是谁、规模多大、哪些绝对不能崩**。没澄清就开画架构，是减分项。

### Q1. 设计一个中后台「管理后台框架」（Vue 3 + 组件库）

**考察点：** 布局与路由壳、权限接入点、模块边界、可替换基建

::: details 参考答案
#### 目标

为多业务线提供统一的**壳应用**：登录会话、布局（侧栏/顶栏）、动态路由与菜单、权限指令、请求层、错误页、主题与水印；业务以「页面模块」插入，而不是复制整仓脚手架。

#### 约束

- 团队以 Vue 3 + Ant Design Vue（或同类）为主；TS 强制。
- 首屏可接受「壳 + 首个业务页」合计可控（内网后台可略宽，但别无脑全量同步路由）。
- 多仓库或 monorepo 都可能；权限以后端为准。
- 要能灰度、要能按业务分包懒加载。

#### 方案权衡

| 方案 | 优点 | 代价 |
| ---- | ---- | ---- |
| A. 单一巨石后台 | 联调简单、权限一套 | 构建慢、发布耦合、权限误伤面大 |
| B. 壳 + 业务子应用（微前端） | 独立发布、技术栈可异构 | 路由/样式/公共依赖治理成本高 |
| C. Monorepo 多 package + 统一壳 | 类型与组件复用好、发布仍可拆 | 工程门槛、CI 复杂度上升 |

推荐默认路径：**先 C 的轻量版**（`app-admin` 壳 + `features/*` 业务包 + 共享 `shared`），真有独立发布与多团队强隔离再上 B。

关键设计点：

1. **路由**：布局路由固定；业务路由由权限接口下发后 `addRoute`；组件用白名单 `import.meta.glob` / `componentMap`。
2. **请求层**：统一 `baseURL`、Token、错误码、取消与幂等键协议；服务端负责幂等记录、冲突判定与结果复用，前端不能单独保证写操作幂等。
3. **扩展点**：菜单图标映射、页面 keep-alive 白名单、全局水印、字典缓存——做成注册表，而不是改壳源码。
4. **质量门禁**：ESLint + 路由 meta 类型 + 资源—动作能力映射静态检查（可选）。

#### 端到端补全

- **API / 数据流：** 登录建立会话 → 拉能力快照、菜单和基础字典 → 生成路由 → 页面查询经统一请求层进入领域 API；服务端状态与 UI 状态分开管理。
- **容量与成本：** 按路由数、并发会话、首屏请求数和业务包体积估算；菜单与字典按租户和版本缓存，避免每个页面重复拉取。
- **安全边界：** 壳只消费能力快照，服务端逐资源实例授权；动态组件只允许签名清单中的映射，禁止后端下发任意模块路径。
- **依赖故障：** 权限接口失败时高风险入口默认关闭；字典失败展示原值或局部空态；单个业务包加载失败不得拖垮壳。
- **发布回滚：** 壳和业务包有兼容矩阵、独立灰度与上一稳定产物；后端契约先扩展后收缩。
- **可观测：** 记录路由可用率、登录恢复率、资源加载失败、版本和 TraceId，并按业务 Owner 路由告警。
- **Owner：** 平台 Owner 负责壳与接入协议，业务 Owner 负责页面与领域 API；共享故障按 Runbook 联合处置。

#### 演进

1. **MVP**：登录 + 布局 + 静态菜单 + 2 个业务页 + 统一请求。
2. **V1**：动态路由 / 按钮权限、字典与用户偏好、错误监控接入。
3. **V2**：按业务分包、可插拔布局、设计令牌主题；只有独立发布冲突、故障隔离和自治收益经数据证实后，才评估微前端，不以团队数量设机械阈值。
4. **长期**：模块联邦或包级版本策略；壳升级与业务升级解耦（peerDeps + 兼容矩阵）。
:::

**追问：**
1. 多 tab 页签（keep-alive + 缓存淘汰）你放在壳还是业务？
2. 微前端的样式隔离与公共 AntDV 多实例怎么处理？
3. 壳发版如何保证旧业务页不炸？

**踩坑：** 业务直接改壳的 layout；或权限只藏菜单不拦路由；一上来全量微前端。

### Q2. 设计前端监控体系（稳定性 + 体验）

**考察点：** 采集分层、采样、隐私、报警闭环、和性能指标挂钩

::: details 参考答案
#### 目标

让线上问题**可发现、可定位、可归因**：JS 错误、资源失败、接口异常、白屏、核心性能（LCP/INP/CLS 或内网自定义）、关键业务漏斗（登录成功率、下单成功率）。

#### 约束

- 包体积与主线程开销有预算；不能拖垮弱网 H5。
- 合规：脱敏、禁止扫本地存储明文、用户标识可哈希。
- 多端：Web 管理端、H5、可能还有小程序（小程序另有平台数据，需对齐字段）。
- 已有或可自建上报网关；报警要对人负责（on-call），不是只堆大盘。

#### 方案权衡

| 层次 | 采什么 | 注意 |
| ---- | ------ | ---- |
| 错误 | `window.onerror` / `unhandledrejection`、框架 errorHandler、资源 `error` | SourceMap 私有化；去重与聚合 |
| 性能 | PerformanceObserver、长任务、路由切换耗时 | 采样率；SPA 软导航要自己打点 |
| 行为 / 业务 | 关键按钮、接口 code、自定义 `metric` | 和产品漏斗对齐命名 |
| 会话 | sessionId、版本号、环境、用户角色（非敏感） | 便于「仅某版本」过滤 |

自建 vs 商业 SaaS：团队小、合规严 → 可自建采集 + 现有日志平台；要快速有洞察 → SaaS + 敏感字段网关剥离。

SDK 形态：薄封装 `report(event, payload)` + 插件（error/perf/api）；错误也受应用级与租户级配额、指纹聚合、入口限流和动态采样控制，高价值新错误优先保留。接口监控优先在请求层统一拦截，比页面手埋稳。

#### 端到端补全

- **API / 数据流：** SDK 批量上报 → 网关鉴权、配额与脱敏 → 队列 → 清洗指纹 → 指标/事件存储 → 查询告警；客户端失败只丢监控，不阻断业务。
- **容量与成本：** 以峰值事件/s、高基数字段和留存天数估算；错误、性能、行为分级采样，租户配额防止单应用挤占。
- **安全边界：** 字段白名单、HMAC 轮换标识、SourceMap 私有访问、最小留存和查询审计；会话回放另行评审。
- **依赖故障：** 网关过载丢低优先级事件；队列积压延迟告警；存储降级保聚合指标；SDK 熔断并限制内存队列。
- **发布回滚：** SDK 按版本灰度且可远程降采样/停插件；服务端 Schema 向后兼容，异常版本可快速回滚。
- **可观测：** 平台自身 SLI 写清分母、窗口和排除项，例如「5 分钟窗口内成功接收的合法批次 / 到达网关的合法批次」，仅排除演练和明确维护窗口。
- **Owner：** SDK、数据管道与告警各有 Owner；业务团队拥有告警规则和 on-call，平台团队不替业务判断影响。

#### 演进

1. **MVP**：错误 + 版本号 + 轮换密钥生成的 HMAC 用户标识；原始身份不落采集端，映射最小留存且访问有审计；钉钉/飞书按阈值报警。
2. **V1**：API 失败率大盘、白屏检测（根节点空 + 骨架超时）、SourceMap 解码流水线。
3. **V2**：性能预算门禁（CI）、发布对照（跨版本对比）、会话回放（慎用，隐私评审）。
4. **长期**：SLO（如「管理端可交互错误率 < x%」）驱动排期；和后端 TraceId 打通。
:::

**追问：**
1. 如何区分「脚本错误」和「业务可预期失败」？
2. 小程序监控和 H5 字段怎么统一？
3. 报警风暴你怎么降噪？

**踩坑：** 只接 SDK 不看大盘；上报 PII；在 render 里同步疯狂 `report`。

### Q3. 设计一套前端组件库（面向中后台 + 少量 H5）

**考察点：** 原子/业务分层、Token、文档与发布、破坏性变更

::: details 参考答案
#### 目标

沉淀**可复用、可主题化、可版本化**的 UI 能力：基础组件（Button/Modal）少造轮子，重点做**业务组件**（ProTable、SchemaForm、OrgPicker）与设计令牌，让多项目观感与交互一致。

#### 约束

- 主力 Vue 3；不轻易同时维护 React 版，除非有强需求。
- 基于 Ant Design Vue / Vant 做**增强与约束**，而不是从零画按钮。
- 发布要 semver；文档站点与 Playground 必须有，否则没人用。
- 包体积：业务项目按需引入；避免强绑全量图标库。

#### 方案权衡

| 层级 | 职责 | 是否自研 |
| ---- | ---- | -------- |
| 设计 Token | 色板、间距、圆角、字体 | 要，CSS 变量 |
| 基础组件 | 直接用 AntDV/Vant | 原则上不封装「换皮」 |
| 模式组件 | Table+查询、Form 布局 | 薄封装，暴露 slot |
| 业务组件 | 组织树、审批流水线 | 自研，带领域假设 |

仓库策略：`ui`（通用）与 `biz-ui`（绑定领域）拆开，避免通用库被业务字段污染。技术：Vite library mode + TS 声明；Monorepo 下用 workspace 协议本地联调。

API 设计原则：**props 语义稳定、slot 扩展、事件命名一致**；复杂逻辑用 composable 导出，而不是只能通过组件黑盒用。

#### 端到端补全

- **API / 数据流：** Token 由设计源生成 → 组件消费 → 文档与视觉基线验证 → 包发布 → 业务锁定版本；业务数据只通过 props/事件，不进入全局单例。
- **容量与成本：** 关注包体积、CSS 体积、组件渲染开销、视觉回归截图量和多版本维护成本；按影响范围选择测试集。
- **安全边界：** 富文本、URL 和透传属性按组件威胁面限制；依赖供应链扫描，文档 Playground 与生产凭证隔离。
- **依赖故障：** 字体/图标资源失败有系统字体与文本兜底；第三方基础库升级失败可钉旧版；单个业务组件异常由局部错误边界隔离。
- **发布回滚：** semver、变更清单、兼容矩阵和弃用窗口；重大版本先 canary 应用，再撤回版本或发布修复版，已发包不覆盖。
- **可观测：** 统计版本覆盖、升级耗时、组件错误、可访问性缺陷和重复实现；效果必须对比接入前基线。
- **Owner：** 设计与前端共同拥有 Token 和交互规范；组件 Owner 负责支持 SLA，业务 Owner 负责场景验收。

#### 演进

1. **MVP**：Token + 3～5 个最高频业务组件 + 文档站 + changelog。
2. **V1**：主题切换、暗色（若需要）、单元测试 / 视觉回归抽样、peerDeps 对齐 Vue/AntDV 大版本。
3. **V2**：RFC 流程做破坏性变更；codemod 辅助升级；按需自动引入优化。
4. **长期**：度量「接入率 / 重复组件数下降」；淘汰长期 0 引用组件。
:::

**追问：**
1. 「再包一层 a-button」什么时候合理？
2. 多项目不同 AntDV 大版本怎么共存？
3. 组件库和脚手架谁先谁后？

**踩坑：** 一上来造完整 Atomic Design；业务字段写进通用 Button；无文档靠口口相传。

### Q4. 设计低代码 / 配置化表单方案

**考察点：** Schema 驱动、扩展点、复杂联动、与手写 Form 分界

::: details 参考答案
#### 目标

让运营 / 后端配置或前端用自定义 Schema（可映射 JSON Schema）快速生成中后台表单：校验、布局、联动、异步选项。若目标业务经样本统计约 80% 为标准 CRUD，可将其作为阶段覆盖假设；复杂交互保留**逃生舱**手写，不能把 80/20 当通用定律。

#### 约束

- 字段类型有限且可扩展（input/select/date/upload/自定义）。
- 要对接后端校验规则或至少同源（避免前后规则漂移）。
- 性能：百级字段要能分组 / 懒渲染，不能一次挂载 200 个重组件。
- 权限：字段级可见 / 可编；值不能只靠前端藏。

#### 方案权衡

| 方案 | 适用 | 风险 |
| ---- | ---- | ---- |
| 纯 JSON Schema + 渲染器 | 配置平台、多租户差异大 | 联动 DSL 容易变成新语言 |
| 代码 Schema（TS 对象） | 前端主导、要类型提示 | 「低代码」纯度下降，但可维护 |
| 拖拽搭建器 | 非研发配页面 | 工程与权限、版本治理重 |

推荐：**TS/JSON Schema 渲染器 + 自定义组件注册表**；拖拽搭建另立项目，不要和渲染器绑死。

核心模型：

```ts
type Field = {
  name: string
  label: string
  type: string // 自定义字段类型，可通过适配器映射 JSON Schema
  props?: Record<string, unknown>
  rules?: unknown[]
  visibleOn?: string // 或函数注册名
  effect?: { watch: string[]; run: string }
}
```

联动用「声明式 visible/disabled + 少量注册函数」，禁止在 Schema 里塞任意 JS 字符串 eval。上传、富文本等重字段异步加载组件定义。

#### 端到端补全

- **API / 数据流：** 配置草稿 → Schema 校验与审批 → 不可变版本发布 → 渲染器拉取 → 用户输入 → 前端体验校验 → 服务端权威校验和持久化。
- **容量与成本：** 以字段数、联动边数、配置版本数和峰值表单提交量估算；大表单分步加载，历史版本分层归档。
- **安全边界：** 组件注册白名单、表达式受限解释器、上传鉴权和富文本净化；字段可见不代表服务端可写。
- **依赖故障：** 选项接口失败允许重试或只读；未知字段类型拒绝发布或显示明确占位；渲染器异常回退上一稳定配置。
- **发布回滚：** 配置必须经过审批、版本、审计和灰度；回滚配置时评估已提交数据是否兼容，必要时执行迁移。
- **可观测：** 记录渲染失败率、提交成功率、字段耗时、自定义逃生率和配置版本，按表单 Owner 告警。
- **Owner：** 平台 Owner 负责 Schema/渲染器，业务 Owner 负责规则、数据合规与发布审批；安全 Owner 审核高风险组件。

#### 演进

1. **MVP**：布局 + 基础类型 + 校验 + 回填/提交适配器。
2. **V1**：联动、异步 options、字段权限、分组/步骤条。
3. **V2**：与流程引擎/审批单结合；Schema 版本化与迁移脚本。
4. **长期**：可视化编辑器；监控「渲染器兜底率」（多少页被迫手写）反哺组件扩展。
:::

**追问：**
1. 循环依赖联动（A 变 B、B 变 A）怎么防？
2. 后端下发 Schema 被篡改的风险？
3. 和 Ant Design Vue Form 的 `name path` 怎么对齐？

**踩坑：** Schema 里 `eval`；无逃生舱导致极端页硬拧配置；校验只做前端。

### Q5. 设计中后台权限体系（前端视角的端到端）

**考察点：** RBAC、菜单/路由/按钮/数据权、前后端分工、多租户

::: details 参考答案
#### 目标

保证**越权不可达**：无权限用户看不见入口、进不了路由、打不出成功写操作；审计可追踪。前端是体验与防御纵深，**权威在后端**。

#### 约束

- 模型以 RBAC 为主，必要时加基于资源实例和上下文的策略。
- 统一「资源类型—动作」词汇，并分别映射为前端能力项与服务端策略；UI 能力标识和 API 授权策略不能共用一个码冒充同一判断。
- 超管、多角色并集、权限变更后要能生效（重新拉码或短 TTL）。
- 多租户时角色空间隔离。

#### 方案权衡

| 控制面 | 前端做什么 | 后端做什么 |
| ------ | ---------- | ---------- |
| 菜单 | 消费能力快照过滤树 | 下发主体在当前租户下的导航能力 |
| 路由 | `addRoute` + 守卫 403 | 直接刷 URL 仍执行权威授权 |
| 按钮 | 按资源—动作映射判断能力 | 按主体、资源实例、租户、动作与上下文执行策略 |
| 数据 | 默认筛选项、字段脱敏展示 | 数据范围判定、字段裁剪并记录决策日志 |

实现要点：登录后拉带 `tenantId/subjectId/policyVersion/expiresAt` 的**能力快照**和菜单树，生成路由并存 Store；组件按统一资源—动作词汇映射能力，禁止散落 `if (role === 'admin')`。服务端对每次敏感请求基于主体、资源实例、租户、动作、上下文和策略版本权威授权，记录允许/拒绝、命中策略与 TraceId 的决策日志。

数据权限：列表请求不带「我要看全公司」的前端开关作权威；最多提供 UI，以服务端为准。

#### 端到端补全

- **API / 数据流：** 身份提供方签发会话 → 权限中心生成带策略版本的能力快照 → 前端映射导航能力 → 请求携带主体与租户上下文 → 服务端策略决策并写日志。
- **容量与成本：** 以主体数、资源实例数、策略数和判定 QPS 估算；能力快照短 TTL，服务端判定缓存键包含主体、租户、资源、动作和策略版本。
- **安全边界：** OIDC/OAuth 流程、租户切换、主体冒用和策略管理面分权；高风险操作在策略服务不可用时默认拒绝。
- **依赖故障：** 身份服务故障禁止新登录但可按风险延续短会话；快照失败隐藏敏感入口；策略判定超时按动作风险 fail-close。
- **发布回滚：** 策略版本化、双人审批、租户灰度和上一版本回滚；词汇映射变更先兼容前后版本。
- **可观测：** 记录判定延迟、拒绝率、缓存命中、策略版本与决策日志；异常拒绝率关联策略发布。
- **Owner：** 身份、策略平台、业务资源各有 Owner；业务服务 Owner 对最终授权和审计完整性负责。

#### 演进

1. **MVP**：统一资源—动作词汇、角色映射、能力快照、菜单与路由守卫、服务端决策日志。
2. **V1**：数据范围、字段级、权限变更强制重登或热更新码表。
3. **V2**：资源—动作词汇与策略治理平台（申请/审批/过期）；自动化测试「越权用例」。
4. **长期**：ABAC / 策略引擎对接；与审计日志、脱敏规范一体。
:::

**追问：**
1. 资源—动作词汇和各端能力映射怎么定才利于演进？
2. 微前端下子应用权限如何下发？
3. 前端路由懒加载组件被打包进 chunk，算不算泄露？

**踩坑：** 只藏按钮；权限存在 localStorage 可篡改就信；刷新丢动态路由。

### Q6. 跨端项目治理（H5 / uni-app / 小程序 / 管理端）

**考察点：** 代码复用边界、发版矩阵、设计一致性、质量门禁

::: details 参考答案
#### 目标

在多端并存时，让团队有**清晰的复用与差异规则**：业务节奏可预期，不因一端需求拖死另一端；共享逻辑可测，UI 差异可解释。

#### 约束

- 端：Vue 3 管理端、Vant H5、uni-app 小程序可能同时在。
- 人力有限，不能每端一支完整团队。
- 小程序有包体积与审核；H5 有弱网与 WebView 差异。
- 设计资源未必每端一稿，需要 Token 级对齐而不是像素级抄。

#### 方案权衡

| 复用层 | 放什么 | 不放什么 |
| ------ | ------ | -------- |
| `shared-utils` / 领域 model | 校验、金额、日期、API DTO 类型 | 带 DOM 假设的工具 |
| `shared-api` | 请求封装差异用 adapter | 写死平台 URL 拼接脏逻辑 |
| UI | 各端组件库 | 强行一套组件打全端 |
| 页面 | 极少「一字不改」 | 复杂交互页 |

策略：

1. **合约优先**：同一业务后端 API 尽量统一；端上差异用 BFF 或 adapter。
2. **条件编译谨慎**：uni-app `#ifdef` 控制在基础设施，业务满屏 ifdef 宣布失败。
3. **发版矩阵**：表格列出端 × 版本 × 强制更新策略；阻断问题按端热修。
4. **质量**：公共包单测；端上 E2E 只覆盖主路径；包体积预算进 CI。

组织上：指定「平台 Owner」审共享包变更；业务需求先标影响端，再估期。

#### 端到端补全

- **API / 数据流：** 共享领域请求经端适配器进入 API；响应映射统一模型，各端独立处理导航、存储与 UI 生命周期。
- **容量与成本：** 维护端 × 版本 × API 能力矩阵，核算包体积、审核周期、设备覆盖和长尾版本支持成本，不以复用率单独优化。
- **安全边界：** 各端凭证存储、WebView Bridge 白名单、深链校验和小程序域名约束分别建模；服务端仍权威授权。
- **依赖故障：** Bridge 不可用回退 Web 能力；端能力缺失做 feature detection；共享 API 故障按主路径和非核心模块分级降级。
- **发布回滚：** H5 可切旧资源，小程序受审核约束需配置降级，App 长尾依赖服务端兼容；不可逆数据采用补偿。
- **可观测：** 统一事件词汇但保留端、容器、版本和设备维度，比较各端任务完成率、崩溃/白屏与 API 成功率。
- **Owner：** 平台 Owner 负责共享协议和适配器规范，各端 Owner 负责发布、设备兼容和 on-call，业务 Owner 负责结果一致性。

#### 演进

1. **MVP**：抽 `shared` 包 + 文档「何时能复用」；统一错误码与登录态刷新策略。
2. **V1**：设计 Token 多端映射；API adapter 标准化；发版检查清单。
3. **V2**：跨端埋点字段字典；组件级复用度量；废弃一套老 H5。
4. **长期**：评估是否收敛端数量（能 H5 就不硬上小程序等）。
:::

**追问：**
1. 管理端和 C 端 H5 的设计系统要不要强行统一？
2. 小程序独立分包和 uni 主包怎么划？
3. 共享包 breaking change 怎么通知各端？

**踩坑：** 盲目 all-in 跨端框架；共享包变成大泥球；一端紧急需求直接改 shared 破坏另一端。

### Q7. 设计「配置化列表页」框架（查询 + 表格 + 操作）

**考察点：** Schema 列表、列定义、请求协议、扩展槽、性能

::: details 参考答案
#### 目标

用一份配置生成中后台标准列表：**查询区 + 工具栏 + 表格 + 分页 + 行操作 + 导出**，让新 CRUD 列表以小时计而非天计；复杂列表可局部定制而不 fork 整页。

#### 约束

- 协议对齐后端：分页 `{ list, total }`、排序字段白名单、查询参数命名一致。
- 列要支持：格式化、枚举字典、权限控制、固定列、溢出省略。
- 大数据：虚拟滚动或「只做服务端分页」，别假装一次拉 10 万行。
- 可测试：请求函数可注入，不写死在组件内部。

#### 方案权衡

| 方案 | 优点 | 代价 |
| ---- | ---- | ---- |
| 配置 JSON + 通用 ProTable | 快 | 复杂单元格表达力差 |
| 配置 + slot 具名逃生 | 平衡 | 要规范 slot 命名 |
| 纯手写 Table | 最灵活 | 重复劳动、风格漂移 |

推荐 **ProTable：`columns + searchFields + actions + request`**，单元格用 `customRender` / slot；禁止在配置里塞 React/Vue 组件的字符串名以外的任意代码。

关键设计：

1. **request(params)** 统一把查询表单、分页、排序编成 API 参数；返回标准结构。
2. **columns** 声明 `dataIndex/title/valueType/permission`；`valueType` 映射到金额、日期、字典。
3. **actions**：工具栏与行操作带 `permission` 与 `confirm`。
4. **状态**：URL query 同步（可分享筛选）；重置与默认值清晰。
5. **性能**：列过多时按需展示列设置；远程字典缓存。

#### 端到端补全

- **API / 数据流：** URL/查询表单 → 参数白名单与类型转换 → 服务端分页、筛选、排序 → 标准列表 DTO → 表格；批量操作传资源 ID 与幂等键。
- **容量与成本：** 以行数、列数、导出规模、并发查询和字典基数估算；大导出改异步任务与对象存储短期链接，不在浏览器拼全量文件。
- **安全边界：** 服务端限制可筛选/排序字段，逐资源授权批量与行操作，导出防公式注入并审计下载；前端列隐藏不是数据脱敏。
- **依赖故障：** 列表 API 失败保留筛选和旧数据；字典失败显示原值；导出任务可查询状态并重试，不能重复创建。
- **发布回滚：** Schema 与 DTO 版本兼容，列配置灰度；回滚前确认用户已保存的列设置可被旧版读取或安全丢弃。
- **可观测：** 记录查询 P95、超时率、空结果异常、导出排队时长和操作成功率，关联用户、租户、版本和 TraceId。
- **Owner：** 平台 Owner 负责 ProTable 与协议，业务 Owner 负责字段语义、授权规则和导出数据合规，后端 Owner 负责容量与幂等。

#### 演进

1. **MVP**：查询 + 表格 + 分页 + 行操作权限。
2. **V1**：导出、批量选择、列设置持久化、URL 同步；批量导出与行操作由服务端逐资源授权，写操作使用幂等键并记录操作者、条件、结果和 TraceId 审计。
3. **V2**：可编辑单元格、主子表、与配置化表单详情联动。
4. **长期**：列表 Schema 可由低代码平台生成；监控「自定义 slot 占比」防止框架空心化。
:::

**追问：**
1. 筛选条件与 URL 同步时，类型与数组字段怎么序列化？
2. 后端字段变更如何减少前端列配置灾难？
3. 虚拟列表和合并单元格冲突怎么办？

**踩坑：** 配置吞掉所有定制导致业务 copy 一份 ProTable 魔改；请求层把分页参数写死三种风格。

### D1. 设计一个面向多团队的微前端平台

**考察点：** 独立交付、接入协议、运行时治理、故障隔离

::: details 参考答案
#### 基础结论

Q1 设计单一中后台壳与模块边界；本题新增「多技术栈、多团队独立发布、跨应用故障隔离」约束。目标不是「把页面切碎」，而是让 5～10 个业务团队在统一体验下独立开发、灰度、发布和回滚；若自治收益未被证实，仍优先模块化单体。

#### 原理深挖

平台分控制面与运行面：控制面管理应用注册、版本、权限、灰度和兼容矩阵；运行面负责路由匹配、资源加载、生命周期、上下文注入与隔离。壳只提供版本化协议，不暴露内部 Store。

#### 工程场景

- **约束：** Vue/React 并存，主导航一致，壳首屏 P75 ≤ 2.5 s，单个子应用故障不能白屏全站。
- **方案：** 子应用提供签名清单与入口；稳定分桶灰度；公共依赖按兼容组共享；超时或生命周期异常时熔断为错误卡片。
- **指标：** 接入时长、独立发布率、壳启动开销、跨应用事故数和回滚 MTTR。
- **演进：** 先接入两个发布冲突最严重的业务，验证协议后再平台化；运行时沙箱等原理细节参见 [微前端](/interview/questions/12-microfrontend)。

#### 反例 / 踩坑

按菜单数量拆应用；强制所有依赖单例；跨应用直接读全局变量；壳升级要求全部子应用同步发布；没有离线资源和失败兜底。

#### 资深回答模板

「规模是 8 个团队、日活 50 万；数据流从控制面清单到壳加载和子应用 API；对比模块化单体、构建时集成和运行时微前端；故障验证清单服务、资源加载和子应用异常；证据看发布等待、壳开销、隔离率和 MTTR；反思拆分是否匹配真实组织边界。」
:::

**追问链：**
1. 子应用间通信和跳转如何设计？
2. 公共组件库多版本怎样处理？
3. 控制面故障时已上线应用能否继续运行？

### D2. 设计一个统一权限中心，服务多个前端应用

**考察点：** RBAC/ABAC、策略分发、审计、多租户

::: details 参考答案
#### 基础结论

Q5 设计单个中后台的权限接入；本题新增「20 个应用、多租户、集中策略发布」约束。权限中心统一资源—动作词汇及其映射、主体上下文、策略版本与审计；前端只消费能力快照改善体验，服务端按资源实例执行权威授权。

#### 原理深挖

核心模型包含用户/服务主体、租户、角色、资源层级、动作和条件。管理面负责申请、审批、发布、回滚；数据面提供低延迟判定与版本化快照。简单场景以 RBAC 为主，数据范围和上下文条件再引入 ABAC。

#### 工程场景

- **约束：** 20 个应用、1000 个权限点，多租户隔离，策略变更 5 分钟内生效，高风险写操作不可默认放行。
- **方案：** 资源—动作词汇注册表防语义漂移，并分别映射前端能力与服务端策略；策略发布带版本和审计；前端 SDK 读取短 TTL 能力快照；网关/服务端基于主体、资源实例、租户、动作、上下文和策略版本判定。
- **故障：** 中心不可用时读取最后已知好版本，低风险只读可短时延续，高风险写入默认拒绝。
- **演进：** 先统一权限词汇和审计，再迁移菜单、按钮与 API；最后补权限申请和自动越权测试。

#### 反例 / 踩坑

应用各自硬编码角色；UI 标识与 API 策略共用一个码；权限全量永久缓存；跨租户切换复用旧快照；服务端不记录允许/拒绝、命中策略与 TraceId；策略发布无灰度和回滚。

#### 资深回答模板

「规模是 20 个应用、1000 个资源—动作项；数据流从身份到能力快照、服务端决策和日志；对比分散 RBAC、集中 RBAC 与条件策略；故障验证租户串权、策略超时和旧版本；证据看判定 P95、拒绝异常率、策略生效与审计完整率；反思集中化边界。」
:::

**追问链：**
1. 资源数量达到百万级如何建模？
2. 权限中心如何避免成为所有发布的瓶颈？
3. 临时权限和到期回收如何设计？

### D3. 设计一个可运营的前端监控平台

**考察点：** 数据管道、聚合、告警、成本与隐私

::: details 参考答案
#### 基础结论

Q2 解决应用侧采集、指标和告警的基础闭环；本题新增「日活 500 万、峰值事件流、平台多租户运营」约束，重点是数据管道、成本与平台 SLO。验收指标包括 MTTD、MTTR、告警有效率、SourceMap 解析率和单事件成本。

#### 原理深挖

系统由采集 SDK、上报网关、消息队列、清洗聚合、事件存储、符号化服务、查询告警和发布中心组成。原始事件高基数且昂贵，应在入口做限流、采样、脱敏和指纹聚合。

#### 工程场景

- **规模：** 日活 500 万，峰值 5 万事件/s，错误保留 30 天，聚合指标保留 1 年。
- **方案：** 错误高采样、性能分层采样；`app/version/route/fingerprint` 聚合；SourceMap 私有上传并按版本匹配；告警使用多窗口阈值关联发布。
- **故障：** 上报端过载时服务端丢弃低优先级性能事件，SDK 有熔断，绝不阻塞主线程和业务请求。
- **演进：** 从错误与版本归因开始，再建设性能、Trace 关联和会话回放；回放需单独隐私评审。

#### 反例 / 踩坑

所有事件全量永久保存；日志中包含 Token 和输入内容；报警按单条错误触发；监控网关故障反向拖垮页面；接入后无人值班。

#### 资深回答模板

「规模是日活 500 万、峰值 5 万事件/s；数据流经 SDK、网关、队列、聚合和告警；对比 SaaS、自建与混合方案；故障验证配额耗尽、队列积压和存储降级；证据看有明确分母与窗口的接收 SLI、告警有效率、MTTR 和单事件成本；反思采样偏差与隐私边界。」
:::

**追问链：**
1. 错误指纹如何避免聚合过度？
2. SourceMap 泄露风险如何控制？
3. 如何证明监控平台的投入产出？

### D4. 设计一个配置化运营活动平台

**考察点：** Schema、发布链路、预览、风控与回滚

::: details 参考答案
#### 基础结论

目标是让运营在 30 分钟内搭建并安全发布常见活动页，同时保留复杂活动的代码扩展能力。平台必须把「搭建」与「安全发布」同等对待。

#### 原理深挖

配置模型包含页面树、组件 Schema、数据源、规则、实验和版本。编辑器、渲染器与发布服务通过版本化协议解耦；组件不是任意代码，而是经过审核的注册表能力。

#### 工程场景

- **约束：** 峰值百万 PV，移动端弱网，运营可预览和定时发布，涉及优惠券与用户分群。
- **方案：** 草稿/审核/发布状态机；预览使用隔离环境和测试身份；配置经双人审批、版本审计和租户灰度后生成不可变版本并推 CDN；动态数据经受控 API 代理；按人群稳定分桶。
- **故障：** 配置解析失败回退上一版本；数据源超时隐藏局部组件；优惠发放仍由服务端校验幂等和资格。
- **演进：** 先覆盖 Banner、列表和表单等高频模块，再加入实验、素材治理和模板市场。

#### 反例 / 踩坑

Schema 中允许 `eval`；运营可直发生产；预览与生产数据源不同；组件升级破坏历史页面；追求 100% 配置化导致 DSL 失控。

#### 资深回答模板

「规模是百万 PV、数百活动版本；数据流从草稿审批到 CDN 配置、动态 API 和提交；对比代码活动页、Schema 渲染和拖拽平台；故障验证坏配置、数据源超时和优惠重复发放；证据看搭建时长、回滚 RTO、任务成功率与违规发布数；反思配置化边界。」
:::

**追问链：**
1. 历史页面如何兼容组件升级？
2. 多人同时编辑怎样处理冲突？
3. 活动被恶意配置成钓鱼页如何防止？

### D5. 设计一套跨端工程体系

**考察点：** 共享边界、适配层、版本矩阵、端侧质量

::: details 参考答案
#### 基础结论

Q6 讨论有限人力下的跨端复用判断和发版治理；本题新增「统一工程控制面、长尾版本与端能力矩阵」约束。体系服务 Web、H5、小程序和混合 App 的一致交付，但只复用领域模型、协议、Token 和无平台假设的逻辑；UI 与生命周期按端实现。

#### 原理深挖

公共内核通过端口访问存储、网络、导航和设备能力，各端提供适配器。发布控制面维护端 × 应用版本 × API 能力矩阵，解决小程序审核和 App WebView 长尾版本问题。

#### 工程场景

- **约束：** 3 个端、2 个业务团队，小程序主包受限，App 容器半年才强更。
- **方案：** Monorepo 放共享领域包和契约测试；端能力用 feature detection；设计 Token 编译为各端变量；API 使用能力协商而非 User-Agent 猜测。
- **指标：** 跨端需求交付周期、共享包变更失败率、各端崩溃/白屏率和版本覆盖。
- **演进：** 先统一登录、错误码和埋点协议，再抽稳定领域逻辑；不以共享代码比例作为成功指标。

#### 反例 / 踩坑

为了复用把所有页面写满条件编译；共享包依赖 DOM；一端热修直接破坏公共契约；假设所有客户端都已升级；设计要求像素级完全一致。

#### 资深回答模板

「规模是 3 个端、多个容器版本；数据流从共享领域模型经端适配器到 API；对比各端独立、共享内核和全量跨端框架；故障验证 Bridge 缺失、审核延迟和长尾兼容；证据看交付周期、端侧任务成功率、版本覆盖和共享变更失败率；反思复用边界。」
:::

**追问链：**
1. 何时应该为某一端分叉实现？
2. 公共包破坏性升级如何发布？
3. App 容器能力缺失时 H5 如何降级？

### D6. 设计一个 BFF / API 聚合层

**考察点：** 聚合边界、缓存、鉴权、可用性

::: details 参考答案
#### 基础结论

BFF 为特定体验聚合和裁剪后端能力，减少前端扇出与协议耦合；它不拥有核心业务规则和权威数据。只有当多个客户端需求明显不同或页面调用链成为瓶颈时才引入。

#### 原理深挖

BFF 负责并行编排、字段整形、协议适配、轻量缓存和客户端友好错误；领域事务、库存判断与权限权威仍在服务端领域服务。身份上下文必须以受信令牌或网关签名传播，BFF 不接受客户端自报的主体与租户；调用下游时保留主体、租户、资源、动作、策略版本和 Trace 上下文。GraphQL、REST 聚合和网关编排要按团队能力与查询复杂度选择。

#### 工程场景

- **约束：** 首页依赖 8 个服务，移动弱网，目标首屏接口 P95 ≤ 800 ms，任一推荐服务故障不能阻断交易入口。
- **方案：** 聚合接口并行调用，设置分依赖超时与总预算；按租户、主体/客户端和路由限流；用隔离舱或独立连接池限制慢下游并发，核心数据失败返回错误，推荐失败返回空模块。
- **授权与缓存：** BFF 先验证身份和租户成员关系，再由下游对资源实例权威授权；缓存键至少包含租户、权限/策略版本、查询条件和数据版本，用户相关结果还要包含主体或可证明等价的权限分组，禁止跨租户命中。
- **高可用：** 多可用区无状态部署，配置与缓存降级不影响核心透传；定义如「5 分钟窗口内合法核心请求成功数 / 合法核心请求总数」的 SLI、目标 SLO、排除项和错误预算。
- **观测与运维：** 传播 W3C Trace Context，记录每个下游耗时、限流、隔离、缓存和降级率；BFF 有生产 Owner、容量评审、发布回滚、Runbook 与 on-call。
- **演进：** 先为一个高价值页面建立薄 BFF，避免变成新的业务单体；重复编排再下沉共享服务。

#### 反例 / 踩坑

把所有接口都代理一遍；信任客户端传来的租户；缓存键缺少租户或策略版本；在 BFF 复制授权与领域规则；串行调用下游；无限并发拖垮连接池；单可用区且没有 SLO/on-call。

#### 资深回答模板

「规模是百万请求/日、首页扇出 8 个服务；数据流携带受信主体、租户和 W3C Trace 上下文；对比客户端聚合、网关编排与 BFF；故障验证慢下游、跨租户缓存、限流和可用区失效；证据看有分母窗口的可用性 SLI、P95、降级率与成本；反思 BFF 是否吸收了领域职责。」
:::

**追问链：**
1. BFF 与 API Gateway 的边界是什么？
2. 聚合返回部分成功时协议如何设计？
3. GraphQL 是否天然优于 REST BFF？
