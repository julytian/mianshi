### D1. Vite 依赖预构建与生产构建为什么是两条不同管线？

**考察点：** 开发时 ESM 直出、生产 Rollup 打包、冷启动与 HMR 体感

::: details 参考答案
#### 基础结论
开发要的是「改完立刻看见」，生产要的是「体积与加载可控」，Vite 因而采用不同链路。

#### 原理深挖
开发：浏览器原生 ESM + 按需编译（esbuild 转译 TS/JSX），不先打整包，所以冷启动快；依赖用 pre-bundle（esbuild）扫进 `node_modules/.vite`，减少瀑布请求。生产：Rollup 做 tree-shaking、code splitting、资源哈希——和「开发链路」不是同一条管道。

预构建主要处理开发态依赖发现、CJS/UMD 兼容和依赖请求成本。生产底层构建器正处于版本演进，回答必须绑定项目 Vite 版本，不把当前默认实现说成永久契约。

#### 工程场景
升级时同时跑 dev、production build 与 preview；只有动态生成且扫描不到的依赖才考虑 `optimizeDeps.include`，并记录 lockfile、配置和依赖变化。

#### 反例 / 踩坑
开发预构建成功不代表生产插件链、CJS 转换和 SSR 一定成功；反复删 `.vite` 只能验证缓存症状，不能替代根因分析。

#### 资深回答模板
口述别停在「快」：要说清**为什么快**（不打包整应用）、**哪里仍会慢**（巨型依赖、过多 glob 动态 import、插件链太重）、**和 Webpack 的真正差异**（配置心智：约定 + 插件钩子，而不是巨石 loader 规则迷宫）。十年经验说法：工具换代不是宗教，是「开发体验预算」和「生产产物可控」的重新分配。

#### 追问链
1. 依赖为什么会在开发中途触发重新预构建？
2. 本地正常、production build 失败先比较哪些差异？
3. Vite 升级时如何识别底层构建器变化？
:::

**追问：**
1. 为什么说「Vite 开发不打包、生产要打包」？这对排查「本地正常线上挂」有什么启发？
2. `optimizeDeps` 什么时候要你手动 include / exclude？
3. 若公司还在 Webpack，你推动迁移的判断标准是什么？

**踩坑：** 依赖了 Node 内置或仅 CJS 的脏包，开发 pre-bundle 过了、生产 Rollup 炸——别只会清缓存，要会看是不是双构建管线差异。

### D2. Vite 插件钩子、虚拟模块与 HMR 如何组成可维护扩展？

**考察点：** 钩子时机、`transform` / `resolveId` / `load`、约定优于魔改

::: details 参考答案
#### 基础结论
先想：插件就是在构建生命周期里「插一脚」——解析路径、读文件、改源码、改产物、注入 HTML。Vite 插件兼容 Rollup 钩子，再加 Vite 特有的 `configureServer`、`transformIndexHtml` 等。

#### 原理深挖
虚拟模块对用户使用 `virtual:plugin-name/...`，内部 id 按约定加 `\0`。HMR 可用 `handleHotUpdate` 缩小受影响模块，并通过 `import.meta.hot` 接受或失效；dev 与 build 可用 `apply` 区分。兼容的底层插件接口随 Vite 版本演进，应查目标版本官方文档。

#### 工程场景
实战常见：
- 把 `svg` 当组件（`resolveId` + `load` 吐出 Vue SFC）；
- 按环境注入业务常量（比满天飞 `define` 更可控）；
- 本地 mock / 代理增强；
- 构建后上传 sourcemap、生成版本文件。

插件过滤 id、缓存纯转换、生成可组合 Source Map，并为 resolve/load/transform 与 HMR 写集成测试。无法安全局部更新时应整页刷新。

#### 反例 / 踩坑
字符串替换破坏语法与 Source Map；虚拟 id 不命名空间；HMR 只推新代码却不清旧监听；transform 扫描全仓拖垮更新。

#### 资深回答模板
口述结构：要解决什么痛 → 卡在哪个钩子 → 为什么不写 CLI 脚本而做成插件（要吃 HMR / 和打包图联动）。原则：**能配置解决别写插件；插件要小、可测、可关**。团队里「神秘 transform 改业务代码」是债。

#### 追问链
1. `resolveId` 与 `load` 如何配合虚拟模块？
2. 什么时候 HMR 应降级整页刷新？
3. 多个 transform 如何保持 Source Map 链正确？
:::

**追问：**
1. `enforce: 'pre' | 'post'` 解决什么顺序问题？
2. 开发态插件和生产态插件为什么有时要拆？
3. 插件里乱改 AST / 字符串替换，出了 bug 你怎么定位？

**踩坑：** 在 `transform` 里对所有文件做重活，HMR 体感直接崩——要过滤 `id`、缓存结果、避开 `node_modules`（除非必要）。

### Q3. 前端环境变量怎么设计才不踩雷？`VITE_` 前缀到底防什么？

**考察点：** 构建期注入、密钥边界、多环境文件、运行时配置

::: details 参考答案
先想：浏览器里的代码**没有真正的服务端秘密**——打进 bundle 的都能被看见。`VITE_`（或同类）前缀是「白名单：允许暴露给客户端」的显式标记，防止误把 `DB_PASSWORD` 之类写进前端。

分层习惯：
1. **构建期**：`import.meta.env.VITE_API_BASE`——不同环境打不同包或同一套流水线注入；
2. **运行时**：`config.json` / 窗口全局 / 网关下发——同一产物多环境部署时更香；
3. **密钥**：只放服务端、BFF、CI secret，前端最多拿「可公开的 client id」。

口述要讲清：`.env` / `.env.local` / `.env.production` 的优先级；本地 `.env.local` 不进库；CI 用 secret 注入而不是把生产地址写进仓库。别把「换环境 = 改源码常量」当方案。
:::

**追问：**
1. 什么时候必须用运行时配置而不是 `VITE_*`？
2. 前端拿了第三方 `accessKey`，你怎么和安全同学对齐风险？
3. 多租户 / 白标产品，环境变量模型怎么变？

**踩坑：** 以为「不写 `VITE_` 前缀就安全」——若你自己用 `define` 或脚本硬塞，照样泄漏；前缀只是约定闸门，不是加密。

### Q4. 包体积膨胀了，你怎么做 bundle 分析与归因？

**考察点：** rollup-plugin-visualizer / 依赖归因 / 重复打包 / 错误引入

::: details 参考答案
先想：体积问题先**看见**，再**归因**，最后才谈优化手段——别一上来乱砍依赖。

做法：生产构建开 visualizer（treemap）或 `vite-bundle-visualizer`，看：
- 谁占顶（UI 库、图表、编辑器、polyfill、moment 时区包）；
- 是否重复打包同一库（monorepo 多版本、错误 peer）；
- 是否「入口误引」——管理后台首页拉进了仅报表页才要的 ECharts 全量。

归因话术：是**依赖选择**问题、**引入路径**问题，还是**拆包策略**问题。优化顺序通常：换轻量替代 / 按需与按路由拆 → 压缩与现代浏览器目标 → 再抠 gzip/brotli 边角。面试给一个你真实砍掉的数字（如主包 -180KB）比背十个工具名强。
:::

**追问：**
1. treemap 里看到 `lodash` 全量，你怎么验证是谁引进来的？
2. `manualChunks` 拆得太碎会怎样？
3. 体积和请求数怎么权衡？

**踩坑：** 只看「构建产物 MB」不看「首屏实际下载」——HTTP 缓存命中、路由懒加载后，用户路径不同，体感差很多。

### Q5. 代码分割（code splitting）你会怎么设计？动态 import 的边界在哪？

**考察点：** 路由级拆分、组件级拆分、共享 chunk、预加载

::: details 参考答案
先想：拆包目标不是「文件越多越好」，而是**首屏只付首屏的账**，后续导航再付。

常用分层：
1. **路由级**：`()` => import(`./views/Foo.vue`)`——中后台默认答案；
2. **重型组件级**：编辑器、地图、图表、Excel 导出——交互触发再加载；
3. **共享抽离**：Vue / Vue Router / UI 基础库进稳定 vendor，利于长缓存；
4. **预加载**：关键下一跳用 `<link rel="modulepreload">` 或路由器钩子里idle 预取——别对所有路由预取，等于没拆。

边界：过碎 → 瀑布请求与调度开销；过粗 → 首屏背锅。动态 import 的路径要静态可分析（别纯变量拼路径），否则打包器兜不住。业务上还要处理 loading / error 边界，避免白屏。
:::

**追问：**
1. 同一依赖被多个异步 chunk 引用，最终会怎样？
2. 微前端场景下，「拆包」和「子应用独立构建」怎么分工？
3. SSR / 流式场景下拆包思路有何不同？

**踩坑：** 在同步导入链里「随手」引入重型库，路由懒加载形同虚设——要用分析工具确认首页图里没有它。

### D3. CI 如何并行、增量与远程缓存，同时保证结果可信？

**考察点：** lint / typecheck / test / build / 门禁分级、主干保护

::: details 参考答案
#### 基础结论
先想：门禁是**风险分层**，不是工具堆砌。MR 上要拦「确定会疼」的，主干上要拦「发布不可逆」的。

#### 原理深挖
任务图决定可并行项与依赖项；affected 计算依赖 Git 基线和包图；远程缓存键至少包含源码输入、lockfile、工具版本、配置、环境变量白名单与命令。缓存产物要可校验、分权限，不可信分支不应写生产可信缓存。

#### 工程场景
常见分级：
- **必卡**：`eslint`（错误级）、`vue-tsc` / `tsc --noEmit`、单测（改动相关或核心包）、生产 `build`；
- **可异步 / 夜间**：全量 E2E、bundle size 趋势、依赖漏洞扫描；
- **发布前**：冒烟、迁移脚本、配置差分。

先测关键路径，再并行无依赖任务；monorepo 用 affected 缩范围，主干和定时任务保留全量兜底。缓存命中率、恢复耗时和误命中都要观测。

#### 反例 / 踩坑
只用分支名作缓存键、忽略 Node 版本与环境输入会拿到陈旧产物；浅克隆基线缺失会漏算 affected；并行 E2E 共享账号和数据会制造 flaky。

#### 资深回答模板
落地关键：失败要**可本地复现**（同一脚本）；允许紧急通道但要留审计；别把「格式问题」和「类型错误」混成同一种失败体验。口述讲你推动过的一条：例如「类型检查只在 CI 跑 → 开发机漏网 → 改成 pre-push + CI 双闸」。十年经验：门禁太多团队会绕过；太少债务会爆炸——用数据调阈值。

#### 追问链
1. 如何验证远程缓存没有误命中？
2. PR 基线变化后 affected 如何重算？
3. 哪些任务不适合缓存？
:::

**追问：**
1. 单测不稳定（flaky）时，门禁策略怎么定？
2. monorepo 里如何做 affected-only 检查加速 CI？
3. 「先合再修」和「严格红灯」你怎么跟 TL 对齐？

**踩坑：** CI 用 `|| true`、忽略失败产物上传——绿勾比红灯更危险。

### Q7. ESLint 和 Prettier 怎么分工？冲突了你怎么收场？

**考察点：** 职责边界、eslint-config-prettier、团队一致性

::: details 参考答案
先想：ESLint 管「对不对 / 会不会埋雷」，Prettier 管「好不好看」。混在一起就会无穷争论分号与换行。

实践：
- Prettier 格式化（或 Biome 同类）；
- ESLint 负责正确性、Vue/TS 最佳实践、import 边界、禁止 `any` 策略等；
- 用 `eslint-config-prettier` 关掉和 Prettier 打架的 stylistic 规则；
- 编辑器 format on save + CI `prettier --check`，避免「我机器上好好的」。

规则集要**可解释**：新规则用 warn 试跑再升 error；禁止「一人一份 eslint 插件狂欢」。大仓治理用渐进：目录级 overrides，而不是一天全仓变红。
:::

**追问：**
1. 为什么很多团队开始看 Biome / Oxlint？你会怎么评估替换？
2. `eslint --fix` 能不能进 CI 自动修？
3. Vue 模板里的规则和 script 规则如何对齐？

**踩坑：** 同时开 ESLint stylistic 与 Prettier，PR 里来回打架——新人最怕这种「玄学红」。

### Q8. Husky + lint-staged 解决什么？和 CI 门禁如何搭配才不烦？

**考察点：** 提交钩子、暂存区检查、本地反馈循环

::: details 参考答案
先想：钩子的价值是**反馈左移**——几秒内告诉你格式/基础 lint，而不是等 CI 十分钟。

`lint-staged` 只跑**暂存文件**，避免全仓 eslint 劝退。典型：`*.{ts,vue}` → eslint；`*.{ts,js,vue,css,md}` → prettier。类型检查通常太重，不放 pre-commit，放 pre-push 或 CI。

搭配原则：本地轻、CI 全；钩子可跳过（`HUSKY=0`）但要文化约束与审计；Windows / 不同包管理器下路径要测。口述别吹「有了 husky 就质量好」——没有规则共识，钩子只是噪音发生器。
:::

**追问：**
1. 为什么有人反对 git hooks？你怎么回应？
2. monorepo 里 lint-staged 如何只跑对应 package 的配置？
3. commit message 规范（commitlint）你放哪一层？

**踩坑：** pre-commit 跑全量 `vue-tsc` + 全量单测——团队会集体 `--no-verify`，钩子等于死亡。

### Q9. Vue 项目单测策略你会怎么定？测什么、不测什么？

**考察点：** Vitest + Vue Test Utils、可测设计、投入产出比

::: details 参考答案
先想：单测买的是**重构勇气**和**回归刹车**，不是覆盖率虚荣。

分层建议：
- **纯逻辑 / composable**：优先测（入参出参、边界、错误）——ROI 最高；
- **复杂组件**：测关键交互与状态切换（打开弹窗、校验失败、权限隐藏），少测「渲染出某个 class 名」；
- **快照**：易碎，慎用；
- **E2E（Playwright/Cypress）**：留给关键用户路径（登录、下单、发布）。

可测设计：把请求、时间、路由做成可注入；别在组件里写死 `window.xxx`。覆盖率门槛可对「核心包」设，不对「全仓 90%」神教。口述举一个：抽 `useOrderFee` 测费率边界，比测整个结算页 DOM 便宜一个数量级。
:::

**追问：**
1. 组件测里要不要挂真实 Pinia / Router？如何 stub？
2. 异步请求怎么测才稳（假定时器 / MSW）？
3. 「没有测试的老页面」你怎么渐进补测？

**踩坑：** 为了覆盖率去测私有实现细节，一重构全红——测的是行为契约，不是内部函数名。

### Q10. Monorepo 你怎么讲认知模型？什么时候该上、什么时候别上？

**考察点：** 包边界、workspace、共享策略、CI affected

::: details 参考答案
先想：Monorepo 解决的是「多包协作与版本对齐的交易成本」，不是「把所有代码丢一个 git 里装逼」。

适合：组件库 + 多个业务 app、共享工具链与类型、需要原子提交跨包改动。不适：团队自治极强、发布节奏完全无关、权限与合规要求强隔离——硬揉只会变成巨石权限与 CI 地狱。

认知要点：
- **包边界清晰**（`packages/*` 公共 API，禁跨包偷摸相对路径打洞）；
- **依赖方向**（app → lib，禁止环）；
- **工具**：pnpm workspace / Turborepo / Nx 管任务图与缓存；
- **版本**：内部包 `workspace:` 协议，对外发版另说。

口述讲清你踩过的：共享了「半业务组件」导致所有 app 耦合发版——共享的应该是稳定原语，不是业务泥球。
:::

**追问：**
1. 内部包用固定版本号还是 `workspace:*`？
2. 如何防止 app 直接引用另一个 app 的源码？
3. 单仓多包和「多仓 + 私服」怎么选？

**踩坑：** 根目录一个巨大 `package.json` 把所有依赖吊在一起——失去包边界，只剩目录分类。

### Q11. 发版与版本号你怎么定规矩？SemVer 在前端库和业务 App 上有何不同？

**考察点：** SemVer、changelog、标签、业务 App 的「构建号」

::: details 参考答案
先想：版本号是**兼容性合同**。对库（组件库、SDK）严格 SemVer：breaking → major，兼容功能 → minor，修 bug → patch。对业务 App，用户不读版本号，更关心「可追溯的构建身份」：`git sha` + 构建时间 + 环境；对外展示可用日历版或营销版，对内必须能定位提交。

流程直觉：changeset / standard-version / release-please 生成 changelog；打 tag；产物带版本文件（`version.json`）方便排查。预发布用 `alpha/beta/rc`。口述强调：**谁有权发正式版、回滚指向哪个 tag、热修是否占版本号**——比背 SemVer 定义重要。
:::

**追问：**
1. 组件库 minor 里「看起来兼容」但 CSS 行为变了，算不算 breaking？
2. 多包 monorepo 独立发版 vs 锁步发版怎么选？
3. 热修复（hotfix）从哪条分支切？

**踩坑：** App 每次改文案也 bump major——版本失去语义，排查时反而噪音。

### D4. 前端灰度发布怎样定义观测窗口、停止线与回滚动作？

**考察点：** 流量分割、错误率、性能、回滚条件

::: details 参考答案
#### 基础结论
先想：灰度不是「少机器」，是「小爆炸半径 + 可观测 + 可快撤」。

#### 原理深挖
灰度要保证同一用户或会话的版本黏性，指标按版本、路由、租户与设备切片。停止线基于错误预算、白屏、资源失败、性能和业务转化，并考虑基线与统计波动；没有最小样本的固定等待时间不构成安全证明。

#### 工程场景
前端常见手段：按用户 / 租户 / 百分比切静态资源版本（CDN 目录或 HTML 入口指向）；配合 feature flag 做逻辑灰度。监控三角：
- **错误**：JS error、资源 404、白屏探针；
- **体验**：LCP/INP 分位、接口成功率；
- **业务**：关键转化是否掉崖。

发布控制面记录版本、操作者、分群规则和回滚目标；先自动停止扩量，是否自动回滚按故障可逆性决定。HTML 短缓存，hash 资源保留覆盖观察与回滚窗口。

#### 反例 / 踩坑
请求级随机分流导致同一用户混载版本；只看总错误率掩盖单个租户；回滚入口时旧 chunk 已删除；后端不向后兼容使前端单独回滚失效。

#### 资深回答模板
「我先定义分群与版本黏性，再按版本观测技术、体验和业务指标。停止线可自动执行，回滚目标和静态资源预先验证；样本量与兼容窗口决定何时继续扩量。」

#### 追问链
1. 灰度样本很小时如何避免误判？
2. 前后端版本兼容窗口如何约定？
3. 自动回滚可能在哪些场景扩大故障？
:::

**追问：**
1. 本地缓存了旧 chunk，灰度新 HTML 时最怕什么？
2. 只有 Sentry、没有业务指标，灰度够不够？
3. 客户端强缓存 HTML 时，你怎么做发布？

**踩坑：** 新老 chunk 混载（HTML 新、JS 旧缓存策略乱）导致运行时 `Loading chunk failed`——要版本化目录 + 合理 Cache-Control。

### Q13. LCP、INP、CLS 你怎么一口讲清？优化时各抓什么？

**考察点：** 核心 Web Vitals、诊断直觉、分位而非平均数

::: details 参考答案
先想：三个指标分别对应「看见主内容有多慢」「交互有多迟滞」「布局有多跳」。

- **LCP**：最大内容绘制——常常是英雄图、大标题、首屏列表首屏块。抓：服务器/CDN TTFB、资源优先级、图片尺寸与格式、阻塞渲染的 CSS/字体、别被巨石 JS 拖晚。
- **INP**：交互到下一帧绘制的延迟——长任务、主线程被大包解析/hydration 占满、事件处理器太重。抓：拆长任务、减主线程 JS、优化处理器、必要处 `requestAnimationFrame` / 让出主线程。
- **CLS**：累计布局偏移——图片/广告无尺寸、字体闪动、动态插入顶栏。抓：宽高或 aspect-ratio、字体策略、预留骨架。

口述一定带：**看 P75/P95，分页面、分设备**；实验室 Lighthouse 是线索，线上 RUM 才是判决。
:::

**追问：**
1. LCP 元素是一张懒加载图片，说明什么？
2. INP 差但 FPS 看起来还行，可能原因？
3. 为什么「优化了包体积但 LCP 没动」？

**踩坑：** 只报首页平均分给领导——被少数差页面/差网络用户的长尾打脸。

### Q14. 首屏优化你会按什么顺序动手？如何证明有效？

**考察点：** 关键路径、资源优先级、渲染路径、对比实验

::: details 参考答案
先想：先定义「首屏」是哪个路由、什么用户、什么网络，再动手——否则优化戏台。

常见顺序（由因到果）：
1. 量基线（Web Vitals、HAR、Performance）；
2. 砍关键路径 JS（路由拆分、去掉同步重依赖）；
3. 图片与字体（正确尺寸、现代格式、`font-display`）；
4. 关键 CSS 内联 / 减阻塞；
5. 接口并行与骨架，消瀑布；
6. CDN 与缓存；
7. 必要再上 SSR/流式——别一上来架构升级。

证明：同一环境前后对比（LCP 降多少、主包 KB、可交互时间）；最好带灰度对照。口述用 STAR：现象 → 假设（主包里进了图表）→ 验证（visualizer）→ 手段（异步）→ 数字。
:::

**追问：**
1. 骨架屏会改善哪类指标、改善不了哪类？
2. 首屏接口必须串行时，前端还能做什么？
3. 中后台和 H5 营销页，首屏策略差在哪？

**踩坑：** 为了首屏把所有逻辑推迟，首交互却巨卡——LCP 好看、INP 爆炸，用户仍骂。

### Q15. 前端缓存策略你会怎么分层讲？HTML / JS / API 各怎么设？

**考察点：** Cache-Control、哈希文件名、协商缓存、Service Worker 边界

::: details 参考答案
先想：缓存的本质是「错了能换新、对了别重复下」。

分层：
- **带 content hash 的静态资源**（`app.abc123.js`）：`Cache-Control: public, max-age=31536000, immutable`——改内容即改文件名；
- **HTML 入口**：短缓存或协商缓存（`no-cache` + etag），保证能指到新资源清单；
- **API**：看业务——列表可短缓存或客户端 SWR；用户私有数据默认不共享缓存；鉴权响应小心 `CDN 缓存`；
- **Service Worker**：离线与秒开利器，也是「刷不掉旧世界」的重灾区——要有版本更新与跳过等待策略。

口述画一条发布链路：更 HTML → 拉新 hash 资源 → 旧资源仍可被旧 HTML 引用一段时间。灰度与回滚都建立在这套约定上。
:::

**追问：**
1. 为什么有人给 HTML 也设一年长缓存会出事？
2. `immutable` 没 hash 时危险在哪？
3. CDN 回源与浏览器缓存同时存在时，你怎么排查「我清了 CDN 用户还是旧的」？

**踩坑：** 本地开发关缓存习惯带到线上排查——用无痕或禁用缓存对照，再查真实头。

### Q16. 生产环境 Source Map 怎么用？如何既可调试又不裸奔？

**考察点：** hidden/nosources、上传监控平台、权限与泄漏

::: details 参考答案
先想：Source Map 是「线上堆栈 → 源码」的桥。没有它，Sentry 只剩混淆行号；有了它若公网可下，等于开源你家业务。

实践：
- 构建生成 map，**不**随静态资源公开部署（或 `hidden-source-map`：生成但不在文件尾注释引用）；
- CI 把 map 上传到 Sentry/类似平台，绑定 release = git sha；
- 访问权限仅限错误监控与受控内网；
- 发版后保留一段时间便于排障，过期清理。

调试流程：报错 → release → 还原栈 → 结合面包屑与用户路径。别在生产开完整内联 map。
:::

**追问：**
1. `hidden-source-map` 和完全不生成有何差别？
2. 第三方脚本报错没有 map，你怎么处理？
3. 开了压缩 + 混淆，map 缺失时如何临时定位？

**踩坑：** Nginx 把 `.map` 当静态文件公开了——扫目录即源码。部署配置要显式拒绝或根本不上传到 CDN 桶。

### Q17. 微前端什么时候该上、什么时候坚决不上？

**考察点：** 组织边界、技术边界、成本、替代方案

::: details 参考答案
先想：微前端首先是**组织与交付解耦**的架构，其次才是 iframe/qiankun/Module Federation 技术选型。

该上的信号：多团队独立发版、技术栈短期无法统一、遗留系统要渐进替换、模块边界清晰且有平台组护航。

不该上的信号：同一小队维护、只是想「炫技拆仓库」、共享状态密集成一团、没有统一的路由/鉴权/样式治理预算——拆完变成分布式单体，调试成本指数涨。

替代：monorepo 多 app + 统一设计体系、iframe 强隔离嵌入、后端拼装、简单的「路由级懒加载巨石」先撑住。口述要敢说「我们评估后没上」——这也是资深判断。

本章只讨论组织边界、独立交付收益和平台成本。JS 沙箱、样式隔离、路由、通信、依赖共享等具体机制统一见 [微前端题库](./12-microfrontend.md)，避免两处维护相互冲突的答案。
:::

**追问：**
1. 两个团队是否真的拥有独立发布权和清晰领域边界？
2. 平台组要承担哪些长期治理与故障响应责任？
3. 何时应先用 monorepo 多应用验证边界，再决定微前端？

**踩坑：** 用技术隔离替代组织治理，最后仍要同步联调、同步发布，只是多了一层平台税。

### Q18. 组件库建设节奏你会怎么定？从「能用」到「敢发」跨过哪些坎？

**考察点：** API 稳定性、文档、视觉回归、发版节奏

::: details 参考答案
先想：组件库是产品，不是文件夹。节奏比「一次写完 50 个组件」重要。

阶段：
1. **原语期**：Button/Input/Modal 等，先服务 1～2 个真实业务，拒绝空想 API；
2. **契约期**：props 语义稳定、changelog、peerDeps（vue 版本）、主题 token；
3. **质量期**：单测 + 关键视觉回归（Chromatic/截图）、无障碍基线；
4. **运营期**：定期 minor、breaking 集中 major、废弃期（deprecation）给迁移窗口。

建设原则：业务特化组件留在业务仓；库里放可复用原语与模式。文档即门面——没有 Playground 的组件库团队不会用。口述强调「慢发 breaking、快修 patch」。
:::

**追问：**
1. 业务方提了强定制需求，你接进库还是让业务包装？
2. CSS 方案（CSS Variables / Uno / 预处理器）怎么选才利于主题？
3. 多技术栈（Vue2/3）共存期如何维持？

**踩坑：** 组件库和业务同一天锁步发版、没有版本窗口——库一改，全线应用被迫救火。

### Q19. Code Review 你怎么定团队规范？什么算「必须挡」，什么算「风格偏好」？

**考察点：** CR 效率、风险分类、文化建设

::: details 参考答案
先想：CR 是降低「一个人的盲区」，不是展示谁的审美更高级。

必须挡：正确性与安全（权限、XSS、密钥）、数据丢失风险、明显性能陷阱（同步超大列表无虚拟化却上生产）、不可回滚的迁移、测试/门禁被故意拆掉。

**追问：**
1. 紧急热修是否允许简化 CR？如何补审计？
2. 新人 PR 你怎么 review 才有教学又不羞辱？
3. AI 生成的大段代码，CR 重点看什么？

**踩坑：** 百文件巨型 PR——没人看得懂，LGTM 成形式主义。拆 PR 是工程能力。

### Q20. pnpm 相对 npm / yarn，你会怎么讲「为什么团队该换」？

**考察点：** 硬链 + 内容寻址、幽灵依赖、磁盘与 CI 速度

::: details 参考答案
先想：包管理器差异的核心是**依赖布局哲学**，不是命令长得像不像。

pnpm：内容寻址存储 + 硬链/符号链接到项目，磁盘省、安装快；默认更严，**不轻易允许幽灵依赖**（用到但没声明的包）——这在迁移时会疼一阵，长期更健康。workspace 对 monorepo 一流公民。npm 近年也在进步，但很多仓仍吃幽灵依赖的隐性耦合。

口述结构：痛（CI 安装慢 / 幽灵依赖线上偶然炸）→ 换 pnpm 的收益 → 迁移成本（补齐 peer、改 lockfile、缓存配置）→ 与 corepack 锁定版本。别神化：小项目 npm 也够；关键是**锁文件一致、CI 可复现**。
:::

**追问：**
1. 什么是幽灵依赖？举一个 Vue 插件踩坑例子。
2. `pnpm shamefully-hoist` 什么时候不得不开？
3. 私有 registry 与 `pnpm fetch` 缓存怎么配到 CI？

**踩坑：** 本地用 pnpm、CI 用 npm ci 各装各的——lockfile 形同虚设，行为漂移。

### Q21. 前端 Docker + Nginx 部署，你怎么讲一条「够用且干净」的链路？

**考察点：** 多阶段构建、静态资源、反代、健康检查

::: details 参考答案
先想：浏览器应用大多是「构建静态文件 + Nginx 提供」——Docker 包的是**可复现的运行环境与配置**，不是在容器里跑 Vite dev。

轻量套路：
1. 构建阶段：Node 镜像 `pnpm install --frozen-lockfile` + `pnpm build`；
2. 运行阶段：`nginx:alpine` 只拷 `dist` 与 nginx 配置；
3. Nginx：`try_files` 支持 SPA history；静态资源长缓存；`index.html` 短缓存；必要时反代 `/api`；
4. 健康检查打静态或专门 `healthz`；
5. 环境差异用运行时 `config.json` 或入口注入，避免为每个环境单独打业务镜像（看场景）。

口述提安全：非 root、只读文件系统（能开则开）、不把 secret 写进镜像层。
:::

**追问：**
1. 为什么多阶段构建能缩小镜像？
2. SPA 刷新 404 通常是哪行配置没写对？
3. 同域反代与 CORS 跨域，你怎么选？

**踩坑：** 把 `node_modules` 打进最终镜像，或在容器里 `npm run dev` 当生产——又慢又不安全。

### Q22. Feature Flag 轻量用法你会怎么落地？和分支策略如何配合？

**考察点：** 解耦发布与上线、风险控制、清理债务

::: details 参考答案
先想：Flag 的价值是**把「部署代码」和「对用户开启功能」拆开**——代码先合入，功能后放量。

轻量做法：配置中心 / 远程 JSON / 甚至环境变量布尔；按用户、租户、百分比；服务端下发优先于纯前端写死（防改包）。配合：主干开发 + flag 藏未完成功能，减少长命分支。

纪律：
- 命名清晰、默认安全（失败时关）；
- 有主人与过期时间——做完要删，否则变成永久 if 坟场；
- 别用 flag 代替设计：十层嵌套 flag 是事故温床。

口述举一例：大改结算页，先暗合，灰度 5% 开旗，监控没事再全量，出问题关旗秒级止血（相对重新发版）。
:::

**追问：**
1. 前端 flag 和后端 flag 不一致会怎样？如何对齐？
2. 测试环境如何覆盖「旗开/旗关」矩阵而不组合爆炸？
3. Flag 清理你怎么推进，避免没人删？

**踩坑：** 把密钥或定价逻辑只藏在前端 flag 后——关旗不是安全边界，只是产品开关。

### Q24. 依赖升级与安全漏洞（npm audit）你怎么治理，才不会「要么从不升、要么一次炸」？

**考察点：** 依赖卫生、锁定策略、升级节奏

::: details 参考答案
先想：依赖是负债也是杠杆。策略是**持续小步**，不是年终一次大爆炸。

3. 私有 fork / patch-package 的退出条件是什么？

**踩坑：** 为消 audit 盲目 `--force` 升到不兼容版本，开发环境绿、生产运行时红。

### D5. chunk 如何划分才能兼顾首屏、瀑布与长期缓存？

::: details 参考答案
#### 基础结论
分包目标是让用户只下载当前路径需要的代码，并让低频变化依赖获得较长缓存寿命；不是文件越小越好。入口、路由、重型功能和稳定公共依赖是常见边界。

#### 原理深挖
内容哈希由 chunk 内容及引用关系决定，上游模块变化可能级联改变引用它的 chunk。过度 `manualChunks` 会增加请求、模块解析和瀑布；把所有 vendor 固定一包又会因任一依赖升级导致整包失效。

#### 工程场景
基于真实路由覆盖与网络瀑布看首屏下载、缓存复用和重复模块；为编辑器、图表等交互后功能异步加载；保留构建 manifest 做版本归因，并用预算防止主包回涨。

#### 反例 / 踩坑
按 npm 包一包到底、把共享 chunk 拆得极碎、只看 gzip 总量不看关键路径，都会优化错目标。

#### 资深回答模板
「我按用户路径和变化频率分包，以首屏请求链、缓存命中和二次导航共同验收。manualChunks 只处理有证据的稳定边界，并持续检查级联 hash 与重复依赖。」

#### 追问链
1. 为什么公共 chunk 变化会影响异步 chunk 的 hash？
2. HTTP/2 是否意味着可以无限碎包？
3. 如何评估 vendor 包的合理粒度？
:::

### D6. 生产 Source Map 如何安全存储并准确还原错误？

::: details 参考答案
#### 基础结论
Source Map 用生成代码位置映射源码。生产可生成 map 供受控错误平台使用，但不应默认公开到 CDN；release、dist、文件 URL 与构建产物必须一一对应。

#### 原理深挖
多次 transform 要组合映射链；压缩后列号同样重要。hidden map 只是产物不附公开引用，不代表部署系统不会上传 `.map`；`nosources` 降低源码暴露，但调试能力也受限。

#### 工程场景
CI 构建一次，上传 map 到监控平台后再发布同一产物；用 git SHA 标识 release，部署规则拒绝 map 公网访问。发布前用故意异常验证还原到正确提交和源码行。

#### 反例 / 踩坑
重新构建 map 上传会与线上字节不一致；只按版本号不按文件路径匹配；插件 transform 不返回 map，会让后续映射断链。

#### 资深回答模板
「Source Map 安全与准确同等重要。我保证一次构建、release 绑定、受控上传和公网拒绝，并用合成错误做端到端还原测试。」

#### 追问链
1. hidden 与 nosources map 分别解决什么？
2. CDN 改写路径后如何保持 artifact 匹配？
3. 第三方脚本无 map 如何降噪？
:::

### D7. CI 远程缓存怎样建立可信边界与可复现性？

::: details 参考答案
#### 基础结论
缓存是性能优化，不是正确性来源。任何缓存命中都应等价于相同输入的本地执行；关键任务要支持禁用缓存复跑，构建环境与依赖安装必须可复现。

#### 原理深挖
输入包括文件、依赖图、lockfile、工具链、命令和影响输出的环境变量。秘密不应直接进入可共享键或日志；fork PR 只读或隔离缓存命名空间，防止缓存投毒。

#### 工程场景
锁定 Node 与包管理器版本，使用 frozen lockfile；缓存元数据记录生产者、输入摘要和校验和。抽样双跑比较输出，监控命中率、节省时间与失效原因。

#### 反例 / 踩坑
缓存 `node_modules` 却忽略平台和 ABI；把测试结果缓存但未声明时区、locale；不可信分支可覆盖主干构建缓存。

#### 资深回答模板
「我先让任务纯化和输入显式，再上缓存。权限、校验、抽样复算和一键禁用共同保证可信；缓存错一次的风险要纳入收益计算。」

#### 追问链
1. 原生依赖为什么需要平台维度？
2. 环境变量如何进入缓存键又不泄密？
3. 如何调查异常高命中却产物错误？
:::

### D8. 如何做到一次构建、多环境部署且配置一致？

::: details 参考答案
#### 基础结论
理想链路是不可变制品晋级：同一 JS/CSS 产物从测试推到生产，环境差异通过受控运行时配置注入。若必须按环境构建，也要保证源码提交、依赖和工具链一致并可追溯。

#### 原理深挖
构建期 `import.meta.env` 会被替换进 bundle，换环境通常需要重建；运行时 `config.json` 或入口注入可在启动时加载。客户端配置全部可见，密钥仍只能留在服务端。

#### 工程场景
定义带 schema 与版本的公开配置，启动前校验 API 基址、租户和开关；制品附 SBOM、SHA 和构建信息。部署系统原子更新配置与入口，冒烟检查二者版本兼容。

#### 反例 / 踩坑
测试通过后为生产重新安装依赖重建；容器启动脚本无差别替换压缩 JS 字符串；配置缓存时间长于 HTML，导致新入口读取旧 schema。

#### 资深回答模板
「我优先构建一次、制品晋级，环境差异走有 schema 的公开运行时配置。制品、配置和入口都有版本及兼容校验，秘密不进入浏览器。」

#### 追问链
1. 运行时配置加载失败如何降级？

### D9. 前端观测如何从日志升级到 SLO 与可行动告警？

::: details 参考答案
#### 基础结论
观测覆盖错误、性能、可用性和业务结果；SLO 用服务级指标定义可接受目标，告警围绕错误预算消耗和用户影响，而不是每条异常都叫醒值班。

#### 原理深挖
客户端采样会影响统计偏差；指标需按 release、路由、设备、网络和租户切片。平均值会掩盖长尾，性能常看 P75/P95；错误率分母应是会话、页面浏览或关键动作，必须先统一语义。

#### 工程场景
定义白屏率、资源加载成功率、关键动作成功率与 Core Web Vitals SLO；错误平台与 trace id、发布版本关联。告警包含影响范围、最近发布、仪表盘和回滚手册，并做合成探测补足无人访问时段。

#### 反例 / 踩坑
只采集 JS error 不看资源失败；每个 404 单独告警；采样后拿原始计数跨版本比较；告警没有 owner 和行动步骤。

#### 资深回答模板
「我从用户承诺反推 SLI/SLO，用错误预算决定告警灵敏度。每条告警必须能定位版本、影响人群并指向动作，否则只是日志噪声。」

#### 追问链

### D10. 前端供应链如何治理锁文件、脚本执行与漏洞审计？

::: details 参考答案
#### 基础结论
锁文件保证解析结果可复现，但不自动保证包可信。治理同时覆盖 registry、完整性、安装脚本、维护者变更、SBOM、许可证和漏洞可达性。

#### 原理深挖
包管理器会校验锁文件中的完整性信息，但上游账号接管、恶意新版本和 install script 仍是风险。审计严重度只是线索，要结合依赖是否进入生产、漏洞路径是否可达和可利用条件排序。

#### 工程场景
提交 lockfile，CI frozen install，锁定包管理器；高安全仓默认限制生命周期脚本并审批例外；使用私有代理、来源白名单、Renovate 小步升级、SBOM 和制品签名。

#### 反例 / 踩坑
为清 audit 数字盲目 `--force`；删除锁文件重装；只扫运行时依赖而忽略会执行代码的构建插件；长期 patch 没有退出计划。

#### 资深回答模板
「我把可复现、来源可信和漏洞处置分开治理。锁文件必需但不充分；升级按可达风险排序，安装脚本与构建依赖按生产代码同级审查。」

### D11. 前端发布如何设计秒级回滚，同时避免新旧资源混载？

::: details 参考答案
#### 基础结论
每次发布写入独立、不可变的 hash 资源目录，入口 HTML 指向该版本。回滚是原子切回上一入口或路由规则；旧资源保留至少覆盖缓存、灰度和回滚窗口。

#### 原理深挖
HTML 应短缓存或协商缓存，hash 资源可长期 immutable。回滚只对向后兼容的 API、配置和数据模型安全；Service Worker、SSR 缓存与 CDN 多层缓存会让入口切换并非天然瞬时。

#### 工程场景
发布前验证上一版本仍可访问；记录 manifest、配置 schema 和后端兼容矩阵。回滚后清或刷新入口层缓存，观测资源 404、白屏和业务恢复，并保留故障版本供取证。

#### 反例 / 踩坑
覆盖同名资源、发布后立即清旧目录、给 HTML 一年缓存、数据库破坏性变更与前端同步上线，都会让回滚失效。

#### 资深回答模板
「回滚能力在发布前设计：不可变资源、可切入口、旧版本保留和跨端兼容。按钮只是最后一步，我会定期演练并用指标确认恢复。」

1. Service Worker 如何影响回滚？

3. 何时应该前滚修复而不是回滚？

### D12. 构建性能如何从冷启动、增量和生产构建三条链路优化？

::: details 参考答案
#### 基础结论
先分冷启动、热更新、类型检查与生产构建，不用一个总耗时掩盖不同瓶颈。优化顺序是测阶段、找关键路径、减少输入和工作量，最后才升级硬件。

#### 原理深挖
插件数量不等于成本，关键是每个钩子处理的文件范围、是否串行 I/O、是否破坏缓存。Source Map、压缩、类型声明和大模块图可能主导生产构建；HMR 慢则常看 transform 与失效范围。

#### 工程场景
记录阶段计时与 CPU/内存 profile；过滤插件 id、缓存纯转换、拆类型检查与转译、monorepo 用任务图和远程缓存。升级 Vite 或插件前后用固定提交、机器和多次样本比较。

#### 反例 / 踩坑
关闭 Source Map 或类型检查只让数字好看却转移风险；用一次热缓存结果宣传冷构建；并行过度导致内存抖动和 CI OOM。

#### 资深回答模板
「我把构建当流水线 profile：先找耗时阶段和输入规模，再减少失效与重复工作。每个优化同时记录冷/热、资源峰值和正确性门禁。」

### D13. HMR 如何保证状态保留与副作用清理，而不是只追求不刷新？

::: details 参考答案
#### 基础结论
HMR 是开发反馈机制，模块必须明确接受更新、替换导出并清理旧副作用；无法安全热替换时整页刷新更正确。状态保留是选择，不是所有模块的默认权利。

#### 原理深挖
模块图从变更模块向 importer 传播，直到找到接受边界；若边界不存在则失效扩大。旧模块注册的事件、定时器和单例若未 dispose，会与新模块并存。

#### 工程场景
插件用 `handleHotUpdate` 返回准确模块集合；客户端用 `import.meta.hot.accept` 与 `dispose` 管理资源。状态模块定义可迁移 schema，组件修改后测试多次热更新监听数不增长。

#### 反例 / 踩坑
为了保状态吞掉不兼容更新；每次 HMR 重建 WebSocket 却不关闭旧连接；插件返回过宽模块集合导致全站抖动。

#### 资深回答模板
「HMR 先保证语义正确，再谈保状态。接受边界、dispose 和状态迁移是一组契约；边界不确定就全刷，并用重复热更新测试查泄漏。」

#### 追问链
1. 什么是 HMR 接受边界？
2. 模块单例为什么容易在 HMR 中泄漏？
3. 虚拟模块变化如何通知消费者？
:::

### D14. 微前端决策如何以组织与交付指标验收，而不是陷入机制选型？

::: details 参考答案
#### 基础结论
微前端的主要收益是团队独立交付和渐进迁移；若团队、领域和发布仍强耦合，技术拆分只会增加平台税。本章只保留决策与交付验收，具体机制见 [微前端题库](./12-microfrontend.md)。

#### 原理深挖
独立仓库或独立运行时不等于独立演进。要检查 API 兼容、共享设计系统、故障域、发布权限和跨团队变更频率；高频同步修改说明边界可能切错。

#### 工程场景
先用一个边界清晰模块试点，记录 lead time、独立发布率、跨团队阻塞、故障恢复和平台维护成本。设立宿主与子应用 SLA、版本兼容政策和退出方案。

#### 反例 / 踩坑
因「多个菜单」就拆微前端；用 EventBus 掩盖共享状态；没有平台 owner 却要求业务团队自行解决路由、监控和发布一致性。

#### 资深回答模板
「我先验证组织边界，再选技术。试点成功标准是独立交付更快且故障域更小；如果同步变更和平台成本上升，就回到模块化单体或 monorepo。」
