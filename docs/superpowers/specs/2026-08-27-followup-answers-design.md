# 题库追问答案补全设计

## 1. 背景与目标

当前站点包含 14 个题库模块、382 道主问题。主问题均有参考答案，但约 302 处「追问 / 追问链」只给出问题，展开后约有 600 个追问缺少参考答案。本次同时新增独立的「数据库与 Prisma」模块及 NestJS + Prisma 教程，使全站扩展为 15 个题库、409 道主问题。

本次改造目标：

- 为 15 个题库中的全部追问补充参考答案。
- 新增 27 道数据库与 Prisma 面试题，并在首次发布时同步提供主答案和追问答案。
- 新增独立的 NestJS + Prisma 实战教程。
- 每个追问答案控制在约 100～200 字。
- 答案能够独立回应追问，同时避免机械重复主答案。
- 保持页面可扫读，不让追问答案默认占据大量篇幅。
- 增加自动校验，防止追问漏答、错位或数量不一致。

## 3. 内容格式

### 3.1 单个追问

```md
**追问：** 一个简单 CRUD 项目是否也需要四层？

::: details 追问参考答案

不需要机械套用四层。分层数量应由业务复杂度、变化频率和团队协作成本决定。简单 CRUD 可以先保持页面、业务服务和请求层三个清晰边界；当规则复用、状态协调或测试隔离需求增加时，再逐步拆出领域层。关键不是层数，而是依赖方向明确、职责可以独立变化。

:::
```

### 3.2 多个追问

```md
**追问链：**

1. 业务要首屏更快又要更多个性化，如何取舍？
2. 指标暂时拿不到基线时如何决策？
3. 哪些决策应延迟到信息更充分时？

::: details 追问参考答案

**1. 业务要首屏更快又要更多个性化，如何取舍？**

先把首屏公共骨架和个性化内容拆成不同优先级。首屏只阻塞身份、权限和首要任务所需数据，低价值个性化模块延迟加载或在空闲时补齐；再以移动端 P75 LCP、关键任务完成时间和个性化转化指标共同验收。不能只追求首屏数字，否则可能牺牲真正影响业务的内容。

**2. 指标暂时拿不到基线时如何决策？**

先做可逆、低成本的决定，并同步建立最小观测。可以用实验环境、抽样日志和相似页面数据形成临时假设，但必须记录假设来源、置信度和复审时间。涉及不可逆数据结构或高迁移成本的方案应延后，避免用没有基线的精确数字包装主观判断。

**3. 哪些决策应延迟到信息更充分时？**

与规模强相关、替换成本高且当前没有真实压力的决策应延迟，例如过早分库分表、全量微前端改造或自研复杂平台。接口契约、安全基线、数据所有权等基础边界不能延迟，因为后续修复成本更高。判断标准是可逆性、信息增益和等待造成的风险，而不是单纯追求一次设计到位。

:::
```

### 3.3 格式约束

- 折叠标题统一使用 `::: details 追问参考答案`。
- 折叠区位于原追问或追问链之后、分隔线之前。
- 多个追问沿用原编号，答案标题与追问原文一致。
- 不在原有 `::: details 参考答案` 内嵌套新的折叠区。
- 不改变 Q / D 编号，不删除原追问，不修改站内锚点。

## 4. 答案质量标准

每个追问答案至少满足以下 3 项：

1. **直接结论：** 首句回应问题，不先堆背景。
2. **关键依据：** 说明原理、约束、协议语义或框架行为。
3. **工程落点：** 给出适用场景、判断条件、故障处理或验证方式。

根据题目需要补充：

- 方案取舍与不适用边界；
- 安全、性能、稳定性或可访问性风险；
- 指标口径和验证方法；
- 版本敏感说明；
- 最小代码或伪代码。

禁止：

- 只回答「视情况而定」。
- 简单复制主答案。
- 使用无法验证的绝对结论。
- 为凑字数加入无关背景。
- 杜撰框架 API、源码变量或默认行为。

## 7. 自动校验设计

扩展 `scripts/validate-question-bank.mjs`，增加追问答案校验：

1. 识别题目区块中的 `**追问：**` 和 `**追问链：**`。
2. 每处追问标记后必须存在一个 `::: details 追问参考答案`。
3. 折叠区必须正确闭合且内容非空。
4. 单追问必须有一个有效答案。
5. 追问链中的问题数量必须与答案标题数量一致。
6. 多追问答案标题应保留编号，并与原追问文本对应。
7. 检查重复答案标题、占位文案和明显过短答案。
8. 输出每个文件的主问题数、追问数和已回答数。

同步扩展 `scripts/validate-question-bank.test.mjs`，覆盖：

- 单追问正确匹配；
- 多追问正确匹配；
- 缺少折叠区；
- 折叠区未闭合；
- 问答数量不一致；
- 编号或文本错位；
- 空答案和占位文案；
- 代码块中的伪追问不参与统计。

## 8. 审查与验证

每批完成后执行：

```bash
pnpm docs:validate:test
MIN_TOTAL_QUESTIONS=400 MAX_TOTAL_QUESTIONS=420 EXPECTED_TOTAL_QUESTIONS=409 pnpm docs:check
```

内容审查分两层：

1. **规格审查：** 覆盖是否完整、格式是否一致、追问与答案是否一一对应。
2. **技术审查：** 技术事实、版本边界、工程场景、重复度和口述质量。

最终验收要求：

- 15 个模块的追问回答率为 100%。
- 原有 382 道主问题保持不变，新增数据库模块后总量精确为 409。
- 追问问题数与答案数完全一致。
- 无空答案、占位文案、重复 Q / D 编号。
- VitePress 构建和死链检查通过。
- GitHub Pages 部署成功，并抽查核心模块线上页面。

## 9. 风险与控制

### 内容体积增长

原题库与新增数据库模块合计约 650 个追问答案，预计增加大量 Markdown 内容。使用折叠区减少默认页面长度，但构建产物和搜索索引仍会增长。最终检查 chunk 体积和页面加载情况。

### 批量内容重复

相近追问容易生成同质答案。每批审查时检查同模块重复，并通过「基础概念 / 故障场景 / 架构取舍」明确职责。

### 版本事实漂移

Vue、Vite、NestJS、Prisma、Cursor、微前端框架和小程序能力变化较快。版本敏感答案应注明基线，并优先核对官方文档。

### 校验误判

Markdown 代码块中可能包含「追问」示例。解析逻辑必须跳过 fenced code block，并以题目区块和粗体标记为边界。
