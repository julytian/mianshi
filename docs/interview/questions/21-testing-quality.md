# 测试与质量保障面试题库

> **怎么用：** 普通题按「测试目标 → 隔离边界 → 断言证据 → 失败诊断」口述 1～2 分钟；深层题按「风险 → 测试组合 → 确定性 → CI 证据 → owner 与例外」展开。测试层级按反馈速度和风险选择，不把测试金字塔理解为固定比例，也不以重试、快照数量或单一覆盖率粉饰质量。

---

## 一、测试分层与 Vue 单元测试

### Q1. 如何区分 unit、component、integration 与 E2E 测试？

**考察点：** 测试边界、反馈速度、真实性、风险驱动和测试金字塔

::: details 参考答案

Unit 测试验证纯函数、类或 composable 等最小行为单元，依赖通常可控，运行最快；component 测试挂载一个 Vue 组件，覆盖 props、emits、插槽、DOM 与用户交互；integration 测试让多个真实模块协作，例如组件、Pinia、Router 与由 MSW 模拟的 HTTP 边界；E2E 在真实浏览器中从用户入口验证关键任务及前后端集成。

层级不是按工具名称或是否访问 DOM 划分，而是看真实参与者和替身边界。测试金字塔表达“越靠近底层通常越快、越容易定位，越靠近端到端越真实但越昂贵”的取舍，不是固定比例。应从支付、登录、权限、兼容性等风险反推组合：算法分支多用 unit，组件交互用 component，跨模块协议用 integration，少量关键旅程用 E2E；重复价值低的层级可以省略。

:::

**追问：** 为什么不能规定所有项目都必须保持 70% unit、20% integration、10% E2E？

::: details 追问参考答案

项目风险和架构不同：设计系统更需要组件与视觉证据，编排型应用的跨模块集成风险更高，纯计算库则适合大量 unit。固定比例容易诱导团队拆出没有业务价值的测试来凑数。更可靠的做法是按故障影响、发生概率、可探测性和反馈成本建立风险清单，记录每项由哪一层覆盖、谁负责，以及 CI 中保留了什么失败证据。

:::

### Q2. Vitest 中如何编写可靠的单元测试？

**考察点：** 测试结构、隔离、参数化、Mock 生命周期和确定性

::: details 参考答案

测试应围绕可观察行为组织，使用清晰的 arrange、act、assert，并让名称描述输入、动作和结果。纯逻辑优先用参数化测试覆盖等价类、边界值和错误路径；每个用例独立创建数据，固定时区、locale、随机种子和系统时间，不能依赖执行顺序或开发机环境。失败信息应能指出业务规则，而不只是“快照不同”。

Vitest 的 `vi.fn()` 适合记录协作者调用，`vi.spyOn()` 适合观察对象边界，模块 Mock 只用于难以控制的外部边界。用 `beforeEach` 重建状态，并按语义选择 `vi.clearAllMocks()`、`vi.resetAllMocks()` 或 `vi.restoreAllMocks()`；不要共享可变单例。优先注入时钟、ID 生成器和 API 客户端，避免全局 Mock。测试还应能在随机顺序、并行和 CI 环境中稳定运行。

:::

**追问：** `clearAllMocks`、`resetAllMocks` 与 `restoreAllMocks` 有什么区别？

::: details 追问参考答案

`clearAllMocks` 清除调用记录但保留 Mock 实现；`resetAllMocks` 还重置 Mock 实现，适合每例重新定义行为；`restoreAllMocks` 把通过 `spyOn` 等替换的原始实现恢复。机械地全部调用会掩盖生命周期设计问题。应明确测试是否只需清调用、是否要丢弃实现，以及是否修改了真实对象，并在每例建立独立状态。

:::

### Q3. Vue Test Utils 应如何测试组件而不绑定实现细节？

**考察点：** 用户可观察行为、语义查询、props、emits、插槽和 shallow 边界

::: details 参考答案

组件测试从公开契约出发：传入 props 和插槽，通过真实点击、输入等操作，断言可访问 DOM、状态提示和 emitted 事件。优先按 role、label、可见文本或稳定业务标识定位，避免依赖 CSS 层级、内部 ref、私有方法、组件实例字段和实现时序。重构 Composition API、拆分函数或调整 class 后，只要用户行为不变，测试就不应失败。

`mount` 能保留更真实的子组件交互，`shallowMount` 适合昂贵或独立验证的子树，但过度 stub 会漏掉 props、slot、provide/inject 和事件协作问题。Teleport、Transition 与全局插件应按测试目标配置。断言前只等待该动作真正引起的 Vue 更新或 Promise，不使用任意 sleep。失败时保留渲染 DOM 与关键输入，便于判断是产品回归还是测试错误。

:::

**追问：** 为什么直接调用 `wrapper.vm.submit()` 通常不是首选？

::: details 追问参考答案

它绕过按钮可用状态、表单校验、事件绑定和用户实际入口，并绑定组件内部方法名；重构实现会造成无意义失败，真实交互断裂却可能仍通过。优先触发用户可执行的 submit 或 click，再断言 UI、emits 或边界调用。只有公开暴露方法本身就是组件契约时，才直接调用并明确该契约。

:::

### Q4. 如何测试 Vue composable 的生命周期和响应式行为？

**考察点：** effect scope、组件宿主、依赖注入、清理和响应式断言

::: details 参考答案

无生命周期依赖的 composable 可直接调用，修改输入 ref 后通过返回的 ref、computed 或公开方法断言行为。依赖 `onMounted`、`onUnmounted`、provide/inject 或组件实例的 composable，应创建最小宿主组件并挂载，而不是伪造 Vue 内部上下文。涉及 `watch` 时，要根据 flush 策略等待 `nextTick`，并验证旧副作用是否通过 cleanup 停止。

浏览器 API、时钟和网络应通过参数或适配器注入；测试既验证成功值，也验证 loading、error、取消、重复调用和卸载清理。使用 `effectScope` 的独立响应式逻辑要显式 `stop()`，宿主组件则 `unmount()`，随后确认监听器、Observer、定时器和未完成请求没有继续改变状态。

:::

**追问：** composable 测试结束时只清空 Mock 为什么不够？

::: details 追问参考答案

Mock 调用记录不是运行资源。未卸载宿主或未停止 scope，可能留下 watcher、全局监听、定时器和异步回调，污染后续用例并形成偶发失败。测试应调用 `unmount()`、`scope.stop()` 或 composable 提供的 dispose，恢复被替换的全局对象，并断言取消信号或 remove 操作发生，从资源所有权上保证隔离。

:::

### Q5. fake timers、microtasks、`flushPromises` 与 `nextTick` 的边界是什么？

**考察点：** Event Loop、宏任务、微任务、Vue 调度和时间控制

::: details 参考答案

fake timers 主要接管 `setTimeout`、`setInterval` 和可配置的时间 API，适合 debounce、重试、超时和轮询；Promise 回调属于 microtask，通常不会因为只推进定时器就自动完成。`nextTick()` 等待 Vue 已排队的 DOM 更新，不能保证任意网络 Promise 链已结束；`flushPromises()` 尝试排空当前可达的 Promise 队列，但不会替你推进未来的 timer，也不能证明系统再无异步工作。

测试应按因果顺序驱动：触发动作，推进到目标时间，等待 timer 回调产生的 microtask，再等待 Vue 渲染，最后断言。具体可使用异步 timer API，必要时组合 `flushPromises()` 和 `nextTick()`，但不能用“多 flush 几次”碰运气。每例恢复真实 timers，并限制循环 timer 次数，避免未清理轮询导致挂起。

:::

**追问：** 为什么 `await nextTick()` 后 API 结果仍可能没有渲染？

::: details 追问参考答案

`nextTick` 只等待当时已经进入 Vue 更新队列的工作。如果 API Promise 尚未 resolve，其状态赋值还没发生，自然没有对应渲染可等。应先让该 Promise 受控完成或用 `flushPromises` 推进已有微任务，再等待 Vue 的 `nextTick`。若请求由 timer 触发，还必须先推进 timer；顺序应对应生产代码的真实因果链。

:::

## 二、状态、边界与浏览器测试

### Q6. Pinia 与 Vue Router 测试如何做到隔离？

**考察点：** `setActivePinia`、插件、memory history、导航就绪和状态泄漏

::: details 参考答案

Pinia 单元测试在每个用例创建新的 `createPinia()` 并 `setActivePinia`，需要 action 真执行时不要默认 stub；组件测试则通过 `global.plugins` 安装独立实例。若 Store 依赖 Pinia 插件，必须把插件安装到 app，不能只创建 Pinia。不要复用导入时就实例化的 Store，也不要在测试间共享可变 state。

Router 使用 `createMemoryHistory()` 和每例新的路由实例，配置最小但真实的 routes。测试导航组件时先 `router.push()`，再 `await router.isReady()` 后挂载或断言；路由守卫和 Store 协作由 integration 测试覆盖。不要 Mock `useRoute` 的内部响应式结构来代替关键导航测试，也不要依赖固定端口、浏览器历史或上一用例留下的当前位置。

:::

**追问：** `createTestingPinia` 中 action 被 stub 后可能漏掉什么问题？

::: details 追问参考答案

它适合组件只需验证“触发了哪个 action”的窄场景，但会跳过 action 内的状态变更、错误处理、并发控制和 API 协作。组件若依赖 action 执行后的 UI，全部 stub 可能产生假阳性。应明确该测试边界，必要时设置 `stubActions: false`，并在 Store 单元或组件集成测试中运行真实 action。

:::

### Q7. Mock、Stub、Fake 与 MSW 应如何选择？

**考察点：** 测试替身、协议边界、网络模拟、失败路径和实现耦合

::: details 参考答案

Stub 为调用返回预设结果，Mock 还验证交互，Fake 是具有简化但可工作的实现，例如内存仓库或可控时钟。选择取决于要隔离的边界：纯函数依赖可用 Stub；必须确认向支付网关发出一次幂等请求时可用 Mock；需要多步状态变化时 Fake 往往比大量调用脚本更稳。

MSW 在 `fetch` / XHR 的网络边界拦截请求，应用仍运行真实序列化、客户端、缓存和错误处理，适合 component / integration 测试。handler 应按 API 契约返回成功、校验失败、超时和乱序响应，并对未处理请求报错。不要 Mock 自己的 composable 或 API client 实现来测试使用它的代码，否则重构细节会驱动测试，且可能漏掉 URL、header、JSON 和状态码问题。

:::

**追问：** 什么时候内存 Fake 数据库可能比逐方法 Mock 更合适？

::: details 追问参考答案

当场景包含创建、查询、更新、唯一性或事务式状态变化时，逐方法 Mock 需要预编排调用顺序，容易与实现耦合；内存 Fake 可让多个操作围绕同一状态运行，更接近端口语义。但 Fake 不能冒充真实数据库的锁、隔离级别、SQL 方言和约束，关键差异仍需容器化集成测试或真实测试库覆盖。

:::

### Q8. API schema 测试与 consumer-driven contract 的边界是什么？

**考察点：** OpenAPI、契约验证、消费者期望、语义兼容和 E2E 边界

::: details 参考答案

Schema 契约测试检查请求、响应、状态码和字段是否符合 OpenAPI、JSON Schema 等机器可读规范，可在 provider CI 验证实现，也可据同一 schema 生成类型和 Mock。它擅长发现字段类型、必填项和枚举漂移，但 schema 合法不代表业务语义正确，例如金额单位、排序、权限和幂等性仍可能错误。

Consumer-driven contract 由具体消费者发布其真实使用的交互，provider 在 CI 验证这些期望，适合多团队独立发布和识别“某字段是否真的有人依赖”。它不是让消费者锁死 provider 的所有响应，也不能替代 provider 自身规则测试、少量跨系统 E2E 和版本治理。契约 broker 中应记录 consumer、provider、版本、环境与验证结果，部署决策基于实际制品关系。

:::

**追问：** API 响应通过 JSON Schema 后为什么前端仍可能失败？

::: details 追问参考答案

Schema 常只约束结构，可能没有表达时区、货币单位、排序稳定性、空值语义、权限过滤或跨字段不变量；示例和生产数据规模也可能不同。应把可机器表达的约束写入 schema，把关键语义写成 provider 规则测试和消费者契约，并用少量集成或 E2E 验证鉴权、网关与真实部署链路。

:::

### Q9. Playwright 如何编写稳定且隔离的 E2E 测试？

**考察点：** Locator、web-first assertions、storage state、并行隔离和诊断证据

::: details 参考答案

优先用 `getByRole`、`getByLabel`、`getByText` 等面向用户的 Locator，必要时使用稳定 `data-testid`，避免易变 CSS、XPath 和 `.nth()`。Locator 会在动作时重新解析元素；`expect(locator).toBeVisible()`、`toHaveText()` 等 web-first assertions 会在超时内重试目标条件。不要用固定 sleep，也不要先读取瞬时值再普通断言。

每个 test / worker 使用独立用户、租户、订单或 namespace，数据通过 API fixture 建立并清理。认证可复用 setup 生成的 storage state，但文件不得入库且不同角色、并行 worker 要隔离；测试内部对会修改的账号不能共享同一 state。保留 trace、截图、视频、console 和网络失败证据。重试只用于确认波动和收集证据，首轮失败仍应计入 flaky 治理，不能让最终通过掩盖问题。

:::

**追问：** 为什么 `page.waitForTimeout(2000)` 不是可靠的等待方式？

::: details 追问参考答案

固定等待与系统真实完成条件无关：快环境浪费时间，慢环境仍会失败，并把网络、动画和数据竞争变成概率问题。应等待用户可观察条件，例如按钮可用、响应完成后的提示、URL 或列表内容；优先用 Locator 动作和 web-first assertions 的自动等待。若业务有真正的时间规则，应控制服务器或虚拟时钟，而不是猜延迟。

:::

### Q10. 视觉回归测试如何减少噪声又保留价值？

**考察点：** 基线环境、动态区域、截图范围、阈值和人工审查

::: details 参考答案

视觉回归适合发现布局、颜色、字体、图标和响应式断点变化。基线必须绑定浏览器、操作系统、视口、DPR、字体和主题，数据、时区、locale、动画与网络保持确定；通常截稳定组件或关键页面区域，而不是无差别全站截图。基线更新属于代码变更，应有 owner 审查差异和原因。

时间、随机头像、广告、光标、骨架动画等动态区域优先通过固定 fixture、关闭动画、等待字体与图片完成来稳定；确实无法稳定的区域可局部 mask，但不能遮住核心交互。像素阈值只吸收已知渲染噪声，不能逐步调大到放过真实回归。视觉通过也不证明语义、键盘或业务正确，需与功能和可访问性测试组合。

:::

**追问：** 为什么把整个动态列表 mask 掉通常是错误做法？

::: details 追问参考答案

它虽然消除噪声，也同时隐藏行高、空状态、溢出、对齐和关键内容缺失等真实问题。应固定列表数据和排序，稳定时间与图片，只 mask 最小且无业务意义的动态像素。若区域无法确定化，应缩小截图边界或为布局写明确断言，并记录未覆盖风险和 owner。

:::

### Q11. 自动可访问性测试和覆盖率指标有哪些边界？

**考察点：** axe、人工测试、辅助技术、statement、branch 和 mutation coverage

::: details 参考答案

axe 等自动检查能稳定发现部分规则化问题，例如缺失可访问名称、明显对比度或 ARIA 关系错误，适合在 component 与 E2E CI 运行；但它无法判断名称是否准确、焦点顺序是否符合任务、动态通知是否可理解，也不能替代键盘、缩放、屏幕阅读器等人工和辅助技术（AT）测试。关键流程应记录测试的浏览器、AT 版本、操作步骤与 owner。

Statement coverage 表示执行过的语句比例，branch coverage 表示条件、switch、短路等分支是否走过；高覆盖率只说明执行，不说明断言有效。Mutation coverage 主动改变运算符、条件或返回值，观察测试能否杀死变异体，更接近测试敏感度，但成本更高且存在等价变异。门禁应按风险设置增量 statement / branch 要求，对核心规则选择 mutation，结合缺陷、评审和 E2E 证据，不能追求一个全局百分比。

:::

**追问：** 100% statement coverage 为什么仍可能漏掉严重缺陷？

::: details 追问参考答案

同一语句可能在多个条件分支下执行，statement 满分不代表真假分支、边界值和异常路径都验证；用例也可能只调用代码而没有有效断言。应查看 branch coverage、关键不变量和失败路径，并用 mutation testing 检查测试是否会对错误逻辑敏感。覆盖率是未测试区域的线索，不是正确性证明。

:::

## 三、深层场景题

### D1. 如何按风险设计前端测试组合？

::: details 参考答案

#### 基础结论

先列业务与技术风险，再为每项选择成本最低且能提供可信证据的测试层级。组合不追求固定金字塔比例，而追求关键风险有 owner、可重复验证、失败可定位，并避免同一行为在多层无价值重复。

#### 原理深挖

风险可按影响、发生概率和可探测性评估。Unit 快且定位准，但不能证明模块接线；component 覆盖 Vue 渲染与交互；integration 验证 Store、Router、网络协议等协作；E2E 最接近用户环境，却受数据、网络和部署影响。测试越真实不一定越好，若失败不能归因或反馈过慢，会降低团队响应速度。相反，全部 Mock 的 unit 即使很多，也无法为发布提供跨边界信心。

#### 工程场景

以结算页为例：金额和优惠规则用表驱动 unit 与属性测试；表单、错误提示和键盘操作用 component；组件、Pinia、Router 与 MSW 覆盖登录过期、库存冲突和重试；provider schema 与消费者契约约束 API；Playwright 只保留登录、下单、支付回跳等关键旅程，并用独立账号和订单。PR 跑快速层和受影响契约，合并后跑跨浏览器 E2E、视觉与 axe，灰度继续看真实错误。风险矩阵记录 owner、门禁、最后验证时间和证据链接。

#### 反例 / 踩坑

按 70/20/10 凑数量、所有层重复 happy path、为提高覆盖率测试 getter、Mock 掉 Router 和 API client 后宣称完成集成、把所有流程塞进一个超长 E2E，或失败时只重跑到绿色，都会制造虚假信心。

#### 资深回答模板

我先按影响、概率和可探测性排风险，再选择最便宜的可信证据：规则下沉 unit，Vue 行为放 component，协议与接线放 integration / contract，少量核心旅程放 E2E。每项绑定 owner、数据隔离和 CI 产物；定期结合线上缺陷调整组合，而不是维护固定比例。

:::

**追问链：**
1. 同一 happy path 是否需要四层都测试？
2. 如何判断应增加 E2E 还是 integration？
3. 风险矩阵应如何持续更新？

::: details 追问参考答案

**1. 同一 happy path 是否需要四层都测试？**

不必。只有不同层提供独立风险证据时才重复，例如金额规则的 unit 定位计算，E2E 证明支付链路接通。若 component 与 E2E 都只断言同一静态文本，应保留反馈更快或真实性更需要的一层，把资源用于异常、权限和兼容路径。

**2. 如何判断应增加 E2E 还是 integration？**

若风险来自浏览器、真实导航、部署配置、Cookie、跨源或前后端接线，E2E 更合适；若只需验证组件、Store、Router 和 HTTP 契约协作，integration 更快、更确定。先问最小真实边界在哪里，并要求失败产物能区分代码缺陷、环境问题与数据污染。

**3. 风险矩阵应如何持续更新？**

每次线上事故、逃逸缺陷、架构变更和 flaky 根因都回填矩阵，检查原有测试为什么未发现，并调整层级、门禁或可观测性。每项记录 owner、影响、覆盖证据、最后演练日期和残余风险；低价值测试应删除，不能只增不减。

:::

### D2. 如何测试异步竞态、取消和时间相关逻辑？

::: details 参考答案

#### 基础结论

把时间、请求完成顺序和取消信号变成可控制输入，显式验证“最新结果获胜、旧任务不再提交、卸载后无副作用”等不变量。不能依赖真实延迟、固定 sleep 或多次 flush 碰出目标顺序。

#### 原理深挖

前端异步链同时包含 timer task、Promise microtask、Vue scheduler 和浏览器事件。fake timers 只控制其中一部分，`flushPromises` 与 `nextTick` 也各有边界。竞态的关键不是“等待足够久”，而是构造 deferred Promise，让 A、B 按指定顺序完成，并观察 AbortSignal、请求 ID 或版本号如何阻止陈旧提交。取消通常是协作式的：发出 abort 不代表底层工作瞬间停止，代码仍需忽略随后到达的结果和错误。

#### 工程场景

搜索建议测试先发请求 A，再改关键词发 B；先 resolve B，断言显示 B，再 resolve A，断言界面不回退。验证新请求会 abort A，AbortError 不展示为业务失败，组件卸载后不更新状态。debounce 使用 fake timers 推进精确时间，再等待请求 Promise 和 Vue DOM；重试测试固定退避时钟和随机源，分别覆盖成功、上限、取消与离线。CI 记录随机种子、事件顺序和未处理 rejection。

#### 反例 / 踩坑

真实等 300 ms、统一 `await flushPromises()` 三次、只断言最后一次请求被调用、Mock 掉取消实现、把 AbortError 当普通错误、测试结束未恢复 timers，或用无限重试掩盖偶发顺序，都会让竞态测试不确定。

#### 资深回答模板

我把请求、时钟和随机源注入，使用 deferred Promise 精确排列完成顺序。测试不仅看最终值，还验证旧请求被取消、陈旧结果被丢弃、卸载后不提交，以及 timer、microtask、Vue 更新的因果顺序；失败时输出事件时间线和种子。

:::

**追问链：**
1. 调用 `abort()` 后为何仍要做陈旧结果保护？
2. fake timers 下应怎样推进 debounce 请求？
3. 如何让随机退避测试保持确定性？

::: details 追问参考答案

**1. 调用 `abort()` 后为何仍要做陈旧结果保护？**

并非所有客户端、适配器或后端工作都能立即取消，Promise 也可能已进入完成阶段；有些库会把取消转换成普通结果。应同时使用 AbortSignal 和请求序号或当前 key 校验，提交状态前确认仍是最新任务，并把取消与真实错误分开处理。

**2. fake timers 下应怎样推进 debounce 请求？**

先启用 fake timers 并触发输入，断言阈值前未请求；推进到阈值让 timer 回调发起请求，再受控 resolve Promise，最后等待对应 microtask 和 Vue `nextTick` 后断言 DOM。每例清理 pending timer 并恢复真实时钟，不能假设推进 timer 会自动完成 Promise。

**3. 如何让随机退避测试保持确定性？**

把随机源和时钟作为依赖，测试使用固定序列或种子，断言每次调度范围、上限与取消，而不是使用真实 `Math.random()`。失败日志输出种子和生成值；属性测试也固定并报告可复现种子，CI 重跑必须能够重现原始案例。

:::

### D3. 如何治理 E2E 数据隔离与 Flaky Test？

::: details 参考答案

#### 基础结论

Flaky Test 是产品、测试或环境中未受控状态的证据，不是简单“多重试几次”的问题。先保证每个 worker 的身份和数据 namespace 独立，再用 trace、网络、日志和重试对照分类根因，由明确 owner 在期限内修复或隔离。

#### 原理深挖

并行 E2E 会共享数据库、队列、缓存、账号、第三方沙箱和时间，任何全局状态都可能造成顺序依赖。storage state 只复用认证材料，不自动隔离服务器数据；多个测试修改同一用户时仍会竞争。Playwright 的自动等待只能等待 DOM 条件，无法修复后台最终一致性或错误测试数据。Retry 可揭示“首轮失败、后续通过”，但若 CI 只看最终状态，就会隐藏回归并污染可靠性指标。

#### 工程场景

为每个 worker 生成唯一租户、用户和订单前缀，通过 API fixture 建立最小数据并幂等清理；测试不依赖执行顺序和生产式共享种子库。角色分别生成短期 storage state，文件只留在 CI artifact，不提交仓库。失败保存首轮 trace、截图、console、请求响应摘要、后端 correlation ID 和数据 namespace。看板统计 flaky rate、首轮失败率和隔离时长；隔离测试需关联缺陷、owner 和到期日，关键流程不能长期 quarantine。

#### 反例 / 踩坑

全套共用 admin 账号、按固定名称查第一条订单、依赖上一用例清理、等待固定秒数、失败后全套重跑、将 retry 后通过视为绿色，或删除“不稳定但重要”的测试，都会把真实竞态和环境问题隐藏起来。

#### 资深回答模板

我先让 worker 拥有独立用户、租户和业务键，fixture 通过 API 幂等建数与清理。Playwright 使用语义 Locator 和 web-first assertion；首轮失败保留 trace、网络及服务端关联 ID。重试只辅助归因，flaky 仍计入门禁，并由 owner 按期限修复。

:::

**追问链：**
1. storage state 能否直接在所有并行测试间共享？
2. 允许 retry 后 CI 应如何判定？
3. 什么情况下可以暂时 quarantine 测试？

::: details 追问参考答案

**1. storage state 能否直接在所有并行测试间共享？**

只读角色且服务器状态互不影响时可以复用认证快照；若测试修改购物车、权限、密码或会话，复用同一账号会竞争。应按角色和 worker 生成独立身份或数据 namespace，限制 state 文件权限与有效期，并确保不含可长期使用的密钥。

**2. 允许 retry 后 CI 应如何判定？**

最终通过可避免偶发基础设施问题阻断所有发布，但首轮失败必须标记 flaky、保存两次证据并计入独立预算。超过阈值应阻断或降级相关测试组，不能只显示绿色。Retry 次数要小且固定，不能动态增加到通过。

**3. 什么情况下可以暂时 quarantine 测试？**

仅当根因已登记、测试本身阻断无关交付且有替代风险控制时暂时隔离，并设置 owner、修复期限和可见告警。支付、登录等唯一关键证据不能直接隔离；应先停止相关发布或增加人工验证。到期未修复要升级，而不是永久静默。

:::

### D4. 如何建立 API 契约和跨团队兼容机制？

::: details 参考答案

#### 基础结论

以版本化 schema 作为公共语法，以 consumer-driven contract 记录真实依赖，再配合 provider 规则测试和少量部署后 E2E。兼容决策必须绑定具体 consumer / provider 制品、环境、owner 和可回滚发布顺序。

#### 原理深挖

OpenAPI / JSON Schema 可验证结构，却不能完整表达权限、幂等、顺序、金额单位和跨字段语义；消费者契约能指出谁依赖什么，但消费者示例不应定义 provider 的全部业务。新增可选字段通常兼容，删除字段、收紧枚举、改变 null、默认值或语义可能破坏现有消费者。生成类型只能改善编译期，运行时仍需验证不可信响应。多团队独立部署还要考虑旧 consumer 与新 provider、新 consumer 与旧 provider 的双向窗口。

#### 工程场景

schema 在仓库版本化并做 breaking-change diff；前端基于稳定版本生成类型，同时在边界做运行时校验。消费者发布最小交互到 broker，provider CI 验证待发布版本，并以 can-I-deploy 类关系检查目标环境。破坏性变更采用 expand-and-contract：先增加兼容字段，provider 双写或双读，消费者迁移并上报使用率，确认旧版本退出后再删除。失败保存 schema diff、契约参与者版本和验证日志。

#### 反例 / 踩坑

共享一份手写 TypeScript interface 就称为契约、只验证示例 JSON、消费者断言 provider 响应所有无关字段、直接修改枚举含义、契约通过后跳过鉴权 E2E，或不知道哪个生产版本验证过，都会造成虚假兼容。

#### 资深回答模板

我用 schema 管结构，用消费者契约识别真实依赖，用 provider 规则测试管业务语义。CI 对具体制品做兼容 diff 和契约验证，发布采用 expand-and-contract；结果进入 broker 并绑定环境与 owner，少量 E2E 再验证网关、鉴权和部署接线。

:::

**追问链：**
1. 新增 enum 值一定向后兼容吗？
2. 谁应该拥有消费者契约？
3. 契约测试通过后为何还保留少量 E2E？

::: details 追问参考答案

**1. 新增 enum 值一定向后兼容吗？**

不一定。provider schema 看似只扩展，但旧消费者若使用穷举 switch 并在未知值抛错，就会失败。消费者应有 unknown 回退，provider 在投放新值前验证活跃消费者并灰度；类型生成也要避免让编译期穷举掩盖运行时开放集合。

**2. 谁应该拥有消费者契约？**

消费团队拥有其真实期望和测试数据，提供方拥有验证环境、业务规则及兼容承诺；平台团队可维护 broker 和门禁。契约必须有双方 owner，消费者不能借契约指定无关实现，提供方也不能在未验证活跃消费者时单方面宣布兼容。

**3. 契约测试通过后为何还保留少量 E2E？**

契约通常隔离验证单个交互，未覆盖 DNS、网关路由、TLS、认证配置、部署版本、真实序列化和跨服务编排。少量 E2E 验证这些接线与关键旅程，但不应重复所有字段组合；失败需能关联到具体制品和服务日志。

:::

### D5. 如何组合视觉回归、可访问性自动化与人工检查？

::: details 参考答案

#### 基础结论

视觉截图证明像素和布局变化，axe 等规则引擎证明部分机器可判定问题，键盘与辅助技术人工测试证明任务是否真正可完成。三类证据互补，任何一种都不能单独宣称界面可用或符合 WCAG。

#### 原理深挖

像素差异对字体、抗锯齿和动态内容敏感，却看不到语义树；自动 a11y 能发现缺少名称或错误 ARIA，却无法判断文案质量、焦点顺序、读屏上下文和认知负担。人工测试真实性高但成本大、难以每次全量执行。因此应把稳定规则左移到组件和 CI，把关键模板做确定化视觉基线，再按风险制定浏览器、键盘、缩放、高对比度与屏幕阅读器矩阵。

#### 工程场景

设计系统组件在 Vitest / 浏览器组件测试中运行 axe，并验证键盘事件和焦点；Playwright 对登录、表单错误、Modal、菜单和支付流程运行 axe 与键盘旅程。视觉基线固定浏览器、视口、DPR、字体、locale、主题和数据，关闭动画，仅 mask 最小动态区域。发布前由受训人员按清单测试 200% / 400% 缩放、仅键盘、焦点恢复和主流 AT；记录浏览器、AT 版本、证据、缺陷严重度与 owner。

#### 反例 / 踩坑

axe 零违规就宣布无障碍、整页 mask 动态内容、提高像素阈值消除失败、只用鼠标人工点一遍、用 ARIA 修补错误语义，或基线变化无人审查，都会让门禁失去意义。

#### 资深回答模板

我把规则化问题交给组件级 axe 和键盘测试，把布局主题交给确定化视觉回归，把任务完成和语义质量交给人工与 AT。每类测试明确能证明和不能证明什么，差异由 owner 审查，关键流程保留版本化证据。

:::

**追问链：**
1. 自动扫描零违规能否证明符合 WCAG？
2. 视觉基线频繁变化时怎样治理？
3. 人工 AT 测试应优先覆盖哪些流程？

::: details 追问参考答案

**1. 自动扫描零违规能否证明符合 WCAG？**

不能。自动工具只能判断可编码的一部分成功准则，且依赖当时 DOM 状态；它无法可靠评估替代文本是否合适、阅读和焦点顺序、错误恢复、读屏播报及任务认知。报告应标明规则集、扫描范围和未覆盖项，并保留人工、键盘和 AT 验证。

**2. 视觉基线频繁变化时怎样治理？**

先判断是环境噪声、动态数据还是产品确实频繁改动。固定字体、浏览器、数据、动画和截图时机，缩小到稳定组件；真实变化必须随 PR 说明并由组件 owner 审查。不能批量接受或持续放宽阈值，长期无价值的截图应删除或改成结构断言。

**3. 人工 AT 测试应优先覆盖哪些流程？**

优先覆盖登录、导航、搜索、表单错误、支付或提交、Modal / Menu / Combobox、动态通知和超时恢复等高影响流程，并包含仅键盘、缩放和至少目标用户常用的浏览器 / 屏幕阅读器组合。按用户数据和风险排期，不要求每次发布穷举全部组合。

:::

### D6. 如何使用属性测试、变异测试和故障注入提升测试有效性？

::: details 参考答案

#### 基础结论

属性测试扩大输入空间，变异测试检验断言敏感度，故障注入验证系统面对依赖失败时的韧性。三者针对不同盲区，应优先用于核心规则和高风险边界，并保证随机种子、变异报告和故障实验可复现。

#### 原理深挖

示例测试只验证挑选的点；属性测试描述对大量输入成立的不变量，并通过 shrinking 缩小失败案例。Mutation testing 修改条件、运算符或返回值，若测试仍通过则变异体存活，说明执行覆盖并未形成有效断言；等价变异需人工识别。故障注入则改变运行环境，例如超时、500、断网、乱序、存储配额或依赖降级，验证超时、重试、幂等、降级和可观测，而不是证明业务计算本身。

#### 工程场景

金额分摊可验证总和守恒、非负和顺序不影响结果，CI 输出 seed 与最小反例；权限和结算核心模块夜间运行 mutation，按存活变异体而非只看 score 排查。MSW 注入慢响应、断网、格式错误和乱序，测试取消与错误 UI；预发布环境对可逆依赖注入超时和限流，观察告警、trace、重试预算与恢复。实验有 blast radius、owner、停止条件和回滚，不直接在无隔离生产流量上尝试。

#### 反例 / 踩坑

随机失败却不记录 seed、属性只是重复示例、追求 mutation 100% 而忽略等价变异、故障注入没有停止开关、无限重试把下游故障放大，或只看 UI 最终恢复不查告警证据，都会增加成本而非信心。

#### 资深回答模板

我用属性测试验证核心不变量并保存最小反例，用变异测试抽查断言是否真的能发现错误，再通过可控故障注入验证超时、取消、降级和监控。三者按风险运行，固定 seed，限制影响范围，并由 owner 审查存活变异与实验结论。

:::

**追问链：**
1. 属性测试失败后如何保证 CI 可复现？
2. 存活变异体是否都必须补测试？
3. 前端故障注入应设置哪些安全边界？

::: details 追问参考答案

**1. 属性测试失败后如何保证 CI 可复现？**

框架应输出随机 seed、运行次数和 shrinking 后的最小反例，并把这些信息保存为 CI artifact。修复时先用同一 seed 或反例建立回归测试，再检查更广输入。重跑生成新 seed 不能替代复现原失败，否则会把随机逃逸误判为修复。

**2. 存活变异体是否都必须补测试？**

不一定。它可能等价、不可达或位于无业务价值的防御代码。应先分类：关键逻辑的可观察变化需要补断言；等价变异记录并配置忽略；无用代码可删除。Mutation score 用于发现薄弱点，不应成为逼迫团队编写低价值测试的单一 KPI。

**3. 前端故障注入应设置哪些安全边界？**

明确目标环境、流量范围、持续时间、owner、停止阈值和恢复方式；故障只通过可审计开关作用于测试租户或稳定实验桶。限制重试总量，避免真实支付和通知副作用，保留 trace 与告警证据。生产实验还需业务批准、实时监控和自动终止条件。

:::

### D7. 如何设计质量门禁、发布信心与紧急例外？

::: details 参考答案

#### 基础结论

质量门禁应把测试、静态检查、契约、覆盖率、可访问性和发布观测组合成可解释证据。每个门禁有风险来源、阈值、owner 和处置动作；紧急例外必须限时、可审计、有补偿控制，不能靠重试或口头承诺把红灯变绿。

#### 原理深挖

门禁过松会放过缺陷，过严或不稳定会诱导绕过。Statement / branch coverage 适合发现本次变更未执行区域，却不能证明断言质量；mutation 能提供更强信号但成本高。E2E、视觉与 a11y 也各有误报和盲区。因此采用分层证据和差异化策略：安全、支付、权限等关键域要求更强门禁；低风险文案可快速通道。发布信心还依赖制品一致性、灰度、监控与回滚，而不止合并前绿色。

#### 工程场景

PR 必须通过 typecheck、lint、unit / component、受影响 contract、增量 statement / branch 阈值和无未归因测试失败；核心规则定期 mutation。关键旅程跑 Playwright，首轮失败即记录 flaky，trace 等 artifact 留存。视觉差异由 owner 审批，axe 阻断明确严重度，人工 AT 按发布风险执行。合并后以同一制品灰度，检查错误率、任务成功率和契约兼容。紧急例外由业务与技术 owner 批准，记录原因、范围、补偿测试、feature flag / 回滚、到期时间和复盘任务。

#### 反例 / 踩坑

只看总 coverage、允许 retry 后全绿、批量接受视觉基线、关闭 flaky 测试无期限、构建后重新打包导致证据不对应制品、紧急发布永久跳过门禁，或告警无 owner，都会使 CI 失去审计价值。

#### 资深回答模板

我把门禁设计成风险证据链：快速静态与单元检查先阻断，契约和浏览器测试覆盖边界，覆盖率看增量分支，核心规则抽查 mutation；发布后同一制品灰度观测。每个失败有 owner 和 CI 证据，重试不抹掉首轮失败；例外限时、可回滚并强制复盘。

:::

**追问链：**
1. 覆盖率门禁应看全局还是增量？
2. CI 中 retry 后通过的测试能否算完全通过？
3. 紧急例外最少要记录哪些信息？

::: details 追问参考答案

**1. 覆盖率门禁应看全局还是增量？**

两者作用不同：全局阈值防止长期基线坍塌，增量 statement / branch 阈值约束本次新代码，避免历史债务阻止所有改动。关键域还应按文件或风险设置阈值并结合 mutation、断言评审；不能通过删除代码、排除文件或写无断言调用来过线。

**2. CI 中 retry 后通过的测试能否算完全通过？**

不能。它可以在策略允许时不阻断本次发布，但状态应标为 flaky，保留首轮和重试证据，计入可靠性预算并分配 owner。若相关流程高风险、flaky 超阈值或没有替代证据，应继续阻断。Retry 是诊断手段，不是成功定义。

**3. 紧急例外最少要记录哪些信息？**

至少记录被绕过的门禁、业务紧迫性、影响范围、风险接受人与技术 owner、现有 CI 证据、补偿测试或人工检查、feature flag / 回滚方案、监控指标、到期时间和复盘任务。例外到期自动失效，后续变更不能默认继承。

:::
