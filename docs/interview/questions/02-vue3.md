### Q1. `ref` 和 `reactive` 怎么选？Proxy 在中间扮演什么角色？

**考察点：** `ref` / `reactive`、Proxy、拆包习惯、类型推断

::: details 参考答案
`ref` 包一层 `{ value }`，适合基本类型、以及「整个值要被替换」的引用（对象也行）。`reactive` 直接对对象做深层 Proxy，解构会丢响应式，整表替换也不自然。

底层都是 Proxy（再加 `RefImpl` 等封装）：读属性时 track，写属性时 trigger。口述别停在「Proxy 比 Object.defineProperty 强」——要说清：**能监听增删、数组索引、`Map`/`Set`**，且惰性代理嵌套对象。

实战习惯：组件局部状态多数用 `ref`（含对象）；需要「一组字段一起改、很少整表替换」时用 `reactive`；跨 composable 传出去优先 `ref`，避免解构陷阱。TS 下 `ref` 推断往往更稳。

本题只保留响应式 API 选型；track/trigger、effect 栈和调度批处理见 D11，computed/watch 时序见 D12。
:::

**追问：**
1. 为什么对 `reactive` 做解构会丢响应？`toRefs` 解决了什么、没解决什么？
2. `ref` 在模板里为什么不用 `.value`，在 script 里又必须写？
3. 什么场景你会坚持用 `reactive` 而不是 `ref`？

::: details 追问参考答案

**1. 为什么对 `reactive` 做解构会丢响应？`toRefs` 解决了什么、没解决什么？**

`reactive` 的依赖追踪发生在 Proxy 属性访问上，`const { count } = state` 只把当时的值赋给局部变量，后续读写不再经过代理。`toRefs(state)` 会为现有可枚举属性创建相连的 ref，解构后仍能追踪和写回；但它不会让普通副本恢复响应，也不会自动覆盖调用后新增的属性，更不改变 props 只读约束。

**2. `ref` 在模板里为什么不用 `.value`，在 script 里又必须写？**

模板编译器会对渲染上下文中的顶层 ref 做自动拆包，所以 `count` 通常等价于读取 `count.value`；这是模板语法便利，不是 ref 本体变了。JavaScript 中没有这层编译转换，必须显式 `.value` 才能读取或替换容器值。还要注意数组、集合里的 ref 和深层表达式并非处处自动拆包，边界代码应以实际规则为准。

**3. 什么场景你会坚持用 `reactive` 而不是 `ref`？**

当状态天然是一组共同演进的字段、主要做属性级修改而很少整体替换时，我会用 `reactive`，例如表单草稿、坐标或筛选条件。它让 `state.name` 读写更直接，也便于把整个对象交给依赖属性访问的逻辑。前提是团队保持对象身份，不随意解构；若需要频繁整表替换、跨 composable 传递或表达可空值，我更倾向 `ref`。

:::

**踩坑：** `reactive({ list: [] })` 里 `state.list = newList` 能触发；但若你把 `list` 解构出去再赋新数组，响应式断了——这是高频事故。

### Q4. Vue3 组件通信你怎么画一张「选型图」？

**考察点：** props/emit、v-model、provide/inject、Pinia、事件总线取舍

::: details 参考答案
由近到远：

1. **父子**：props 下、emit / `v-model` 上；别用「改 prop」偷懒。
2. **跨多层但不全局**：`provide/inject`（主题、表单上下文、布局槽位 API）。
3. **跨页面/跨业务域共享**：Pinia（或等价 store）。
4. **兄弟且无共同业务状态**：抬到父组件，或抽 composable + store；慎用全局 EventBus。

口述强调边界：**通信方式是耦合声明**。props 是契约；provide 是「隐式契约」；store 是「应用级契约」。选错会变成「到处都能改、谁都不敢动」。
:::

**追问：**
1. 什么时候用 `defineModel` 比「prop + emit」更合适？
2. provide 一个响应式对象 vs provide 一个只读 computed，你怎么选？
3. 微前端或多应用共存时，全局 EventBus 为什么危险？

::: details 追问参考答案

**1. 什么时候用 `defineModel` 比「prop + emit」更合适？**

组件就是标准双向输入控件、契约明确对应 `modelValue` 与 `update:modelValue` 时，`defineModel` 能减少声明样板，并自然支持具名 model、默认值和转换器。若一次操作会产生多个业务事件、需要区分提交与草稿，或更新规则不该伪装成赋值，我会保留具名 prop 与 emit。它是编译宏和接口简写，不会取消单向数据流。

**2. provide 一个响应式对象 vs provide 一个只读 computed，你怎么选？**

先看后代需要的是完整状态还是受控视图。表单上下文要读取多字段并调用显式 action，可 provide `readonly(reactiveState)` 加修改方法；只暴露某个派生结论，例如权限或主题值，则 provide 只读 computed，依赖更窄、写入口更清楚。无论哪种都应定义 `InjectionKey` 契约，避免后代直接改共享对象造成来源不明。

**3. 微前端或多应用共存时，全局 EventBus 为什么危险？**

全局 EventBus 把应用实例、发布版本和生命周期混在一个隐式命名空间里，容易事件重名、重复订阅、卸载后残留回调，也无法可靠表达发送方与接收方的协议版本。微前端通信应由宿主提供有类型、可注销、可版本化的端口，或使用明确的共享状态协议；每轮 unmount 都释放订阅，不能把组件事件当跨应用总线。

:::

### Q5. `provide` / `inject` 的响应式与默认值怎么讲？

**考察点：** 注入键、只读约定、Symbol key、默认值工厂

::: details 参考答案
`provide(key, value)` 在祖先，`inject(key, default?)` 在后代。key 用 `InjectionKey<T>` 或 `Symbol`，避免字符串撞车。

响应式要点：provide 出去的若是 `ref`/`reactive`，后代改 `.value` 或属性会反映回去——这是能力也是坑。团队约定常见两种：

- provide `readonly(state)` + 显式方法（推荐）；
- 或 provide 一组函数 API（`openModal`），状态不直接暴露。

默认值：`inject(key, () => createDefault(), true)` 工厂形式避免共享同一对象引用。没有 provider 又没默认会得到 `undefined`——类型上要诚实。
:::

**追问：**
1. `app.provide` 和组件 `provide` 生命周期差异是什么？
2. inject 拿到的值在子组件里再 provide 出去，适合什么场景？
3. 和 React Context 对比，你怎么讲异同？

::: details 追问参考答案

**1. `app.provide` 和组件 `provide` 生命周期差异是什么？**

`app.provide` 绑定到某个应用实例，应用内所有后代都可注入，通常一直存活到 `app.unmount()`，适合路由、服务端口等应用级依赖。组件 `provide` 绑定提供者组件的树和生命周期，只对其后代可见，组件销毁后这条上下文边界也消失。SSR 和多应用场景不能复用带用户状态的全局值，应每个请求或应用创建。

**2. inject 拿到的值在子组件里再 provide 出去，适合什么场景？**

适合做上下文适配或分层覆盖，例如嵌套表单继承父级校验器，再覆盖字段路径；主题组件继承上层 token，只改局部密度。子组件应创建清晰的新契约，必要时用 computed 保持与父值联动，而不是无意义原样转发。还要避免直接修改祖先状态，优先暴露只读值和显式 action，防止依赖链难追踪。

**3. 和 React Context 对比，你怎么讲异同？**

两者都沿逻辑组件树向后代传递依赖，适合消除多层 props 透传，也都可能形成隐式耦合。差异在更新模型：Vue 注入 ref、reactive 或 computed 后按实际响应式依赖更新；React Context 的 provider value 身份变化会通知消费方，再由 React 协调渲染。它们都不是默认全局 store，频繁共享业务状态仍应设计边界。

:::

**踩坑：** 在异步组件或路由懒加载边界，inject 失败——不是 Vue 坏了，是 provider 树断了或 key 不一致。

### Q6. Composition API 生命周期和 Options 怎么对应？卸载时你清理什么？

**考察点：** `onMounted` 等、与 `setup` 执行时机、对称清理

::: details 参考答案
粗略映射：`beforeCreate`/`created` ≈ `setup` 本身；`onBeforeMount`/`onMounted`；`onBeforeUpdate`/`onUpdated`；`onBeforeUnmount`/`onUnmount`；另有 `onErrorCaptured`、`onActivated`/`onDeactivated`（keep-alive）、`onServerPrefetch`（SSR）。

`setup` 在组件实例创建时同步执行——此时还没有 DOM。DOM 相关放 `onMounted`；需要「更新后读布局」放 `onUpdated` 或 `nextTick`，并警惕死循环。

卸载对称清理：定时器、`addEventListener`、ResizeObserver、WebSocket、订阅 store 的外部监听、第三方实例 `destroy`。`watch`/`watchEffect` 在组件作用域内一般会自动停；**模块级或手动 `effectScope` 外的**要自己管。
:::

**追问：**
1. `onMounted` 里发请求，组件很快卸了，怎么避免 setState on unmounted？
2. `onUpdated` 滥用会导致什么？
3. keep-alive 场景下 `onUnmounted` 和 `onDeactivated` 谁会触发？

::: details 追问参考答案

**1. `onMounted` 里发请求，组件很快卸了，怎么避免 setState on unmounted？**

请求应有明确 owner：创建 `AbortController`，在 `onUnmounted` 或 `onScopeDispose` 中 abort，并在写状态前检查本轮请求是否仍有效。若参数连续变化，还要在 watcher 清理中取消上一轮，避免旧响应覆盖新值。Vue 对已卸载组件的渲染 effect 会停止，但网络、Promise 和业务回调不会自动消失，所以不能只靠组件不再渲染。

**2. `onUpdated` 滥用会导致什么？**

`onUpdated` 会在组件任意响应式更新并完成 DOM patch 后触发，范围比某个业务字段更宽。回调里无条件修改自身依赖，可能形成更新循环；反复测量和写布局还会造成强制同步布局与抖动。应优先用精确 `watch` 配合 `flush: 'post'`，只在确实需要整个组件更新后的 DOM 时使用，并保证逻辑幂等、读写分批。

**3. keep-alive 场景下 `onUnmounted` 和 `onDeactivated` 谁会触发？**

缓存组件切出时实例没有销毁，会触发 `onDeactivated`，不会触发 `onUnmounted`；重新进入时触发 `onActivated`。新 key 只会切换或创建另一缓存项，旧项不会自动移除；只有被 `include`/`exclude` 裁剪、被 `max` 淘汰或整个 KeepAlive 卸载等情况，实例才真正卸载。定时器通常在 deactivated 暂停，最终释放仍由 unmounted 兜底。

:::

### Q7. `<script setup>` 你怎么讲「它省了什么、藏了什么」？

**考察点：** 编译宏、自动暴露、`defineProps`/`defineEmits`、作用域

::: details 参考答案
`<script setup>` 是编译期语法糖：顶层绑定自动暴露给模板；`defineProps`/`defineEmits`/`defineExpose`/`defineModel`/`defineOptions` 是编译宏，不是运行时函数。

省了：`export default { setup() { return { ... } } }` 的样板、options 与 composition 混搭的心智负担。

藏了：组件名（常靠文件名 / `defineOptions`）、对父级暴露的实例方法必须 `defineExpose`、与普通 `<script>` 共存时的双脚本语义。

TS 用法：`defineProps<{ title: string }>()` + `withDefaults`；运行时声明与类型声明别重复打架。团队规范写清「宏能用哪些、禁止在非 setup 里调用」。
:::

**追问：**
1. 为什么 `defineProps` 不能赋值给外部变量再「条件调用」？
2. `defineExpose` 不写时，父组件 `ref` 能拿到什么？
3. 和普通 `setup()` 函数相比，测试方式有何变化？

::: details 追问参考答案

**1. 为什么 `defineProps` 不能赋值给外部变量再「条件调用」？**

`defineProps` 是 `<script setup>` 编译宏，编译器必须在顶层静态分析它，生成组件的 props 选项和 setup 绑定；它不是运行时可任意调用的函数。放进条件、循环或外部函数后，编译期无法确定稳定契约，也不存在可供分支执行的真实实现。需要条件行为时应保持 props 声明固定，再在普通运行时代码中按值分支。

**2. `defineExpose` 不写时，父组件 `ref` 能拿到什么？**

使用 `<script setup>` 的组件默认是关闭的，父组件通过模板 ref 得到公开实例，但不会自动看到子组件的顶层变量和方法。只有 `defineExpose({ focus, reset })` 明确列出的成员才成为公共接口；框架保留的公开实例能力不等于内部状态全部暴露。这样能减少父组件越界操控，库组件应把暴露面当稳定 API 设计和测试。

**3. 和普通 `setup()` 函数相比，测试方式有何变化？**

用户行为测试基本不变：都应挂载组件，通过 props、DOM 与 emitted 结果验证契约。差异主要在白盒入口：普通 `setup()` 返回值可能出现在公开实例上，而 `<script setup>` 默认不暴露，测试不能依赖内部变量；确需操控的能力要么通过 `defineExpose` 成为正式接口，要么把纯逻辑抽成 composable 单测，避免为测试扩大组件 API。

:::

**踩坑：** 把 `defineProps` 的返回值解构后丢响应性（应用 `toRefs` 或保持 `props.xxx` 访问）。

### Q8. Pinia 相对 Vuex，你怎么讲「为什么该换」和「怎么拆 store」？

**考察点：** store 设计、composition 写法、持久化、与组件状态边界

::: details 参考答案
Pinia：无 mutations 八股、TS 友好、支持多个 store、devtools 体验更好、composition 风格（`defineStore(id, () => { ... })`）与组件同一套心智。

拆分原则：

- **按业务域**（user / cart / permission），不是按页面堆一个 God Store；
- 组件私有 UI 状态（弹层开闭、输入中）别进 Pinia；
- 跨页共享、权限、缓存、需要时间旅行调试的进 store；
- store 里放「状态 + 改状态的动作」，别变成「随便 import 的工具箱」。

`storeToRefs` 解构 state/getters 保响应式；action 可以直接解构。持久化用插件，但要想清楚「哪些字段能进 localStorage、版本迁移怎么办」。

本题只保留客户端 store 拆分；SSR 跨请求隔离与安全序列化见 D4。
:::

**追问：**
1. setup store 里用 `watch`，和组件里 `watch` 生命周期有何差异？
2. 两个 store 互相调用，如何避免循环依赖？
3. Pinia 在 SSR 里为什么常常要「每请求一份」？

::: details 追问参考答案

**1. setup store 里用 `watch`，和组件里 `watch` 生命周期有何差异？**

组件 `setup` 中同步创建的 watcher 随组件卸载停止；setup store 的 watcher 不会因使用它的组件或 `app.unmount()` 自动销毁。单个 store 不再使用时调用 `$dispose()`；微应用整体卸载时，以当前 Pinia 3.x 官方 API 为基线，可调用 `disposePinia(pinia)` 停止容器 scope，旧版若无该导出应先确认或升级。两者都要接入主动 unmount 流程。

**2. 两个 store 互相调用，如何避免循环依赖？**

先消除顶层求值环：两个 setup store 不要在定义阶段互相读取对方状态或立即执行 action。可在 action 内按需调用另一个 store，或把共同规则提到无状态 service/composable；跨域流程由更高层协调器编排。若双方必须关联，明确单向依赖并通过参数或事件返回结果，避免 getter 相互读取造成初始化循环和难以测试的隐式耦合。

**3. Pinia 在 SSR 里为什么常常要「每请求一份」？**

服务端进程会并发处理不同用户；若复用模块级 Pinia，store 状态可能从一个请求泄漏到另一个请求，既造成水合不一致，也构成数据安全问题。正确做法是应用工厂按请求创建 app、router 和 Pinia，只序列化可公开的首屏状态，客户端在 mount 前恢复。组件外用 store 时还要显式传入本请求的 Pinia 上下文。

:::

**踩坑：** 直接 `const { list } = useXxxStore()` 解构 state，响应式丢失——经典坑，面试官很爱问。

### Q9. 路由守卫和懒加载路由，你会怎么设计权限流？

**考察点：** 全局/路由/组件守卫、动态路由、导航失败、分包

::: details 参考答案
守卫层次：`beforeEach` 做登录与权限总闸；路由 `meta` 声明角色/标题；`beforeEnter` 做单页特例；组件内 `onBeforeRouteLeave` 做未保存提示。

典型流：未登录 → 跳登录并带 `redirect`；已登录拉用户信息/菜单 → 动态 `addRoute` → `next({ ...to, replace: true })` 重进；注意**动态路由只加一次**的标志位，避免重复注册。

懒加载：`() => import('./views/Foo.vue')`，配合 Vite/Webpack 分包；重要首屏别全懒到「点哪下哪」却白屏过久——关键路径可预取。

失败处理：重复导航、守卫 `return false`、异步错误要用 `router.onError` / 导航结果 Promise 接住，别只 `console.log`。
:::

**追问：**
1. `next()` 多次调用或漏调用会怎样？Vue Router 4 推荐什么写法？
2. 动态路由刷新 404，根因通常是什么？
3. 懒加载 chunk 加载失败，产品层你怎么兜底？

::: details 追问参考答案

**1. `next()` 多次调用或漏调用会怎样？Vue Router 4 推荐什么写法？**

旧式守卫依赖 `next` 完成一次导航，漏调用会让导航悬空，多路径重复调用则可能得到警告或产生难判断的结果。Vue Router 4 仍兼容 `next`，但推荐直接 `return true`、`false`、路由位置，或抛出错误；异步守卫可 `await` 后返回。这样控制流只有一个返回出口，分支更容易由 TypeScript 和测试覆盖。

**2. 动态路由刷新 404，根因通常是什么？**

常见有两层：前端刷新后内存中的动态路由尚未根据用户权限恢复，首轮匹配就落到 404；或服务端没有 history fallback，把深链接当真实文件请求。应在路由 ready 前恢复用户与路由，再重进目标地址，同时配置网关回退到入口 HTML。还要区分真正无权限与尚未初始化，不能用无限重定向掩盖竞态。

**3. 懒加载 chunk 加载失败，产品层你怎么兜底？**

先区分离线、网络抖动和发布后旧 HTML 引用已删除 chunk。页面应显示可理解的错误态，允许有限次数重试；检测到版本失配时提示刷新并保留未提交数据，而不是自动无限 reload。发布侧保留旧静态资源一段时间、入口 HTML 短缓存、资源内容哈希长缓存，并把 chunk URL、版本和网络状态上报用于定位。

:::

**踩坑：** 在 `beforeEach` 里无条件 `await` 超重接口，每次跳转都卡死——权限数据应缓存，失效再拉。

### Q10. `keep-alive` 解决什么？和缓存策略相关的坑有哪些？

**考察点：** `include`/`exclude`/`max`、激活钩子、缓存粒度

::: details 参考答案
`keep-alive` 缓存组件实例，切走时走 `deactivated` 而不是销毁，回来走 `activated`，避免重复请求与滚动位置丢失（还要自己记 scroll）。

实战：列表 → 详情 → 回列表，列表包 `keep-alive`；用 `include` 白名单或路由 `meta.keepAlive` 控制，别全局无脑缓存所有页面。`max` 防止缓存无限涨。

注意：

- 被缓存的组件，`onUnmounted` 不会在切走时触发；
- key 变化会切换或创建新的缓存项，但不会自动移除旧项；
- 缓存的是组件实例，不是「路由 path」本身——抽象路由组件时要设计好 key；
- 内存与「过期数据」是两难：回来是否静默刷新，要产品策略。
:::

**追问：**
1. 同一组件多路由复用，如何让 keep-alive 分别缓存？
2. 缓存页里定时器该挂在 `activated` 还是 `mounted`？
3. 和手动「页面级状态存 Pinia」相比，keep-alive 的边界在哪？

::: details 追问参考答案

**1. 同一组件多路由复用，如何让 keep-alive 分别缓存？**

`KeepAlive` 按组件类型和 vnode key 识别缓存项；同一页面组件对应多个路由时，应在承载它的动态组件或 `RouterView` 插槽上提供稳定、能区分实例的 key，例如路由名加业务实体 id。不能用随机 key，否则每次都重建；也不宜无脑用完整 URL，把无关 query 变化变成新缓存。缓存身份应与期望保留的页面状态一致。

**2. 缓存页里定时器该挂在 `activated` 还是 `mounted`？**

如果定时器只应在页面可见活跃时运行，应在 `onActivated` 启动、`onDeactivated` 停止，并保证重复激活不会叠加。`onMounted` 对缓存实例通常只执行一次，若在那里永久启动，切走后仍会轮询和改状态。最终 `onUnmounted` 再清一次作为兜底；若是必须后台持续的应用级任务，应移到有明确 owner 的 store/service，而非页面组件。

**3. 和手动「页面级状态存 Pinia」相比，keep-alive 的边界在哪？**

`KeepAlive` 保存整个组件实例及本地响应式状态，适合短期导航返回、表单草稿和滚动上下文，但会保留 DOM 相关资源与副作用，需要容量和过期策略。Pinia 保存显式业务状态，不保存组件实例，适合跨页面、刷新恢复或多入口共享。长期数据应进 store，瞬时视图状态可缓存；两者都不能替代服务端缓存或持久化设计。

:::

### Q11. 异步组件与 `Suspense` 怎么配合？和路由懒加载是什么关系？

**考察点：** `defineAsyncComponent`、loading/error、Suspense 边界

::: details 参考答案
`defineAsyncComponent(() => import('./Heavy.vue'))` 做组件级懒加载，可配 `loadingComponent`、`errorComponent`、`delay`、`timeout`、`onError` 重试。

路由懒加载是「路由记录上的异步组件」；页面内异步组件是「局部重块」。二者可叠加。

`Suspense` 目前是 experimental，可用 `#fallback` 统一等待 UI，但没有自身错误槽；错误由父级 `onErrorCaptured` 处理。边界要小而清晰。

本题只保留「组件自治还是统一等待」的基础选型；Suspense 接管后哪些 async component 选项失效、`suspensible: false` 与错误处理见 D8。
:::

**追问：**
1. `async setup` 里顶层 await 失败，错误往哪冒？
2. 异步组件重试策略怎么设计才不像死循环？
3. 和 React lazy + Suspense 对比，你怎么讲？

::: details 追问参考答案

**1. `async setup` 里顶层 await 失败，错误往哪冒？**

`async setup` 或 `<script setup>` 顶层 await 的拒绝会进入 Vue 的组件错误处理链，祖先的 `onErrorCaptured` 可捕获，未被阻止时继续到 `app.config.errorHandler`。若它处于 Suspense 下，Suspense 负责等待与 fallback，但自身没有错误槽，错误 UI 仍需父级边界处理。业务上还应区分可预期请求失败，能就地恢复的不要全交给全局处理器。

**2. 异步组件重试策略怎么设计才不像死循环？**

在 `defineAsyncComponent` 的 `onError(error, retry, fail, attempts)` 中先分类：离线或瞬时网络错误可指数退避并限制次数；404、语法错误和版本不兼容应立即 fail。重试要可取消、记录 attempts，并给用户明确按钮。发布导致旧 chunk 失效时可提示刷新，但要保留草稿；绝不能在失败回调里无条件同步 retry，造成请求风暴。

**3. 和 React lazy + Suspense 对比，你怎么讲？**

两者都能异步加载组件，并由 Suspense 类边界显示等待 UI。Vue 的 `defineAsyncComponent` 还提供超时、加载态、错误态与重试；被 Vue Suspense 接管后，这些自治选项不再生效。Vue Suspense 当前仍是 experimental 且没有错误槽；React 通常也由独立 Error Boundary 处理错误，不能把等待态与错误态混为一谈。

:::

### Q12. 自定义指令你还用吗？什么场景指令比组件更合适？

**考察点：** 指令钩子、与组件边界、权限指令、清理

::: details 参考答案
指令适合「对单个 DOM 的命令式增强」：自动 focus、点击外关闭的底层绑定、曝光埋点、简单权限切 `display`（争议大）。组件适合有结构、有状态机、有插槽的 UI。

Vue3 指令钩子：`created`/`beforeMount`/`mounted`/`beforeUpdate`/`updated`/`beforeUnmount`/`unmounted`。务必在 `unmounted` 解绑监听。

趋势：能用 composable + 模板 ref 表达的，优先 composable——可测试、可组合、类型更好。指令留在「必须贴 DOM、且复用面极广」的薄封装。
:::

**追问：**
1. 权限指令 `v-permission` 和路由守卫、按钮级组件方案，你怎么分层？
2. 指令的 `binding.value` 更新时如何避免重复绑定？
3. 为什么说在指令里写复杂业务状态是坏味道？

::: details 追问参考答案

**1. 权限指令 `v-permission` 和路由守卫、按钮级组件方案，你怎么分层？**

路由守卫控制页面能否进入，但不是安全边界，服务端仍必须鉴权；按钮组件负责统一禁用、隐藏、提示原因等产品语义；指令只做少量现有 DOM 的展示增强。权限判定应来自同一领域函数，三层复用结果而非各写一套。涉及操作反馈和可访问性时优先组件，不能仅删除按钮就宣称权限已受保护。

**2. 指令的 `binding.value` 更新时如何避免重复绑定？**

在 `mounted` 创建一次监听器，把 handler、observer 或清理函数存到以元素为键的 `WeakMap`；`updated` 比较新旧值，只更新配置或先清理再重建，保证幂等；`unmounted` 必须释放。不要每次 updated 都匿名 `addEventListener`，因为无法精确 remove。若行为可表达为响应式参数，回调读取最新值也能减少重复绑定。

**3. 为什么说在指令里写复杂业务状态是坏味道？**

指令生命周期围绕 DOM，不提供清晰的组件 UI、props、事件和状态机边界。把请求、权限流程或多步骤交互塞进去，会让状态藏在元素和闭包里，难测试、难调试，也容易在更新和卸载时泄漏。指令应保持为薄 DOM 适配层；复杂状态放 composable 或组件，指令只接收结果并执行可逆的命令式操作。

:::

**踩坑：** 指令闭包抓住旧 vnode/el，更新后操作了过期 DOM——更新逻辑要幂等，卸载要彻底。

### Q13. Composable 怎么设计才不像「把 setup 剪贴到函数里」？

**考察点：** 输入输出约定、副作用边界、可测试性、命名

::: details 参考答案
好的 composable：

- **入参明确**（options 对象优于一长串位置参数）；
- **返回值稳定**（`{ state, getters, actions }` 或少量 ref）；
- **副作用可关闭**（返回 `stop`，或依赖调用方生命周期）；
- **不私藏全局单例**（除非名字就叫 `useGlobalXxx` 且文档写死）；
- **命名 `useXxx`**，一事一函数，别 `usePage` 三千行。

和组件：composable 管「状态与行为」，组件管「渲染与拼装」。和 Pinia：需要跨实例共享再上 store；仅单组件复用逻辑用 composable。

测试：对纯逻辑 composable 可直接调用；带 DOM/路由的用包装或注入 mock。
:::

**追问：**
1. composable 内部 `watch`，调用方多次调用会不会泄漏？
2. 如何避免「composable 互相调用」变成隐式依赖蜘蛛网？
3. 返回 `reactive` 大对象 vs 多个 `ref`，你怎么选？

::: details 追问参考答案

**1. composable 内部 `watch`，调用方多次调用会不会泄漏？**

每次调用都会创建独立 watcher；若在组件 `setup` 的同步阶段创建，它们随各自组件作用域停止，不等于泄漏，但重复调用仍会重复执行副作用。模块顶层、异步回调或 detached scope 中创建则必须显式 stop。公共 composable 应声明 owner，使用 `onScopeDispose` 清理外部资源，必要时返回 `stop`，并避免偷偷共享全局单例。

**2. 如何避免「composable 互相调用」变成隐式依赖蜘蛛网？**

让每个 composable 围绕单一能力，输入依赖通过参数或注入显式传入，输出保持稳定；跨能力编排放到页面级 composable，而不是底层互相 import。对请求客户端、时钟等外部依赖定义接口，测试可替换。发现 A 调 B、B 又读 A 时，应提取共同纯逻辑或建立单向层次，并用依赖图和命名约定约束。

**3. 返回 `reactive` 大对象 vs 多个 `ref`，你怎么选？**

字段共同组成一个稳定模型、调用方多用 `state.x` 且不需要解构时，可返回 reactive 对象；字段相对独立、需要选择性传递或直接解构时，多 ref 更清楚。大对象并不天然更慢，关键是依赖读取与更新范围。无论选择哪种，都要写明替换语义；若返回 reactive 又鼓励解构，应配 `toRefs`，避免隐式断链。

:::

### Q14. 列表性能：`key`、`v-memo`、`v-once` 你会怎么讲取舍？

**考察点：** diff key、原地复用、局部跳过更新

::: details 参考答案
- **`key`**：稳定且唯一的业务 id，禁止用随机数、谨慎用 index（插入/排序会错位，输入框状态乱串）。
- **`v-once`**：渲染一次后静态化，适合真·永不变更的块。
- **`v-memo`**：依赖数组不变则跳过该子树更新，适合大列表里「行 UI 复杂但多数行不变」。

先做对：虚拟列表（大数据）、减少组件层级、稳定 props、别在模板里造新对象/新函数当 prop（除非必要）。`v-memo`/`v-once` 是手术刀，用错会「界面不刷新」。

口述顺序：数据量 → key 策略 → 组件拆分 → 再谈 memo。

本题只保留 key 与 memo 选型；keyed diff、最长递增子序列和状态错位诊断见 D1。
:::

**追问：**
1. `key` 用 index 在「只追加、不删不排序」时是否可接受？
2. `v-memo` 依赖漏写会怎样？多写又怎样？
3. 和 `shallowRef` 控制大列表行数据，如何组合？

::: details 追问参考答案

**1. `key` 用 index 在「只追加、不删不排序」时是否可接受？**

若列表严格只在尾部追加、既不删除重排也不在中间插入，并且行没有需要跨更新保留的本地状态，index 可作为受限实现。但这个约束很容易被后续需求打破，筛选、分页合并或置顶都会让身份改变。工程上仍优先业务 id 或创建时稳定的临时 id，并把“只追加”写成数据层不变量和测试，而非口头假设。

**2. `v-memo` 依赖漏写会怎样？多写又怎样？**

依赖漏写时，真实影响子树的值变化却未进入数组，Vue 会跳过更新，界面显示旧数据，这是正确性缺陷。多写依赖通常不会错，但任一多余值频繁变化都会让 memo 失效，只剩比较开销。应把数组看成该子树渲染输入摘要，用测试覆盖每个状态变化；先确认瓶颈，再使用，不能靠它修复不稳定的数据设计。

**3. 和 `shallowRef` 控制大列表行数据，如何组合？**

可把大列表放进 `shallowRef`，采用不可变更新替换 `.value`，避免整棵数据深代理；行用稳定 key，`v-memo` 依赖行版本、选中态等真正影响渲染的值。局部编辑态可单独放细粒度 ref，提交时合并成新行。若原地改行，必须显式 `triggerRef`，但团队更应统一更新协议，防止漏触发与旧 UI。

:::

**踩坑：** 为了「强制刷新」用 `key=Math.random()`——性能与状态双杀。

### Q15. SSR / hydration 你怎么讲「水合失败」常见原因？

**考察点：** 服务端与客户端一致性、客户端 only 组件、时间/随机数

::: details 参考答案
SSR 产出 HTML，客户端用同一棵 vnode 树「粘」上去叫 hydration。两边 DOM 结构不一致就会警告甚至错位。

常见原因：

- 服务端没有、客户端有的分支（`window`、`localStorage`、时区、随机 id）；
- 非法 HTML 嵌套被浏览器改写（`<p>` 里塞 `<div>`）；
- 第三方只认浏览器的组件在 SSR 直接渲染；
- 文案/i18n 在两端数据源不同。

手段：`ClientOnly` 包裹、`onMounted` 再读浏览器 API、保证种子数据一致、关键块用 `Suspense`/异步数据在服务端就拉齐。Nuxt 等有现成约定，面试讲清「一致性约束」比背配置项重要。

本题只保留 mismatch 原因清单；确定性诊断、状态序列化和恢复成本见 D3。
:::

**追问：**
1. 为什么说「hydration mismatch 有时只是警告，却埋下事件绑错节点」？
2. SEO 页和强交互后台，对 SSR 的需求差在哪？
3. `data-server-rendered` / 现代 Vite SSR 链路你了解多少？（点到即可）

::: details 追问参考答案

**1. 为什么说「hydration mismatch 有时只是警告，却埋下事件绑错节点」？**

水合会尝试复用服务端 DOM 并把客户端 vnode、事件和组件实例对应上。结构不一致时，Vue 可能恢复、替换局部节点或继续绑定，因此页面看似正常，但节点身份、表单值、焦点或事件归属可能已偏离预期。生产不能只屏蔽警告，应复现首次 HTML、浏览器规范化 DOM 与客户端首棵 vnode，并验证点击、输入和后续更新。

**2. SEO 页和强交互后台，对 SSR 的需求差在哪？**

内容页看重搜索抓取、首屏可见内容和分享预览，SSR 或 SSG 通常收益明确，需保证关键正文服务端可输出。强交互后台多在登录后使用，SEO 弱，瓶颈常是接口、脚本与表格渲染；SSR 会增加服务端成本和水合复杂度，未必划算。应按页面选择渲染策略，而不是全站统一，并用 LCP、TTI 与运维成本验证。

**3. `data-server-rendered` / 现代 Vite SSR 链路你了解多少？（点到即可）**

早期 Vue 水合链路常借根节点标记识别服务端渲染内容；现代 Vue 3 通常由客户端 `createSSRApp` 配合 `mount` 进入 hydration，不应把某个 attribute 当稳定控制 API。Vite SSR 负责服务端加载入口、生成 HTML，并把请求级状态安全注入；客户端创建同构 app、恢复状态再挂载。具体标记属于版本实现，契约是首屏确定一致。

:::

### Q16. Vue2 → Vue3，你会强调哪些「真会疼」的差异？

**考察点：** 响应式系统、碎片、生命周期、破坏性 API、生态迁移

::: details 参考答案
真疼点优先说：

1. **响应式**：`Object.defineProperty` → Proxy；Vue2 的「新增属性要 `Vue.set`」故事结束，但出现 `ref` 拆包、`reactive` 解构新坑。
2. **碎片（Fragment）**：多根节点合法，`$el`、穿透样式、迁移期选择器要小心。
3. **生命周期改名**与 Composition API 成为一等公民。
4. **过滤器移除**、部分全局 API 改应用实例挂载（`createApp`）。
5. **插槽、v-model、.sync** 语义统一调整。
6. **包体积与 Tree-shaking**：按需更好，但构建链要跟上。

迁移策略：新功能 Composition + `<script setup>`；老模块允许 Options 共存；用兼容构建/迁移构建分期，别幻想 big bang。
:::

**追问：**
1. Vue2 里改数组下标的坑，在 Vue3 还存在吗？
2. 混入（mixin）在 Vue3 项目里你还建议用吗？
3. 生态（Vuex→Pinia、Vue Router 4、UI 库）你怎么排期？

::: details 追问参考答案

**1. Vue2 里改数组下标的坑，在 Vue3 还存在吗？**

Vue 3 使用 Proxy，可拦截数组索引赋值和 length 变化，所以 `arr[0] = value` 能触发响应式更新，不再需要 `Vue.set`。但新坑仍在身份和浅响应边界：解构出的普通值不会联动，`shallowRef` 内部原地修改不触发，raw 与 proxy 混用会影响比较。迁移时应删掉过时补丁，同时补测排序、截断与整表替换。

**2. 混入（mixin）在 Vue3 项目里你还建议用吗？**

新代码通常不建议 mixin，因为字段来源不透明、命名冲突、生命周期合并顺序难追踪，也不利于类型推断。优先用 composable 显式返回状态和方法，或用 provide/inject 表达上下文。遗留 mixin 不必一次重写，可在改需求时逐步抽离；应用级选项扩展只有在插件确有跨组件行为时使用，并把公共接口和清理责任写清。

**3. 生态（Vuex→Pinia、Vue Router 4、UI 库）你怎么排期？**

先做依赖清单和兼容矩阵，按阻塞链排序：构建工具与 Vue 核心先稳定，再升级 Router、状态库，最后处理 UI 库和业务页面。建立 Vue 2/3 可并行的适配层与关键链路测试，按业务域迁移，避免同时改状态、路由和视觉。高风险插件先做样板验证；每阶段保留回滚点，并用线上错误率和关键流程验收。

:::

### Q18. `Teleport` 解决什么？和「把弹层塞 body」手写有何差别？

**考察点：** 传送门、事件与逻辑归属、可访问性

::: details 参考答案
`Teleport` 把子树渲染到专用目标容器（如 `#teleports`），但**逻辑父组件不变**：props、provide、事件还在原组件树。解决弹层被 `overflow: hidden`、`z-index` 上下文卡住的问题。

比手写 `appendChild`：生命周期、更新、卸载由 Vue 管。SSR 时目标容器应只承载 Teleport；服务端与客户端首次 hydration 的 `disabled` 状态必须一致，可先都设为 `true`，再在 `onMounted` 后启用传送，避免 mismatch。

注意：无障碍焦点陷阱、滚动锁定、多弹层叠层管理仍要业务做；Teleport 只解决「挂载点」，不解决「弹层管理架构」。
:::

**追问：**
1. 多个 Teleport 到同一容器，顺序如何控？
2. `disabled` 属性适合什么响应式场景？
3. 和 `provide` 弹层服务（命令式 API）怎么组合？

::: details 追问参考答案

**1. 多个 Teleport 到同一容器，顺序如何控？**

多个 Teleport 可以追加到同一目标，基础 DOM 顺序通常受各自挂载顺序影响，但业务不应靠偶然顺序表达弹层层级。应由统一 overlay manager 分配 z-index、激活顺序和焦点栈，必要时在目标容器内设置明确层级节点。关闭时恢复焦点和滚动锁；若依赖框架新增的 defer 等能力，要注明版本，不把内部插入细节当稳定 API。

**2. `disabled` 属性适合什么响应式场景？**

`Teleport` 的 `disabled` 可切换子树在原位置渲染还是传送到目标。SSR 时服务端与客户端首次 hydration 必须取相同值，例如都为 `true`；客户端 `onMounted` 后再改为 `false` 启用传送。目标使用只承载 Teleport 的专用容器，不直接使用 `body`，以免服务端其他内容干扰水合。切换会移动真实 DOM，并不等于卸载。

**3. 和 `provide` 弹层服务（命令式 API）怎么组合？**

顶层提供 `open/close` 服务和响应式弹层栈，由 OverlayHost 统一渲染，再用 Teleport 放到只承载弹层的专用容器。调用方仅持有可关闭句柄，不直接 appendChild；宿主管理层级、焦点、滚动锁与卸载清理。SSR 入口预置同名空容器，并保证首次 hydration 状态一致。provide 负责访问协议，Teleport 只负责 DOM 挂载位置。

:::

### Q19. 错误处理：组件树、异步、全局，你怎么分层？

**考察点：** `onErrorCaptured`、`app.config.errorHandler`、路由与请求错误

::: details 参考答案
分层：

1. **局部**：`try/catch` 包住可预期失败（表单提交、解码）；
2. **组件边界**：`onErrorCaptured` / 错误边界组件，挡住子树渲染错误，展示降级 UI；
3. **全局**：`app.config.errorHandler` 打点上报；
4. **异步**：Promise 拒绝、`unhandledrejection`；路由 `router.onError`；请求层统一拦截器。

原则：渲染错误与业务错误分开；用户可见文案友好，细节进日志；别在 `errorHandler` 里再抛导致死循环。生产环境关掉暴露堆栈的调试 UI。

本题只保留错误分层；传播阻断、边界自身失败与多通道去重见 D9。
:::

**追问：**
1. `onErrorCaptured` 返回 `false` 意味着什么？
2. 异步组件加载失败和 setup 抛错，用户侧分别怎么呈现？
3. 和「接口 500」相比，你为什么常把后者放在数据层而不是 errorHandler？

::: details 追问参考答案

**1. `onErrorCaptured` 返回 `false` 意味着什么？**

返回 `false` 会阻止该错误继续沿祖先组件链传播，也不会再交给应用级 errorHandler。只有当前边界已经完成用户降级和可靠上报时才应阻断，否则容易把故障静默吞掉。边界自身渲染失败不会由自己兜住，仍需外层边界；同一错误若局部和全局都上报，要用指纹去重，而不是靠随意返回 false。

**2. 异步组件加载失败和 setup 抛错，用户侧分别怎么呈现？**

chunk 加载失败通常可识别为网络或版本问题，展示“重试/刷新”并保留用户数据；可由异步组件自治 errorComponent，或由父级错误边界统一处理。setup 抛错表示组件初始化失败，通常降级整个局部功能并提供返回入口。两者都进入 Vue 错误链，但恢复动作不同，日志应分别记录资源 URL、发布版本或组件链。

**3. 和「接口 500」相比，你为什么常把后者放在数据层而不是 errorHandler？**

接口 500 是可预期的业务 I/O 失败，数据层知道请求语义、重试条件、错误码和缓存策略，组件也能显示针对性的空态或重试。全局 Vue errorHandler 面向渲染、生命周期和 watcher 等未处理异常，缺少请求上下文。只有请求 Promise 未被处理并从 Vue 管理的回调抛出时才可能上浮，但仍应先在请求边界标准化。

:::

### Q21. `nextTick` 到底在等什么？和 `setTimeout(0)` 差在哪？

**考察点：** 更新队列、微任务、DOM 读取时机

::: details 参考答案
改了响应式数据，DOM 更新是异步批量的。`nextTick(fn)` 在 Vue 刷新完 DOM 更新队列后执行——通常挂在微任务（具体以实现为准，但语义是「Vue 的更新之后」）。

用它：改完数据后读 `scrollHeight`、聚焦输入框、测布局。

`setTimeout(0)` 是宏任务，更靠后，且与浏览器渲染、其他宏任务交错，不保证「刚好在 Vue patch 后第一时间」。能 `nextTick` 就别用 `setTimeout` 碰运气。

链式 `await nextTick()` 多次通常没必要；若仍读不到，先怀疑是不是还有别的异步（图片加载、子组件又改了一次状态）。
:::

**追问：**
1. 在 `watch` 默认 flush 下，回调里要不要再 `nextTick` 才能读 DOM？
2. `flush: 'sync'` 时 `nextTick` 的必要性如何变化？
3. 和浏览器 `requestAnimationFrame` 搭配测布局，你怎么排？

::: details 追问参考答案

**1. 在 `watch` 默认 flush 下，回调里要不要再 `nextTick` 才能读 DOM？**

默认 `flush: 'pre'` 的 watcher 会在父组件更新后、所属组件 DOM 更新前执行，所以回调直接读自身 DOM 通常还是旧值。可改为 `flush: 'post'`，语义最明确；也可在回调中 `await nextTick()` 等本轮 Vue 更新完成。若读取的是父组件 DOM 或另一个异步资源，时序要另行判断，不能把 nextTick 当所有异步完成的保证。

**2. `flush: 'sync'` 时 `nextTick` 的必要性如何变化？**

sync watcher 在响应式写入时立即执行，不等待组件更新队列，也不享受常规批处理，因此此时 DOM 更确定还是旧的。若回调要读本次写入对应的新 DOM，仍需 `await nextTick()`，或更适合改用 post watcher。sync 只应用于极少量必须同步失效的逻辑；对数组或高频状态使用会逐次触发，增加递归和性能风险。

**3. 和浏览器 `requestAnimationFrame` 搭配测布局，你怎么排？**

先修改响应式状态，再 `await nextTick()`，确保 Vue 已完成本轮 DOM patch；如果只需读取当前布局，此时通常即可测量。若需要等浏览器进入下一帧、样式计算或与动画写入分离，再 await 一次 `requestAnimationFrame` 后读，写操作可放下一帧避免读写交错。图片、字体加载仍是独立异步，需监听其完成，不能靠多等几帧猜。

:::

### Q22. `shallowRef` / `shallowReactive` 什么时候必须上手？

**考察点：** 浅层响应、大对象、不可变数据、性能

::: details 参考答案
默认深层 Proxy 对巨对象（编辑器文档、图表 option、协议树）成本高，且你本来就整树替换。

- **`shallowRef`**：只追踪 `.value` 替换；内部字段改了不触发——适合配合不可变更新（新对象赋值）。
- **`shallowReactive`**：只代理第一层属性；嵌套对象不是响应式。

典型：ECharts option、大 JSON、第三方实例句柄、虚拟列表的 raw items。

代价：团队要统一「怎么更新」；有人原地 `obj.a.b = 1` 会静默不刷新——文档和 lint 约定要跟上。

本题只保留浅响应选型；代理身份风险见 D6，大表虚拟化与响应式降级组合见 D14。
:::

**追问：**
1. `triggerRef` 解决什么场景？
2. `markRaw` 和 shallow 系列如何配合避开响应式？
3. 把 pinia state 设为 shallow 有什么注意点？

::: details 追问参考答案

**1. `triggerRef` 解决什么场景？**

`shallowRef` 只追踪 `.value` 的替换，若为性能或第三方 API 必须原地修改内部对象，依赖它的 effect 不会自动运行；`triggerRef(ref)` 可显式通知消费者重新执行。它适合少数有明确批处理边界的场景，例如一次修改大文档后统一刷新。若到处手动 trigger，说明更新协议太脆弱，通常应改为不可变替换或细分状态。

**2. `markRaw` 和 shallow 系列如何配合避开响应式？**

第三方类实例可先 `markRaw(instance)`，再放入 `shallowRef`，既避免实例被代理，也只在句柄替换时更新；大不可变树通常只需 shallowRef。`markRaw` 只标记传入对象本身，未标记的嵌套对象进入 reactive 图后仍可能代理，因此不能假设整棵树永久 raw。边界应集中封装，比较业务实体仍优先稳定 id。

**3. 把 pinia state 设为 shallow 有什么注意点？**

Pinia setup store 可以返回 shallowRef 等状态，但内部原地修改不会触发订阅和视图更新，持久化、devtools 与 `$subscribe` 的观察粒度也可能不同于普通深响应状态。团队必须统一根替换或显式 trigger 的协议，并验证 SSR 序列化与 hydration。仅对有性能证据的大不可变数据使用，普通业务 state 不应为“可能更快”而浅化。

:::

**踩坑：** 对 `shallowRef` 的对象做原地 mutate 再期望视图更新——不会，除非 `triggerRef` 或换新 `.value`。

### Q23. `toRef` / `toRefs` / `toValue` 解决什么问题？

**考察点：** 保持响应式的引用、props 解构、规范化取值

::: details 参考答案
- **`toRef(obj, 'key')`**：得到指向该属性的 ref，改它等于改原对象字段；
- **`toRefs(obj)`**：对象每个属性都变成 ref，适合展开给模板或下游且保持链接；
- **`toValue`/`unref`**：统一取出 ref 或裸值，写库 API 时友好。

经典场景：`const props = defineProps(...)` 后若要解构，用 `toRefs(props)`；或单个 `toRef(props, 'id')` 传给 composable。

注意：对 props 的 ref **不建议写回去**（单向数据流）；`toRefs` 对数组/纯 Map 不是万能锤。
:::

**追问：**
1. `toRef` 一个不存在的属性会发生什么？
2. composable 参数接受 `MaybeRef` 时，内部如何写才地道？
3. 和直接传整个 `props` 对象相比，`toRefs` 的可读性 trade-off？

::: details 追问参考答案

**1. `toRef` 一个不存在的属性会发生什么？**

属性签名 `toRef(obj, key)` 会创建与该属性相连的 ref，即使属性当前不存在，读取通常为 `undefined`，给 `.value` 赋值会写回原对象并触发其响应式规则。这也是它与 `toRefs` 的差异：`toRefs` 只转换调用时对象已有的可枚举属性。若对象是只读 props，写回仍会警告或失败，不能借 toRef 绕过单向数据流。

**2. composable 参数接受 `MaybeRef` 时，内部如何写才地道？**

若参数允许值、ref 或 getter，优先声明 `MaybeRefOrGetter<T>`，在需要读取时用 `toValue(source)` 统一取值；需要持续追踪则在 computed 或 watch getter 中调用，不能在外面先取一次变成快照。只支持 ref 与值时 `unref` 足够。API 文档应说明 getter 是否会重复执行、何时建立依赖，避免调用方误以为普通函数只运行一次。

**3. 和直接传整个 `props` 对象相比，`toRefs` 的可读性 trade-off？**

传整个 props 保留来源，代码中 `props.userId` 清楚表明是组件输入，也避免批量制造 ref；但 composable 会依赖整个组件契约，复用和测试较差。传单个 `toRef(props, 'userId')` 让依赖最显式。`toRefs` 适合确实要解构多个字段时，但字段多会增加 `.value` 和命名噪声，且不包含未来新增属性，不能机械全转。

:::

### Q24. `effectScope` 是干什么的？和组件作用域有何关系？

**考察点：** 副作用分组生命周期、库作者场景、手动 stop

::: details 参考答案
`effectScope` 把若干 `computed`/`watch`/`watchEffect` 收进一个作用域，`scope.stop()` 一次性停掉。组件实例自带一个作用域，所以组件内的 watch 会随卸载停——这是「免费的」。

你需要手动 scope 的场景：

- 在组件外创建可销毁的「迷你响应式运行时」；
- 库代码按需挂载/卸载一批 effect；
- 热切换某种模式时拆掉旧监听。

面试讲清：**不是日常业务标配**，但是「别把监听挂全局却忘了停」的正规武器。

本题只保留 effectScope API 判断；组件树外副作用 owner、异步创建与 detached scope 约束见 D2。
:::

**追问：**
1. `effectScope(true)` 分离模式你听说过吗？解决什么？
2. 和 `watch` 返回的 `stop` 函数相比，何时用 scope 更好？
3. Pinia/VueUse 里哪些 API 默默用了 scope 思维？

::: details 追问参考答案

**1. `effectScope(true)` 分离模式你听说过吗？解决什么？**

传 `true` 创建 detached scope，它不会被当前活动父 scope 收集，因此父组件或父 scope 停止时，它仍可继续运行。适合生命周期独立于创建者的共享服务、缓存或微应用实例，但必须指定新的 owner，并在其 dispose 时手动 `scope.stop()`。它不是防止意外卸载的快捷开关；没有明确销毁路径的 detached scope 基本就是泄漏候选。

**2. 和 `watch` 返回的 `stop` 函数相比，何时用 scope 更好？**

只有一个 watcher 时直接持有 stop 最简单。一个功能会创建多个 watch、watchEffect、computed，并且需要作为整体反复启动和销毁时，effectScope 能统一归组，减少遗漏；DOM 监听、Socket 等非响应式资源仍需通过 `onScopeDispose` 注册清理。scope 管的是生命周期集合，不替代每种资源自己的释放 API，也不应为组件内普通监听重复套层。

**3. Pinia/VueUse 里哪些 API 默默用了 scope 思维？**

Pinia 用作用域把 store 的响应式副作用归到容器或 store 生命周期，许多 VueUse composable 用 `tryOnScopeDispose` 一类机制在当前作用域结束时自动移除监听、计时器和观察者。面试不必承诺具体私有实现或所有版本一致，稳定结论是这些库都要求“创建资源时绑定 owner”。调用方仍要看 API 文档，组件外使用时可能需要手动 stop。

:::

### Q25. 组件上的 `v-model` / `defineModel` 怎么讲清楚？

**考察点：** model 参数、多 v-model、修饰符、单向数据流

::: details 参考答案
Vue3：默认 `modelValue` + `update:modelValue`；多 v-model 如 `v-model:title`。`defineModel()` 是 `<script setup>` 宏，少写样板，本质仍是 prop + emit。

子组件应 emit 更新，而不是直接改 prop（对象内部字段被改是现实中的灰色地带——团队应禁止「偷改」）。

修饰符：`defineModel({ set(v) { ... } })` 或传统 `modelModifiers`；`.trim` 等可在边界消化。

取舍：表单控件库用 v-model 提升一致性；过度多 v-model 会让接口难懂——有时不如具名 props/events。
:::

**追问：**
1. `v-model` 和一个 prop + 多个 emit 并存时如何避免打架？
2. 自定义修饰符如何设计才不魔法？
3. 和「全受控 / 非受控」输入组件设计如何对应？

::: details 追问参考答案

**1. `v-model` 和一个 prop + 多个 emit 并存时如何避免打架？**

先定义唯一的值变更通道：`v-model` 只负责当前值与 `update:modelValue`，`change`、`blur`、`submit` 等事件表达时机或业务动作，不再重复携带另一套真值。父组件以 modelValue 为单一事实来源，子组件不要同时 watch prop 写本地、再 watch 本地回传。确需草稿态时，明确区分 draft 与 committed，并只在指定事件提交。

**2. 自定义修饰符如何设计才不魔法？**

修饰符应是少量、可组合、无隐藏 I/O 的边界转换，例如 trim、number 或固定格式归一化；命名直接说明行为，并在类型和文档中列出。通过 `defineModel` 的 modifiers 与 get/set 实现时，要保证转换幂等、输入法组合期间不破坏文本。涉及异步校验、远程提交或多字段联动时用显式 prop/event，不塞进看不见的修饰符。

**3. 和「全受控 / 非受控」输入组件设计如何对应？**

Vue 的 prop 加 `update:modelValue` 接近受控组件：父级持有真值，子级每次变更都发事件。非受控模式则由子组件持有初始值后的内部状态，只在提交时通知父级。组件库最好选一种主模式；若两者兼容，要区分 `modelValue` 与 `defaultValue`，禁止运行中模糊切换，并明确 reset、校验和表单提交读取哪一份状态。

:::

**踩坑：** 子组件 `watch` prop 同步到本地 state，再 `watch` 本地 emit 回去——稍不注意振荡，需要「来源标记」或只在事件里 emit。

### Q26. 作用域插槽你会怎么讲「数据往上、UI 往下」？

**考察点：** 默认插槽 vs 作用域插槽、渲染委托、性能注意

::: details 参考答案
普通插槽：父传模板片段给子。作用域插槽：子把数据交回父的模板，父决定怎么渲染——典型 Table 列、`v-for` 列表壳、Select 自定义 option。

心智：**子管数据与行为，父管外观**。API 设计时，作用域字段要稳定、文档化，别一年改三次解构字段名。

性能：作用域插槽本质是函数，父级更新可能带动重渲染；重列表里避免在插槽内堆重逻辑，能子组件内聚就内聚。
:::

**追问：**
1. `v-slot` 简写与动态插槽名怎么用？
2. 插槽兜底内容写在子组件还是父组件？
3. 和 `render props` 思想如何类比？

::: details 追问参考答案

**1. `v-slot` 简写与动态插槽名怎么用？**

具名插槽可写 `#header`，作用域参数写成 `#default="{ item }"`；动态名使用 `#[slotName]`，表达式受动态指令参数规则约束。动态插槽适合 schema 表格按列名渲染，但名字应有稳定协议和类型辅助，避免任意字符串导致静默回退。默认插槽在组件标签上简写时要注意与多个具名插槽的作用域边界，优先保持结构清晰。

**2. 插槽兜底内容写在子组件还是父组件？**

通用、体现组件基本可用性的默认内容放子组件，例如按钮默认图标位、空列表提示；与具体业务和页面语气相关的内容由父组件传入。子组件兜底应可访问、可本地化，并在提供插槽后完全可替换。若没有内容代表不同状态，不应只靠 `$slots` 猜业务，应用显式 prop 区分 loading、empty 和 error，避免契约含糊。

**3. 和 `render props` 思想如何类比？**

两者都是“逻辑提供方把状态和操作交给渲染调用方”：Vue 作用域插槽通过 slot props，React render props 通过函数参数。它们适合无头组件，让子级管理选择、分页等行为，父级决定 UI。代价也类似：嵌套过深、参数契约易漂移、每次渲染有函数调用。应保持字段稳定，复杂逻辑下沉，避免插槽内重复昂贵计算。

:::

### Q27. Fragment（多根节点）带来哪些连锁影响？

**考察点：** 多根、$attrs、样式穿透、迁移

::: details 参考答案
Vue3 允许组件多根。好处：少包一层无意义 `div`，DOM 更干净。代价：

- 模板里 `ref` 在组件上拿到的是组件实例，多根没有单一根 `$el` 的老假设；
- 非 props 的 attribute 默认不再自动落到「唯一根」——多根时要明确 `inheritAttrs` 与 `v-bind="$attrs"` 落点；
- CSS 选择器、测试查询若假设单根会碎。

口述：多根是能力，不是强制；需要统一落 attrs 或过渡动画时，包一层仍合理。
:::

**追问：**
1. 过渡 `<Transition>` 对多根子节点有什么要求？
2. 多根与 `Teleport` 组合时，事件冒泡路径怎么想？
3. 设计系统组件为什么常常仍保留单根？

::: details 追问参考答案

**1. 过渡 `<Transition>` 对多根子节点有什么要求？**

`Transition` 面向单个进入或离开的元素/组件根；被包组件若渲染多个非注释根，框架无法把一次过渡稳定施加到唯一目标。需要给可动画区域增加明确单根，或对列表使用 `TransitionGroup` 并为子项提供稳定 key。不要为了消警告随意包 div，应同时评估布局；动画目标、持续时间和离场状态都应属于清晰的 DOM 边界。

**2. 多根与 `Teleport` 组合时，事件冒泡路径怎么想？**

Vue 组件事件由子组件显式 emit 给父组件，不是 DOM 事件，也不会沿组件树自动冒泡。Teleport 只移动 DOM，provide/inject、props 和 emit 的逻辑父子关系不变；原生点击则按实际 DOM 树冒泡到传送目标的祖先。多根只是增加实际 DOM 落点，因此事件委托、outside-click 和 stopPropagation 必须按真实 DOM 路径设计，不能混用两套模型。

**3. 设计系统组件为什么常常仍保留单根？**

单根能提供稳定的 attrs、class/style、ref、过渡和布局落点，使组件库契约更可预测，也便于消费者覆盖样式和测试。多根适合确实没有统一语义容器的结构，但需要手动分配 `$attrs`，容易让事件和无障碍属性落错节点。是否加根应由语义和 API 决定；不能为了单根制造破坏列表、表格或可访问性的无意义 DOM。

:::

### Q28. Attributes 透传（fallthrough）规则你怎么讲？

**考察点：** `inheritAttrs`、`class`/`style` 合并、禁用透传

::: details 参考答案
未在 props 声明的 attribute（含事件监听）会落到组件根元素；`class`/`style` 与根上已有值合并。`inheritAttrs: false`（或 `defineOptions`）后手动 `v-bind="$attrs"` 到内部真实输入框——表单库标配。

多根节点时，自动透传行为要特别小心，官方建议显式绑定。

事件：`emits` 声明过的不会进 attrs；未声明的原生监听可能当 attrs 落下——既要利用也要避免重复绑定。
:::

**追问：**
1. 为什么封装 `<input>` 时几乎总是 `inheritAttrs: false`？
2. `$attrs` 在 `<script setup>` 里怎么拿？
3. `class` 透传与 CSS modules / scoped 叠加时注意什么？

::: details 追问参考答案

**1. 为什么封装 `<input>` 时几乎总是 `inheritAttrs: false`？**

表单组件的根节点常是带标签、错误提示的 wrapper，若自动透传，`name`、`disabled`、`aria-*` 和原生监听会错误落到 div。关闭 inheritAttrs 后，可把 `$attrs` 精确绑定到内部 input，并把 class/style 是否作用于外壳单独设计。还要声明组件自身 emits，避免同一监听既由组件触发又作为原生 attrs 下落，造成双调用。

**2. `$attrs` 在 `<script setup>` 里怎么拿？**

使用公开的 `useAttrs()` 获取 attrs 对象，模板中也可直接访问 `$attrs`。它反映未声明为 props 或 emits 的透传属性，但不是为了像普通 reactive 状态那样深度 watch；若需要基于某属性执行响应式副作用，更应把它声明为 prop。库组件通常在模板中 `v-bind="attrs"` 到明确节点，并通过 `defineOptions({ inheritAttrs: false })` 关闭自动落点。

**3. `class` 透传与 CSS modules / scoped 叠加时注意什么？**

透传 class 会与目标根节点已有 class 合并，但 scoped CSS 依赖编译生成的作用域 attribute，CSS Modules 则把本地类名映射为哈希；外部 class 并不会自动获得组件内部作用域。应明确哪个节点接收用户 class，并提供稳定的 part/class API，而不是让消费者依赖内部哈希。多根或手动 `$attrs` 时尤其要测试合并顺序和样式优先级。

:::

**踩坑：** 忘记声明 `emits`，父组件 `@change` 又透传到原生 DOM，出现「回调触发两次」类问题。

### Q29. 卸载清理：你会列一张「必须对称」的清单吗？

**考察点：** 监听、观察者、订阅、第三方实例、abort

::: details 参考答案
清单（口述用）：

1. `window`/`document` 事件；
2. `setInterval` / `setTimeout`；
3. `IntersectionObserver` / `MutationObserver` / `ResizeObserver`；
4. WebSocket / EventSource / 订阅总线；
5. 请求用 `AbortController`；
6. 第三方地图/图表 `dispose`；
7. 手动创建的 `effectScope`；
8. 对外部 DOM 的 class/style 污染还原。

组件内 `watch` 通常自动清；**全局单例上注册的回调**不会。keep-alive 场景用 `onDeactivated` 暂停、`onActivated` 恢复，而不是只写 `onUnmounted`。

原则：谁申请谁释放；composable 返回 `stop`；Code Review 把「有注册无释放」当缺陷。

本题只保留清理清单；微应用可重复 mount/unmount 状态机、app 单次挂载约束见 D5。
:::

**追问：**
1. 如何用一次实战事故证明清理的重要性？
2. `onUnmounted` 里再触发异步完成回调，怎么防？
3. 热更新（HMR）下重复挂载会放大哪些泄漏？

::: details 追问参考答案

**1. 如何用一次实战事故证明清理的重要性？**

我会按证据链描述：列表页每进入一次都注册一个 window resize 和 Socket 订阅，离开只清 DOM；重复导航后一次消息触发多次请求，内存和 CPU 持续上涨。通过监听器计数、堆快照和重复 mount/unmount 脚本定位，再把注册与 disposer 放同一 composable，用 onScopeDispose 收口。最后以多轮导航后监听数归零和请求单次触发验收。

**2. `onUnmounted` 里再触发异步完成回调，怎么防？**

卸载钩子应做取消而非启动新的无主异步：请求用 AbortController，订阅先解除，Promise 回调检查 generation token 或 disposed 标志，只有当前实例仍有效才写状态。必须异步上报时使用独立、可容忍页面离开的通道，不再捕获组件和 DOM。Vue 停止渲染 effect 不会取消外部 Promise，因此防线应建在资源 owner 与回调入口。

**3. 热更新（HMR）下重复挂载会放大哪些泄漏？**

HMR 会替换模块或重建组件，模块顶层 EventBus、计时器、watcher、Socket 和全局样式若没有 dispose，会每次更新再注册一份，开发环境很快出现多次回调。组件作用域资源通常能随重载清理，但模块级资源要使用构建工具提供的 hot dispose 钩子。HMR 暴露的问题不应都归咎开发模式，它常提示生产重复挂载也会泄漏。

:::

### Q30. Vue2 Options 与 Composition，迁移期你怎么带团队？

**考察点：** 混用策略、代码评审、培训、边界

::: details 参考答案
务实策略：

- 新文件默认 `<script setup>` + TS；
- 老 Options 不强制一夜重写；抽出逻辑时优先 composable，Options 的 `setup()` 也可调用；
- 禁止新建 mixin；用 composable 替代；
- 约定目录：`composables/`、`stores/`、`components/` 职责清晰；
- Review 看点：副作用清理、props 解构、任意 `any`、store 滥用。

成功标准不是「全员背 API」，而是「改需求时知道状态放哪、别再复制粘贴 200 行 methods」。
:::

**追问：**
1. 如何说服「Options 也能写很好」的同事尝试 Composition？
2. 测试策略要不要随 Composition 调整？
3. 设计系统底座用 Options 还是 Composition，你怎么定？

::: details 追问参考答案

**1. 如何说服「Options 也能写很好」的同事尝试 Composition？**

先承认 Options 能写出高质量代码，不把语法偏好当能力高低。选择一个横跨 data、computed、watch、生命周期且需要复用的真实功能做小范围重构，对比逻辑内聚、类型推断和测试复用，再让团队评审结果。新模块默认 Composition，稳定旧模块不为迁移而迁移；用数据和维护体验推动，而不是一次性禁令或 API 清单。

**2. 测试策略要不要随 Composition 调整？**

组件测试仍以用户可见行为为主，不因写法变化就改成测内部 ref。Composition 提供了把纯状态逻辑抽成 composable 单测的机会，但涉及 provide、生命周期、DOM 或路由时仍需通过宿主组件挂载。迁移期保持原有契约测试作为保护，再补 composable 边界与清理测试。目标是更好隔离职责，不是为了覆盖率把实现细节全部暴露。

**3. 设计系统底座用 Options 还是 Composition，你怎么定？**

看维护团队、类型要求、复用模式和目标 Vue 版本。Vue 3 新设计系统通常选 `<script setup>` 与 Composition，便于共享无头逻辑、泛型和副作用清理；若既有 Options 组件稳定且无收益，不必机械重写。无论语法，真正稳定的是 props、emits、slots、attrs 与可访问性契约，还要验证打包 tree-shaking、类型声明和多版本兼容。

:::

### Q31. 依赖注入 + 表单上下文：你会怎么设计 `Form` / `FormItem`？

**考察点：** provide/inject 实战、联动校验、解耦

::: details 参考答案
经典模式：`Form` provide `{ model, rules, registerField, validate }`；`FormItem` inject 后注册字段、显示错误；输入组件通过 `FormItem` 或直接 `v-model` 到 model。

优点：减少 props 打洞。风险：隐式依赖导致离开 Form 就不能用——输入组件应能独立受控；Form 只是增强。

校验：字段级与表单级；异步校验要可取消；卸载字段要 unregister，避免校验到幽灵字段。

这题用来展示你能把 provide/inject、composable、单向数据流合成一个「库作者级」方案。
:::

**追问：**
1. 嵌套 Form（子表单）如何设计 context 覆盖？
2. 和纯 `veebox`/`vuelidate` 思路比，自研 Form 的边界在哪？
3. TypeScript 如何给 `model` 路径做较真类型？

::: details 追问参考答案

**1. 嵌套 Form（子表单）如何设计 context 覆盖？**

子 Form inject 父 context，创建自己的 context 再 provide，字段路径可加前缀，校验和提交默认在本地收口；是否向父级注册为一个复合字段要显式配置。不能原样修改父 context，否则字段注销、错误定位和禁用态会混乱。生命周期中成对 register/unregister，并用 Symbol InjectionKey 区分协议，测试嵌套提交、重置与动态移除。

**2. 和纯 `veebox`/`vuelidate` 思路比，自研 Form 的边界在哪？**

先做需求差距评估：成熟库已处理异步校验、字段数组、触发时机、可访问性和边界案例，自研只有在领域协议、性能或 UI 约束明显不匹配时才合理。可以自研薄适配层，把业务 schema 映射到库，而非重造校验引擎。若决定自研，必须承担类型、国际化、SSR、动态字段和长期升级测试成本，不能只实现演示路径。

**3. TypeScript 如何给 `model` 路径做较真类型？**

可用条件类型递归生成 `Path<T>` 与 `PathValue<T, P>`，让字段名和对应值类型关联；数组、可选字段和递归深度需设边界，避免编译器性能恶化。大型表单库通常在“完全精确”与可维护性间折中：常用一两层强类型，动态 schema 提供泛型逃生口。运行时仍要校验路径存在，类型不能替代外部数据验证。

:::

### Q32. 渲染函数 / JSX 与模板，你会怎么选？

**考察点：** 表达力、优化、团队习惯、动态性

::: details 参考答案
模板：可读、编译优化友好、设计师与多数前端更熟。JSX/h：高动态（schema 表单、递归协议树、按数据生成复杂 children）更顺手。

团队项目里可以混用：90% 模板，少数工具组件 JSX。不要宗教战争。注意 JSX 项目的 typings、pragma、以及和 `v-model`/插槽语法的对应写法。

口述加一句：选择标准是「变更时谁更好改、谁更少 bug」，不是「哪个更酷」。
:::

**追问：**
1. 递归组件用模板和 JSX 各自注意什么？
2. 函数式组件在 Vue3 还值得追吗？
3. 编译优化在 JSX 上打几折，你怎么向老板解释？

::: details 追问参考答案

**1. 递归组件用模板和 JSX 各自注意什么？**

模板递归可利用组件名自引用，结构直观，但必须有终止条件、稳定 key，并避免每层深 watch；JSX 对动态节点类型、schema 分派更灵活，也更容易在一个函数里堆积复杂分支。两者都要防循环数据和超深树，必要时虚拟化或迭代展开。选型看协议动态程度和团队可读性，不以“递归就必须 JSX”为规则。

**2. 函数式组件在 Vue3 还值得追吗？**

Vue 3 普通组件实例成本已降低，函数式组件不再天然带来显著性能优势。它仍适合真正无状态、只根据 props/context 返回 vnode 的极薄适配器，尤其在 TSX 工具代码中；但没有组件实例和完整生命周期，复杂逻辑反而难管理。应通过 profile 证明热路径收益，不能为了“更快”把可维护组件全部改成函数。

**3. 编译优化在 JSX 上打几折，你怎么向老板解释？**

不能给固定折扣。模板是受限 DSL，编译器更容易静态分析并生成 PatchFlags、静态提升和 Block Tree 提示；JSX 是通用 JavaScript，动态性更强，通常可提取的信息较少，但插件和手工稳定引用仍能优化。应以具体组件的生产 trace、更新次数和 patch 成本比较；选择首先服务可维护性，再对已证实的热点调整。

:::

### Q33. 自定义指令 vs 组件 vs composable：曝光埋点你会怎么落地？

**考察点：** 交叉观察器、复用边界、性能与隐私

::: details 参考答案
常见落地：

- **指令 `v-expose`**：绑定 el，IntersectionObserver 一次，上报后可 disconnect；适合「加点就行」；
- **composable `useExposure(elRef)`**：可测试、可传阈值配置，复杂 SPA 更干净；
- **组件**：还要带 UI 时才包。

注意：列表虚拟滚动下「看见再上报」与 DOM 回收；页面隐藏时暂停；采样与去重；合规（别上报敏感文案）。

这题看你能否把 API 选型讲成工程决策，而不是背钩子名。
:::

**追问：**
1. 上报失败重试放哪一层？
2. keep-alive 页面重复曝光怎么去重？
3. 指令方案如何做 TypeScript 类型增强？

::: details 追问参考答案

**1. 上报失败重试放哪一层？**

重试应放统一遥测客户端或队列层，而非每个指令和组件各自实现。该层负责批量、退避、次数上限、离线缓存、幂等事件 id 和页面离开时发送策略；调用方只提交结构化事件。对 4xx 等不可重试错误立即丢弃并告警，对网络失败有限重试。还要设置容量和过期时间，避免埋点队列反过来占满存储或主线程。

**2. keep-alive 页面重复曝光怎么去重？**

先和产品定义“每次激活算一次”还是“会话内实体只算一次”。以页面实例、实体 id、曝光位和会话生成去重键；deactivated 时暂停 observer，activated 时恢复并按规则开启新轮次。虚拟列表 DOM 会复用，不能以元素身份去重，应以数据身份和可见阈值、持续时间判断。去重状态需要容量和过期策略，避免长期增长。

**3. 指令方案如何做 TypeScript 类型增强？**

为指令值定义明确接口，例如 `{ id: string; threshold?: number }`，用 `Directive<HTMLElement, ExposureOptions>` 标注实现；需要模板全局提示时，在 Vue 的 `ComponentCustomProperties` 中声明 `vExpose`。元素内部状态优先存入 WeakMap。类型只保证编译期，运行时仍要校验动态 schema 参数。

:::

**踩坑：** 在 `updated` 里 new Observer 却不 disconnect，列表一滚内存起飞。

### Q34. 应用级性能：你从哪些 Vue 特有抓手切入？

**考察点：** 组件粒度、异步边界、稳定 props、devtools

::: details 参考答案

1. 如何证明某次优化有效（指标）？
2. `Object.freeze` 在 Vue3 还有位置吗？

::: details 追问参考答案

**1. 如何证明某次优化有效（指标）？**

先固定可重复场景和数据规模，记录生产构建下的基线：交互可看 INP、长任务和组件更新时间，滚动看丢帧与内存，首屏看 LCP 与水合耗时。一次只改变一个因素，低端设备多次采样并比较 P75/P95，同时跑正确性回归。Vue Devtools 解释谁在更新，浏览器 trace 解释 JS、布局或绘制，最终再用 RUM 验证真实用户。

**2. `Object.freeze` 在 Vue3 还有位置吗？**

有，但不是通用响应式优化开关。冻结对象表达运行时不可修改的 JavaScript 契约，可用于常量配置或外部不可变数据，Vue 不应被期待追踪其内部变更。对大数据仅想避免深代理时，`shallowRef` 或 `markRaw` 的意图通常更明确，并允许根替换。freeze 是浅冻结，嵌套仍可能可变；还可能让第三方库写入时报错。

**3. 和 Web Worker 拆计算相比，你何时才上？**

只有 profile 证明主线程被可并行的 CPU 密集计算长期占用，例如大规模解析、搜索或布局预计算，我才用 Worker。组件更新、DOM patch 和样式布局不能直接搬过去；还要计算结构化克隆、消息序列化和同步协议成本。先减少无效计算、缓存派生和分片调度，Worker 方案需支持取消、版本号和过期结果丢弃，并以 INP 收益验收。

:::

### Q35. 从零搭一个中型 Vue3 应用，目录与约定你怎么定？

**考察点：** 工程组织、边界、可演进

::: details 参考答案
口述一版够用的骨架：

- `src/views` 页面、`components` 通用 UI、`composables`、`stores`、`api`、`router`、`utils`、`assets`；

- 路径别名、`unplugin-auto-import` 可适度，避免魔法到新人找不到定义；
- 环境变量前缀、请求层错误码、权限模型一开始立约；
- 测试：纯函数与 composable 优先，关键链路 e2e 抽样。

**追问：**
1. monorepo 里多个 Vue 应用如何共享组件库？
2. 何时引入微前端，而不是先把模块边界理清？
3. 你如何避免「utils 垃圾场」？

::: details 追问参考答案

**1. monorepo 里多个 Vue 应用如何共享组件库？**

把 tokens、无头逻辑和 UI 组件拆成有明确 public exports 的 workspace 包，Vue 作为 peer dependency，避免每个应用打入不同实例。组件库独立做类型、单测、可访问性、文档与构建产物验证，应用通过版本或变更集升级。不要直接跨目录 import 内部源码；业务差异用 adapter 或插槽注入，SSR、主题和不同构建器都要做消费测试。

**2. 何时引入微前端，而不是先把模块边界理清？**

微前端解决的是独立团队、独立发布、技术栈或运行隔离等组织与交付问题，不会自动修复耦合。若只是代码大、目录乱或共享状态无边界，应先按领域模块化、明确 API 和构建拆包。只有独立部署收益能覆盖运行时通信、路由、样式、性能和治理成本时再引入，并先试点一条低风险链路，定义 mount/unmount 契约和观测指标。

**3. 你如何避免「utils 垃圾场」？**

只把无领域含义、纯且稳定的函数放通用 utils，例如格式转换；带订单、权限等业务词汇的逻辑回到对应 feature/domain，外部 I/O 放 service，带响应式生命周期的放 composable。每个包有 public API、owner 和测试，禁止默认导出大杂烩。定期按 import 关系审查：一个工具被单个领域使用，就不应为了“可能复用”提前全局化。

:::

### D2. `effectScope` 如何让 composable 的副作用生命周期可控？

::: details 参考答案
#### 基础结论

#### 原理深挖
scope 管理的是其 `run()` 期间创建并被捕获的 effect。异步回调晚于同步创建阶段再启动 watcher，可能不属于预期组件作用域，需要显式持有 stop。`effectScope(true)` 创建 detached scope，不随父 scope 停止，owner 必须更明确。

#### 工程场景

#### 资深回答模板
「我先定义副作用 owner。组件内借组件 scope，组件外建显式 scope；所有监听与外部资源都挂同一 dispose 路径。异步创建 effect 要特别审查，不能假设自动回收。」

### D5. Vue 微前端子应用怎样做到可重复挂载、卸载与资源隔离？

::: details 参考答案
#### 基础结论
承接 Q29/Q35 的清理与应用边界：子应用需要可重复、成对且状态机明确的 `mount` / `unmount` 契约，不应把 mount 称为幂等。`idle → mounted → idle` 是正常路径；mounted 状态再次 mount 必须明确拒绝，或先完整 unmount 再创建新实例。

#### 原理深挖
每轮 mount 都创建新的 Vue app、router 和 Pinia；同一个 app 实例只能 mount 一次，不能在 unmount 后拿旧实例再次 mount。组件树内 effect 由 `app.unmount()` 随树释放；手动 `effectScope` 只归组组件树外创建的 watcher/computed，不替代事件、Socket 和第三方实例清理。

#### 工程场景
宿主传容器、路由基座、鉴权快照和通信端口；实现状态守卫并保存本轮 disposer。用 `mount → 操作 → unmount → mount` 多轮测试监听数量、DOM 残留、内存和状态重置；具体机制链接 [微前端题库](./12-microfrontend.md)。

#### 反例 / 踩坑
复用已卸载 app、重复 mount 时静默覆盖引用、卸载只清 `innerHTML`、把组件内副作用错误地交给 detached scope，都会制造幽灵状态或泄漏。

#### 资深回答模板
「我把微应用当可销毁资源作用域。mount 创建实例并记录 disposer，unmount 先停止外部流量再卸 Vue、释放资源，最后验证容器和监听归零；机制选型交给微前端专项。」

### D6. Vue 响应式身份、`toRaw` 与 `markRaw` 的边界如何管理？

::: details 参考答案
#### 基础结论

#### 资深回答模板
「响应式代理有身份成本。我优先用业务 id，第三方不透明对象用浅容器；toRaw 只做边界适配，markRaw 要记录不可响应的更新契约，并用 profiling 证明必要。」

::: details 参考答案
#### 基础结论
承接 Q11 的异步组件基础选型：`<Suspense>` 目前仍是 experimental 功能，只提供 `#default` / `#fallback`，没有自身错误槽。异步错误应由 Suspense 父组件的 `onErrorCaptured`（或 Options API `errorCaptured`）处理。

#### 原理深挖
异步组件默认 `suspensible: true`：存在父级 Suspense 时，loading 状态由 Suspense 接管，异步组件自己的 `loadingComponent`、`errorComponent`、`delay`、`timeout` 会被忽略。只有显式 `suspensible: false`，该组件才自行管理这些选项。Suspense 仍不替代请求取消和错误上报。

#### 工程场景
决定每个异步组件由 Suspense 统一接管，还是设 `suspensible: false` 自治 loading/error，不能同时期待两套 UI 生效。父组件用 `onErrorCaptured` 展示错误态；chunk 失败区分离线、旧资源被清理和真实代码错误。

#### 反例 / 踩坑
给 Suspense 设计不存在的 `#error` 槽；接管后仍期待 `errorComponent` 展示；全应用一个边界；`onError` 无限重试；fallback 高度不稳定导致 CLS。

#### 资深回答模板
「我先声明 Suspense 是 experimental，且没有错误槽。默认接管 async component 后，其 loading/error/delay/timeout 选项被忽略；需要组件自治就设 `suspensible: false`。错误由父级 `onErrorCaptured` 收口。」

#### 追问链
1. 路由懒加载与异步组件如何分工？
2. chunk 404 为什么常在发布后集中出现？
3. Suspense fallback 如何避免布局跳动？

### D11. `track` / `trigger`、effect 栈与调度批处理如何串成一次更新？

**考察点：** track / trigger、effect、activeEffect、条件分支漏收集

::: details 参考答案
#### 基础结论
承接 Q1 的 ref/reactive 基础：D11 只扩展依赖图、effect 栈、分支清理和调度批处理。正在运行的渲染 effect、computed 或 watchEffect 读取属性时建立依赖，写入时按图调度。

#### 原理深挖
关键句：**没读到的属性不会建立依赖**。`if (obj.a) { use(obj.b) }` 在 `a` 为假时不会追踪 `b`——下次只改 `b` 可能不更新。列表 `v-for` 只访问了你用到的字段；`JSON.stringify` 会扫到很多键，依赖面变大。

嵌套 computed、组件渲染和 `watchEffect` 需要用 effect 栈恢复外层 effect；分支切换时还要清理旧依赖。`trigger` 通常把任务交给调度器，组件更新与 watcher 作业进入队列去重、批量刷新，而非每次赋值都立即 patch。具体数据结构属于实现细节，不承诺源码变量名。

#### 工程场景
用 `onTrack` / `onTrigger`、Vue Devtools 与 Performance 验证依赖面。批量同步改状态后应避免重复渲染；大对象只读取必要字段，派生值交给 computed。

#### 反例 / 踩坑
effect 内同步写回自身依赖可能递归更新；把任何异步都当成同一批次会错判刷新次数。异步回调中脱离 effect 的首次读取不会自动建立依赖。

#### 资深回答模板
口述结构：谁在读 → 读了什么 → 写了什么 → 谁被唤醒。别背源码函数名堆砌，讲清「条件漏收集」和「过度收集」两端。

#### 追问链
1. 条件分支切换后，旧依赖为什么要清理？
2. 同一 tick 连续修改多个 ref，调度器如何去重？
3. `flush: 'sync'` 为什么会损失批处理收益？
:::

### D12. `computed` 脏检查与 `watch` 的 flush 时机如何影响正确性？

**考察点：** 惰性计算、显式依赖、立即执行、清理函数

::: details 参考答案
#### 基础结论
承接 Q1 的响应式读取和 Q21 的更新时机：基础选型仍是 computed 做纯派生、watch 做显式副作用、watchEffect 做简单自动依赖。D12 只扩展惰性失效、异步收集边界和 flush 的 DOM 时序。

#### 原理深挖
computed 通常惰性求值：依赖变更先使缓存失效并通知消费者，下一次读取时再执行 getter。公开语义是缓存、惰性与依赖驱动，不应把某个版本的内部字段名当契约。

`watch` 默认回调在父组件更新之后、所属组件 DOM 更新之前；`flush: 'post'` 用于读取更新后的 DOM，`sync` 同步触发且不享受常规批处理。`watchEffect` 只跟踪同步执行阶段读取的依赖，`await` 之后的新读取不纳入该次自动收集。

#### 工程场景
取舍：能 `computed` 就别 `watch` 硬算一份状态；副作用用 `watch`/`watchEffect`；需要精确控制依赖列表或拿到 oldValue 时用 `watch`。

请求 watcher 用清理回调取消旧请求；测量 DOM 用 post；只有缓存失效等极少数场景才评估 sync。

#### 反例 / 踩坑
computed getter 写请求或改状态，会把读取变成副作用入口；大对象 deep watch 会递归遍历；异步 watcher 不清理会让旧响应覆盖新状态。

#### 资深回答模板
「computed 负责纯派生和缓存，watch 负责可控副作用。先确定需要旧值、DOM 时机还是自动依赖，再选 API 与 flush；异步副作用必须有失效清理。」

#### 追问链
1. computed 依赖变化后为什么不一定立即执行 getter？
2. 默认 watcher 中读所属组件 DOM 会看到新还是旧？
3. `watchEffect(async () => ...)` 在第一个 await 前后如何收集依赖？
:::

### D13. 静态提升、PatchFlags 与 Block Tree 如何协作缩小更新范围？

**考察点：** 编译器与运行时协作、更新粒度

::: details 参考答案
#### 基础结论
承接 Q16 的 Vue3 编译收益和 Q32 的模板/JSX 选型：D13 只扩展编译提示如何缩小运行时更新范围。Vue3 模板编译会分析静态与动态：

- **静态提升（hoistStatic）**：纯静态节点提到渲染函数外，每次 render 复用同一 vnode；
- **PatchFlags**：标记动态节点「到底动态在哪」（文本、class、props…），patch 时走快速路径，少做全量对比；
- **Block Tree**：把动态后代收集到 block，跳过静态子树遍历。

#### 原理深挖
编译器在 VNode 上携带动态信息，运行时更新可优先遍历 block 收集的动态后代，并按 PatchFlag 走针对性分支。结构性指令会改变 block 边界；优化以正确性为先，不代表静态节点在任何情况下都零成本。

#### 工程场景
口述目的：说明「为什么手写 render 不一定更快」——你丢掉了编译器给的提示。也解释「模板比随意 JSX 更吃得到优化」的说法从何而来（JSX 也能优化，但信息密度通常不同）。

用 Vue Devtools 和浏览器 trace 判断更新扇出；先稳定 props、减少无谓依赖，再评估 `v-memo`，不手工模拟内部标志。

#### 反例 / 踩坑
把 PatchFlag 当公共 API 手写、背固定常量值或承诺某模板「零 diff」，都可能随版本失真。模板内反复创建对象还会让子组件收到不稳定 props。

#### 资深回答模板
别假装背源码行号；讲清「静态越多、更新越便宜」。

#### 追问链
1. 结构性指令为什么会形成新的 block 边界？
2. PatchFlag 与 `v-memo` 分别在哪一层减少工作？
3. 如何验证一次模板改写真实降低了更新成本？
:::

### D14. 大表单、大表格如何组合虚拟化与响应式降级？

**考察点：** 分片更新、字段级校验、虚拟滚动、受控粒度

::: details 参考答案
#### 基础结论
承接 Q14 的列表基础与 Q22 的浅响应：D14 只扩展动态行高虚拟化、依赖成本诊断和编辑态隔离。先区分数据规模、DOM 规模、更新频率与交互要求。

#### 原理深挖
虚拟列表只保留可视窗口附近 DOM；固定行高简单，动态行高需要测量缓存和锚点补偿。深层 Proxy、deep watch 与大范围 computed 会扩大依赖和遍历；`shallowRef` 只在根替换时触发，必须配合不可变更新或显式触发约定。

#### 工程场景
大表单：

- 状态按区块拆 composable / 子表单组件，避免单对象千字段深 `watch`；
- 校验防抖、失焦校验 vs 提交总校验分层；
- 能 `shallowRef` 整表替换时再触发，细字段用局部更新；
- 昂贵预览用 `computed` + 缓存，别每个 keystroke 全量重算。

大表格：

- 虚拟列表（行高近似或动态测量）；
- 列配置稳定，单元格组件轻量化；
- 行数据用不可变更新或版本号，避免深层 Proxy 遍历十万格；
- 选择态、编辑态与源数据分离；
- `key` 用业务 id；编辑中的行慎用整表重渲染。

#### 反例 / 踩坑
整表 `reactive` 加 deep watch 自动保存、用 index 作可排序行 key、动态行高不做滚动锚点、每次输入复制十万行，都会把一种瓶颈换成另一种。

#### 资深回答模板
「我先量数据、DOM、依赖和布局四条链。展示用虚拟窗口，状态按编辑域拆，原始大数据用浅响应与根替换；以滚动稳定性、输入延迟、长任务和内存验收。」

3. 虚拟表格怎样保证键盘导航与无障碍？
