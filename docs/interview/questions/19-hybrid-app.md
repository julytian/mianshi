# Hybrid App 面试题库

> **怎么用：** 普通题按「平台差异 → 协议边界 → 生命周期 → 验证」口述 1～2 分钟；深层题按「结论 → 原理 → 场景 → 失败模式 → 验证」展开。本文面向 Android WebView、iOS WKWebView 与跨端容器架构，具体行为以目标系统、内核、框架版本和真机结果为准。

> **关键边界：** Web 内容、URL 参数和 Bridge 入参均不可信。Android 敏感 Bridge 首选 AndroidX WebKit 的 `WebViewCompat.addWebMessageListener`，为 `allowedOriginRules` 配置精确 HTTPS origin，并逐消息校验 `sourceOrigin` 与 `isMainFrame`；legacy `addJavascriptInterface` 会向所有 frame 注入对象，回调本身没有可信 origin / frame 证据，不能承担逐消息来源鉴权。iOS 注册 `WKScriptMessageHandler` 时处理强引用环并及时移除。Native API 只在允许页面身份、来源、导航代次和权限白名单下开放。

> **合规说明：** Apple 与 Google Play 的规则不是同一条统一禁令：Apple 需分别评估 2.5.2 的自包含 / 不下载改变功能代码原则，以及 4.7 对 HTML5 / JavaScript mini apps 等软件的条件与 4.7.2 Native API 限制；Google Play 对 WebView / 解释器中的 JavaScript 有例外，但运行时内容仍不得促成任何 Play 政策违规。政策会变化，每次发布前复核当期官方条款。

## 一、架构、容器与通信

### Q1. Hybrid App 的典型架构是什么，适合哪些场景？

**考察点：** 容器分层、Web 与 Native 边界、交付效率、体验和合规约束

::: details 参考答案

Hybrid App 通常由原生壳、WebView 页面、JSBridge、原生能力插件、资源与发布系统组成。原生壳负责进程、窗口、导航、系统权限和设备能力，Web 层负责适合快速迭代的业务 UI，Bridge 以窄接口连接两侧。服务端、资源包和监控平台共同构成交付链路，不能只把它理解为「网页套壳」。

它适合活动、内容、表单和需要多端复用的业务，也可承载部分核心流程；是否采用取决于首屏、动画、离线、设备能力、团队结构、审核和安全要求。重图形、持续后台、高实时或深度平台集成不一定适合 WebView。架构应按页面和能力逐项选择，不用「Hybrid 必然慢」或「一套代码零成本」作绝对判断。

:::

**追问：** 哪些指标能帮助决定某个页面是否放入 Hybrid 容器？

::: details 追问参考答案

应同时看业务迭代频率、端间复用收益、启动与首屏预算、交互帧率、内存、离线要求、系统能力数量、故障隔离和审核约束。先做代表性真机样例，比较冷启动、热启动、弱网、低端机和可访问性，再按页面选择；不能只依据框架宣传或单次跑分。

:::

### Q2. Android WebView、iOS WKWebView 与系统浏览器有什么关键差异？

**考察点：** 内核与更新、进程模型、存储、权限、调试和线程约束

::: details 参考答案

Android WebView 通常由系统 WebView 或 Chrome 组件提供 Chromium 内核，更新渠道、版本碎片和厂商系统会影响行为；应用通过 `WebView` 生命周期、设置和客户端回调控制导航。iOS 的 `WKWebView` 使用 WebKit，多进程执行网页内容，应用通过 `WKNavigationDelegate`、`WKUIDelegate`、`WKUserContentController` 等集成。两端 API、进程恢复、Cookie 接口和消息机制不能直接类比。

系统浏览器拥有完整地址栏、标签页、站点权限、下载和安全 UI；内嵌 WebView 的页面身份、导航、权限提示、文件选择与证书处理需要宿主显式治理。Web API 在内核层存在，也不代表宿主已实现对应委托。`addWebMessageListener` 的回调在 Android UI 线程执行，大 JSON 解析、加解密与 I/O 必须下沉，避免 ANR；legacy `addJavascriptInterface` 的 Java 方法运行在 WebView 私有后台线程，访问共享状态要同步，触碰 UI 要切回 UI 线程。iOS UI 与 WKWebView 操作位于主线程，耗时任务同样下沉后再回主线程交付。

:::

**追问：** 为什么在桌面 Chrome 中正常不能证明 Android WebView 中也正常？

::: details 追问参考答案

WebView 可能使用不同内核版本、系统组件、厂商配置和宿主设置，Cookie、文件选择、权限、弹窗、下载与多窗口还依赖 Native 回调。应建立目标 Android 版本与 WebView 版本矩阵，在真实宿主中验证；UA 相似只能提供线索，不能替代能力检测和真机测试。

:::

### Q3. JSBridge 的请求—响应协议应包含哪些字段？

**考察点：** Message ID、版本、超时、取消、幂等、错误契约和上下文绑定

::: details 参考答案

请求至少包含唯一 message id、协议 version、method、参数、能力上下文和可选幂等键；响应回传同一 id，并以明确的 success / error 联合类型表示结果。错误应区分不支持、参数非法、未授权、用户取消、超时、页面已失效和原生内部错误，避免只返回模糊字符串。

调用方设置超时并能发送 cancel；Native 收到取消后尽力中止，无法中止时也不得把迟到结果交给已销毁页面。副作用操作用幂等键和服务端 / Native 去重，不能因 Web 重试重复支付或保存。每条消息绑定页面身份、可信来源、frame、当前导航代次和会话；导航后旧代次消息全部失效。Native 对 method 做权限白名单、参数 schema、大小和取值验证，绝不信任 Web 输入。

:::

**追问：** 为什么仅有 Promise 和回调函数名还不够？

::: details 追问参考答案

Promise 只描述 JS 侧异步结果，不提供跨进程关联、超时、取消、导航失效或重放语义；回调函数名还可能被覆盖和注入。稳定协议需要不可碰撞的 message id、版本、错误码与上下文绑定，并在页面销毁时批量拒绝未完成请求，才能避免泄漏和串页回调。

:::

### Q4. Bridge 如何做版本协商与能力探测？

**考察点：** Protocol Version、Capability、向前兼容、降级和远程开关

::: details 参考答案

页面启动后读取只读的容器信息或发送握手，获得协议主次版本、平台、能力列表及每项能力版本，而不是从 UA 或 App 版本硬编码推断。协议主版本不兼容时拒绝调用；次版本通过忽略未知可选字段、保持既有错误语义实现兼容。能力应按方法和特性粒度表达，例如 `camera.capture@2`，不能只返回 `hasBridge=true`。

Web 先检测能力再调用，并提供纯 Web、系统页面或不可用提示等降级。Native 仍在每次调用时重新鉴权，能力列表不是授权令牌。灰度和远程开关可关闭有问题能力，但要有本地安全默认值；协商结果还要绑定页面身份和导航代次，不能被另一个页面复用。

:::

**追问：** App 版本号能否直接替代能力列表？

::: details 追问参考答案

不能。相同 App 版本可能因平台、系统、插件灰度、远程开关或设备硬件而具有不同能力，版本比较也容易遗漏补丁与回滚。App 版本可用于诊断，运行时应以受信 Native 返回的细粒度 capability 为准，并对调用失败保留降级路径。

:::

## 二、生命周期、导航与身份

### Q5. Android 与 iOS 的生命周期如何影响 Hybrid 页面？

**考察点：** Activity / Fragment、UIViewController、前后台、进程终止、资源释放

::: details 参考答案

Android WebView 常随 Activity、Fragment 和进程状态变化，旋转、重建、切后台或系统回收都可能让页面、窗口和 JS 上下文变化；是否保留实例取决于宿主策略。iOS 的 WKWebView 常由 UIViewController 持有，应用前后台和 WebContent 进程终止需要分别处理，`webViewWebContentProcessDidTerminate` 后通常要按状态决定重载或恢复。

宿主应定义创建、挂载、可见、暂停、销毁和恢复状态机。后台结果交付前检查 owner 和导航代次仍有效；销毁或即将进入不可信导航时，Android 分别调用 `removeJavascriptInterface` 或 `WebViewCompat.removeWebMessageListener` 移除已注册入口，并取消在途任务。iOS 的 `WKUserContentController` 会强持有注册的 `WKScriptMessageHandler`，需使用弱代理或合适生命周期，并在相同边界调用 `removeScriptMessageHandler(forName:)`，否则可能形成 retain cycle。

:::

**追问：** 为什么页面收到 Native 异步结果前要检查导航代次？

::: details 追问参考答案

调用发出后用户可能已返回、跳转、复用 WebView 或重新加载；旧结果若注入当前页面，会把前一页面数据串给后一页面。创建导航时递增 generation，消息记录 generation 与页面身份；回调只在 owner 存活且代次一致时交付，否则丢弃并清理。

:::

### Q6. Native 返回栈与 Web 路由应如何同步？

**考察点：** 单一所有者、History、深链、返回优先级和循环防护

::: details 参考答案

先规定每一层导航由谁拥有：原生页面由 Native 栈管理，容器内同文档路由由 Web Router 管理，跨业务或需系统能力的跳转走受控 Native 路由。返回键可按弹层、Web 可回退条目、Native 页面栈、退出应用的顺序处理，但要结合产品语义，不能仅凭 `history.length` 判断。

双方通过带 route id、来源和导航代次的事件同步，区分 push、replace、pop 与恢复；接收对方同步事件时不再反向新增记录，避免循环。深链先由 Native 校验 scheme、host、路径和登录状态，再映射到允许的 Web 路由。路由参数仍是不可信输入，敏感对象用短期引用标识而不是完整数据。

:::

**追问：** 如何避免 Android 返回键在 Web 与 Native 间形成死循环？

::: details 追问参考答案

定义一次返回事务 id 和明确 owner：Native 询问当前 Web 页面是否消费，Web 只返回结果或执行一次 pop，不再触发新的 Native back；超时则按安全默认策略处理。路由同步消息标记来源和动作，重复事务幂等忽略，并用自动化覆盖弹层、重定向与快速连按。

:::

### Q7. Hybrid 中 Cookie、Session 与 SSO 有哪些平台边界？

**考察点：** Cookie Store、SameSite、WKProcessPool、WebsiteDataStore、系统浏览器 SSO

::: details 参考答案

WebView Cookie 仍遵循 Domain、Path、Secure、HttpOnly、SameSite 等规则；`SameSite` 按 site 而非 App 身份判断，跨站登录、iframe 和第三方 Cookie 受系统与隐私策略影响。Android WebView 通过 `CookieManager` 管理；当 App target Android 5.0（API 21）及以上时，第三方 Cookie 默认不接受，可用 `setAcceptThirdPartyCookies(webView, ...)` 按 WebView 显式配置，但启用前要评估跟踪、CSRF 和登录必要性。Android WebView 与系统 Chrome 也不是天然共享会话。

iOS `WKWebsiteDataStore` 管理网站数据；共享同一持久 data store 的 WKWebView 可共享相关 Cookie，`WKProcessPool` 影响 Web 内容进程组织与历史兼容行为，但不能简单宣称它等同 Cookie 仓库，非持久 data store 也与默认持久存储隔离。Capacitor、Cordova、uni-app App 可能把本地页面置于 `localhost`、自定义 scheme 或其他框架配置的 origin；这会改变相对 API 的跨源关系、Cookie Domain / Secure / SameSite 判断和 SSO 回调。设计前必须记录每个平台与版本的实际页面 origin，不能沿用普通 HTTPS 站点假设，也不能靠放宽所有第三方 Cookie 修复。

与系统浏览器做 SSO 应使用标准 OAuth / OIDC 授权流程、系统认证会话和回调，不复制浏览器 Cookie。Native Token 与 Web Session 交换要通过短期一次性 code，由服务端绑定设备会话、audience 和 PKCE 等条件，避免把长期 Token 注入 JS。登出需同时撤销服务端会话、清理受控 Web 数据和 Native 凭证，并验证多 WebView 一致性。

:::

**追问：** 为什么把 Native Access Token 直接拼进 WebView URL 很危险？

::: details 追问参考答案

URL 会进入历史、Referer、代理、崩溃日志、截图和分析系统，页面脚本与第三方资源也可能读取。应由服务端签发短期、一次性、绑定目标会话与回调的交换码，通过受控 HTTPS 页面兑换 HttpOnly Session Cookie；日志只记录不可逆关联标识。

:::

## 三、权限、文件与资源

### Q8. 相机、定位和文件权限在 Hybrid 中应如何处理？

**考察点：** 系统权限、Native 授权、Web 请求、用户意图和最小权限

::: details 参考答案

这是多层决策：操作系统声明和运行时授权决定 App 能否访问设备；Native 容器根据当前页面身份、来源、功能白名单和用户动作决定是否代理；Web API 或 Bridge 再返回明确结果。Android 的 WebChromeClient 权限请求、文件选择回调与 iOS 的 WKUIDelegate、系统权限 API 并不相同，宿主必须逐项实现和验证。

只在用户明确操作后解释用途并请求最小权限，区分未授权、拒绝、不再询问、系统限制和设备不支持。不要伪造浏览器权限模型：Bridge 获得相机能力不等于 `navigator.permissions` 会呈现同一状态，也不应通过脚本假装标准 API 已获授权。Native 服务端最终都要做访问控制，Web 输入不得决定任意权限或文件路径。

:::

**追问：** 用户拒绝定位权限后，页面应该怎样降级？

::: details 追问参考答案

停止自动重复弹窗，返回稳定的 `PERMISSION_DENIED` 与是否可引导设置等受控信息，提供手动选择城市、输入地址等替代流程。只有用户再次主动触发时才解释恢复方式；Native 不绕过系统限制，Web 也不把拒绝当崩溃或无限重试。

:::

### Q9. 上传、下载和本地文件访问应怎样设计？

**考察点：** Content URI、安全作用域、临时文件、类型校验和下载交付

::: details 参考答案

Web 页面不应获得任意本地绝对路径。Android 优先通过系统文档选择器和 `content://` URI，以临时授权读取；iOS 通过文档选择器、照片选择器和安全作用域 URL 等受控接口。Bridge 返回短期文件句柄或受限元数据，Native 在每次读写时校验页面身份、用途、大小、MIME 与生命周期，完成后撤销权限并清理临时文件。

上传要流式处理、支持取消和进度，服务端重新验证真实类型、大小、权限与内容；客户端 `accept` 和 MIME 只改善体验。下载应使用受控目录、随机文件名和系统分享 / 预览能力，危险类型不在可信主域内联执行。日志不得记录预签名 URL、用户文件内容或可重放句柄。

:::

**追问：** 为什么不能把 `file://` 根目录直接开放给 WebView？

::: details 追问参考答案

宽泛文件访问会让被注入或被导航到的不可信页面读取应用私有文件，并与跨源、通用文件 URL 访问设置组合成数据泄露。应使用系统选择器、受限内容 URI 或短期虚拟句柄，只授权用户选中的对象；同时关闭不需要的文件访问能力并限制导航来源。

:::

### Q10. Web 资源缓存和更新应如何划分？

**考察点：** HTTP Cache、本地资源包、Service Worker、版本一致性和回滚

::: details 参考答案

在线资源优先遵循 HTTP 缓存：内容哈希静态资源长期不可变，入口和清单短缓存或再验证。离线资源包由 Native 更新器管理，必须有版本清单、签名、每文件 hash、大小上限和兼容条件；下载到新目录后完整校验，再原子切换活动指针，失败继续使用旧版本。Service Worker 若启用，是另一层缓存，需明确与 Native 包的职责，避免双重失效和版本混用。

页面、资源包、Bridge 和 API schema 版本要兼容；回滚保留上一已知可用版本并有熔断开关。私有 API 响应和账号数据不得打入公共资源包。允许更新的内容类型由各商店当期规则分别决定，Apple 2.5.2 / 4.7 与 Google Play 的 WebView / 解释器例外不能合并成同一判断；具体政策边界在 Q13 展开。

:::

**追问：** 为什么下载完成后不能直接逐文件覆盖当前资源目录？

::: details 追问参考答案

逐文件覆盖会让并发页面读到半新半旧版本，进程崩溃或断电还可能留下不可恢复目录。应在独立目录下载，验证签名、清单和所有 hash 后，通过原子指针或目录替换一次切换；旧版本保留到新版本健康确认后再回收。

:::

### Q11. Hybrid 的调试、日志和崩溃如何关联？

**考察点：** Trace ID、Web Console、Native Crash、脱敏、版本维度和时钟

::: details 参考答案

建立贯穿页面导航、Bridge message、Native 调用、网络请求和服务端 trace 的关联标识。日志包含 App、系统、WebView / WebKit、资源包、页面和 Bridge 版本，以及导航代次、方法、耗时和规范化错误码；不记录 Cookie、Token、完整 URL 查询、文件内容和敏感参数。Web 错误带 source map 版本，Native 崩溃带符号表版本。

Android 可在授权调试构建中使用 WebView 调试和 Logcat，iOS 使用 Safari Web Inspector、系统日志与崩溃工具；生产调试入口必须关闭或受控。跨进程时钟用相对时间与服务端时间校正。前端异常不等于 Native 崩溃，WebContent 进程终止也应单独分类，最后按同一 trace 和版本时间线归因。

:::

**追问：** 为什么只上报 JavaScript 堆栈仍难以定位 Bridge 故障？

::: details 追问参考答案

JS 堆栈看不到 Native 排队、权限判断、线程切换、系统回调和进程终止。需要以 message id 关联请求接收、校验、执行、回调和超时，并携带页面身份、导航代次及两侧版本；同时对参数脱敏，才能区分页面取消、协议不兼容和 Native 内部失败。

:::

### Q12. uni-app App、Capacitor 与 Cordova 的定位和差异是什么？

**考察点：** 编译与运行模型、插件生态、迁移成本、PWA 边界

::: details 参考答案

uni-app 的 App 端是其跨端编译与运行体系，页面形态和原生渲染能力取决于所选模式、平台与插件；不能把小程序、H5 和 App 端行为视为完全一致。Capacitor 以现代 Web 应用嵌入原生工程为核心，强调原生项目可见、插件 API 与 Web/PWA 兼容。Cordova 也是 WebView 容器加插件模型，生态历史较长，项目质量与维护状态需要逐项评估。三者的本地页面可能使用 `localhost`、自定义 scheme 或框架特定 origin，且会随平台与配置变化；Cookie、SameSite、CORS、OAuth 回调和 SSO 必须以运行时实际 origin 重新设计与真机验证。

三者都不等同 PWA：PWA 运行于浏览器安装与权限模型。它们也不等同 React Native、Flutter 或纯原生，后者的 UI 渲染、语言运行时和系统集成路径不同。选型比较团队技能、插件缺口、调试、升级、包体、性能实测、无障碍与商店合规；不下「某框架绝对更快」的结论。

:::

**追问：** 从 Cordova 迁移到 Capacitor 是否只是替换依赖？

::: details 追问参考答案

不是。需要盘点插件 API、原生定制、导航、Cookie、文件 URI、权限、启动流程和构建签名；即使存在兼容层，生命周期与平台配置仍可能不同。应按能力逐项迁移，用真机契约测试验证，再分版本灰度，不把插件名称相似视为行为一致。

:::

### Q13. Hybrid 的签名、应用商店和热更新合规边界是什么？

**考察点：** App 签名、资源签名、审核政策、功能变更和供应链

::: details 参考答案

应用包由平台分发签名证明发布者与包完整性；资源热更新还需应用自己的离线签名和 hash 校验，签名私钥放在受控发布系统，客户端只内置可轮换公钥。更新清单限定 App / Bridge 兼容范围、资源类型和回滚版本，采用灰度、熔断、审计与原子切换。

技术上能下载并执行不代表合规，两个商店要分别判断：

- **Apple：** 2.5.2 原则上要求 App 在 bundle 内自包含，不得下载、安装或执行引入或改变 App 功能的代码，有限教育类例外另有条件。4.7 又允许符合条件、未嵌入二进制的 HTML5 / JavaScript mini apps、mini games、chatbots、plug-ins 等软件，但开发者仍对其符合全部审核指南和法律负责，并满足 4.7.1～4.7.5；其中 4.7.2 规定，未经 Apple 事先许可，不得向这些软件扩展或暴露 Native 平台 API / 技术。
- **Google Play：** 禁止绕过 Play 自更新 App 或从 Play 之外下载 dex、JAR、`.so` 等可执行代码；对运行在虚拟机或解释器、通过间接方式访问 Android API 的代码存在例外，官方示例包括 WebView / 浏览器中的 JavaScript。但运行时加载的解释型内容仍不得导致任何 Play 政策违规，带 JavaScript Interface 的 WebView 也不得加载不可信或未经验证的内容。

因此不能写成「两家都禁止远程 JavaScript」，也不能把例外理解为任意热更新许可。政策和地区要求会变化，产品、法务、安全与发布负责人必须在每次发布前核对当期官方规则并保留审核证据。

:::

**追问：** 资源包有 HTTPS 下载后还需要签名吗？

::: details 追问参考答案

需要。TLS 保护一次传输并验证服务器身份，但不能替代制品来源、发布权限和离线存储完整性；CDN、发布账户或本地缓存受损时仍可能投放错误包。客户端应验证受信公钥签名、清单与文件 hash，并防版本回退，再原子启用。

:::

## 四、深层工程场景

### D1. 如何设计可演进的 JSBridge？

::: details 参考答案

#### 基础结论

把 Bridge 当跨进程 RPC 协议：接口窄、版本化、可探测、可取消、可观测，并让旧 Web 与新 Native、新 Web 与旧 Native 在明确窗口内共存。

#### 原理深挖

消息必须携带唯一 id、协议 version、method、参数、页面身份、来源、frame 与导航代次。响应是稳定结果或错误联合类型。超时只表示调用方不再等待，不保证副作用未发生；因此取消要显式，副作用操作还需幂等键。Capability 反映实际能力，不由 App 版本机械推导。

#### 工程场景

用 schema 生成 TypeScript 与 Native DTO，Native 白名单路由并验证类型、长度、枚举和权限。握手返回 capability 及版本；调用表维护超时和 cancel，页面销毁时批量拒绝。Android 优先用 `WebViewCompat.addWebMessageListener` 配置精确 HTTPS `allowedOriginRules`，并在回调中校验 `sourceOrigin`、`isMainFrame` 和导航代次；其回调位于 UI 线程，大解析与 I/O 下沉。legacy `addJavascriptInterface` 回调在 WebView 私有后台线程，必须同步共享状态并切回 UI 线程更新界面。iOS 结果回主线程交付，日志用 message id 贯穿两侧。

#### 反例 / 踩坑

动态执行任意方法名、把 JSON 直接映射反射调用、把 legacy `addJavascriptInterface` 当成能识别可信 origin / 主 frame 的入口、只用函数名回调、无导航代次、超时后自动重试支付，都会扩大攻击面或产生串页和重复副作用。

#### 资深回答模板

我先定义版本化 envelope、能力表和错误契约，再把安全上下文与导航代次绑定到每次调用。Native 按方法白名单与 schema 重新鉴权，调用支持 timeout、cancel 和幂等；生命周期结束统一清理，以契约测试覆盖版本组合和迟到回调。

:::

**追问链：**
1. 超时后为什么不能断言 Native 没有执行？
2. 协议主版本和次版本如何处理？
3. 怎样测试 Bridge 的跨版本兼容？

::: details 追问参考答案

**1. 超时后为什么不能断言 Native 没有执行？**

超时只是 JS 等待窗口结束，消息可能已进入 Native 队列、系统 UI 或服务端。调用方应发送 cancel 并忽略迟到响应；有副作用的操作携带幂等键，并提供查询最终状态的接口，不能盲目重试造成重复执行。

**2. 协议主版本和次版本如何处理？**

主版本用于不兼容语义变化，不匹配时拒绝并降级；次版本只增加可选字段或能力，旧端忽略未知可选字段。不能悄悄改变既有错误码和默认值；能力列表应精确到方法版本，并记录淘汰窗口。

**3. 怎样测试 Bridge 的跨版本兼容？**

维护 Web 版本 × App 版本 × 平台矩阵，用同一契约样例验证握手、正常响应、未知字段、缺失能力、超时、取消、重复请求、导航和进程终止。真机测试线程和系统 UI，发布前再用灰度错误率确认兼容假设。

:::

### D2. 如何保证 Bridge 安全并隔离不可信 Web 内容？

::: details 参考答案

#### 基础结论

默认任何 Web 页面和消息都不可信。Bridge 只向经过页面身份、来源、frame、导航代次和业务权限验证的文档开放最小能力，Native 是最终授权点。

#### 原理深挖

仅检查当前 URL 字符串不足以抵御重定向、iframe、DNS / 内容接管和导航竞态。应由受控导航策略建立页面身份，并把能力 token 或上下文绑定到本次主框架导航。Native 对参数做 schema 与语义验证，文件、路由和网络目标使用白名单映射，不接收任意路径或 URL。

#### 工程场景

可信业务与外部内容使用不同 WebView 或至少不同配置和进程 / 数据存储边界；外部页面完全不注入 Bridge。Android 敏感能力首选 AndroidX WebKit 的 `WebViewCompat.addWebMessageListener`：`allowedOriginRules` 只列精确 HTTPS origin，收到消息后再校验 `sourceOrigin`、`isMainFrame`、导航代次、方法权限和参数。legacy `addJavascriptInterface` 会把对象注入所有 frame，Java 回调没有可用于逐消息鉴权的可信 origin / frame；不支持安全消息 API 时，敏感 Bridge 不得开放给可导航到其他来源或包含第三方 iframe 的页面。进入不可信导航或销毁时分别调用 `removeWebMessageListener` / `removeJavascriptInterface`。iOS 使用命名 message handler、弱代理并及时移除，CSP 和导航 allowlist 作为纵深防御。

#### 反例 / 踩坑

根据页面传来的 `origin` 自证身份、对白名单做字符串前缀匹配、允许 iframe 调敏感 API、接受任意 Intent / URL / 文件路径、忽略导航后旧消息，或为了调试在生产打开通用执行接口，都会让一次 XSS 升级为 Native 权限滥用。

#### 资深回答模板

我把 WebView 当不可信客户端：Android 用安全消息 API 的精确 HTTPS origin 规则，并逐消息验证 `sourceOrigin`、主 frame、代次、方法和参数；legacy 接口没有这些来源证据，敏感页面不能同时允许任意导航或第三方 iframe。外部内容使用无 Bridge 的隔离容器，两端都在导航与销毁边界撤销 handler，并用恶意页面做越权测试。

:::

**追问链：**
1. 为什么导航 allowlist 不能只用 `startsWith`？
2. iframe 是否应该继承主页面 Bridge 权限？
3. WKScriptMessageHandler 的内存问题怎样处理？

::: details 追问参考答案

**1. 为什么导航 allowlist 不能只用 `startsWith`？**

字符串前缀会误放 `https://trusted.example.attacker.com`、用户信息段、编码变体和非预期 scheme。应使用标准 URL 解析后精确比较 scheme、规范化 host、端口和允许路径，拒绝凭证字段与危险跳转，并在每次最终导航重新建立身份。

**2. iframe 是否应该继承主页面 Bridge 权限？**

默认不应。第三方或被注入 iframe 可能借主页面权限调用 Native。消息需识别主 frame 与来源；敏感能力只允许受控主文档。确需子 frame 时建立独立、最小 capability 和精确 origin，并限制可传数据与生命周期。

**3. WKScriptMessageHandler 的内存问题怎样处理？**

`WKUserContentController` 强持有 handler，若控制器又持有 WebView，直接注册 `self` 可能形成 retain cycle。可使用弱转发对象，并在页面或控制器结束时按名称移除 handler；回调仍要在主线程检查 owner 与导航代次。

:::

### D3. 如何治理启动白屏、WebView 池和预加载？

::: details 参考答案

#### 基础结论

先定义冷启动到可用的分段指标，再按瓶颈选择进程预热、WebView 预创建、资源预取或服务端优化。池化只能用于预先约束的数据域；平台没有通用的「清理后等同新实例」保证，绝不能跨用户复用私有状态。

#### 原理深挖

白屏可能来自原生启动、WebView 创建、内核进程、DNS / TLS、HTML、资源、JS 执行、首帧或路由数据。预加载能把成本前移，却增加内存、流量和旧版本风险。WebView 内含 Cookie、history、页面 JS、缓存、表单、Bridge handler 与未完成请求。iOS 的 `WKBackForwardList` 没有公开清空 API；要求空历史时必须新建 `WKWebView`。`WKWebsiteDataStore` 在创建 `WKWebViewConfiguration` 时决定，清理共享 data store 会影响使用它的其他 WebView，不能把事后清理当成实例隔离。

#### 工程场景

采集 App start、容器创建、navigation start、commit、DOMContentLoaded、FCP、业务首屏和可交互时间，并记录错误与白屏持续时间。iOS 敏感会话在创建前预分配独立持久或非持久 `WKWebsiteDataStore`；需要空历史时新建 WKWebView，不能清理共享 store 伤及其他实例。Android 真正的网站数据隔离依赖 AndroidX WebKit `MULTI_PROFILE` 能力，并在创建 / 首次加载前把 WebView 绑定到独立 profile；不支持时，即使销毁重建 WebView，也可能继续使用进程级共享的 Cookie 与网站数据。无法证明隔离时不跨账号池化。

#### 反例 / 踩坑

启动即预载全部业务会抢 CPU 和网络；用启动图遮住无限白屏只改变视觉；用私有 API 或伪造后退操作声称清空 `WKBackForwardList`、清理共享 `WKWebsiteDataStore`、Android 不分 profile 只重建实例，都会留下串数据或误伤其他页面的风险。只看平均 FCP 还会掩盖低端机长尾和加载失败。

#### 资深回答模板

我先把白屏拆成 Native、容器、网络、渲染和业务阶段，以 p75 / p95 及失败率定位。池化只服务预先设计的隔离域：iOS 敏感会话预分配独立 data store 且空历史用新实例，Android 先检测并绑定独立 profile；没有平台隔离能力就不跨账号池化。

:::

**追问链：**
1. WebView pool 为什么容易造成跨账号泄露？
2. 首屏与白屏应该怎样定义？
3. 预加载何时可能让体验更差？

::: details 追问参考答案

**1. WebView pool 为什么容易造成跨账号泄露？**

WebView 不只有 DOM，还关联 Cookie、网站数据、history、缓存、JS 堆、表单、截图和未完成 Bridge 调用。iOS 无公开 API 清空 `WKBackForwardList`，共享 data store 的清理还会影响其他实例；Android 若无 `MULTI_PROFILE` 并在加载前绑定独立 profile，重建实例也不等于数据隔离。因此敏感账号必须预先设计独立存储边界，不能依赖归还时清理。

**2. 首屏与白屏应该怎样定义？**

FCP 只表示首次内容绘制，不一定是业务首屏。可定义从 Native 启动或导航开始，到首个非占位业务内容可见的时间；白屏则按根视图无有效内容的持续区间和超时失败率统计。指标需关联页面、版本、设备和冷暖状态。

**3. 预加载何时可能让体验更差？**

低内存设备上预建 WebView 会触发回收，后台下载会争抢当前页面网络，预执行脚本占主线程和电量，预载旧资源还会增加版本错配。应按命中概率、资源预算和网络条件选择，并设置取消、上限与远程开关。

:::

### D4. 如何处理前后台、进程回收和状态恢复？

::: details 参考答案

#### 基础结论

把进程终止视为正常故障模型，关键状态持续保存到受控持久层；恢复依靠版本化快照与服务端真相重建，而不是期待离开事件必达或 JS 堆永远存在。

#### 原理深挖

Android 后台进程可能被回收，Activity 也会重建；iOS 应用和 WKWebView 的 WebContent 进程可能分别终止。内存中的路由、Bridge Promise、上传进度和 Token 都可能丢失。生命周期回调适合快速暂停与保存，但系统强杀、崩溃时不保证执行。

#### 工程场景

持续保存路由引用、表单草稿、业务 revision 和幂等操作 id，不保存可直接重放的敏感凭证到 Web。恢复先验证用户、App / 资源 / schema 版本，再重建页面并查询服务端最终状态。未完成 Bridge 请求统一以 `CONTEXT_LOST` 结束；媒体、定位和实时连接重新请求或校验权限。

#### 反例 / 踩坑

只在 `onDestroy` 或进入后台时保存；恢复后无条件重复提交；把整份 JS store 含 Token 序列化；WebContent 进程终止后无限 reload；用旧页面快照直接显示敏感数据而不重新确认账号。

#### 资深回答模板

我按可丢 UI、可恢复草稿、服务端事务和敏感凭证分类状态。关键编辑增量持久化，副作用用幂等 id；进程恢复先验证身份与版本，再从服务端对账。旧 Bridge 上下文全部失效，连接和权限按当前系统状态重建。

:::

**追问链：**
1. 哪些状态不应直接放进 Web 快照？
2. 如何恢复提交到一半的订单？
3. 怎样测试进程回收路径？

::: details 追问参考答案

**1. 哪些状态不应直接放进 Web 快照？**

Access Token、Session Cookie、支付凭证、完整个人信息和可重放文件句柄不应进入普通 Web 存储或日志。快照只保存最小业务引用、非敏感草稿和 schema 版本；敏感凭证由系统安全存储或服务端会话管理，恢复时重新授权。

**2. 如何恢复提交到一半的订单？**

提交前生成幂等键并持久化操作引用，服务端按该键保证一次语义。恢复后查询订单状态，而不是直接再 POST；明确区分未创建、处理中、成功和可重试失败，只有服务端确认安全时才允许重试。

**3. 怎样测试进程回收路径？**

在测试构建中分别模拟 Activity 重建、Android 后台进程死亡、iOS 应用重新启动和 WKWebView 内容进程终止，覆盖上传、授权、路由和表单中间态。验证不会串账号、重复副作用或无限刷新，并检查低存储与旧快照迁移。

:::

### D5. 如何治理原生插件兼容、灰度和降级？

::: details 参考答案

#### 基础结论

插件是平台代码和系统 API 的长期兼容责任。用统一契约包裹第三方插件，维护平台与版本矩阵，以 capability、灰度、熔断和等价降级控制风险。

#### 原理深挖

插件可能依赖 Android Manifest、Activity Result、iOS entitlement、隐私清单、线程和生命周期；升级框架不保证插件仍兼容。Web 调用契约应与插件实现解耦，避免业务直接依赖插件错误字符串或平台对象。

#### 工程场景

适配层规范参数、结果、权限和错误码，契约测试运行于模拟器与关键真机。发布按 App 版本、系统、设备和用户分群灰度，监控调用成功率、超时、崩溃和权限拒绝。远程关闭能力后提供系统页面、Web 上传或人工流程；回滚不依赖从商店之外下载 dex、JAR、`.so` 或其他原生可执行代码。

#### 反例 / 踩坑

插件升级直接全量；只在单一旗舰机测试；把「无此方法」当用户拒绝；远程配置开启旧 App 不支持的能力；出现问题后通过 Web 热更新绕过原生商店审核下载新二进制。

#### 资深回答模板

我用自有 adapter 隔离插件和业务，能力协商精确到版本，契约与真机矩阵覆盖权限和生命周期。发布小流量观察崩溃、超时与错误分布，异常可远程关闭并降级；需要修改原生代码时走正常商店发布。

:::

**追问链：**
1. 插件错误码为什么要由适配层规范化？
2. 灰度应观察哪些插件指标？
3. 旧 App 不支持新能力时怎样降级？

::: details 追问参考答案

**1. 插件错误码为什么要由适配层规范化？**

不同平台和插件版本可能返回异常、数字、字符串或空结果，业务直接依赖会导致分支扩散。适配层映射为不支持、权限拒绝、用户取消、暂时失败和内部错误等稳定契约，同时保留脱敏原始原因用于诊断。

**2. 灰度应观察哪些插件指标？**

至少按平台、系统、App、插件和设备维度观察调用量、成功率、取消、权限拒绝、超时、耗时分位、Native 崩溃和页面失效。还要看业务完成率，防止技术成功但结果不可用；达到阈值自动熔断并保留对照组。

**3. 旧 App 不支持新能力时怎样降级？**

Web 先读取 capability，不展示不可用入口或切换到系统浏览器、普通文件上传、手工输入等基础路径。服务端也校验客户端能力与数据格式；不得仅靠版本字符串假设支持，更不能诱导旧端调用后无限重试。

:::

### D6. Hybrid 网络代理、TLS、证书固定和抓包边界如何设计？

::: details 参考答案

#### 基础结论

生产网络始终执行正常 TLS 证书链和主机名校验；代理、证书固定与抓包都按威胁模型和运维能力选择。任何环境都不以「忽略证书错误」作为修复方案。

#### 原理深挖

WebView 请求可能直连，也可能由 Native 网络层代理，两者的 Cookie、缓存、CORS、重定向和证书栈不同。证书固定能降低特定 CA 误签风险，却增加证书轮换、灾备和系统兼容成本；固定公钥时也需备份 pin、过渡窗口和可控更新路径，不能阻断紧急恢复。

#### 工程场景

明确哪些请求归 WebView、哪些走 Native，统一 trace 但保持凭证最小化。生产使用系统信任和严格主机校验；需要 pin 的高风险域配置当前与备份 key，并演练轮换。抓包只在获得授权的测试环境、测试账号和测试数据中，通过专用构建与受控证书完成，结束后清理证书和日志。

#### 反例 / 踩坑

在证书回调中无条件放行、生产信任用户安装 CA、把代理返回内容当可信、为了统一网络而破坏 Cookie / CORS 语义、只有单一 pin 且无轮换，都会把排障便利变成安全或可用性事故。

#### 资深回答模板

我先画清 WebView 与 Native 请求边界，再保持生产 TLS 严格校验。证书固定只用于明确高风险场景，并配置备份 pin、轮换和熔断预案；抓包限定授权测试环境和脱敏数据，绝不通过忽略证书错误解决连接问题。

:::

**追问链：**
1. 为什么不能在生产忽略证书错误？
2. 证书固定为什么需要备份 pin？
3. Native 代理 Web 请求有什么语义风险？

::: details 追问参考答案

**1. 为什么不能在生产忽略证书错误？**

忽略错误会同时绕过过期、主机名不匹配、不受信 CA 和中间人证书等身份校验，使攻击者能读取或篡改登录与业务数据。正确做法是修复证书链、域名、时间或代理配置，并在失败时安全终止和上报。

**2. 证书固定为什么需要备份 pin？**

当前私钥泄露、证书续期或 CA 切换时需要过渡到新 key；只有一个 pin 会让客户端在轮换后全部断网，旧 App 又无法立即更新。备份 pin 也必须离线保护并定期演练，配置多个 pin 不等于关闭正常证书验证。

**3. Native 代理 Web 请求有什么语义风险？**

代理可能改变 Origin、CORS、Cookie SameSite、缓存键、重定向、流式响应和 Service Worker 可见性，还可能扩大 Native 凭证权限。只代理明确 API，定义等价契约和目标白名单，并分别测试认证、上传下载、取消和错误行为。

:::

### D7. 如何建立跨端监控、Trace 和故障归因？

::: details 参考答案

#### 基础结论

用统一事件模型关联 Native、WebView、页面、Bridge、网络和服务端，但每层保留自己的错误域。归因依靠同一次会话的时间线和证据，不用某一层最先报错替代根因分析。

#### 原理深挖

Web JS、WebContent / renderer 进程、App 进程和服务端可能独立失败；线程排队、导航取消和超时也会形成相似表象。跨进程时钟不完全一致，trace 要包含单调相对时间、服务端时间和父子 span。客户端日志可被篡改或丢失，不能作为唯一安全证据。

#### 工程场景

定义 navigation id、page instance id、message id、request id 和服务端 trace id 的父子关系。采集版本、平台、系统、WebView、资源包、网络类型、导航代次、耗时和规范错误，敏感字段默认删除。仪表盘按首屏、Bridge、崩溃与业务漏斗分层，异常样本可重建关键时间线。

#### 反例 / 踩坑

把完整 URL、Cookie、Token 和 Bridge 参数全量上报；Web 与 Native 各自生成无关联日志；只看平均值；客户端超时就记为服务端失败；source map 或符号表版本不匹配，都会让监控泄密或误归因。

#### 资深回答模板

我用导航实例作为根，Bridge 与网络建立子 span，贯穿到服务端；版本、代次和错误域完整但载荷脱敏。归因时比较排队、执行、网络和进程事件，按长尾与业务影响排序，客户端证据再与服务端和崩溃记录交叉验证。

:::

**追问链：**
1. 如何关联 Web 错误与 Native 崩溃？
2. 客户端时钟不准怎么办？
3. Bridge 参数能否全部写入日志？

::: details 追问参考答案

**1. 如何关联 Web 错误与 Native 崩溃？**

页面实例、导航 id 和 App session id 应进入两侧事件；Native 崩溃报告带 App、符号表和最近脱敏 breadcrumb，Web 错误带资源与 source map 版本。按同一会话时间线关联只能说明相关性，还需线程、进程和调用证据确认因果。

**2. 客户端时钟不准怎么办？**

单设备内部耗时优先使用单调时钟，跨系统排序记录服务端接收时间和定期估算的时钟偏差；事件同时保留 wall time 与相对 offset。不要只按客户端绝对时间拼接，也不要假设 Android、Web 与服务器时钟完全一致。

**3. Bridge 参数能否全部写入日志？**

不能。参数可能含 Token、Cookie、定位、文件 URI 和个人信息。应为每个 method 定义允许记录的字段、类型和长度，敏感值删除或使用不可逆短期关联标识；生产采样、访问权限和保留期也要受控。

:::

### D8. 如何设计安全、可回滚且合规的资源热更新？

::: details 参考答案

#### 基础结论

更新包必须由受控流水线签名、客户端验签并逐文件校验 hash，在独立目录准备后原子切换；发布采用灰度、健康门禁、熔断和上一稳定版回滚。技术安全门禁与商店合规门禁并行，Apple 与 Google Play 分别评估。

#### 原理深挖

TLS 只保护传输，不能证明制品经过批准。清单需绑定包版本、App / Bridge 兼容范围、文件 hash、大小、过期和最低允许版本；签名验证发布者，防回滚保护避免攻击者投放有漏洞旧包。资源、页面和 Bridge 多版本并存，协议必须兼容。

#### 工程场景

构建生成不可变资源与 canonical manifest，在隔离签名服务签名。客户端限制下载域、大小和磁盘，验证签名、版本、所有 hash 后 fsync 并原子切换指针；启动健康检查失败回退。灰度按稳定分桶，监控白屏、崩溃、Bridge 和业务指标，保留审计链。

#### 反例 / 踩坑

仅校验下载 URL、把签名私钥放客户端、逐文件覆盖、失败后删除唯一旧版、灰度分桶漂移，都会破坏安全或可用性。合规上，不能忽略 Apple 2.5.2 与 4.7 的不同适用条件，也不能把 Google Play 对解释器 / WebView JavaScript 的例外扩张为可下载原生可执行代码或可违反其他政策。

#### 资深回答模板

我把资源包视为供应链制品：签名确认来源，hash 确认内容，版本策略防回退，独立目录和原子指针保证一致。合规评估分开做：Apple 核对 2.5.2、4.7 及 4.7.2 Native API 边界，Google Play 核对解释器 / WebView JavaScript 例外及全部内容政策；发布前按最新条款复核。

:::

**追问链：**
1. 签名与 hash 分别解决什么问题？
2. 灰度分桶为什么要稳定？
3. 热更新政策应如何持续管理？

::: details 追问参考答案

**1. 签名与 hash 分别解决什么问题？**

文件 hash 能发现内容变化，但攻击者若可同时替换清单，也能替换 hash；数字签名用受控私钥证明清单来源和完整性，清单再绑定每个文件 hash。客户端还需校验版本、兼容范围和防回滚，不能只验其中一层。

**2. 灰度分桶为什么要稳定？**

同一用户或设备反复进入不同版本会污染指标、增加缓存和状态迁移问题，也难以复现故障。使用不含敏感语义的稳定标识与发布盐分桶，记录实际生效版本；紧急熔断仍可覆盖分桶并回到已验证版本。

**3. 热更新政策应如何持续管理？**

为允许资源类型、功能边界和审核材料建立平台分别清单：Apple 记录 2.5.2 与 4.7 / 4.7.2 的适用依据，Google Play 记录 WebView / 解释器例外和内容合规结论。政策会变化，历史批准不是永久许可；每次发布复核当期官方条款，有疑问时走正式审核或完整 App 版本发布。

:::

### D9. 如何在 Hybrid、PWA、React Native、Flutter 与原生之间选型？

::: details 参考答案

#### 基础结论

选型不是单一性能排名，而是业务页面、体验目标、设备能力、团队与交付约束的多维决策。大型产品可以按场景组合，但必须控制导航、设计系统、身份和监控的一致性成本。

#### 原理深挖

Hybrid 主要在 WebView 中运行 Web UI；PWA 受浏览器安装、权限和后台能力约束；React Native 通常以 JavaScript / TypeScript 驱动原生组件与平台能力；Flutter 使用 Dart 和自身渲染体系；原生直接使用平台 SDK。具体性能受页面、实现、设备和版本影响，不能推出绝对优劣。

#### 工程场景

先列体验 SLO、首屏、动画、离线、后台、硬件、无障碍、包体、审核和团队技能，做代表性垂直切片。衡量开发与长期升级成本、插件成熟度、故障定位和人才供应。制定两年演进与退出路径，允许内容页 Hybrid、核心高交互原生等受控组合。

#### 反例 / 踩坑

只比较 Demo FPS、把代码复用率当总成本、忽略系统新版本与插件维护、把 PWA 当无条件替代商店应用、声称 RN / Flutter / 原生永远更快，都会让选型缺乏可验证边界。

#### 资深回答模板

我先按业务路径设体验和能力门槛，再用真实设备垂直样例比较开发、运行、运维和合规总成本。结论细化到页面和能力，不做框架信仰；混合方案统一身份、导航、设计与监控，并预先定义升级和迁移出口。

:::

**追问链：**
1. 如何设计有说服力的选型 PoC？
2. 多技术栈混用最大的架构成本是什么？
3. 为什么不能用绝对性能结论做决策？

::: details 追问参考答案

**1. 如何设计有说服力的选型 PoC？**

选择最能暴露风险的真实链路，包含冷启动、列表、动画、表单、设备权限、离线和错误恢复；使用相同数据与设备，记录长尾首屏、帧稳定性、内存、包体和开发维护工时。PoC 还要完成签名、监控和升级，而非只做静态首页。

**2. 多技术栈混用最大的架构成本是什么？**

边界会带来身份、导航、状态、设计系统、无障碍、发布和监控不一致，问题还可能在跨栈交界处互相甩锅。应定义统一契约、owner、版本策略和故障归因，并限制技术栈数量；复用收益不足以覆盖边界成本时不要拆分。

**3. 为什么不能用绝对性能结论做决策？**

框架版本、渲染路径、业务复杂度、插件、设备和工程质量都会改变结果；某个 benchmark 只证明特定条件。应以自身关键路径和用户设备分布测试 p75 / p95、失败率与体验 SLO，并把维护和发布成本一起纳入。

:::
