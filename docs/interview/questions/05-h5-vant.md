### Q1. H5 适配你会选 rem、vw 还是别的？viewport 怎么讲清楚？

**考察点：** viewport、rem / vw / 响应式、一倍稿与 DPR

::: details 参考答案
先定目标：设计稿通常 375 / 750，要在不同手机宽度上「比例正确」，并处理大屏不要无限放大。

常见方案：
1. **vw**：CSS 直接按设计稿换算，链路短；注意最小 / 最大字号与横屏；
2. **rem**：`html` 根字号随宽度变（flexible 思路或 postcss-pxtorem），组件内用 rem；灵活，但要搞清「哪些用 rem、哪些用 px」（1px 边框、字号下限）；
3. **现代响应式**：布局用 flex / grid + 断点，间距用 clamp；适合内容型，不只是「整页缩放」。

viewport：`width=device-width, initial-scale=1, viewport-fit=cover`（全面屏安全区时常要 cover）。口述别背公式，要讲**你怎么保证视觉稿还原、大屏是否限宽、与 Vant 的 375 约定如何对齐**。Vant 本身按 375，改根字号要确认没把组件库字号带飞。
:::

**追问：**
1. 为什么有人禁止 `user-scalable=no`？无障碍与业务防误触怎么权衡？
2. `1px` 细线在 DPR=3 设备怎么处理？
3. 横屏、折叠屏你怎么降级布局？

**踩坑：** 只改业务页 rem，第三方嵌入页或弹层按 px 写死，一放大全错位——适配策略要全应用一致。

### Q2. 安全区（safe-area）在刘海屏 / 底部横条上你怎么落地？

**考察点：** `viewport-fit`、`env(safe-area-inset-*)`、固定底栏、Vant 组件

::: details 参考答案
全面屏：顶部刘海 / 灵动岛、底部 Home Indicator 会吃掉固定头尾。做法：
1. `viewport-fit=cover` 允许铺满；
2. 用 `env(safe-area-inset-top/bottom/...)`（或 `constant()` 兼容旧 iOS）给固定栏加 padding；
3. Vant 的 `Tabbar`、`NavBar`、弹层类组件关注其 safe-area 相关 props / 样式变量，别重复加双倍 padding。

内容区：底部固定按钮要抬高；全屏弹层的关闭按钮别贴物理边缘。Android 厂商差异大，真机抽检比只看模拟器重要。

口述结构：为什么需要 → CSS 环境变量 → 和组件库如何配合 → 真机验收清单。
:::

**追问：**
1. 横屏时 inset 变化，固定样式会出什么问题？
2. 内嵌 App WebView 时安全区以谁为准——网页还是原生导航？
3. `safe-area` 与键盘顶起同时出现，优先级怎么处理？

**踩坑：** 给 `body` 加了 bottom inset，又给 `van-tabbar` 加一次，底部巨空白——先分清「谁负责吃安全区」。

### Q3. 滚动穿透（遮罩底下页面跟着滚）你怎么根治？

**考察点：** touch 事件、body 锁滚、`overflow`、iOS 弹性滚动

::: details 参考答案
典型场景：Popup / Dialog / ActionSheet 打开时，底下列表仍在滚。根因是触摸滚动默认作用到背后滚动容器，iOS 弹性滚动更明显。

治理组合拳：
1. 打开弹层时锁 `body`（`overflow: hidden` + 记下 scrollTop，关时还原）——注意会丢掉滚动位置若没记；
2. 弹层内容区自己滚，并在边界 `touchmove` 上 `preventDefault`（要 `passive: false`，且只在需要时绑）；
3. 优先用 Vant 已处理穿透的组件能力，别层层自造；
4. 新方案可关注 `overscroll-behavior: contain`。

十年经验：锁 body 会影响 `position: fixed` 元素抖动——要统一滚动容器策略（只让 `#app` 内某层滚）。
:::

**追问：**
1. 为什么有的页面锁 body 后弹层里也滚不动？
2. 多弹层叠加开关顺序乱了，滚动锁怎么引用计数？
3. 和「整页是自定义下拉刷新容器」冲突时怎么排？

**踩坑：** 全局 `touchmove.preventDefault`——把弹层内部滚动一并掐死，用户以为页面坏了。

### Q4. 弱网环境下 H5 体验你怎么做「能用」而不是「能演示」？

**考察点：** 超时、重试、骨架屏、降级、缓存与离线

::: details 参考答案
弱网不是加个 loading 那么简单。分层：
1. **预期**：骨架屏 / 占位，避免白屏；关键操作按钮防重复提交；
2. **请求**：合理超时、幂等重试（只对安全的 GET / 明确幂等接口）、失败文案分「无网 / 超时 / 业务错」；
3. **数据**：列表保留旧数据再静默刷新；静态资源长缓存；接口层可考虑 SWR 思路；
4. **降级**：大图降清晰度、自动播放视频改点击播放、非首屏模块延迟请求；
5. **可观测**：把慢请求、失败率按页面打点，别等客服反馈。

口述要带场景：地铁、电梯、活动高峰——你怎么保证下单 / 支付路径最短、少依赖非关键资源。
:::

**追问：**
1. 重试会不会造成「下单两次」？边界怎么定？
2. Service Worker 在活动 H5 里你敢上到什么程度？
3. 接口 3 秒才回，产品要「秒开」，你怎么谈判拆首屏数据？

**踩坑：** loading 遮罩全局锁死 30 秒——用户杀进程重进，本地状态与服务端不一致。

### Q5. 移动端输入框与软键盘，你踩过哪些坑？怎么处理？

**考察点：** 键盘顶起、`visualViewport`、focus 滚动、iOS 固定底栏

::: details 参考答案
高频问题：
1. **固定底栏被顶飞 / 遮挡**：iOS 上 `position: fixed` 随键盘表现不一致；应用 `visualViewport` 监听或改为非固定布局；
2. **聚焦后页面被顶起，收起键盘留下空白**：滚动复位；注意 `scrollIntoView` 别过猛；
3. **安卓 WebView 高度变化**：`window.resize` / `visualViewport.resize` 更新布局；
4. **输入体验**：`type`、`inputmode`、`pattern` 正确；数字键盘与小数；禁用自动缩放（字号 ≥16px 是老套路之一）；
5. **Vant Field** 与表单：错误提示别被键盘挡住，提交时滚到首个错误字段。

口述金句：键盘问题没有统一 CSS 银弹，要**分 iOS / Android / 内嵌 WebView** 验收。
:::

**追问：**
1. 为什么有的机型 `100vh` 含键盘区域，布局会跳？
2. 弹层内输入框聚焦，滚动容器该滚弹层还是 window？
3. 第三方安全键盘 / 一键登录 SDK 插入时如何共存？

**踩坑：** 用 JS 强行 `window.scrollTo(0,0)` 清空白，却把用户正在看的长表单滚跑——要只在 keyboard dismiss 时针对性修。

### Q6. H5 路由返回栈与「物理返回 / 右滑返回」你怎么设计？

**考察点：** history、栈管理、拦截返回、与 App 容器协作

::: details 参考答案
浏览器 / WebView 都有历史栈。SPA 用 Vue Router 的 `push/replace/back`。原则：
- 能 `replace` 的中间态（登录后回跳、向导步）别无限 `push`，否则用户按返回会穿梭「脏历史」；
- 弹层 / 筛选面板打开时，可用 `pushState` 占一层，物理返回先关层再退页——体验接近原生；
- 离开未保存表单：`onBeforeRouteLeave` + 确认；
- 内嵌 App：有的容器会劫持返回，需与 JSBridge「返回消费」协议对齐（前端先处理，处理不了再交给原生）。

口述讲清：**返回是产品逻辑，不是只会 `router.back()`**。
:::

**追问：**
1. 微信支付 / 授权中间页跳回，栈乱了怎么修？
2. `keep-alive` 列表页返回保留位置，和路由缓存怎么配？
3. 同一 URL 多打开几次，返回路径爆炸如何治理？

**踩坑：** 每开一个 Popup 都 `push` 历史却忘记关时 `back`，用户要连按多次才能离开页面。

### Q7. 埋点 / 数据分析在 H5 你怎么做才不拖垮业务？

**考察点：** 曝光 / 点击、PV/UV、渠道参数、隐私合规

::: details 参考答案
分层：
1. **自动**：PV、路由变化、基础性能（可接 GA / 神策 / 自研）；
2. **业务**：关键漏斗（曝光商品、点购买、提交订单）——事件名与属性字典化，禁止各写各的中文描述；
3. **技术**：接口失败、白屏、资源超时——给排查用。

实现：异步上报、批量、失败重试；别在点击主路径同步 `await` 埋点。SPM / 渠道：`utm` 或业务 trace 从落地页透传到下单。合规：隐私协议前少采个人信息；可识别信息脱敏。

十年经验：埋点挂了业务不能挂；埋点质量靠评审与校验平台，不靠「多打点」。
:::

**追问：**
1. 曝光埋点如何防「滚过去就算」的误报？
2. SPA 路由 PV 与浏览器刷新如何去重？
3. 和 App 原生埋点如何打通同一用户路径？

**踩坑：** 在 `computed` / 模板渲染路径里发请求打点——一卡顿或重复渲染就数据爆炸。

### Q8. H5 首屏优化你怎么抓？和「整站性能」有何不同？

**考察点：** 关键渲染路径、资源优先级、接口并行、Vant 按需

::: details 参考答案
首屏目标：最快看到**有效内容**（不只是壳）。抓手：
1. **减请求**：路由懒加载、Vant 按需、首屏无关模块后置；
2. **减阻塞**：关键 CSS 内联慎重、字体子集、图片尺寸与格式（WebP/AVIF）、骨架代替白屏；
3. **数据**：首屏接口并行；能内嵌首屏数据更好（注意缓存与个性化）；
4. **容器**：CDN、HTTP/2、DNS 预解析；WebView 可考虑预热与资源预置（与端上协作）；
5. **度量**：LCP / FCP（或业务「首屏可交互」自定义点），按机型与网络分桶。

口述别堆手段：先讲**你如何定义首屏完成**，再讲最大瓶颈是包体、接口还是图片。
:::

**追问：**
1. 活动页首屏要「秒开」，框架 + UI 库体积怎么砍？
2. 骨架屏和真实布局不一致造成的 CLS 你怎么处理？
3. 慢的是 WebView 初始化还是 H5 本身，如何归因？

**踩坑：** 首屏为了炫把轮播大图 + 视频全上，指标全挂——视觉与性能要产品一起砍。

### Q9. H5 与 App WebView 的 JSBridge 你怎么设计与排障？

**考察点：** Bridge 协议、版本兼容、鉴权、调试

::: details 参考答案
Bridge 是「前端调原生能力 / 原生调前端」的契约：登录态、关闭 WebView、分享、支付、扫码、取设备信息等。

设计要点：
1. **协议稳定**：方法名、参数、错误码版本化；未知方法优雅降级；
2. **调用形态**：Promise 化封装 + 超时；原生回调防重复；
3. **注入时机**：`Ready` 事件后再调，别假设 `window.Native` 已在；
4. **安全**：暴露给 H5 的 API 最小集；敏感操作用原生鉴权；
5. **环境探测**：App / 微信 / 浏览器能力矩阵，缺能力走 H5 降级。

排障：约定日志通道、能在 Chrome inspect / Safari Web Inspector 看 H5，原生侧打同 traceId。十年经验：Bridge bug 一半是时序，一半是版本没对齐。
:::

**追问：**
1. iOS `WKWebView` 与安卓注入差异，前端如何抹平？
2. 登录态放 Cookie、Header 还是 Bridge 注入 Token？
3. 如何防止普通浏览器里恶意页调用你们的伪 Bridge？

**踩坑：** 页面 `mounted` 立刻调 Bridge，iOS 偶发未注入——表现为「只有安卓正常」，其实是 Ready 竞态。

### Q10. 下拉刷新与列表加载（Vant List / PullRefresh）你怎么用才不出鬼？

**考察点：** 分页、竞态、空态、触底、与滚动容器

::: details 参考答案
模式：`PullRefresh` 管下拉重置；`List` 管触底加载更多。状态机要清晰：`loading`、`finished`、`error`、空列表。

关键坑：
1. **滚动父容器不对**：List 监听的不是那个滚的元素，永远不触底或疯狂触底；
2. **竞态**：快滑时旧页响应覆盖新页——用请求序号或 abort；
3. **重置**：下拉刷新要清空 list、重置 page、`finished=false`；
4. **筛选变化**：等同刷新，别只改参数不重置；
5. **高度**：父级无高度 / `overflow` 不正确会导致「一进页连续加载很多页」。

口述讲状态机比讲组件 API 更像老人。
:::

**追问：**
1. 总数未知只能「有没有下一页」时，finished 如何判断？
2. 反向列表（聊天）和正向商品列表差异？
3. 下拉刷新与页面自身弹性滚动冲突怎么处理？

**踩坑：** `v-model:loading` 在请求失败时没置回 false——List 卡死，再也加载不了。

### Q11. 图片懒加载与占位，在 H5 里你怎么做才兼顾体验和流量？

**考察点：** IntersectionObserver、`loading=lazy`、尺寸占位、CDN

::: details 参考答案
策略：
1. 首屏关键图不懒加载，次屏 / 列表用懒加载（Vant `Lazyload` 或原生 `loading="lazy"` + Observer 兜底）；
2. **占位**：宽高或 aspect-ratio 先占位，防 CLS；骨架或低清 LQIP / 主色块；
3. **体积**：CDN 按屏宽出图、WebP、质量参数；列表缩略图与详情大图分离；
4. **错误**：加载失败占位与重试；
5. **列表复用**：注意组件复用导致图片不刷新——`:key` 与指令更新。

弱网下优先保证「先出字再出图」；别为了动效用超大 APNG 当图标。
:::

**追问：**
1. 横向滚动列表里懒加载为什么容易「该出不出」？
2. 背景图 `background-image` 如何懒加载？
3. 与 WebP 兼容探测放前端还是 CDN Accept？

**踩坑：** 所有图片一张默认大图占位，首屏请求数没少，体积反而暴涨。

### Q12. Vant 表单与移动端校验体验，你会怎么做「少烦用户」？

**考察点：** Field 校验时机、错误展示、提交路径、无障碍

::: details 参考答案
移动端表单原则：少打断、错得明白、修得方便。
- 校验时机：输入中别狂弹；失焦或提交时集中校验更常见；
- 错误展示：字段下文案 + 提交时滚动到首错；长表单用步骤条拆开；
- 组件：Picker / Datetime / Area 用 Vant 半屏选择，减少键盘输入错误；
- 主键操作：主按钮固定底部（含安全区），二次提交防抖；
- 无障碍：label 关联、错误用 `aria` 可读（视团队要求）。

和中后台差异：屏幕小，一次只做一件事；能选就不输；能默认就默认。
:::

**追问：**
1. 服务端校验错误如何映射回具体 Field？
2. 多步骤表单草稿本地缓存如何做与清理？
3. 验证码倒计时与页面缓存 / 返回如何保持？

**踩坑：** 用 `alert` 做校验失败——系统弹窗体验差，且在 WebView 可能被定制成奇怪 UI。

### D1. H5 如何建立 viewport、动态视口单位与组件库的一致适配基线？

::: details 参考答案
#### 基础结论
适配先定义内容宽度、字号下限、横竖屏和大屏策略，再选择 rem、vw 或响应式布局。`viewport-fit=cover` 只允许内容铺到安全区，不会自动补 inset；Vant 4.x 的尺寸基线、safe-area props 与业务转换配置必须统一。

#### 原理深挖
布局视口、视觉视口和设备像素不是一回事。传统 `100vh` 在地址栏或软键盘变化时可能与可见区域不一致，现代 `svh`、`lvh`、`dvh` 分别表达小、大、动态视口，但内嵌 WebView 的支持取决于系统内核。rem/vw 是 CSS 尺寸映射，不应把 DPR 直接等同于缩放倍数。

#### 工程场景
我会设置标准 viewport，主布局采用 flex/grid 与 `clamp()`，设计稿转换只覆盖约定属性；内容型页面设最大宽度。固定底栏由一个层级消费 `env(safe-area-inset-bottom)`，组件已处理时不重复添加。通过浏览器、iOS/Android WebView、横屏、字体放大和折叠屏矩阵验证。

#### 反例 / 踩坑
全站机械按 750 稿缩放会让平板字号和按钮巨大；禁止用户缩放会伤害无障碍。把 `dvh` 当所有旧 WebView 的通用答案，或 body 与 Vant 组件重复吃安全区，都会产生裁切或巨额空白。

#### 资深回答模板
「我先定义适配目标，再选单位。布局优先响应式，设计稿转换只做受控映射；动态视口与安全区按浏览器和 WebView 能力渐进增强，并由唯一容器负责 inset，最终以真机矩阵验收。」

#### 追问链
1. 用户把系统字体调大后，固定高度组件如何避免截断？
2. iOS 地址栏收起时，`vh`、`dvh` 和 `visualViewport.height` 有何取舍？
3. App 已为 WebView 留出原生安全区，H5 如何协商避免重复？
:::

### D2. 滚动容器、软键盘与弹层如何设计成可恢复的状态机？

::: details 参考答案
#### 基础结论
移动端滚动与键盘问题不能靠一个 CSS 片段解决。先确定唯一主滚动容器，再把弹层打开、输入聚焦、视觉视口变化、键盘收起和路由离开建模，确保滚动位置、焦点和锁状态都能恢复。

#### 原理深挖
键盘出现时布局视口、视觉视口以及 WebView resize 策略可能不同；`visualViewport` 能提供可见区域变化，但并非所有容器一致支持。body 锁滚常通过记录 scrollTop、固定 body 并在关闭时恢复；多弹层必须引用计数，否则先关闭的弹层会误解锁后面的弹层。

#### 工程场景
封装 `useViewportKeyboard` 与 `useScrollLock`：监听 resize/focus/blur，按阈值和时序判断键盘态，但不把高度变化都武断视为键盘。表单聚焦时只滚动最近容器，底部操作栏按可见视口偏移；路由离开和组件卸载强制清理监听、样式与锁计数。

#### 反例 / 踩坑
全局 `touchmove.prevent` 会杀死弹层内部滚动；每次 blur 都 `window.scrollTo(0, 0)` 会丢用户位置。仅用 UA 判断键盘或仅监听 `window.resize`，在部分 iOS 与定制 Android WebView 上会误判。

#### 资深回答模板
「我先统一滚动容器，再把弹层锁滚和键盘视口作为带清理的状态机。能力上优先 visualViewport、resize 做降级，恢复时保留滚动和焦点；所有结论按 iOS、Android、浏览器和 App WebView 真机验证。」

#### 追问链
1. Popup 内嵌长表单时，错误字段滚动应由谁负责？
2. 原生导航栏高度动态变化，H5 如何获得可信可视区域？
3. 页面缓存后再次激活，旧键盘监听和滚动锁如何防重入？
:::

### D3. 弱网与离线恢复如何保证提交不重复、页面不失真？

::: details 参考答案
#### 基础结论
弱网恢复要区分读请求、幂等写和不可自动重试的业务动作。缓存可以提升可用性，但页面必须标识数据新鲜度；订单、支付等状态最终以服务端查询为准，不能因客户端超时就判定失败或重发。

#### 原理深挖
GET 可按退避与抖动重试，写请求需服务端幂等键、去重窗口和状态查询。Service Worker 能缓存静态资源和受控的公共 GET，但受注册范围、更新生命周期、存储配额及 WebView 支持影响；含用户敏感数据的接口不应无差别 Cache First。

#### 工程场景
我会建立请求状态机：idle、pending、unknown、success、failure。断网时保留已展示数据并显示离线标识；网络恢复后合并刷新。草稿带 schema 版本、用户命名空间和过期时间；待提交队列只接收明确可幂等动作，刷新或杀进程后可恢复，并向用户展示处理结果。

#### 反例 / 踩坑
Axios 拦截器对所有错误自动重试，会造成重复下单；把接口响应长期缓存却不标时间，会展示过期库存。`navigator.onLine` 只表示网络接口状态，不保证业务服务可达。

#### 资深回答模板
「我按请求语义设计恢复：读请求可退避重试，写请求必须有服务端幂等键，超时进入未知态再查单。离线缓存带用户、版本和时效，网络恢复做对账；Service Worker 只在支持矩阵和数据边界明确时使用。」

#### 追问链
1. 支付拉起后 WebView 被杀，回来如何恢复订单状态？
2. 多个离线编辑对同一资源产生冲突，如何提示和合并？
3. WebView 禁用或限制 Service Worker 时如何降级？
:::

### D4. WebView Bridge 如何做到协议可演进、调用可追踪且来源可信？

::: details 参考答案
#### 基础结论
Bridge 是跨运行时 RPC，不是往 `window` 上挂几个函数。协议至少包含版本、requestId、方法、参数、结果、错误和超时；安全上要校验页面来源、登录上下文与用户手势，敏感动作由原生再次授权。

#### 原理深挖
iOS `WKScriptMessageHandler`、Android JavaScript 注入及不同 App 版本的注入时序不同。前端要等待 ready 并维护能力协商，而不是只判断 UA。回调需至多结算一次，页面销毁时拒绝未完成 Promise；原生调用 H5 也应校验目标页面与消息 schema。

#### 工程场景
启动时调用 `getCapabilities` 获取协议版本和方法集；每次请求记录 requestId、H5 release、App 版本与 traceId。高风险方法使用域名 allowlist、短时上下文和原生确认，Token 不通过 query 或日志暴露。协议采用向后兼容字段，废弃方法经历观测、告警和版本门槛。

#### 反例 / 踩坑
仅检查 `window.Native` 存在无法防止恶意页面伪造对象；允许任意 URL 页面调用支付、读取 Token 或打开外部链接会扩大攻击面。没有超时和去重时，原生重复回调会导致重复提交。

#### 资深回答模板
「我把 Bridge 当版本化 RPC：ready 后能力协商，请求有 ID、超时、单次结算和统一错误。原生按可信域、会话和用户手势二次校验敏感能力，双方日志用 traceId 串联，不能把 UA 或前端按钮当安全边界。」

#### 追问链
1. App 新增方法但 H5 先发布，如何优雅降级？
2. 登录 Token 应由 Cookie、请求头还是 Bridge 管理？
3. WebView 跳到第三方域名后，如何撤销 Bridge 暴露？
:::

### D5. 浏览器与 App WebView 的返回栈如何组成一致的导航协议？

::: details 参考答案
#### 基础结论
H5 路由栈、浏览器 history 和 App 原生页面栈是三个状态源。必须约定返回优先级：先关闭页面内临时层，再退 SPA 路由，最后通知原生关闭容器；是否消费返回要有明确响应。

#### 原理深挖
`pushState` 只改变浏览器历史，无法天然同步原生手势返回。iOS 侧滑可能先开始原生转场，Android 物理返回则由宿主回调；不同容器还可能禁用 `popstate` 或注入自己的历史。登录、授权、支付中间页应使用可恢复 returnUrl 或业务状态，不依赖「刚好 back 两次」。

#### 工程场景
设计 `canGoBack` / `handleBack` Bridge 协议，H5 返回 `{ consumed, reason }`。Popup 等临时层用统一 overlay stack，只有栈顶消费返回；关键页面保存可恢复业务状态。路由埋点记录 navigationId、来源和动作，自动化用浏览器、安卓物理键、iOS 侧滑及原生关闭按钮分别验收。

#### 反例 / 踩坑
每开弹层都 push 一层、关闭时却忘了回退，会制造幽灵历史；H5 和原生同时执行 back 会直接退出两层。把所有中间跳转都 push，也会让用户在登录和回调页间来回穿梭。

#### 资深回答模板
「我明确三层栈和返回仲裁：临时 UI、SPA、原生容器依次处理，协议返回是否已消费。支付授权靠可恢复状态而非固定回退次数，所有入口和物理返回都进入同一导航状态机。」

#### 追问链
1. 用户从分享链接直接进入二级页，返回应去哪里？
2. `keep-alive` 保留列表位置时，如何避免恢复过期数据？
3. iOS 侧滑进行到一半取消，H5 状态如何保持一致？
:::

### D6. H5 埋点如何同时保证数据质量与 Core Web Vitals 可行动？

::: details 参考答案
#### 基础结论
当前 Core Web Vitals 是 LCP、INP、CLS，良好阈值分别为不高于 2.5 s、200 ms、0.1，并应看第 75 百分位。指标要与页面版本、容器、网络和业务结果关联；实验室分数不能替代真实用户监控。

#### 原理深挖
LCP 受服务端响应、资源发现、下载和渲染延迟共同影响；INP 观察访问生命周期中的交互延迟；CLS 关注无预期布局位移。WebView 预热可能改变 navigation 起点，iframe 与后台上报也有采集边界，因此需要定义统一口径并记录 App 版本与容器启动阶段。

#### 工程场景
事件 schema 版本化，曝光使用 IntersectionObserver 加可见比例和停留时长，点击用 eventId 去重。性能上采用官方 `web-vitals` 口径或等价实现，按路由、机型、网络、浏览器/WebView 分桶，把 LCP 元素、INP 交互目标和 CLS 来源作为诊断维度。上报异步批量，退出时用可用的可靠通道，但不阻塞业务。

#### 反例 / 踩坑
只报平均值会掩盖长尾；把 FCP 当 LCP、把接口结束当首屏完成，会优化错目标。在 computed、render 或滚动回调直接打点会重复上报并拖慢页面，形成观测干扰。

#### 资深回答模板
「我先统一事件与性能口径，再看真实用户的 P75。Core Web Vitals 按 LCP、INP、CLS 分解到元素、交互、位移来源，并带上 release、容器和网络维度；埋点有版本、去重和质量监控，挂掉不能阻塞主链路。」

#### 追问链
1. WebView 初始化慢与 H5 LCP 慢如何拆分责任？
2. 无 CrUX 数据的内网或 App H5，如何建立性能基线？
3. 埋点被广告拦截或页面快速关闭时，质量如何评估？
:::

### D7. 长列表、图片与手势竞争如何在低端机上一起治理？

::: details 参考答案
#### 基础结论
长列表性能是数据、DOM、图片解码、响应式更新与手势调度的组合问题。先分页或窗口化，再控制单项复杂度；图片必须预留尺寸并按显示尺寸下发，手势只在方向明确后接管。

#### 原理深挖
图片下载完成后仍需解码和上传纹理，大图缩成缩略图显示也会占内存。虚拟列表回收 DOM 时，本地状态和曝光状态必须按 itemId 外置。横向 Swipe 与纵向页面滚动竞争时，应设置方向阈值、touch-action 和被动监听策略，避免每帧同步布局读取后再写样式。

#### 工程场景
Vant List 管分页状态，必要时接入经过真机验证的虚拟方案；请求支持取消和游标去重。图片用 `srcset`/CDN 参数、WebP/AVIF 能力与 aspect-ratio 占位，首屏 LCP 图不懒加载并设置优先级。手势动画用 transform，复杂计算按帧节流，并尊重减少动态效果偏好。

#### 反例 / 踩坑
仅加 `loading="lazy"` 不会解决原图过大和解码峰值；虚拟列表用下标 key 会串图、串选中态。全局阻止 touchmove 会让纵向页面无法滚动，JS 跟手修改 top/left 还会反复布局。

#### 资深回答模板
「我用性能录制区分列表更新、图片解码和手势任务。数据分页、DOM 窗口化、状态按 ID 外置；图片按展示尺寸下发并占位，手势先判方向再用 transform 驱动，最后在低端真机和弱网一起验收。」

#### 追问链
1. 聊天反向列表追加历史消息时，如何保持视觉锚点？
2. 图片预览为什么容易造成内存峰值，如何释放？
3. 虚拟列表中的曝光埋点如何避免重复计算？
:::

### D8. H5 使用 SSE 或流式 Fetch 时，重连、鉴权与 WebView 边界是什么？

::: details 参考答案
#### 基础结论
SSE 适合服务端单向推送，原生 `EventSource` 以 URL 建连，只提供有限配置，不能自定义 POST 方法和任意请求头；需要 POST、细粒度 Header 或自定义流解析时可考虑 Fetch ReadableStream，并验证 WebView 支持。

#### 原理深挖
SSE 使用 `text/event-stream`，事件块可带 `id`、`event`、`data` 和 `retry`；浏览器会重连，可通过 Last-Event-ID 续传，但服务端必须保存或重放相应游标。HTTP/1.x 下同域并发连接数较低，HTTP/2 由流并发协商；代理缓冲、空闲超时和页面后台冻结都可能让「连接还在」成为假象。

#### 工程场景
协议定义 eventId、序号、心跳、终态和可重放窗口。鉴权优先同源安全 Cookie 或短时一次性票据，不把长期 Token 放 query；断线按指数退避加抖动，恢复时先对账再续流。页面隐藏、路由离开和 App 切后台时关闭或暂停，前台恢复后检查任务最终状态。

#### 反例 / 踩坑
把 SSE 当双向 WebSocket、每条消息都直接改大列表、无限立即重连，都会放大故障。依赖自定义 Authorization Header 的原生 EventSource 方案通常落不了地；只看 `onopen` 也不能证明代理没有缓冲消息。

#### 资深回答模板
「我先确认是单向事件流，再选 EventSource 或流式 Fetch。协议有事件 ID、心跳、终态和重放，重连先对账且带退避；鉴权不用长期 query Token，并把代理、HTTP 版本、后台冻结和 WebView 内核纳入验收。」

#### 追问链
1. AI 流式输出中途断线，如何避免文本重复或缺段？
2. 服务端无法重放历史事件时，客户端恢复策略是什么？
3. iOS WebView 切后台后连接被冻结，回前台如何判活？
:::
