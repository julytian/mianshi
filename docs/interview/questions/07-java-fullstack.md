### Q1. Spring Boot 分层（Controller / Service / Mapper）你会怎么划，避免「上帝类」？

**考察点：** 分层职责、DTO/VO/Entity、前端可感知的接口边界

::: details 参考答案
默认三层心智：

1. **Controller**：协议层——接参、校验入口、调 Service、组装统一响应；不写业务规则、不直接拼 SQL。
2. **Service**：业务编排——事务边界、领域规则、跨表流程；可再拆 Domain / Application，单体够用即可。
3. **Mapper（DAO）**：数据访问——MyBatis-Plus 或 XML；只关心持久化，不关心 HTTP。

对象别混：`Entity` 贴表；入参用 `DTO` / `Query`；出参用 `VO`——别把表实体直接甩给前端（字段泄露、改表牵动前端）。前端视角：你关心的是 **URL + 入参契约 + 错误码**，后端分层是为了改业务时不把 Controller 写成 800 行。

AI 生成代码常见病：业务写进 Controller、Service 互相循环依赖——Review 时先砍分层越界。
:::

**追问链：**
1. 分页查询的筛选条件放 Controller 拼还是 Service？边界怎么定？
2. 多个 Controller 共用一段「状态流转」，你会抽到哪一层？
3. 什么时候值得引入 Facade / Manager，什么时候过度设计？

::: details 追问参考答案

**1. 分页查询的筛选条件放 Controller 拼还是 Service？边界怎么定？**

Controller 只负责把 query 参数绑定、校验并转换为查询 DTO，不直接拼 `QueryWrapper`。筛选组合、数据权限、默认排序和分页上限属于业务或数据访问规则，应由 Service 编排，Mapper 落 SQL。这样同一查询被导出、定时任务复用时语义一致，也便于单测；纯协议格式转换才留在 Controller。

**2. 多个 Controller 共用一段「状态流转」，你会抽到哪一层？**

状态流转是业务规则，应抽到 Service 或领域服务，由一个方法统一校验当前状态、操作者权限、目标状态和副作用，并在事务内完成持久化。Controller 只传入命令并映射响应。若不同入口只是参数或展示不同，可共享同一用例；不要抽成静态工具类，否则事务、依赖和审计上下文都难管理。

**3. 什么时候值得引入 Facade / Manager，什么时候过度设计？**

当一个用例需要编排多个 Service、对外提供稳定粗粒度入口，或需隔离第三方与领域模型时，可引入 Facade；Manager 可承接无明确实体归属的复合能力。若只是单表 CRUD、仅转发一个 Service，新增层只会制造跳转和 DTO 搬运。判断标准是是否降低耦合、明确边界，而不是层数是否显得完整。

:::

**踩坑：** 为了「快」，Controller 直接 `mapper.selectList`——联调能通，但权限、事务、复用全散掉，二期必还债。

### Q2. 统一响应体与错误码，前后端怎么约定才不天天扯皮？

**考察点：** `code` / `message` / `data`、业务码 vs HTTP 状态、前端拦截器

::: details 参考答案
常见约定：

```json
{ "code": 0, "message": "ok", "data": {} }
```

或 `success` + `code`。关键是 **一份文档写死**：

- 成功：`code === 0`（或 200 业务码），`data` 有类型；
- 失败：业务可预期错误用**稳定业务码**（如 `40001` 参数错、`40100` 未登录、`40300` 无权限），`message` 可展示；
- HTTP：不少团队成功统一 200，用 body.code 区分——前端 axios 拦截器认业务码；也有 REST 派用 4xx/5xx，但要和网关、文件下载例外对齐。

前端落地：请求封装里统一拆包、`message` toast、特殊码跳登录；页面只处理 `data`。后端用全局异常处理（`@ControllerAdvice`）把校验异常、业务异常映射到同一形状，**禁止**有的接口扔字符串、有的扔 HTML。

口述强调：错误码是产品契约，不是后端私有实现细节。
:::

**追问链：**
1. 列表空与「资源不存在」要不要不同码？前端怎么表现？
2. 国际化时 `message` 谁翻译——后端还是前端按 code 映射？
3. 文件下载 / 导出流式响应如何绕过统一 JSON 包装？

::: details 追问参考答案

**1. 列表空与「资源不存在」要不要不同码？前端怎么表现？**

列表经行级权限过滤后无结果，返回 200 与空 `list`；用户已知并访问无权接口时返回 403。按 ID 查询若存在枚举风险，则对「不存在」和「无权查看」统一返回 404，对外状态、文案及可观察耗时保持不可区分。内部受控安全审计必须区分两类决策，仅记录非敏感主体与资源标识、决策原因和 traceId，并按最小权限限期留存，绝不泄露给客户端。

**2. 国际化时 `message` 谁翻译——后端还是前端按 code 映射？**

稳定业务 `code` 才是机器契约。面向多端产品时，前端按 code 和本地语言包翻译更易随界面统一；后端保留默认 message 供日志与兜底。服务端校验的动态参数可返回 message key 加参数，由前端格式化。若邮件、短信等由后端直接触达用户，则后端按明确 locale 翻译，避免双方各翻一半。

**3. 文件下载 / 导出流式响应如何绕过统一 JSON 包装？**

下载接口直接写响应流并设置正确的 `Content-Type`、`Content-Disposition`，通过返回 `ResponseEntity<Resource>`、`StreamingResponseBody` 或框架排除规则绕过统一包装。前端以 blob 接收，但仍要根据状态码和响应类型识别 JSON 错误。不要先把整个文件读入内存，也不能让响应切面把二进制序列化成统一 JSON。

:::

**踩坑：** 成功时 `data` 有时是对象有时是数组有时直接是分页结构——TS 类型全崩；约定「列表永远 `{ list, total }`」。

### Q3. RESTful 接口你会怎么设计，和「前端真正好用」怎么平衡？

**考察点：** 资源路径、动词、幂等语义、查询 vs 命令

::: details 参考答案
原则：名词资源 + HTTP 动词表达动作。

- `GET /api/orders` 列表；`GET /api/orders/{id}` 详情；
- `POST /api/orders` 创建；`PUT/PATCH` 更新；`DELETE` 删除（或软删用状态字段）。

实战会妥协：复杂动作用 `POST /api/orders/{id}/cancel` 比硬套 DELETE 更清晰；批量操作用 `POST .../batch-delete`。**不要**为了 REST 纯度让前端传一堆难懂的 method override。

与前端协作清单：

1. 路径稳定、版本可演进（`/api/v1` 或网关路由）；
2. 筛选用 query，body 留给写操作；
3. 幂等：GET 安全；写操作考虑 Idempotency-Key 或业务唯一键；
4. 文档（OpenAPI / Apifox）与实现同步，枚举值前后端同一份。

口述：我按资源建模，但交付导向——前端少拼怪 URL、少猜副作用。
:::

**追问链：**
1. 为什么「登录」常用 POST 而不是 GET？
2. 部分更新用 PUT 还是 PATCH，你们团队怎么定？
3. 管理后台大量「审核通过」类动作，全做成 RPC 风格 POST 可以吗？

::: details 追问参考答案

**1. 为什么「登录」常用 POST 而不是 GET？**

登录会提交密码、验证码等敏感凭证并创建会话或签发 Token，具有副作用，因此用 POST 更符合语义。GET 参数容易进入 URL、浏览器历史、代理日志和缓存，还可能被预取，风险更高。即使用 HTTPS，也不应把凭证放查询串；响应还应禁止缓存、限制频率，并避免在错误信息中泄露账号是否存在。

**2. 部分更新用 PUT 还是 PATCH，你们团队怎么定？**

PUT 通常表示用完整资源表示替换目标，重复提交结果相同；PATCH 表示提交部分变更，更适合后台表单只改少数字段。团队可约定更新接口统一用 PATCH，或把 PUT 定义为可选字段更新，但必须在 OpenAPI 写清缺失字段是保留还是清空。无论选哪种，都要做字段白名单、版本冲突和服务端权限校验。

**3. 管理后台大量「审核通过」类动作，全做成 RPC 风格 POST 可以吗？**

可以，审核、取消、发布是领域命令，用 `POST /orders/{id}/approve` 往往比硬套 CRUD 更清晰。关键是路径和命名一致，明确状态前置条件、权限、幂等与审计，并返回稳定错误码。若动作只是资源字段的普通修改，可用 PATCH；若包含流程流转和副作用，显式命令端点更能表达业务，不必追求形式纯度。

:::

**踩坑：** 用 GET 做删除或改状态——缓存、预取、爬虫会误触发；浏览器还会把参数打进日志。

### Q4. MyBatis-Plus 的 CRUD 与分页，你会怎么接到前端表格？

**考察点：** `IPage`、`Page`、条件构造、与 AntDV Table 对齐

::: details 参考答案
后端：`Page<T> page = new Page<>(pageNum, pageSize)` + `lambdaQuery` / `QueryWrapper`，返回 `{ list, total }`（或 MP 的 `records` / `total`，**在 VO 层统一成前端字段名**）。

分页不是只传 `Page` 就自动生效，还要注册插件：

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    PaginationInnerInterceptor pagination =
        new PaginationInnerInterceptor(DbType.MYSQL);
    pagination.setMaxLimit(100L);
    interceptor.addInnerInterceptor(pagination); // 多插件时通常放最后
    return interceptor;
}
```

MyBatis-Plus 从 3.5.9 起将分页插件依赖拆开；使用 `PaginationInnerInterceptor` 时需显式加入与核心版本对齐的 `mybatis-plus-jsqlparser`（或对应支持模块），不能只抄配置却漏依赖。具体 artifact 与版本以项目所用官方版本文档为准。

前端表格惯例：`current` / `pageSize` / `total`；翻页、改 pageSize 重新请求。注意：

1. **页码从 0 还是 1**——写进约定，别有的接口从 0；
2. 排序字段白名单，防 SQL 注入式 `orderBy` 拼接；
3. 最大 `pageSize` 封顶（如 100），导出走专用接口不是拉 pageSize=99999；
4. 软删、数据权限（只看自己部门）放在 Service / 拦截器，别指望前端不传就能安全。

口述带一句联调：先对一份「空列表、一页满、最后一页不足 pageSize」三种响应，表格空态与分页器才稳。
:::

**追问链：**
1. 深分页（翻到很大页）性能问题，前后端怎么一起降级？
2. `select *` 大宽表列表页你会怎么收字段？
3. 前端「前端分页」和「后端分页」选型标准？

::: details 追问参考答案

**1. 深分页（翻到很大页）性能问题，前后端怎么一起降级？**

大偏移分页会扫描并丢弃大量记录，可限制最大可跳页数，对连续浏览改用基于稳定排序键的游标分页，如 `createdAt + id`。前端相应取消任意跳页，提供「加载更多」或缩小筛选范围提示。后台导出走异步任务。若业务必须跳页，再结合覆盖索引和延迟关联优化，但不能承诺任意深度都等时。

**2. `select *` 大宽表列表页你会怎么收字段？**

先按页面真实展示和交互定义列表 VO，SQL 只选择主键、展示字段、状态与必要关联键，详情再按需查询。大文本、JSON、Blob 和敏感字段不进列表，关联名称可 join 或批量补齐。字段收窄能减少磁盘 IO、网络传输和序列化成本，也避免 Entity 新增列后被无意暴露；仍需用执行计划验证索引覆盖效果。

**3. 前端「前端分页」和「后端分页」选型标准？**

数据量固定且很小、已因其他目的完整加载、无敏感数据时可前端分页，交互快但首包成本高。数据持续增长、需服务端筛选排序、权限隔离或总量较大时必须后端分页。不能为省接口一次拉全量，也不能让前端分页掩盖权限问题。选型要结合数据上限、更新频率、网络成本和导出需求写明阈值。

:::

**踩坑：** 总数用错误的 count 查询（join 膨胀）导致分页器乱跳——count 与 list 策略要一致，必要时单独 count SQL。

### Q5. 复杂查询与前端筛选联动，条件怎么设计才可演进？

**考察点：** 动态条件、时间范围、多选、模糊查、前后端字段映射

::: details 参考答案
管理后台典型：关键字、状态下拉、多选标签、创建时间 range、关联组织树。

后端设计：

1. 查询对象 `OrderQuery`：可选字段全 null-safe；MP `lambdaQuery` 里 `eq` / `like` / `in` / `between` 按需拼接；
2. 时间：前端传 ISO 或 `yyyy-MM-dd HH:mm:ss`，约定时区；结束时间用「次日 0 点」还是 `23:59:59` 写死；
3. 模糊：`like` 左右 `%` 有索引代价，重要字段考虑前缀或搜索服务；
4. 枚举：前后端同一 code，禁止前端传中文「已完成」。

前端：筛选变更防抖、重置页码到 1、URL query 同步（可分享筛选态）。联调时用「只改一个筛选项」抓包，确认未带脏字段。

口述结构：契约（Query 字段）→ 动态 SQL 安全拼接 → 前端重置分页 → 性能底线。
:::

**追问链：**
1. 多表关联筛选导致慢，你会拆接口还是加冗余字段？
2. 「全部 / 未删除 / 回收站」三态和软删字段怎么映射？
3. 筛选条件 15 个，AI 生成了一坨 if，你怎么重构？

::: details 追问参考答案

**1. 多表关联筛选导致慢，你会拆接口还是加冗余字段？**

先用真实 SQL、数据量和执行计划定位瓶颈，补合适索引、收窄字段或改批量查询，不能凭感觉拆接口。高频查询且关联值变化少时，可冗余可检索字段，但要定义更新链路、回填与对账。拆接口适合展示数据可延迟加载且允许前端分阶段呈现；若筛选语义必须原子一致，拆开会改变结果，应保留服务端统一查询。

**2. 「全部 / 未删除 / 回收站」三态和软删字段怎么映射？**

查询 DTO 用明确枚举如 `scope=active|deleted|all`，不要让前端直接传数据库删除标记。Service 将 active 映射为未删、deleted 映射为已删，all 仅对有权限的管理场景开放；MyBatis-Plus 逻辑删除默认会过滤已删数据，查询回收站通常需专门 SQL。恢复和彻底删除也应是独立命令并记录审计。

**3. 筛选条件 15 个，AI 生成了一坨 if，你怎么重构？**

先保留类型化 Query DTO 和白名单，再按值类型封装可复用条件方法，如字符串空白、时间范围、枚举集合；复杂组合用规格对象或专用 Mapper SQL，避免反射式万能拼接。重构目标是让每个字段语义可读、可测，而非消灭所有 if。排序列必须服务端映射，不能把字段名和方向原样拼进 SQL。

:::

**踩坑：** 前端把 `undefined` 序列化成字符串 `"undefined"` 或空字符串当等值查——后端要把空白当「未传」。

### Q6. JWT 登录态怎么设计，前端 Token 存在哪、怎么续期？

**考察点：** 登录签发、Authorization、存储选型、过期与刷新

::: details 参考答案
链路：

1. 登录校验账号密码（或短信）→ 服务端签发 JWT（或 Sa-Token 同类方案）→ 返回 `accessToken`（可加 `refreshToken`）；
2. 前端存：**管理后台**常见 `localStorage` / `sessionStorage`，或内存 + 持久化策略；**更敏感场景**评估 HttpOnly Cookie（要处理 CSRF）；
3. 请求头：`Authorization: Bearer <token>`；
4. 过期：拦截器遇 401 / 业务码未登录 → 尝试 refresh（单飞，避免并发打爆）→ 失败跳登录并带 redirect。

资源服务按**本地信任配置**校验签名算法与可信密钥，并把 `iss` 与配置的 issuer 精确匹配、把 `aud` 与本服务配置的 audience 匹配；不是 Token 里「存在这两个 claim」就算通过。还要校验 `exp`、`nbf` 等时效约束。Spring Security 可用 `issuer-uri` 与 `audiences` 配置，或组合对应 validator。

讲清边界：JWT 适合无状态水平扩展；需要强制下线 / 踢人时，往往要黑名单或改用服务端 session（Redis）。前端不解析敏感业务权限当唯一依据——权限仍以服务端为准。

口述金句：Token 在哪存是安全与体验的权衡，续期要做单飞。
:::

**追问链：**
1. 多 Tab 同时 401，如何只刷新一次？
2. Token 放 localStorage 的 XSS 风险你怎么跟安全同学对齐？
3. 小程序 / H5 / 后台三端登录态能否共用一套签发？

::: details 追问参考答案

**1. 多 Tab 同时 401，如何只刷新一次？**

单个 Tab 内用共享 Promise 和请求队列保证同一时刻只有一个 refresh；跨 Tab 可用 `BroadcastChannel` 或带租约的存储协调，让一处刷新后广播新 Token，其他页面重放请求。refresh token 必须轮换，服务端记录 token family，旧令牌再次出现视为重放并撤销整族。协调失败时宁可重新登录，不能无限刷新循环。

**2. Token 放 localStorage 的 XSS 风险你怎么跟安全同学对齐？**

`localStorage` 中的 Token 可被同源 XSS 脚本直接读取，风险不能靠过期时间消除。应结合威胁模型决定：敏感系统优先 HttpOnly、Secure、SameSite Cookie，并补 CSRF 防护；若业务仍用存储型 Token，则缩短 access token、限制权限，落实 CSP、输出编码和依赖治理。最终方案需记录攻击面、体验代价与应急撤销能力。

**3. 小程序 / H5 / 后台三端登录态能否共用一套签发？**

可以共用身份中心和密钥治理，但不应无差别复用同一 Token。各端应使用不同 client、audience、有效期和刷新策略，资源服务严格校验 `iss` 与目标 `aud`；后台高权限账号还可要求 MFA。权限由服务端按用户、租户和客户端上下文判定，前端解析 claim 只能优化展示，不能成为授权依据。

:::

**踩坑：** 前端「永不过期」或把过期时间只存在客户端不校验——改系统时间或过期后继续带旧 Token 刷接口，直到网关才爆。

### Q7. 权限码前后端怎么对齐？（菜单、按钮、接口）

**考察点：** RBAC、权限码、路由守卫、接口鉴权一致性

::: details 参考答案
三层权限要对齐同一套 code（如 `order:export`）：

1. **菜单 / 路由**：后端返回可访问菜单树或权限列表，前端动态路由；
2. **按钮**：`v-permission="'order:export'"` 控制显隐——**仅 UX**，不是安全边界；
3. **接口**：Gateway / 拦截器 / 方法注解校验同一权限码；无权限返回 403 业务码。

数据权限（仅本部门订单）在 Service 拼条件或行级过滤，前端筛选器不能当成隔离手段。

联调清单：给测试账号「有菜单无按钮」「有按钮无接口」两种错误配置，确认不会误以为「前端藏了就安全」。角色变更后要能刷新权限（重新拉 profile 或重新登录）。
:::

**追问链：**
1. 权限码该由前端写死字典还是完全后端下发？
2. 超管绕过与普通角色，接口层如何统一？
3. 按钮级权限与「行内操作是否可见」如何结合数据状态（如已关闭订单）？

::: details 追问参考答案

**1. 权限码该由前端写死字典还是完全后端下发？**

权限码的定义和授权关系应以后端为真源，前端可以在代码中引用类型化常量，避免拼写错误，并由登录资料下发当前用户的能力集合。菜单结构可后端配置，也可前端维护路由元数据后按权限过滤。无论展示如何实现，接口都必须再次授权；不能因为后端下发了按钮就信任客户端提交的权限码。

**2. 超管绕过与普通角色，接口层如何统一？**

把超管作为授权策略的一种输入，在统一的鉴权组件或方法注解中先判断可信身份的超级管理员标记，再评估普通权限码和数据范围。不要在每个 Controller 散落 `if (admin)`，也不要接受客户端传入超管标识。高危操作即使超管也可保留二次确认、审计和不可绕过的合规约束，避免万能账号失控。

**3. 按钮级权限与「行内操作是否可见」如何结合数据状态（如已关闭订单）？**

可操作性同时取决于用户能力和资源状态：前端只有在拥有权限码且行状态允许时展示或启用按钮，并给禁用原因；后端收到命令后重新读取当前状态、校验数据权限和状态机，再执行原子更新。列表可返回 `allowedActions` 优化复杂规则展示，但它只是快照，并发变化后仍以服务端即时判定为准。

:::

**踩坑：** 只做了菜单权限，导出 / 删除接口裸奔——抓包改 URL 就能越权；口试一定要主动提接口鉴权。

### Q8. Redis 在业务里你会用在哪些场景？（口语级）

**考察点：** 会话、热点缓存、限流/防重、分布式锁心智

::: details 参考答案
前端偏全栈够用的场景：

1. **登录会话 / Token 黑名单 / 验证码**：短 TTL，读写频繁；
2. **热点读缓存**：配置、字典、商品详情；减轻 MySQL；
3. **防重复提交 / 占位**：同一业务键用 `SET key value NX EX <seconds>` 或 `SET key value NX PX <milliseconds>` 做短时占位，并由数据库唯一约束兜底；
4. **限流**：固定/滑动窗口、令牌桶等需要计数与时间语义；多步读改写通常用 Lua 保证原子性，不能把一次 `SET NX` 直接等同于限流；
5. **分布式锁（轻量）**：定时任务或下单防并发（讲清边界，不吹完美）；
6. **排行榜 / 计数** 等结构型需求（按需）。

不滥用：不是所有 DB 查询都先套 Redis——多一层一致性与运维成本。MQ（如 RabbitMQ）用于异步解耦（发短信、削峰），和 Redis 职责别混。

口述：先说场景与 TTL，再说失败降级（Redis 挂了读库还是失败），显得你交过真实系统。
:::

**追问链：**
1. 验证码存 Redis 的 key 设计要注意什么？
2. 缓存穿透 / 击穿你怎么口语解释，会采取哪一招？
3. 什么数据绝对不该进 Redis？

::: details 追问参考答案

**1. 验证码存 Redis 的 key 设计要注意什么？**

手机号低熵，Key 应使用服务端密钥对规范化号码做 HMAC，并带环境、业务和密钥版本；日志既不记录完整号码，也不记录可关联摘要。密钥轮换需保留短暂双版本查找窗口，待旧验证码 TTL 到期后下线旧密钥。校验用 Redis Lua 原子完成比对、失败计数与成功删除；失败计数沿用剩余 TTL，达到上限后锁定至过期，禁止先 `GET` 再 `DEL`。

**2. 缓存穿透 / 击穿你怎么口语解释，会采取哪一招？**

穿透是持续查询本来就不存在的数据，每次都落到 DB，可用参数校验、短 TTL 空值或布隆过滤器；击穿是单个热点 Key 失效时大量并发同时回源，可用逻辑过期、请求合并或带超时的互斥重建。两者都要配限流和降级，并监控回源量；锁只减少并发重建，不保证数据库与缓存强一致。

**3. 什么数据绝对不该进 Redis？**

不能把 Redis 当唯一事实库保存余额、库存扣减结果、订单终态等不可丢失且需强一致审计的数据；明文密码、私钥、完整身份证等高敏信息也不应因读取方便直接缓存。超大对象、几乎不读或频繁整体变更的数据通常也不合算。确需缓存敏感派生数据时，应最小化字段、加密、短 TTL 并严格控制访问。

:::

**踩坑：** 缓存 key 没有业务前缀与环境前缀，测试环境冲掉生产，或不同模块 key 冲突。

### Q9. 缓存与数据库一致性，你怎么口语讲清楚？

**考察点：** 旁路缓存、过期、延迟双删心智、可接受不一致

::: details 参考答案
先定业务容忍度：字典晚 1 分钟可接受；库存/余额通常不能只靠「最终随便一致」。

常见实践（单体够用）：

1. **Cache-Aside**：读：先缓存，未命中读 DB 再回填；写：先更新 DB，再删缓存（或更新缓存）；
2. **TTL** 作为兜底，避免永久脏数据；
3. 并发下「删缓存与写 DB」乱序可能导致脏读——延迟双删、订阅 binlog 是进阶，面试点到「知道问题、一般用删缓存+TTL」即可；
4. 强一致场景：少缓存或短 TTL + 以 DB 为准的读路径。

前端协作：用户改完资料立刻在 UI 显示乐观更新，同时接受详情页再次拉取；管理后台「保存成功仍见旧值」往往是 CDN/本地缓存或后台缓存未删——联调时对一下是否打到带缓存的接口。

边界：不讲论文级分布式事务，讲「可接受窗口 + 删除策略 + 兜底过期」。
:::

**追问链：**
1. 为什么很多人推荐「更新 DB 后删缓存」而不是「更新缓存」？
2. 热点 Key 过期瞬间打崩 DB，怎么缓解？
3. 前端能否「改完强制带 timestamp 刷接口」规避缓存？适用吗？

::: details 追问参考答案

**1. 为什么很多人推荐「更新 DB 后删缓存」而不是「更新缓存」？**

Cache-Aside 中 DB 是事实源，写成功后删缓存，下次读再按最新数据回填，能避免每个写路径都正确计算缓存对象，也减少低频读取数据的无效更新。仍存在提交后删除失败或并发回填旧值的窗口，所以要在事务提交后删、设置 TTL，并对关键场景用重试、binlog 失效或对账兜底，而非宣称绝对一致。

**2. 热点 Key 过期瞬间打崩 DB，怎么缓解？**

可给 TTL 加随机抖动避免批量同时过期，对单热点使用请求合并、互斥重建或逻辑过期，让一个请求回源，其余等待或读可接受的旧值。还要预热热点、限制回源并发，并准备本地缓存或降级数据。互斥锁必须带唯一 token、过期时间并校验后释放；它解决惊群，不把缓存变成强一致系统。

**3. 前端能否「改完强制带 timestamp 刷接口」规避缓存？适用吗？**

时间戳只能绕过浏览器、CDN 或按完整 URL 建 Key 的 HTTP 缓存，对后端按业务 Key 读取 Redis 没有必然作用，还会破坏 CDN 命中并掩盖失效链路。保存后前端可更新本地视图并重新查权威接口，但后端必须正确提交 DB、删除缓存并返回版本。调试时可临时绕缓存，不能作为生产一致性方案。

:::

**踩坑：** 只更新缓存不更新 DB，或事务回滚了但缓存已写——双写无事务是一致性事故高发区。

### Q10. 幂等与防重复提交，前后端怎么配合？

**考察点：** 幂等键、Token、唯一约束、按钮防抖

::: details 参考答案
重复提交来源：双击、弱网重试、网关超时客户端重放。

组合拳：

1. **前端**：按钮 loading、提交中禁用、防抖；**不能当唯一手段**；
2. **后端幂等**：
   - 业务唯一键（订单号、`uk_user_activity`）；
   - 请求头 `Idempotency-Key` / formToken：Redis setnx，TTL 内重复请求返回首次结果或明确「处理中」；
   - 状态机：已支付不能再支付；
3. **安全重试**：仅对明确幂等的写接口自动重试；支付/创建类要业务幂等。

口述场景：创建订单按钮连点——前端立刻锁，后端唯一索引或幂等键兜底，用户看到「请勿重复提交」而不是两笔订单。
:::

**追问链：**
1. 幂等键由前端生成还是后端发 formToken？各有什么利弊？
2. 超时后用户刷新页面再提交，如何与「真失败」区分？
3. MQ 消费为什么也要幂等？

::: details 追问参考答案

**1. 幂等键由前端生成还是后端发 formToken？各有什么利弊？**

前端生成 UUID 适合离线或可重试创建，少一次请求，但服务端必须把它绑定用户、接口和请求摘要，不能盲信任；后端预发 formToken 可控制有效期和使用次数，安全语义清晰，却多一次获取并要处理过期。无论来源，都应在服务端原子占位、保存首次结果，并以数据库业务唯一约束作最终兜底。

**2. 超时后用户刷新页面再提交，如何与「真失败」区分？**

超时只表示客户端没收到结果，不能推断服务端失败。客户端应使用原 Idempotency-Key 查询原请求状态或安全重放，服务端返回处理中、成功结果或明确失败；也可按业务单号提供查单接口。只有确认未创建且幂等记录已终止，才允许新建。客户端回调和页面状态都不是事实源，订单或支付结果以服务端查单为准。

**3. MQ 消费为什么也要幂等？**

MQ 常按至少一次投递设计：消费者处理成功后 ACK 可能丢失，Broker 会重投；消费超时、重平衡和人工重放也会产生重复。消费者应以业务唯一键、事件 ID 去重表或状态机保证重复消息不重复扣款、发券。幂等记录与业务写入最好在同一数据库事务内，否则先记去重再写失败会造成永久漏处理。

:::

**踩坑：** 只做前端禁用，用户开两个 Tab 或重放抓包仍能建双单——口试一定要落到服务端。

### Q11. 事务边界放哪？前端重复点击和事务有什么关系？

**考察点：** `@Transactional`、传播、长事务、与 HTTP 请求的关系

::: details 参考答案
事务放在 **Service 业务方法**，不要包在 Controller，更不要包住远程 HTTP / 发邮件等慢 IO。

原则：

1. 一个业务用例一个事务（下单写订单+明细）；
2. 查多写少可拆：先校验再短事务写入；
3. 默认 `proxy` 模式只拦截经代理进入的外部调用；同类内部自调用绕过代理，因此目标方法上的 `@Transactional` 不会因此启动新事务。若显式使用 AspectJ weaving，则不受这条代理边界限制；
4. 默认回滚规则通常是 `RuntimeException` / `Error` 回滚、checked exception 不回滚；可用 `rollbackFor` / `noRollbackFor`，Spring 6.2+ 还可配置全局默认。吃掉异常不抛出仍会让事务误提交。

与前端：重复点击可能开启两段并发事务——靠幂等与唯一约束，不靠「事务自己去重」。长事务拖连接池，列表接口更不该开事务。

口述：事务是 DB 一致性工具，不是防重复提交工具；边界要短、要在业务层。
:::

**追问链：**
1. 事务里调第三方支付接口为什么危险？
2. 只读接口要不要开事务？
3. 多数据源下事务还能怎么讲（点到为止）？

::: details 追问参考答案

**1. 事务里调第三方支付接口为什么危险？**

数据库事务持锁和占连接期间调用外部支付，网络延迟会放大锁等待；若支付成功但本地事务回滚，或本地提交后响应丢失，就出现跨系统不一致。更稳妥的是短事务记录订单与 outbox，再异步调用并按业务单号幂等、查单和补偿。不能把远程 HTTP 当成本地事务的一部分，也不能信客户端支付回调。

**2. 只读接口要不要开事务？**

简单单次查询通常无需显式事务；多个查询必须看到同一快照时，可在 Service 使用只读事务并结合数据库隔离级别。`readOnly=true` 主要是给事务管理器和驱动的优化提示，不是安全权限，也不保证所有数据库禁止写入。默认代理模式仍要求经代理调用才生效，自调用目标方法不会凭注解开启新的事务。

**3. 多数据源下事务还能怎么讲（点到为止）？**

一个本地事务管理器通常只覆盖它绑定的数据源，方法里同时写两个库不会自动获得原子性。强一致确有必要时才评估 JTA/XA，并承担性能和运维成本；多数业务优先按边界拆分，用本地事务加 outbox、幂等消费、重试和对账实现可验证的最终一致。需要先明确失败状态与补偿责任人。

:::

**踩坑：** 大事务里做文件上传、循环远程调用——超时后连接占满，全站接口变慢，前端误以为「后端挂了」。

### Q12. 文件上传接口你会怎么设计，前端怎么联调？

**考察点：** multipart、大小限制、类型校验、存储路径、权限

::: details 参考答案
后端：`multipart/form-data`，限制大小与后缀/MIME；生成不可猜路径（UUID）；存本地或 OSS；库里只存 URL / objectKey。生产优先对象存储，应用节点本地盘会丢、难扩。

安全：改后缀绕过、图片马、未鉴权上传成「免费图床」——要登录 + 权限 + 类型校验（魔数优于只看扩展名）。

前端：`FormData`、进度条、取消；大文件考虑分片（点到即可）。联调注意：统一响应拦截器别把二进制当 JSON；nginx `client_max_body_size` 与 Spring `max-file-size` 要一起调。

返回：`{ url, name, size }`，前端回填表单字段，提交业务时只传文件标识。
:::

**追问链：**
1. 上传与「创建业务单据」拆成两步还是一步，怎么取舍？
2. 私有桶文件如何给前端临时访问？
3. 小程序 uploadFile 与 H5 差异你怎么适配？

::: details 追问参考答案

**1. 上传与「创建业务单据」拆成两步还是一步，怎么取舍？**

通常拆成先上传获得 `fileId`，再创建单据引用它，便于进度、重试和对象存储直传，也避免把大文件 IO 包进数据库事务。代价是会产生未绑定临时文件，因此上传记录要有 owner、状态和 TTL，定时清理；创建单据时再次校验归属并原子绑定。小文件且业务必须同步校验时可一步，但仍不能用客户端 URL 直接入库。

**2. 私有桶文件如何给前端临时访问？**

后端先校验登录身份、租户、文件归属和下载权限，再返回短时有效的预签名 URL，或由受控下载接口代理流式输出。URL 应限制有效期、方法，必要时绑定响应头，不能把对象存储永久密钥或长期公网地址给前端。高敏文件还需审计、限速和防缓存策略；链接泄露窗口无法完全消除，因此时效要与场景匹配。

**3. 小程序 uploadFile 与 H5 差异你怎么适配？**

抽象统一上传服务，参数层统一文件、业务类型和元数据，传输层分别适配小程序 `uploadFile` 的临时路径与 H5 的 `File/FormData`。两端的进度、取消、并发和响应格式能力不同，应归一化成功、错误与鉴权刷新流程。服务端保持同一 multipart 契约和权限校验，不能只根据客户端传来的 MIME 或后缀判定类型。

:::

**踩坑：** 只校验扩展名、文件直接落在可执行目录或未鉴权 GET 原图路径——安全面试一追就穿。

### Q13. Excel 导出（管理后台）前后端怎么协作才不炸？

**考察点：** 异步导出、超时、权限、与筛选条件一致

::: details 参考答案
小数据：同步导出，后端 EasyExcel / POI 写流，`Content-Disposition` 附件；前端 `blob` 下载，注意响应类型与错误 JSON 的区分（blob 里可能是错误信息）。

大数据：

1. 同样筛选条件异步任务 → Redis/DB 记任务状态 → 完成后下载链接；
2. 限流与权限：导出也要 `order:export`；
3. 字段脱敏；最大行数限制；
4. 超时：网关 60s 掐断——重活别走同步。

前端：导出按钮带当前筛选；loading；失败可读错误；禁止「前端拉取全部再 xlsx」假导出（大数据必崩、权限绕过风险）。

口述对比：百行同步、十万行异步任务，是工程判断不是组件熟练度。
:::

**追问链：**
1. 导出与列表接口 SQL 不一致（少条件）怎么验收？
2. 为什么不建议前端全量拉 JSON 再导出？
3. 导出任务堆积你怎么降级给产品？

::: details 追问参考答案

**1. 导出与列表接口 SQL 不一致（少条件）怎么验收？**

让列表与导出共享类型化 Query 和数据权限规格，避免各写一套条件。验收选择包含时间、状态、租户、软删和边界分页的固定数据集，比较导出总数、主键集合及脱敏字段，并加入契约或集成测试。导出可不受分页限制，但不能绕过筛选、排序白名单和权限；异步任务还要固化提交时的条件快照。

**2. 为什么不建议前端全量拉 JSON 再导出？**

全量 JSON 会同时占用服务端序列化、网络、浏览器内存和主线程，数据稍大就超时或崩溃；它还可能绕过后端导出权限、字段脱敏和行数限制。小规模、已在本地的数据可做便捷导出，但正式报表应由后端流式生成或异步任务处理，记录审计并提供过期下载链接，前端只负责提交条件和展示进度。

**3. 导出任务堆积你怎么降级给产品？**

先按用户和租户限制并发、行数与队列容量，超限时明确排队或拒绝。导出结果默认不跨用户复用；确需复用时，指纹必须包含用户、租户、授权范围、字段权限、脱敏规则及数据版本时间点，任一变化都重新生成。下载时重新鉴权并签发短时链接，任务状态持久化且可观测，前端展示处理中、失败原因和预计等待。

:::

**踩坑：** axios 默认按 JSON 解析，文件流被毁；或错误时 blob 解析失败只显示「下载失败」——要按 content-type 分支。

### Q14. 参数校验（Validation）你怎么做，和前端表单校验如何分工？

**考察点：** `@Valid`、分组、业务校验、错误信息回传

::: details 参考答案
后端：`spring-boot-starter-validation`，DTO 上 `@NotNull` / `@Size` / `@Email` 等，Controller `@Valid` / `@Validated`；全局异常转统一错误码，最好带字段级错误列表供表单高亮。

分工：

- **前端**：即时体验、少打无效请求；
- **后端**：安全与数据正确性的最后防线——前端可被绕过。

业务规则（库存、状态机）放 Service 抛业务异常，别全塞注解。分组校验：创建 / 更新不同规则。AI 生成代码常忘校验或校验了却返回 500——Review 必看。

口述：双重校验不是重复劳动，是体验与安全分层。
:::

**追问链：**
1. 嵌套对象、列表元素怎么校验？
2. 前端已用 Zod/异步校验，后端还要重复吗？
3. 校验失败返回 400 HTTP 还是 200+业务码，和你们统一响应如何统一？

::: details 追问参考答案

**1. 嵌套对象、列表元素怎么校验？**

父 DTO 的嵌套字段或集合上加 `@Valid` 触发级联，元素类型再声明 `@NotNull`、`@Size` 等约束；容器本身是否可空、列表长度和元素是否可空要分别表达。Controller 用 `@Valid` 或 `@Validated`，全局异常处理返回带字段路径的错误，如 `items[2].name`。复杂跨字段关系用类级约束或 Service 业务校验。

**2. 前端已用 Zod/异步校验，后端还要重复吗？**

必须。前端校验用于即时反馈和减少无效请求，但脚本、抓包重放、旧客户端都能绕过；后端校验才是数据与安全边界。可从 OpenAPI 或共享 Schema 生成部分规则减少漂移，但库存、唯一性、权限等异步业务规则必须在服务端按当前事实重验。前端异步校验通过也只是瞬时结果，提交时仍可能发生并发变化。

**3. 校验失败返回 400 HTTP 还是 200+业务码，和你们统一响应如何统一？**

两种约定都能实现，但应全局一致。更符合 HTTP 语义的是参数格式或 Bean Validation 失败返回 400，同时 body 仍用统一 `{code,message,data}`；业务状态冲突可用 409 或团队业务码。若遗留网关要求 HTTP 200，也必须用稳定非零 code。前端拦截器应同时读取状态码和 body，下载接口另按响应类型处理。

:::

**踩坑：** 只校验 query/body，路径变量与请求头里的租户 ID 不校验——越权隐患。

### D1. N+1 与慢 SQL，前后端怎么协作排查？

**考察点：** N+1、索引、Explain、接口耗时拆解

::: details 参考答案
#### 基础结论
N+1：列表查 20 条订单，循环再查用户——21 次查询。治理：join、批量 `IN` 查询后内存组装、MyBatis 延迟加载慎用。

排查协作：

1. 前端：Chrome Network 看接口总耗时、是否瀑布请求（先列表再对每行打详情——前端 N+1）；
2. 后端：日志 SQL 次数、慢查询日志、`Explain`；
3. 约定：列表接口一次返回展示所需字段，避免卡片区串行打 N 个详情。

慢 SQL：缺索引、`select *`、深度分页、函数包列导致索引失效。全栈偏前口试：能说明「我怎么用日志/监控定位是前端并发还是单 SQL 慢」，并会提合理索引与批量查，不装 DBA。

#### 原理深挖
MyBatis-Plus 分页依赖 `PaginationInnerInterceptor`，`maxLimit` 可限制单页上限；复杂 join 的 count 优化可能与列表语义不一致，要用真实 SQL 和执行计划核对。N+1 的本质是关联装配发生在循环里，查询次数随行数增长。

#### 工程场景
先用浏览器 Network 判断是否为前端逐行请求，再用 trace 关联接口、SQL 次数与耗时。列表只取展示字段，关联名称批量查询后按 id 组装；大偏移分页改游标或限制可翻页范围。

#### 反例 / 踩坑
只在本地 10 条数据上验收；把所有关联都改成大 join，导致 count 膨胀和重复行；允许前端透传排序列，既拖慢查询又带来 SQL 注入风险。

#### 资深回答模板
「我先用 Network 和 trace 定界是前端瀑布还是服务端 N+1，再用 SQL 次数、执行计划和接近生产的数据量验证。优化优先批量查与收窄字段，不把自己包装成 DBA。」
:::

#### 追问链
1. `searchCount=false` 适合什么交互？
2. 游标分页为何不适合任意跳页？
3. 批量 `IN` 很大时如何分批并保持结果顺序？

::: details 追问参考答案

**1. `searchCount=false` 适合什么交互？**

适合无限滚动、下一页、导出预取等不展示总条数的交互。MyBatis-Plus 分页默认可能发 count，大表 count 往往比列表更贵；`searchCount=false` 只查当前页。代价是不能画准确页码器，也不能用总数做伪精确进度。产品要总条数时，用缓存近似值或异步计数，并在 UI 标明约数。复杂 join 的 count 本就可能与列表语义不一致。

**2. 游标分页为何不适合任意跳页？**

游标按上一页最后一条的排序键取之后 N 条，假设顺序稳定、方向连续。跳到第 17 页没有可靠偏移，除非退化成大 `OFFSET` 或预计算断点。插入删除还会让页码语义漂移。适合时间线、消息和下拉加载；后台要跳页加总页数仍用有上限的页码分页，并限制最大偏移。排序必须是服务端白名单，保证游标字段唯一且与索引一致。

**3. 批量 `IN` 很大时如何分批并保持结果顺序？**

把 ID 列表按数据库与超时切成多批查询，结果放 Map，再按原始 ID 顺序组装。不要依赖数据库 `IN` 返回序，也不要把几千 ID 一次打进 SQL。分批可并行但要限流，失败要能按批重试。列表接口仍受页大小约束，`IN` 批只服务当前页或明确的批量任务。注意参数长度、索引命中和 SQL 日志体积。

:::

**追问链：**
1. 如何快速判断是前端瀑布还是后端 N+1？
2. MyBatis-Plus 一对多查询有什么常见坑？
3. 给产品「列表要展示 12 个关联名」时如何避免打爆？

::: details 追问参考答案

**1. 如何快速判断是前端瀑布还是后端 N+1？**

先看浏览器 Network：若列表后又由页面发出每行详情请求，是前端瀑布；若浏览器只有一个列表请求，但同一 trace 下 SQL 数量随返回行数增长，是后端 N+1。再用接口耗时、SQL 日志和 APM span 交叉确认，不能只凭总耗时猜。修复后用接近生产的数据比较请求数、SQL 数和 P95 耗时。

**2. MyBatis-Plus 一对多查询有什么常见坑？**

一对多 join 会把主表行重复展开，分页插件可能先按展开行分页，导致一页主记录变少，count 也可能膨胀。常用做法是先分页查主表 ID，再批量查子表并组装，或为 count 单写去重 SQL。MyBatis-Plus 3.5.9+ 使用分页拦截器还需显式引入版本匹配的 `mybatis-plus-jsqlparser`，并用真实 SQL 验证。

**3. 给产品「列表要展示 12 个关联名」时如何避免打爆？**

先确认哪些字段首屏必需，把可展开信息延迟到详情；必需关联名由后端按关联类型批量 `IN` 查询并用 Map 组装，或在可控基数下 join，避免前端和后端逐行查询。列表只选展示字段并限制页大小，对稳定名称可缓存。排序只能使用服务端白名单映射；按关联名排序时必须评估索引和分页语义。

:::

**踩坑：** 本地数据少看不出来，生产一放大超时——联调环境要用接近量级的数据抽检。

### D2. AI 生成的 Java 代码，你上线前的审查清单是什么？

**考察点：** 安全、越权、SQL、异常、幻觉 API

::: details 参考答案
#### 基础结论
审查清单（可直接口述）：

1. **安全**：SQL 是否字符串拼接；XSS/文件类型；密钥是否硬编码；
2. **越权**：是否仅靠前端传 `userId`；更新/删除是否校验资源归属；
3. **性能**：循环查库、无分页、`select *`、缺少索引提示；
4. **正确性**：事务是否包对；异常是否被吞；空指针路径；
5. **契约**：响应是否走统一包装；错误码是否稳定；字段名是否与前端一致；
6. **幻觉**：是否引用不存在的依赖/方法/配置项；能否编译通过；
7. **运维**：日志是否含敏感信息；配置是否区分环境。

流程：AI 出初稿 → 自己跑通单测/本地联调 → 对照清单 → 再给前端联调。叙事：AI 加速手速，责任仍在我。

#### 原理深挖
编译成功只能证明符号和类型大致成立，不能证明事务代理生效、资源归属正确或并发下无重复写。Spring 的代理边界、MyBatis 动态 SQL、序列化字段与权限注解都需要行为测试。

#### 工程场景
要求 AI 基于仓库现有 Controller、异常和 Mapper 模式生成；人工先写越权、重复提交、事务回滚和空值用例，再跑编译、测试与真实接口烟测。新增依赖必须核对官方坐标、版本和许可证。

#### 反例 / 踩坑
看到 `@Transactional`、`@PreAuthorize` 就认为安全；为让测试通过而 mock 掉鉴权和数据库；让 AI 顺手升级 Spring Boot 或 MyBatis-Plus 大版本。

#### 资深回答模板
「AI 可以补样板，我负责验证代理边界、数据权限、SQL、事务和契约。高风险路径先定义失败用例，再让生成代码接受编译、集成测试和联调三道门禁。」
:::

#### 追问链
1. 如何证明同类自调用使事务未按预期生效？
2. AI 生成的 DTO 为什么仍可能泄露字段？
3. 哪些 Java 改动应禁止自动合并？

::: details 追问参考答案

**1. 如何证明同类自调用使事务未按预期生效？**

写集成测试：外层无事务的同类方法调用带 `@Transactional` 的内层，让内层抛运行时异常，断言数据未按预期回滚。打开 SQL 日志核对事务边界。默认 JDK 代理下自调用不走代理，注解不生效；抽到独立 Bean 或自注入后再测应对调。checked exception 默认不回滚，需 `rollbackFor`。不要用纯 mock 掉数据源来证明。

**2. AI 生成的 DTO 为什么仍可能泄露字段？**

AI 常把 Entity 当 VO，或按表字段一键生成，密码哈希、内部状态、成本价、他人手机号会随 JSON 出去。Jackson 默认序列化 getter，多一个字段就多一次泄露。必须显式 VO / 投影，对照前端契约而不是表结构。测试断言响应 JSON 白名单。即使用了 MapStruct，源对象含敏感字段仍可能被映射进去。

**3. 哪些 Java 改动应禁止自动合并？**

迁移脚本、权限注解、事务边界、支付与库存、安全配置和依赖大版本禁止无人审批合并。AI 改构建坐标、改密钥配置、改网关忽略鉴权同样拦截。自动合并只适用于有测试保护的样板；涉及数据正确性和不可逆变更必须 Owner 加行为测试。禁止规则写进 CODEOWNERS 和 CI，而不是口头约定。

:::

**追问链：**
1. 举一个你真实改过的 AI 幻觉或漏洞例子（可准备）。
2. 哪些模块你不允许 AI 直接改生产？
3. 如何把清单沉淀进 Code Review / CI？

::: details 追问参考答案

**1. 举一个你真实改过的 AI 幻觉或漏洞例子（可准备）。**

例如 AI 给 Service 方法加了 `@Transactional`，却由同类方法直接调用，并声称会开启 `REQUIRES_NEW`。Spring 默认代理模式下自调用绕过代理，新事务并未生效；我把事务入口移到独立 Bean，并用集成测试验证异常后的提交结果。还补测 checked exception：默认不回滚，明确需要时配置 `rollbackFor`，AspectJ weaving 才不受该代理边界限制。

**2. 哪些模块你不允许 AI 直接改生产？**

认证授权、支付结算、数据权限、数据库迁移、密钥配置和不可逆删除都禁止无人审查直改；并发状态机、事务边界、文件上传与消息消费也必须由 Owner 评审。AI 可生成样板和测试草稿，但变更要经过最小权限检查、集成测试、迁移演练和回滚方案。风险取决于影响面与可逆性，不是代码行数。

**3. 如何把清单沉淀进 Code Review / CI？**

把高频问题变成 PR 模板与自动门禁：编译、单测、集成测试、依赖和密钥扫描、OpenAPI 契约、数据库迁移检查；CODEOWNERS 要求安全、支付等目录由对应 Owner 审批。静态规则可拦 SQL 拼接和敏感日志，事务、自调用、越权与幂等仍需行为测试。每次事故把可复现条件补成测试，而不是只加口头提醒。

:::

**踩坑：** 「能跑通 demo」就合并——漏掉数据权限与幂等，是全栈 vibe coding 最高频事故。

### D3. 微服务点到为止：为什么拆、网关对前端有什么影响？

**考察点：** 拆分动机、Gateway、路由与鉴权、环境配置

::: details 参考答案
#### 基础结论
拆分动机（够用表述）：团队边界、独立发布、热点模块扩缩——不是为拆而拆。中小业务单体 + 模块化往往更香。

对前端的影响重点在 **网关**：

1. **统一入口**：浏览器只打 `https://api.xxx.com`，网关路由到 order/user 服务；
2. **鉴权收口**：Token 校验常在网关，后端服务信任内网头（要防头被伪造的内网约定）；
3. **前缀与跨域**：CORS、路径重写（`/api/order/**`）变更会导致前端全挂；
4. **超时与限流**：网关超时短于后端，前端表现为 504；
5. **聚合**：BFF / 网关聚合可减少前端瀑布，但别把页面逻辑全塞网关。

口述：我不一定深挖 Nacos/Feign 源码，但我清楚环境（dev/test/prod）路由差异和 401 到底是网关还是服务拒绝。

#### 原理深挖
网关统一认证不等于下游自动安全：身份头必须由可信网络链路重写，外部同名头要先剥离。超时、重试和限流叠加后可能放大流量，非幂等写操作不能由网关无条件重试。

#### 工程场景
前端始终访问同一 API 域名；用 trace id 串起网关与服务日志；灰度按用户或租户稳定分桶，并保证静态资源、API 与数据库兼容窗口一致。

#### 反例 / 踩坑
前端直连服务绕过网关；网关和应用各重试 3 次形成九倍请求；只灰度前端资源却让新页面命中旧接口。

#### 资深回答模板
「我关注微服务对浏览器的可见边界：统一入口、身份传递、超时、灰度和可追踪性。框架机制由后端主导，我负责契约与联调证据闭环。」
:::

#### 追问链
1. 401、403、504 分别从哪几层定位？
2. 灰度用户刷新后为何要保持分桶稳定？
3. 网关重试的允许列表如何定义？

::: details 追问参考答案

**1. 401、403、504 分别从哪几层定位？**

401 先看网关是否验签失败、Token 过期或 audience / issuer 不匹配，再看资源服务是否二次拒绝。403 是已认证但无权限或数据越权，对权限码、资源归属和网关头是否被伪造。504 是网关等下游超时，查网关超时、服务 P99、线程池和慢 SQL，而不是前端重试。每层日志用同一 trace id。不要把三种码都映射成「请重新登录」。

**2. 灰度用户刷新后为何要保持分桶稳定？**

刷新若重新随机分桶，用户会在新旧 API、静态资源和库结构之间跳动，表现为偶现 404、字段缺失或重复提交。分桶键用 userId / 租户哈希并在 Cookie 或网关粘滞，窗口内不变。前后端和数据库兼容窗口要重叠。回滚也按同一桶撤离。不能用客户端时间或每次请求随机数当灰度。

**3. 网关重试的允许列表如何定义？**

只重试被认定安全的幂等读，或带幂等键且服务端去重的写；下单、支付、发送短信默认不重试。按方法、路径和错误类型做白名单，限定次数、超时和幂等键传递。下游 4xx 不重试，超时与 502 / 503 才考虑。应用内已有重试则网关关闭，避免乘法。名单要评审并配指标，防止全路径重试三次。

:::

**追问链：**
1. 本地前端联调多个微服务，hosts / 代理怎么配更省事？
2. 网关统一加的请求头，前端还要带什么？
3. 什么规模你建议先别拆微服务？

::: details 追问参考答案

**1. 本地前端联调多个微服务，hosts / 代理怎么配更省事？**

让前端始终请求统一相对路径 `/api`，本地由 Vite 代理到开发网关，网关再路由各服务；需要固定域名时只给网关配一条 hosts，避免前端维护多个端口。环境差异放 `.env`，但不把密钥进仓库。代理要保留或生成 trace id，并对 WebSocket、SSE 超时和 CORS 单独验证，确保本地链路接近预发。

**2. 网关统一加的请求头，前端还要带什么？**

前端只发送公开契约允许的头，如 `Authorization`、内容类型、幂等键和客户端版本；用户 ID、租户角色、权限集合等身份头应由网关在验签后覆盖生成，并先剥离外部同名头。资源服务还要校验头来自可信链路。JWT 的 `iss`、`aud` 与权限仍由服务端验证，不能把前端自报身份当授权依据。

**3. 什么规模你建议先别拆微服务？**

业务边界尚不稳定、团队人数少、发布节奏一致且单体容量有余时，优先模块化单体。微服务会增加服务发现、网关、链路追踪、数据一致性、测试和 on-call 成本；若没有独立扩缩、隔离故障或团队自治的明确收益，拆分只会把本地调用变成远程失败。先用指标证明瓶颈，再按清晰边界渐进拆。

:::

**踩坑：** 前端直连某个服务端口绕过网关——鉴权、日志、灰度全不一致，上预发才爆。

### D4. 前后端联调排障，你有没有一套方法论？

**考察点：** 分层定位、抓包、环境、契约、日志关联

::: details 参考答案
#### 基础结论
方法论（可当成口试框架）：

1. **复现**：固定环境、账号、数据；记下 requestId / 时间；
2. **定界**：浏览器 Network——状态码、耗时、请求体、响应体；先分清是前端没发对、网关拦了、还是服务业务错；
3. **对照契约**：路径、方法、字段类型、分页、错误码是否与文档一致；
4. **后端日志**：同一 requestId 看入口参数、SQL、异常栈；
5. **数据**：DB 里实际行是否符合预期（软删、权限过滤）；
6. **缓存 / 定时**：是否读到旧缓存；
7. **结论沉淀**：是契约问题、实现 bug 还是环境配置——修完补回归用例。

工具：DevTools、Apifox/Postman、后端日志、必要时候 SQL。态度：先假设自己传错，用证据说话，不甩锅。

#### 原理深挖
一次请求要有稳定关联键：入口生成或透传 trace id，响应头返回给前端，异步消息再把它写入消息属性。日志只记录必要字段并脱敏，不能把 Token、密码或完整个人信息当排障捷径。

#### 工程场景
错误报告固定包含环境、版本、账号角色、请求摘要、trace id、时间和最小复现。前端先导出 HAR 或关键请求证据，后端按同一 id 查网关、应用、SQL 和缓存链路。

#### 反例 / 踩坑
仅凭截图说「接口坏了」；日志打印整个请求对象导致凭证泄露；trace id 只在同步线程有效，进线程池或 MQ 后丢失。

#### 资深回答模板
「我先复现并拿到 trace id，用 Network 定界协议层，再沿网关、应用、SQL、缓存逐层排除。结论要能落成契约修订或回归用例，而不是一句‘环境问题’。」
:::

#### 追问链
1. trace id 与业务订单号各解决什么问题？
2. 偶现超时如何保留最小必要证据？
3. 日志脱敏后仍需排查原值怎么办？

::: details 追问参考答案

**1. trace id 与业务订单号各解决什么问题？**

trace id 串联一次调用经过网关、服务、SQL、缓存和 MQ 的技术轨迹，回答这次请求怎么走的。订单号标识业务实体全生命周期，回答这笔单经历了哪些状态。两者都要，且应互相写入日志。排障先用 trace 定界延迟和异常，再用订单号对账与补偿。不要用用户手机号当关联键，也不要把订单号误当成分布式追踪。

**2. 偶现超时如何保留最小必要证据？**

固定环境、版本、账号角色、时间、trace id、耗时分解和是否重试；采样慢请求的 SQL 数与下游 span。不要为偶现打开全量明文日志。指标看错误率与 P95 / P99，不报平均冒充稳定。能复现则保留 HAR 和最小数据集。证据服务定位，禁止把 Token、身份证整段写入日志。

**3. 日志脱敏后仍需排查原值怎么办？**

用可逆的受控通道：授权人员通过审计工单查加密库或令牌化映射，而不是把脱敏关掉。日志只留哈希或截断，原值在权限系统里限时访问，排查结束关闭权限。不能把「临时取消脱敏」变成默认配置。对支付与隐私字段，优先用订单号加 trace 在只读副本核对，而不是回放完整报文。

:::

**追问链：**
1. 「我本地是好的」你怎么推进？
2. 偶现 bug 如何抓（弱网、并发、时区）？
3. 如何用同一套方法论带新人联调？

::: details 追问参考答案

**1. 「我本地是好的」你怎么推进？**

先固定失败环境、版本、账号角色、请求参数和时间，用同一份 curl 或 HAR 在双方环境复现；比较前端构建配置、网关路由、响应头、服务版本和数据。拿 trace id 串联网关、应用、SQL、缓存日志，逐层定界。结论必须落到具体差异和回归用例，「本地正常」只能说明一套条件通过，不能否定线上证据。

**2. 偶现 bug 如何抓（弱网、并发、时区）？**

先定义最小必要证据：用户与版本、时间、trace id、请求摘要、状态迁移和耗时；在保护隐私前提下增加结构化日志、指标和 trace。再用网络节流、并发脚本、固定时钟与不同时区复现，记录随机种子和数据快照。观测要覆盖错误率、P95/P99、重试和队列积压，不能靠无限打印敏感原文。

**3. 如何用同一套方法论带新人联调？**

提供一页排障清单和标准问题模板：先复现，Network 定界，再对契约、trace、日志、数据和缓存，最后写结论与回归。带新人时让其先提交证据而非猜测，我按检查点复盘遗漏；常见案例沉淀为演练和自动化测试。方法论的目标是统一证据语言和升级路径，不是让新人机械执行命令。

:::

**踩坑：** 只看前端 console，不看 Response body；或后端改了字段名未通知，双方互相改半天。

### D5. 接口版本与兼容，前端发版不同步时你怎么扛？

**考察点：** 兼容策略、字段演进、灰度、契约测试

::: details 参考答案
#### 基础结论
现实：前端多端（后台/H5/小程序）发版窗口不同，后端不能说切就切。

策略：

1. **加字段兼容**：只增不删；废弃字段保留一段时间；
2. **枚举扩展**：前端未知枚举要有兜底展示，不能白屏；
3. **版本路径**：`/api/v2` 或 Header 版本，破坏性变更走新版本；
4. **特性开关**：后端按版本或租户开关行为；
5. **契约测试 / Apifox**：CI 校验响应形状，减少「悄悄改」。

全栈视角：你改后端时主动问「哪个端还没发」；改前端时容忍旧字段。口述体现责任感和发布意识。

#### 原理深挖
兼容不仅是 JSON 字段：鉴权 claim、分页语义、枚举、缓存 key、消息事件和导出列都可能形成跨版本契约。数据库迁移遵循 expand → migrate → contract，先扩展兼容，再迁数据，最后删除旧结构。

#### 工程场景
OpenAPI 做契约基线，消费方测试覆盖旧包；灰度期间同时观察新旧版本成功率。破坏性变更提供版本化端点和明确下线日期，未知枚举由前端降级展示并上报。

#### 反例 / 踩坑
后端先删字段再等前端上线；把状态数字改字符串却认为 JSON 仍可解析；灰度失败直接回滚应用，但数据库脚本不可逆。

#### 资深回答模板
「我把兼容窗口当发布设计的一部分：先加后删、契约测试、稳定灰度和可回滚迁移。前端要容忍未知枚举，后端要知道仍在线的客户端版本。」
:::

#### 追问链
1. 哪些数据库迁移无法靠应用回滚恢复？
2. Header 版本与 URL 版本如何取舍？
3. 如何证明旧小程序仍能消费新响应？

::: details 追问参考答案

**1. 哪些数据库迁移无法靠应用回滚恢复？**

删除列、改类型截断、破坏性约束、不可逆清洗和已执行的数据回填，应用回滚代码也救不回。应走先扩展再迁移最后收缩：先加列双写，再切读，最后才删旧列。回滚预案是向前兼容的新脚本，不是假装还原代码就能还原库。灰度失败先回滚应用，库变更必须单独评估。备份与演练是删除类变更的前提。

**2. Header 版本与 URL 版本如何取舍？**

URL 版本对网关路由、缓存键、文档和客户端可见性更直观，适合破坏性并行。Header 版本适合同一路径多小版本、减少路径爆炸，但缓存、CDN 和排障都要记住协商头。团队小、端多且要长期并行时优先 URL；内部微调可用 Header。无论哪种，都必须服务端强制校验，不能只信前端自报。

**3. 如何证明旧小程序仍能消费新响应？**

把提审或线上旧包当消费方：契约测试用旧 schema 跑新环境响应，字段只增不删、枚举可降级。体验版或线上抽旧版本账号走登录、列表、下单。监控按客户端版本看解析失败和 4xx。未知字段必须可忽略。缺证据就假设旧包会挂，而不是看新包联调通过。

:::

**追问链：**
1. 强制用户升级客户端的条件是什么？
2. GraphQL / BFF 能否缓解版本痛苦？代价是什么？
3. 数据库列改名比接口改名更危险，为什么？

::: details 追问参考答案

**1. 强制用户升级客户端的条件是什么？**

只有旧版本存在不可兼容的安全漏洞、合规要求、数据损坏风险，或维持兼容的成本已超过约定窗口时才强制升级。应先统计在线版本、发布修复版、设置灰度和截止日期，并为审核中的小程序、弱网用户准备只读或降级路径。强制升级不是替代兼容设计；后台仍需阻断危险旧协议并保留可观测的升级失败率。

**2. GraphQL / BFF 能否缓解版本痛苦？代价是什么？**

GraphQL 允许客户端按需选字段，BFF 可为不同端适配聚合与字段形状，能减少后端领域接口直接迁就多端，但都不能消除语义破坏和旧客户端存活问题。代价包括 Schema 演进、鉴权到字段、N+1、缓存、容量和额外 Owner；BFF 还可能复制业务逻辑。仍要遵循弃用窗口、契约测试和服务端授权。

**3. 数据库列改名比接口改名更危险，为什么？**

数据库列可能同时被多个应用版本、报表、任务、ORM 映射、缓存和消息流程依赖，且迁移与回滚涉及持久数据；接口改名通常还能通过版本端点并行兼容。安全做法是 expand-migrate-contract：先加新列并双写或回填，验证读取切换后再停止旧写，最后删除旧列。不能把应用回滚等同于数据库恢复。

:::

**踩坑：** 后端「顺手」把 `status` 从数字改成字符串——旧包解析失败，小程序审核中的版本全挂。

### D6. 用 Spring Boot 给管理后台做「最小可用后端」，你会怎样一周内闭环？

**考察点：** 交付切片、CRUD 闭环、鉴权、联调、AI 协作节奏

::: details 参考答案
#### 基础结论
交付切片（示意）：

1. **D1**：项目骨架、统一响应、全局异常、登录签发 JWT、用户表；
2. **D2**：业务主表 CRUD + MyBatis-Plus 分页筛选，对齐前端表格；
3. **D3**：权限码 + 一个需鉴权的写接口 + 防重复提交；
4. **D4**：上传/导出（按产品必要项）+ Validation；
5. **D5**：Redis 热点或验证码、慢查询检查、联调清单与 README。

原则：先主路径（登录→列表→详情→写操作），再边角；AI 生成样板代码，人审安全与契约；每天能给前端可联调的环境。

面试叙事：强调**闭环与边界**，不是框架全家桶展示。微服务、复杂工作流不进第一周。

#### 原理深挖
最小可用不等于省略安全底线。统一错误、DTO 校验、服务端鉴权、事务和日志属于纵向基线；Redis、MQ、微服务只有在需求证据出现时才引入，避免用基础设施掩盖业务未闭环。

#### 工程场景
以「登录 → 列表 → 编辑 → 权限拒绝 → 错误恢复」为演示切片。每天交付可调用契约和测试账号；前端可先按 OpenAPI mock，后端用接口测试独立推进，随后切真实环境。

#### 反例 / 踩坑
先搭代码生成平台、消息总线和复杂 RBAC，却没有一条真实业务路径；为赶演示把管理员账号写死；只测快乐路径不测 401、403 和重复提交。

#### 资深回答模板
「我以可演示竖切组织一周：先契约和安全基线，再完成真实 CRUD 与权限失败路径。框架选型服从需求，不用全家桶证明资历。」
:::

#### 追问链
1. 前后端并行时谁维护契约真源？
2. 哪些横切能力必须在第一条写接口前完成？
3. 如何把演示数据与生产迁移隔离？

::: details 追问参考答案

**1. 前后端并行时谁维护契约真源？**

OpenAPI 或等价 schema 是真源，由实现接口的后端更新，前端用生成类型和 mock；变更走评审，CI 做兼容检查。口头文档和「以页面为准」都会漂。并行时先冻结错误码、分页和鉴权，再分竖切。BFF 若存在，对外契约仍只有一份。演示数据不能当规范。

**2. 哪些横切能力必须在第一条写接口前完成？**

统一响应与异常、DTO 校验、JWT 的 issuer / audience 校验、服务端鉴权、请求日志与 trace，以及事务与幂等约定。没有这些，写接口会把越权和不可观测债务固化。Redis、MQ、微服务不是前置。第一条写接口就要能测 401 / 403 / 重复提交，而不是只测 200。

**3. 如何把演示数据与生产迁移隔离？**

演示用独立库或独立 schema，种子脚本与生产迁移历史分开；演示账号、密钥、支付回调地址不得进生产配置。迁移版本号和生产同一套工具，但脚本内容按环境过滤。上线检查禁止携带演示开关和固定管理员密码。回滚和备份演练只对生产副本做，不用演示库冒充。

:::

**追问链：**
1. 只有你一个人时，前后端进度怎么切避免互相等？
2. 哪三件事第一周必须手写审查不能全信 AI？
3. 如何向面试官证明「不是教程级别 CRUD」？

::: details 追问参考答案

**1. 只有你一个人时，前后端进度怎么切避免互相等？**

先定义 OpenAPI、错误码和示例数据，把工作切成登录、列表、编辑等可演示竖切。前端依据契约用 mock 完成交互，后端用接口测试独立实现；每天固定一次切真实环境，优先修契约差异。不要先写完整前端再补后端，也不要先搭全套基础设施。每个切片都包含成功、权限拒绝和失败恢复路径。

**2. 哪三件事第一周必须手写审查不能全信 AI？**

第一是身份与数据授权，确认 JWT 的可信 issuer、audience、服务端权限和资源归属；第二是事务与幂等，检查默认代理、自调用、checked exception 回滚配置及唯一约束；第三是持久化和文件边界，审查 SQL、迁移、上传类型与访问控制。AI 可补样板，但这些路径必须由人定义失败用例并验证。

**3. 如何向面试官证明「不是教程级别 CRUD」？**

展示一条端到端证据链：契约如何定、401/403 如何区分、并发重复提交怎样由幂等键和唯一约束处理、慢 SQL 怎样用 trace 与执行计划定位、上传和导出如何控权限。再说明可观测指标、故障降级和一次真实取舍。重点是能讲清失败路径、数据真源与验证结果，而不是罗列用了多少中间件。

:::

**踩坑：** 第一周沉迷搭完美权限中台与代码生成器，主业务接口还是空的——演示时没故事。

### D7. MQ 如何做到可靠投递、幂等消费与最终一致？

::: details 参考答案
#### 基础结论
MQ 工程上通常按「至少一次」假设设计：生产端确认消息被 Broker 接收，消费端业务成功后再确认；网络与确认丢失仍可能造成重投，重复消息由业务幂等消化。具体保证取决于 Broker、队列持久化与客户端配置。最终一致不是「迟早会对」，而是有状态、重试、补偿和人工兜底。

#### 原理深挖
数据库提交与发消息是两个动作，任一失败都会产生裂缝。常见做法是本地事务同时写业务表和 outbox 事件表，再由可靠任务投递；消费端用业务唯一键、去重表或状态机保证重复执行不产生第二份结果。死信队列只保存失败，不自动修复业务。

#### 工程场景
订单创建后异步发通知：事务内写订单与事件；投递程序带 `eventId` 发送；消费者先检查幂等记录，再写通知状态并确认。前端收到「已受理」后轮询、SSE 或 WebSocket 看进度，并明确处理中、失败可重试。

#### 反例 / 踩坑
先发消息后提交事务，回滚后消费者仍执行；捕获异常却确认消息导致永久丢失；无限立即重试拖垮下游；只靠前端按钮禁用保证幂等。

#### 资深回答模板
「我不承诺魔法般 exactly-once，而是用 outbox 解决提交裂缝、业务键解决重复消费、限次退避和死信承接失败，再用对账任务验证最终一致。」
:::

#### 追问链
1. 消费成功但 ACK 丢失会发生什么？
2. 幂等记录与业务写入为何要在同一事务？
3. 死信消息恢复后如何避免乱序覆盖新状态？

::: details 追问参考答案

**1. 消费成功但 ACK 丢失会发生什么？**

至少一次投递下，Broker 会重投。业务若已成功，必须靠幂等键或状态机把第二次变成空操作，否则会重复通知、重复扣款。ACK 丢失不等于业务失败，不要再执行一遍副作用。监控重投次数。outbox 与消费去重表要能解释「已处理」。前端展示以业务状态为准，不因重复消息闪烁。

**2. 幂等记录与业务写入为何要在同一事务？**

若先写业务再写去重表且中途失败，重投会再执行；若先去重再业务且业务回滚，会永久丢消息。同一本地事务提交，要么都成功要么都回滚，重投才能安全跳过或重试。跨库无法靠一个 `@Transactional` 解决，需要 outbox 或分布式约束。不要用「先查内存集合」当幂等。

**3. 死信消息恢复后如何避免乱序覆盖新状态？**

死信是旧事件，恢复前先读当前业务状态与版本。只允许单调前进：已支付不能被旧的已创建覆盖。按事件 ID 或版本号丢弃过期事件，必要时只补副作用不改主状态。恢复要限速、可观测，并先在只读对账。不要把死信队列当重放全部历史的命令日志。

:::

### D8. JWT 刷新、缓存保护与实时进度如何组成可运营链路？

::: details 参考答案
#### 基础结论
这是三个独立边界：Spring Security Resource Server 负责校验 Bearer Token；refresh 属于授权端或客户端续期流程，前端并发 401 要单飞；缓存采用 Cache-Aside 并有穿透、击穿、雪崩保护；实时通知按单向 SSE、双向 WebSocket 选型。

#### 原理深挖
JWT 至少校验签名与 `exp`、`nbf` 等时效，并按资源服务的信任配置匹配 issuer 和 audience；claim 存在但值不受信任仍必须拒绝，不能只 Base64 解码。refresh token 应轮换并支持撤销，Sa-Token 等会话方案也必须服从同一失效与权限边界。缓存空值或布隆过滤可挡穿透，热点单飞/互斥重建挡击穿，TTL 抖动和降级挡雪崩。原生 `EventSource` 是服务端到浏览器单向长连接，主动结束调用 `close()`；WebSocket 支持双向通信。

#### 工程场景
大文件导入先返回任务 id；前端用短 access token 调查询接口，刷新时共享一个 Promise；任务元数据落库，热点进度短 TTL 缓存；简单进度用 SSE，协同控制才用 WebSocket。断线重连携带最后事件 id 或重新查任务快照，日志贯穿 user、task 与 trace id。

#### 反例 / 踩坑
资源服务自行「续签」任何过期 JWT；每个 401 都并发 refresh；缓存不存在对象不设短 TTL；SSE 每次组件挂载都新建却不关闭；把 WebSocket 内存会话当唯一任务状态。

#### 资深回答模板
「认证、缓存和推送各有权威源：Token 由授权链路管理，DB 是任务事实，Redis 只加速，SSE/WebSocket 只传变化。前端负责单飞刷新、断线恢复和状态展示，后端负责鉴权、幂等与可追踪。」
:::

#### 追问链
1. refresh token 轮换如何识别重放？
2. 热点重建锁过期后旧持有者为何不能直接删新锁？
3. SSE 在 HTTP/1.1 多 Tab 下有什么连接限制？

::: details 追问参考答案

**1. refresh token 轮换如何识别重放？**

每次刷新签发新 refresh 并立刻作废旧的；若已作废的 token 再次出现，视为重放或泄露，撤销整个家族并要求重新登录。服务端存 token 家族 ID 与轮换序号，而不是只看 JWT 没过期。并发刷新要单飞，避免双端各拿到不同有效票。日志记家族撤销，不记明文 refresh。audience 与绑定设备一并校验。

**2. 热点重建锁过期后旧持有者为何不能直接删新锁？**

`SET NX EX` 的锁过期后，其他线程可能已持有新锁并写缓存。旧持有者直接删除会误删新锁，造成并发重建和脏写。删除必须核对持有者令牌后再删，或改用带版本令牌的协议。锁过期说明临界区太长，应缩短或续期，而不是到期后盲目清理。不要把「锁 key 还在」当仍拥有互斥。

**3. SSE 在 HTTP/1.1 多 Tab 下有什么连接限制？**

HTTP/1.1 对同源常有约 6 条连接上限，每个标签一条 SSE 会占满，导致后续 API 卡住。多标签应复用共享通道或页间同步，或退化为一处连接；HTTP/2 才按流协商。还要处理后台冻结和代理缓冲。不能每个组件挂载都新建事件源且不关闭。这是浏览器连接模型，不是推送协议本身的能力。

:::
