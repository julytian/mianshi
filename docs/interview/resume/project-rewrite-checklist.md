# 项目经历改写清单

项目经历不是职责集合，而是一组可验证的问题解决证据。先按“背景 → 难点 → 决策 → 行动 → 指标 → 复盘”补齐事实，再压缩成简历要点。

## 六段事实检查

### 背景

- [ ] 服务对象、业务目标和使用场景清楚。
- [ ] 说明了本人角色、参与阶段和职责边界。
- [ ] 删除客户名、内部地址、未公开金额等敏感信息。

### 难点

- [ ] 难点来自业务、技术或协作约束，不是“时间紧、任务重”。
- [ ] 能说明规模、历史包袱、端差异或风险，但没有编造数字。
- [ ] 区分项目本身复杂与本人实际负责的复杂部分。

### 决策

- [ ] 至少说明一个关键取舍及其约束。
- [ ] 能回答为什么没有选择另一个常见方案。
- [ ] 写明接受的成本以及灰度、回滚或演进路径。

### 行动

- [ ] 区分“我亲自完成”“我推动协作”和“团队共同完成”。
- [ ] 使用设计、实现、定位、推动、建立等具体动词。
- [ ] 行动与难点对应，没有突然出现无关技术词。

### 指标

- [ ] 结果有数据源、统计口径、基线、时间窗和样本范围。
- [ ] 能解释外部干扰因素，不把相关性写成因果关系。
- [ ] 没有可靠数字时，使用工单、发布记录、采用范围等可核验结果。
- [ ] 已按“可公开 / 经公司制度及有权主体明确授权、仅向指定招聘方披露 / 不可对外”记录披露级别。
- [ ] 第二级已记录授权依据、范围、指定披露对象和有效期；普通数据负责人、平台管理员或项目成员不当然具备对外授权权力。
- [ ] 明白可验证不等于允许披露，未经公司制度及有权主体明确授权的数据不进入投递版。
- [ ] 证明材料默认只记录内部系统名称、工单号或检索线索；未经明确允许，不下载、截图或转存公司材料到个人设备。
- [ ] 离职后仍遵守保密义务和原授权限制。

### 复盘

- [ ] 写明失败尝试、遗留问题或方案代价。
- [ ] 能说明后续如何改进，以及重做时会怎样选择。
- [ ] 复盘与面试叙述一致，不为了“完美故事”隐去关键事实。

## 改写示例

以下示例中的 `[占位符]` 必须替换为本人事实。数字仅能来自真实证据，不要把占位符改成猜测值。

### 1. 中后台复杂业务

**改写前**

> 负责后台管理系统开发，使用 Vue 和 Ant Design Vue 完成页面。

**改写后**

> 面向 `[业务角色/流程]` 的运营后台，负责 `[模块边界]`；针对 `[多角色权限/动态表单/复杂状态]`，在比较 `[方案 A]` 与 `[方案 B]` 后选择 `[决策]`，实现 `[关键行动]`，使 `[可验证结果]`。结果来自 `[权限审计/缺陷平台/工单]`，统计时间为 `[时间窗]`。

**为什么更好**

从技术和页面清单变成业务背景、复杂度、个人边界、取舍和结果，能判断候选人是否真正处理过复杂中后台。

**还需证据**

- [ ] 角色与权限规模的真实口径；
- [ ] 方案对比或评审记录；
- [ ] 缺陷、工单或业务验收记录；
- [ ] 本人与后端、产品的职责边界。

**最终简历版（1～2 行）**

> 负责 `[业务模块]` 的权限与动态表单方案，在 `[约束]` 下选择 `[方案]` 并完成 `[行动]`，使 `[经授权披露的结果]`。

### 2. 性能与稳定性

**改写前**

> 优化项目性能，首屏速度提升 50%。

**改写后**

> 针对 `[核心路由]` 在 `[设备/网络]` 下加载慢的问题，通过 `[真实用户监控/性能剖析]` 定位 `[瓶颈]`，采取 `[拆包/缓存/渲染优化]`；`[指标名称]` 从 `[基线]` 改善至 `[结果]`。数据来自 `[平台]`，口径为 `[P75/P95/会话率]`，时间窗为优化前后各 `[周期]`，并说明 `[版本/流量变化]` 的影响。

**为什么更好**

明确了用户场景、定位方法和统计方法，避免用单次 Lighthouse 分数或没有基线的百分比冒充线上收益。

**还需证据**

- [ ] 监控截图或可脱敏报表；
- [ ] 路由、设备、网络和分位值口径；
- [ ] 优化前后版本与时间窗；
- [ ] 灰度、回滚和异常率变化。

**最终简历版（1～2 行）**

> 通过 `[监控/剖析方法]` 定位 `[核心路由]` 的 `[瓶颈]`，实施 `[关键优化]`；`[指标]` 从 `[基线]` 改善至 `[结果]`（`[口径与时间窗]`）。

### 3. H5、uni-app 与微信小程序多端

**改写前**

> 使用 Vant 和 uni-app 开发多个移动端项目。

**改写后**

> 负责 `[业务]` 的 Vant H5 与 uni-app 编译微信小程序交付；将 `[领域类型/校验/请求]` 下沉为共享能力，把 `[授权/导航/支付]` 保留在端适配层，解决 `[端差异或弱网问题]`，最终覆盖 `[可核验端或渠道范围]`，并通过 `[发布记录/缺陷数据]` 验证稳定性。仅实际使用 Vant Weapp 时才将其列为微信小程序组件库。

**为什么更好**

体现了多端抽象边界和实际约束，而不是把“写过多个端”当成架构能力。

**还需证据**

- [ ] 真实支持的端和个人负责范围；
- [ ] 共享层与适配层代码或设计记录；
- [ ] 包体、发布或兼容问题清单；
- [ ] 渠道采用与稳定性证据。

**最终简历版（1～2 行）**

> 负责 `[业务]` 的 Vant H5 与 uni-app 编译微信小程序交付，通过共享领域能力和端适配层解决 `[差异]`，结果由 `[可披露证据]` 验证。

- [ ] 迁移和维护成本；
- [ ] 失败案例及后续治理。

**最终简历版（1～2 行）**

### 5. 微前端架构

**改写前**

**改写后**

> 面对 `[团队独立发布/技术栈并存/存量迁移]` 约束，参与或负责 `[准确职责]`；比较 `[运行时集成]` 与 `[构建时集成/保持单体]` 后，在 `[明确模块]` 采用 `[方案]`，通过 `[依赖隔离、通信契约、灰度回滚]` 控制风险，使 `[发布独立性或故障隔离结果]` 可由 `[发布记录/故障记录]` 验证。

## 压缩成简历要点

事实补齐后，每条要点可使用以下结构：

> 在 `[背景/约束]` 下，我负责 `[职责边界]`；选择 `[决策]` 并完成 `[关键行动]`，带来 `[结果]`（数据源：`[来源]`；口径：`[口径]`；时间窗：`[范围]`），同时沉淀 `[团队影响或复盘]`。

最终简历只保留每组“最终简历版”的 1～2 行，不必把六段全部展开。详细背景、证据、失败尝试和复盘放入事实母版 / 面试证据台账，不随简历投递。台账还应记录披露级别、脱敏方式和是否仅供本人复盘；第二级必须记录公司制度及有权主体的授权依据、范围、指定披露对象和有效期。若证据不足或不允许披露，先降低表述强度、脱敏或删除指标，不要补造数字。
