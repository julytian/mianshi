# 题库追问答案补全设计

## 1. 背景与目标

当前站点包含 14 个题库模块、382 道主问题。主问题均有参考答案，但约 302 处「追问 / 追问链」只给出问题，展开后约有 600 个追问缺少参考答案。

本次改造目标：

- 为 14 个题库中的全部追问补充参考答案。
- 每个追问答案控制在约 100～200 字。
- 答案能够独立回应追问，同时避免机械重复主答案。
- 保持页面可扫读，不让追问答案默认占据大量篇幅。
- 增加自动校验，防止追问漏答、错位或数量不一致。

## 2. 已确认决策

| 决策项     | 结论                                             |
| ---------- | ------------------------------------------------ |
| 覆盖范围   | 14 个题库中的全部 Q 题追问和 D 题追问链          |
| 答案深度   | 标准答案，每问约 100～200 字                     |
| 展示方式   | 每道主问题使用一个「追问参考答案」折叠区集中回答 |
| 主答案处理 | 保持现有主答案，仅在发现明确错误时修正           |
| 交付方式   | 按能力域分批补齐，每批独立校验和内容审查         |
| 发布要求   | 全量校验、构建和线上部署通过                     |

## 3. 内容格式

### 3.1 单个追问

```md
**追问：** 一个简单 CRUD 项目是否也需要四层？

::: details 追问参考答案

不需要机械套用四层。分层数量应由业务复杂度、变化频率和团队协作成本决定。简单 CRUD 可以先保持页面、业务服务和请求层三个清晰边界；当规则复用、状态协调或测试隔离需求增加时，再逐步拆出领域层。关键不是层数，而是依赖方向明确、职责可以独立变化。

:::
```

### 3.2 多个追问

```md
**追问链：**

1. 业务要首屏更快又要更多个性化，如何取舍？
2. 指标暂时拿不到基线时如何决策？
3. 哪些决策应延迟到信息更充分时？

::: details 追问参考答案

**1. 业务要首屏更快又要更多个性化，如何取舍？**

[约 100～200 字答案]

**2. 指标暂时拿不到基线时如何决策？**

[约 100～200 字答案]

**3. 哪些决策应延迟到信息更充分时？**

[约 100～200 字答案]

:::
```

### 3.3 格式约束

- 折叠标题统一使用 `::: details 追问参考答案`。
- 折叠区位于原追问或追问链之后、分隔线之前。
- 多个追问沿用原编号，答案标题与追问原文一致。
- 不在原有 `::: details 参考答案` 内嵌套新的折叠区。
- 不改变 Q / D 编号，不删除原追问，不修改站内锚点。

## 4. 答案质量标准

每个追问答案至少满足以下 3 项：

1. **直接结论：** 首句回应问题，不先堆背景。
2. **关键依据：** 说明原理、约束、协议语义或框架行为。
3. **工程落点：** 给出适用场景、判断条件、故障处理或验证方式。

根据题目需要补充：

- 方案取舍与不适用边界；
- 安全、性能、稳定性或可访问性风险；
- 指标口径和验证方法；
- 版本敏感说明；
- 最小代码或伪代码。

禁止：

- 只回答「视情况而定」。
- 简单复制主答案。
- 使用无法验证的绝对结论。
- 为凑字数加入无关背景。
- 杜撰框架 API、源码变量或默认行为。

## 6. 自动校验设计

扩展 `scripts/validate-question-bank.mjs`，增加追问答案校验：

1. 识别题目区块中的 `**追问：**` 和 `**追问链：**`。
2. 每处追问标记后必须存在一个 `::: details 追问参考答案`。
3. 折叠区必须正确闭合且内容非空。
4. 单追问必须有一个有效答案。
5. 追问链中的问题数量必须与答案标题数量一致。
6. 多追问答案标题应保留编号，并与原追问文本对应。
7. 检查重复答案标题、占位文案和明显过短答案。
8. 输出每个文件的主问题数、追问数和已回答数。

同步扩展 `scripts/validate-question-bank.test.mjs`，覆盖：

- 单追问正确匹配；
- 多追问正确匹配；
- 缺少折叠区；
- 折叠区未闭合；
- 问答数量不一致；
- 编号或文本错位；
- 空答案和占位文案；
- 代码块中的伪追问不参与统计。

## 7. 审查与验证

每批完成后执行：

```bash
pnpm docs:validate:test
MIN_TOTAL_QUESTIONS=380 MAX_TOTAL_QUESTIONS=410 EXPECTED_TOTAL_QUESTIONS=382 pnpm docs:check
```

内容审查分两层：

1. **规格审查：** 覆盖是否完整、格式是否一致、追问与答案是否一一对应。
2. **技术审查：** 技术事实、版本边界、工程场景、重复度和口述质量。

最终验收要求：

- 14 个模块的追问回答率为 100%。
- 主问题总量保持 382，不因补答改变。
- 追问问题数与答案数完全一致。
- 无空答案、占位文案、重复 Q / D 编号。
- VitePress 构建和死链检查通过。
- GitHub Pages 部署成功，并抽查核心模块线上页面。

## 8. 风险与控制

### 内容体积增长

约 600 个标准答案预计增加大量 Markdown 内容。使用折叠区减少默认页面长度，但构建产物和搜索索引仍会增长。最终检查 chunk 体积和页面加载情况。

### 批量内容重复

相近追问容易生成同质答案。每批审查时检查同模块重复，并通过「基础概念 / 故障场景 / 架构取舍」明确职责。

### 版本事实漂移

Vue、Vite、NestJS、Cursor、微前端框架和小程序能力变化较快。版本敏感答案应注明基线，并优先核对官方文档。

### 校验误判

Markdown 代码块中可能包含「追问」示例。解析逻辑必须跳过 fenced code block，并以题目区块和粗体标记为边界。
