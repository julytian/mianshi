# AI / vibe coding 面试题库

> **怎么用：** 先盖住答案，自己口述 1～2 分钟（拆任务、审查、责任边界），再点开 `参考答案` 对照补洞。本模块为**写透**：几乎每题都有追问链，建议顺着追问再练一轮。中英文术语之间请习惯留空格，口述时也建议如此。

本模块默认候选人会用 **Cursor / Claude 类工具** 做 **Vue 3 + Java Spring Boot** 同会话交付：面试官想听的不是「我会提示词」，而是**你会拆解、会审查、会负责上线质量**。

口述金句：AI 是加速器，门禁与责任仍在我；我交付的是可运行、可回滚、可解释的结果，不是聊天记录。

### Q1. 你会怎么把一个需求拆成适合 AI 逐段完成的任务，而不是丢一句「帮我做完」？

**考察点：** 任务粒度、上下文边界、验收标准、串并行

::: details 参考答案
原则：**人对齐目标与约束，AI 吃清晰切片**。拆分顺序通常是：

1. **先定契约**：接口形状、错误码、权限模型、页面状态（空/载/错/成功）——这是人和 AI 的共同真源。
2. **再定骨架**：后端包结构（Controller / Service / Mapper）、前端路由与目录、DTO/VO 命名——先让 AI 生成「空实现 + 类型」，再填肉。
3. **垂直切片优先**：例如「订单列表查询」一条竖切（表 → API → 列表页）比「先写完所有后端再写前端」更容易端到端验证。
4. **每片带验收**：输入样例、期望 JSON、页面验收点、单测名；完成一片再开下一片，避免上下文腐烂。
5. **显式非目标**：写明「不做导出 / 不做复杂工作流」，减少 AI 过度发挥。

粒度经验：单次会话适合「一个接口 + 一个页面模块」或「一个横切关注点（统一异常）」。超过这个范围就拆会话或写进任务清单让 AI 按序号执行。
:::

**追问：**
1. 产品需求很模糊时，你先让 AI 做什么，还是先做人？
2. 竖切和横切（先基础设施）怎么选？
3. 拆太碎导致上下文丢失，你怎么补？

**踩坑：** 一句话生成整站；或切片之间契约漂移（字段名前后端各写各的）。

### Q2. 你写给 AI 的提示词通常长什么样？有没有固定结构？

**考察点：** Prompt 结构、约束、示例、迭代方式

::: details 参考答案
我用相对固定的「六段式」，可短可长，但缺一段就容易飘：

1. **角色与栈**：Vue 3 + `<script setup>` + TS；Spring Boot 3 + MyBatis-Plus + MySQL；统一响应体形状贴出来。
2. **目标**：这一步要交付什么文件 / 什么行为。
3. **约束**：目录约定、命名、禁止事项（禁止改无关文件、禁止引入新重依赖、禁止在前端做权威鉴权）。
4. **上下文**：相关已有代码片段、表结构、OpenAPI 片段——只贴必要，不整仓倾倒。
5. **输出格式**：先给方案要点再改代码；或直接按文件路径输出；要求列出假设。
6. **验收**：如何自测、边界用例。

迭代方式：第一轮要骨架与假设列表 → 我确认假设 → 第二轮填实现 → 第三轮要测试与错误处理。比「一次生成完美」稳得多。

对 Java + Vue 同会话：在提示里写清**当前改哪一侧**，另一侧只给契约，避免 AI 两边同时大改却对不齐。
:::

**追问：**
1. 上下文太长被截断时，你怎么压缩？
2. 要不要让 AI「先问你 5 个问题再写」？何时有效？
3. 中文需求 + 英文代码注释，你怎么要求风格一致？

**踩坑：** 只写「按最佳实践」；或把整本需求文档糊进去却不说本步范围。

### Q3. Vue 前端和 Java Spring Boot 后端在同一次 AI 会话里协作，你怎么控场？

**考察点：** 全栈会话编排、契约同步、联调顺序

::: details 参考答案
同会话优势是契约不容易各说各话；风险是 AI 幻觉出两边「看似匹配」的假 API。控场步骤：

1. **先锁契约文档**：路径、方法、入参、响应 `{ code, message, data }`、分页 `{ list, total }`、错误码——当作会话内的 source of truth。
2. **生成顺序**：表字段 / Entity → DTO/VO → Controller+Service 骨架 → 前端 API 模块（TS 类型）→ 页面；每步用同一字段名。
3. **联调顺序**：后端先用 Postman / curl 跑通 → 前端接真实接口；不要两边都 mock 到最后一刻才发现字段不一致。
4. **会话卫生**：大改一侧时，明确「另一侧只更新类型与调用，不重构 UI」。跨会话时把契约贴回去。
5. **权限双端**：后端 `@PreAuthorize` / 权限码与前端按钮 / 路由 meta 同源列表，禁止 AI 只藏按钮。

口述：我是导演，AI 是摄影；镜头（切片）由我切，成片（上线）由我签。
:::

**追问：**
1. AI 在前端写了 `/api/order/list`，后端却生成了 `/api/orders`，你怎么系统化避免？
2. 同一会话上下文乱了，重开还是续写？
3. 数据库迁移脚本也让 AI 写吗？你怎么审？

**踩坑：** 信任「两边都生成了所以一定能通」；或让 AI 在前端硬编码 token / 权限判断当安全方案。

### Q4. 审查 AI 生成代码时，你的清单里安全和越权怎么查？

**考察点：** 安全审查、鉴权、敏感数据、前端不可信

::: details 参考答案
安全清单（前后端都看，后端是权威）：

**后端（Spring Boot）**

- 是否所有写操作与敏感读都经过认证？权限码是否与业务对象绑定（能不能改别人的 id）？
- IDOR：只校验「已登录」不够，要校验资源归属 / 数据权限。
- 入参校验（`@Valid`）、SQL 注入（是否拼接）、文件上传类型与路径穿越。
- 密码 / 密钥 / 连接串是否进仓库或进日志；异常是否把堆栈直接回给前端。
- CSRF / CORS 配置是否过宽（`*` + 带 cookie）。

**前端（Vue）**

- XSS：`v-html`、富文本、URL 跳转是否消毒。
- 敏感信息是否进 localStorage 明文、是否打进埋点。
- 路由守卫与按钮显隐只是体验，**不能**当唯一授权。
- 是否把内部管理接口暴露到错误的构建环境。

口述一句：AI 很会「做出能点的界面」，不一定会「做出不能越权的系统」。
:::

**追问：**
1. 举一个 AI 常见的「看起来有权限注解但仍可越权」例子？
2. 导出 Excel / 下载文件接口有什么特殊风险？
3. 管理后台「仅内网」能否放松鉴权？你怎么看？

**踩坑：** 只跑功能验收就上线；或看见 `@PreAuthorize` 就勾过，不测横向越权。

### Q5. 怎么发现并处理 AI「幻觉」出来的 API、配置项或依赖？

**考察点：** 幻觉识别、核实手段、依赖治理

::: details 参考答案
幻觉高发区：

- 不存在的 npm / Maven 包或错误版本 API；
- Spring 注解属性、MyBatis-Plus 方法名臆造；
- Vue Router / Pinia / Ant Design Vue 过时或错误组件 API；
- 「某某最佳实践中间件」实则不存在。

核实动作（形成肌肉记忆）：

1. **编译与类型**：`pnpm typecheck` / `mvn compile` 是第一道筛；
2. **跳进定义**：IDE 点不进去的符号高度可疑；
3. **对照官方文档或项目内已有用法**，禁止「另一个项目好像有」；
4. **锁文件与私服**：新依赖必须能解析，且说明为什么要引入；
5. **让 AI 引用依据**：要求「基于当前仓库已有封装改」，而不是凭空新造请求层。

处理：删掉幻觉调用，回到项目已有 `request` 封装 / 已有 Service 基类；必要时开短会话只做「对齐现有模式」。
:::

**追问：**
1. 类型能通过但仍是逻辑幻觉（错误业务码），怎么防？
2. AI 升级了 major 版本 API，和仓库实际版本不一致，怎么办？
3. 你如何在面试里诚实讲一次「被幻觉坑过」？

**踩坑：** 看见代码很全就合并；或关闭类型检查「先跑起来再说」。

### Q6. 什么情况下你明确不信任 AI，必须手写或人工主导？

**考察点：** 风险边界、专业判断、工具定位

::: details 参考答案
我会划红线区——AI 可以草稿，但**决策与最终实现必须人主导**：

1. **安全与合规**：鉴权模型、加密、个人信息、支付/账务状态机；
2. **并发与数据一致性**：幂等、事务边界、扣减库存等；
3. **不可逆运维**：生产数据修复脚本、权限批量变更；
4. **核心领域规则**：状态流转、计价——业务口径必须以产品/后端文档为准，不能「模型觉得合理」；
5. **性能关键路径**：若 AI 给出看似巧的缓存，必须先证伪再上；
6. **许可证不明的粘贴代码**。

信任区：样板 CRUD、表单与表格胶水、正则与格式转换初稿、测试用例草稿、文档与注释、重构时的机械搬移（仍要 CR）。

一句话：速度用在样板上，脑子用在边界上。
:::

**追问：**
1. 截止日前 AI 给出「能跑」的鉴权实现，你来不及细审，怎么办？
2. 团队新人全盘信任 AI，你作为 Lead 怎么定规范？
3. 「不信任」会不会让你丢掉效率优势？如何平衡？

**踩坑：** 两个极端——完全不用，或完全放飞；面试里吹「全自动上线」反而减分。

### Q7. 为了速度，你的 AI 辅助工作流长什么样（从需求到可演示）？

**考察点：** 节奏、工具链、反馈回路、可重复性

::: details 参考答案
一条我用来冲刺交付的闭环（Vue + Spring Boot）：

1. **10～20 分钟人工**：澄清 MVP、画出页面状态与表字段、写接口草稿（可 Markdown 表）。
2. **AI 生成后端竖切**：Entity/Mapper/Service/Controller + 统一异常已有则复用；立刻 `compile` + 本地调用。
3. **AI 生成前端 API 类型与页面**：接真实后端；同时开 ESLint/类型检查。
4. **人工审查清单**：鉴权、校验、错误码、空态、幂等按钮；改提示补洞而非手工从零重写（除非质量崩）。
5. **最小测试**：后端 1～2 个 Web 层或 Service 测试；前端关键函数单测或 E2E 烟测一条。
6. **演示包**：README 启动步骤、种子数据、已知限制列表——避免 Demo 只能在你机器上活。

提速关键不是「更会喊 AI」，而是**缩短反馈环**：每次生成后立刻编译/请求/点击，错误贴回会话修正。
:::

**追问：**
1. 没有现成统一响应体 / 请求封装时，你先让 AI 造轮子吗？
2. 工作流哪一步最不该省？
3. 和只用 Copilot 补全相比，Agent 会话式开发多了什么风险？

**踩坑：** 一直生成不运行；或演示前才第一次联调，幻觉集中爆雷。

### Q8. 面试里怎么讲「我用 AI 写的」，才显得专业而不是「不会写代码」？

**考察点：** 叙事措辞、责任归属、能力证据

::: details 参考答案
推荐叙事框架：

- **定位**：AI 是我的结对工程师，我负责规格、架构边界、审查与验收。
- **证据**：讲清你做的决策——为何这样拆表、为何权限这样设计、你抓过哪些 AI 错误。
- **对比**：同样功能若纯手写预估 X，AI 辅助用 Y，质量门禁没降。
- **避免**：不要说「我也不会，都是 AI 写的」；不要伪装完全手写若被追问细节会穿帮。
- **加分句**：我有一份审查清单；上线事故我仍按 on-call 负责；团队里我推动「AI 代码同样走 CR」。

可准备 60 秒版：用 AI 加速样板 → 人工守安全与业务规则 → 用编译/测试/联调关闭闭环 → 对结果负责。
:::

**追问：**
1. 面试官说「那你离开 AI 还能写吗？」你怎么接？
2. 现场手写题写慢了，如何不与「AI 很强」叙事打架？
3. 是否主动展示一段你改过 AI 输出的 diff 思路？

**踩坑：** 过度炫工具名；或隐瞒使用导致深挖实现细节时崩盘。

### Q9. 讲一次 AI 辅助开发的失败案例：错在哪、你怎么收的场？

**考察点：** 诚实复盘、学习能力、风险意识（行为面试）

::: details 参考答案
用 STAR 讲真失败（示例骨架，请替换为你的实事）：

- **S**：要快速做管理后台「用户禁用」+ 列表筛选，前后端同会话生成。
- **T**：当天可演示。
- **A**：AI 生成了看起来完整的 Service；前端按钮也藏了。我只测了「管理员自己的账号」，没测改其他租户用户。
- **R**：演示后发现横向越权隐患；紧急补数据权限与集成测试，推迟对外环境。
- **L**：把「越权用例」写进 AI 任务的验收标准；规定敏感写操作必须手写测试用例名再让 AI 补实现。

面试官听的是：你能发现边界、能止损、能沉淀机制——失败本身不是减分。
:::

**追问：**
1. 若已上生产才发现，你的止损顺序？
2. 失败后你会禁止团队用 AI 吗？为什么？
3. 如何把个人失败变成团队检查单？

**踩坑：** 编造「没有失败」；或把锅全推给模型，看不出你的责任。

### Q10. 团队要用 AI 编程时，你会定哪些规范，避免「每人一套野路子」？

**考察点：** 工程规范、密钥、CR、知识沉淀

::: details 参考答案
最低团队规范建议：

1. **密钥**：禁止把生产密钥、客户数据粘进提示；用脱敏样例；企业版/隐私模式按公司要求。
2. **同样走门禁**：AI 代码不享受免 CR、免测试特权；大型 AI diff 必须拆 PR。
3. **提示与契约进仓库**：常用 prompt 片段、接口约定、代码模板放 `docs/` 或内部 wiki，减少漂移。
4. **依赖引入审批**：AI 提议的新库要说明替代方案与体积/许可证。
5. **共享审查清单**：安全 / 越权 / 幻觉 API / 错误处理——CR 模板勾选。
6. **知识回流**：解决过的坑写成短文，避免每人重复付学费。

Lead 话术：鼓励用 AI 提速，用流程管风险，而不是道德说教「不许用」。
:::

**追问：**
1. 有人把半个代码库贴进公共模型，你怎么处理？
2. 规范太严导致大家偷偷用，怎么办？
3. 开源项目与闭源商业代码，提示策略有何不同？

**踩坑：** 只发一纸禁令没有替代工具；或毫无规范导致泄密与依赖地狱。

### Q11. 「对交付质量负责」在 AI 时代你怎么落地到日常动作？

**考察点：** ownership、定义完成、可观测、回滚

::: details 参考答案
负责不是口号，是可检查动作：

- **DoD（完成定义）**：代码合并 + 测试通过 + 文档/变更说明 + 可回滚 + 监控/日志要点；AI 生成不自动满足 DoD。
- **我签的名**：PR 作者是我，评审意见我响应，线上问题我值班——不说「那是 AI 写的」。
- **质量分层**：样板允许高 AI 比例；核心域提高人工比例与测试比例。
- **可观测**：关键接口与页面有错误追踪，发布后观察窗口（如 30～60 分钟）。
- **债务诚实**：AI 留下的重复代码与含糊命名，记入债务或当场清，不假装「以后重构」。

面试收束句：工具变了，**签字笔还在我手里**。
:::

**追问：**
1. 同事用 AI 写坏了你负责的模块，责任怎么分？
2. 老板只要速度不要测试，你怎么守 DoD？
3. 如何度量「AI 辅助」有没有真的提高净速度（含返工）？

**踩坑：** 把 ownership 定义成「我生成过」而不是「我验证过」；或出了事才第一次读那份代码。

### Q12. Cursor / Claude 类工具你怎么用？ Agent、Chat、Inline 各适合什么？

**考察点：** 工具实践、场景匹配、上下文管理

::: details 参考答案
按场景选模式（名称因产品而异，讲清用途即可）：

| 模式 | 适合 | 注意 |
| ---- | ---- | ---- |
| Inline / 补全 | 改函数、补类型、写样板 | 盯住是否符合项目风格 |
| Chat | 问设计、解释栈追踪、小范围重构方案 | 要贴代码与报错，避免空对空 |
| Agent / 多文件 | 竖切功能、跨 Vue+Java 多文件联动 | 必须给范围与验收；生成后立刻编译 |
| 规则 / 记忆（Rules） | 固化栈与目录约定、审查清单 | 定期更新，防止过期规范误导 |

实践技巧：

- 用规则文件写明：包管理器、Vue 风格、统一响应体、禁止事项；
- 大改用分支；随时可丢弃的实验会话不要直接在主分支硬刚；
- `@` 引用文件精准投喂，胜过「全项目你自己看」；
- 卡住时切换策略：缩小范围、提供失败日志、给正确示例各一次。

Java + Vue：可以同工作区多模块，但每次 Agent 任务写清「允许修改的路径」。
:::

**追问：**
1. Agent 改崩了无关文件，你怎么防、怎么恢复？
2. 规则写太长有副作用吗？
3. 无网 / 内网环境怎么降级工作流？

### Q13. 用 AI 生成测试时有哪些坑？你会怎样用它又不被它骗？

**考察点：** 测试有效性、断言质量、覆盖错觉

::: details 参考答案
AI 写测试的典型问题：

1. **断言太弱**：只断言 `not null` / 状态 200，测不出业务错误；
2. **与实现绑定过死**：复制实现细节，重构即红，或测私有实现而非行为；
3. **假覆盖**：分支没走到越权/边界，报告却很高；
4. **测错对象**：前端只测工具函数，不管页面契约；后端只 mock 掉所有依赖变成空气测试；
5. **数据不真实**：用的样例绕开了校验注解与权限。

正确用法：

- **人先写用例名与场景表**（正常 / 无权限 / 缺参 / 边界），再让 AI 填实现；
- 要求断言关键字段与错误码；
- 敏感路径至少一条集成测试或 API 测试走真实校验链；
- 把「AI 生成测试」也纳入 CR：专门看断言是否有牙齿；
- 变异思维：故意改坏代码，看测试会不会红——不会红就扔掉。

口述：测试的价值是**能抓住回归**，不是文件行数。
:::

**追问：**
1. 前端组件测试和 E2E，AI 更适合写哪类？为什么？
2. 如何避免为了绿而改测试去迁就错误实现？
3. 遗留无测试项目，你会让 AI 先补哪些？

**踩坑：** 合并前只有 AI 测试且全绿就安心；或删除失败测试「先让流水线通过」。

### D1. 如何用 AI 做联调排障而不变成「乱改试错」？

**考察点：** 调试方法论、证据、最小修改

::: details 参考答案
#### 基础结论
排障时 AI 容易「顺便重构」。纪律：

1. **先固定复现**：请求 URL、body、headers（脱敏）、响应、前端报错栈、后端日志时间线——整包贴给 AI。
2. **先要诊断再要补丁**：要求输出「可能原因排序 + 验证方法」，你先验证 Top1，再允许改代码。
3. **一次只改一个假设**：改完立刻复现；不行就回滚再试。
4. **区分层**：CORS、网关、JWT 过期、业务码、前端拆包错误——先定位层再让 AI 改对应侧。
5. **留下记录**：根因与防护写进 PR 描述，避免同一幻觉二次出现。

Vue 侧常见：拦截器把 `code !== 0` 当成功；Java 侧常见：全局异常把校验错误变成 500。这些要会自己判断，不能全听模型。

#### 原理深挖
模型会根据不完整证据补全故事，日志越零散，越容易给出多个互相冲突的改动。可靠流程应把「事实、假设、验证、结论」分开，并让每个补丁只对应一个已验证根因。

#### 工程场景
提供脱敏请求、trace id、前后端版本、最小复现和最近 diff；先要求故障树与验证命令。修复后补失败用例、回滚步骤和观察指标，无法复现时先加安全观测，不让 AI 猜改生产。

#### 反例 / 踩坑
把完整生产日志和 Token 粘进公共模型；同时改 CORS、拦截器和后端异常；模型说「应该好了」就停止验证。

#### 资深回答模板
「AI 负责扩展假设，我负责用证据淘汰假设。每次只验证一个根因，补丁必须被原失败用例和回归测试同时证明，生产数据先脱敏。」

#### 追问链
1. 没有复现环境时怎样安全增加证据？
2. AI 连续两次建议无效后如何重置上下文？
3. 哪些日志字段绝不能输入外部模型？
:::

**追问：**
1. 只有前端控制台红字、没有后端权限时，你怎么缩小范围？
2. AI 建议「把异常吞掉让页面不报错」，你为什么通常拒绝？
3. 生产问题能否把真实日志丢进公共 AI？边界是什么？

**踩坑：** 让 AI 连续改五处「也许相关」的代码；或用 `try/catch` 空捕获当修复。

### D2. 若让你 1～2 天用 AI 交付一个「可演示的小闭环」，你会怎么选模型与任务边界？

**考察点：** 端到端规划、MVP、风险、演示策略

::: details 参考答案
#### 基础结论
示例计划（可按面试题裁剪成你的项目）：

**目标闭环**：登录（JWT）→ 列表分页筛选 → 新建/编辑 → 权限码控制的禁用操作 → 基础错误提示。

**Day 0.5 人工**：表结构、接口表、页面草图、DoD、非目标列表。  
**Day 0.5～1 AI+人工**：后端竖切 + 编译通过 + 种子数据；前端登录与请求封装对齐。  
**Day 1～1.5**：列表与表单；权限前后端对齐；补越权与校验测试。  
**Day 1.5～2**：打磨空态/错误态、README、演示脚本；发布到测试环境；观察日志。

风险预案：鉴权复杂就先做「单角色 + 明确后续待办」；导出/统计一律不做。演示时主动说出限制，比被问穿更专业。

收束：计划体现**契约先行、竖切验证、审查清单、可演示限制透明**——这就是 AI 时代全栈偏前的 Lead 素养。

#### 原理深挖
模型选择看风险、上下文长度、工具能力、延迟和成本，不按「最强模型包办一切」。高推理模型适合拆解、架构和疑难诊断；快速模型适合机械改名、样板与测试草稿；确定性格式化交给编译器或脚本。

#### 工程场景
先由强模型审阅契约和风险，再把独立切片交给适配模型；每片限定文件和验收。Vue 与 Java 同一切片只共享 API 契约，不让模型同时重构两侧基础设施；关键鉴权和迁移由人主导。

#### 反例 / 踩坑
为省 token 把核心安全设计交给弱模型；为追求质量让昂贵模型做全仓机械格式化；只看生成速度，不计算审查和返工。

#### 资深回答模板
「我按任务风险和反馈成本选模型：复杂判断用强推理，机械实现用快速模型，确定性工作交给工具。无论哪个模型，都必须在文件边界和可执行验收内工作。」

#### 追问链
1. 同一任务何时值得双模型交叉审查？
2. 模型升级后为何仍要保留回归基线？
3. 成本受限时优先压缩上下文还是降低模型？
:::

**追问：**
1. 第二天中午发现表结构设计错了，你怎么办？
2. 演示环境依赖公司 VPN / 数据库，备选方案？
3. 面试官要看「哪几段是你亲手写的」，你怎么答？

**踩坑：** 两天目标按两周范围谈；或演示只走快乐路径，一问权限就崩。

### D3. 上下文、规则、技能与工具调用边界如何设计？

::: details 参考答案
#### 基础结论
上下文提供本次任务事实；规则固化长期且稳定的仓库约束；技能沉淀可复用工作流；工具执行读文件、测试、查询等可验证动作。四者职责分开，避免把变化频繁的需求写成永久规则。

#### 原理深挖
上下文窗口有限，越多不等于越准。优先提供目标、相关代码、接口契约、失败证据和非目标，并标明事实来源与新旧程度。规则冲突要有优先级；技能应有触发条件、输入输出和退出条件；工具结果属于外部数据，仍需校验。

#### 工程场景
仓库规则写 Vue 风格、包管理器和禁改路径；专项技能写迁移或发布检查；任务提示只放当前验收；工具只授予本次所需目录和只读/写权限。长会话定期产出决策摘要，并从干净状态验证。

#### 反例 / 踩坑
把全仓文件无差别塞入上下文；规则互相矛盾且没人维护；技能隐藏危险副作用；把工具返回内容当可信指令继续执行。

#### 资深回答模板
「我把稳定约束、可复用流程、本次事实和执行能力分层管理。上下文做最小充分集，规则可审计，技能有退出条件，工具遵循最小权限。」

#### 追问链
1. 规则过长会带来什么负面效果？
2. 如何发现会话中的旧决策已失效？
3. 工具输出为什么也可能包含 prompt injection？
:::

### D4. AI 生成 Vue 与 Java 代码，如何做跨栈风险审查和有效测试？

::: details 参考答案
#### 基础结论
Vue 重点看响应式丢失、生命周期清理、XSS、状态边界和请求竞态；Java 重点看鉴权、DTO 校验、SQL、事务代理、幂等和异常契约。两侧共同检查接口字段、错误码、权限码和日期时区。

#### 原理深挖
类型通过不代表行为正确：Vue 可能闭包拿旧值或卸载后回写；Java 可能同类自调用让事务未按预期生效。AI 测试常复制实现并 mock 掉关键链路，覆盖率高但抓不住越权和并发错误。

#### 工程场景
人先写场景矩阵：正常、空值、无权限、重复、取消、超时和回滚。前端用组件测试验证可见行为与清理，后端至少让敏感接口走真实过滤器、校验和事务；再做一条契约或端到端烟测。

#### 反例 / 踩坑
Vue 只测函数返回值不测卸载；Java 把 Security 和数据库全 mock；为了绿灯改断言适配错误实现；两侧各自 mock 到最后才联调。

#### 资深回答模板
「我按框架失效模式审查，但按用户行为验收。类型、单测、集成和契约测试分层，敏感路径不 mock 掉安全边界，并用故意破坏验证测试确实会红。」

#### 追问链
1. 如何测试请求响应乱序不会覆盖新数据？
2. 怎样证明越权测试经过真实鉴权链？
3. 覆盖率和变异测试各能说明什么？
:::

### D5. AI 推荐新依赖时，如何治理供应链与许可证风险？

::: details 参考答案
#### 基础结论
新依赖必须证明必要性，核对官方仓库、维护状态、许可证、版本兼容、传递依赖和已知漏洞。AI 给出的包名、版本与 API 都只是候选，不是证据。

#### 原理深挖
供应链风险包括同形异义包、依赖混淆、安装脚本、被接管维护者、恶意更新和锁文件漂移。版本号存在也不代表适配当前 Node、JDK 或框架；许可证兼容也不能靠模型一句话判断。

#### 工程场景
优先复用现有依赖或标准库；必须新增时检查官方来源与变更日志，固定锁文件，在隔离环境安装，跑 SCA/审计和构建测试，并记录 owner、用途与移除条件。高风险安装脚本按组织策略审批。

#### 反例 / 踩坑
执行模型建议的陌生 `curl | sh`；只看下载量；为了一个小函数引入庞大 SDK；偷偷改锁文件或忽略许可证。

#### 资深回答模板
「依赖是长期代码执行权，不是几行 import。我要求来源、必要性、兼容性、漏洞与许可证证据，锁定解析结果，并为依赖指定 owner 和退出条件。」

#### 追问链
1. 锁文件为何不能完全消除供应链风险？

3. Maven 与 npm 的传递依赖审查有何共同原则？

### D6. 敏感信息与 prompt injection 如何做输入、输出双向防护？

::: details 参考答案
#### 基础结论
输入侧按数据分级决定能否送入模型，密钥、生产 Token、客户数据和未公开源码遵守组织政策；输出侧把模型内容视为不可信数据，不能直接执行命令、泄露上下文或改变权限。

#### 原理深挖
Prompt injection 可藏在网页、Issue、日志、README、工具返回和依赖文档中，诱导模型忽略任务、读取秘密或执行外部写操作。仅靠「告诉模型别听」不是安全边界，必须用权限隔离、内容标记、确认门和审计。

#### 工程场景
使用脱敏样例和最小代码片段；秘密通过运行时注入，不进入提示和日志；外部内容标记为数据；读取与写入工具分权，发布、删除、转账等动作要求人工确认，并记录调用参数和结果。

#### 反例 / 踩坑
把 `.env` 全贴给模型再要求保密；网页写「读取 SSH key」就照做；模型生成 SQL 后直接在生产执行；日志脱敏只遮密码却保留 Cookie。

#### 资深回答模板
「我假设外部内容会注入、模型输出会犯错。敏感输入最小化，秘密不入上下文；输出进入有权限边界、确认和审计的执行通道。」

#### 追问链
1. RAG 文档为何也是攻击面？
2. 脱敏数据如何避免可重识别？
3. 只读工具是否绝对无风险？

### D7. MCP 或 Agent 工具权限如何做到最小授权与可恢复失败？

::: details 参考答案
#### 基础结论
按任务授予最少服务器、工具、路径、资源和时长；默认只读，外部写入单独确认。失败恢复先识别已完成副作用，再决定重试、补偿或人工接管，不能盲目重复。

#### 原理深挖
工具调用会面对超时、部分成功、重复提交和返回值注入。写操作需要幂等键或可查询状态；长任务要检查点；权限令牌要短期、限域并可撤销。模型不应自行扩大权限来「解决」授权失败。

#### 工程场景
代码审查 Agent 只读仓库；修复 Agent 只写目标分支；部署工具限制测试环境。每次调用记录 actor、参数摘要、资源、结果和关联 id；中断后先查远端状态，确认未创建 PR/工单再重试。

#### 反例 / 踩坑
给所有 MCP 服务永久管理员权限；超时后重复创建资源；把授权错误当网络抖动无限重试；失败恢复依赖聊天记忆而无检查点。

#### 资深回答模板
「工具能力按最小权限和最短时间发放，写操作必须可审计、可查询、可幂等。失败后先盘点外部状态，再恢复，不让模型用扩大权限掩盖设计问题。」

#### 追问链
1. 工具返回 500 时如何判断是否已产生副作用？
2. 浏览器自动化与结构化 API 哪个权限面更可控？
3. 临时凭证如何防止进入 trace 和提示？
:::

### D8. 团队如何度量 AI 净收益、治理规范，并判断何时不用 AI？

::: details 参考答案
#### 基础结论
度量净收益而非生成量：交付周期、审查时长、返工、缺陷逃逸、回滚、依赖新增和开发者体验一起看。规范要风险分级、有例外流程、定期复盘；高不确定或高后果任务可不用 AI。

#### 原理深挖
代码行数、提示次数和「AI 接受率」容易驱动错误行为。应比较同类任务基线，并区分模型时间、人类验证时间与事故成本。度量用于改进流程，不能演变成个人监控，否则团队会隐藏使用和问题。

#### 工程场景
选取样板、普通业务和高风险任务做试点；记录 lead time、返工和缺陷；把敏感数据、依赖、测试、工具权限写入门禁。需求口径未定、无法验证、生产不可逆操作、学习核心基础或沟通成本低于提示成本时，人工主导。

#### 反例 / 踩坑
以生成代码量宣布效率翻倍；要求人人使用同一模型；缺陷增加却只看 PR 速度；为了展示 AI 而把五分钟手改包装成复杂 Agent 任务。

#### 资深回答模板
「我看从需求到稳定上线的净周期，而不是生成速度。治理按风险分级，指标不考核个人；当目标不清、结果不可验证或后果不可逆时，我宁可不用 AI。」

#### 追问链
1. 如何设计不伤害团队信任的试点？
2. AI 使用率下降是否一定是坏事？
3. 哪类任务最适合作为收益基线？
:::
